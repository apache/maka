## 1. 问题背景

`E:\ggbdpq\gh\language` 是一门自制编程语言 **lang-go** 的 monorepo：

- `go/` 是 Go 参考实现（v0.7.0，git tag 已到 v0.7.0），**约 23,600 行**（实现 ~19,570 + 测试 ~4,040），**17 个 internal 包 + cmd/lang-go CLI**，**零第三方依赖**（`go.mod` 仅 `module lang-go` + `go 1.26`）。
- 语言能力：解释器 + →Go 转译 + →JS 转译**三路执行**；语义前端 = syntax（词法/解析/AST）→ semantic（解析器，E2xxx）→ types（检查器，E3xxx/E4xxx）→ HIR（脱糖）→ IR（核心中间表示）。
- 工具链面：`contract`（Agent JSON 协议）、`graph`（语义图/效果推导）、`edit`/`fix`（sha256 前置校验的安全编辑事务）、`format`（注释 100% 保留 + 幂等）、`refactor`（语义级重构）、`load`（目录即包）、`bind`（extern "go" FFI 草案）、REPL。
- 验收判据（根 README 已定）：同一 lang-go 程序，各实现三路 stdout **逐字节一致**（examples + m4 全量差分测试机械化此判定）。

根 README 已预留 `python/`、`rust/`、`typescript/` 三个移植目录（"未开始，按 YAGNI 开工时再创建"）；`docs/lang-go-v0.4-v1.0-prompts.md` 末节已有"长期多语言实现原则"（顺序 Go → Rust → TypeScript → Python；不逐行翻译；唯一必须一致的是语义/诊断/协议/一致性结果/可观察行为）。

用户诉求：**结合 lang-go 的 Go 实现，为 Rust / Python / TypeScript 各制定一套完整移植计划**，放到 `docs/plans/{rust,python,typescript}/`；不做逐步提交（用户最后一次性手动提交）。随后追加关键信息：**计划要供三个独立新会话并行开发**。

## 7. 技术方案（跨实现共性对齐点，写入 _shared.md §7）

1. **int64 回绕**：Rust `wrapping_*`；Python 每步过 `i64(x)=((x+2**63)%2**64)-2**63`；TS `BigInt.asIntN(64, …)`（int 一律 BigInt，裸 number 禁作 lang-go int）。
2. **浮点格式化 = `FormatFloat('g',-1,64)` 精确移植**：全链路唯一入口；TS 可直接复用 genjs prelude 里已写好的 JS 实现；Rust/Python 自行移植（~150 行/端）；禁用宿主默认 float 格式化。
3. **字符串码点语义**：Rust `chars()`；Python 原生；**TS 是 UTF-16 码元，必须显式码点化**（`s[i]` 禁用）。
4. **插入序 map**：Rust 手写 `Vec`+索引（不引 IndexMap）；Python dict / TS Map 原生；键相等语义照 value.go。
5. **JSON 双向 Go 语义**：jsonParse = int/float 分型 + 键排序 + null→None；jsonStringify 与 contract 输出 = Go Marshal 语义（键字母序/struct 序 + **HTML 转义** + 紧凑分隔）——宿主原生序列化都不带 HTML 转义，三端各实现一个 `gojson` 工具模块。
6. **值语义三拷贝**：struct/enum 在绑定/传参/返回三时机 copyValue（浅拷结构、内层数组/映射共享，照 value.go）。
7. **并发子集**：解释器全同步单线程，不引线程/async（TS 仅 http.get 一处异步，CLI 顶层 async 化）。
8. **prelude 原文内嵌**：GO_PRELUDE(845 行)/JS_PRELUDE(374 行) 逐字节复制为字符串常量，M5 第一件事是与 go 源文件 diff 锁死；禁止改写。
9. **gofmt 策略**：移植端不链接 go/format，发射端直接产出确定性格式；硬验收只看产物 stdout。
10. **递归深度**：统一显式上限 10000，超限报 E1001；Rust 另起 64MB 大栈线程。
11. 行尾 UTF-8+LF；CLI 只作用当前目录、usage 原文移植；退出码 1/2 口径照 cli.go。

## 10. 有效方案及原因

- **先摸底再提问**：用探索代理产出行级事实测绘（25 个包的 wc -l、测试分布、契约资产清单），使 11 个决策问题全部带推荐答案，两轮即收敛；事实性内容（版本号、行数、码表）一律自测不靠猜。
- **bug-compatible 优先于修漂移**：跨实现逐字节一致是硬验收，修上游漂移会引入联动变更（golden 再生是 Go 版职权），因此移植端照抄现状、漂移进"上游待修清单"。
- **契约与实现分离**：把"五项一致性"写成唯一硬约束，其余内部结构完全放开——这既保证验收机械可判，又让三个并行会话各自按宿主惯用法快速推进。
- **验收资产零复制**：相对路径引用 `go/` 下语料与 golden，Go 版更新时三端自动跟上；复制副本必然四份漂移。
- **里程碑同编号同门槛**：三端 M0–M9 对齐，用户可横向对比并行进度；每关有可机械执行的 Gates（golden 字节 diff、stdout diff、码表核对脚本）。
- **计划多文件化**：单文件会超 1500 行难维护；按流水线阶段拆分后，施工会话按册施工、按册验收。
- **prelude 原文内嵌 + diff 锁死测试**：生成的 Go/JS 目标代码是跨实现等价的核心，任何改写都会撕碎逐字节契约。
- **把"宿主最险的坑"前置到 M0/M1**：FormatFloat/HTML 转义（gojson）先行，码点/int64 陷阱写进各册专属注意，避免后期返工。

## 12. 踩坑经验

- **契约细节藏在实现里**：`jsonStringify` 的 HTML 转义只写在 `stdlib.go` 一行注释里（"map 键按字母序，两端确定"），不 grep 就会漏——三端原生 JSON 库全都不做 Go 式 HTML 转义。
- **"零依赖"在 Rust 有个硬缺口**：std 无 JSON、无 HTTPS 客户端；提前明确例外清单（serde/serde_json/ureq）比后期争论便宜。
- **JS 的数字地基全错**：number 是 double（int 必须 BigInt）、string 是 UTF-16（码点必须显式化）、JSON.parse 丢 int/float 分型——TS 侧三处都必须绕。
- **Python 的 `types` 包名陷阱**：包内子模块叫 `types` 会让 `import types` 语义混乱，改名 `typesys` 一劳永逸。
- **Windows 实测**：`core.autocrlf` 类问题在纯读取仓不触发，但计划已要求产出物一律 LF、文件读写显式换行策略。
- **go 工具链版本未实测**（见待验证）——计划把它列为 M0 自检项，而不是假设可用。

## 16. 可迁移到其他项目的通用经验

1. **移植 = 契约复刻，不是逐行翻译**：先把"必须逐字节一致的清单"钉死（协议/诊断码/golden/可观察行为），其余内部结构完全交给宿主惯用法。
2. **验收资产单一真值源**：测试相对路径引用原件、零副本；golden 再生只属于上游。
3. **bug-compatible 原则**：跨实现一致性 > 修上游缺陷；漂移集中登记为"上游待修清单"，两边不互相污染。
4. **数字与文本是跨语言移植的三大暗礁**：整数宽度与回绕、浮点格式化（禁用宿主默认）、字符串码元 vs 码点（JS UTF-16）、JSON 转义差异——一律做成"每端一个工具模块 + 全链路唯一入口"。
5. **探索先于提问**：行级摸底（wc -l、grep 调用面）后，问题才能自带推荐答案；事实自测、决策才问人。
6. **计划面向并行执行来设计**：多文件按阶段拆分、里程碑同编号、目录边界协议、每关可机械验收——计划本身就是施工与协作协议。
7. **外部工具链一律守卫式依赖**：缺失 skip 并明示，绝不谎报全绿；软门（如 gofmt 对齐）与硬门（stdout 逐字节）分开表述。
