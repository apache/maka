# 01 · 目标架构

## 1. 进程拓扑

```text
浏览器 ──► Vite :8888
            ├─ /api/agent/*    ─► apps/agent  :8809  (TS · createAgent)   ← 新
            ├─ /api/evidence/* ─► apps/agent  :8809                      ← 新
            └─ /api/*（其余）   ─► apps/api    :8808  (FastAPI · 任务/订单/支付)
```

- 迁移期由环境变量 `AGENT_BACKEND=ts|py` 控制前两条代理的目标，默认 `ts`；设为 `py` 时回到旧行为（回退开关）。WP9 删除该开关。
- `scripts/demo.mjs` 改为启动 3 个进程：api、agent、web。任一进程退出就拉停全部，沿用现有逻辑。
- `apps/agent` 读取与 FastAPI **相同**的环境变量：`OPENAI_API_KEY / OPENAI_PROVIDER / OPENAI_BASE_URL / OPENAI_MODEL`。启动时 `process.loadEnvFile()` 读 `.env`。没有 key 就走离线剧本。

## 2. apps/agent 分层

```text
apps/agent/
  package.json            name=@agent-hub/agent, type=module, 依赖见 ADR-0003
  src/
    server.ts             HTTP：路由、请求校验、SSE 写帧、断连中止
    agent.ts              唯一的 createAgent 装配点：模型、工具、中间件、checkpointer、系统提示词
    translate.ts          agent stream → AgentStreamEvent（出站 zod 校验、error/done 收口）
    tools.ts              search_evidence / search_catalog / present_recommendation
    data.ts               证据库、商品目录（从 Python 迁来，唯一来源）
    llm.ts                provider 表 → ChatOpenAI
    scripted-model.ts     离线策略模型（BaseChatModel 子类）
    scripts.ts            三场景剧本策略（文案与旧 agent.py 逐字一致）
    *.test.ts             node:test
```

依赖方向：`server → agent → (tools, llm, scripted-model) → data`；`translate` 只依赖 `@agent-hub/shared`。

**`translate.ts` 不 import langchain 的运行时**，只用 `AIMessageChunk.isInstance` 这类类型判断。这样它能用录制的 chunk 单测。

## 3. 一轮对话的数据流

```text
POST /api/agent/chat {message, threadId?}
  │ ChatRequest.safeParse → 422
  ▼
agent.stream({messages:[user]}, {thread_id, streamMode:['messages','custom'], signal, recursionLimit:100})
  │
  ├─ model_request ── reasoning_content ─────────────► thought（当前段追加）
  │                ── tool_call_chunk(name) ─────────► thought 新段（固定文案）
  │                ── content（前 24 字扣留）──────────► 有工具调用 → thought；否则 → token
  ├─ tools ── search_evidence  → ToolMessage(content=给模型, artifact=证据[])
  │        ── search_catalog   → ToolMessage(content=给模型, artifact=商品[])
  │        ── present_recommendation
  │             ├ 校验 evidenceIds ⊆ 本轮证据 artifact、skuIds ⊆ 本轮商品 artifact
  │             │   ✗ → throw → ToolMessage(status=error) → thought「校验未通过…」→ 模型重试
  │             └ ✓ → writer(card) → writer(evidence × n) ─► card, evidence…
  └─ 结束 ──► thought{final:true}（若未发）→ done{replyId}
     异常 ──► error{code: aborted | server | protocol}（不再发 done）
```

## 4. 关键设计决定

### 4.1 卡片是工具，不是结构化输出

- 卡片在时间线上位于"思考之后、正文之前"，后面还跟着证据。做成工具，天然得到这个顺序。
- 工具能读 `runtime.state.messages`，因此能做**因果校验**：引用的证据必须是本轮检索到的。结构化输出拿不到工具结果的来源。
- 校验失败时直接抛错。ToolNode 默认把错误包成 `ToolMessage(status:'error')` 回灌，模型会自己补检索（已验证）。

### 4.2 价格只从目录取

`present_recommendation` 只接收 `skuIds`。商品名、价格、类型、emoji 都由服务端从 `CATALOG` 填充，模型无法报价。这是后续 WP8"对话内下单"的前提。

### 4.3 开场白扣留（preamble hold-back）

真实模型常在调用工具前先说一句"我先查一下"。如果把它当正文发出去，思考区就会在工具调用前被收起，UI 段落会回跳。规则如下：

- 每次模型调用的前 `PREAMBLE = 24` 个字符先扣住；
- 同一调用里出现 `tool_call_chunk` → 这段文本记为 thought；
- 超过 24 字仍没有工具调用 → 作为 token 发出，之后直接透传；
- 正文开始后（final thought 已发），再出现的工具调用不再追加思考段。

### 4.4 错误收口

- 所有出站事件都在 `translate` 里 `AgentStreamEvent.parse`。
- 任何异常只产出**一个** `error`，且 error 与 done 互斥。
- 映射规则：
  - `AbortError` / signal 已中止 → `aborted`；
  - `ZodError` → `protocol`；
  - 限额 / 递归上限 / 上游 → `server`。
- 上游原始报错可能含 key 或 URL，只写服务端日志，不发给前端。

### 4.5 离线 = 同一张图

`ScriptedChatModel(policy)` 每次被调用时读会话消息，决定下一步：本轮还没检索证据 → 调 `search_evidence`，依此类推。它**不是**按调用次数出队，所以：

- 多轮、错误重试、中止都能确定性复现；
- E2E 测到的就是生产链路，只差 model 这一个对象。

### 4.6 限额策略（已验证）

| 中间件 | 配置 | 原因 |
|---|---|---|
| `toolCallLimitMiddleware` | `runLimit: 6, exitBehavior: 'error'` | 实测默认的 `continue` 在一步内调用全被拦截时直接结束本轮，没有正文；`end` 注入英文 AIMessage，且不在 model_request 节点 |
| `modelCallLimitMiddleware` | `runLimit: 8, exitBehavior: 'error'` | 统一由翻译层映射为中文 `error{server}` |
| `recursionLimit` | `100` | 每轮约 5 个图步数，默认 25 只够约 5 轮 |
