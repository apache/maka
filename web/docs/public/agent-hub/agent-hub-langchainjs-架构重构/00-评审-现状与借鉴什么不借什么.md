# 00 · 评审：现状、为什么这次引依赖、用什么不用什么

## 1. 现状一句话

agent-hub 的**前端协议层是长板**，智能体层是空壳：

- **长板**：zod 单一事实源、跨 chunk 安全的 SSE 解码、五事件分段渲染、证据抽屉、可信度阈值。
- **空壳**：后端"智能体"只是一次 Chat Completions 调用，外面套了一个围栏解析状态机：
  - 没有工具，也没有循环；
  - 没有记忆；
  - 证据不是模型推理出来的，而是按场景静态挂上去的。

## 2. 为什么 coding-agent 不引、agent-hub 要引

| 维度 | coding-agent | agent-hub |
|---|---|---|
| 项目卖点 | 核心零依赖、五语言同构 | 流式事件管线 + A2UI + 证据溯源的产品体验 |
| 智能体循环 | 已手写且成熟（40 轮、断尾修复、权限） | 不存在 |
| 引 langchain 的代价 | 毁掉卖点 | 4 个运行时依赖，ADR 记录即可 |
| 自己写要补的 | 只差几个钩子 | 循环、工具调用、参数校验、错误回灌、限额、记忆、摘要、中止、流式多路复用 |
| 结论 | 借语义 | **直接用 `createAgent`** |

## 3. 为什么用 TypeScript 新服务，而不是 Python 版 LangChain

1. 契约单一事实源在 `packages/shared/contracts.ts`（zod）。TS 服务可以**直接 import 同一份 schema** 做出站校验，`schemas.py` 镜像这一层就不需要再同步（A-P2-1 三处手工同步 → 两处）。
2. 已验证 Node 24 能直接加载 workspace 里导出 `.ts` 的包（strip-only），不需要构建步骤，与 `packages/shared` 现有用法一致。
3. 前端、shared、智能体都是 TS：一个人改契约，能一次改完、一次跑测。
4. 风险可控：绞杀者模式。新服务只接管两个路由，FastAPI 的任务和订单不动；切流有开关，可以随时回退。

## 4. 借什么（逐项落点）

| langchain.js 能力 | 用在哪 | 解决什么 |
|---|---|---|
| `createAgent` 循环 + ToolNode | `agent.ts` | 工具调用、错误回灌、自我修正 |
| `tool(…, { responseFormat: 'content_and_artifact' })` | `search_evidence` / `search_catalog` | 给模型看的文本，与给服务端校验用的结构化数据分开 |
| `ToolRuntime.state` / `writer` | `present_recommendation` | 读本轮检索结果做因果校验；卡片和证据经 custom 流直达前端 |
| `streamMode: ['messages','custom']` | `translate.ts` | token、reasoning、工具调用增量与卡片多路复用 |
| `MemorySaver` + `thread_id` | `agent.ts` | 多轮记忆 |
| `summarizationMiddleware` | `agent.ts` | 长对话压缩，用独立模型 |
| `modelCallLimitMiddleware` / `toolCallLimitMiddleware`（`exitBehavior:'error'`） | `agent.ts` | 防死循环与费用失控 |
| `ChatOpenAI` + `configuration.baseURL` | `llm.ts` | 四家 OpenAI 兼容厂商，替代手写 httpx |
| `BaseChatModel` 子类 | `scripted-model.ts` | 离线剧本走同一张图 |
| `fakeModel`（`langchain` 包导出） | 单元测试 | FIFO 响应，测工具与中间件分支 |
| `humanInTheLoopMiddleware` | WP8（可选） | 对话内下单前人工确认 |

## 5. 不借什么（以及原因）

| 不用 | 原因 |
|---|---|
| LangGraph 自定义 StateGraph | 一个 ReAct 循环够用；createAgent 已是图，不需要再手搭 |
| `@langchain/langgraph-sdk` / LangGraph Server / Agent Chat UI | 前端协议是本项目的卖点，不换成 LangGraph 的 thread/run 协议 |
| `streamEvents` v2 | 事件太细、体积大；`messages`+`custom` 够用且已验证 |
| `providerStrategy` / `responseFormat` 结构化输出 | 卡片是"给用户看的 UI 动作"，不是最终答案；做成工具才能和正文、证据交错，并且能校验后回灌 |
| `todoListMiddleware`、`llmToolSelectorMiddleware`、`piiMiddleware` 等 | 只有 3 个工具、单一任务，用不上 |
| LangSmith | 不引外部遥测；需要时再单独立 ADR |
| 把任务（养护方案生成）迁到 LangGraph durable execution | 现在只是定时器模拟，Python 修好重启语义就够；作为"未来选项"写进 05 |
| 持久化 checkpointer（SQLite/Postgres） | 先 `MemorySaver`，重启丢记忆已在 ADR-0005 写明；接口不变，后续可替换 |

## 6. 保留并写进规范的长板

- 五事件协议与帧格式 `event: <type>\ndata: <单行 JSON>\n\n`。
- `sse-decoder` 签名冻结；前端 store 在边界 `AgentStreamEvent.parse`。
- 金额一律用"分"；价格只信服务端。
- 证据与结论分离：卡片只带 `evidenceRefs`，证据详情走 evidence 事件或 `/api/evidence/:id`。
- 不引测试框架：`node:test` / `pytest`。
