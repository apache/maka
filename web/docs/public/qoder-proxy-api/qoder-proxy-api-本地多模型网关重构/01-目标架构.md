# 01 · 目标架构

## 1. 进程拓扑

```text
  Claude Code ──/v1/messages──────┐
  Codex ───────/v1/responses──────┤        ┌──────────── apps/gateway（单进程，零运行时依赖）────────────┐
  OpenCode ────/v1/chat/completions┤        │                                                              │
  playground（createAgent）────────┘  ───► │ server ─► protocols（入口保真）─► routing pipeline ─► providers │ ──► Qoder gateway / cli / cloudAgents
                                            │              ▲                       │   │                   │ ──► DeepSeek / Kimi / GLM …（OpenAI 兼容）
  浏览器 http://127.0.0.1:8320/ui ────────► │ admin API ───┘   RouteEventBus ◄──────┘   └─ HealthBook        │
                       ▲  /admin/events(SSE)│      │                │                                       │
                       └────────────────────┤      ▼                ▼                                       │
                                            │ config.json      usage.sqlite (node:sqlite)                   │
                                            └──────────────────────────────────────────────────────────────┘
```

- **一个进程，一个端口**（默认 `127.0.0.1:8320`）：数据面 `/v1/*`，管理面 `/admin/*`，控制台 `/ui/*`。
- 只绑回环地址。`/admin/*` 校验 admin token，并校验 `Host` / `Origin`，防 DNS rebinding（02 §3.1）。
- 下游 Key 分两类：
  - **Agent Key**：每个 Agent 一把，接入时生成，用来识别是谁发的请求；
  - **legacy `PROXY_API_KEY`**：兼容现有用法，识别为 `agent=unknown`。

依赖方向（`pnpm check` 里的 architectureCheck 强制）：
- `core` 不依赖任何人；

- `apps/gateway` 不 import `packages/contracts`，也不 import `zod`（ADR-0007）。

## 3. 一次请求的数据流

1. `server` 认证下游 Key → 得到 `agent`；读请求体（**8 MB 上限**，超限 413）。
2. `protocols/*` 把下游协议转成 `CanonicalRequest`，**保真**：工具历史、图片、thinking 签名都要保留（WP2）。
3. `routeStream(request, ctx, deps)`：
   1. 执行中间件 `beforeRequest`（默认参数、剥离某供应商不认的字段等）；
   2. `resolveTarget(alias)`：`group/<id>` → 路由组；`provider/model` 或 `QODER_MODEL_ROUTES` → 直连；其他 → 默认 provider（保留 v0.1 语义）；
   3. `plan()`：给每个成员判定 `ready / resting / skipped` 并写原因，按策略排序 → 发 `route.decision`；
   4. 逐个尝试：发 `upstream.attempt`，先**扣住**不构成内容的事件（`message.start`、`usage`）；
   5. 第一个内容事件（`text/thinking/tool.*/message.end`）到达即 **commit**，发 `upstream.firstByte`，从此原样下发；
   6. commit 前失败 → `HealthBook.failure()` 判定歇多久、能否改道 → 发 `upstream.failed`（必要时再发 `reroute`）→ 试下一个；
   7. commit 后失败 → 发 `error` 事件，不改道；
   8. 收尾 `request.end{outcome, member, ms, reroutes, usage}`。
4. 协议层先 `peekFirst()`：
   - 首事件就是 `error` → 返回真实 HTTP 状态码（429 + `Retry-After` / 502 / 504 / 400）；
   - 否则 `beginSse` 后写出。
5. `RouteEventBus` 的订阅者：`/admin/events`（控制台）、用量写入器（只消费 `request.end`）、可选日志。

## 4. 管线与 langchain middleware 的对应

| langchain v1 middleware | 网关管线 | 说明 |
|---|---|---|
| `beforeModel` | `GatewayMiddleware.beforeRequest` | 返回新请求，不原地修改 |
| `wrapModelCall` 观察 | `GatewayMiddleware.onEvent` | 只观察；抛错被吞，不影响数据面 |
| `modelFallbackMiddleware` | 路由组 + `plan()` + 改道 | 只在 commit 前；只在组内 |
| `modelCallLimitMiddleware` | `maxAttempts`（默认 3） | 一次请求最多试几个上游 |
| `modelRetryMiddleware` | **不做**同成员重试 | 同一上游立即重试大多还是失败，换成员更有效 |
| `summarizationMiddleware` / HITL | 不适用 | 网关不改内容 |

## 5. 状态与存储

| 数据 | 位置 | 格式 | 写入者 |
|---|---|---|---|
| 供应商（无 Key）、路由组、Agent 接入记录、方案 | `~/.qoder-proxy-api/config.json` | JSON；原子写（tmp + rename）；带 `version` | admin API |
| 供应商 Key、Agent Key、admin token | `~/.qoder-proxy-api/secrets.json` | JSON，权限 0600 | admin API |
| 用量 | `~/.qoder-proxy-api/usage.sqlite` | `node:sqlite`；只存元数据 | 订阅 `request.end` |
| 健康簿、会话亲和 | 内存 | — | 管线 |
| 路由事件 | 内存环形缓冲（500 条） | — | 管线 |
| Agent 配置备份 | `~/.qoder-proxy-api/backups/` | 原文件完整副本 + sha256 | 配置写入器 |

- 配置热更新：admin 写盘成功后，构建一份**新的不可变** `PipelineDeps` 快照并替换引用。在途请求继续用旧快照，健康簿和亲和表跨快照共享。
- 环境变量（`QODER_MODEL_ROUTES` 等）继续有效，并且优先于 `config.json`。界面上把来自环境变量的条目标为只读。
