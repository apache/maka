# 第 11 章 SSAP 真实代码案例精讲

## 11.1 这一章的目标

前面第 1 到第 10 章，已经把整套 React Code Review 的框架搭好了。  
但框架只有落到真实项目代码里，才会真正长成能力。

所以这一章不再讲抽象原则，而是直接围绕 SSAP 的真实代码做拆机式精讲。  
目标有三个。

第一，把你前面学到的审查框架，落到真实文件上。  
第二，把“我感觉这里不太对”升级成“我能准确命名问题、解释成因、判断后果、提出改法”。  
第三，把这些案例沉淀成你以后面试、review、重构时能直接调用的脑中地图。

这一章会集中吃透五个核心文件：

`src/components/table/index.tsx`  
`src/components/search-form/index.tsx`  
`src/components/echarts/base-chart.tsx`  
`src/pages/dashboard/index.hook.tsx`  
`src/pages/rules/config/index.hook.tsx`

这五个文件几乎覆盖了中后台 React 项目最核心的复杂度来源：

基础组件抽象。  
表格与搜索区。  
第三方重型组件。  
长 hook。  
复杂表单联动。  
异步请求。  
副作用链。  
性能与可维护性。  

你后面如果要真正精通 React 技术栈里的 code review，这一章必须反复看，直到你看到类似结构就能自动归类。

## 11.2 先给整章一个总结论

如果把 SSAP 这几个核心文件放在一起看，会发现它们不是各自独立的问题，而是共同指向同一组结构性矛盾。

第一，很多模块已经具备明显的能力复用意识，说明项目并不是毫无工程化基础。  
第二，问题主要不在不会写 React，而在复杂度增长后，边界没有继续同步收紧。  
第三，最典型的风险集中在四个层面：

状态和数据源开始变多。  
事件和副作用开始混层。  
基础组件开始承担越来越多职责。  
长 hook 开始吞掉页面边界。  

所以你读下面所有案例时，脑子里要一直记住一句话：

真正的 review 不是在挑某一行代码的毛病，而是在追踪复杂度是如何一点点长出来的。

# 案例一：`src/components/table/index.tsx`

这个文件只有 254 行，表面看不长。  
但它是整套系统里非常值钱的 review 案例，因为它是基础表格组件。一旦这里设计不稳，问题会被复制到所有接入页。

## 11.3 问题定义

这个组件同时承担了这些职责：

列表数据请求。  
loading 控制。  
分页状态维护。  
请求参数拼装。  
行选择状态管理。  
格式化列表数据。  
对外暴露 `init` 和 `refresh`。  

这意味着它已经不是一个纯展示组件，而是一个半容器型基础组件。

这种组件最值得 review，因为它的复杂度不在单点实现，而在于：

它到底该管到哪里为止。  
它哪些职责是公共能力。  
哪些职责已经逼近页面层。  

## 11.4 这个组件写得好的地方

先不要只挑问题。  
这个组件有几处写法其实是有工程意识的。

第一，它把 `init` 和 `refresh` 通过 `useImperativeHandle` 暴露给父层。  
这说明作者已经意识到表格刷新是一个可复用能力，而不是只能靠页面层自己拼请求。

第二，它把分页配置抽成了 `pagination`，用 `useCreation` 做稳定化。  
这里能看出作者知道表格分页本身是一块相对独立的能力。

第三，它提供了 `formatListFunc`。  
这个点非常关键，说明它尝试把接口原始数据和表格显示数据的转换留在可配置层，而不是硬编码死在组件内部。

第四，它把 `onLoadingStatusChange` 和 `onRowSelect` 暴露给外层。  
这说明它不是想把所有事情都吞进去，而是希望和页面层形成桥接。

所以你要学到一个很重要的 code review 习惯：

先识别作者已经做对了什么，再判断它停在哪一层。  
这样你的 review 才会像建设性的改进，不像纯否定。

## 11.5 这个组件最核心的问题

### 问题一：请求链路缺少异常闭环

当前 `fetch` 的核心结构是：

打开 loading。  
拼装 params。  
请求数据。  
回写 list 和 pageInfo。  
关闭 loading。  
清空 selectedRows。  

这个链路有一个非常典型的风险：

如果 `fetchApi` 抛异常，后面的 `setLoadingFalse()` 就走不到。  
结果就是整个表格可能长期停留在 loading。

这不是小细节，这是基础组件级故障。  
因为一旦它出问题，所有用这个表格的页面都会受影响。

高质量 review 语言应该是：

这里的 loading 生命周期没有形成异常对称闭环。当前实现默认请求成功才能关闭 loading，一旦接口抛错，公共表格组件会卡在 loading，属于基础组件级故障。建议将请求过程包裹在 try/finally 中，确保成功和失败都能回收界面状态。

### 问题二：`fetch` 闭包中引用了 `pageInfo` 和 `loading`

`fetch` 是通过 `usePersistFn` 包起来的，这会让函数引用稳定。  
但稳定引用不等于稳定逻辑。

这里要特别警惕两个问题：

一，`pageInfo` 在 `fetch` 中被直接展开再写回。  
二，`loading` 被用作请求重入保护。  

这类写法的风险在于，随着组件逻辑继续增大，闭包里到底拿到的是不是你以为的最新状态，会越来越难验证。

尤其是：

`setPageInfo({ ...pageInfo, pageNum, pageSize, count })`

这种写法虽然短期能跑，但它天然比函数式更新更脆。  
因为它依赖你在当前闭包里拿到的 `pageInfo` 足够新。

更稳的思路通常是把 `pageInfo` 的更新写成函数式，根据 prev 计算新值。  
这样可以减少闭包时序歧义。

### 问题三：参数变化重刷与分页变化重刷，共用同一请求函数，但模型没有完全收紧

这个组件已经在努力统一请求入口，这是优点。  
但它还差最后一刀。

现在的触发路径至少有三类：

初始化 `init()`。  
参数变化触发 `fetch()`。  
分页变化触发 `fetch()`。  

问题不在它们有没有共用 fetch，而在它们是否已经形成单一请求模型。

比如参数变化时，如果是分页表格，当前实现不会主动重置到第一页，而是继续用当前 `pageNum`、`pageSize`。  
这会带来一个典型场景：

用户在第 5 页。  
改了搜索条件。  
数据总量变少。  
理论上很多产品都希望回到第一页。  
但当前模型可能还停留在原页码。  

这类问题不是绝对错，而是必须在 review 里被显式讨论。  
因为它关系到参数变化在产品语义上到底算重新查询还是当前页刷新。

高质量 review 语言应该是：

当前表格已基本形成统一请求入口，但参数变化后的分页回收策略还不够显式。建议明确规定搜索条件变化是否强制回第一页，避免不同页面对同一基础组件产生行为预期差异。

### 问题四：`selectedRows` 的生命周期还可以更清晰

现在它在 `fetch` 成功后被清空。  
这是一个合理选择，但也暴露了一个问题：

`selectedRows` 到底是页面态，还是组件态。  
当前实现更像把它当成列表数据刷新后需要自动回收的局部态。  

这没错，但 reviewer 要继续往下追问：

跨页是否保留勾选。  
刷新后是否一定清空。  
批量操作后是否一定清空。  
有没有页面希望自定义这套策略。  

如果以后不同页面有不同要求，这个基础组件会面临继续吞逻辑还是向外暴露策略参数的选择。  
所以这里已经是一个典型的今天可用，未来会继续长复杂度的点。

## 11.6 这个组件的总判断

这是一个有工程化意识，但抽象边界还没有完全收紧的基础组件。

它的主要问题不是写错了 React，而是：

异常闭环不够稳。  
状态更新还带一点闭包脆弱性。  
分页和查询行为语义没有完全冻结。  
selection 生命周期未来很可能继续复杂化。  

如果让我给它下一个总评语，会是：

这是一个已经开始承担平台能力的表格组件，方向是对的，但还需要补上异常闭环、状态更新稳态化、分页语义冻结和选中态策略显式化，才能真正成为长期稳定的公共层。

# 案例二：`src/components/search-form/index.tsx`

这个文件 274 行。  
在中后台项目里，这种搜索区组件非常常见，也非常容易被低估。

因为很多人看搜索区，只看到几个输入框加一个搜索按钮。  
真正的复杂度其实在：

查询条件怎么组织。  
标签怎么生成。  
表单值和外层值怎么同步。  
children 结构和 schema 配置谁说了算。  

这个组件是整本手册里最适合讲状态与抽象边界的案例之一。

## 11.7 这个组件写得好的地方

第一，它已经有了统一搜索入口的意识。  
`onSearch(formData)` 说明它试图把搜索行为收敛成一个统一出口。

第二，它引入了 tags，把当前查询条件做成可视化展示。  
这说明作者已经意识到搜索区不仅是输入区，也是查询状态展示区。

第三，它支持 `children` 扩展搜索项。  
这说明它在努力做抽象，而不是把每个搜索条件写死。

第四，它把部分逻辑用 `useCallback` 包起来。  
这至少说明作者开始关注函数稳定性和局部复用。

这些都说明，这不是随手拼出来的代码。  
它是一个认真尝试抽公共搜索区的组件。

## 11.8 这个组件最核心的问题

### 问题一：状态太多，而且出现明显派生状态

当前组件里维护了这些状态：

`searchSelectVal`  
`tags`  
`searchData`  
`selectedChild`  
`formData`  

这五份状态里，真正需要特别警惕的是后三者。

`searchData` 是从 `children` 解析出来的。  
`selectedChild` 又是根据选中的搜索条件从 `children` 里找出来再 clone 的。  
`tags` 又是查询条件的另一种可视化投影。  

这就意味着，这个组件已经开始形成三套视角：

结构视角。  
表单值视角。  
标签展示视角。  

这类设计最危险的地方，不在当前能不能跑，而在于它会持续制造同步成本。  
只要后续再加一个动态项、联动项、复杂标签项，状态漂移风险就会上升。

高质量 review 语言应该是：

当前搜索组件同时维护 children 解析结果、选中子组件、表单值和标签态，已经出现明显的派生状态堆叠。建议逐步明确唯一查询源，并把结构解析结果与展示投影降到最少，避免后续联动场景出现状态漂移。

### 问题二：`selectedChild` 直接存 ReactNode，是一个很值得警惕的设计

这是这段代码里非常典型、也非常有讨论价值的一点。

当前逻辑是：

选中某个搜索项后。  
调用 `getChildComponent`。  
找到对应 child。  
clone 它。  
然后把 clone 后的 ReactNode 放进 `selectedChild` state。  

这类设计短期可用，但从长期维护看，有几个问题：

第一，它让 state 开始承载 UI 结果，而不只是业务事实。  
第二，它让结构变更和状态变更变得难以分离。  
第三，它会让后续 debug 很不直观，因为 state 里不再只是普通数据，而是 ReactNode。  

更稳的设计通常是：

state 只存当前选中了哪个字段。  
至于具体渲染哪个 child，由 render 阶段根据这个字段去决定。  

这就是典型的派生 UI 不要塞进 state。

### 问题三：`await setFormData(...)` 暴露了状态语义误判

这是一个特别值钱的案例。  
因为它不是写法风格问题，而是 React 状态模型理解问题。

`setState` 不是 promise。  
这里用 `await`，不会真正帮你建立你想要的时序保证。  

这类代码最危险的地方，不是它一定立刻出 bug，而是它会把错误的心智模型写进代码。  
后面别人读到时，会误以为：

这里 await 过了。  
所以下面逻辑拿到的一定是新 state。  

这在复杂表单和搜索区里，后续非常容易埋坑。

高质量 review 语言应该是：

这里把 setState 当成可等待的异步步骤，属于 React 更新语义误判。建议不要依赖 await setState 建立顺序，而应通过函数式更新、显式新值或后续由 state 驱动的 effect 来组织时序。

### 问题四：`onClickPlus` 的标签构建，已经开始承担业务规则

这个函数里做了几件事：

读取当前选择条件和值。  
校验是否已选择搜索条件。  
拼接文本。  
判断该字段是否已经被添加过。  
生成 tag。  
更新 tags。  
更新 formData。  

也就是说，这一个事件函数已经同时承担了：

输入校验。  
展示拼装。  
去重规则。  
查询参数写入。  

这类函数短期可接受，但随着规则继续增多，很容易继续膨胀。  
比如以后如果加入某些字段可重复、某些不可重复，时间范围不允许重复，多选字段要展开成多个 tag，这个函数会很快变得难维护。

所以这里的 reviewer 应该意识到：

这不是一个 bug，而是一个已经进入复杂化通道的节点。

### 问题五：搜索区抽象仍偏结构驱动，还没有真正进入 schema 驱动

当前组件的抽象方式，本质上仍然是：

把 children 当作输入结构。  
再从 children 里解析 name、label、type。  
再拼成 searchData。  
再回头 clone 组件。  

这说明它的抽象还停留在从 JSX 结构里反推配置。

这种方式的上限通常不高。  
因为一旦联动、权限、动态字段、字段分组、复杂校验再加进来，你会越来越依赖 children 解析和组件类型判断，后续复杂度会非常快地上升。

更成熟的方向，往往是转成 schema 驱动：

字段 id。  
字段名称。  
字段类型。  
字段组件。  
字段校验。  
字段联动规则。  

统一放在结构化配置里。

## 11.9 这个组件的总判断

这是一个有明显抽象意图，但抽象方式还停留在结构驱动阶段的搜索组件。

它最值得你学习的，不只是它写得哪里不对，而是：

你能从里面看见一个公共组件是怎么一步步长复杂度的。  
一开始只是 children 复用。  
然后加 tags。  
然后加选中项。  
然后加表单值。  
最后开始出现多份状态和派生 UI。  

这就是中后台项目里非常真实的复杂度生长路径。

如果让我给它一个总评，会是：

这是一个已经跨出简单复用阶段的搜索组件，但当前抽象核心还不够稳。建议尽快明确唯一查询源，回收派生 UI 状态，并逐步从 children 驱动过渡到 schema 驱动，否则后续联动和复杂搜索需求会快速推高维护成本。

# 案例三：`src/components/echarts/base-chart.tsx`

这个文件虽然只有 131 行，但它是整套项目里最典型的重型组件案例。  
它能把 React code review 中最容易被误讲成性能优化的问题，全部拉回到正确语境：

生命周期分层。  
第三方实例管理。  
事件绑定解绑。  
observer 清理。  
受控 loading。  

## 11.10 这个组件写得好的地方

第一，它已经意识到实例要缓存。  
通过 `cInstance` 保存图表实例，这是正确方向。

第二，它知道容器销毁时要 `dispose()`。  
这说明作者对第三方实例内存泄漏是有警觉的。

第三，它使用了 `ResizeObserver`。  
说明作者没有停留在简单 window resize，而开始考虑容器级响应。

第四，它把 loading 做成受控。  
这对于基础图表组件是合理抽象。

所以这不是一个完全不会写图表组件的文件。  
它是一个知道关键问题在哪里，但还没有把语义层彻底拆开的文件。

## 11.11 这个组件最核心的问题

### 问题一：实例创建、配置更新、事件绑定，被放进同一个 effect

这是整个组件最重要的问题。

当前一个 effect 同时做了：

获取或初始化实例。  
绑定 click 事件。  
调用 `setOption(options)`。  
在 cleanup 中 `dispose()`。  

而它的依赖里有 `options`。

这意味着只要 `options` 变化，这个 effect 就会重新执行。  
cleanup 会先跑。  
实例可能先被销毁。  
然后再重新初始化。  

结果是，本来只是更新配置，现在却很可能变成实例生命周期重走一遍。

这类问题经常被很多人说成“这里可以优化一下”。  
其实它已经不是简单优化问题，而是副作用语义混层。

更合理的分层通常是三段：

一，实例创建与销毁，只跟 DOM 生命周期绑定。  
二，配置更新，只负责 `setOption`。  
三，事件绑定与解绑，单独管理。  

这就是标准的第三方实例生命周期分层。

### 问题二：事件绑定存在重复绑定风险

当前代码里每次 effect 执行都会：

`cInstance.current.on('click', ...)`

但没有显式 `off`。  
如果 effect 因依赖变化多次执行，就可能重复绑定。

这里即便实例被 dispose，也仍然暴露了一个审查习惯问题：

绑定事件时，reviewer 必须立刻追问解绑策略。  
尤其在第三方实例组件里，这几乎是条件反射。

### 问题三：`debounceResize` 每次 render 都在新建

当前 `debounceResize = debounce(resize, 500)` 写在组件体里。  
这意味着每次 render 都会生成新的 debounce 函数。

这会带来两个问题：

第一，observer 中真正订阅的是哪一个 debounce 实例，不够稳定。  
第二，组件卸载时如果要 cancel debounce，也没有统一引用可以处理。  

这类问题不是必然马上炸，但它是典型的性能和资源管理细节没完全收紧。

更稳的做法通常是：

让 debounce 实例本身稳定。  
并在卸载时显式 cancel。

### 问题四：`ResizeObserver.observe(viewElem!)` 的防御性不够

这里用了非空断言。  
说明作者默认 `cDom.current` 在 effect 执行时一定存在。  
大多数时候确实是，但这类重型基础组件里，reviewer 应该更敏感：

是否存在首次 render、条件渲染切换或卸载边界问题。  

即便项目当前环境没暴露问题，这种地方也值得加一层更稳妥的保护。

## 11.12 这个组件的总判断

这是一个已经触碰到正确方向，但生命周期还没有真正分层的图表基座。

它最值得你学习的，不是 ECharts API 本身，而是：

任何第三方实例型组件，只要你把创建、更新、销毁、事件写在同一层，复杂度迟早会上来。  

如果让我给它一个总评，会是：

这是一个具备基础实例管理意识的图表组件，但当前把实例创建、配置更新和事件绑定放在同一副作用层里，导致生命周期语义不够清晰。建议优先做生命周期分层，这比单纯增加 memo 更有价值。

# 案例四：`src/pages/dashboard/index.hook.tsx`

这个文件 656 行。  
这是整套项目里最典型的长 hook 案例。

面对这种文件，最忌讳的 review 方式只有一句：

太长了，建议拆一下。

这句话没错，但几乎没有价值。  
真正高级的 review，要回答下面这些问题：

它到底长在什么地方。  
职责混在了哪几层。  
哪些状态本来只属于局部区域。  
哪些请求链已经开始互相牵连。  
应该按什么切口拆。  

## 11.13 先看这个 hook 做了什么

从当前代码看，这个 hook 至少同时承担了这些职责：

首页筛选条件管理。  
业务域和应用切换。  
折线图、饼图、柱状图数据请求。  
权限树和角色用户联动。  
行为分类 top10 用户弹窗。  
权限关联用户弹窗。  
角色关联用户弹窗。  
表格分页。  
阈值输入和失焦触发。  
系统初始化后的页面初始化。  

你一旦把这些职责列出来，就会立刻明白：

问题根本不在文件长。  
问题在于页面主逻辑、局部弹窗逻辑、图表逻辑、默认值逻辑全聚在一个边界里。

## 11.14 这个 hook 写得好的地方

第一，它有比较明确的命名习惯。  
像 `getDashboardLineData`、`getDashboardAuthPieData`、`getPermissionUserList`、`onBehaviorTopUserListOpen` 这类命名，至少让你能大致推断出函数职责。

第二，它有按图表和弹窗类型分组的意识。  
从 `userDataMap`、`selectDialogType`、各类 `onXXXOpen` 命名上能看出来。

第三，它大量使用了 `usePersistFn` 和 `useCreation`。  
虽然不能自动解决结构问题，但至少说明作者在尝试控制引用稳定性和派生值计算。

这几点说明，这个文件不是代码随便堆起来，而是有组织能力，但边界被业务持续吞掉。

## 11.15 这个 hook 最核心的问题

### 问题一：页面主视图和弹窗子视图没有真正隔离

从代码结构看，`modalVisible`、`modalData`、`selectDialogType`、`onUserListPageChange`、`handleClose` 这些都属于弹窗作用域逻辑。  
但它们与首页图表和筛选逻辑共处在一个 hook 里。

这会带来什么后果。

当你改首页筛选逻辑时，要在脑中同时考虑弹窗。  
当你改弹窗分页逻辑时，要在脑中同时看到 dashboard 其他区域。  
review 时很难快速判断某个状态到底是整页级还是局部级。

更好的拆法通常至少可以切成：

`useDashboardFilters`  
`useDashboardCharts`  
`useDashboardDialogs`

这类拆法的核心不是为了文件好看，而是为了把页面级状态和局部弹窗状态隔离开。

### 问题二：多组 effect 正在形成隐式链路

从后半段 effect 看，至少存在这些链：

权限树变化，设置默认选中权限列表。  
选中权限列表变化，请求权限饼图。  
角色数据变化，设置默认角色。  
业务域变化，重置系统默认值。  
系统值变化，触发整套统计请求。  
`modalVisible + tagList` 变化，设置默认行为分类并请求 top10。  

这类设计最危险的地方，不是其中某个 effect 错了，而是随着业务继续发展，你越来越难判断一个状态变化到底会沿着哪几条链扩散。

这就是典型的副作用链开始长出来。

### 问题三：多个异步函数里的 loading 开关没有异常对称保护

例如：

`getDashboardLineData`  
`getDashboardAuthPieData`  
`getDashboardRolePieData`

它们都大致是：

先打开 loading。  
再 await fetch。  
再关闭 loading。  

问题和 table 类似。  
如果中间请求抛异常，loading 关闭逻辑可能走不到。

这类问题单看某个函数不大，但放在 dashboard 这种首页里，用户感知会很强：

某个图表可能长期 loading。  
而且首页是高频入口，故障影响面更大。

### 问题四：局部交互可能牵动大范围状态

比如：

业务域变化会 `resetChartsData()`。  
应用变化会清空多个区域。  
角色变化会重算图表。  
行为分类切换会刷新弹窗数据。  

这类设计不一定错，但 reviewer 要特别有意识：

这个动作理论上应该影响谁，实际上影响了谁。

如果你未来发现：

改一个筛选值。  
整个 dashboard 都在重跑。  
那根因往往不是缺少 memo，而是这里的边界本来就没切清。

## 11.16 这个 hook 的总判断

这是一个业务划分意识已经存在，但作用域边界没有真正拆开的首页 hook。

它的主要问题不是单行实现，而是：

页面级逻辑和局部弹窗逻辑混在一起。  
多组 effect 形成隐式链。  
图表请求 loading 缺少异常闭环。  
状态影响范围不够局部化。  

如果让我给它一个总评，会是：

这是一个典型的中后台首页大 hook。命名和组织已有基础，但边界尚未从按功能堆在一起升级到按作用域和职责拆开。后续继续加需求时，复杂度会主要从副作用链和局部状态扩散这两处持续放大。

# 案例五：`src/pages/rules/config/index.hook.tsx`

这个文件 675 行。  
如果说 dashboard hook 代表首页联动复杂度，那这个 hook 就代表复杂表单和规则配置页复杂度。

它几乎把中后台最难 review 的部分都包含了：

新增、编辑、查看三态。  
复杂表单。  
枚举联动。  
模板注入字段。  
权限树。  
规则模板选择。  
批量配置与单个配置切换。  
采集来源和业务域联动。  

这个文件是整套手册里最适合训练你如何看复杂表单页的地方。

## 11.17 先看这个 hook 做了什么

它至少同时处理了这些事情：

路由参数解析。  
页面类型识别。  
表单默认值。  
规则详情请求。  
系统、应用、行为分类、采集来源枚举联动。  
权限树请求。  
规则模板列表请求。  
模板选中和编辑态同步。  
提交参数构造。  
初始化与卸载清理。  
多组 useEffect 联动请求。  

你一旦把这些职责列出来，就会发现一个重要事实：

这个文件不是业务复杂所以代码复杂这么简单。它还有明显的结构复杂度正在追着业务复杂度一起长。

## 11.18 这个 hook 写得好的地方

第一，它对页面类型有显式区分。  
`PAGE_TYPE.VIEW / CONFIG / ADD` 这层识别非常重要，说明作者有意识地区分三种态。

第二，它大量使用了 `useCreation` 组织派生数据。  
例如 `appName`、`systemList`、`appList`、`collectList`、`selectedTemplateList`，这说明作者知道复杂表单页面的派生数据必须显式收拢。

第三，它把大量 onChange 逻辑都做成了明确命名的回调。  
比如 `onCollectTypeChange`、`onAuditDepartmentChange`、`onApplicationChange`、`onBatchConfigurationChange`。  
这对阅读复杂表单页非常重要。

第四，它在初始化与卸载时有基本状态回收。  
这说明作者不是完全没有生命周期意识。

这些都说明，这个 hook 的作者是有明显工程能力的。  
所以 review 它时不能粗暴地说写得太乱，而要更精准地指出：它已经走到了下一轮结构收敛的节点。

## 11.19 这个 hook 最核心的问题

### 问题一：表单状态、枚举状态、模板状态、请求状态全部混在同一个 hook 边界里

这是整个文件最核心的问题。

当前 hook 同时维护：

`formData`  
`originalFormData`  
`behaviorTagList`  
`collectListByBehaviorTag`  
`originalCollectList`  
`permissionData`  
`monitorDimensionList`  
`templateList`  
`templateIds`  
`editTemplateIds`

也就是说，它既管表单事实，也管枚举缓存，也管模板选择，还管权限树。

这类设计在项目初期很常见，因为写起来顺。  
但一旦逻辑继续增长，review 成本会直线上升。

更合理的分层方向，至少可以考虑：

表单主状态。  
枚举与选项数据。  
模板选择与模板注入。  
提交参数构造。  
页面初始化与路由态。  

### 问题二：多个 onChange 回调在重置下游状态，但缺少统一状态迁移模型

比如：

`onCollectTypeChange`  
会重置一大批字段。  
还会清空行为分类、权限树、模板选中值、清除校验。

`onAuditDepartmentChange`  
会重置另一批字段。  
还会清空行为分类和权限树。

`onSystemChange`  
会重置应用、采集来源、权限。

`onApplicationChange`  
又会重置另一批字段。

这说明当前页面其实已经有一条很强的状态迁移链。  
只要上游字段变动，下游就要被系统性重置。

问题在于，这条迁移链目前是分散在多个 handler 里的。  
短期没问题，长期会越来越难验证哪一类变动应清空哪一批状态。

这类页面如果继续长，很容易走到一个节点：

任何新增联动规则，都必须在多个 handler 和多个 effect 里来回补。

### 问题三：模板动态注入字段是一个非常典型的高复杂区

当前有一段 effect：

根据 `selectedTemplateList`，动态给 `formData` 注入额外字段结构。

这类逻辑本身是合理的，因为模板就是在动态扩展表单。  
但它非常容易成为复杂度爆点。

因为 reviewer 必须继续往下问：

这些动态字段什么时候初始化。  
什么时候清空。  
模板取消选择后，旧字段是否回收。  
编辑态和新增态注入策略是否一致。  
字段值和模板列表是否可能不同步。  

也就是说，这里不是一段普通 effect。  
这里其实是动态表单 schema 系统的胚胎。  
如果不把它当成高复杂区来审查，后面就会越来越难收。

### 问题四：多组 effect 的依赖是业务正确的，但结构上已经开始形成联动网络

例如：

`formData.formatId` 变化，获取采集来源列表、模板列表。  
`formData.formatId` 变化，更新监控维度下拉列表。  
`formData.formatId + auditDepartment + configBy` 变化，获取行为分类列表。  
`formData.tagId` 变化，获取行为分类下采集来源。  
`formData.application` 变化，获取权限树。  
`selectedTemplateList` 变化，动态更新 formData。  

这些 effect 从业务上看都说得通。  
但从结构上看，它们已经构成了一张联动网。  
你现在还能读懂，是因为你刚好在聚焦这个文件。  
等过几个月需求再叠上去，这张网的维护成本会明显升高。

所以 reviewer 应该能给出比依赖写得挺全更高一级的判断：

这段代码的主要风险不在 effect 是否正确，而在 effect 网络的规模已经接近需要重新分层。

### 问题五：提交逻辑已经具备明显的参数编排层，值得单独抽离

后半段 `onSubmit` 里，会基于：

页面类型。  
单个配置还是批量配置。  
模板列表。  
statement。  
formatId。  
application。  
tagId。  

去构造最终提交参数。

这说明页面其实已经存在一套很明确的提交参数编排逻辑。  
这种逻辑放在当前 hook 里虽然还能接受，但从工程化角度，它已经够资格成为单独层次了。

因为：

它不是普通事件。  
它是一套可测试的业务编排。  

这类逻辑一旦抽离，后续 review、单测、回归成本都会下降。

## 11.20 这个 hook 的总判断

这是一个业务理解深度较高，但结构分层尚未跟上复杂度增长的复杂表单页 hook。

它最值得你学习的地方，不只是这里好多 useEffect，而是：

复杂表单页真正难的，不是表单控件，而是联动网络。  
一旦联动网络开始长，review 的核心任务就变成了把网络重新压回几条可理解的主链。

如果让我给它一个总评，会是：

这是一个典型的中后台复杂规则配置页 hook。业务建模已经相当充分，但当前复杂度主要被单一边界承接，导致枚举联动、模板注入、提交编排和页面态管理全混在一个 hook 中。建议优先按表单主状态、选项数据、模板系统、提交编排四个方向切层，这会比局部修补 effect 更有长期收益。

## 11.21 把五个案例放在一起，你应该学到什么

如果把这五个文件合在一起看，你会发现 SSAP 这套代码非常像很多真实中后台 React 项目的成长轨迹。

最开始，大家其实都知道要做一些抽象。

于是有了基础 table。  
有了公共 search-form。  
有了 base-chart。  
有了页面 hook。  

然后业务一层层加上来。

基础组件开始承接更多事情。  
搜索区开始出现多份状态。  
图表组件开始把生命周期揉到一起。  
`dashboard` hook 开始吞掉弹窗和图表逻辑。  
`rules config` hook 开始承接整张联动网。  

这就是你以后做 code review 时，最该警惕的复杂度增长方式。

它几乎不会以突然写出一段很烂的代码的方式出现。  
它更常见的样子是：

每一步都看起来挺合理。  
但累计起来，边界慢慢松了。  

所以真正高级的 reviewer，看的不是今天这行对不对，而是：

这段代码是不是正在把系统带向更难维护的方向。

## 11.22 给你的最终收口：以后怎么用这一章

这一章不是让你背五个文件。  
而是要把它们压成五类脑中原型。

### 原型一：基础表格组件原型

看到 table 组件，就先问：

请求闭环。  
分页语义。  
selection 生命周期。  
公共能力和业务污染。  

### 原型二：复杂搜索区原型

看到 search-form，就先问：

唯一查询源。  
派生状态。  
结构驱动还是 schema 驱动。  
标签和表单是否同步。  

### 原型三：第三方实例原型

看到图表、编辑器、地图，就先问：

实例创建。  
配置更新。  
事件绑定解绑。  
observer 清理。  
loading 受控。  

### 原型四：首页大 hook 原型

看到 dashboard 这类长 hook，就先问：

页面级状态。  
局部弹窗状态。  
effect 链。  
局部动作影响范围。  
是否可以按作用域拆。  

### 原型五：复杂规则配置页原型

看到 rules config 这类文件，就先问：

表单主状态。  
联动网络。  
动态 schema。  
提交编排。  
多业务态共存。

最值得先改哪一刀。  

## 11.23 本章小结

这一章最大的价值，不在于多讲了几个问题，而在于把 SSAP 的真实项目代码，彻底转译成了你的审查语言。
