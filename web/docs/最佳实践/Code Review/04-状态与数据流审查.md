# 第 4 章 状态与数据流审查

## 4.1 问题定义

状态与数据流，是 React Code Review 最核心的一章。

很多 React 代码表面上能跑，真正危险的问题却集中在状态设计里。状态一旦建错，后面的渲染、交互、副作用、异步请求、性能和维护性都会一起出问题。  
所以 review React，先看 state，不是因为 state 最显眼，而是因为它是后面一切行为的源头。

在 SSAP 这类中后台项目里，状态问题尤其容易以三种方式出现。

第一，重复状态和派生状态过多。  
第二，局部 state、props、store、表单值之间存在双数据源。  
第三，状态更新语义被误解，导致时序判断、不可变更新和依赖触发都开始失真。

这一章的任务，就是建立“状态与数据流审查”的总框架，并把它落到 SSAP 的真实代码里。

## 4.2 成因

状态问题之所以高发，原因通常有四类。

第一类，为了图快，先把能跑通的值都塞进 state。  
第二类，没有区分“真实状态”和“派生结果”。  
第三类，把 React 的 setState 语义当成同步赋值，或者当成 promise。  
第四类，页面复杂度升高后，没有及时把状态重新分层，导致状态源越来越多。

中后台项目比 demo 更容易踩这些坑，因为复杂查询区、弹窗、表格、图表、表单联动会让状态数量快速膨胀。

## 4.3 原则

做状态与数据流审查，统一遵循七条原则。

第一，单一数据源原则。一个业务事实尽量只维护一份主状态。  
第二，派生值优先计算，不优先存储。能从现有状态和 props 算出来的值，优先用计算，不额外存 state。  
第三，不可变更新原则。状态变化应通过新引用表达，避免直接修改原对象和原数组。  
第四，最小状态原则。只保留真正驱动界面的最小必要状态。  
第五，职责分层原则。局部 state、表单状态、全局 store、服务端数据要有清晰边界。  
第六，更新语义准确原则。不能把 setState 误认为同步赋值，也不能误认为它会像 promise 一样 await。  
第七，可追踪原则。状态的来源、去向和触发条件要能被 reviewer 快速追踪。

这七条原则，是后面状态类规则和案例的总纲。

## 4.4 后果

状态设计一旦出问题，最常见的后果有六种。

第一，界面显示和真实数据不一致，也就是状态漂移。  
第二，某个值改了，另一个副本没改，出现双数据源失同步。  
第三，渲染触发不稳定，局部更新行为难以预测。  
第四，effect 依赖难写，副作用容易脱钩。  
第五，问题定位很慢，因为不知道哪个才是真正的源状态。  
第六，重构成本极高，因为任何改动都可能牵动多个状态副本。

很多人以为状态问题只是“写法不好看”，实际上它会直接决定项目是否稳。

## 4.5 代码案例

这一章先用 SSAP 的三个主案例来建立感觉。

### 案例一：`src/components/search-form/index.tsx`

这个组件是状态审查最好的训练场。

从结构看，它通常同时维护多组数据：查询项配置、当前选中配置、表单值、搜索标签、选择值等。这里最应该 review 的，不是哪一个变量名好不好，而是先问：

哪些是真状态。  
哪些其实是从 children 或当前字段推导出来的派生值。  
哪些值被存成了第二份副本。  
哪些 state 的存在只是为了绕过一次计算。  

如果 `searchData` 来自 children 的解析结果，`selectedChild` 又来自当前选中项与 `searchData` 的映射，那么这两者就带有明显的派生属性。这里的风险不在“用 state 一定错”，而在“状态是否已经开始承担本可计算的职责”。

这个组件里还有一个非常有代表性的点：`await setFormData(...)` 这类写法。它揭示了一个常见误区，开发者会下意识把 setState 当成 promise，试图用 await 强行建立时序。但 React 的状态更新语义并不是这样设计的，这种写法不会真正提供你想要的顺序保证，反而会让后续阅读者误以为这里存在异步阻塞语义。

这类问题在 review 里可以这样表达：

“这里把 setState 当成了可等待的异步操作，更新语义有误判。建议把依赖后续值的逻辑改为显式使用新值、函数式更新，或将后续流程放入真正受状态驱动的 effect 与回调中。”

### 案例二：`src/components/table/index.tsx`

表格组件看起来更偏请求和分页，但它同样是状态问题高发区。

这里通常会同时出现：

loading。  
pageInfo。  
fetchParams。  
selectedRows。  
服务端列表数据。  

做 review 时，关键不是一个个变量看，而是先画数据流。

什么触发 fetch。  
fetch 完成后谁更新谁。  
pageInfo 是输入、过程态、还是输出态。  
参数变化和分页变化是否共享同一请求模型。  
selectedRows 是局部展示态，还是业务动作态。  

如果这些角色没有分清，表格会很快进入“能用但难维护”的状态。

这里还有一个特别适合写进手册的例子。`fetch` 逻辑里如果没有 `try/finally`，请求异常时 `loading` 可能无法收口。这个点经常被误以为只是请求处理问题，实际上它同样是状态管理问题，因为 `loading` 是界面状态，它的生命周期应该对异常分支同样闭合。

这类 review comment 可以这么写：

“这里的 loading 状态没有形成对称闭环。一旦 fetchApi 抛错，表格可能长期停留在 loading。建议使用 try/finally 保证界面状态无论成功失败都能回收。”

### 案例三：`src/pages/dashboard/index.hook.tsx`

长 hook 文件是状态与数据流审查的高级训练区。

你看到一个 600 多行的 hook，不要先抱怨文件长，先问三个问题：

它到底在维护多少组业务事实。  
这些事实之间有没有耦合。  
哪些状态只是为了迁就当前写法临时加出来的。  

在 dashboard 这类首页 hook 里，最容易出现的问题是：默认值、筛选条件、图表数据、弹窗状态、列表分页、权限树选中、阈值配置等全部混在一个大文件里。这个时候最该做的 review，不是盯某个 setState，而是判断状态是否已经失去分层。

换句话说，文件长本身不是问题。状态职责混杂、来源过多、依赖难追踪，才是问题。

## 4.6 解法

状态与数据流审查，建议固定成一条七步路线。

### 第一步：先找真实状态

先判断哪些值是真正驱动界面的业务事实。比如当前页码、当前选中项、服务端返回结果、表单输入值。

### 第二步：再找派生值

凡是能从 props、children、已有 state 算出来的值，都优先视为派生值候选。不要默认它值得单独存储。

### 第三步：找第二数据源

一旦同一业务事实出现两份以上表达方式，马上提高警惕。比如列表筛选值和标签值、配置数组和选中配置对象、局部 state 和 form 实例值同时描述同一事实。

### 第四步：看更新语义是否准确

这里重点扫：

有没有直接改对象或数组。  
有没有把 setState 误当同步语句。  
有没有把 setState 误当 promise。  
有没有依赖旧值却没用函数式更新。  

### 第五步：看职责边界是否清楚

判断局部 state、全局 store、表单实例、服务端数据四者有没有越界。尤其在复杂页面里，一定要避免“局部 state 存一份，表单实例也存一份，接口返回里再来一份”。

### 第六步：看是否影响后续 effect 和请求链路

状态一旦建得混乱，effect 依赖就会越来越难写。每看到多份状态副本，都要顺手问一句：后续副作用还能写得稳吗。

### 第七步：最后给出最小重构路径

高级 review 不只是指出“状态太多了”，还要给可执行建议。

例如：

先删掉明显的派生 state。  
把状态源统一到 form 实例或单一对象。  
把查询条件和展示标签拆开职责。  
对依赖旧值的更新改用函数式写法。  
把长 hook 中不同职责的 state 提炼到子 hook。  

## 4.7 快速定位

以后你看任何 React 代码里的状态问题，先用这组问题做快速定位。

这个值是真状态，还是派生结果。  
同一业务事实有没有两份以上副本。  
这个状态是谁创建的，谁消费的，谁触发更新的。  
更新时是不是依赖旧值。  
有没有直接修改引用类型。  
有没有把 setState 理解错。  
这个状态是否会让 effect 更难写。  

如果这七问走完，你大概率已经能快速锁定大部分状态类问题。

## 4.8 本章小结

状态与数据流，是整本手册最重要的一章。因为后面的事件、effect、异步、性能，本质上都建立在状态设计之上。

这一章你要真正掌握的，不是“少用 state”这种空话，而是三件事。

第一，学会区分真实状态和派生值。  
第二，学会识别双数据源和状态语义误判。  
第三，学会把状态问题翻译成 review 语言和重构路径。

当你能稳定做到这三点时，React Code Review 才真正开始进入系统化阶段。
