# 第 5 章 列表、表格与搜索区审查

## 5.1 问题定义

在 React 中后台项目里，列表、表格与搜索区，是最容易“看起来没问题，实际上问题很多”的区域。

原因很简单。它们往往同时承载了几类职责：

一，数据展示。  
二，查询筛选。  
三，分页切换。  
四，行选择与批量操作。  
五，弹窗联动。  
六，请求触发与参数管理。  

一旦这些职责被揉在一起，代码虽然还能跑，但 review 难度会快速上升。很多线上问题也不是来自复杂算法，而是来自列表页这种高频场景里的设计松动。

所以这一章的核心任务，是建立一套针对“列表、表格与搜索区”的专项审查框架。目标不是只会看有没有 `key`，而是要能系统判断：

这个列表页的数据流是否清晰。  
这个表格基础组件是否职责过重。  
这个搜索区是否出现了双数据源。  
分页、筛选、排序、勾选、批量操作是否形成了稳定模型。  
哪些问题属于功能缺陷，哪些问题属于长期维护风险。  

---

## 5.2 成因

列表、表格与搜索区之所以容易成为问题高发区，根因通常有六类。

第一，展示层和请求层耦合过深。  
组件一边负责 UI，一边直接管理 fetch、分页、参数拼装、选中态和异常处理，导致公共组件越来越重。

第二，查询条件没有单一来源。  
同一份查询事实，既存在表单里，也存在 state 里，还可能被转换成 tags 或 params 再存一份。

第三，分页、筛选、排序、搜索词没有统一请求模型。  
代码里可能看起来都能触发刷新，但触发语义不一致，后续维护非常痛苦。

第四，基础表格组件承担了过多业务语义。  
本来应该只做通用展示与交互桥接，却逐渐演变成“半业务容器”。

第五，搜索区习惯用“堆 state”的方式扩展。  
每加一个查询项、多选项、标签项，就多加一份状态，最后数据流开始失控。

第六，列表页因为太常见，容易被低估。  
大家默认“这就是普通 CRUD 页面”，于是前期不做设计，后期问题一起爆出来。

这几个成因，在 SSAP 这种中后台项目里非常典型。因为业务页面多、表格多、查询区复杂、配置项多，天然容易堆出复杂度。

---

## 5.3 原则

列表、表格与搜索区审查，统一遵循八条原则。

第一，查询条件单一来源原则。  
一组查询条件只应有一个真正可信的源头。可以是表单实例，可以是统一 queryState，但不要同时维护多份。

第二，请求模型统一原则。  
初始化、翻页、筛选、重置、排序、批量操作后的刷新，最好走同一套请求入口和参数模型。

第三，基础组件低业务耦合原则。  
公共 Table 组件应尽量只关心展示能力、事件透传、基础状态桥接，避免吞入太多业务规则。

第四，分页语义清晰原则。  
当前页、页大小、总数、查询参数，要能清晰区分“输入态”和“输出态”。

第五，列表项身份稳定原则。  
列表渲染必须有稳定 key，行选择和批量操作必须依赖稳定 id，而不是位置索引。

第六，搜索区配置优先原则。  
复杂搜索区优先朝 schema 化、配置化演进，少让 UI 结构直接驱动大量临时 state。

第七，操作后回收一致原则。  
查询、重置、翻页、删除、批量操作后，界面状态要有明确回收和同步规则。

第八，页面体验闭环原则。  
列表页至少要考虑 loading、empty、error、无权限、无数据、查询无结果这些常见状态。

这八条原则，是后面规则展开的基础。

---

## 5.4 后果

如果列表、表格与搜索区设计失衡，常见后果通常有九种。

第一，查询条件和实际请求参数不一致。  
用户以为自己查的是 A，系统实际发出去的是 B。

第二，分页跳转后数据错乱。  
查询条件变了，页码没有重置。或者页码重置了，参数却没同步。

第三，重置操作不彻底。  
表单清空了，标签没清；标签清了，内部 params 还保留旧值。

第四，基础组件越来越难改。  
因为它已经夹带了太多业务语义，改一个点会影响大量页面。

第五，请求链路分散。  
翻页走一套，筛选走一套，初始化走一套，批量操作后刷新再走一套，review 时难以追踪。

第六，勾选状态和列表数据脱钩。  
页码一变、数据一刷、勾选态就开始错位。

第七，性能开始恶化。  
搜索条件一变，整页跟着重渲；列定义、render 函数、筛选对象每次重建，表格成本持续上升。

第八，问题很难定位。  
因为你已经说不清，到底是表单的问题、params 的问题、分页的问题，还是 table 组件本身的问题。

第九，用户体验不稳定。  
有时显示 loading，有时无声失败，有时刷新后停留在错误页码，有时列表和搜索标签对不上。

这些问题单个看都不算“惊天大 bug”，但它们一旦长期存在，就会让整个中后台系统越来越难维护。

## 5.5 代码案例

这一章重点结合 SSAP 的两个核心文件来讲。

### 案例一：`src/components/table/index.tsx`

这个基础表格组件，是列表与表格审查的第一主案例。

它天然会管理这些元素：

`loading`  
`pageInfo`  
`fetchParams`  
`selectedRows`  
`fetchApi` 请求  
列表数据格式化  
外部透传的 columns 与 rowKey  

只要看到这种基础表格组件，你做 review 时就不能只盯 JSX。你要先问：

这个组件到底是“展示组件”还是“半容器组件”。  
它有没有把请求模型吃得太深。  
分页与参数变化是否通过统一入口触发刷新。  
异常时 loading 能否完整回收。  
勾选态是否和 rowKey、数据刷新保持一致。  

这个文件里最值得写进手册的一个点，是异步闭环问题。

如果 `fetch` 流程里没有 `try/finally`，请求异常时 `loading` 可能不回收，公共表格组件会卡住。这种问题很适合拿来训练你的 review 表达：

“这里的问题不只是缺少异常处理，它已经影响到了基础界面状态的闭环。公共表格组件一旦失去 loading 收敛能力，会把故障放大到所有依赖页面。”

另一个 review 切口，是分页与参数的关系。

你要特别留意：

页码变化是不是只改 pageInfo。  
筛选变化是不是会同步重置 pageNum。  
请求入参与界面分页状态是不是同一份事实。  
列表刷新后 selectedRows 是否需要回收。  

高质量 review 不会只说“分页这里还能优化”。  
更准确的说法应该是：

“这里建议统一分页和筛选的请求入口，避免当前页、查询参数和刷新动作在多个函数中分别维护，降低后续行为漂移风险。”

### 案例二：`src/components/search-form/index.tsx`

这个搜索区组件，是中后台项目里最能暴露数据流问题的区域。

它通常同时处理：

查询项配置  
当前选中项  
表单值  
查询标签  
外部 children 解析结果  
联动显示逻辑  

这里最常见的 review 误区，是只盯某个输入框、某个 `useState`，忽略整体结构。

真正该问的是：

搜索区是“配置驱动”，还是“结构驱动”。  
查询条件有没有统一收敛到一个出口。  
标签展示是不是另存了一份条件副本。  
是否把能从 children 推导出来的值又额外存成 state。  
表单实例值和局部 state 是否共同描述同一事实。  

这个组件里一个非常典型的点，是派生状态过多的风险。

例如：

`searchData` 由 `children` 转换而来。  
`selectedChild` 又依赖当前项和 `searchData`。  
`tags` 又是查询条件的另一种投影。  

这种结构如果没有及时收敛，就会逐渐形成三套视角：

UI 结构视角。  
表单值视角。  
标签展示视角。  

review 时要特别警惕这三套视角是否已经出现不一致。

另一个典型点，是“重置语义”。

搜索区最容易出现的问题之一，就是用户点击重置之后：

表单看起来清空了。  
标签没清干净。  
外部请求参数还残留旧值。  
某些动态项仍然保留上一次的选中状态。  

所以你做搜索区 review 时，必须把“重置”当成一个专项动作检查，而不是当成普通按钮。

高质量 review comment 可以这样写：

“当前搜索区既维护表单值，又维护标签态和派生配置。建议明确以表单值或统一 queryState 作为唯一查询源，标签只做展示投影，避免重置和回填时出现状态漂移。”

### 案例三：表格和搜索区联动关系

真正麻烦的，从来不是单个组件，而是两者联动。

在 SSAP 这种页面里，典型流程通常是：

用户改搜索条件  
生成请求参数  
触发表格刷新  
回写分页  
表格选择项变化  
触发批量操作  
操作完成后刷新列表  
刷新后需要决定是否清勾选、是否回第一页、是否保留当前条件  

这里最容易 review 出价值的地方，就是“动作后回收规则”。

你要问：

查询后是否回第一页。  
重置后是否回第一页。  
删除最后一条后是否要自动回前一页。  
批量操作后是否清空 selectedRows。  
刷新后是否保留当前搜索条件。  

这类问题表面上像产品细节，实际上是列表页数据流稳定性的关键组成部分。

## 5.6 解法

列表、表格与搜索区审查，我建议你固定成一条八步路线。

### 第一步：先画页面的数据流图

不要急着看实现。  
先问页面里有哪些核心事实：

查询条件  
请求参数  
分页信息  
列表结果  
行选择状态  
批量操作结果  

把这六类事实先在脑中画清楚。

### 第二步：判断谁是查询条件的唯一来源

复杂搜索页最重要的第一刀，就是统一查询源。

可以接受的做法有两种：

一种，以 form 实例值为源，提交时生成 params。  
另一种，以统一 queryState 为源，表单只是 UI 输入层。  

怕的是混合做法。也就是 form 里一份，state 里一份，tags 再一份。

### 第三步：统一请求入口

初始化、翻页、搜索、重置、排序、批量操作刷新，最好走统一 fetch 流程。

这样做的收益是：

请求参数构造集中。  
loading 集中。  
异常处理集中。  
分页状态集中。  
review 成本下降。  

### 第四步：把基础表格组件的职责压回去

Table 组件可以管理基础 loading、分页桥接、selection 透传，但不要无限吞业务。

一旦你发现基础组件里开始出现大量特定业务判断，就应该提高警惕：

这是公共能力，还是临时图省事。  
它值不值得抽到页面层。  
它会不会污染所有接入页。  

### 第五步：重置动作单独 review

重置不是“清空几个字段”这么简单。  
你要明确重置会影响哪些状态：

表单值  
查询标签  
分页页码  
请求参数  
联动字段  
selectedRows  
列表结果  

一个成熟的列表页，重置动作应该有稳定且可预测的行为。

### 第六步：专项检查勾选态

表格勾选是最容易被低估的状态。

你要问：

rowKey 是否稳定。  
跨页是否保留勾选。  
刷新后是否清勾选。  
批量删除后是否回收勾选。  
selectedRows 是页面态还是业务态。  

### 第七步：再看性能热点

列表和表格天生容易出性能问题，重点看：

columns 是否每次重建。  
render 函数是否过重。  
筛选对象是否每次新建。  
search-form 一改值，是否带动整页重渲。  
table 和 search 是否缺少边界隔离。  

### 第八步：最后补体验闭环

至少确认：

loading  
empty  
error  
无结果  
重置后反馈  
批量操作后反馈  
无权限提示  

这些不是装饰，它们会直接影响列表页是否“像一个成熟页面”。

## 5.7 快速定位

以后你看到任何列表页、表格页、搜索页，先问这十个问题。

查询条件到底以谁为准。  
请求入口是不是统一。  
分页和筛选是否使用同一模型。  
重置会不会留下旧状态。  
勾选态是否稳定。  
table 基础组件是不是吃了太多业务。  
search-form 里有没有派生状态过多。  
tags 和表单值会不会失同步。  
列表刷新后哪些状态该保留，哪些该回收。  
这个页面一改搜索条件，会不会带着整块 UI 一起重跑。

只要这十问能形成条件反射，你看中后台列表页的速度会快很多。

---

## 5.8 本章小结

列表、表格与搜索区，是 React 中后台项目里最常见，也最容易被低估的一组场景。

这一章最重要的收获，不是背几个技巧，而是建立三种意识。

第一，列表页 review 的本质，是审查数据流是否单一、请求模型是否统一。  
第二，基础表格组件要警惕“公共能力被业务污染”。  
第三，搜索区 review 的关键，不是看输入框，而是看查询条件是否出现了多份副本和派生状态失控。

你以后再看这类代码，不要先问“这个表格能不能跑”。  
先问：

谁在描述查询条件。  
谁在触发请求。  
谁在控制分页。  
谁在保留勾选。  
谁在收口重置。  

这才是进入系统化 code review 的开始。
