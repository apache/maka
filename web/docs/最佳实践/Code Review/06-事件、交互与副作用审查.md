# 第 6 章 事件、交互与副作用审查

## 6.1 问题定义

在 React 项目里，很多代码表面上看是“点击一下、展示一下、请求一下”，真正的复杂度却藏在事件、交互与副作用的交界处。

这是 code review 最容易失分的一章。  
因为它有一个典型特征：

现象很像小 bug。  
根因却常常是交互链路不清、事件边界模糊、副作用职责混乱。

比如：

点击子按钮，父容器也一起响应。  
条件变化后触发了重复请求。  
组件卸载了，旧请求还在回写。  
图表更新和实例销毁混在一个 effect。  
用户做了一个操作，界面却连锁触发了三四个隐式行为。  

所以这一章的任务，是建立一套针对“事件、交互与副作用”的专项审查框架。目标不是只会看 `useEffect` 依赖，而是要系统判断：

事件传播路径是否可控。  
交互动作是否单义。  
副作用是否真的在同步外部系统。  
异步行为是否与当前交互状态保持一致。  
哪些问题是功能错误，哪些问题是隐患累积。  

## 6.2 成因

事件、交互与副作用之所以容易失控，通常有六个根因。

第一，事件语义没有分层。  
页面里“点击”“展开”“选择”“提交”“刷新”这些动作，本来属于不同层级，却被写成互相牵连的一串隐式触发。

第二，组件把 UI 事件和业务副作用混在一起。  
某个点击处理函数里，既改 state，又发请求，又改弹窗，又改分页，后续一旦变复杂，链路就很难追踪。

第三，effect 被当成万能补丁。  
本来应该在事件里完成的逻辑，被挪到 effect；本来应该只同步外部系统的 effect，又开始承担状态修补职责。

第四，依赖和真实触发源脱钩。  
effect 用到了多个业务值，依赖数组却不完整，导致旧数据、漏触发、重复触发一起出现。

第五，异步请求和当前界面状态没有绑定。  
用户已经切换条件、关闭弹窗、卸载组件，旧请求还在回写，最后把界面带回过期状态。

第六，第三方实例型组件没有做生命周期分层。  
比如图表、编辑器、地图、播放器等，它们天然带副作用，如果初始化、更新、解绑都揉在一个 effect 里，复杂度会迅速上升。

## 6.3 原则

这一章统一遵循八条原则。

第一，事件单义原则。  
一次用户动作，尽量只表达一个主意图。不要让“点击选择”顺便变成“展开卡片”或“重置筛选”。

第二，交互边界显式原则。  
组件内外层交互要明确谁该响应，谁不该响应。需要阻止冒泡时，就要明确阻止。

第三，副作用外部同步原则。  
effect 的职责，是同步外部系统、订阅外部资源、处理生命周期，不是拿来补一切状态逻辑。

第四，依赖一致原则。  
effect 内部用到什么真实依赖，依赖数组就应该对应什么真实依赖。

第五，异步结果时效原则。  
请求结果返回时，要确认它仍然对应当前用户视图，不能盲目回写。

第六，cleanup 对称原则。  
订阅、事件绑定、observer、定时器、第三方实例，都要有对称清理。

第七，交互反馈闭环原则。  
用户触发了动作，就要有清晰反馈。至少要考虑 loading、成功、失败、禁用态、空态。

第八，实例生命周期分层原则。  
第三方实例的创建、更新、销毁和事件绑定，应该是不同层级的语义，不要混成一个 effect。

## 6.4 后果

如果事件、交互与副作用没有审查好，常见后果通常有九种。

第一，交互串扰。  
点了按钮，父容器也响应；关闭弹窗时又顺手触发了别的逻辑。

第二，重复请求。  
一次用户动作，本应只触发一次请求，结果因为多层 state 联动和 effect 监听，发了两次甚至更多。

第三，旧数据覆盖新数据。  
用户切换筛选条件后，先发出的旧请求后返回，反而把新结果盖掉。

第四，卸载后回写。  
组件已经不可见，异步结果还在 setState，增加告警和不稳定性。

第五，交互不可预测。  
用户自己都说不清为什么这个动作会触发那几个联动，代码阅读者更难追踪。

第六，图表或第三方实例反复销毁重建。  
这会带来明显性能损耗和状态丢失。

第七，effect 越写越多，页面越来越脆。  
因为很多原本该在事件层解决的问题，被补丁式地移到了副作用层。

第八，问题难定位。  
你无法快速判断，到底是事件处理函数错了，依赖数组错了，还是异步回写时机错了。

第九，用户体验割裂。  
操作没有反馈，失败无感知，按钮能点但不该点，重复点击导致重复提交。

## 6.5 代码案例

这一章围绕三个 SSAP 主案例展开。

### 案例一：按钮点击与父层交互串扰

这个案例你在面试题里已经吃过亏。  
它最典型的结构是：

外层卡片点击负责展开。  
内层按钮点击负责选择。  

如果按钮点击没有阻止冒泡，用户点“选择该项”时，父容器的展开逻辑也会一起执行。表面看是小问题，实质是事件语义混乱。

这种问题最适合训练 review 表达：

“这里存在交互串扰风险。按钮点击本应只表达选择动作，但当前会继续冒泡到父层，导致展开逻辑一起执行。建议在子层显式阻止冒泡，让交互意图保持单义。”

### 案例二：`src/pages/dashboard/index.hook.tsx`

长 hook 页面最容易出现副作用链路过长的问题。

在 dashboard 这类首页里，通常会同时出现：

默认值初始化。  
筛选条件变化。  
图表数据请求。  
弹窗开关。  
表格分页。  
枚举回填。  
权限树默认选中。  

review 这类文件时，不能只看“有没有 useEffect”，而要问：

这些 effect 分别在同步什么。  
哪些逻辑本该在事件里完成。  
哪些 effect 之间已经形成隐式链。  
是否同一个业务动作通过多条路径触发了同一结果。  

高质量 review 不会简单说“effect 太多了”。  
更好的说法应该是：

“当前首页 hook 的交互动作和副作用链路耦合较深。建议先按初始化、筛选联动、图表请求、弹窗控制四类职责拆开，降低 effect 之间的隐式依赖。”

### 案例三：`src/components/echarts/base-chart.tsx`

这是事件与副作用审查里非常好的高级案例。

图表组件天然包含：

实例创建。  
setOption 更新。  
click 事件绑定。  
resize 监听。  
实例销毁。  

如果这些都写在一个依赖 `options` 的 effect 里，就会带来一个典型问题：

每次 options 更新，都可能触发 cleanup 和重新初始化。  
这样“配置更新”就和“实例生命周期”混成了一团。

这类 review 语言应该更准确：

“当前图表组件把实例初始化、配置更新和事件绑定放进了同一层副作用。这样 options 变化时会引入不必要的实例销毁与重建。建议将实例创建与销毁、options 更新、事件绑定解绑拆成不同语义层级。”

### 案例四：请求回写时效性

这个案例在 `table/index.tsx`、`rules/config/index.hook.tsx` 这类文件里都会高频出现。

任何依赖用户当前条件的请求，都必须警惕两个问题：

请求回来时，这个页面还是当前视图吗。  
请求回来时，这组条件还是最新条件吗。  

如果没有这层判断，就很容易出现旧请求覆盖新结果。

高质量 review comment 可以这样写：

“这里的异步结果默认直接回写状态，但没有体现当前视图时效性。建议补上取消请求、版本戳、active flag 或统一请求层防抖去重，避免旧响应覆盖当前界面。”

## 6.6 解法

事件、交互与副作用审查，建议固定成一条九步路线。

### 第一步：先画交互动作表

先不要看 effect。  
先列出页面上的主动作：

点击。  
选择。  
展开。  
搜索。  
重置。  
提交。  
关闭。  
删除。  
批量操作。  

先把动作表列出来，你才知道这个页面到底有哪些“行为节点”。

### 第二步：判断每个动作的主意图

每个动作都问一句：

它到底想表达什么。  
它是否只表达了这一件事。  
是否有额外副作用被顺手带出来。  

如果一个动作既改了局部状态，又触发请求，又联动别的区域，还没有清晰命名，那就该提高警惕。

### 第三步：检查事件传播路径

重点看：

子组件点击是否误触发父组件。  
列表项点击和内部按钮点击是否冲突。  
弹窗关闭动作是否会触发底层页面点击。  
键盘事件和鼠标事件是否会重复进入同一逻辑。  

### 第四步：区分事件逻辑和副作用逻辑

这是最关键的一刀。

你要问：

这段逻辑本来就该在用户点击时发生。  
还是它只是因为某个状态变了，被动同步外部系统。  

前者应该优先放在事件处理里。  
后者才应该考虑放进 effect。

### 第五步：逐个检查 effect 的真实职责

每个 effect 都要问三句话：

它在同步什么外部事实。  
它依赖什么真实值。  
它清理了什么外部资源。  

如果答不出来，这个 effect 大概率已经承担了不该承担的职责。

### 第六步：专项检查异步回写时效性

任何请求都问：

有没有 loading。  
有没有 error。  
有没有取消。  
有没有版本保护。  
用户切换条件后旧请求是否还能回写。  

### 第七步：专项检查第三方实例生命周期

面对图表、编辑器、播放器等重型组件，固定拆三层：

实例何时创建。  
配置何时更新。  
资源何时销毁。  

只要这三层混在一起，后面必然难维护。

### 第八步：看反馈是否闭环

用户做了动作之后，界面必须给出合理反馈：

是否禁用重复点击。  
是否展示 loading。  
失败后是否可恢复。  
成功后是否回收旧状态。  

### 第九步：最后给最小修复路径

比如：

先拆掉明显的交互串扰。  
再统一请求回写保护。  
再收敛 effect 职责。  
最后做第三方实例生命周期分层。  

这样改动路径才清晰。

## 6.7 快速定位

以后你看到任何交互复杂的 React 页面，先问这十个问题。

这个动作的主意图是什么。  
它会不会顺带触发别的动作。  
是否存在事件冒泡串扰。  
哪些逻辑应该在事件层，哪些应该在 effect 层。  
effect 里到底在同步什么外部事实。  
依赖数组和真实依赖一致吗。  
异步结果回来时，当前视图还是原来的视图吗。  
有没有 cleanup。  
第三方实例的创建、更新、销毁是否混在一起。  
用户操作后是否得到清晰反馈。  

这十问形成条件反射之后，你对“交互类问题”的识别速度会快很多。

## 6.8 本章小结

事件、交互与副作用，是 React Code Review 最容易从“小问题”一路长成“大隐患”的区域。

这一章最重要的收获，不是记住几个 useEffect 规范，而是建立三种能力。

第一，学会把交互问题翻译成“动作意图”和“传播边界”。  
第二，学会区分事件层逻辑和副作用层逻辑。  
第三，学会把异步请求和第三方实例都放回生命周期管理视角里看。

当你能稳定做到这三点，很多过去看起来零散的小 bug，就会自动汇聚成一条可解释、可修复、可复用的 code review 路线。
