# 第 3 章 SSAP 项目全景：从业务结构到 Review 切口

## 3.1 问题定义

要把 React Code Review 讲得有价值，不能只停在抽象规则。  
必须落到真实项目，尤其是你自己做过、未来面试也会反复讲到的项目。

这本手册选择 SSAP，不是偶然。  
因为 SSAP 不是简单 demo，它更接近真实的中后台复杂度：

表格多。  
搜索区复杂。  
图表存在。  
弹窗联动多。  
表单配置多。  
长 hook 明显。  
页面状态和请求编排复杂。  

这类项目最适合训练 code review，因为它天然包含大量真实风险，而不是只包含一些教材级错误。

所以这一章的任务，是先建立 SSAP 项目全景图。  
后面所有章节，都会回到这个全景图里找切口。

## 3.2 成因

为什么 SSAP 特别适合用来写这本手册，根因主要有四类。

第一，它的复杂度足够真实。  
不是只渲染几个组件，而是典型中后台页面，涉及搜索、列表、分页、弹窗、图表、表单依赖和配置项。

第二，它的复杂度来源清晰。  
问题不会只集中在某一行代码，而会集中在状态、交互、副作用、请求编排、基础组件职责边界这些真正影响长期质量的区域。

第三，它和你的面试目标高度一致。  
你现在的求职方向，本来就以 React 中后台和业务工程能力为主。用 SSAP 写手册，和你未来的面试表达完全同路。

第四，它既能讲局部问题，也能讲系统问题。  
既可以讲一个 `useEffect`，也可以讲一个长 hook 的复杂度来源；既可以讲表格组件异常闭环，也可以讲复杂搜索区为何容易失控。

## 3.3 原则

围绕 SSAP 做 code review，全书统一遵循五个原则。

第一，优先找“复杂度热点”。  
不是所有文件都值得花同样精力。先抓最能放大问题的文件。

第二，优先找“公共能力入口”。  
基础组件比页面细节更值得审查，因为它们会复制问题。

第三，优先找“状态和请求交汇点”。  
中后台页面的核心风险，经常出现在状态、副作用和请求编排的交汇处。

第四，优先找“未来会持续恶化”的位置。  
不是只看现在会不会报错，还要看半年后会不会变得不可维护。

第五，所有案例都要可回到面试表达。  
每个代码案例最后都要能总结成一句高质量 review 语言，而不只是代码观察。

## 3.4 后果

如果没有先做项目全景梳理，后面写规则会出现三个问题。

第一，规则会悬空。  
你会写出很多“看起来对”的规则，但说不清在自己的项目里具体出现在哪里。

第二，案例会失焦。  
今天讲这个组件，明天讲那个 hook，最后没有一条主线把它们串起来。

第三，面试价值会下降。  
因为你很难把规则和自己的真实项目绑定，最终只能讲成通用八股。

所以，第 3 章其实是在给整本手册做“项目级地图”。

## 3.5 代码案例

这一章先冻结全书的五个核心案例文件。

### 案例一：`src/components/table/index.tsx`

这是基础表格组件。  
它很适合承载以下主题：

基础组件职责边界。  
请求时序和 loading 闭环。  
分页与参数的统一模型。  
selection 状态管理。  
公共组件如何放大问题。  

### 案例二：`src/components/search-form/index.tsx`

这是复杂搜索区组件。  
它很适合承载：

查询条件单一来源。  
派生状态和双数据源。  
schema 化思维。  
标签态和表单值的关系。  
重置动作是否形成稳定回收。  

### 案例三：`src/components/echarts/base-chart.tsx`

这是图表基座。  
它非常适合承载：

第三方实例生命周期。  
配置更新和实例销毁的分层。  
事件绑定与解绑。  
性能与资源释放。  

### 案例四：`src/pages/dashboard/index.hook.tsx`

这是首页长 hook。  
它很适合承载：

长 hook 的复杂度来源。  
多 effect 串联。  
默认值初始化。  
图表与弹窗联动。  
状态职责是否已经失控。  

### 案例五：`src/pages/rules/config/index.hook.tsx`

这是复杂规则配置页 hook。  
它很适合承载：

复杂表单字段依赖。  
多业务态共存。  
联动请求。  
模板注入字段。  
新增、查看、编辑多态管理。  

这五个文件，就是整本手册的主案例池。

## 3.6 解法

围绕 SSAP 做整本手册，我建议采用“三层切入法”。

### 第一层：先按模块分类

把全项目先拆成几类：

基础组件。  
页面 hook。  
表单与搜索区。  
图表和重型组件。  
列表和批量操作页。  

这样后面每一章就不会失去焦点。

### 第二层：再按复杂度来源分类

每个案例再问：

它的复杂度主要来自状态。  
还是来自副作用。  
还是来自请求编排。  
还是来自公共抽象。  
还是来自渲染和性能。  

这样你讲问题时，才不会一直停在“代码很多”。

### 第三层：最后按 review 切口分类

每个案例进入正文时，都回到同一套切口：

问题定义。  
成因。  
原则。  
后果。  
代码案例。  
解法。  
快速定位。  

这就是全书统一的七段模板。

## 3.7 快速定位

以后你拿到一个中后台 React 项目，先不要急着全量 review。  
先找这几类文件：

最重的基础组件。  
最长的 hook。  
最复杂的搜索区。  
最重的图表组件。  
最常被复用的表格页。  

因为真正能拉开你 review 水平的，通常不是普通展示组件，而是这些复杂度集中区。

## 3.8 本章小结

这一章解决的是“这本手册到底围绕什么项目、什么代码、什么案例展开”。

它冻结了整本手册的主案例池，也让后面每一章都有明确落点。  
从这里开始，规则不再是抽象条目，而会逐渐长成：

基于 SSAP 真实代码的系统化审查方法。
