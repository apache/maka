# 第 9 章 工程化、可维护性与基础组件抽象

## 9.1 问题定义

React 项目做到一定规模之后，很多问题已经不再是“这一行代码对不对”，而是“这个项目还能不能继续稳地长下去”。

这就是工程化、可维护性与基础组件抽象要解决的问题。

在前面的几章里，我们已经分别看过：

状态与数据流。  
列表、表格与搜索区。  
事件、交互与副作用。  
异步请求与错误恢复。  
图表、重型组件与性能。  

但当这些问题持续累积，最后都会汇聚到一个更高层的问题：

代码是否还能被人快速理解。  
基础组件是否还能安全复用。  
长 hook 和长组件是否还在可控边界内。  
项目是否已经形成“修一个地方，坏一片地方”的脆弱结构。  

所以这一章的任务，是建立一套针对“工程化、可维护性与基础组件抽象”的专项审查框架。目标不是只说“代码有点乱”，而是要系统判断：

复杂度到底来自哪里。  
公共抽象是否真正成立。  
基础组件是否已经被业务污染。  
模块边界是否清晰。  
哪些问题只是风格差，哪些问题已经伤到项目长期演化能力。  

---

## 9.2 成因

工程化和可维护性问题之所以容易被忽视，通常有八个根因。

第一，项目在早期只追求先跑通。  
一开始页面不多、逻辑不复杂，很多“临时方案”都看起来没问题。等项目长大后，这些临时方案就变成长期结构。

第二，大家习惯从功能视角看代码，不习惯从演化成本看代码。  
某个需求今天能交付，不代表这段设计经得起未来十个需求继续叠加。

第三，基础组件最容易被“顺手塞业务”。  
一开始只是加一个小判断，后面再加一个特例，最后公共组件里混进了越来越多页面级语义。

第四，长 hook 和长组件会逐步吞掉边界。  
初始化放一点，请求放一点，弹窗放一点，表单联动再放一点，最后所有职责都被吸进同一个文件。

第五，工程化规范只停在工具层。  
项目里可能有 ESLint、Prettier、TypeScript，但这些工具只能约束表层一致性，不能自动保证抽象质量和边界设计。

第六，复用欲望大于抽象能力。  
很多人一看到重复就想抽公共组件，却没有先判断“重复的是结构，还是只是表象”。结果抽出来的不是通用能力，而是半成品。

第七，业务复杂度容易伪装成代码复杂度。  
开发者会说“这个页面业务本来就复杂”，但实际上真正难维护的部分，常常是结构设计没有及时分层。

第八，中后台项目很容易在“可用”阶段停太久。  
因为系统表面上能跑，大家就默认工程结构也没问题，直到维护成本突然失控。

---

## 9.3 原则

工程化、可维护性与基础组件抽象审查，统一遵循十条原则。

第一，职责单一原则。  
一个模块、一个 hook、一个组件，应尽量只承担一类核心职责。

第二，边界显式原则。  
状态、请求、展示、事件、配置、公共能力之间的边界，要能一眼看清。

第三，基础能力去业务污染原则。  
公共组件要尽量承载“能力”，不要吞入具体页面规则。

第四，抽象晚于理解原则。  
在没有真正理解重复模式之前，不要急着抽象。

第五，复杂度可拆解原则。  
如果一个文件已经难以阅读，应该优先考虑按职责拆开，而不是继续往里堆注释。

第六，命名可推断原则。  
好的工程化结构应该让阅读者通过命名就能推断职责。

第七，局部修改可预测原则。  
改动一个点时，应该能大致预测会影响哪些模块。影响范围越不可预测，工程质量越差。

第八，公共接口稳定原则。  
基础组件、基础 hook、公共工具函数的输入输出要稳定，避免每个页面都要做特例适配。

第九，失败隔离原则。  
一个公共模块出问题时，不应轻易把故障扩散到整个系统。

第十，演化优先原则。  
评估一段代码，不只看它今天能不能工作，还要看它未来是否容易继续扩展。

---

## 9.4 后果

如果工程化、可维护性与基础组件抽象没有审查好，常见后果通常有十种。

第一，文件越来越长，但谁也不敢拆。  
因为状态、请求、表单、图表、弹窗已经混成一团，拆哪都怕出事。

第二，基础组件越来越重。  
一个公共 table、modal、search-form 逐渐演变成一堆业务例外的集合体。

第三，修改范围失控。  
改一个小功能，必须联动改多个页面和多个基础组件。

第四，review 越来越低效。  
因为 reviewer 很难快速判断哪部分是通用能力，哪部分是业务补丁。

第五，新同事上手很慢。  
他不是不会 React，而是根本看不懂这个项目现在按什么边界组织。

第六，问题容易反复出现。  
因为根因没有被结构化解决，只是在局部打补丁。

第七，复用越来越痛苦。  
看似有很多公共组件，实际上接一个页面就要加一个特判。

第八，测试与验证成本上升。  
抽象层次混乱时，任何改动都需要大量人工确认，自动化也很难建立。

第九，性能和异步问题更难定位。  
因为真正的复杂度不是单个 bug，而是结构导致的问题扩散。

第十，项目会进入“表面能跑，内部脆弱”的状态。  
这种项目最危险，因为它不会立刻爆，但会持续消耗开发效率。

## 9.5 代码案例

这一章重点结合 SSAP 的四个主案例。

### 案例一：`src/components/table/index.tsx`

这是基础组件抽象最重要的案例之一。

一个基础表格组件，理论上应当提供的是：

表格展示能力。  
分页桥接能力。  
行选择桥接能力。  
统一请求触发入口。  
基础 loading 与空态支撑。  

你做 review 时，要反复问一个问题：

“这个组件到底在提供能力，还是已经在承载业务规则？”

一旦你发现组件里开始出现大量特殊判断，就要提高警惕：

这个判断是所有表格共有的吗。  
还是某个页面的临时需求。  
它抽到公共层后，会不会污染所有接入页。  

高质量 review comment 应该这样写：

“当前基础表格组件逐渐承担了部分页面级业务语义。建议回收具体业务判断到页面层，让公共组件只保留展示桥接和基础交互能力，避免后续复用成本持续上升。”

### 案例二：`src/components/search-form/index.tsx`

复杂搜索组件特别容易发生“抽象表面成立，内部边界混乱”。

从外部看，它像一个公共搜索区。  
从内部看，却可能同时承担：

children 解析。  
字段配置转换。  
表单状态。  
标签态。  
选中项状态。  
动态联动显示。  

这类组件最该 review 的，不是“有没有复用成功”，而是：

它的抽象边界到底是什么。  
它输出的是统一查询能力，还是一团混合状态。  
它是否已经需要 schema 化，而不是继续靠 JSX children 驱动。  

高质量 review 表达可以是：

“当前搜索组件的公共抽象仍偏结构驱动，内部同时维护多类派生状态。建议逐步向 schema 化和统一查询源演进，减少 children 解析、标签映射和表单值之间的耦合。”

### 案例三：`src/pages/dashboard/index.hook.tsx`

长 hook 是可维护性审查最典型的案例。

看到一个 600 多行的 hook，不要先说“太长了”。  
要先判断：

它到底混进了几类职责。  
哪些职责其实可以拆成子 hook。  
哪些状态和请求其实只属于局部区域。  
哪些默认值、初始化逻辑、本来就不该和页面主逻辑绑死。  

这类文件最容易形成“所有逻辑都能找到理由留下来”的状态。  
可维护性 review 的价值，就在于逼你从“每段逻辑都有理由”退回到“这些逻辑是否应在同一边界里”。

更准确的 review 语言应该是：

“当前 dashboard hook 同时承担筛选条件、图表数据、弹窗控制、默认值初始化等多类职责。复杂度根因在于边界未拆，而不是单点实现细节。建议先按筛选区、图表区、弹窗区、初始化逻辑拆分子 hook，降低认知负担和变更风险。”

### 案例四：`src/pages/rules/config/index.hook.tsx`

复杂规则配置页 hook 很适合拿来讲“业务复杂度”和“结构复杂度”的区别。

这种页面业务确实复杂。  
但 review 时不能用“业务复杂”替代码结构背锅。

你要问：

复杂的是字段依赖，还是结构组织。  
复杂的是业务规则本身，还是因为新增、编辑、查看三态都混在一个文件。  
复杂的是接口多，还是因为请求、表单、模板注入、联动逻辑没有分层。  

一个高质量 reviewer，不会否认业务复杂。  
但也不会接受“所以就只能写成这样”。

## 9.6 解法

工程化、可维护性与基础组件抽象审查，建议固定成一条十步路线。

### 第一步：先看职责数量，而不是文件长度

长文件不是问题本身。  
真正的问题是一个文件承载了多少类职责。

固定先数这几类：

状态。  
请求。  
展示。  
交互。  
弹窗。  
表单。  
图表。  
默认值初始化。  

如果一个模块同时承担了太多类，先提高警惕。

### 第二步：判断这是公共能力，还是页面特例

面对基础组件时，先问：

这个能力是否真的通用。  
是否已经被页面特例污染。  
每接一个页面，是不是都要往里再加判断。  

一旦答案偏向后者，就说明抽象质量有问题。

### 第三步：区分“重复”与“可抽象”

不是所有重复都值得抽。  
你要先判断重复的是：

UI 壳子。  
交互模式。  
数据模型。  
还是只是表面长得像。  

只有当“输入、输出、语义”都比较稳定时，抽象才值得做。

### 第四步：检查公共接口是否稳定

重点看：

props 是否越来越多。  
默认行为是否越来越难预测。  
接入页面是否经常需要传很多特殊开关。  
公共组件是否暴露了太多内部细节。  

接口越膨胀，说明抽象越不稳。

### 第五步：专项检查长 hook 和长组件

固定问：

它能否按职责拆。  
它能否按作用域拆。  
它能否按页面区域拆。  
它是否把初始化逻辑、事件逻辑、请求逻辑、展示逻辑混在一起。  

### 第六步：检查命名和目录结构是否支持理解

好的工程化结构，会让阅读者快速建立地图。

你要看：

组件名是否体现职责。  
hook 名是否体现作用域。  
工具函数是否有清晰边界。  
目录是否按业务还是按能力组织。  

### 第七步：检查故障是否会被公共层放大

基础组件要重点审查：

一旦这里有 bug，会影响几个页面。  
错误是否会扩散。  
页面层有没有机会局部兜底。  

### 第八步：判断当前复杂度是否值得重构

不是所有乱都要立刻重构，但要有判断标准。

如果它已经影响：

阅读速度。  
review 质量。  
需求迭代速度。  
问题定位效率。  
公共复用稳定性。  

那就说明到了必须重构的节点。

### 第九步：给出最小重构路径

不要只说“建议重构”。  
要说：

先拆什么。  
先收什么状态。  
先把哪些业务判断回收到页面层。  
先把哪个长 hook 切成几个子 hook。  

### 第十步：最后看工程资产是否能沉淀

成熟的工程化 review，不只改代码，还要问：

这次是否值得沉淀成公共模式。  
是否值得形成约定。  
是否值得写进组件使用规范或 review 规则。

## 9.7 快速定位

以后你看到任何看起来“还能跑但越来越难维护”的 React 代码，先问这十个问题。

这个模块到底承担了几类职责。  
它是公共能力，还是页面特例。  
当前抽象是真的通用，还是只是勉强复用。  
基础组件是否被业务污染。  
长 hook 和长组件的复杂度根因是什么。  
接口和 props 是否已经膨胀。  
命名和目录结构是否支持快速理解。  
一个公共模块出错会影响多大范围。  
当前复杂度是否已经影响迭代效率。  
有没有明确的最小重构路径。  

这十问形成条件反射之后，你对“可维护性问题”的判断会更稳定。

---

## 9.8 本章小结

工程化、可维护性与基础组件抽象，是 React Code Review 里最容易被晚发现、但代价最高的一组问题。

这一章最重要的收获，是建立三种能力。

第一，学会从“长期演化成本”而不是“当前能不能跑”来评估代码。  
第二，学会区分真正的公共能力和被业务污染的伪抽象。  
第三，学会把长 hook、长组件和基础组件问题，统一翻译成“职责、边界、接口、扩散风险”这四类稳定语言。  

当你能稳定做到这三点，工程化 review 才真正开始有重量。因为你不再只是帮团队找 bug，而是在帮项目守结构。
