# 第 12 章 Vercel 64 条规则的本地化映射

## 12.1 这一章要解决什么问题

到这一章，前面的工作已经做了两件事。

第一，我们已经把 React Code Review 的总框架搭起来了。  
第二，我们已经用 SSAP 的真实代码，把复杂度最容易长出来的区域拆开看过了。

接下来要做的，不是简单把 `vercel-react-best-practices` 里的规则翻译成中文。  
真正要做的，是把那套偏通用、偏现代 React 与 Next.js 的最佳实践，映射到你当前最真实的工作场景里，也就是：

SSAP 这种中后台 React 项目。  
表格、搜索区、图表、长 hook、复杂配置页。  
你当前的求职方向与面试表达。  
你未来想沉淀成长期资产的 64 条 review 规则。

所以这一章的核心任务是：

把 Vercel 那套规则，转译成你自己的本地化审查语言。  
让它不只是“别人仓库里的好规则”，而是真正能落到你项目、你 review、你面试里的规则体系。

---

## 12.2 为什么要做“本地化映射”

如果你只是机械吸收外部最佳实践，会有三个常见问题。

第一，规则听起来都对，但不知道在自己项目里该看哪里。  
比如“避免不必要的重渲染”“拆分副作用”“按需加载重型依赖”，这些都没错，但如果你不能立刻对应到 `table`、`search-form`、`base-chart`、`dashboard hook`、`rules config hook`，规则就会悬空。

第二，规则容易停在 API 层。  
很多人学 React 最佳实践，最后只记住了 `useMemo`、`useCallback`、`React.memo`、懒加载、依赖数组完整性。  
这当然重要，但你现在需要的是能落到“为什么我的中后台项目会变复杂”的结构语言。

第三，规则难以转成面试输出。  
你不是只要做得对，你还要能说得清。  
如果规则不能转成“问题、原则、后果、修法”的表达，它就很难在面试里发挥价值。

所以，本地化映射不是翻译工作。  
它是一次“把通用规则压缩成你自己的认知系统”的工作。

---

## 12.3 本地化映射的基本原则

这一章统一遵循五个映射原则。

### 原则一：先按“复杂度来源”映射，不按仓库目录照搬

外部规则通常按主题组织，比如异步、渲染、服务端、包体积、缓存。  
这没有问题。  
但你要落到自己的项目里时，更应该先按复杂度来源映射：

状态。  
搜索区。  
表格。  
图表。  
长 hook。  
复杂表单。  
异步请求。  
工程化抽象。  

因为这才是你在 SSAP 里真正遇到问题的入口。

### 原则二：每条规则都必须能落到一个真实案例

如果一条规则落不到真实代码，它就还不是你的规则。  
所以后面的映射里，我们会尽量给每条规则都标一个典型落点。

### 原则三：每条规则都必须能转成 review comment 语言

你以后不是背规则标题，而是要会说：

这里有什么问题。  
违反了什么原则。  
会导致什么后果。  
建议怎么修。  

所以本地化映射必须面向 review 语言。

### 原则四：优先映射最能提升你真实能力的规则

你当前最值钱的，不是先映射所有边缘规则，而是先映射那些能立刻提升你：

看 PR 的能力。  
分析 SSAP 项目的能力。  
面试 code review 题表达能力。  

### 原则五：最终要回到“64 条规则总表”

这一章不是终点。  
它是为后面第 14 章服务的。  
也就是把外部规则消化之后，整理成你自己的 64 条规则体系。

## 12.5 第一批最值得本地化的 16 条规则

这一节先不一次性铺满 64 条。  
先挑出最能立刻提升你真实能力的 16 条，做深度本地化映射。

---

### 规则 01：能算出来的值，不要额外存一份 state

**原始精神**  
尽量减少派生状态，保持单一数据源。

**本地化翻译**  
凡是能从 `props`、`children`、已有 `state`、表单值推出来的东西，优先现算，不优先再存。

**SSAP 对应案例**  
`search-form/index.tsx` 里的 `searchData`、`selectedChild`、`tags` 三套视角。  
这就是典型的派生状态堆叠。

**高质量 review comment**  
这里存在明显的派生状态堆叠。当前组件同时维护结构解析结果、选中渲染结果和展示标签，后续联动场景会放大状态漂移风险。建议收缩唯一查询源，把能计算出来的视图结果移回 render 阶段或统一配置层。

---

### 规则 02：不要把 UI 结果塞进 state

**原始精神**  
state 应该尽量表达业务事实，而不是已经渲染好的 UI 结果。

**本地化翻译**  
不要在 state 里直接存 ReactNode、已拼好的 JSX、已 clone 的组件。

**SSAP 对应案例**  
`search-form/index.tsx` 里的 `selectedChild`。

**高质量 review comment**  
当前 `selectedChild` 直接持有 ReactNode，这会让状态开始承担 UI 结果，而不是业务事实。建议只存“当前选中了哪个字段”，具体组件由 render 根据配置决定。

---

### 规则 03：effect 只负责同步外部系统，不负责补一切状态

**原始精神**  
`useEffect` 是副作用工具，不是状态补丁工具。

**本地化翻译**  
凡是本来应该在事件里完成的逻辑，不要为了“看起来更 React”就塞进 effect。  
effect 更适合处理请求、订阅、实例同步、外部资源。

**SSAP 对应案例**  
`dashboard/index.hook.tsx`  
`rules/config/index.hook.tsx`

**高质量 review comment**  
当前部分 effect 已开始承担状态迁移与业务补丁职责。建议回到“effect 只同步外部事实”的原则，把纯事件驱动逻辑收回 handler，把 effect 留给真正依赖外部资源的链路。

---

### 规则 04：effect 依赖必须对应真实使用值

**原始精神**  
依赖数组不是“让 linter 安静”，而是在声明副作用和什么绑定。

**本地化翻译**  
effect 里用了什么，就要严肃审查依赖是否和真实业务依赖一致。

**SSAP 对应案例**  
面试题里的 `user.id` 依赖脱钩。  
`rules/config/index.hook.tsx` 多组联动 effect。

**高质量 review comment**  
这里的副作用触发条件和真实数据依赖没有完全对齐。短期可能还能工作，但一旦条件切换或组件复用，容易出现旧数据和漏触发。建议把依赖定义拉回业务事实层，而不是只按当前“能跑”来写。

---

### 规则 05：请求必须形成 loading 的异常对称闭环

**原始精神**  
开始请求和结束请求要形成完整生命周期，错误分支不能缺席。

**本地化翻译**  
凡是打开 loading，就必须保证成功失败都关闭 loading。

**SSAP 对应案例**  
`table/index.tsx`  
`dashboard/index.hook.tsx` 的多个图表请求。

**高质量 review comment**  
这里的 loading 生命周期没有异常对称闭环。一旦接口抛错，界面可能长期停留在 loading。建议统一请求入口，并通过 try/finally 保证成功失败都能回收状态。

---

### 规则 06：旧请求不能覆盖新视图

**原始精神**  
异步结果的正确性，取决于它返回时是否仍然属于当前上下文。

**本地化翻译**  
任何依赖当前筛选条件、当前表单值、当前弹窗状态的请求，都要考虑过期回写。

**SSAP 对应案例**  
`rules/config/index.hook.tsx` 的联动请求。  
`dashboard/index.hook.tsx` 的图表和弹窗请求。

**高质量 review comment**  
当前异步结果默认直接回写状态，但没有体现当前视图时效性。建议补充取消请求、版本戳或最新响应优先策略，避免旧结果覆盖当前页面状态。

---

### 规则 07：基础组件优先提供能力，不优先吞业务规则

**原始精神**  
公共抽象越往下层，越应该少携带页面特例。

**本地化翻译**  
基础 table、search-form、base-chart 这类组件，最怕被一页一页的特例污染。

**SSAP 对应案例**  
`table/index.tsx`  
`search-form/index.tsx`

**高质量 review comment**  
当前基础组件已开始承担部分页面级业务语义。建议把页面特例回收到页面层，让公共层只保留稳定能力，否则后续复用成本会持续升高。

---

### 规则 08：抽象应晚于模式稳定，不要因为重复两次就急着抽

**原始精神**  
复用不是目的，稳定抽象才是目标。

**本地化翻译**  
看到重复时，先问“重复的是输入输出语义，还是只是表面长得像”。

**SSAP 对应案例**  
`search-form/index.tsx` 的 children 驱动抽象。  
`table/index.tsx` 的能力边界。

**高质量 review comment**  
当前抽象已经具备复用意图，但输入和输出语义仍不够稳定。建议先冻结查询模型或接口边界，再继续沉淀公共层，避免形成伪抽象。

---

### 规则 09：第三方实例必须做生命周期分层

**原始精神**  
创建、更新、销毁、事件绑定是不同层级的职责。

**本地化翻译**  
图表、编辑器、播放器、地图，只要你把这些动作写在同一层 effect，复杂度迟早会上来。

**SSAP 对应案例**  
`base-chart.tsx`

**高质量 review comment**  
当前图表组件把实例创建、配置更新和事件绑定放进了同一层副作用。建议做生命周期分层，让创建与销毁只跟容器生命周期绑定，配置更新和事件绑定单独管理。

---

### 规则 10：性能优化先切边界，再谈 memo

**原始精神**  
优化的第一刀通常是结构，不是 API。

**本地化翻译**  
先看是谁不该更新却更新了，再决定要不要加 `memo`、`useMemo`、`useCallback`。

**SSAP 对应案例**  
`dashboard/index.hook.tsx`  
`search-form/index.tsx`  
`table/index.tsx`

**高质量 review comment**  
当前局部状态改动会带动较大范围 UI 重新执行。建议先按筛选区、图表区、弹窗区切边界，再评估哪些输入需要稳定化，而不是直接在现有结构上堆 memo。

---

### 规则 11：搜索、翻页、重置、刷新应优先统一成单一请求模型

**原始精神**  
相同语义的行为，尽量走同一模型。

**本地化翻译**  
列表页最怕初始化一套、搜索一套、翻页一套、重置一套、批量操作回刷再一套。

**SSAP 对应案例**  
`table/index.tsx`  
`search-form/index.tsx`

**高质量 review comment**  
当前列表页的搜索、翻页和刷新已部分统一，但参数变化后的分页回收策略还不够显式。建议进一步冻结单一请求模型，降低后续行为漂移。

---

### 规则 12：长 hook 不一定错，但职责混装一定危险

**原始精神**  
复杂文件的核心问题不是行数，而是边界不清。

**本地化翻译**  
不要一上来就说“太长了”，先判断里面到底塞了几类职责。

**SSAP 对应案例**  
`dashboard/index.hook.tsx`  
`rules/config/index.hook.tsx`

**高质量 review comment**  
当前 hook 同时承担页面筛选、图表请求、弹窗控制、默认值初始化等多类职责。复杂度根因在于边界未拆，而不是单点实现细节。建议按作用域和职责拆分子 hook。

---

### 规则 13：复杂表单最难的不是控件，而是联动网络

**原始精神**  
复杂表单的风险主要来自依赖关系和状态迁移，而不是单个 input。

**本地化翻译**  
看到多组 onChange 重置下游字段、多组 effect 联动请求时，就说明复杂度已经从“表单控件”升级成“状态迁移网”。

**SSAP 对应案例**  
`rules/config/index.hook.tsx`

**高质量 review comment**  
当前页面已经形成明显的字段联动网络。问题不在单个 handler，而在状态迁移链分散在多个回调和 effect 中。建议尽快沉淀统一迁移模型或分层状态机，降低后续扩展成本。

---

### 规则 14：危险内容默认不可信

**原始精神**  
任何直接注入页面的内容，都要默认先质疑其安全性。

**本地化翻译**  
看到 `dangerouslySetInnerHTML`、富文本注入、直接拼 HTML，就要立刻进入安全审查模式。

**SSAP 对应案例**  
面试题场景。  
后续中后台富文本或富提示区域都适用。

**高质量 review comment**  
这里直接渲染 HTML 内容，存在 XSS 风险。除非数据源经过可信清洗，否则不应直接注入页面。建议优先避免原样插入，或补上明确的清洗策略。

---

### 规则 15：状态、错误、空态、无权限必须让用户看得懂

**原始精神**  
用户体验不是装饰，而是状态表达系统。

**本地化翻译**  
loading、empty、error、无结果、无权限，这几类状态如果长得差不多，用户就会误判。

**SSAP 对应案例**  
`table/index.tsx`  
`search-form/index.tsx`  
dashboard 和弹窗区域。

**高质量 review comment**  
当前页面的状态表达还不够可区分。建议明确区分 loading、empty、error 和无权限，避免用户把失败误判成“没有数据”。

---

### 规则 16：任何规则最终都要能转成面试和 review 的四段式输出

**原始精神**  
规则只有被表达出来，才算真正掌握。

**本地化翻译**  
你学到的每一条规则，最后都要能压缩成：

这里有什么问题。  
违反了什么原则。  
会导致什么结果。  
建议怎么修。  

**SSAP 对应案例**  
全书所有案例。

**高质量 review comment 模板**  
这里存在一个什么问题。  
它违反了什么原则。  
在当前模块里会导致什么具体后果。  
建议先从哪一刀开始改。  

---

## 12.6 这 16 条规则如何回到你自己的 64 条体系

到这里，你应该已经能感受到一件事：

Vercel 的通用规则，并不是要照抄。  
真正重要的是，它们提供了一个高密度、高标准的外部参照。  
而你现在做的本地化映射，本质上是在完成三件事：

把它们压回你最真实的项目场景。  
把它们转译成你能直接说出来的 review 语言。  
把它们重组进你自己的 64 条规则骨架。

所以后面第 14 章的 64 条规则总表，应该长成下面这种样子：

每一条都有编号。  
每一条都有一句原则。  
每一条都有主场景。  
每一条都有典型症状。  
每一条都有高质量 review comment 范式。  

这样它才是你自己的规则系统，而不是别人的规则清单。

## 12.7 本章小结

这一章最重要的价值，不在于把 Vercel 的规则翻译成中文，而在于完成了一次认知降维。

你现在不是在背“外部最佳实践”。  
你是在做三件更重要的事：

第一，把外部规则转成你自己的项目语言。  
第二，把通用最佳实践压回 SSAP 真实案例。
