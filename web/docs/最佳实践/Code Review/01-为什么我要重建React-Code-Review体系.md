# 第 1 章 为什么我要重建 React Code Review 体系

## 1.1 问题定义

这本手册的起点，不是“我想多背一些 React 八股”，而是我已经在真实面试和真实项目里反复撞到了同一种问题：

我平时能写出基本正确的代码，也能避开很多低级错误。  
但一到 code review 场景，尤其是陌生代码、限时题、面试追问、复杂中后台页面，我往往做不到快速、稳定、成体系地识别问题，更做不到把问题讲清楚。

这说明我的问题不在“完全不会写 React”，而在另一层：

我有开发经验。  
我缺审查框架。  
我知道一些规范。  
我还没有把规范翻译成稳定的审查语言。  
我能修一些问题。  
我还没有形成高压场景下的快速定位路线。

所以，重建 React Code Review 体系，本质上是在补一块长期被忽略的能力底座。

## 1.2 成因

为什么已经写了多年 React，仍然会在 code review 上频繁失分，根因通常有五类。

第一，开发习惯和审查能力不是同一件事。  
很多问题你平时不会写错，不代表你能在陌生代码里快速识别出来，更不代表你能解释为什么错、会坏在哪里、应该怎么修。

第二，知识停留在“感觉层”，没有上升到“原则层”。  
比如你知道不能直接改 state，但如果不能立刻说出不可变更新、引用变化、浅比较、更新触发这条因果链，面试和 review 时就会失去说服力。

第三，长期依赖团队环境托底。  
ESLint、Prettier、组件库、已有项目模板、同事 review，会帮你挡掉很多问题。可一旦进入陌生代码，你就会发现脑中没有自己的巡检路线。

第四，缺少固定扫描顺序。  
看代码时容易东看一点、西看一点，最后只能得到“好像哪里都不太对”的感觉，无法形成高质量结论。

第五，中后台项目的复杂度被低估。  
表格、搜索区、图表、复杂表单、长 hook、联动请求，这些都不是 demo 难度。如果没有体系化 review 方法，复杂度很快就会超过直觉处理范围。

## 1.3 原则

重建 React Code Review 体系，必须先明确几个根原则。

第一，Code Review 不是挑毛病，而是识别风险。  
你要看的不是“有没有更优雅”，而是“这段代码会不会坏、会怎么坏、代价多大”。

第二，Code Review 不是随机浏览，而是按顺序巡检。  
没有固定扫描顺序，就没有稳定质量。

第三，Code Review 不是只看语法和风格，而是先看数据流、状态、交互、副作用和故障后果。  
高级前端和普通前端的分水岭，经常就在这里。

第四，Code Review 不该只停在指出问题，还要能给出最小修复路径。  
一个好的 reviewer，不会只说“这里不好”，而会说“这里最先该改哪一刀”。

第五，Code Review 最终要沉淀成可复用资产。  
它不应该只存在于当场发挥里，而应该逐步沉淀成规则、案例、模板和口述结构。

## 1.4 后果

如果不主动重建这套体系，会持续出现几类问题。

第一，面试里失分。  
你明明做过项目，也知道一些规范，但因为答题结构混乱，最后看起来像“只会写业务，不懂原理”。

第二，团队协作中 review 质量不稳定。  
有时能看出来，有时看不出来；有时先抓低优先级问题，有时漏掉主问题。

第三，复杂项目越做越虚。  
代码量一大，长 hook 一多，表格和搜索区一复杂，就会越来越不敢碰。

第四，很难把经验传给 AI 或同事。  
因为你自己脑中没有稳定框架，技能就无法复用。

第五，成长速度会变慢。  
因为每次都在零散补洞，而不是构建长期可调用的方法系统。

## 1.5 代码案例

这一章先不急着展开细节代码，而是先从你后面整本手册要反复使用的 SSAP 主案例说起。

### 案例一：长 hook 页面

像 `src/pages/dashboard/index.hook.tsx` 和 `src/pages/rules/config/index.hook.tsx` 这种文件，天然会带来三个挑战：

状态很多。  
副作用很多。  
联动关系很多。  

如果没有框架，看这种代码很容易只剩下“文件太长”的直觉。但真正重要的问题是：

职责是否失控。  
状态是否分层。  
请求是否有统一入口。  
副作用是否和真实依赖一致。  

### 案例二：基础组件

像 `src/components/table/index.tsx` 和 `src/components/search-form/index.tsx` 这类基础组件，一旦设计不稳，问题会被复制到大量页面。

所以你后面这本手册，不会只讲“某一行怎么写”，而会反复训练一种思路：

基础组件先看职责边界。  
再看数据流。  
再看异常闭环。  
再看是否把业务逻辑吞进公共层。  

### 案例三：第三方重型组件

像 `src/components/echarts/base-chart.tsx` 这类图表组件，最能暴露 React 项目里常见的副作用和性能问题。  
这会让你明白，性能 review 不是单独一章，它和状态设计、生命周期管理、事件绑定其实连在一起。

## 1.6 解法

重建体系，不靠“多看几篇文章”就能完成。它需要一条明确路线。

第一步，把 code review 的对象重新分类。  
不要再把所有问题混成一团。先按状态、列表、事件、副作用、异步、性能、安全、体验这些大类拆开。

第二步，建立固定扫描顺序。  
以后无论看陌生代码、同事 PR、笔试题，统一按同一路线巡检。

第三步，建立统一输出模板。  
每个问题都按“问题、原则、后果、修法”表达。

第四步，结合真实项目代码反复训练。  
不再只用 demo 练习，而是用 SSAP 这种真实中后台代码去对照。

第五步，把规则逐步沉淀成手册。  
先写总框架，再写核心章节，再写 64 条规则总表和面试模板。

## 1.7 快速定位

以后你只要出现下面几种感觉，就说明应该回到这本手册：

我觉得哪里不对，但说不清。  
我知道不该这么写，但解释不完整。  
这段代码能跑，但我不放心。  
文件很长，我不知道从哪里看起。  
表格、搜索区、图表、长 hook 一复杂，我就开始乱。  

这些都不是知识点不够多，而是框架还没建稳。

## 1.8 本章小结

这一章的结论只有一句话：

我要重建的，不是一套零散 React 规范，而是一套能服务真实项目、团队协作、面试表达和 AI 辅助的 React Code Review 体系。

后面的每一章，都会围绕这个目标展开。它们不是彼此独立的小技巧，而是同一套审查系统的不同切面。
