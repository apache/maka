# 第 13 章 面试中的 Code Review 输出模板

## 13.1 这一章要解决什么问题

前面第 1 到第 12 章，已经把整套 React Code Review 的底层框架、真实案例、Vercel 规则映射都搭起来了。  
但到真正面试时，很多人还是会卡住。

不是因为他没学过。  
而是因为他不会在高压场景下，把脑中的知识快速压缩成稳定输出。

这正是这一章要解决的问题。

这一章不再讲更多新知识点。  
这一章只做一件事：

把你已经学过的所有规则，压缩成面试现场可以直接说出口的模板。

你前面已经反复验证过了。  
面试里最容易失分的，不是完全不会，而是：

看到问题，说不清。  
知道不对，说不透。  
能修代码，说不出原理。  
抓到一个点，排不出优先级。  
回答像补漏洞，不像做审查。  

所以这一章的核心任务，是帮你建立一套“面试型 code review 输出系统”。

它要解决五个问题：

第一，拿到一段陌生代码，先从哪里开始看。  
第二，发现问题之后，怎么按优先级往外说。  
第三，怎么把零散问题讲成结构化回答。  
第四，怎么避免只说现象，不说原则和后果。  
第五，怎么让你的回答听起来像真正做过 review 的前端，而不是临场猜题的人。

---

## 13.2 为什么很多人面试里 review 题答不好

这里先不谈技巧，先把问题本质说透。

面试里的 code review 题，本质上考的不是“你会不会 React API”，而是三层能力。

第一层，识别能力。  
你能不能快速看到问题。

第二层，归类能力。  
你能不能判断这个问题属于状态、交互、副作用、异步、安全、性能、工程化中的哪一类。

第三层，表达能力。  
你能不能把问题说成一个完整链条：

是什么问题。  
违反了什么原则。  
会导致什么结果。  
应该怎么修。  

很多人平时写代码没问题，到了面试却答不好，原因通常有六个。

第一，没有固定扫描顺序。  
看到哪里说哪里，主次失衡。

第二，只记住了零散知识点，没有形成稳定分类。  
比如知道 `push` 不对，知道 `dangerouslySetInnerHTML` 危险，知道 `useEffect` 依赖要全，但这些都是散点。

第三，长期依赖项目环境托底。  
真实开发中，ESLint、团队规范、公共组件、同事 review 已经帮你挡掉很多问题。  
一到陌生代码场景，脑中路线图是空的。

第四，回答只停在“现象层”。  
常见说法是：“这里不太好”“这里最好别这样写”。  
这种回答几乎没有分量。

第五，没有优先级意识。  
先说内联样式，后说直接改 state。  
这会让面试官立刻判断你抓不住主问题。

第六，没有口头模板。  
脑中知道很多，但嘴里出不来。  
因为没有被压缩成可复用句式。

所以这一章后面所有模板，本质上都是在做同一件事：

把你的经验变成可调用的口头结构。

---

## 13.3 面试中的总答题框架

这一节先给你一版总框架。  
以后任何 React Code Review 题，先套这个外层结构。

### 总开场模板

> 我会先按固定顺序做 code review。  
> 先看模块职责和状态，再看列表与渲染结构，然后看事件和副作用，再看异步链路，最后补性能、安全和可维护性。  
> 我会优先说 P0 和 P1 级问题，也就是会直接导致错误结果、状态异常、请求异常或明显隐患的问题。

这段开场的价值很高。  
因为它会立刻把你的身份，从“随机找 bug 的人”切换成“有方法论的 reviewer”。

如果题目比较简单，你还可以更短一点：

> 我会先抓主问题，再补次问题。优先看 state、effect、异步和交互链路，因为这些最容易直接影响结果。

## 13.4 四段式模板：所有问题都要这样说

这是全章最重要的模板。  
你后面所有表达，都应该尽量往这个结构靠。

### 标准四段式

第一，这里有什么问题。  
第二，它违反了什么原则。  
第三，它会导致什么结果。  
第四，我建议怎么修。

这是你当前最该练到条件反射的一套结构。

### 通用句式版

> 这里有一个什么问题。  
> 它违反了什么原则。  
> 在当前代码里会导致什么结果。  
> 更稳的修法是什么。

### 例子 1：直接修改 state

> 这里直接修改了 state，违反了 React 的不可变更新原则。  
> 这样会让引用地址不变，React 做浅比较时可能无法正确识别状态变化，导致更新不稳定。  
> 更稳的修法是返回一个新数组，比如用函数式更新生成新引用。

### 例子 2：effect 依赖不完整

> 这里的 effect 用到了 `user.id`，但依赖数组没有把它纳入进来。  
> 这违反了副作用依赖和真实业务依赖保持一致的原则。  
> 后果是组件复用或条件切换时，容易出现漏请求、旧数据或逻辑漂移。  
> 建议把真实依赖补齐，并根据场景补上取消请求或时效保护。

### 例子 3：dangerouslySetInnerHTML

> 这里直接渲染 HTML 内容，存在 XSS 风险。  
> 它违反了默认不信任输入内容的安全原则。  
> 一旦数据源不可信，就可能把危险脚本注入页面。  
> 建议优先避免直接注入，或者在渲染前增加明确的清洗策略。

## 13.5 五类高频题的专用模板

面试里最常见的问题，其实可以压成五类。  
后面你只要对号入座，输出就会稳很多。

### 模板一：状态类问题

适用于：

直接改 state。  
派生状态过多。  
双数据源。  
状态职责混杂。  
setState 语义误判。

**句式模板**

> 这里主要是状态建模问题。  
> 它违反了单一数据源 / 不可变更新 / 最小状态这类原则。  
> 当前后果是状态容易漂移，后续副作用也会更难写。  
> 建议把真正的源状态收敛到一处，把派生结果移回计算层或 render 层。

### 模板二：交互类问题

适用于：

按钮冒泡。  
点击串扰。  
局部动作误触发父级。  
重复点击。  
禁用态和反馈不完整。

**句式模板**

> 这里主要是交互边界问题。  
> 当前一个动作会顺带触发另一个动作，交互意图不够单义。  
> 这会让用户操作结果不可预测，也让后续维护时很难判断动作边界。  
> 建议显式隔离事件传播，并把每个动作压回单一语义。

### 模板三：副作用与异步类问题

适用于：

effect 依赖不完整。  
重复请求。  
旧请求覆盖新结果。  
loading 不收口。  
错误恢复缺失。

**句式模板**

> 这里主要是副作用和异步链路问题。  
> 当前副作用触发条件与真实依赖没有完全对齐，或者请求生命周期没有形成完整闭环。  
> 后果是容易出现重复请求、旧数据、loading 卡死或失败无反馈。  
> 建议统一请求入口，补齐依赖和异常收口，并根据场景加入时效保护。

### 模板四：性能类问题

适用于：

整页重渲。  
图表重建。  
columns 重建。  
昂贵计算在 render 路径。  
首屏加载过重。

**句式模板**

> 这里是一个性能热点，但根因不一定只是少了 memo。  
> 更本质的问题是边界没有切清 / 输入不稳定 / 实例生命周期没有分层。  
> 后果是局部动作会带动大范围重渲，或者重型组件被反复初始化。  
> 建议先做边界隔离和生命周期分层，再看是否有必要补 memo 和缓存。

### 模板五：工程化与抽象类问题

适用于：

长 hook。  
长组件。  
基础组件被业务污染。  
伪抽象。  
props 膨胀。

**句式模板**

> 这里的问题不是单点写法，而是结构开始失控。  
> 当前模块同时承担了多类职责，或者基础抽象已经被页面特例持续污染。  
> 后果是后续需求越加，越难定位和复用，局部修改的影响范围也会越来越不可预测。  
> 建议先按职责和作用域拆边界，把页面特例回收到页面层，让公共层只保留稳定能力。

## 13.6 先说什么，后说什么：优先级模板

这是你后面必须反复练的部分。  
因为很多面试不是你不会，而是你先说错了重点。

### P0 优先说什么

P0 是会直接导致错误结果、状态异常、请求异常、安全风险的。

典型包括：

直接改 state。  
effect 依赖脱钩。  
请求异常不收 loading。  
旧请求覆盖新结果。  
dangerouslySetInnerHTML。  
关键 key 缺失导致状态错位。  
交互串扰导致错误动作触发。

### P1 接着说什么

P1 是高概率隐患，当前也许还能跑，但很容易继续恶化。

典型包括：

派生状态过多。  
基础组件职责过重。  
图表生命周期没分层。  
搜索区双数据源。  
长 hook 边界没拆。  
列表请求模型不统一。

### P2 最后补什么

P2 才是这些：

双等号。  
样式组织。  
命名稍弱。  
轻量可访问性缺口。  
低收益优化建议。

### 面试时的排序句式

> 我先说两个 P0 问题，再补两个 P1 隐患，最后再补几个细节问题。

或者：

> 我会先说会直接影响结果和稳定性的点，最后再补风格和维护性层面的问题。

这两句非常实用。  
它会立刻让面试官知道，你不是在乱找点。

## 13.7 五分钟 code review 题的实战模板

这是最贴近你大疆那道题的部分。  
你以后遇到类似题，直接套这套流程。

### 第一步：先开场定方法

> 我先按固定顺序扫一遍，优先看 state、effect、事件传播和异步链路，因为这些最容易直接影响结果。

### 第二步：先报两个最重的问题

比如：

> 第一，这里直接修改 state，是 P0。  
> 第二，这里的 effect 依赖和真实数据源不一致，也是 P0 或高 P1。

### 第三步：再补交互和安全

> 接着我会补交互串扰和安全风险。比如这个按钮点击可能会冒泡到父层，另一个是这里如果有危险内容直接注入页面，会有 XSS 风险。

### 第四步：最后补体验和小问题

> 最后再补几个细节，比如条件渲染可能把 0 渲染出来、列表 key 是否稳定、语义和可访问性是否完整。

### 第五步：每个点都按四段式展开

不要说：

“这里不太好，最好不要这样。”

要说：

“这里是一个什么问题，违反什么原则，会怎样坏，建议怎么改。”

## 13.8 如果面试官追问“为什么”，怎么接

这部分非常关键。  
因为很多人第一句能说对，一追问就空。

你要提前准备好三类“为什么”。

### 为什么 1：原理层为什么

适用于 state、effect、浅比较、引用类型。

**模板**

> 原因在于 React 更关注引用变化和依赖边界。  
> 如果这里直接改原对象或原数组，或者副作用依赖和真实业务值不一致，表面上看代码还能跑，但 React 的更新模型和你的业务模型就开始脱钩了。

### 为什么 2：工程层为什么

适用于长 hook、基础组件、伪抽象。

**模板**

> 这个问题今天未必立刻炸，但它会持续提高后续维护成本。  
> 因为一旦职责混在一起，任何新需求都只能继续往现有边界里堆，最后阅读、review 和修改成本都会一起上升。

### 为什么 3：用户层为什么

适用于体验、安全、交互。

**模板**

> 从用户视角看，这会让操作结果变得不可预测，或者让状态无法被区分。  
> 用户不关心你是不是少写了一个依赖，他只会觉得这个页面有时候没反应，有时候结果不对。

这三类“为什么”一定要练熟。  
因为面试官最喜欢做的，就是把你从“会说现象”往“能不能解释层”压。

## 13.9 面试中的三种长度模板

不是所有题都要讲一样长。  
你至少要准备三种长度。

### 模板 A：20 秒极简版

适合时间很紧、先抢重点。

> 我先说主问题。  
> 第一，这里直接修改 state，违反不可变更新原则，容易导致更新不稳定。  
> 第二，这个 effect 的真实依赖不完整，后续容易出现旧数据和漏请求。  
> 这两个是最值钱的问题，其他我再补交互和安全。

### 模板 B：60 秒标准版

适合大多数面试题。

> 我会先按状态、effect、交互、异步、安全这个顺序看。  
> 这段代码里最严重的一个问题是直接修改 state，它违反了 React 的不可变更新原则，后续会让引用不变，更新行为不稳定。  
> 第二个问题是 effect 依赖和真实数据源没有对齐，这会导致条件切换时出现漏请求或旧数据。  
> 再往下我会补交互串扰和安全风险，比如子按钮是否会冒泡到父层、危险内容是否会直接注入页面。  
> 最后再看条件渲染细节、key 和一些体验问题。

### 模板 C：90 秒结构化版

适合面试官明确让你“多讲一点”。

> 我会先按优先级说。  
> 先说 P0。第一，这里直接修改 state，属于状态建模错误，违反不可变更新原则，会导致 React 可能无法正确识别变化，建议改成函数式不可变更新。  
> 第二，这里的副作用依赖和真实数据源脱钩，后续在切换用户或复用组件时，容易出现漏请求、旧数据或逻辑漂移，建议把真实依赖补齐，并视情况加时效保护。  
> 再说 P1。这里的交互边界不够清晰，子级点击可能会触发父级行为，用户操作结果会变得不可预测，建议显式隔离事件传播。  
> 还有一个 P1 是异步闭环，如果请求失败没有完整收口 loading 或 error，界面会卡住或者给用户错误反馈。  
> 最后我再补安全和体验层，比如危险内容注入、条件渲染脏输出、key、语义和可访问性这些细节。

## 13.10 面试里的禁忌说法

这一节非常重要。  
有些说法你以后最好少用，因为它们会直接削弱你的分量。

### 禁忌 1：“这里感觉不太对”

问题是它没有信息量。  
你要尽量替换成：

这里有一个状态建模问题。  
这里有一个副作用依赖问题。  
这里有一个交互串扰风险。  

### 禁忌 2：“平时一般不会这样写”

这句话等于在说“我只会背规范，不会解释”。

更好的替换是：

它违反了什么原则。  
会导致什么结果。  
所以我会怎么改。

### 禁忌 3：“这里可以优化一下”

太空。  
你要说清楚：

是性能优化。  
是结构优化。  
是生命周期分层。  
还是输入稳定化。

### 禁忌 4：上来先说轻问题

比如先说样式、命名、双等号、内联对象。  
这会让面试官立刻判断你抓不住主问题。

### 禁忌 5：只说“为什么不推荐”，不说“为什么会坏”

面试官更想听后果链。  
比如：

会导致引用不变。  
会导致旧请求覆盖新结果。  
会导致 loading 卡死。  
会导致交互不可预测。

## 13.11 最后的总模板：一套可直接背的回答骨架

这一段你后面可以反复练，直到形成肌肉记忆。

> 我会先按固定顺序做 code review，优先看状态、effect、交互、异步和安全，因为这些最容易直接影响结果。  
> 如果先说最严重的问题，第一类通常是状态建模问题，比如直接修改 state、双数据源、派生状态过多，这类问题会让状态漂移或更新不稳定。  
> 第二类是副作用和异步链路问题，比如 effect 依赖脱钩、loading 不收口、旧请求覆盖新结果，这类问题会直接影响正确性和稳定性。  
> 第三类是交互边界问题，比如事件冒泡串扰、动作意图不单一，这会让用户操作结果不可预测。  
> 再往后我会补性能、安全、语义和工程化问题。  
> 我回答每个点都会尽量说清楚：这里有什么问题，违反了什么原则，会导致什么结果，建议怎么修。

这段一旦练熟，你以后无论遇到什么 React code review 题，开局都会稳很多。

## 13.12 本章小结

这一章最重要的价值，不在于再教你几个 React 知识点，而在于把前面所有知识压缩成了“面试现场可调用的输出结构”。

你应该带走四个结论。

第一，面试里的 code review，不是考你会不会 React API，而是考你能不能稳定识别、归类和表达问题。  
第二，所有问题都尽量往四段式上压：问题、原则、后果、修法。  
第三，优先级极其重要。先说 P0 和 P1，最后再补细节。  
第四，真正拉开差距的，不是你多背了多少零散点，而是你有没有把知识压成可重复输出的模板。

这一章之后，你已经具备进入第 14 章的条件了。  
下一步最合理的是进入第 14 章《React Code Review 64 条规则总表》，把整本手册最终收口成一套真正可冻结、可复用、可跨对话唤醒的规则系统。
