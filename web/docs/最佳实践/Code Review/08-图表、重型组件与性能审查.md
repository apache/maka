# 第 8 章 图表、重型组件与性能审查

## 8.1 问题定义

在 React 项目里，性能问题最容易被两种方式误解。

第一种误解，是把性能问题想得太窄。  
一提性能，就只想到 `useMemo`、`useCallback`、`React.memo` 这几个 API，好像只要把它们加上去，性能就被优化了。

第二种误解，是把性能问题想得太远。  
一提性能，就想到百万级数据、极端 benchmark、浏览器底层机制，好像只有那种级别才叫性能问题。

真实项目里的性能问题，尤其是中后台项目，更常见的情况是：

图表组件频繁销毁重建。  
表格列定义和 render 函数不断重建。  
搜索区一改，整页跟着重渲。  
第三方实例没有做生命周期分层。  
一个弹窗里挂了很多重型组件，打开就很卡。  
页面首屏把不该进主包的图表和编辑器全带进来了。  

所以这一章的任务，不是教你几个“性能技巧”，而是建立一套围绕图表、重型组件和真实页面渲染成本的审查框架。目标是系统判断：

哪些问题是真正的性能热点。  
哪些问题表面看是性能，根因其实是状态、副作用或组件边界。  
哪些优化值得做，哪些优化是过度优化。  
如何把性能问题讲成可落地的 review 语言，而不是空泛建议。  

---

## 8.2 成因

图表、重型组件与性能问题之所以高发，通常有七个根因。

第一，把性能问题后置。  
很多项目默认先跑通功能，等页面卡了再回头补。结果越往后改，成本越高。

第二，误把“API 记忆化”当成性能体系。  
开发者知道 `useMemo` 和 `useCallback`，却没有先判断渲染热点在哪里、边界怎么切、实例生命周期怎么分层。

第三，第三方实例型组件天然复杂。  
图表、编辑器、地图、播放器等都不是普通 JSX，它们有自己的实例生命周期、事件系统和资源占用。

第四，列表、表格、图表这些重型区域天生放大渲染成本。  
一个搜索条件变化，如果带动整页、整表、整图表一起更新，成本会很快累积。

第五，组件边界切得不清。  
明明只是局部数据变化，却把整个页面树都拖着重新执行。

第六，主包和首屏路径设计不严。  
很多重量级依赖本来可以懒加载，却被直接打进首屏。

第七，中后台页面很容易低估性能问题。  
因为它们不像 C 端动效那样直观，但用户会通过卡顿、慢、点了没反应来感受到质量下降。

---

## 8.3 原则

图表、重型组件与性能审查，统一遵循十条原则。

第一，先找热点原则。  
先判断哪里最重，再谈优化。不要一上来全局加 memo。

第二，边界优先原则。  
优化的第一刀通常不是加 Hook，而是把组件边界切对。

第三，实例生命周期分层原则。  
第三方实例的创建、更新、销毁、事件绑定要分层。

第四，局部更新原则。  
局部状态变化，应尽量只影响局部子树。

第五，稳定输入原则。  
传给重型组件的 props、options、callbacks、columns、data，要尽量稳定。

第六，首屏节制原则。  
图表、编辑器、富文本、地图等重型依赖，优先考虑按需加载。

第七，计算延后原则。  
昂贵计算和复杂转换，不要无脑放进每次 render。

第八，真实收益原则。  
优化要看是否真能减少渲染、实例重建或网络开销，避免“为了优化而优化”。

第九，用户感知原则。  
性能不是只看 profiler 数字，也看用户操作时是否卡顿、等待是否可解释。

第十，可维护性优先原则。  
一个难以理解的优化写法，如果收益很小，通常不值得引入。

---

## 8.4 后果

如果图表、重型组件与性能没有审查好，常见后果通常有十种。

第一，页面局部操作引发整页重渲。  
用户只是改了一个筛选值，整块 dashboard 都重新执行。

第二，图表不断销毁和重建。  
本来只是数据更新，却因为 effect 结构不当，实例被反复 dispose 再 init。

第三，弹窗打开明显卡顿。  
因为弹窗内部挂载了多个重型组件，且没有做懒加载或边界隔离。

第四，列表或表格滚动、筛选变慢。  
columns、render、筛选对象不断重建，放大渲染成本。

第五，首屏加载变重。  
首页把不必要的图表或编辑器直接打进主包，拖慢初始体验。

第六，交互看起来“没反应”。  
按钮点下去，界面要等很久才更新，用户无法判断系统是否收到操作。

第七，优化点越加越乱。  
到处都是 memo、callback、useMemo，但性能并没有明显改善。

第八，重型实例泄漏资源。  
observer、事件监听、实例对象没有对称清理，越用越重。

第九，review 无法聚焦。  
团队只会说“这里性能好像不太行”，却说不清热点、原因和改法。

第十，长期维护成本上升。  
页面越来越脆，任何改动都可能带来新的重渲或性能退化。

## 8.5 代码案例

这一章重点结合 SSAP 的三个主案例。

### 案例一：`src/components/echarts/base-chart.tsx`

这是图表与重型组件审查最核心的案例。

图表组件天然包含：

实例创建。  
配置更新。  
事件绑定。  
resize 监听。  
实例销毁。  

如果这些语义被揉在一个依赖 `options` 的 effect 里，就会出现非常典型的问题：

只要 options 变化，就先 cleanup，再重建实例。  
这样本来只是更新数据，却变成整套图表生命周期重走一遍。

这个问题表面上像“可以优化”，实质已经是设计层问题。  
因为它违反了实例生命周期分层原则。

高质量 review comment 应该这样写：

“当前图表组件把实例创建、配置更新和事件绑定放进了同一层副作用，导致 options 变化时可能触发不必要的实例销毁与重建。建议将实例初始化与销毁独立出来，将 setOption 作为单独更新路径，事件绑定解绑单独管理。”

另一个值得专项检查的点，是 resize 处理。

你要问：

resize 监听是否稳定。  
组件卸载时是否解除 observer。  
防抖函数是否会重复创建。  
图表 resize 是否在不可见状态下也被频繁触发。  

### 案例二：`src/pages/dashboard/index.hook.tsx`

dashboard 页面是性能 review 的天然主战场。

因为这里往往同时存在：

筛选条件。  
图表数据。  
多个卡片。  
弹窗表格。  
默认值初始化。  
联动请求。  

这种页面最容易出现的不是单点 bug，而是“局部状态改动牵动整页”。

你做 review 时，要特别看：

哪些 state 改了会带动整个 dashboard 重跑。  
图表 options 是否每次重建。  
某个筛选动作是否会让无关图表也刷新。  
弹窗状态是否影响主页大区域渲染。  
重型子组件是否有边界隔离。  

高质量 review 语言应该是：

“当前 dashboard 页面中筛选条件、图表数据和弹窗控制耦合较深，局部交互可能带动大面积子树重新执行。建议按筛选区、图表区、弹窗区拆分边界，并尽量保证图表输入稳定。”

### 案例三：`src/components/table/index.tsx` 与 `src/components/search-form/index.tsx`

性能问题并不只在图表里，表格和搜索区同样是热点。

表格场景要重点看：

columns 是否每次 render 重建。  
cell render 是否做了昂贵逻辑。  
列表刷新后 selectedRows 是否导致额外重渲。  
分页变化是否让整个页面跟着刷新。  

搜索区场景要重点看：

每次输入是否触发整页更新。  
tags、formData、selectedChild 等状态是否彼此联动导致多余重渲。  
复杂 children 解析是否每次都重新做。  
搜索条件变化是否拖着表格和图表一起刷新。  

高质量 review 不能只说“这里可以 memo 一下”。  
更准确的说法是：

“当前搜索区状态改动会带动较大范围 UI 重跑，建议先明确查询源和局部边界，再评估是否需要对派生计算和子组件输入做稳定化处理。”

### 案例四：首屏与重型依赖

虽然 SSAP 主要是中后台项目，但依然要有首屏路径意识。

任何重型依赖都要多问一句：

它是否必须首屏就加载。  
它是否只在弹窗中使用。  
它是否可以按需加载。  
它是否可以等用户进入具体场景再加载。  

图表、富文本、复杂编辑器、导出模块、地图 SDK 这些，都是首屏 review 的重点目标。

## 8.6 解法

图表、重型组件与性能审查，建议固定成一条十步路线。

### 第一步：先找真正的热点区域

先问页面里什么最重：

图表。  
表格。  
复杂搜索区。  
弹窗里的富组件。  
首屏大依赖。  

不要一上来全局找优化点，先抓最重的。

### 第二步：判断问题属于哪一类

很多“性能问题”其实有不同根因。

有些是状态边界问题。  
有些是 effect 结构问题。  
有些是 props 不稳定。  
有些是实例生命周期没分层。  
有些是首屏加载策略不合理。  

先分类，后给建议。

### 第三步：先切边界，再谈 memo

性能优化的第一刀，通常是边界隔离。

比如：

把 dashboard 拆成筛选区、图表区、弹窗区。  
把大表格拆成外层容器和内层纯展示。  
把搜索区中的重逻辑从 render 路径移走。  

如果边界不对，再多 memo 也只是补丁。

### 第四步：专项检查第三方实例生命周期

面对图表、编辑器、播放器，固定问：

实例什么时候创建。  
什么时候只更新配置。  
什么时候销毁。  
事件如何解绑。  
observer 如何清理。  

### 第五步：检查重型组件输入是否稳定

重点看：

options。  
data。  
columns。  
callbacks。  
formatter。  
render 函数。  

这些输入如果每次都是新引用，很多 memo 和实例优化都会失效。

### 第六步：检查昂贵计算是否在 render 路径

比如：

大型数据转换。  
树结构拍平。  
复杂 filter 和 map。  
多层 children 解析。  

这类计算应优先考虑提取、缓存或延后，而不是每次 render 都重算。

### 第七步：检查局部动作是否拖动整页

一个很有价值的问题是：

“这个 state 改动之后，理论上谁该更新，实际上谁在更新？”

如果理论上只该更新局部，实际上整页都动了，问题就很明确。

### 第八步：检查首屏与懒加载策略

重型依赖优先判断：

首屏必须吗。  
可以按路由分包吗。  
可以按交互触发加载吗。  
可以在弹窗打开时再加载吗。  

### 第九步：判断当前优化是否值得

不是所有地方都值得加 memo。  
要问：

收益大吗。  
复杂度会增加多少。  
后续维护会不会更难。  

### 第十步：最后给出最小收益最大的改法

例如：

先拆图表实例生命周期。  
再隔离 dashboard 边界。  
再稳定 columns 和 options 输入。  
最后才考虑局部 memo 和缓存。  

这样路径更清楚，也更容易落地。

## 8.7 快速定位

以后你看到任何图表页、dashboard 页、重型弹窗、复杂表格页，先问这十个问题。

这个页面真正最重的区域在哪里。  
它的问题是边界、状态、effect，还是输入不稳定。  
第三方实例的创建、更新、销毁是否分层。  
图表或编辑器会不会因为 props 变化被反复重建。  
局部 state 改动是否带动整页重跑。  
columns、options、callbacks 是否不断新建。  
昂贵计算是否在 render 路径。  
首屏是否加载了本可延后的重型依赖。  
现有优化是否真的减少了渲染和实例重建。  
这条优化建议是否值得引入额外复杂度。  

只要这十问形成条件反射，你对性能问题的判断会更接近真实收益，而不是停留在 API 层面。

---

## 8.8 本章小结

图表、重型组件与性能审查，最怕两个极端。

一个极端是完全不看性能，等页面卡了再说。  
另一个极端是到处乱加 memo，以为这就是性能优化。  

这一章最重要的收获，是建立三种能力。

第一，学会先找真实热点，再谈优化。  
第二，学会把第三方实例放回生命周期分层视角里看。  
第三，学会把性能问题翻译成“边界、输入、实例、首屏路径”这四类稳定语言。  

当你能稳定做到这三点，性能 review 就不再是零散技巧，而会真正变成你 code review 体系里的一个成熟分支。
