# React Code Review 规则速查表（64 + 7 条补遗）

## 使用方法

先按 8 大组定位，再按规则编号快速检查。每条规则都压成一句原则，优先用于看 PR、做项目复盘和准备面试。

## 第一组：状态建模与数据流 8 条

- **R01 单一数据源优先于多份状态副本**：同一业务事实，尽量只维护一份主状态。
- **R02 派生值优先计算，不优先存储**：能从已有状态、props、children 算出来的值，不优先再存一份。
- **R03 不可变更新是 React 状态安全的底线**：更新对象和数组时，用新引用表达变化，不直接改原值。
- **R04 state 只存业务事实，不存 UI 结果**：state 优先表达“是什么”，不是“已经渲染成什么”。
- **R05 setState 语义不能误判成同步赋值或 promise**：不要用错误心智模型组织状态时序。
- **R06 状态粒度过粗，会放大更新范围**：只让真正需要更新的区域被更新。
- **R07 页面级状态、局部状态、表单状态、服务端状态要分层**：不同来源的状态不能糊成一层。
- **R08 状态设计要先问“以后 effect 会不会更难写”**：状态问题往往先伤副作用。

## 第二组：事件、交互与副作用 8 条

- **R09 一个动作尽量只表达一个主意图**：事件单义，比“顺手做很多事”更稳。
- **R10 事件传播路径必须可控**：该冒泡的冒泡，该阻止的阻止。
- **R11 effect 只做副作用，不做万能补丁**：effect 是同步外部事实的工具，不是修一切状态的工具。
- **R12 effect 依赖必须和真实业务依赖一致**：依赖数组在声明关系，不是在安抚 linter。
- **R13 cleanup 必须对称**：订阅、observer、事件绑定、实例都要有对应清理。
- **R14 交互反馈必须闭环**：用户做了动作，界面要明确回应。
- **R15 复杂页面要优先检查“隐式副作用链”**：一个状态变化会触发几条链，越多越危险。
- **R16 第三方实例的创建、更新、销毁、事件绑定必须分层**：这是第三方实例组件的基本纪律。

## 第三组：异步请求与错误恢复 8 条

- **R17 同一页面的请求入口尽量统一**：初始化、搜索、翻页、重置、操作回刷，优先收敛成单一请求模型。
- **R18 loading 必须成功失败都能收口**：打开 loading，就必须设计关闭 loading。
- **R19 error 和 empty 不能混成一种状态**：失败不等于没有数据。
- **R20 旧请求不能覆盖新结果**：异步结果回写时必须确认它还属于当前视图。
- **R21 请求失败后，页面必须有恢复路径**：失败不是终点，失败后还要能继续用。
- **R22 联动请求必须明确触发源**：字段变化触发请求时，要能说清谁驱动谁。
- **R23 批量操作、删除、提交后的回收规则必须统一**：操作结束后，页面状态要按规则回收。
- **R24 基础组件的异步设计要按“故障放大器”标准审查**：公共层一旦异步设计不稳，问题会成倍复制。

## 第四组：列表、表格与搜索区 8 条

- **R25 列表渲染必须有稳定 key**：key 是列表身份系统，不是消除警告的装饰。
- **R26 搜索条件必须有唯一可信来源**：form、state、tags、params 不能各说各话。
- **R27 搜索、翻页、重置、刷新要共用同一请求模型**：同类行为尽量同源。
- **R28 重置动作必须单独审查**：重置不是清空几个字段，而是一次状态回收动作。
- **R29 selectedRows 的生命周期必须显式**：勾选态不是小细节，它是页面状态。
- **R30 columns 和 render 函数是表格性能热点，必须重点扫**：表格性能经常死在“看起来只是个 render”。
- **R31 搜索区复杂度的本质，不在控件数量，而在状态关系**：复杂搜索区最怕多份状态副本和派生 UI 堆叠。
- **R32 基础搜索组件如果继续成长，应尽快从结构驱动转向 schema 驱动**：children 驱动适合早期，复杂联动场景更适合 schema 驱动。

## 第五组：图表、重型组件与性能 8 条

- **R33 先找性能热点，再谈优化**：不是所有地方都值得优化，先抓最重的区域。
- **R34 性能优化第一刀通常是切边界，不是堆 memo**：结构边界对了，很多优化自然成立。
- **R35 第三方实例必须按“创建、更新、销毁”三层分开**：实例生命周期分层是重型组件的基本纪律。
- **R36 重型组件的输入必须稳定**：options、data、columns、callbacks 如果一直变，新引用会吞掉所有优化收益。
- **R37 昂贵计算不要无脑放在 render 路径**：昂贵计算应提取、缓存或延后。
- **R38 局部动作不应拖动整页**：理论上谁该更新，实际上就尽量只让谁更新。
- **R39 重型依赖优先考虑按需加载**：图表、编辑器、富文本、地图等，先问是否必须首屏加载。
- **R40 优化建议必须看真实收益，不做形式优化**：一个更难懂的写法，如果收益很小，通常不值得。

## 第六组：工程化、可维护性与基础抽象 8 条

- **R41 长文件的核心问题不是行数，而是职责数量**：太长不是结论，职责混装才是结论。
- **R42 长 hook 优先按作用域拆，不优先按代码块拆**：先按页面区域和行为作用域切，不要只机械分文件。
- **R43 复杂表单优先按主状态、选项数据、模板系统、提交编排分层**：复杂表单页的结构分层要比控件本身更重要。
- **R44 基础组件最怕业务污染**：公共层越往下，越应该承载能力，而不是页面特例。
- **R45 真正的抽象必须有稳定输入、稳定输出、稳定语义**：看起来复用了，不等于抽象成功了。
- **R46 命名和目录结构必须支持快速建图**：别人第一次进来就应该大致看懂职责。
- **R47 公共层故障要按“扩散半径”审查**：一个公共模块出问题时，会波及多少页面，要作为 review 标准之一。
- **R48 重构建议必须给“最小重构路径”**：不要只说建议拆、建议重构，要说先拆哪一刀。

## 第七组：安全、语义、无障碍与体验 8 条

- **R49 危险内容默认不可信**：看到 HTML 注入、富文本插入，先进入安全审查。
- **R50 交互优先使用原生语义元素**：能用 button 就别用 div 模拟按钮。
- **R51 loading、empty、error、无权限必须可区分**：不同状态不能长成同一种空白。
- **R52 错误提示必须能帮助恢复**：错误信息不是为了“报错”，而是为了让用户继续走下去。
- **R53 表单辅助信息必须服务于理解**：label、placeholder、必填提示、禁用原因都属于体验系统。
- **R54 重要交互必须可通过键盘完成**：鼠标不是唯一输入设备。
- **R55 操作反馈必须闭环**：点了之后，要知道系统有无响应。
- **R56 同类页面的体验规则应尽量一致**：一致性本身就是可用性。

## 第八组：面试与 Review 输出模板 8 条

- **R57 开场先报方法，不要直接乱说点**：先让面试官知道你有扫描顺序。
- **R58 先说 P0 和 P1，再补 P2 细节**：优先级比问题数量更重要。
- **R59 所有问题都尽量压成四段式**：问题、原则、后果、修法，是面试表达的主骨架。
- **R60 先归类，再展开**：说“这是状态问题”“这是异步闭环问题”，会显得你很稳。
- **R61 面试里尽量少说“感觉”“一般不这么写”**：感觉型表达没有分量。
- **R62 追问“为什么”时，要准备原理层、工程层、用户层三种回答**：不要只会说现象，要能往下走三层。
- **R63 准备 20 秒、60 秒、90 秒三种长度答案**：同样一个问题，不同面试节奏要有不同长度模板。
- **R64 最终目标不是“多找问题”，而是“像真正 reviewer 一样说话”**：高水平面试输出，像在做真实 review，不像在猜题。

## 补遗一（R65-R67，2026-09，题库答案键与 Vercel 70 条对齐）

- **R65 独立请求并行发起**：相互不依赖的请求用 Promise.all 并行，不人为串行。（归第三组异步；Vercel `async-parallel`，CRITICAL 级，原 64 条盲区）
- **R66 条件渲染不用 `&&` 兜数字**：表达式可能为 0 时用三元或显式布尔，否则 0 会被渲染上屏。（归第五组渲染；源自原题考点）
- **R67 状态写入前先过业务约束**：去重、存在性、权限校验在写入前做，不交给 UI 兜底。（归第一组状态；源自原题考点）

## 补遗二（R68-R71，2026-09，maka 实战复盘，通用 review 规则）

- **R68 测试有效性**：fixture 形状 ≠ 生产 producer 真实发出的形状时，测试证明的是 fixture 而非系统。（maka #4506）
- **R69 write-only 机制按死代码审查**：参与不进任何决策的状态与记录，读起来像仍在参与。（maka #4518）
- **R70 哨兵值按真实形状写**：首图/初始实体往往是 0、空串、空对象，不是 undefined。（maka #4514）
- **R71 交付物一致性**：PR 正文/Summary/Checklist 与 diff 矛盾 = P1，正文也是交付物。（maka #4506）
