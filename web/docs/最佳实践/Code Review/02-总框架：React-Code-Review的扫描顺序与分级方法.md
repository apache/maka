# 第 2 章 总框架：React Code Review 的扫描顺序与分级方法

## 2.1 问题定义

React Code Review 最容易出的问题，不是知识点不会，往往是顺序乱。

很多人拿到一段代码，会在几个局部来回跳：

先看到 state，想到一点。  
又跳去 JSX，看出一个条件渲染问题。  
又回到 useEffect，感觉依赖不太对。  
再扫两眼样式和事件。  
最后脑子里似乎到处都有问题，嘴上却说不完整。

这类 review 方式很像随机搜索。它会导致三个结果。

第一，抓不到主问题。  
第二，问题优先级排序不稳。  
第三，输出像补 bug，不像做审查。

所以这一章的任务只有一个：

建立一套固定扫描顺序、严重级别划分和统一输出模板。

以后你不管看陌生代码、同事 PR、项目旧代码，还是现场笔试题，都用同一套路线图。

## 2.2 成因

为什么需要固定扫描顺序，根因有三层。

第一层，没有顺序就会先抓低价值问题。  
比如内联样式、命名、空值判断和直接修改 state、effect 依赖脱钩、安全风险，价值根本不在一个层级。

第二层，没有顺序就容易遗漏。  
你今天看到了 key，明天漏了竞态，后天又漏了副作用清理，review 质量始终不稳定。

第三层，没有顺序就很难形成面试表达。  
高级前端能把 review 讲得像体系，普通前端只能讲成零散感觉。

## 2.3 原则

这一章的总原则有五条。

第一，先看系统性，再看局部。  
先看模块边界、状态、数据流和请求链路，再看语法和风格。

第二，先看故障后果，再看规范本身。  
不要只说不规范，要说会如何坏。

第三，先做归类，再给结论。  
把问题稳定归进状态、交互、副作用、异步、安全、性能、维护性等类别。

第四，先分级，再排序。  
P0 和 P3 不能混着说。

第五，所有输出统一用“问题、原则、后果、修法”。  
这条是后面整本手册最重要的表达骨架。

## 2.4 后果

如果没有这套总框架，会持续出现四类后果。

第一，review 结论总是漂。  
今天说得多，明天说得少，没有稳定覆盖面。

第二，总是先抓枝叶，漏掉主干。  
主问题没抓住，再多 comment 都显得轻。

第三，面试里容易被追问打穿。  
因为你只是在说现象，没有建立原则和后果链路。

第四，很难沉淀出团队级和个人级方法论。  
没有统一扫描顺序，就没有统一规则体系。

## 2.5 代码案例

这一章先给出扫描顺序，不急着细抠某一行代码。后面章节会把规则落到 SSAP 具体文件。

### 案例一：长 hook 文件

看到 `dashboard/index.hook.tsx` 或 `rules/config/index.hook.tsx` 这种大文件，第一眼不是问哪行有问题，而是先问：

职责是否混杂。  
状态来源是否过多。  
副作用和请求是否可追踪。  

### 案例二：基础组件

看到 `table/index.tsx`、`search-form/index.tsx` 这类基础组件，第一眼也不是先找样式问题，而是看：

它是不是承担了过多业务语义。  
它的状态和请求模型是否统一。  
它会不会把故障放大到所有接入页。  

### 案例三：第三方实例组件

看到 `base-chart.tsx` 这种组件，就要直接联想到：

实例创建和销毁。  
配置更新。  
事件绑定与解绑。  
资源释放。  
性能和副作用是不是混在一起。  

## 2.6 解法

这里冻结一版总扫描顺序 1.0。

### 第一层：先看模块边界和职责

先问：

这个组件或 hook 到底负责什么。  
它是不是承担了太多职责。  
状态来源是不是过多。  
数据流是不是一眼能读懂。  

### 第二层：再看状态与数据流

固定问：

有没有直接修改 state。  
有没有重复状态、派生状态、双数据源。  
状态粒度是不是过重。  
props、local state、store 三者是否可能漂移。  
能算出来的值，是否被错误放进 state。  

### 第三层：再看渲染结构与交互链路

固定扫：

列表是否有稳定 key。  
条件渲染是否会出现脏输出。  
事件是否会冒泡串扰。  
局部交互是否误触发外层逻辑。  
大列表、大表格、大表单是否存在明显的重渲风险。  

### 第四层：再看副作用与异步请求

重点看：

effect 依赖是否完整。  
请求是否有 loading、error、empty。  
是否有重复请求。  
是否存在竞态、过期响应、卸载后回写。  
是否有缓存意识。  
cleanup 是否对称。  

### 第五层：最后看性能、维护性、安全与体验

最后补：

是否有无意义重渲。  
第三方实例生命周期是否分层。  
长组件、长 hook 是否影响维护。  
是否存在 XSS 风险。  
是否具备基础语义与可访问性。  
是否有用户体验层面的空白区域。  

这五层顺序，就是整本手册后续的总入口。

### 分级方法

统一采用 P0 到 P3 四级。

P0：错误结果、明确故障、明显安全风险。  
P1：高概率隐患、重要链路不完整、性能和稳定性会持续恶化。  
P2：中等级别问题，影响代码质量和体验。  
P3：风格层和一致性层，可提但不能先提。  

### 统一输出模板

这里有一个什么问题。  
它违反了什么原则。  
它会导致什么结果。  
建议怎么修。

这就是后面所有 comment 和面试表达的统一骨架。

## 2.7 快速定位

以后做 React Code Review，统一按下面顺序启动：

先看职责。  
再看状态。  
再看结构和交互。  
再看 effect 和异步。  
最后补性能、安全、维护性和体验。  

只要这条顺序形成条件反射，你的 review 质量就会迅速稳定下来。

## 2.8 本章小结

这一章解决的是“先看什么、先说什么”。

它给整本手册提供了三个底座：

固定扫描顺序。  
统一问题分级。  
统一表达模板。  

后面各章展开的所有规则，都必须回到这个总框架上，否则章节再多，也只会重新散掉。
