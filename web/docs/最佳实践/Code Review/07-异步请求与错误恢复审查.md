# 第 7 章 异步请求与错误恢复审查

## 7.1 问题定义

在 React 中后台项目里，异步请求几乎无处不在。

列表页要请求。  
搜索区要请求。  
弹窗打开要请求。  
表单联动要请求。  
图表切换要请求。  
初始化要请求。  
批量操作结束后还要再次请求。  

所以很多页面真正的复杂度，不在 JSX，也不在样式，而在“请求是怎么发的，结果是怎么回来的，失败之后页面会怎样”。  
这正是 code review 里非常高价值的一章。

因为异步代码有一个很危险的特征：

功能演示时常常能跑通。  
边界条件、竞态、失败分支、重复请求、loading 卡死、过期回写，却往往要到真实使用时才暴露。

所以这一章的任务，是建立一套针对“异步请求与错误恢复”的专项审查框架。目标不是只会看 `fetch` 或 `await`，而是要系统判断：

请求触发源是否单一。  
请求结果是否和当前视图匹配。  
异常分支是否有闭环。  
loading、error、empty 是否完整。  
失败后用户是否还能恢复。  
哪些问题属于显性故障，哪些问题属于迟早会炸的隐患。  

---

## 7.2 成因

异步请求和错误恢复之所以容易出问题，通常有七个根因。

第一，请求触发点分散。  
初始化发一次，翻页发一次，搜索发一次，重置发一次，删除完又发一次。每个地方都能刷新，但没有统一入口，后续维护会非常痛苦。

第二，开发时默认走成功路径。  
很多代码只把“请求成功返回数据”这条链路写通，没有认真设计失败、超时、空数据、权限不足、部分字段缺失等分支。

第三，loading 被当成顺手加的 UI 状态。  
加了开始 loading，却没有保证在成功和失败两个分支都对称关闭。

第四，请求结果默认可直接回写。  
代码假设“只要请求回来了就说明还能用”，没有判断页面是否已切换、条件是否已变化、组件是否已卸载。

第五，错误恢复策略缺失。  
请求失败之后，用户是能重试、能返回、能看到错误原因，还是只能看到一个空白区域，很多页面没有认真设计。

第六，复杂表单和联动请求没有分层。  
字段一改就触发请求，请求回来又改字段，字段再变又触发请求，最后链路越来越脆。

第七，中后台项目经常把异步复杂度藏起来。  
一个 CRUD 页面看起来很普通，但一旦带上搜索、分页、批量操作、弹窗详情、图表联动，请求复杂度立刻翻倍。

---

## 7.3 原则

异步请求与错误恢复审查，统一遵循九条原则。

第一，请求入口统一原则。  
同一页面的初始化、搜索、翻页、重置、刷新、操作后回刷，尽量走统一请求模型。

第二，状态闭环原则。  
每个请求至少要考虑 loading、success、error、empty 这几个基础状态，并保证状态流转完整。

第三，异常对称原则。  
成功分支怎么收状态，失败分支也要同样收状态，不能只写 happy path。

第四，结果时效原则。  
异步结果回写前，要确认它仍然属于当前页面、当前条件、当前用户动作。

第五，失败可恢复原则。  
请求失败后，页面不应只停在报错或空白，应该给用户至少一种继续操作的路径。

第六，去重与竞态控制原则。  
重复触发的请求要考虑防抖、取消、版本戳、最新响应优先等策略。

第七，错误可解释原则。  
失败时至少要让用户知道发生了什么，而不是只在控制台里报一条错误。

第八，基础组件异常兜底原则。  
基础表格、基础图表、基础弹窗这类公共组件，要特别警惕异常状态是否会被放大到所有页面。

第九，操作后回收一致原则。  
新增、删除、批量操作、提交成功后，页面状态应该如何回收，要有一致规则。

## 7.4 后果

如果异步请求与错误恢复没有审查好，常见后果通常有十种。

第一，页面卡在 loading。  
请求失败了，但 loading 没关，用户会以为系统一直在转。

第二，旧请求覆盖新结果。  
用户刚切换条件，旧请求后返回，把新结果冲掉。

第三，空数据和错误状态混淆。  
页面看起来“没有数据”，其实是请求失败。

第四，重复请求浪费资源。  
一次动作触发多次请求，后端压力上升，前端状态也开始不稳定。

第五，用户无法恢复。  
请求失败后没有重试、没有提示、没有退路，只能刷新整个页面。

第六，基础组件故障放大。  
公共表格组件一旦 loading 或错误处理不完整，所有接入页面都会受影响。

第七，数据和分页失同步。  
用户做完操作后，列表刷新了，但页码没回收，或者删到最后一条后还停在空页。

第八，弹窗和详情态错乱。  
用户已经关闭弹窗，请求回来后又把旧内容写进状态。

第九，问题难定位。  
你分不清到底是请求没发、请求失败、结果回写错了，还是状态回收没做好。

第十，用户对系统失去信任。  
因为从用户视角看，页面有时无响应，有时重复刷新，有时空白，有时突然跳回来。

## 7.5 代码案例

这一章重点结合 SSAP 的三个主案例来讲。

### 案例一：`src/components/table/index.tsx`

这是异步请求与错误恢复审查最典型的基础组件案例。

表格组件通常承担这些异步职责：

发列表请求。  
切换 loading。  
接收分页信息。  
格式化结果。  
同步 selectedRows。  
响应翻页与刷新。  

这里最值得 review 的，不是“会不会发请求”，而是：

请求是不是统一入口。  
loading 是否成功失败都能关闭。  
异常后表格会呈现什么。  
空数据和错误状态是否可区分。  
分页和参数是否在异常后还能保持一致。  

这个组件里最适合写进手册的案例，就是 `try/finally` 缺失问题。

如果请求过程里只在成功后关闭 loading，失败时不回收，整个表格就会卡在转圈状态。  
这是非常典型的 review 训练点，因为它逼你学会从“界面状态闭环”角度看问题。

高质量 comment 应该这样写：

“这里的请求缺少对 loading 的异常对称收口。一旦接口抛错，表格会长期停留在 loading。建议将 loading 打开与关闭包进统一请求函数，并通过 try/finally 保证成功失败都能回收。”

### 案例二：`src/pages/rules/config/index.hook.tsx`

复杂规则配置页特别容易出现联动请求混乱。

这种页面经常有：

字段 A 改变，去请求枚举。  
字段 B 改变，去请求模板。  
模板回来，再注入表单项。  
表单项变化，又影响别的字段。  

这类页面最该 review 的，不是“接口调没调通”，而是：

联动请求是否有明确触发源。  
旧请求回来时，当前字段条件是否仍然有效。  
失败后动态表单是否会落入半残状态。  
用户是否知道当前字段为什么没出来。  

这种场景里，一个很值钱的 review 问题是：

“如果 formatId 已经变了，旧的模板请求回来后还能直接写进表单吗？”

一旦不能回答清楚，就说明当前异步结果时效性没有设计好。

### 案例三：`src/pages/dashboard/index.hook.tsx`

首页 hook 里通常会有多组请求同时存在。

初始化请求。  
默认值请求。  
图表请求。  
弹窗内表格请求。  
筛选联动请求。  

这类场景最容易出的问题，不是单个请求写错，而是请求关系不清。

你做 review 时要先问：

哪些请求是初始化时必发。  
哪些请求依赖用户筛选。  
哪些请求依赖弹窗开关。  
同一个业务动作会不会同时触发两条请求路径。  

如果这些关系不清，就很容易出现：

页面一打开，重复请求两次。  
筛选一改，图表和弹窗都刷新。  
弹窗已关闭，内部请求还在回写。  

高质量 review 语言应该是：

“当前首页 hook 中多组请求的触发边界不够显式。建议按初始化请求、筛选驱动请求、弹窗作用域请求三类分层，避免交叉触发和过期回写。”

## 7.6 解法

异步请求与错误恢复审查，建议固定成一条十步路线。

### 第一步：先列出页面的所有请求源

不要急着看实现。  
先列出：

初始化。  
搜索。  
翻页。  
重置。  
弹窗打开。  
字段联动。  
批量操作后刷新。  
手动点击刷新。  

把所有入口先列出来。

### 第二步：判断哪些入口应统一

很多页面的真正问题，不是请求多，而是请求入口太散。

你要问：

这些动作本质上是不是都在做“刷新当前列表”。  
这些动作能不能复用同一个请求函数。  
参数构造能不能集中。  

统一入口是降低复杂度最有效的一刀。

### 第三步：检查状态闭环

每个请求至少确认四件事：

开始时是否进入 loading。  
成功时是否退出 loading 并更新 success/empty。  
失败时是否退出 loading 并进入 error。  
重试时是否能重新走完整流转。  

### 第四步：专项检查异常分支

很多代码只在 `try` 里写逻辑，没有认真设计 `catch`。

你要问：

接口异常时页面会显示什么。  
用户能不能知道失败。  
基础组件会不会卡死。  
失败后是否还能继续操作。  

### 第五步：专项检查结果时效性

任何依赖用户当前条件的请求，都要问：

请求回来时，条件还是不是原条件。  
组件是不是还在。  
弹窗是不是还开着。  
这条结果是不是最新的一条。  

### 第六步：判断是否需要取消或版本保护

不是每个请求都必须上 AbortController，但要有判断意识。

以下场景优先考虑：

搜索输入频繁触发。  
筛选条件快速切换。  
弹窗开关频繁。  
同一个资源短时间内会重复请求。  

可以采用的手段包括：

取消请求。  
请求序号。  
最新响应优先。  
防抖。  
统一缓存层。  

### 第七步：检查错误恢复路径

失败后页面至少应该提供一种恢复方式：

重试按钮。  
保留原有数据。  
回退到上一个稳定状态。  
给出清晰的报错提示。  

### 第八步：检查操作后回收规则

新增、编辑、删除、批量操作之后，要明确：

是否回第一页。  
是否保留搜索条件。  
是否清空 selectedRows。  
是否更新总数。  
是否关闭弹窗。  

这一步非常重要，因为很多“异步问题”其实是在操作后状态回收阶段暴露出来的。

### 第九步：检查基础组件是否放大故障

公共 Table、SearchForm、BaseChart、Modal，如果请求和错误恢复设计不稳，会把同一类故障复制到所有页面。

所以 reviewer 对基础组件要更苛刻。

### 第十步：最后给出最小修复路径

比如：

先补 loading 的 try/finally。  
再补 error 提示与重试。  
再做请求入口统一。  
最后补竞态保护和缓存策略。  

这样修改成本最可控。

## 7.7 快速定位

以后你看任何含异步请求的 React 页面，先问这十个问题。

请求是从哪里触发的。  
这些触发源能不能统一。  
loading 是否成功失败都能关闭。  
error 和 empty 能不能区分。  
失败后用户能怎么恢复。  
请求回来时页面状态还是原来那个状态吗。  
会不会出现旧请求覆盖新结果。  
操作成功后哪些状态需要回收。  
基础组件会不会把故障放大。  
这个页面是否只设计了成功路径。  

只要这十问形成条件反射，你对异步问题的识别速度会明显提高。

---

## 7.8 本章小结

异步请求与错误恢复，是 React 中后台项目里最容易“功能能跑、边界全漏”的一章。

这一章最重要的收获，不是再多背几个 `try/catch` 写法，而是建立三种能力。

第一，学会把请求问题放回“触发源、结果回写、状态闭环”三段结构里看。  
第二，学会把错误恢复当成页面设计的一部分，而不是接口失败后的附属品。  
第三，学会把基础组件的异步设计当成故障放大器来审查。  

当你能稳定做到这三点，很多过去看起来零碎的 loading、竞态、空态、失败态问题，就会自动被你归类进同一套 review 框架里。
