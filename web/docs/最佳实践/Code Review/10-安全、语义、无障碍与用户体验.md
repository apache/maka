# 第 10 章 安全、语义、无障碍与用户体验

## 10.1 问题定义

很多前端做 code review 时，会把安全、语义、无障碍与用户体验放到最后，甚至直接忽略。

原因很现实。  
这些问题往往不像语法错误那样会立刻报错。  
也不像接口失败那样会马上白屏。  
更不像性能卡顿那样第一眼就能被抱怨。

但真正成熟的 React Code Review，不能只盯“能不能跑”，还要盯“跑出来是否安全、是否可理解、是否可使用、是否让用户感到稳定”。

这一章要处理的，就是这四组经常被低估、却会直接影响产品质量的问题：

安全。  
语义。  
无障碍。  
用户体验。  

这几组问题有一个共同特点：

它们经常看起来像“小细节”。  
但一旦积累，就会直接伤害系统可信度。

比如：

把不可信 HTML 直接插进页面。  
按钮看起来能点，其实没有正确语义。  
表单校验失败了，却没有清晰提示。  
空数据和请求失败表现成同一种空白。  
交互需要键盘时完全无法操作。  
操作成功失败没有反馈，用户只能猜。  

所以这一章的任务，是建立一套针对“安全、语义、无障碍与用户体验”的专项审查框架。目标不是把这几项当作补充清单，而是把它们纳入 React code review 的主框架。

---

## 10.2 成因

安全、语义、无障碍与用户体验之所以容易被忽视，通常有八个根因。

第一，开发和 review 都更容易关注“主流程能不能跑通”。  
只要页面能展示、接口能请求、按钮能点，很多人就默认任务完成。

第二，这几类问题经常不会第一时间在开发环境暴露。  
XSS 风险、键盘可达性、语义错误、空态设计不完整，往往要到真实用户使用时才显现。

第三，团队里常把它们视作“锦上添花”。  
但实际上，对中后台系统来说，这些问题并不只是体验问题，还会影响错误操作率、学习成本和系统可信度。

第四，很多开发者对浏览器默认语义和可访问性机制理解不够。  
比如什么时候该用 button，什么时候该用 div，什么时候该有 label、aria、focus 管理，这些并不总是被系统化学习。

第五，安全问题容易被后端兜底幻觉掩盖。  
前端会默认“服务端应该过滤”，于是 review 时对危险插入、权限展示、输入约束放松警惕。

第六，用户体验问题常常散落在多个局部。  
按钮 loading、空态、错误态、操作反馈、禁用态、文案解释，各自看都不大，连起来才构成完整体验。

第七，组件库会提供部分基础能力。  
这让开发者误以为只要用了组件库，就自动具备语义和无障碍质量。

第八，中后台项目长期由内部用户使用，容易被默认“要求没那么高”。  
但越是高频内部系统，越需要稳定、清晰、可预期的体验。

---

## 10.3 原则

安全、语义、无障碍与用户体验审查，统一遵循十条原则。

第一，默认不信任原则。  
任何来自用户输入、服务端返回、富文本内容的可注入数据，都应先假定不可信。

第二，语义优先原则。  
能用原生语义元素表达的交互，优先使用原生语义，而不是用 div 模拟一切。

第三，可操作可感知原则。  
所有关键交互都应让用户知道当前能不能操作、操作后会发生什么、是否已经成功或失败。

第四，状态可区分原则。  
loading、empty、error、无权限、无结果等状态应能被明确区分，而不是都表现成空白。

第五，错误可解释原则。  
失败时要尽量告诉用户发生了什么，以及下一步能怎么做。

第六，键盘可达原则。  
重要交互不能只对鼠标友好，也应考虑键盘操作路径和焦点流转。

第七，反馈闭环原则。  
提交、删除、批量操作、保存、加载等重要动作，都要有清晰反馈闭环。

第八，权限显式原则。  
用户是否有权限看到、点击、编辑、删除，要有明确边界，不能让无权限状态表现成系统坏了。

第九，文案辅助理解原则。  
文案不仅是装饰，它是界面理解的一部分。模糊文案会直接放大认知负担。

第十，体验一致性原则。  
同类操作在不同页面应尽量有一致反馈、一致交互规则和一致状态表达。

---

## 10.4 后果

如果安全、语义、无障碍与用户体验没有审查好，常见后果通常有十种。

第一，出现安全风险。  
最典型的就是把不可信 HTML 或字符串直接渲染进页面，产生 XSS 注入面。

第二，用户误操作增加。  
按钮、链接、可点击区域语义不清，用户会误判它能做什么。

第三，界面状态难以理解。  
空态、错误态、无权限、无结果都长得差不多，用户不知道到底发生了什么。

第四，键盘用户无法完成操作。  
焦点管理混乱、组件不可聚焦、缺少键盘触发路径，会直接影响可用性。

第五，操作成功失败不透明。  
用户点完保存、删除、刷新，只能猜系统是否响应。

第六，错误恢复成本上升。  
因为没有清晰提示，用户不知道该重试、联系谁、还是切换条件。

第七，组件复用会复制坏体验。  
基础组件如果语义和反馈设计不稳，所有页面都会继承问题。

第八，系统可信度下降。  
哪怕核心功能没坏，只要经常出现“点了没反应”“不知道为什么空白”“不知道能不能点”，用户就会觉得系统不可靠。

第九，review 质量停留在工程层，忽略产品层。  
只盯代码正确性，不盯使用体验，最后交付出来的仍然可能是“技术上能跑、体验上很差”的页面。

第十，面试表达会缺维度。  
中高级前端如果只会谈状态和性能，不会谈安全、语义、无障碍和体验，回答会明显显得窄。

## 10.5 代码案例

这一章重点结合 SSAP 相关场景和你那道面试题里的典型问题来讲。

### 案例一：危险内容渲染

你前面那道 React review 题里，面试官专门提示你找安全问题。最后你定位到 `dangerouslySetInnerHTML`。这就是最典型的安全审查切口。

这个问题的价值不在于“知道这个 API 危险”，而在于你要能继续往下说：

数据来自哪里。  
是否可信。  
是否做过清洗。  
是否有后端兜底。  
前端是否还要做白名单过滤。  

高质量 review comment 应该这样写：

“这里直接渲染 HTML 内容，存在 XSS 风险。除非数据源经过可信清洗，否则不应直接注入页面。建议优先避免原样插入，或者在渲染前增加明确的清洗策略。”

### 案例二：列表与按钮的语义问题

在表格、卡片、搜索区这类中后台页面里，很容易出现大量“看起来能点”的元素，但它们不一定真的有正确语义。

比如：

用 div 模拟按钮。  
可点击区域没有 focus。  
图标可以点，但没有可理解文案。  
行点击和按钮点击混用，语义不清。  

这种问题表面像“无障碍”，其实已经影响普通用户理解。

高质量 review 语言应该是：

“这里建议优先使用具备原生语义的 button 或 link，而不是只依赖 click 事件模拟交互。这样不仅能改善键盘可达性，也能提升阅读和维护时对交互意图的理解。”

### 案例三：`src/components/table/index.tsx`

基础表格组件不仅有工程和请求问题，也有体验问题。

你在 review 这里时，要问：

loading 和 empty 是否区分。  
错误态是否可见。  
无数据时是否给出解释。  
批量操作后是否有成功失败反馈。  
禁用操作是否有原因。  

如果 table 基础组件只能展示数据，却没有为这些状态留出表达能力，它就很难支撑成熟页面。

### 案例四：`src/components/search-form/index.tsx`

复杂搜索区的体验问题通常不是“控件能不能输入”，而是：

用户知不知道该填什么。  
校验失败后有没有清晰提示。  
重置和提交后的状态是否可理解。  
标签和当前条件是否一致。  
联动字段不可用时有没有解释。  

这类问题特别像“小细节”，但它们会直接决定这个页面是不是“能上手”。

### 案例五：弹窗、图表与焦点流转

在 dashboard、规则配置这类页面里，经常会有弹窗、抽屉、图表详情、复杂表单。

这时要特别警惕两个问题：

弹窗打开后焦点是否进入弹窗。  
弹窗关闭后焦点是否能回到原位置。  

如果没有基本焦点管理，键盘用户和高频操作用户都会觉得界面很飘。

## 10.6 解法

安全、语义、无障碍与用户体验审查，建议固定成一条十步路线。

### 第一步：先画出页面的关键操作链

先列出这个页面里真正重要的动作：

搜索。  
重置。  
点击查看。  
打开弹窗。  
提交表单。  
删除。  
批量操作。  
导出。  

你只有先知道关键链路是什么，才能判断哪些体验问题是主问题。

### 第二步：专项检查危险输入和危险输出

固定问：

用户输入会不会被直接渲染。  
服务端返回内容是否可信。  
HTML 是否会被直接插入。  
富文本是否经过清洗。  
错误信息是否原样暴露。  

### 第三步：检查交互元素是否具备正确语义

重点看：

按钮是否真的是 button。  
跳转是否真的是 link。  
是否存在只靠 div 绑定 click 的交互。  
图标按钮是否有足够可理解信息。  

### 第四步：检查状态是否能被用户区分

重点区分：

loading。  
empty。  
error。  
无权限。  
无结果。  
禁用态。  

不同状态如果长得一样，用户就会误判。

### 第五步：检查错误提示与恢复路径

失败时要问：

用户是否知道为什么失败。  
用户是否知道下一步能做什么。  
是否能重试。  
是否保留了原有输入。  

### 第六步：检查表单与搜索区的辅助信息

重点看：

label 是否清楚。  
placeholder 是否真的有帮助。  
必填与选填是否明确。  
联动字段不可用时是否解释原因。  
校验失败时是否能快速定位到具体字段。  

### 第七步：检查键盘可达性与焦点流转

重点看：

重要按钮是否可聚焦。  
弹窗打开关闭时焦点是否有管理。  
列表项和操作按钮是否能通过键盘触达。  
是否存在只能鼠标操作的关键路径。  

### 第八步：检查操作反馈闭环

任何重要动作都问：

点击后有无 loading。  
成功后有无明确反馈。  
失败后有无解释。  
重复点击是否可控。  

### 第九步：检查一致性

同类操作在不同页面要尽量一致：

删除反馈是否一致。  
搜索和重置行为是否一致。  
错误态表现是否一致。  
空态文案是否一致。  

### 第十步：最后给出最小收益最大的改法

例如：

先补危险渲染的清洗策略。  
再统一 loading / empty / error 状态表达。  
再修正高频交互元素的语义。  
最后补焦点管理和键盘可达性。  

这样改动最有收益，也最容易落地。

## 10.7 快速定位

以后你看到任何 React 页面，除了状态、性能、异步之外，再补问这十个问题。

这段内容是否存在注入风险。  
用户能不能一眼看懂这里能做什么。  
关键交互是否使用了正确语义元素。  
loading、empty、error、无权限是否区分清楚。  
失败时用户知道下一步怎么办吗。  
表单和搜索区是否有清晰辅助信息。  
键盘用户能完成关键操作吗。  
弹窗和复杂区域的焦点流转是否稳定。  
操作成功失败有没有闭环反馈。  
同类页面的体验规则是否一致。  

这十问形成条件反射之后，你的 review 就会从“工程审查”提升到“工程 + 产品质量联合审查”。

---

## 10.8 本章小结

安全、语义、无障碍与用户体验，是 React Code Review 最容易被放到最后、却最能体现成熟度的一章。

这一章最重要的收获，是建立三种能力。

第一，学会把安全问题当成默认审查项，而不是等面试官提醒。  
第二，学会把语义和无障碍当成界面可理解性的组成部分，而不是可有可无的加分项。  
第三，学会把用户体验问题翻译成“状态可区分、反馈可恢复、操作可理解”这三类稳定语言。  

当你能稳定做到这三点，你做的 code review 就不再只是面向代码本身，而是真正开始面向用户和系统可信度。
