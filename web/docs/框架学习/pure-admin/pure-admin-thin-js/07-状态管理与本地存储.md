# 07 - 状态管理与本地存储

本章结论：六个 Pinia store 分工明确，每个 store 都提供一个 `useXxxStoreHook()` 函数解决"在 setup 外使用 store"的问题；界面偏好类状态通过 responsive-storage 实现响应式持久化；页面缓存（keep-alive）由 permission store 的 `cachePageList` 管理。localStorage 的读写散布在 store 初始化逻辑里，是本模板状态层的主要特色。

## 六个 store 的分工

| store | id | 职责 | 文件 |
| --- | --- | --- | --- |
| app | `pure-app` | 侧边栏开合、布局模式、设备类型、视口尺寸 | `src/store/modules/app.js` |
| epTheme | `pure-epTheme` | element-plus 主题色、明暗主题 | `src/store/modules/epTheme.js` |
| multiTags | `pure-multiTags` | 标签页集合的增删与持久化 | `src/store/modules/multiTags.js` |
| user | `pure-user` | 用户信息、角色、按钮权限、登录登出 | `src/store/modules/user.js` |
| permission | `pure-permission` | 整体菜单、扁平路由、keep-alive 缓存列表 | `src/store/modules/permission.js` |
| setting | `pure-setting` | 站点标题、固定头、隐藏侧边栏三个全局开关 | `src/store/modules/settings.js` |

setting store 最薄，state 直接从 platform-config 取三个值，`changeSetting({key, value})` 用 `Reflect.has` 防御无效键。布局组件（`src/layout/index.vue`）判断是否渲染侧边栏、是否固定头部读的就是它。

观察这五个文件会发现一个共同模式：state 初始值都写成 `storageLocal().getItem(...) ?? getConfig().默认值`。也就是"本地有就用本地的，本地没有就用 platform-config 的默认值"。这是界面偏好持久化的统一套路，app store 的 `sidebar.opened`、epTheme store 的 `epThemeColor` 都是这个写法。

## Hook 函数模式：为什么每个 store 配两个导出

每个 store 文件都导出两个东西：

```js
export const useUserStore = defineStore("pure-user", { ... });

export function useUserStoreHook() {
  return useUserStore(store);
}
```

`useUserStore` 直接调用必须在组件 setup 上下文里才拿得到 Pinia 实例；而路由守卫、HTTP 拦截器这些模块顶层代码运行时根本不在任何组件里。`useUserStoreHook` 把 `src/store/index.js` 创建的 `store` 实例显式传进去，绕开了对上下文的依赖。规则很简单：**组件里用原函数，组件外（守卫、拦截器、工具函数）用 Hook**。全仓库的 `useUserStoreHook()` 调用点（auth.js、http/index.js）全是组件外场景。

## responsive-storage：响应式的 localStorage

界面偏好需要"改了立刻生效 + 刷新后还在"，普通 localStorage 做不到响应式。模板用 responsive-storage 解决：`src/utils/responsive.js` 的 `injectResponsiveStorage` 在启动时把两块配置注入进去，命名空间 `responsive-`：

- `responsive-layout`：布局模式、主题、暗色开关、侧边栏状态、主题色。
- `responsive-configure`：灰度、弱化、隐藏标签页、显示 logo、水印、标签样式等界面开关。
- `responsive-tags`：仅当 `MultiTagsCache: true` 时存在，持久化标签页集合。

之后任何地方通过 `useGlobal().$storage`（`@pureadmin/utils` 提供）就能响应式地读写这些配置，`src/App.vue` 的水印 watch 就是这么拿 `watermark` 开关的。改 platform-config.json 的默认值只影响"第一次访问"的用户，老用户本地已有存储，不会被覆盖。这也是"改了配置不生效"的高发原因。

## multiTags store：标签页的状态机

标签页的增删全部收口在 `handleTags(mode, value, position)` 一个 action，五种模式：

| mode | 行为 |
| --- | --- |
| `push` | 加标签，带四道防线：`hiddenTag` 不加、外链不加、空 title 不加、`showLink: false` 不加；已存在（path + query + params 全等）不加；超过 `dynamicLevel` 时替换最早的同路径标签 |
| `equal` | 整体替换，用于登出重置、登录初始化 |
| `splice` | 按 path 或按位置删标签 |
| `slice` | 取最后 N 个 |
| — | 所有写操作完成后调 `tagsCache()`，开启持久化时同步进 localStorage |

持久化开关 `multiTagsCache` 默认 false（`public/platform-config.json`），开了以后刷新页面标签页还在。

## permission store：菜单与缓存的中枢

`handleWholeMenus(routes)` 是动态路由注册后的菜单组装入口：静态菜单（`constantMenus`）拼接动态路由，按 rank 排序、按 `showLink` 过滤、按当前用户角色过滤后存进 `wholeMenus`，侧边栏渲染的就是它。

`cachePageList` 是 keep-alive 的名册。路由守卫在每次进入 `keepAlive` 页面时调 `handleAliveRoute(to, "add")` 把组件 name 加进名册；标签页关闭时 delete；标签页上点刷新时走 default 分支，先删后加中间隔 100 毫秒（`useTimeoutFn`），让组件完整销毁重建一次。这就是"标签页刷新"功能的全部秘密。前提是页面组件用 `defineOptions({ name: "Xxx" })` 声明了名字，且与路由 name 一致——welcome 页面里那行 `defineOptions({ name: "Welcome" })` 就是干这个的。

## localforage 封装：带过期时间的离线存储

`src/utils/localforage/index.js` 把 localforage 包成 `StorageProxy` 类：IndexedDB 优先、localStorage 兜底，库名 `pure-admin`，`setItem(k, v, m)` 的第三个参数以分钟为单位设置过期，`getItem` 时校验过期时间，过期返回 null。动态路由缓存（`async-routes` 键）走的是 `storageLocal` 而非它，目前模板里这个封装属于"备好的基建"，业务有大量结构化数据要存离线时用得上。

## 常见误解纠偏

**误解一：改 platform-config.json 就能改所有用户的界面。** 只对清空过浏览器存储的新用户生效，老用户本地存储优先。想强制全员换配置，要么升 `Version` 号并清理存储逻辑，要么提供重置入口。

**误解二：keep-alive 不生效是 element-plus 的问题。** 九成是页面组件没写 `defineOptions` 的 name，或 name 与路由 name 不一致，名册对不上号。

**误解三：Pinia 里的状态刷新后都会丢。** app、epTheme、multiTags、user 这几个 store 的关键状态都在初始化时从 localStorage 恢复，刷新不丢（setting store 每次从 platform-config 取值，本来就不需要恢复）。Pinia 本身不持久化，是模板的初始化代码在起作用。
