# 05 · 权限体系

一句话定义：页面级权限看角色 `roles`，按钮级权限有两套平行方案，`auths` 跟着路由走，`permissions` 跟着用户走。

上一篇：[04 动态路由](./04-动态路由.md) ｜ 下一篇：[06 登录态与请求层](./06-登录态与请求层.md)

## 先打个比方

页面权限是小区门禁，刷你的卡能进哪几栋楼。按钮权限是楼里每个房间的抽屉锁，`auths` 相当于贴在房门上的清单，写明这间房配了哪几把钥匙；`permissions` 相当于你兜里实际带着的钥匙。开抽屉前对一下，兜里的钥匙在清单上，锁就开。

## 页面级：roles

mock 里每个动态路由的 `meta.roles` 标了归属：权限管理给 `["admin", "common"]`，日历排班、字典、租户只给 `["admin"]`。

roles 在两个地方被消费，构成双保险。

第一道是菜单过滤。`src/router/utils.js` 的 `filterNoPermissionTree` 从 localStorage 的 `user-info` 里取当前用户 `roles`，与每个节点 `meta.roles` 求交集（`isOneOfArray`），有交集就显示。目录级有个贴心规则：目录本身不用配 roles，只要它下面有一个子项对用户可见，目录就显示，反之空目录被 `filterChildrenTree` 剔除。

第二道是路由拦截。直接手输 URL 绕过菜单时，`src/router/index.js` 的守卫用同样的 `isOneOfArray` 再查一次，不匹配重定向 `/error/403`。

两个数组的交集判断意味着"有任一匹配角色即可见"。想让页面同时容纳 admin 和编辑者，写 `roles: ["admin", "editor"]` 就行。不写 roles 的路由对所有人开放，因为 `isOneOfArray` 对非数组入参直接返回 `true`。

## 按钮级：auths（路由下发）

mock 的"路由返回按钮权限"页面（`PermissionButtonRouter`，组件 `src/views/permission/button/index.vue`）的 meta 里挂着：

```js
auths: ["permission:btn:add", "permission:btn:edit", "permission:btn:delete"]
```

判断函数是 `src/router/utils.js` 的 `hasAuth(value)`。它读**当前路由** `router.currentRoute` 的 `meta.auths`：传字符串就 `includes` 判断，传数组就要求全部拥有（`isIncludeAllChildren`）。

演示页把三种等价写法都摆出来了，实际项目按场景挑：

```html
<!-- 组件方式：包住一段模板 -->
<Auth value="permission:btn:add"><el-button>新增</el-button></Auth>

<!-- 指令方式：最省字 -->
<el-button v-auth="'permission:btn:add'">新增</el-button>

<!-- 函数方式：需要参与逻辑判断时 -->
<el-button v-if="hasAuth(['permission:btn:add', 'permission:btn:edit'])">批量</el-button>
```

指令实现在 `src/directives/auth/index.js`，逻辑一句话，`mounted` 时没权限就把元素从 DOM 里移除。

## 按钮级：permissions（登录下发）

另一套方案的权限码在登录接口返回，存在用户信息里。`mock/login.js` 里 admin 拿到 `["*:*:*"]`（通配全部），common 拿到 `["permission:btn:add", "permission:btn:edit"]` 两个。

判断函数是 `src/utils/auth.js` 的 `hasPerms(value)`，规则与 `hasAuth` 一致，外加一条：权限列表是 `["*:*:*"]` 时直接放行一切。配套组件 `Perms`、指令 `v-perms`，演示页在 `src/views/permission/button/perms.vue`。

## 两套按钮方案怎么选

| | auths | permissions |
| --- | --- | --- |
| 权限码来源 | 路由 meta，跟页面走 | 登录接口，跟用户走 |
| 生效范围 | 仅当前路由，切页失效 | 全局有效 |
| 判定函数 | `hasAuth()`（router/utils） | `hasPerms()`（utils/auth） |
| 适用场景 | 页面强相关的局部操作 | 贯穿全系统的操作权限 |

实际项目绝大多数情况选 permissions。按钮权限本质是用户属性，由后端一个接口统一发放，前端全站可用。auths 更像演示品，适合"这个页面上有个特殊按钮"的少量场景。

选组件、指令还是函数也有讲究。组件和指令在 `mounted` 时做一次性判断，权限变了 DOM 不会恢复。需要响应式（比如权限随操作变化）就用函数配 `v-if`。

## 新手常见误区

**在 A 页面用 `hasAuth` 判断 B 页面的 auths。** `hasAuth` 永远读当前路由的 meta。跨页面的权限判断一律用 `hasPerms`。

**以为加了 `v-auth` 元素会自动恢复。** 指令在 `mounted` 里直接 `removeChild`，是一次性的。运行时权限会变的界面用函数式判断。

**把 roles 当唯一权限。** roles 挡住的是菜单和路由，页面内部的按钮要靠 auths 或 permissions。两层都要配，漏掉按钮层的话，common 用户进得去页面但界面上全是按钮，体验和安全都不对。

## 动手验证

1. `common` 账号登录，观察菜单：日历排班、字典管理、租户管理消失。地址栏手输 `http://localhost:8848/#/dict/index`，落到 403 页。这两步分别是第一道闸和第二道闸在工作。
2. 进入权限管理 → 按钮权限 → 登录接口返回按钮权限。common 用户看到"新增""编辑"两个按钮，"删除"按钮不渲染。切到 admin 登录再看，`*:*:*` 通配，三个按钮全在，页面顶部还提示了通配符的含义。
3. 打开 `src/views/permission/button/perms.vue`，把某个 `<Perms>` 的 value 改成 common 没有的 `permission:btn:delete`，热更新后按钮消失。亲手改一次比读十遍印象深刻。
