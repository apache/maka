# 07 · 状态管理

一句话定义：六个 Pinia store 六个部门，各管一摊互不越界，组件外使用时一律走 `useXxxStoreHook()` 这个带工牌的入口。

上一篇：[06 登录态与请求层](./06-登录态与请求层.md) ｜ 下一篇：[08 本地存储双轨制](./08-本地存储双轨制.md)

## 六个部门一览

| store | id | 管什么 | 关键 state | 谁在写它 |
| --- | --- | --- | --- | --- |
| user | `pure-user` | 当前用户 | `avatar` `username` `nickname` `roles` `permissions` `isRemembered` `loginDay` | `setToken()`（登录、刷新 token）、登录页 |
| permission | `pure-permission` | 菜单与页面缓存 | `wholeMenus` `flatteningRoutes` `cachePageList` | `initRouter()`、keep-alive 机制 |
| multiTags | `pure-multiTags` | 标签页 | `multiTags`、`multiTagsCache` | 标签栏的所有交互 |
| app | `pure-app` | 侧边栏与设备 | `sidebar` `layout` `device` `viewportSize` | 布局的响应式监听 |
| epTheme | `pure-epTheme` | 主题色 | `epThemeColor` `epTheme` | 右侧设置面板 |
| setting | `pure-setting` | 三项全局开关 | `title` `fixedHeader` `hiddenSideBar` | 设置面板 |

文件都在 `src/store/modules/` 下，一个模块一个文件。读源码时按"state 是什么、actions 谁在调"两条线看，半小时能读完。

几个 store 里的重量级方法值得点名：

- `permission.handleWholeMenus(routes)`：静态菜单与动态路由合并、过滤、排序的地方，第 04 篇的第四步。`cachePageList` 由 `cacheOperate` 管理 add/delete/refresh 三种模式，keep-alive 的名单就是它。
- `multiTags.handleTags(mode, value, position)`：标签页唯一入口，支持 `equal`（整体替换）、`push`、`splice`（删除）、`slice`。`push` 里有五道拦截：`hiddenTag` 不进、外链不进、空标题不进、`showLink: false` 不进、path + query + params 完全一致的重复项不进。自己调 push 不生效时先查这五条。
- `user.logOut()`：纯前端登出，第 06 篇讲过。

## Hook 写法：为什么每个 store 都有两份导出

每个文件尾部都有这样一段：

```js
export function useUserStoreHook() {
  return useUserStore(store);   // 显式传入 pinia 实例
}
```

原因是 Pinia 的使用前提：调用 `useUserStore()` 时必须存在"活跃的 Pinia"。组件里没问题，组件渲染时应用已经装好 Pinia。但路由守卫、`hasPerms()` 这类工具函数、甚至 `src/utils/http` 里的拦截器，执行时机可能在 Pinia 安装之前，或者在 Pinia 上下文之外，裸调会抛 `getActivePinia was called with no active Pinia`。

Hook 版本把 `src/store/index.js` 导出的 store 实例显式传进去，脱离上下文也能稳定拿到同一个 store。这是 pure-admin 的强约定：**组件里用 `useXxxStore()`，组件外一律用 `useXxxStoreHook()`**。拿不准的场合，无脑用 Hook 版本不会错。

## store/utils.js：中转站

打开 `src/store/utils.js` 会发现它没有任何逻辑，只是集中再导出：`store`、`router`、`routerArrays`、`getConfig`、`storageLocal` 等。各 store 统一从 `"../utils"` 取这些依赖，而不是直接去 import router 模块或 config 模块。

这样做的现实原因是循环依赖。`src/router/index.js` 要用 multiTags 和 permission 两个 store（守卫里判断菜单和标签），而 store 的 actions 又要操作 router。如果互相直接 import，模块加载顺序会变得脆弱。中转站把"谁依赖谁"收拢到一个文件里，ESM 的函数调用是运行时才发生的，环就解开了。你往 store 里加依赖时，跟着走 `"../utils"` 这个口子。

## 持久化边界

store 是内存态，刷新即空。六个 store 的恢复策略各不相同，理解这一点能避免"我的状态怎么丢了"的困惑。

- user：state 初始值从 localStorage 的 `user-info` 读，天然恢复。
- permission：`wholeMenus` 等刷新后由守卫触发 `initRouter()` 重建。
- multiTags：`platform-config.json` 的 `MultiTagsCache: true` 时持久化到 `${ns}tags`，当前为 false，每次刷新只剩 `routerArrays`（首页）和 `fixedTag` 的标签。
- app / epTheme：初始值优先读 `${ns}layout`，没有再用平台配置兜底。
- setting：只从 `getConfig()` 读，不持久化。

## 新手常见误区

**在守卫或工具函数里裸调 `useUserStore()`。** 报 `getActivePinia` 错误。换成 `useUserStoreHook()`。

**直接改 store 里的偏好字段指望它记住。** 比如手动 `useAppStoreHook().sidebar.opened = false`，界面变了，刷新后弹回来。偏好的权威数据源是 responsive-storage（下一篇），store 只是运行时镜像。官方做法是调 action（`toggleSideBar`），action 内部会同步写 storage。

**往 store 塞业务数据。** 这六个 store 全是"平台级"状态。列表数据、表单数据放在页面自己的 hook 里（第 11 篇的范式），不要为了"全局都能拿到"就进 store，那会让状态管理退化成垃圾场。

## 动手验证

1. 装 Vue Devtools 浏览器插件，Pinia 面板里能看到六个 store 的实时状态。点一下折叠侧边栏按钮，观察 `pure-app.sidebar.opened` 翻转，同时 Application 面板里 `responsivemaxjs-layout` 的 `sidebarStatus` 同步变化。这就是"action 同步 store 与 storage"的现场。
2. 打开几个页面攒几个标签，然后刷新。标签只剩首页，因为 `MultiTagsCache` 是 false。把它改成 true 再试，标签全部恢复。
3. 在浏览器控制台执行 `window.__PINIA__`？拿不到。正确的观察方式是 Vue Devtools。这条是提醒：别用 window 挂载的旧习惯调试 Pinia。
