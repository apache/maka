# 按开发阶段编排 Skills 的实战指南

> 2026-09-29 编写。针对一个真实迭代的七个阶段（PRD → Figma → 接口 → 测试用例 → 页面开发 → 改 Bug → 项目总结），给出每阶段该触发哪个 skill、进门读什么、出门交什么。
> 技术栈：Taro 3.6 + React 17 + TypeScript + Zustand，多端（H5 内嵌 App / 小程序 / 平板终端）。
> 当前可触发技能 30 个（14 个自建 + 16 个外部），清单见 `C:\Users\802165\.ai\categories\99-归档与淘汰\01-个人开发\README.md`。

## 核心结论

1. **一个阶段只挂一条主线**：主 skill 一个，配角按需。全家桶式加载会稀释触发精度，也会把无关约束灌进上下文。
2. **`ponytail` 是唯一常驻**：它管"最小必要改动"，每个阶段都成立，不需要显式点名。
3. **本人最大的历史短板是改 Bug 阶段的重复低效**——日志证据：定位类信号 59 会话 221 次、Edit 失败率 8%（高频工具最高）、两个主力项目各 21-22 条二次修复。所以第六阶段是本指南的重点，用**三段链**（定位 → 落地 → 验证）替代"边想边改"。
4. **阶段之间靠交付物衔接**，不靠记忆：上一阶段的产出是下一阶段的输入，写在文件里而不是留在会话里。

## 二、逐阶段展开

### 阶段 1：拿到产品 PRD

**主 skill：`gua-helper`** → 它的 `references/01-prd/SKILL.md` 节专治这个场景。

**进门先做的事**（顺序不能反）：

1. 判项目形态（多端产品壳 / 中后台 / Node 服务），决定后面所有默认值。
2. 从 PRD 反查页面入口：现有路由表里有没有、是新页面还是存量改造。
3. 把 PRD 截图/文字转成**模块蓝图**：页面区块 → 数据来源 → 交互 → 边界条件。

**触发话术**：`这期需求要做 X，帮我拆模块蓝图`、`这个 PRD 对应哪个页面入口`。

**需求含糊时切 `grilling`**：它专门追问到设计树穷尽。PRD 里"根据情况展示"这类表述必须问清，否则会变成阶段 6 的缺陷。PRD 里出现不懂的业务概念，用 `gua-learn` 补。

**出门交付**：模块蓝图 + **疑点清单**（哪些边界 PRD 没写、需要 PM 拍板）。疑点清单要落文件——本人历史上有 BUG-010 挂了 4 天无人拍板的案例，根因就是疑点只留在会话里。

**这阶段不做的事**：不写代码、不猜接口字段、不为"以后可能要"预留抽象（YAGNI）。

---

### 阶段 2：拿到 Figma 设计稿

**主 skill：`gua-figma-to-page-dev`**（两部分：资产管线 + 页面还原）。

**标准动作**：

1. **先确认设计真源**：同一业务常有多份 Figma（UI 稿 vs 产品原型稿），视觉以 UI 稿为准，产品稿只补业务结构。搞错真源会全盘白做。
2. **起手盘点三分输入**：本轮要交付什么 / Figma 和截图各提供什么事实 / 工作区已有脏改动哪些不碰。
3. **导资产**：Figma 节点或本地切图 → CDN → 代码常量。`cd` 进 scripts 目录用相对路径跑（绝对路径会破坏 isMain 判断静默退出）。
4. **画组件地图**：一个 Figma 红框对应一个候选业务组件，视觉碎片不急着抽。

**触发话术**：`按这个 Figma 实现页面`、`导出这几个图标上 CDN`、`和设计稿对不上`。

**铁律**：**尺寸取节点 metadata，截图只做肉眼回归**。目测写尺寸是本人踩过最多的坑——不同 WebView 下行高、间距、圆角都会偏。

**出门交付**：组件地图（组件名 + 父子关系 + 数据来源 + 哪些是临时静态数据）+ 资源常量文件。

**配角边界**：具体 SCSS 写法、token 抽离、跨端高度压缩 → `gua-css`；组件职责边界与状态归属 → `gua-ui`。

### 阶段 3：拿到后端接口定义

**主 skill：`gua-helper`** → `references/02-api/SKILL.md` 节。

**契约对账流程**（四个落点必须全覆盖，漏一个就会在联调期返工）：

```
接口文档导出 → 逐字段对账 → service / types / fixtures / mappers 四处同步
```

**本人已验证的三条硬规则**：

1. **契约权威优先级：Apifox 契约文档 > 后端实测下发 > UI 设计稿 > 个人 Spec**。实测与文档冲突时以文档为准并让后端改，不在前端加兼容层。
2. **字段禁止多源兜底**：每个字段只有唯一数据源，取不到就渲染空态。`a || b || c` 式回落是缺陷制造机。
3. **枚举与字典集中**：字典值进 `constants/`，不散落在组件里。

**触发话术**：`对一下这版接口契约`、`这些字段怎么映射`、`接口改了口径要改哪些地方`。

**出门交付**：契约对账表（字段 / 类型 / 可空 / 中文含义 / 消费方）+ DTO 类型 + mapper 骨架。类型复杂时用 `typescript-magician`。

**这阶段的高危动作**：拿 mock 数据当契约。mock 只证明结构对，证明不了后端真实下发形态——这条在阶段 6 会再出现一次。

---

### 阶段 4：拿到测试用例

**主 skill：`tdd`**（外部，已挂全局）。

**本人项目的实际形态**：以**结构测试**为主（Node 直跑 `.test.cjs`，静态扫源码），不做重型 e2e。因为多端构建成本高，而大部分缺陷来自参数、路径、字段口径、状态边界——这些静态可读。

**做法**：

1. 把测试同事的用例翻译成**可机械判定的断言**：模糊的"显示正常"要变成"该元素存在且文案等于 X"。
2. 修 Bug 类用例走 TDD：**先写会失败的测试**，红了再改代码，绿了才算修完。
3. 质量门禁细则查 `gua-helper` 的 `quality-me` 节。

**触发话术**：`这个用例怎么锁`、`先写个会失败的测试`、`补回归锁`。

**项目红线**（在项目 `AGENTS.md`，不在 skill 里）：测试文件只存本机工作区，绝不入库。提交前自查 `git status --short` 不含 `tests/`。

**出门交付**：结构测试文件 + 一句话说明它锁住了什么口径。

### 阶段 5：页面开发（React + Taro）

这阶段技能最多，按**问题类型**选主线，不要全挂：

| 手上的问题 | 主 skill |
| --- | --- |
| 表单弹窗、表格分页、加载更多、空态四态、新增/编辑状态机 | `gua-ui` |
| 看板、时间轴、日历、排班这类多接口页面 | `gua-dashboard` |
| 多端差异、分包、App SDK、真机行为、平台 API | `gua-taro` |
| 样式、还原、跨端高度、老 WebView 兼容、z-index | `gua-css` |
| 组件拆分、渲染边界、重渲治理 | `vercel-react-best-practices` + `vercel-composition-patterns` |
| 架构决策、状态该放哪、要不要引依赖 | `gua-helper`（工程决策门） |

**分层落位**（本人实证的稳定结构，跨项目复用）：

```
services → hooks（按业务域拆）→ 页面编排 → 组件（纯展示）
                ↑
        mappers（DTO → ViewModel，按业务域拆目录，index.ts 只 re-export）
        constants / types / utils（按职责细分）
```

**四条已付代价的经验**：

1. **JSX 只消费归一化后的 ViewModel**，DTO 解析全部在 mapper 层。组件里解析 DTO 会让 JSX 变成数据清洗脚本。
2. **单文件触及上限就按业务域拆**（不按技术分层拆），依赖保持单向，`index.ts` 只做索引不写实现。
3. **注释写决策不写实现**：写"为什么这样定 + 口径变更日期 + 契约来源"，不写"// 获取用户数据"。
4. **缺数据不兜底**：数据缺失时不挂入口、不回落到语义不同的其他入口——回落等于告诉用户一个假事实。

**触发话术**：直接描述问题即可（`弹窗关闭后数据还在`、`这个卡片在平板上高度不对`、`小程序端取不到 duration`）。

### 阶段 6：改 Bug（重点 · 三段链）

**这是本人历史上最烧时间的阶段**，问题不在技术能力，在**动手太早**：拿到症状直接改，改完不确定对不对，于是再改一版。三段链就是用来打断这个循环的。

```
① systematic-debugging  →  ② gua-bug  →  ③ gua-verify-build
   定位根因（不改码）        最小 diff 落地        证明真的修好了
```

#### ① 定位：`systematic-debugging`

**什么时候用**：症状清楚但根因不清楚。它是四阶段流程（根因调查 → 模式分析 → 假设验证 → 实施），核心铁律是 **ALWAYS find root cause before attempting fixes**。

**硬性要求**：回答完这四问才允许进入编辑——

| 问题 | 要拿到什么 |
| --- | --- |
| 真实失败是什么 | 一个可复现的失败断言/日志/请求/页面行为 |
| 最短调用链是什么 | 入口 → 直接调用方 → 一层被调方 |
| 必须不变的契约是什么 | 字段、状态码、返回结构、UI 行为 |
| 最小可验证切口是什么 | 单测 / 契约测试 / 命令 / 人工检查点，选一个 |

**只想看原因、不想改码时明确说"先分析，别构建"** —— `gua-bug` 已把这条写进铁律，本轮只输出诊断不碰文件。

#### ② 落地：`gua-bug`

根因定了才进这一步。两条铁律：

- **先诊断后改码**：四问答不出来就继续查，不用"先改改看"代替定位。
- **一次只修一个根因**：范围外问题记进 optional/off-scope 清单交回，不顺手改。改动面超出已验证根因所需时先停下说明。

**三个高频根因类型**（本人 58 个 fix 提交归纳，直接当检查表用）：

1. **根因 vs 症状**：先 grep 待改函数的所有调用方，修在共享的那一处。只修工单点名的路径会留下所有兄弟调用方仍坏着。
2. **ensure 而非 check**：前置依赖缺失时先补齐再判定。check-and-reject 式守卫在"依赖本来没有生产方"的链路上会 100% 误拦。
3. **平台机制优先于业务代码**："改了没效果""取消后永久 loading""首播回零"这类现象，先查框架/平台机制——组件库内置伪类样式、行高继承、全局 loading 是共享单例、媒体实例首播钩子覆盖业务设置。

#### ③ 验证：`gua-verify-build`

**改完不等于修好**。按五级判定选验证强度：

| 级别 | 触发条件 | 最低验证 |
| --- | --- | --- |
| L0 | 文案、注释、类型、文档 | 类型 + lint + 结构测试 |
| L1 | 组件逻辑、派生计算、mapper | + 目标端本地运行看真实渲染 |
| L2 | 构建期注入、条件编译、分包、路由、依赖 | + 目标环境完整构建，产物里确认生效 |
| L3 | 平台 API、原生交互、手势键盘、老 WebView 兼容 | + 目标机型真机 + vConsole |
| L4 | 接口字段口径、空态缺字段、身份链、跨端格式 | + **真实接口**覆盖有数据/无数据/缺字段三形态 |

**L4 最容易跳过、也最常出事**。本人 21-22 条二次修复的根因全在这一级：后端真实形态与预期不符、真实数据缺字段致入口消失（mock 下正常）、身份链只在真机成立。

**"改了没效果"先按三步排除产物陈旧**：产物里搜本次改动的特征字符串 → 确认重编译与缓存策略 → 清宿主容器缓存。**这三步做完之前不要怀疑代码，不要改第二版。**

**结论必须三段式**：已验证（什么级别 / 什么端机型 / 看到什么具体结果）、未验证（哪级没做 / 为什么 / 风险）、待复验（给用户的操作路径与预期）。禁止把"静态检查通过"写成"已验证"。

### 阶段 7：项目总结

**主 skill：`gua-writer`**。

**三类产出按需选**：

| 产出 | 用什么 | 要点 |
| --- | --- | --- |
| 迭代开发文档 | `gua-writer` | 文件名 `日期-具体做了啥.md`；按工作线而非会话堆积；被推翻的中间态标"演进标注" |
| 月度绩效自评 | `gua-performance` | 从 git 提交反推工作量；**每个结论要有数据或具体事件支撑**；注意 fix 提交数 ≠ 缺陷数 |
| 代码复盘审查 | `gua-review` | R01-R71 规则 + P0-P3 分级 + 四段式发现 |

**沉淀去哪**（三层分离，本人已验证的知识库模型）：

- 跨项目可复用的方法论 → 个人 skill（改 `SKILL.md`）
- 单项目的会话级工作记录 → 项目开发文档目录（按产品/版本）
- 项目专属事实（路径、节点号、配置默认值）→ 对应 skill 的 `references/project-facts.md`

**发现新的可复用工作流时**，用 `gua-project-workflow-skill-builder` 把它做成 skill——但只在"重复出现 ≥2 次且有稳定输出契约"时做，一次性的不做（YAGNI）。

**提交文案风格**：`type(scope): 一句话`，正文 3-4 条分论点，每条一个事实。

## 三、常驻与收尾

| 时机 | 技能 | 作用 |
| --- | --- | --- |
| 全程 | `ponytail` | 最小必要改动，打底不用点名 |

## 四、反模式（本人实际踩过的）

| 反模式 | 代价 | 改法 |
| --- | --- | --- |
| 一次挂 5 个 skill 求全 | 上下文被无关约束填满，触发精度下降 | 一阶段一主线，配角按需 |
| 症状驱动直接改码 | 改完不确定对不对，再改一版，Edit 失败率高 | 三段链，四问未答不进编辑 |
| 用 mock/fixture 验字段口径 | 只证明结构对，证明不了后端真实形态 | 走 L4 真实接口三形态 |
| 改了没效果立刻改第二版 | 第二版叠在陈旧产物上，问题被放大 | 先按三步排除产物陈旧 |
| 一个会话干一整天 | 前面的决策在后面被遗忘或重复讨论（实测最长会话 19 小时） | 按阶段切会话，交付物落文件 |
| 疑点只留在会话里 | 拍板无 deadline，缺陷挂账数天 | 疑点清单落文件，标明待谁拍板 |
| 顺手重构相邻代码 | diff 膨胀，回归风险扩大，审查困难 | off-scope 清单交回用户 |

## 五、不自信的点

1. **新建 skill 的触发准确率未实测**：`gua-verify-build`、`gua-dashboard`、`gua-bug`、`gua-review`、`gua-learn` 都是近两日建的，触发次数为 0。description 是否匹配真实话术需要实际用过才知道——**不命中就显式点名 `$skill-name`，并回来改 description**。
2. **阶段 4（测试）的技能选择偏弱**：`tdd` 是外部通用 skill，没有针对本人"结构测试为主、测试不入库"这套实际做法。如果这阶段反复卡壳，值得自建一个。
3. **阶段 1（PRD）依赖 `gua-helper` 的 01-prd 节，需经路由两跳**，不如独立 skill 触发直接。是否值得提出来，取决于这阶段的实际卡壳频率——目前没有数据支持。
4. **本指南的"阶段"是理想化切分**。真实迭代里 PRD、Figma、接口往往同时到达甚至互相矛盾（本人已发生过"UI 稿与产品稿冲突""后端实测与文档冲突"），那时优先级规则比阶段顺序更重要。
5. **`ponytail` 常驻的实际效果没量化**。它触发 70 次是全技能最高，但"少写了多少代码"没有基线对照，无法证明收益。
