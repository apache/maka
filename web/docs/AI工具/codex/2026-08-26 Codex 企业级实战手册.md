## 0. 结论摘要

Codex 是受权限与项目约束的工程代理，不是聊天机器人。它的价值来自五层组合：**明确目标（提示词）+ 项目约束（AGENTS.md）+ 运行时配置（config.toml）+ 安全底座（sandbox × approval）+ 验证闭环（测试与 diff 审查）**。

核心治理面一览：

| 治理面 | 载体 | 一句话定位 |
|---|---|---|
| 项目规则 | `AGENTS.md` | 给代理读的项目约定，短、准、可执行（上限 32 KiB，约 150 行是实用启发式） |
| 个人偏好 | `~/.codex/config.toml` | 模型、推理强度、sandbox、approval、MCP、项目信任 |
| 个人覆盖 | `AGENTS.override.md` | 个人偏好覆盖团队 AGENTS.md，不污染团队规则 |
| 能力扩展 | Skills / Plugins / MCP / Subagents | 单一职责、白名单、最小授权 |
| 命令策略 | `.codex/rules/`（execpolicy） | Starlark 规则精确控制 allow / prompt / forbidden |
| 安全底座 | sandbox × approval 两轴矩阵 | 见第 6 章，默认 `workspace-write` + `on-request` |

事实优先级（处理任何冲突时按此排序）：用户当次明确指令 > 当前源码与配置 > 真实接口与命令输出 > 官方文档 > 本手册 > 社区经验。

## 1. 定位与边界

### 1.1 Codex 是什么

Codex 是 OpenAI 面向软件工程场景的编码代理：读取项目上下文、调用工具、执行命令、修改文件、解释 diff、运行测试，在用户授权边界内完成开发、调试、审查和文档任务。官方覆盖 CLI、IDE 扩展、Web、Cloud 与 ChatGPT 桌面 App 多个入口。

### 1.2 入口形态对比

| 形态 | 主要用途 | 优点 | 限制 |
|---|---|---|---|
| Codex CLI | 终端与本地仓库中运行代理 | 接近真实工程环境，可执行测试、读写文件、审查 diff | 需理解 sandbox、approval、Git 状态 |
| Codex IDE Extension | 编辑器内辅助开发 | 与编辑、跳转、局部上下文结合紧密（`/ide` 可注入打开文件与选区） | 依赖 IDE 能力和扩展版本 |
| Codex Web / Cloud | 浏览器管理任务、云端执行仓库任务 | 适合异步任务、远程分支、PR 准备（`codex cloud exec` 可从终端提交） | 需要仓库权限与任务边界治理 |
| ChatGPT 桌面 App | 多线程、多工具、视觉化协作 | `codex app` 可从终端拉起；TUI 中 `/app` 无缝续接当前会话 | 部分能力随版本变化 |

### 1.3 与其他工具的差异

| 工具 | 核心定位 | 更适合 | 注意点 |
|---|---|---|---|
| Codex | 受权限与项目约束的工程代理 | 改代码、跑测试、做 review、生成工程文档 | 需要明确授权边界和验证标准 |
| ChatGPT | 通用对话与知识工作 | 解释概念、方案讨论、轻量代码片段 | 不等于本地仓库执行环境 |
| Claude Code | 代码代理工具 | 长上下文代码任务、终端协作 | 规则与能力边界以 Anthropic 当前文档为准 |
| Cursor | IDE 内 AI 编程环境 | 编辑器内联改动、多文件补全 | 工程代理边界需单独治理 |

> 跨模型工作流是社区成熟实践：用一个模型（如 Codex）做方案与实现，用另一个模型（如 Claude Code）做 QA 与 review——独立上下文窗口的"测试时算力"能发现单一模型发现不了的问题。

### 1.4 适合与不适合的任务

| 适合 | 原因 | 验收方式 |
|---|---|---|
| Bug 定位与修复 | 可读代码、跑测试、定位最小修改点 | 失败用例先红后绿 |
| 代码审查 | `codex review` 基于 diff 找风险 | 输出文件行号、风险等级、验证建议 |
| 前端页面改造 | 可结合组件、样式、路由与测试 | 本地截图、单测、E2E 或手工清单 |
| 工程化配置 | 可综合 package、Vite、TS、ESLint | `build`、`lint`、`test` 通过 |
| 文档沉淀 | 可把会话、代码和约定变成文档 | 结构完整、来源清楚、可执行 |

| 不适合 | 原因 | 替代做法 |
|---|---|---|
| 未授权的大范围重构 | 影响面难控 | 先做方案和文件白名单 |
| 涉及生产密钥的操作 | 安全风险高 | 由人手动处理，Codex 只给步骤 |
| 手机上批准复杂代码变更 | 视觉和上下文不足 | 移动端只读摘要，桌面端执行 |
| 官方未说明的高级编排 | 容易误判能力 | 标注待实测，先小样本验证 |

### 1.5 移动端使用边界

移动端（ChatGPT App）适合：查看任务摘要、记录需求想法、轻量只读审查。不适合：批准复杂 diff、执行清缓存/删除/推送。标准流程是"手机提想法 → 生成只读摘要 → 桌面端读取代码 → Plan → 人工确认 → Execute"。

## 2. 核心工作模型

### 2.1 agent loop

```txt
用户目标 -> 指令约束 -> 上下文收集 -> 计划生成 -> 文件修改 -> 命令验证 -> diff 审查 -> 总结交付
```

复杂任务必须拆为计划、执行、验收、复盘四步：上下文窗口有限、文件影响面复杂、测试和人工审查需要明确边界。

### 2.2 上下文来源与叠加顺序

Codex 的工作上下文 = 当前会话 + 用户输入 + 可访问文件 + AGENTS.md + config.toml + 命令输出 + 工具结果。规则叠加顺序：

| 层级 | 载体 | 优先级 |
|---|---|---|
| 用户当次指令 | 会话输入 | 最高 |
| 项目约定 | 子目录 AGENTS.md → 仓库根 AGENTS.md | 越靠近工作目录越高 |
| 个人全局约定 | `~/.codex/AGENTS.md` | 低于项目 |
| 工具默认行为 | 内置 | 最低 |
| 运行时覆盖 | CLI `-c key=value`、`--profile` | 对当次调用最高 |

AGENTS.md 官方机制要点（2026-08 口径）：

- 从 cwd 向上分层发现直至仓库根，上限 32 KiB（`project_doc_max_bytes` 可调）。
- `AGENTS.override.md` 承载个人偏好，不影响团队共享的 `AGENTS.md`。
- `/init` 可在当前目录生成 AGENTS.md 草案，生成后必须人工审查再提交。

### 2.3 token、压缩与拆分（Context Engineering 三件套）

| 概念 | 工程含义 | 手段 |
|---|---|---|
| 上下文窗口 | 代理一次可持有的信息量 | 不把无关日志、依赖、构建产物塞进上下文；`/status` 查看剩余容量 |
| 会话压缩 | 长会话摘要化 | `/compact` 释放 token，保留关键决策；每阶段主动总结目标、文件、决策、未完成项 |
| 任务拆分 | 把大目标拆成小闭环 | 每个闭环有输入、输出、验证；用 `/fork` 分叉探索、`/side` 临时提问不污染主线 |

## 3. CLI 命令全景（2026-08 更新）

### 3.1 Windows 注意事项

PowerShell 执行策略可能拦截 `codex.ps1`，用 `codex.cmd` 绕过：

```powershell
codex.cmd --version    # 查看版本
codex.cmd --help       # 当前版本支持的命令与参数（事实来源）
codex.cmd doctor       # 诊断安装、配置、认证、运行环境
```

Windows 沙箱专项：TUI 内 `/setup-default-sandbox` 升级到管理员级沙箱；`/sandbox-add-read-dir C:\path` 为沙箱追加只读目录。

### 3.3 高频全局 flags

| Flag | 取值 | 含义 |
|---|---|---|
| `-C, --cd` | path | 指定工作目录 |
| `-m, --model` | string | 覆盖默认模型（以 `codex debug models` 目录为准） |
| `-s, --sandbox` | `read-only` / `workspace-write` / `danger-full-access` | 沙箱策略 |
| `-a, --ask-for-approval` | `untrusted` / `on-request` / `never` | 审批策略 |
| `-c, --config` | key=value | 临时覆盖配置（可重复） |
| `-p, --profile` | name | 叠加 `$CODEX_HOME/<name>.config.toml` |
| `--add-dir` | path | 追加可写目录（比放开 danger-full-access 更安全） |
| `-i, --image` | path[,path...] | 附图片到首条提示 |
| `--search` | boolean | 实时联网搜索（默认 cached 模式） |
| `--oss` | boolean | 用本地开源模型（LM Studio / Ollama） |
| `--strict-config` | boolean | config 有未知字段时报错（防配置漂移） |
| `--full-auto` | — | **Deprecated**，改用 `--sandbox workspace-write` |
| `--yolo` | — | 绕过审批与沙箱，仅限外部加固的隔离环境 |

### 3.4 `codex exec` 自动化要点

| Flag | 用途 |
|---|---|
| `--json` | 输出 JSONL 事件流，适合 CI 解析 |
| `-o, --output-last-message <path>` | 最终回复写入文件，供下游脚本消费 |
| `--output-schema <path>` | 用 JSON Schema 校验最终产出结构 |
| `--ephemeral` | 不落盘会话文件（一次性任务） |
| `--skip-git-repo-check` | 允许在非 Git 目录运行 |
| `--ignore-rules` | 本次不加载 execpolicy 规则 |
| `codex exec resume [SESSION_ID]` | 续跑非交互会话，`--last` 取最近、`--all` 跨目录 |
| `-` 作为 PROMPT | 从 stdin 管道读提示 |

CI 推荐组合：`--json` + `-o` 拿到机器可读进度 + 自然语言总结；沙箱用 `workspace-write`，绝不 `--yolo`。

### 3.5 `codex review` 四种目标

```powershell
codex.cmd review --uncommitted          # 审查暂存+未暂存+未跟踪
codex.cmd review --base main            # 对比基线分支
codex.cmd review --commit <SHA> --title "标题"
codex.cmd review "自定义审查指令"        # 或用 - 从 stdin 读
```

四选一，不能组合；`review_model` 可在 config.toml 单独指定审查模型。TUI 内 `/review` 等价交互入口。

## 4. `.codex` 目录结构与 Git 策略

### 4.1 全局目录（个人运行态）

```txt
~/.codex/                 # Windows: C:\Users\<user>\.codex
  AGENTS.md               # 个人全局协作规则
  config.toml             # 模型、sandbox、approval、MCP、插件、项目信任
  hooks.json              # 生命周期钩子（需 features.codex_hooks = true）
  auth.json               # 认证，禁止提交
  rules/                  # execpolicy Starlark 规则
  agents/                 # 子代理 TOML 定义
  skills/  plugins/       # 能力扩展
  memories/               # 跨会话记忆（per-user，非 per-project）
  sessions/  archived_sessions/   # 会话数据，禁止提交
  log/  cache/  sqlite/   # 运行状态
  .sandbox*               # 沙箱运行细节，禁止提交
```

| 类型 | 处理建议 |
|---|---|
| 配置 `config.toml` | 可阅读配置思路，提交前必须脱敏 |
| 认证 `auth.json` | 必须私有，禁止提交 |
| 会话 / 日志 / 缓存 | 私有；排查时只摘录必要片段 |
| 扩展 `plugins`、`skills` | 做能力治理，区分团队共享与个人私有 |
| 沙箱 `.sandbox*` | 运行环境细节，禁止提交 |

### 4.2 推荐项目结构（团队可提交部分）

```txt
project-root/
  AGENTS.md               # 短、准、可执行的项目约定
  AGENTS.override.md      # 个人覆盖，默认不入库
  .codex/
    skills/               # 团队公开技能，单一职责
      <name>/SKILL.md
    agents/               # 子代理定义
    rules/                # execpolicy 命令策略
    prompts/  plans/      # 通用模板（只放模板，不放会话产物）
  docs/
    ai-development/
      codex-workflow.md
```

### 4.3 Git 策略

适合提交：`AGENTS.md`、`.codex/README.md`、`.codex/prompts/*.md`、`.codex/skills/`、`docs/*.md`。

必须忽略：

```gitignore
.codex/auth.json
.codex/sessions/
.codex/log/
.codex/cache/
.codex/*.sqlite
.codex/*.sqlite-*
.codex/.sandbox*
AGENTS.override.md
```

## 5. config.toml 配置治理

### 5.1 配置分层原则

| 层 | 载体 | 放什么 |
|---|---|---|
| 个人默认 | `~/.codex/config.toml` | 模型、推理强度、个人偏好 |
| 场景 profile | `$CODEX_HOME/<name>.config.toml` + `-p` | conservative / trusted 等安全档位 |
| 项目约束 | `AGENTS.md` 或项目 `.codex/config.toml` | 团队规则（项目 config 需信任机制） |
| 临时覆盖 | CLI `-c key=value` | 一次性任务，稳定偏好写回配置 |
| 企业托管 | `requirements.toml` | 管理员维护的环境约束 |

> 架构师提醒：能写进 config 的确定性行为（approval、sandbox、模型）不要写成 AGENTS.md 里的自然语言规则——前者是 harness 强制执行，后者只是"请求"。

### 5.2 配置域速查

| 配置域 | 作用 | 企业建议 |
|---|---|---|
| `model` / `model_reasoning_effort` | 模型与推理强度 | 团队统一推荐值，个人可覆盖 |
| `sandbox`（或 `-s`） | 命令执行隔离 | 默认 `read-only` 或 `workspace-write` |
| `approval_policy`（或 `-a`） | 审批策略 | 高风险项目 `on-request` |
| `mcp_servers.*` | 外部工具 | 白名单管理，密钥走环境变量 |
| `projects.*.trust_level` | 项目信任 | 只信任明确项目 |
| `features.*` / `codex features` | 实验开关 | 谨慎启用，记 changelog |
| `review_model` | 审查专用模型 | 可与主模型分离 |
| `tui.*` | 界面（statusline/keymap/theme） | 个人偏好 |

### 5.3 三个场景模板

模板一：新手安全版（学习、只读分析）：

```toml
model_reasoning_effort = "medium"

[features]
web_search = false

[projects.'E:\your\project']
trust_level = "trusted"
```

```powershell
codex.cmd -C E:\your\project -s read-only -a on-request
```

模板二：前端项目开发版（React / Vue / TS / Vite）：

```toml
model_reasoning_effort = "high"

[projects.'E:\frontend-app']
trust_level = "trusted"
```

```powershell
codex.cmd -C E:\frontend-app -s workspace-write -a on-request
```

模板三：企业团队治理版：

```toml
model_reasoning_effort = "medium"

[features]
web_search = false

[mcp_servers]
# 仅登记团队批准的 MCP server，密钥用 env 传入

[projects.'E:\company\frontend']
trust_level = "trusted"
```

> 三个模板共同点：模型名不写死在共享配置里（模型目录迭代快，个人用 `-m` 覆盖）；密钥和私有路径不进共享配置。

## 6. 权限与安全底座

### 6.1 sandbox × approval 矩阵

| 场景 | sandbox | approval | 说明 |
|---|---|---|---|
| 只读分析 | `read-only` | `on-request` | 防止误写 |
| 常规开发（推荐默认） | `workspace-write` | `on-request` | 最小范围修改，需要额外可写目录用 `--add-dir` |
| CI 自动化 | `workspace-write` | `never`（或外部隔离 + `--yolo`） | 仅可丢弃环境 |
| 高风险排查 | `read-only` | `on-request` | 先输出建议命令，人工执行 |

### 6.2 execpolicy 命令策略（进阶）

`.codex/rules/` 中的 Starlark 规则可对命令前缀做 `allow` / `prompt` / `forbidden` 精确裁决，配合 `codex execpolicy check --rules <file> -- <command>` 离线验证。适合把"npm test 永远放行、rm -rf 永远禁止"这类团队红线从提示词升级为机器执行。

### 6.3 高风险操作黑名单

| 操作 | 处理方式 |
|---|---|
| 删除目录（尤其 `Remove-Item -Recurse -Force $HOME\.codex`） | 先说明影响与回滚 |
| `git clean -xfd` | 会删未跟踪文件，先 `git status` 复核 |
| 登录、登出 | 人工执行 |
| 安装、卸载依赖、修改 lockfile | 先确认并说明原因 |
| 推送、发布 | 人工最终确认 |
| 读取密钥 | 禁止输出，检查类任务只输出"字段类别" |
| 清理全局缓存/包管理器 store | 只给建议命令 |

## 7. 提示词与开发技巧

### 7.1 官方最佳实践（错误 → 更好对照）

| 实践 | 错误提示词 | 更好的提示词 | 为什么更好 |
|---|---|---|---|
| 写清目标 | "帮我优化项目" | "只读分析 Vite 构建慢的原因，输出证据和改动建议，不修改文件" | 目标、权限、产出明确 |
| 先读代码 | "直接修" | "先读取相关文件并画调用链，等我确认后再改" | 降低误改 |
| 先出计划 | "实现需求" | "先给文件白名单、测试命令、回滚点" | 控制范围 |
| 拆任务 | "做完整后台系统" | "先拆成认证、列表、表单、测试四个闭环，只执行第一个" | 可验收 |
| 要验证 | "写完告诉我" | "写完运行 `pnpm test` 和 `pnpm build`，无法运行需说明原因" | 交付可信 |
| 审查 diff | "看看代码" | "按 P0 到 P3 审查当前 diff，给文件行号和复现条件" | 审查可操作 |
| 处理失败 | "继续试" | "记录失败命令、错误、下一次不同策略，三次失败后停止提问" | 避免重复失败 |
| 限制范围 | "顺便整理" | "只改 `src/chart/*`，不要改格式化配置和依赖" | 避免扩大范围 |
| 挑战式验证 | （无） | "prove to me this works——diff main 和我的分支证明给我看" | 社区高分技巧 |
| 推倒重来 | （无） | "knowing everything you know now, scrap this and implement the elegant solution" | 对平庸方案的二次提纯 |

### 7.2 资深技巧精选（官方 + 社区 50 tips 精华）

| 技巧 | 具体做法 |
|---|---|
| 让 Codex 自己修 Bug | 贴 Bug 直接说 fix，不要微观管理实现路径 |
| 后台终端调试 | 让 Codex 把要看的终端命令作为后台任务跑，`/ps` 随时看输出 |
| 浏览器控制台 | 接 Chrome DevTools / Playwright MCP，让 Codex 自己看到 console 报错 |
| 截图驱动 | 卡住时截图给 Codex（`-i` 附图），比文字描述高效 |
| plan 双审 | 用第二个 Codex（或跨模型）以 staff engineer 视角审计划 |
| 阶段门禁计划 | 分阶段计划，每阶段配单测/自动化/集成多种测试 |
| agentic search 优于 RAG | glob + grep 实时搜索比预先索引的 RAG 更可靠（代码漂移 + 权限复杂） |
| worktree 并行 | Git worktree 隔离并行开发线（IDE 内 `/worktree`） |
| 上下文洁癖 | 子代理承接杂活，保持主上下文干净聚焦 |
| 提高规格清晰度 | 交接前把 spec 写细——你越具体，产出越好 |
| 快速理解陌生项目 | 让 Codex 先读 package.json、README、入口、路由、构建配置，输出模块表/入口表/关键数据流 |
| 定位最小修改点 | 先列候选文件，再说明为何只改其中几个 |
| PR review | 按严重度排序，附文件行号；PR 保持小而聚焦，一特性一 PR |
| 交付三要素 | 修改原因、影响范围、验证方式 |

### 7.3 高质量提示词模板库（按类精选）

只读分析：

| 场景 | 模板 |
|---|---|
| 新项目接手 | "请只读分析当前项目，读取 package、README、入口、路由、构建配置，输出项目类型、运行命令、核心模块和风险点。不要创建、修改、删除文件。" |
| 调用链追踪 | "从用户操作追踪到 API 和渲染，输出文件行号级调用链，不要猜测。" |
| 配置安全检查 | "只读检查 config.toml / vite.config / tsconfig，输出安全风险、可疑字段、建议修改。凭据只输出字段类别，禁止输出密钥值。" |

执行控制：

| 场景 | 模板 |
|---|---|
| 三阶段开发 | "按 Read、Plan、Execute 处理。Plan 必须包含文件白名单、测试策略、验收点、回滚点。我确认前不要改文件。确认后先补失败测试，再做最小实现。交付时说明真实执行过的验证命令和未验证事项。" |
| Bug 定位 | "先复现或静态定位这个 bug，列出证据、最小相关文件、预期失败测试，不要先改代码。" |
| TDD 修复 | "先写一个失败测试覆盖当前缺口，确认失败原因后再实现。" |
| 中断恢复 | "先恢复上下文：总结已完成、未完成、已修改文件、已运行命令、失败点和下一步。恢复完成前不要改文件。" |

审查与沉淀：

| 场景 | 模板 |
|---|---|
| 代码审查 | "按 P0 到 P3 审查 diff，只列真实风险、复现条件和建议修复，附文件行号。" |
| 依赖升级 | "只读列升级影响、破坏性变更、回滚方式，不执行安装。" |
| 规则沉淀 | "把这次任务中可复用的经验沉淀为项目规则。只保留高频、明确、可执行的规则，说明触发场景、禁止事项、验证方式。不要把一次性背景、会话记录、密钥写入规则文件。" |
| 复盘 | "基于本次改动复盘：目标是否完成、哪些决策有效、哪些风险仍在、下次如何改进，沉淀为可复用 prompt。" |

### 7.4 Skills 编写要点（社区验证）

| 原则 | 说明 |
|---|---|
| frontmatter 即触发器 | `description` 写给模型看："什么情况下该触发我"，不是给人看的摘要 |
| 文件夹而非单文件 | 用 `references/`、`scripts/`、`examples/` 渐进披露，SKILL.md 保持短 |
| 建 Gotchas 区 | 每个 skill 记录 Codex 的失败点，是信噪比最高的内容，随时间累积 |
| 只写反直觉的 | Codex 默认行为已经会的不写，专注推离默认行为的规则 |
| 给目标和约束 | 不写死步骤流程，避免"铁轨化"束缚模型 |
| 内置脚手架 | 用 `$skill-creator` 起步，仓库内统一一种调用风格 |

## 8. 能力扩展：Skills / Plugins / MCP / Subagents / Hooks / Memories

### 8.1 概念边界

| 名称 | 载体 | 定位 | 治理建议 |
|---|---|---|---|
| Skills | `.agents/skills/<name>/SKILL.md` | 按需加载的指令包，`/skills` 或 `$name` 显式调用、按 description 隐式匹配 | 团队共享需评审，单一职责 |
| Plugins | `.codex-plugin/plugin.json` | 打包 skills + MCP + App 集成的分发单元 | 走 marketplace（`codex plugin marketplace add owner/repo`），版本可回滚 |
| MCP | `config.toml` → `[mcp_servers.*]` | 外接工具与数据源，stdio 与 Streamable HTTP，支持 OAuth（`codex mcp login`） | 白名单、审权限、留日志、密钥走环境变量 |
| Subagents | `.codex/agents/<name>.toml` | `[agents.<name>]` 角色配置，并行编排；内置 `default`、`worker`、`explorer` | 文件白名单防冲突，主代理统一裁决 |
| Hooks | `.codex/hooks.json`（beta） | 注入 agent loop 的 shell 脚本：日志、安全扫描、自动格式化 | 需 `codex_hooks = true`；`/hooks` 里逐个 trust |
| Memories | `$CODEX_HOME/memories/` | 跨会话记忆管线，会话间整合（`[features] memories = true`） | per-user 非 per-project；涉密线程设 `no_memories_if_mcp_or_web_search = true` |

### 8.2 Subagents 防冲突规则

| 规则 | 说明 |
|---|---|
| 主代理统一裁决 | 子代理只产出建议或 patch |
| 文件白名单 | 每个代理只负责自己的文件 |
| worktree 隔离 | 复杂任务使用独立 worktree |
| 独立上下文即测试算力 | 一个代理写码、另一个找茬，分离的上下文窗口产出更好 |
| 最终人工审查 | 合并前审 diff 和测试 |

三个成熟场景：

| 场景 | 编排 |
|---|---|
| 定位→测试→修复 | A 只读定位根因；B 基于根因写失败测试；C 测试失败后最小修复；主代理合并验证 |
| React / 样式 / 测试 | A 组件结构、B 样式兼容、C 测试，互不改同一文件，主代理整合 |
| 调研三线 | A 读源码结构、B 整理最佳实践、C 写教程草稿，主代理统一来源标注 |

### 8.3 MCP 安全清单

| 检查 | 标准 |
|---|---|
| 来源 | 官方、可信团队或已审查仓库 |
| 权限 | 只读优先；写操作必须有明确确认；不默认读取全盘或外发数据 |
| 密钥 | 不写入仓库与共享配置，`--env KEY=VALUE` 或 OAuth |
| 日志 | 不记录敏感正文 |
| 退出 | 可快速 remove / logout |

## 9. 上下文与会话工程

### 9.1 会话生命周期

| 问题 | 判断标准 |
|---|---|
| 何时新开 | 新项目、新目标、上下文污染、权限变化（`/new`、`/clear`） |
| 何时继续 | 同一目标、同一文件范围、未完成验证（`codex resume --last`） |
| 何时分叉 | 想并行试另一方案又不想丢当前线（`/fork`、双 `Esc` 回退分叉） |
| 何时侧聊 | 主线运行中想问个小事（`/side`，不进主 transcript） |
| 何时归档 | 会话有价值但不再活跃（`/archive`，可 `codex unarchive` 找回） |
| 何时丢弃 | 已跑偏、信息过期、敏感内容混入（`/delete` 慎用，含派生会话） |

### 9.2 会话模板

单任务会话头：

```txt
目标：
范围（文件白名单）：
禁止事项：
先读文件：
验证命令：
交付格式：
```

多阶段任务：

```txt
请按 Read、Plan、Execute、Verify、Review 进行。每阶段结束输出阶段结论和下一步，不要跳阶段。
```

### 9.3 缓存与上下文健康管理

| 现象 | 先查 | 安全动作 |
|---|---|---|
| Vite 热更新异常 | 控制台、终端、`.vite` | 重启 dev server |
| 类型报错不消失 | TS server、锁文件 | 重启 IDE TS server |
| 构建结果异常 | `dist`、环境变量 | 重新构建到空目录 |
| 代理行为"变笨" | `/status` 上下文余量 | `/compact` 或 `/new` |
| 配置不生效 | `/debug-config` 层叠顺序 | 找到被哪层覆盖 |

大项目读文件策略：先读 `package.json`、README、AGENTS、构建配置 → `rg --files` 索引 → 按入口、路由、状态、API、组件逐层读取 → 跳过 `node_modules`、`dist`、`build`、`coverage`、`.git` → 大日志只截取错误前后片段。

## 10. 企业级工作流

### 10.1 标准闭环

```txt
需求澄清 -> 只读盘点(Read) -> 最小方案(Plan) -> 授权执行(Execute) -> 测试验证(Verify) -> diff 审查(Review) -> 文档沉淀 -> 规则更新(Retrospective)
```

| 阶段 | 关键动作 | 交付物 |
|---|---|---|
| Read | 盘点 README、package、配置、入口、测试和规则文件 | 项目地图和风险清单 |
| Plan | 最小方案、文件白名单、验收点、回滚点 | 可确认的执行计划 |
| Execute | 只改白名单文件，优先补测试再实现 | 最小 diff 和验证结果 |
| Review | 按严重度检查行为变化、安全、性能、测试缺口 | 可追踪 findings |
| Retrospective | 高频纠正点沉淀为规则、技能或模板 | 规则更新记录 |

### 10.2 场景化工作流表

| 流程 | Codex 提示词要点 | 人工验收点 | 常见风险 | 通过标准 |
|---|---|---|---|---|
| 日常小需求 | "先读相关组件，给最小计划，确认后改" | UI 与交互 | 顺手重构 | 目标行为通过 |
| Bug 修复 | "先写失败测试，再修复" | 复现路径 | 只修表象 | 回归不复现 |
| 重构 | "只重构白名单文件，保持行为不变" | API 兼容 | 行为变化 | 测试全绿 |
| 依赖升级 | "只读列破坏性变更和升级计划" | lockfile 变化 | 隐性 breaking | 构建测试通过 |
| 新人接手 | "只读生成项目导览和任务地图" | 是否准确 | 漏核心路径 | 新人可运行项目 |
| 代码审查 | "按严重度 review，附行号" | 是否可复现 | 风格噪音 | 关键风险处理 |
| 文档沉淀 | "抽取可复用流程和 prompt" | 可执行性 | 脱离实际 | 下次可复用 |

### 10.3 Git 与沉淀纪律

- 修改前看 `git status --short`，区分用户已有改动、本轮改动和暂存区；不覆盖无关改动。
- 默认不自动暂存、不自动提交。提交遵循 `type(scope): summary` Conventional Commit。
- PR 小而聚焦：一特性一 PR，squash merge 保持线性历史，便于 `git revert` 与 `git bisect`。
- 任务完成即提交，commit often。
- 一次性问题不沉淀；稳定重复出现的知识进 README / `docs/`；跨项目经验进全局 Skill（改个人 Skill 前先获用户授权）。
- 交付轻量：简单任务说结果和验证；一般任务补关键文件；只有真实存在未验证项或剩余风险时再说明风险。

### 10.4 团队 AGENTS.md 验收标准（一票检验）

> 任何开发者应该能拉起 Codex、说一句 "run the tests" 就一次成功。做不到，说明 AGENTS.md 缺了必要的 setup / build / test 命令。

| 检查项 | 标准 |
|---|---|
| AGENTS.md | 短、准、可执行；命令齐全；细节放 docs 引用而非内联 |
| config | 最小权限，无硬编码 token 和私人路径 |
| MCP | 白名单 + 最小授权 + 可审计 |
| Skills / Plugins | 单一职责、有来源版本、可回滚 |
| 测试 | 关键路径覆盖；review 要求行号级 findings |
| 安全 | 密钥不入库；高风险操作黑名单 |
| 复盘 | 规则与模板随复盘更新 |

## 11. 常见失败模式与修复

| 失败模式 | 现象 | 纠正提示词 | 预防规则 |
|---|---|---|---|
| 没读懂需求 | 产出偏题 | "复述需求和不确定点，先别改" | 先澄清 |
| 范围过大 | diff 很散 | "只改这些文件" | 文件白名单 |
| 编造 API | 调用不存在接口 | "列 API 来源链接" | 查官方文档 |
| 删除有用代码 | 功能缺失 | "解释每处删除原因" | 禁止顺手删除 |
| 类型过关业务坏 | 行为变了 | "保持运行行为不变" | 行为测试 |
| 只测 happy path | 回归漏掉 | "补边界测试" | 测失败路径 |
| 移动端异常 | 窄屏坏 | "列 375/390/768 视口验收" | 响应式检查 |
| 解释多无产出 | 只有文字 | "产出文件或 diff" | 交付格式 |
| 上下文过长跑偏 | 忘目标 | "先总结当前目标" | `/compact` + 分阶段 |
| 多代理冲突 | 同文件覆盖 | "分配文件白名单" | worktree 隔离 |
| 半迁移状态 | 模式选错 | "先确认当前迁移阶段" | 完成迁移再开新线 |
| 版本误判 | 命令不可用 | "先读取版本和 help" | 本地核验 |
| 安全失控 | 执行高危命令 | "高风险只给建议命令" | sandbox × approval |
| 忽略 AGENTS | 风格不符 | "先读 AGENTS" | 入口规则 |
| PR 描述不可信 | 测试虚假 | "列真实命令输出" | 不编造验证 |

## 12. 90 天学习路线（13 周版）

## 13. 一页速查表

| 目标 | 最佳动作 |
|---|---|
| 不确定需求 | 先让 Codex 复述和提问 |
| 陌生项目 | 只读索引，再画模块图 |
| 改代码 | 文件白名单 + 测试命令 |
| 修 bug | 失败测试先行 |
| 做 review | `codex review --base main` 或 `/review`，按严重度和行号 |
| 长任务 | `/goal` 挂目标 + 分阶段总结 + `/compact` |
| 上下文吃紧 | `/status` 查余量 → `/compact` 或 `/new` |
| 想试另一方案 | `/fork` 分叉，不动主线 |
| 主线跑着想问小事 | `/side` 侧聊 |
| 高风险操作 | 只给建议命令，人工执行 |
| CI 自动化 | `codex exec --json -o out.md` |
| 配置不生效 | `/debug-config` 看层叠 |

```txt
提示词五律：
只读分析：不要修改文件，先列证据。
计划先行：给文件白名单、验收点、回滚点。
最小修改：只改目标文件，不做无关重构。
测试先行：先写失败测试，确认失败原因。
交付总结：修改原因、影响范围、验证方式。
```
