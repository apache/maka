### 4.3 适合这次需求的方法术语

这些是可操作的工程方法，并非大模型专有的思维能力。选择依据是它们能否改变当前决策或验收。

| 方法 | 本次具体用途 | 使用边界 |
|---|---|---|
| 第一性原理 / 需求与不变量 | 先问用户承诺是什么：基线比较、续传、创建成功、补丁不丢失；再看源码是否兑现 | 不从“架构师应该有某模块”推导需求 |
| 契约驱动开发、契约测试 | 明确输入、输出、错误、终态、资源释放与允许偏差 | 编译通过、字段相同不代表完整行为兼容 |
| 差分测试、独立 oracle | 多实现共同对照独立期望；language 检查每一路，coding-agent 期望来自 spec | 多个实现复制相同错误，也能一致通过 |
| 状态机不变量、生命周期所有权 | 保护终态；旧请求不能改新请求；任务只能占用一次；资源由创建者清理 | 就地增加判断与原子占用，不先引入框架 |
| 单一可信来源（SSOT）、高内聚低耦合 | 技能源/投影分开；协议/Provider 分开；清单只维护一份 | 共享语义不等于共享全部实现 |
| 证据驱动工程、评测驱动开发 | 把静态、离线、真实集成、质量评测分别记录 | 不能用用例总数替代任务质量或线上可用性 |
| 对抗式审查、变异测试 | 用完成后 start、重复路径、第二写失败等反例，尝试推翻“已正确” | 针对具体承诺，不凑风险清单 |
| 奥卡姆剃刀、YAGNI、消融验证 | 先就地修字段/判断/断言；有可删除抽象时，用同一验收验证删除 | 不删除权限、数据保护、必要兼容与失败处理 |
| 不确定性登记、知识蒸馏 | 把来源、决策、反例、边界压成短记录，方便以后继续 | 此处是经验提炼，不是模型训练中的知识蒸馏 |

LLM Engineering 应分开看两层：协议、解析、工具与状态用确定性测试；推荐或答案是否有用用任务评测。后者应先定义目标与代表性样例，再结合人工判断比较结果。参考 [OpenAI Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)。本报告没有推荐购买服务或使用某个新评测平台。

Agentic Engineering 的下一步建议是验证工具闭环、错误反馈、停止与恢复；是否需要模型自主调度，应由任务复杂度与收益决定。简单可组合模式、从小方案开始的原则见 [Anthropic Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)。该文发表于 2024 年，其工具清单有更新提示；这里仅引用架构原则。

Context Engineering 可以先落实为轻量索引、文件路径与按需读取；保留决策和未完成项，避免每次加载全部规则与历史。依据 [Anthropic Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。这不要求为现有项目新增向量库或记忆服务。

#### 证据与优先级口径

- **F：已核对事实**。源码、字段、数据或文档的差异已直接读到；不自动代表用户侧故障已复现。
- **R：静态风险**。由调用链推演的失败、竞态或资源残留；实施前用最小反例复现。
- **D：待裁决契约**。多个合理产品选择；不能先把当前行为改成自己的偏好。
- **P1**：已承诺的主行为、数据/终态或验证可信度存在缺口，选中该项目后优先处理。
- **P2**：局部可移植性、维护成本或诊断改进。这里没有证明需要立即处置的线上 P0。

证据置信度与优先级不同：可以高置信地确认“没有前置状态判断”，但实际触发频率未知。以下源码事实置信度较高；所有动态结果仍未验证。

### 4.5 分批推进与 PR 边界

不为全部项目同时开工。先选一个项目、一个公开行为，完成后再选下一项；下表没有承诺工期。

| 批次 | 目的 | 建议候选 | 完成标准 |
|---|---|---|---|
| A：校准入口与承诺 | 让读者和 Agent 能找到事实、理解真实能力 | 父 README 路径；console 旧规则；agent-hub 恢复/fixture 声明；coding-agent 原子性边界 | 文案与源码、现有证据一致；待裁决项仍标明待定 |
| B：修最小确定缺口 | 用小改动兑现已有主行为 | skills-explorer 分类键、diffmap --base、TAPD overrides、language IR 断言、HTTP 中继 | 用户边界先红后绿；相邻既有检查通过；不增加新框架 |
| C：保护失败与生命周期 | 避免错误、重试、并发破坏状态 | 终态保护、流所有权、备份导入、单任务占用、续传/临时资源 | 对应最小反例、状态/字节/资源观察通过 |
| D：选择长期方向 | 根据实际使用决定继续、稳定或归档 | 一个主项目；少量模型质量样例或一条最小集成 | 有明确用户任务、基线与收益；没有收益则停止扩展 |

**如果暂时只做一次优化**：建议从 `diffmap --base` 或 skills-explorer 分类键中选一个。它们的接受输入与实际行为差距明确，验收局部、无需外部账号。若 TAPD 是每天使用的工具，则当次配置兑现应前移。排序随真实使用调整。

PR 切分按契约与根因，不按语言或文件数量：

- 参数丢失：CLI 回归、最小修复与相关文档同一个 PR，标题可写“让 --base 实际启用基线比较”。
- 五语言共同语义：先裁决 spec，再将各实现与同一 conformance 场景作为可审阅的一组变更；不要只修一版并制造漂移。
- 数据发布：来源/分类 ID 的修复与失败发布保护可以分别成 PR，避免一个修复承担完整构建系统设计。
- 行为无变化的文案校准可以独立成 PR；文案跟随行为的变更应一起说明保证与限制。

每个 PR 描述保留：具体触发与前后行为、所依据的契约、实际运行的验证、尚未验证的边界。只附与该 PR 有关的风险，不写通用清单。记录 red/green 结果时写出命令、版本和观察；未跑不写通过。

未来按 tdd 推进时，先确认选中行为与公开边界，再用一个失败场景锁定预期，做最小实现和必要回归。文档改动用事实/链接检查，不硬套红绿测试。测试不读取真实凭证、不替用户执行外部写入。

### 4.6 可持续文档与归档方式

先维护索引和各项目现有文档，不一次性生成17套模板。

1. **总入口**只记录实际路径、用途、生命周期状态、主证据入口与复核日期。新增项目时补一行；产品阶段与仓库位置分开。
2. **项目 README**回答“做什么、怎么最小运行、已经证明什么、明确限制是什么”；复杂契约继续留在现有 spec/ADR，不把 README 扩成全集。
3. **跨项目 docs**保存本报告这类比较与决策。项目 Bug、测试结果、实现 TODO 回到所属仓库；fork 的贡献状态继续回到 fork 台账。
4. **历史快照**写日期、commit、命令、环境与结果；新结果追加或替代当前摘要，保留必要历史依据。源码行号随版本变化，复核时更新。
5. **归档**需由你确定停止投入，再记录最后可运行环境、遗留问题与恢复入口；先标状态，确实需要才移动 `_archive/`，不把“归档”当删除。

候选生命周期仅作分类建议：`active`（持续使用/建设）、`maintenance`（限定修复）、`reference`（学习参考）、`archived`（停止维护且留恢复信息）。本轮不替任何项目设置状态。

项目登记可从最少字段开始：`项目/实际路径/用途/状态/证据入口/下一项/复核日期`。只有真实检索或统计出现瓶颈，再考虑机器可读清单与自动化；无需先引入数据库、向量索引或新看板。
