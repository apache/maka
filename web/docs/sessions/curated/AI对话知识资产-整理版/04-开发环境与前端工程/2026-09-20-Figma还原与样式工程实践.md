# 03-Figma还原与样式工程实践

> 由 1 份 AI 对话沉淀合并。整理目标是保留可复用事实、决策与验证结果，压缩聊天过程。

## 核心沉淀

- Figma 还原应以可定位节点、视觉 token、结构层级和可验证的编译/截图证据为核心，避免只靠肉眼猜样式。
- 样式修复同时关注设计一致性、主题变量、编译探针、Stylelint 与 diff，最终把一次性修复沉淀为可复用 UI 工程流程。

## 来源与整合内容

### 来源：护理服务报告安心延续居家推荐商品样式修复与Figma对齐.md

### 一、问题背景

项目为 `beauty-smart-advisor`，目标区域是护理服务报告的模块五“安心延续”中的“本次护理对应的居家选择”。用户提供了 Figma 链接及开发界面与最新设计图的对比截图，要求对齐节点 `5` 与 `10` 的推荐商品卡片样式。

对比中暴露出三项样式偏差：

1. 推荐商品卡片缺少与设计稿一致的边框；
2. “使用场景”字段颜色没有随浅色／夜间主题正确切换；
3. “注意事项”字段被显示成金色。用户随后明确纠正：该字段应统一使用 `#AAA49A`，而不是金色。

本次仅调整样式令牌与 SCSS，不改动推荐商品的数据、业务字段、渲染结构或交互。

### 3. 关键决策

- 不在组件中写死主题判断，也不修改产品数据；通过报告页现有 CSS 自定义属性完成主题分流。
- 为推荐商品建立专属变量，避免“使用场景”“注意事项”“边框”继续复用泛化的模块品牌色或下次到店卡片变量。
- 产品变量仍保留模块变量与固定值的回退链，降低调用点缺少局部变量时的显示风险。

### 五、目录与命名约定

本次沿用既有模块边界：

```text
src/pages/serviceComplete/components/
├─ HomeCareProducts/
│  └─ index.module.scss     # 推荐商品自身的样式消费方
└─ PageContent/
   └─ index.module.scss     # 报告浅色／夜间主题变量提供方
```

新增变量均以 `--report-product-` 为前缀，语义与职责一一对应：

- `--report-product-usage-scenario-color`：使用场景色；
- `--report-product-note-color`：注意事项色；
- `--report-product-border-color`：商品卡片边框色；
- `--report-product-border-width`：商品卡片边框宽度。

这比继续挪用 `--report-module-brand-color` 或 `--report-next-visit-*` 更能表达产品卡片的局部设计职责。

### 七、有效方案及原因

| 方案 | 结果 | 原因 |
| --- | --- | --- |
| 在报告页按主题提供产品专属 CSS 变量 | 采用 | 主题差异集中在容器层，组件不需要新增判断或 props。 |
| 在商品组件保留变量回退链 | 采用 | 保持现有模块变量可用，并为未提供局部变量的场景保留可预测默认值。 |
| “注意事项”统一设为 `#AAA49A` | 采用 | 这是用户最后一次明确提出的验收值，优先级高于先前 Figma 上下文返回的金色值。 |
| 修改业务数据或新建主题组件 | 未采用 | 当前问题是局部视觉还原，扩大改动会增加无关回归风险。 |

### 八、失败尝试、踩坑与经验

### 1. 不再使用 Stylelint 的 `--syntax scss`

曾执行：

```powershell
npx.cmd stylelint "src/pages/serviceComplete/components/HomeCareProducts/index.module.scss" --syntax scss
```

结果失败。当前 Stylelint 已不再接受该参数，并提示应通过 `customSyntax` 配置处理 SCSS。后续改为不携带该参数的项目现有调用方式，命令退出码为 `0`。

**经验：** 不要把旧版 Stylelint 的 CLI 参数复制到当前项目；先使用仓库已有配置，再根据实际报错决定是否补充 `postcss-scss` 或 `customSyntax`。

### 2. Prettier 检查不等于格式化

修改后第一次 `prettier --check` 因新代码尚未格式化而失败。执行 scoped `prettier --write` 后重新检查通过。

**经验：** 局部 SCSS 改动采用“写入格式化 → 只检查 touched files”的闭环，避免运行全仓 `npm run format` 造成无关改动。

### 3. Figma 证据与用户纠正冲突时的处理

Figma 上下文对“注意事项”返回了金色系，而用户明确要求 `#AAA49A`。实现选择后者，并将最终规则沉淀为独立令牌。

**经验：** 设计工具输出是重要证据，但最新、明确且可验收的用户口径应作为最终决策来源；把冲突点记录在提交说明或交接文档中，避免后续人员误以为灰色是误改。

### 十一、可迁移到其他项目的通用经验

1. **主题化 UI 先拆语义，再拆颜色。** 将“使用场景色”“注意事项色”“产品边框”定义为独立语义令牌，远比一个通用品牌色承载多种文本层级更可维护。
2. **主题变量应由页面容器提供，组件只消费。** 这样可以让同一组件在浅色、夜间或未来的其他主题中复用，无需引入条件渲染和 prop 膨胀。
3. **小型视觉修复保持最小改动。** 只触达组件样式和所属页面主题变量，不改数据结构、业务逻辑、图片资源或公共抽象。
4. **建立“设计证据—用户验收—代码令牌”的可追溯链。** 设计工具值与业务方最后确认的口径出现冲突时，显式记录采用理由，减少后续回归争议。
5. **局部 UI 改动做相称验证。** 先格式化、再检查目标文件、再做编译与 diff 空白检查；若要声明视觉一致，还需补充实际页面截图或人工验收。
