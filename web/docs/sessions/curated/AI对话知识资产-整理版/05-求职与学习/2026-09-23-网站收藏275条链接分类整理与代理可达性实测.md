## 三、关键决策

| 决策 | 理由 |
| --- | --- |
| 网络判定用本机双轮 curl 实测（直连→失败者走代理复测），不用经验值 | 环境里系统代理开着、公司网络出口特殊，经验判断误差大；实测一轮约 3 分钟，换取全部结论可复现 |
| 站点用途派两个并行子代理用 WebFetch 核实，prompt 里写死「抓取失败就写抓取失败，禁止编造」 | 40+ 个冷门站点逐个自己抓太耗上下文；子代理并行快，反幻觉约束保证说明栏不掺假 |
| 重复链接（Figma 11 条深链、ChatGPT 13 条、内网深链）不做去重丢弃，合并到同一站点条目下逐条保留 | 用户要的是「整理」不是「删减」；覆盖率校验也要求每条 URL 原文保留 |
| 抓不到的站点标「未验证」，另设「已知缺口」附录 | 不假装全知；用户可自行决定是否补验 |
| 交叉引用型重复行（"见第 X 类"）全部删除，每条链接只在最贴切处出现 | 首版出现 9 条重复 + 1 处错误标签，破坏"单一主条目"原则 |

## 四、技术方案

### 4.1 可达性探测（直连 vs 代理）

```bash
# 对照组先校准方法：baidu 直连应 200，google 直连应 000、走代理应 200
curl -sIL -o /dev/null -m 6 -w '%{http_code}' https://www.baidu.com
curl -sIL -o /dev/null -m 6 -w '%{http_code}' -x http://127.0.0.1:7897 https://www.google.com.hk

# 批量探测：HEAD 拿状态码，非 000 即可达；失败降级 GET + range 限流
code=$(curl -sIL -o /dev/null -m 8 -w '%{http_code}' -A "Mozilla/5.0 ... Chrome/131" "$scheme://$h")
# 代理复测只跑直连失败者
curl -sIL -o /dev/null -m 10 -w '%{http_code}' -x http://127.0.0.1:7897 "https://$h"
# 并行：xargs -P 16，120+ 域名约 3 分钟
```

判读规则：`000`=连不上（超时/重置，疑似被墙）；任何 HTTP 状态码=TCP+TLS 已通、站点可达；`403/405/468`=站点反爬或不允许 HEAD，**不代表被墙**（prism.openai.com 直连 403 但浏览器正常）。

### 4.2 环境事实（判定成立的前提）

- Windows 系统代理指向 `127.0.0.1:7897`（Clash 系，端口在监听），但 **curl 不读 WinINET 系统代理**，直连 curl 是真直连；
- Google 直连返回 000，证明当时**没有 TUN 全局接管**，直连测量有效；
- `netstat -ano | grep 7897` 确认代理端口监听状态。

### 4.3 可疑响应的真伪校验（防 DNS 劫持假 200）

对状态可疑的域名（403/非标码）追加：`curl -s -w 'code=%{http_code} ip=%{remote_ip}'` 看响应 IP 是否为真实 CDN（Cloudflare 段 104.18.x / 172.66.x）+ 抓 body 前 200 字节看是否站点本体。本次据此确认 toolify.ai、423down.com、ego.app、devin.ai 的响应均为本体而非劫持页。

### 4.4 站点用途核实（子代理并行）

两个 `general-purpose` 子代理各领 14/18 个冷门站点，统一输出格式「网址 | 一句话中文说明 | 面向用户」，硬性要求：抓取失败写「抓取失败」、不许猜测、只回表格不回过程。产出直接进文档说明栏。

### 4.5 完整性校验（交付前必做）

```bash
# 源文件抽 URL（含 file://、chrome-extension://）
grep -oE '(https?|file|chrome|chrome-extension)://[^ |]+' src.txt | sort -u > src_urls.txt
# 逐条在成果文档里找原文
while IFS= read -r u; do grep -qF "$u" doc.md || echo "MISSING: $u"; done < src_urls.txt
```

表格结构自检：`awk '/^\|/{n=gsub(/\|/,"|"); if(n!=4) print NR": "$0}'` 找列数异常行（2 列表为 3 根管道，属正常需按表区分）。分类条数统计：按 `^## N.` 分节数含链接的表格行，回填速览表。

### 4.6 文档结构约定

- 「网络」列四值标记：✅ 直连 / 🔒 需代理 / 🏢 内网 / 💻 本地，开头给图例与判定日期，声明是快照会过期；
- 每类一张三列表：链接（可读标签超链接）｜中文说明｜网络；
- 文末「必须挂代理的域名」速查表 + 「直连可达但容易误判」清单 + 已知缺口附录。

## 五、失败尝试与踩坑

1. **首版完整性校验缺 4 条 URL**：`commandcode.ai/docs/plans/goat`（写作时真漏了）、`github.com/ycccccccy/wx_key.git`（是 Gitee 仓库描述里的 fork 指向，同一仓库的 `.git` 变体）、两条 Figma 链接（`%25` 双重 URL 编码变体、同 node-id 不同 `t` 分享参数）。教训：**URL 变体会造成假缺失**——`%25E9` 是 `%E9` 的二次编码，校验发现 missing 时先判断是不是同一资源。
2. **错误标签**：把微软商店镜像 `msft-store.tplant.com.au` 的交叉引用行误写成「Nyaa 备用镜像」，靠逐行 grep「见第」揪出。
3. **速览表条数与实际不符**：手写估算的数字在增删行后全部漂移，改为脚本按节统计后回填。
4. **Edit 工具状态失效**：用 Python 直写文件后，再调 Edit 报 "File has been modified since read"。教训：**凡绕过 Edit 工具改了文件，必须先 Read 再 Edit**。
5. **nyaa.si 的假信号**：https 直连 000，但 http 返回 301（疑似劫持或半可达），单看一轮会误判「直连可达」；https/http 双 scheme 探测 + 代理复测后才定「需代理」。
6. **HEAD 请求的局限**：`-I` 对部分站返回 000/405，需要 GET + `-r 0-2048` 降级复测，否则会把可达站误判为不可达。

## 六、有效方案及原因（可复用）

- **双轮探测 + 对照组**：先测已知可达/已知被墙的站校准方法，再跑全量——避免代理端口没开、TUN 模式等环境变化让整个测量作废。
- **「域名可达」≠「服务在监听」≠「浏览器能开」三层区分**：curl 状态码只能证明第一层；内网服务和本地端口要单独探；403 防盗链/反爬要单独解释。
- **机械校验兜底**：生成类任务的完整性不靠自述，靠 `grep -qF` 逐条比对，本次靠它抓出 4 条真遗漏。
- **子代理分工标准**：独立、输入输出明确、无共享状态（纯只读核实）才外派；分类与写作这种连续决策留在主会话。

## 九、可迁移到其他项目的通用经验

1. 任何「批量判定」任务先跑 2~3 个已知答案的对照组，校准测量方法再全量执行；
2. 实测 > 经验：被墙/可达这类「常识」错误率超预期（本例 13/123，且含多个反直觉项）；
3. 生成文档后必须做机械覆盖率校验，URL 类内容用原文 `grep -qF`；
4. URL 变体（二次编码 `%25`、`.git` 后缀、追踪参数 `t=`/`spm=`）是覆盖率校验的假阳性来源；
5. 委派子代理的 prompt 必须显式给「失败的合法出口」（如「写抓取失败」），否则模型倾向编造；
6. 文档里显式标注「未验证」和「已知缺口」，比假装完整更可信；
7. 绕过编辑工具直写文件后，必须重新 Read 才能 Edit；
8. 探测类命令统一带 `-m` 超时 + `-A` 浏览器 UA + 并行度控制，否则批量任务会被个别慢站拖死。
