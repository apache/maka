# Coding Agent 项目开发 Skill Builder 创建、原型生成器方法迁移与技能发现修复复盘

> 本文复盘当前 Coding Agent 对话中关于项目开发 Skill Builder 的设计、创建、迁移和后续完善。记录的是本对话实际决策与可复用工程方法，不代表下游技能已通过行为评测。
> 核验日期：2026-09-23（Asia/Shanghai）。

## 一句话结论

最终目标是一个可以从指定项目的当前源码、工作流需求、可选 Git 变更和已有 Skill 中，**实际生成完整、可调用、带证据与验收条件的项目开发 Skill** 的 Builder；原型设计 Builder 只贡献可复用的生成方法与质量门，不把产品原型知识照搬到所有技术工作流。

## 1. 背景与任务演进

最初问题是解释 `product-prototype-skill-builder` 为什么能“生成另一个 Skill”。分析确认，Skill Builder 不是新模型或特殊编译器，而是将证据收集、规则提炼、目标 Skill 写入和校验固化为 Agent 可执行的工作流，实际读写由当前模型和宿主工具承担。

之后，用户希望结合 `E:\Projects\frontend` 中自己的前端开发提交、个人 Skills，为实际项目开发经验生成 Builder；提出的试点链路为 `beauty-smart-advisor` 的“护理报告预约入口 → 表单 → 提交 → 条件式确认 → 成功后更新”。

### 关键纠偏

第一轮实施误将交付物缩减为预约链路 Markdown 参考，没有满足“生成 Builder Skill”的核心需求。用户明确纠正后，交付目标调整为可发现、可调用、生成下游 SKILL.md 的 Builder。

第二轮最初将 Builder 放在 `01-Skill工程` 的临时位置；用户手动将它迁移到 `C:\Users\802165\.ai\categories\99-归档与淘汰\01-个人开发\project-workflow-skill-builder`，并指出它与最初参考的 prototype builder 差异明显。随后补做针对性比较、扩充核心流程与 references，并修正 Codex Junction。

**可迁移的教训：**用户强调“创建一个 Builder Skill”时，完整 Skill 包才是验收物。业务参考页可以是该 Skill 的资源，不能替代 Skill 入口。

## 2. 最终目标与边界

Builder 的任务是将具体项目中的稳定开发经验转成**可供后续 Agent 使用的工作流 Skill**，而不是：

- 直接实现业务功能；
- 仅输出项目分析或 Markdown 经验页；
- 把一次性历史补丁、其他项目的字段、临时阈值固化为通用规则；
- 把视觉、API、CLI、异步任务套成同一套检查清单；
- 先要求 A/B 收益证明，再决定是否执行用户明确要求的 Skill 创建。

创建与效果证明是两个不同验收层级：本对话完成了 Builder 包创建与若干静态/发现检查；没有完成目标生成 Skill 的真实行为评测，也没有测量下游开发收益。

## 4. 从原型 Builder 迁移了什么、区分了什么

参考 Skill：

`C:\Users\802165\.ai\categories\99-归档与淘汰\03-付费购买\product-prototype-skill-builder`

其中保留为通用 Builder 架构的方法：

1. **先识别项目形态**：不要把 Web 后台、移动端、AIGC、编辑器、服务/API 预设成同一种应用。
2. **按证据提炼规则**：当前配置和共享实现优先；单页或单次修复是局部线索。重复次数是采样参考，不是规则正确的数学证明。
3. **生成自洽的目标目录**：SKILL.md 是必需入口；references 按需使用；平台专属 metadata 可选。
4. **规则来源可追溯**：下游 Skill 应能看到规则对应的文件、范围、证据与未验证项。
5. **把质量要求带入下游 Skill**：不是只在 Builder 说“注意质量”，而是转成下游实际的执行动作和验收。

不再把原型领域细节推广到其它项目任务：

- 终端、产品形态和交互框架用于**分类取证**，不是强制套用 UI 章节。
- 控件重置、视觉还原、渲染预览只适用于前端页面/原型输出。
- API Builder 应聚焦 schema、service、DTO、映射、错误语义和契约样本。
- 异步任务 Builder 应聚焦资源/任务标识、状态转移、确认、重试、恢复、迟到响应与幂等；不把原型视觉验收带进来。
- 不强制每种 Skill 都给固定代码骨架或至少十条检查口号；输出随产品证据和用户验收而定。

## 5. 最终生成工作流

### 5.1 核实意图、仓库和现有覆盖

- 从当前请求提取工作流、产物类型、验收、可选作者/时间范围和目标目录。
- 先读适用项目规则、构建入口和目标已有 Skills。
- 用户已明确创建时，复用旧规则不等于拒绝创建目标 Skill；现有同用途 Skill 优先原名最小更新，不制造重复 `-v2`。
- 目标仓库必须真实存在；缺 Git 历史不阻断从当前源码取证。

### 5.2 按工作流形态采集证据

- 先检查少量代表性入口与链路，遇到证据缺口再扩大读取范围。
- Git commit 标题用于定位；关键经验需要查看实际 diff，并复查它是否仍存在于当前代码。
- 区分通用方法、当前项目事实、局部模块约束、历史案例与未验证假设。
- 若多端并存，分别注明适用范围和切换条件；不要把 A 端布局或状态规定强加给 B 端。

### 5.3 生成可调用的目标 Skill

- 必须实际写入目标目录的 `SKILL.md`。
- 对每条关键规则记录触发条件、动作、验收、来源和未验证事项。
- 至少输出需求明确适用的工作流：本版覆盖存量迭代、全新功能、缺陷修复；只保留真实适用分支。
- references 只保存有复用价值且加载时机明确的细节。
- 下游 Skill 不依赖 Builder 的绝对安装路径或所有 Agent 技能一起加载才能运行。
- 用户只要候选/计划时遵循只读要求；用户明确要求创建时，不能把“效果还未 A/B”误当成停止写文件的理由。

### 5.4 按产物类型选择质量要求

适用约束必须进入下游 Skill 本身：

- 全部产物：事实来源、失败语义、改动范围和与任务匹配的验证。
- 前端/UI：现有设计体系、实际涉及控件的可见状态、结构检查；只有渲染环境支持时才要求条件式肉眼验证。
- API/字段：契约来源、映射链、错误/空值/业务失败样本；接口真实语义未知时标待确认。
- 异步任务：任务与资源身份、状态和副作用、部分成功、恢复/取消、竞态与资源清理。
- CLI 或其他产物：当前参数、输出、退出码及副作用检查，不继承 UI 控件清单。

静态检查、宿主发现、行为验证、收益评测是独立证据，彼此不得互相冒充。

## 6. 各方案的实际效果与未完成项

### 有效设计

- 采用“入口 Skill + 按需 references”，把主工作流留在 `SKILL.md`，产品形态、输出契约和质量门分开展示。
- 用户手动迁移后，回头核对 Junction 的真实目标；确认它仍指向旧目录，随后将已核验的 Junction 改指当前归档目录，没有递归删除其目标。
- 以 Codex app-server 的 `skills/list` 验证过创建初版时的技能发现。该检查发生在用户手动迁移之前。

### 曾经走偏的尝试

- **用预约业务 Markdown 代替 Builder**：没有交付用户要求的可调用生成器，用户指出后才纠正。该类业务文档可以作为目标参考，但不是 Builder 本身。
- **先用单一项目内容写一个过宽泛的 Builder**：初版虽然可调用，但没有覆盖参考 prototype builder 的产品形态识别、稳定证据分级和多种下游质量约束。
- **要求“先 A/B 证明有收益”才建立 Skill**：把效果评测误设成创建前置条件。正确顺序是先完成明确要求的 Skill，再将实际使用效果标为未验证，等待后续独立评测。

### 仍需验证

- 手动迁移并扩充后，Codex 会话中的 Skills 列表是否已刷新并发现当前归档位置下的版本。本对话验证了最终 Junction 指向，但没有在迁移和最终更新后重新调用 `skills/list`。
- Builder 是否能为不同项目稳定产出有用的目标 Skill，尚无基于同一任务/源码/模型的基线与新 Skill 对照评测。
- 本对话未运行音频任务或预约项目的下游 Skill 生成和行为验证；已存在的预约参考文档不是生成器效果证据。
- 曾在先前会话列举的 Git 提交计数仅对应当时本地分支快照，随检出分支/历史变化；继续分析时重新检索。

## 7. 建议的 Builder 验收

首次实际调用时，选一个明确项目工作流生成目标 Skill。检查：

1. 目录名、frontmatter name 与 references 链路自洽。
2. 工作流的触发、排除和输入能让下游 Agent 采取具体动作。
3. 关键项目规则引用当前源文件，历史补丁没有被误写成通用真理。
4. 测试用例覆盖正向、失败、状态切换和不应触发；待执行与已执行清楚区分。
5. 每种产物只继承相关质量检查，不出现所有端统一验收表。
6. 下游 SKILL.md 是真实主入口，而非仅有参考文件。
7. 与当前工作流进行新上下文对照，并保留一个未用于提炼的真实任务；记录人类纠正、返工、无关改动及上下文成本。

若 Builder 生成不完整，优先修复相应生成步骤或输出契约；不为每一种项目预制一套过度具体的模板。

## 8. 可迁移到其他项目的经验

- **Skill Builder 是有落盘验收的生成器，不是分析文档名。**
- **流程骨架通用，业务规则必须重取证。** 将 UI、API、异步任务、CLI 的事实混成一种证据等级会制造误导。
- **提交史讲“如何变化”，当前源码回答“现在是什么”。**
- **显式要求不能被“已有方法可复用”弱化。** 可复用的是方法，不是对明确产物的降级。
- **直接解决迁移后目标与发现入口不一致的问题，并验证最终链接，不以目录存在推定宿主已识别。**
- **质量判断分层：结构合法 ≠ 宿主发现 ≠ 行为通过 ≠ 收益证明。**
- **不确定项可记录并待测，不要求为了创建 Skill 先证明它提升了效率。**
