# 02-AI模型接入与代理排障

> 由 5 份 AI 对话沉淀合并。整理目标是保留可复用事实、决策与验证结果，压缩聊天过程。

## 核心沉淀

- “模型不存在”“认证失败”“降智/429”应先按供应商、模型名、鉴权、代理映射和实际请求链路逐层取证，避免直接归因模型本身。
- 代理/中转方案需要把客户端配置、代理层映射、供应商真实 model id 与凭证四层分开验证；必要时用直连作为对照实验。
- 对社区绕过方案与未验证注入技巧保持审慎，优先采用可解释、可回滚、可复现的配置修复。
- cc-switch 的多供应商配置是「解析合并、供应商同名键覆盖」而非文本追加：四统一键放通用配置安全，接入块（base_url 不同）不进通用配置。
- 改 ~/.codex 配置的标准动作：备份目录 + 变更前后 SHA-256 + config.toml 与 template 双改 + tomllib/generate-config 验证，端到端请求验证需完整重启 Desktop。

### 来源：CLIProxyAPI接入智谱GLM报模型不存在排查与修复.md

### 最终结论

**模型名没有问题，问题在端点协议与上游格式不匹配。**

- 智谱有两个不同协议的端点：
  - `https://open.bigmodel.cn/api/paas/v4` —— OpenAI Chat Completions 协议；
  - `https://open.bigmodel.cn/api/anthropic` —— Anthropic（Claude）Messages 协议（官方 Claude Code 接入文档指定的地址）。
- 上游格式选了「Anthropic Messages (原生)」（直连、不转格式），代理便按 Anthropic 协议向 `{请求地址}/v1/messages` 发请求；`paas/v4` 下不存在该路径 → 上游 404 → 客户端把 404 泛化翻译成「模型不存在或无权访问」。
- **两个不同模型名先后报同一错误，正说明与模型名无关，是链路/端点问题**——端点错了，选什么模型都失败。

已核实事实（智谱官方文档）：

- Anthropic 兼容端点：`https://open.bigmodel.cn/api/anthropic`（docs.bigmodel.cn 的 Claude API 兼容 / Claude Code / Coding Plan 快速开始页）。
- `glm-5.3-flash` 是真实模型（docs.bigmodel.cn 模型文档：GLM-5 系列首个原生多模态，320B 总参数 / 18B 激活 MoE）。

### 问题背景

- 用户在 VSCode 插件（Claude Code 类客户端）中通过本地 CLIProxyAPI 代理接入智谱 GLM（`glm-5.3-flash`、`glm-5.3`）。
- 发送任何消息均失败，插件报错：

  ```
  There's an issue with the selected model (glm-5.3-flash). It may not exist or you may not have access to it.
  ```

  换成 `glm-5.3` 后报同样错误。

- 目标：定位报错根因并给出修复配置。

### 修复方案（二选一）

**方案 A（推荐，已给出）：改请求地址，保持原生直连**

- 「请求地址」`https://open.bigmodel.cn/api/paas/v4` → `https://open.bigmodel.cn/api/anthropic`
- 「上游格式」保持 Anthropic Messages (原生) 不变；结尾不带斜杠。
- 理由：直连不转格式，链路最短；若 key 是 GLM Coding Plan 套餐 key，本来就应该走 Anthropic 端点。

**方案 B：改上游格式 + 路由接管**

- 地址保留 `paas/v4`，「上游格式」改 Chat（Chat Completions），并开启路由接管让代理做协议转换。
- 缺点：多一层转换，不如方案 A 直接。

**验证两步**：配置页点「管理与测速」或「获取模型列表」（能拉到模型列表即 key + 端点打通）→ 回插件重发消息。

### 踩坑经验

1. **客户端错误文案不可按字面理解**。"It may not exist or you may not have access to it" 看起来像模型名/权限问题，实际是上游 404 的泛化包装。拿到这类报错先怀疑请求链路（URL、协议、路径），再查模型名。
2. **换模型名复测是低成本定位手段**：两个模型名同样失败 ⇒ 排除模型因素，锁定端点/认证/网络。
3. **"上游格式"与"请求地址"必须协议配对**：原生 Anthropic 格式必须配 Anthropic 端点；Chat 格式地址必须配 Chat 端点并开转换。截图配置页的黄条提示（不要以斜杠结尾、转换需路由接管）就是为此存在的。
4. **配错端点的表现为"全军覆没"而非个别模型失败**——这是区分端点问题与单模型问题的关键特征。

### 可迁移的通用经验

- 任何"Claude 兼容客户端 → 代理 → 国产模型厂商"的链路，先核对厂商是否提供 Anthropic Messages 原生端点（智谱：`/api/anthropic`），有则原生直连优于协议转换。
- 排障顺序：先验证端点连通（拉模型列表/测速）→ 再验证模型名 → 最后查权限/套餐。官方文档的接入示例（`ANTHROPIC_BASE_URL`）是最可靠的端点权威来源。

### 遗留问题与待验证假设

- **本对话内未实际执行修复验证**：方案 A 基于官方文档与配置推断给出，用户尚未回报改后结果。若改后仍报错，下一步用「获取模型列表」确认 key 有效性，再核对该 key 套餐类型（普通 API key vs Coding Plan key）与端点匹配。
- 未验证 `glm-5.3-flash` 在该用户 key/套餐下是否有调用权限（推断可用：其为官方公开模型）。

### 三、最终结论

1. **292 注入方案：永久拒绝（含一切变体：代码实现、spec、分步教学、提示词形态）。** 性质是对第三方服务端调度/风控机制的凭据采集重放规避（配合住宅 IP 轮换规避签发风控），不属于可协助范围。此结论不因网络架构变化、skill 包装或执行者更换而改变。
2. **该方案在用户原架构下本身也不成立（事实层面）**：原请求链为 Codex → cc-switch 本地代理 → vectorengine.ai 中转站 → 站方上游。292 由 OpenAI 端点签发给直连客户端，且绑账号、绑模型（文章 5.2/5.3 自认）；中转架构下出口 IP 和账号均属站方，本地注入点在错误一侧。
3. **源文章不可作为实现依据**：全文无字段名、无头部格式、无端点行为；codex-state-kit 无仓库无链接。它是闭源工具的软文，不是技术文档。
4. **降智第一嫌疑人：中转站号池/路由降级**（中转常见病），非 OpenAI 对个人用户的调度。
5. **用户已切换官方直连**（见下节配置），该动作本身即是"最懒且有效"的解法。

### 十一、可迁移的通用经验

1. **"我只是想正常访问 X"要先拆症状**：连不上（网络问题）与质量降级（服务端/链路问题）解法完全不同；理性化表述不算需求。
2. **架构事实优先于方案讨论**：先读配置搞清"谁连到谁、凭据归属谁"，大量方案会在架构层面自然死亡，无需进入价值观讨论。
3. **判别软文与技术文档**：无字段、无格式、无仓库链接、全篇"截图显示"的工具介绍，只能当广告读。
4. **拒绝的一致性**：同一交付物的不同包装（代码 / 提示词 / 分步教学 / 换执行者）应得到同一答案，否则包装本身就成了绕过手段。
5. **事实自己查，判断留给用户**：配置、日志、路径属于 Agent 能自取的事实；症状体验和风险偏好是用户的决策输入，不混在一起问。

### 来源：OpenClaw部署腾讯云对接微信报错 Provider authentication failed 排查方案.md

### 核心结论

报错含义：**大模型服务商身份认证失败，不是微信渠道配置问题**。根源是模型API凭证（API Key）缺失、填写错误或失效，OpenClaw网关无法调用后端大模型。微信只是消息收发通道，AI回复依赖模型服务商密钥。

### 背景与问题

在腾讯云服务器部署OpenClaw，对接微信渠道，向微信发送消息后，机器人返回报错：
> Provider authentication failed. Check the configured credentials; raw provider details are in the gateway logs.

### 有效方案（3种配置API Key方式，任选其一）

> 操作环境：腾讯云服务器，SSH终端登录
### 方式1：修改主配置文件（推荐）
1. 编辑配置文件
```bash
vim ~/.openclaw/openclaw.json
```

1. 在`models.providers`节点写入对应模型API密钥，示例openai：

```
"models": {
  "providers": {
    "openai": {
      "apiKey": "sk-xxxxxxxxxxxxxxxxxxxx你的有效API密钥"
    }
  }
}
```

1. 保存退出，重启网关

```
openclaw gateway restart
```

### 方式2：环境变量文件（常驻后台守护进程推荐）

```
cat >> ~/.openclaw/.env <<'EOF'
OPENAI_API_KEY=sk-xxxxxx你的密钥

### 踩坑与错误认知

1. ❌ 错误认知：以为是微信token/微信登录凭证报错。✅实际是大模型API密钥认证失败，和微信无关。
2. 复制密钥时，首尾带有空格、多余引号，会直接认证失败。粘贴密钥前清理空白字符。
3. 密钥所属账号余额不足、密钥在服务商后台被禁用，需要重新生成密钥。
4. 权限坑：如果曾经使用sudo启动OpenClaw，配置文件会生成在root目录，普通用户修改配置不会生效；全程使用同一个用户运行网关。

### 后续建议

1. 配置完成后先调用`openclaw doctor`自检，确认全部项目通过，再测试微信消息。
2. 密钥不要硬编码在公开脚本中，优先使用`.env`环境变量方式管理。
3. 定期登录模型服务商后台检查密钥状态与账号余额。
