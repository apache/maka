# 05-Cursor汉化插件-性能与卸载闭环

> 由 2 份 AI 对话沉淀合并。整理目标是保留可复用事实、决策与验证结果，压缩聊天过程。

## 核心沉淀

- 0.0.9 的性能核心是把全页轮询与全量扫描改成增量 MutationObserver + rAF 合并，exact 词典用 Map O(1)，只对新增/变更节点翻译。
- 卸载恢复的核心问题是扩展宿主生命周期短，不能依赖 deactivate 中的延时与长 await；最终通过运行期监听卸载事实、共享清理入口和外部重启看门狗闭环。
- 真实环境日志与磁盘事实优先于“测试全绿”，发布前必须清理 dist、抽查 VSIX 产物并冻结版本号。
- 仍需区分扩展可控弹窗与 Cursor 原生弹窗，避免把平台行为错误归因给插件。

### 二、最终结论

- **卡顿根因**：注入脚本三个机制叠加——每 100ms `setTimeout` 全页扫描（每秒 10 次、与操作无关）、`document.body` 全量 MutationObserver（每次 DOM 变更 rAF 内全页 TreeWalker 重扫）、每个文本节点线性比对 1508 条词典。0.0.8 引入 MutationObserver 后显著恶化。
- **解法**：0.0.9 重写为**增量引擎**——零轮询、零原型劫持、变更只翻译涉及节点、exact 词条走 Map O(1)（1422/1508 条），partial/regex 仅 86 条且只对未命中且 ≤200 字符节点回退。汉化能力保留。
- **卸载自动还原**最终方案：`deactivate` 同步读 `~/.cursor/extensions/{extensions.json,.obsolete}` 判定真卸载 → **先经 explorer.exe 转发调度看门狗（spawn 即返回、零 await）** → 再同步 revert → fire-and-forget `workbench.action.quit`。
- 发布由用户手动完成（Open VSX）。

### 一、问题背景与目标

**项目**：`cursor-loc` 仓库（`E:\guahub\vibe\cursor-loc`），扩展 `ggbdpq.cursor-language-pack-zh-hans`，通过改写 Cursor 安装目录（`resources/app/`）为专有界面（Settings/Agent/Composer 等 MS 语言包覆盖不到的区域）提供简体中文。分支 `feature/v0.0.9`。

**问题链**（用户逐步反馈驱动，共 6 轮）：
1. Cursor 打字/Markdown 滚动卡顿，根因是插件注入的运行时 DOM 翻译扫描器；
2. 首次修复删除了整个翻译机制 → 用户要求**两者兼得**：汉化保留 + 不卡；
3. 装上插件没汉化（补丁从未被打上）；
4. 卸载插件后汉化残留、无提示无重启；
5. 修复后仍未触发卸载自动还原（两次）；
6. 弹窗泛滥（2 次白色弹窗 + 2 种灰色弹窗 + 重启后多窗口）。

**最终目标形态**（用户原话归纳）：首次安装 → 一次引导弹窗 → 点「应用并重启」→ 自动重启生效；卸载 → 自动还原英文 + 自动重启；全程无冗余弹窗。

### 四、失败尝试与死因（关键教训）

| 尝试 | 死因 | 教训 |
|---|---|---|
| 删翻译机制（0.0.9 初版） | 用户实际要「汉化+不卡」两者兼得，删机制过度 | 需求变更要重听原话；「删到只剩静态 NLS」是当时任务书的约束，非用户真实意图 |
| 装上不汉化 | 删了引导弹窗又没保留手动提示，用户不知道要先执行「应用界面汉化」 | 删自动化时必须补上可见入口，否则功能等于不存在 |
| deactivate 里 setTimeout(1000) 兜底 | 卸载后扩展宿主 ~1s 被回收，定时器回调永不执行 | deactivate 与进程退出赛跑，任何 await/延时都不可靠 |
| isExtensionUninstalled 用 process.execPath 推导清单路径 | `process.execPath` 是 Cursor.exe 安装目录，推出来的 `D:\...\AI\extensions\...` 不存在 → 恒「无法判定」→ 跳过还原 | `process.execPath` 是应用二进制；扩展清单在 `~/.cursor/extensions/`（os.homedir 推导），必须实机核对路径 |
| 修正路径后卸载仍不重启 | revert 执行了但 `await schtasks`（1–2s）被宿主回收截断——%TEMP% 无脚本、无任务残留证实 | 与宿主寿命赛跑的 await 不可靠；须 spawn 即返回（explorer 转发）并把调度放在 revert **之前** |
| VSIX 里混入旧构建的 cursor.inject.js | tsc 不清理 dist 陈旧产物，prepare-package 整目录拷贝 | 发版前 rm -rf dist 重建；打包后必须抽查 VSIX 内容 |
| status/市场描述停留在「清理残留」文案 | 多轮方向反转后文档没跟着回滚 | 每次定位反转，description/README/CHANGELOG 要一起过一遍 |

### 五、踩坑经验（可迁移）

1. **「测试全绿但真机不对」循环的破解**：三次修复两次栽在真实环境路径/时序上。破解手段是同步 trace——在可疑链路每步之间 `fs.appendFileSync` 写 `%TEMP%` 侧车日志（卸载场景下 Output Channel 内容随宿主死亡丢失，不可作事后取证源），用户卸载后日志断在哪一步、断点就在哪。
2. **外部进程逃逸 Job Object 的两条正路**：schtasks（可靠但 await 慢）、explorer.exe 转发（spawn 即返回，转发给常驻 shell 执行，不在 Cursor Job 内）。实弹验证方法：explorer → VBS → `start notepad.exe`，看 tasklist。
3. **写跨进程/跨窗口去重状态用 globalState 时间戳**（60 秒窗口），因为主窗与 Agent 窗是两个扩展宿主实例，内存标志不互通。
4. **VS Code 弹窗规范**：`{ modal: true }` 会自动补 Cancel，自写「取消」必然双按钮；确认弹窗只放一个肯定按钮。
5. **用户对原生弹窗的处置要写进文档**：Quit Cursor? 勾 Don't ask again、Change language 提示点一次即永久消失——这些不是本扩展能抑制的，诚实告知比假装修复好。
6. **Git 工作流（用户偏好）**：提交文案中文、`type(scope): 摘要` 风格对齐仓库历史；多次修复后按用户要求 `git reset --soft main` 合并成**唯一一条提交**（工作区未推送过，无 force push 风险），后续改动用 `--amend --no-edit` 折叠进去。
7. **词典结构先量化再设计**：1508 条中 exact 1422/partial 73/regex 13——这个分布直接决定了 O(1) Map + 小数组回退的方案成立；不做量化就设计引擎是拍脑袋。

### 八、遗留问题与待验证假设

1. **卸载自动还原闭环尚未经用户真机验收**（v3 的 explorer 转发方案）。若仍失败，取证顺序：`%TEMP%\cursor-zh-quitwatch-*` 是否存在 → 有则看门狗跑了查日志内容，无则转发未发生。专家问题书（见上）已列 Q1–Q5 与四个竞争假设（宿主存活窗口 / explorer 转发丢弃 / deactivate 未被调用 / 其他）。
2. **lazy-revert 备选方案未决策**：放弃「卸载当场重启」，改为下次启动时发现「扩展已不在但补丁还在」即还原（patch-core API 现成，成本极低，可靠性 100%）。代价：卸载后第一次重启仍见汉化。若 v3 真机再失败，这是推荐退路。
3. 多窗口卸载场景 deactivate 会跑多份 → 看门狗可能双调度（两个 BAT 同时等 Cursor 退出后各 start 一次）。revert 幂等无碍，双启动竞态未处理（可用 %TEMP% 锁文件去重）。
4. macOS 卸载路径走 scheduleMacRestart（detached 脚本），未实测。
5. 市场发布 0.0.9 已冻结；后续任何代码改动需递增 0.0.10。
6. 真实双窗口引导去重、卸载后 quit 命令在垂死宿主中的到达率，均只有契约测试无实机数据。

### 一、结论与问题背景

本次解决了 `cursor-loc` 汉化扩展卸载后，安装目录补丁仍然残留、界面未恢复英文且没有自动重启的问题。

关键修复不是继续压缩 `deactivate` 内的执行时间，而是在扩展运行期间监听扩展目录变化，由磁盘卸载事实触发清理；`deactivate` 保留为补充入口，两个入口共享同一套还原与重启逻辑。

真机验证结果：真实 Cursor CLI 卸载成功后，监听器触发还原，安装入口恢复为 `./out/main.js`，注入文件被删除。退出确认框出现但没有被手动点击，现有看门狗约 20 秒后强制结束 Cursor，再自动拉起；新窗口的 General、Models、Privacy、Agents Window 等已恢复英文。用户随后确认问题解决。

边界必须保留：这次验证证明了“无需手动确认、最终自动重启”，不是“即时、无弹窗、优雅退出”。直接点击扩展面板卸载按钮的完整自动化复测没有完成；最终执行的是实际 Cursor CLI 卸载，配合真实进程、磁盘状态和 Computer Use 界面读取。

### 四、最终技术方案与职责划分

### 运行期间发现卸载

`activate()` 在非 Development 模式下，对 `~/.cursor/extensions` 注册 `fs.watch`，使用 `{ persistent: false }`。目录事件触发磁盘卸载检查，不把“有文件变化”直接当成“扩展已卸载”。监听器关闭函数加入扩展 subscriptions，并记录 `watch.ready` 或 `watch.error`。

选择标准库目录监听，而不是常驻外部服务、定时轮询或新的计划任务。它能覆盖已观察到的“扩展被卸载，但宿主仍存活”场景；并不保证操作系统或所有运行环境中的事件永不丢失。

### 共享清理入口

`cleanupAfterUninstall()` 被监听回调和 `deactivate()` 共同调用：

1. 检查 `uninstallRunning`，避免同一扩展实例的重复通知并发执行。
2. 检查冷重启抑制标志、globalState、扩展上下文和开发模式。
3. 调用 `isExtensionUninstalled()` 读取磁盘清单及 `.obsolete`。
4. 检查补丁状态。
5. 尝试调度重启；调度抛错时记录错误，但仍继续还原。
6. 调用 `runRevert()`；还原成功且调度成功后请求 quit。
7. 同步 trace 记录阶段结果，捕获 quit Promise 拒绝。

`uninstallRunning` 是实例内去重，不是跨窗口、跨进程的分布式锁。

### 外部重启看门狗

Windows 路径继续复用 Explorer → VBS → BAT：

- 临时文件名含扩展宿主 PID 和时间戳。
- 监听 ChildProcess 的 `spawn`、`error`、`exit`，不再将函数返回等同于进程创建成功。
- `spawn` 事件仅证明 Explorer 进程创建；真正执行看门狗要由 BAT 日志确认。
- BAT 等待 Cursor 退出；超时后沿用 `taskkill /F /IM Cursor.exe /T` 强制退出，再启动 Cursor。
- 启动参数使用 `windowsHide: true`，子进程成功创建后 `unref()`。

这里保留了已有强制退出语义，可能涉及所有同名 Cursor 进程。真机操作前明确获得用户允许，并要求保存工作。此机制不能描述成无数据丢失风险的优雅重启。

### 退出阶段日志

`uninstallTrace.ts` 使用 `fs.appendFileSync` 写入：

`%TEMP%\cursor-zh-deactivate-trace.log`

记录时间、PID、事件及相关结果；日志失败被隔离，不阻断还原。关键事件包括 `activate`、`watch.ready`、`status.begin/end`、`schedule.begin/end`、`watchdog.scripts/spawn/error/exit`、`revert.begin/end`、`quit.request/resolved/rejected`。

构建标识用于确认实际运行的是哪个诊断版本，不能只依赖包名中的 `0.0.9`。

### 可迁移的经验

- 把“发现业务事件”和“执行清理”分开设计。进程关闭回调不等于可靠业务卸载事件。
- 一条证据链应绑定构建标识、PID、时间与状态迁移，避免跨版本日志拼接归因。
- 操作发出、进程创建、脚本开始、目标退出、重新启动、业务状态恢复是不同成功层级，应分别取证。
- 退出阶段的关键工作不应依赖正在拆除的 UI/RPC 日志设施；诊断失败不能阻断清理。
- 先复用既有还原逻辑，用最小入口修复解决根因；没有必要先引入外部服务、常驻哨兵或系统配置。
- 测试全绿不证明真实宿主行为。用户复测失败后，应修正覆盖模型，而不是继续添加只验证实现形状的断言。
- 文件名、包内版本、分支名分别核验；保留旧包应验证哈希，而不只是验证路径仍存在。
- 工具故障时切换到适用 CLI，必须如实标明验收路径，不将 CLI 成功描述成 UI 按钮自动化成功。

### 本次未采用的方案

`lazy-revert` 曾作为方向讨论，但没有实现。卸载后扩展不会再次 activate；若要下次启动清理，入口必须放在仍然存活的安装目录启动引导中，且不能依赖已删除的扩展文件。“50ms、100%可靠、必须第二次启动才英文”均未被验证。

没有新增常驻后台进程、轮询服务或独立系统任务；没有为本次任务顺带改造汉化引擎和其他业务项目。
