## 核心沉淀

- 项目已从可行性验证阶段转入正式上线准备，主线是 Java 业务主账本、Node 8089 AI 执行、前端人工确认。

### 1. 一句话结论

AI 识别客户已在 2026 年 7～8 月完成两个月验证，当前应按“下一版本正式上线”推进：Java 负责业务主账本和产品接口，Node 8089 负责音频与 AI 执行能力，前端负责设备中心入口、结果交互和人工确认；AI 只给候选，人工确认后才形成正式业务结果。

### 2. 问题背景与本次目标

项目最初积累了多轮需求研讨、旧产品原型、页面草稿、工作流版本、Node 自测资料和接口草案。资料存在重复、版本偏移、旧路径失效和“验证阶段结论”被误当成当前实施目标的问题。对话先以当前 8089 源码为事实基准，提炼五次需求研讨的稳定结论，再清理已被吸收的旧文档、分类 docs、补齐 Node/Java/前端接口交接资料，并明确后续按上线闭环实施。

本次对话解决的具体问题包括：

- 从五份音频转文本研讨记录中抽取 AI 识别客户的稳定需求。
- 对比旧资料、当前 Node 代码和新需求，识别重复、偏移和仍有价值的内容。
- 清理已确认无价值的历史 Markdown/TXT，保留仍有运行或引用价值的输入源资料。
- 把 docs 按需求、页面、接口、输入源、可视化、治理和工作流分类。
- 形成 Node 自身、Node 对 Java、Java 对前端的接口和 MySQL 建议。
- 把项目阶段从“继续验证”校正为“下个版本上线”。
- 优化 `.gitignore`，使其具备可维护的分类注释、敏感配置保护和生成物隔离。

### 3.3 关键决策

- 上线版本坚持“Java 主账本、Node AI 执行、前端产品交互”的职责分离。
- 前端只调 Java；Node 的内部 token、COS 信息和执行细节不下发给前端。
- P0 先以 run、review、callback event 三类数据承载业务状态，快照和识别明细先保存 JSON。
- 生产链路不依赖 mock；mock/self-test 留作测试能力和本地回归基线。
- 旧资料只保留可追溯价值，不再作为当前实施指令；需要移动或删除时先更新引用并验证可恢复性。

### 6. 当前/目标架构约定

最后更新的 AGENTS 指定了目标架构：业务模块优先、轻量 Clean Architecture、Fastify Plugin 边界。新能力归位原则如下：

- 生产业务流程进入 `core`。
- 可替换能力按“一能力一文件夹”放在 `capabilities/<capability>/`。
- 跨能力公共件放 `shared`。
- 依赖装配仅在 `module.ts`。
- HTTP Route 只做校验、调用 Use Case、状态映射和 DTO 输出。
- Application 只依赖 Domain 和 Ports，Infrastructure 实现 Ports。
- mock 只在 `capabilities/mock-lab/` 和根级 `mock/` 数据资产中存在，生产链路不得依赖 mock。

AGENTS 中描述的目标目录为 `src/modules/recognition/`，包含 `core`、`shared`、`capabilities`、`devtools`、`tests`、`module.ts` 和 `index.ts`。该结构是最新项目规范；本次对话没有在最后一步重新扫描源码确认其全部已经落地，后续开发前必须以实际目录为准。

同一规则还规定：TypeScript 文件 500 行硬上限、400 行预警；文件使用语义 role 后缀，例如 `*.route.ts`、`*.use-case.ts`、`*.repository.ts`、`*.provider.ts`；新增对外能力从模块 `index.ts` 暴露。

### 6.1 目录与命名约定

- 目录表达“一类东西”，文件表达“一个职责”。普通文件用 `<domain>.<role>.ts`，业务行为用 `<verb>-<domain>.<role>.ts`。
- HTTP、Application、Domain、Infrastructure 依赖方向为 `HTTP -> Application Use Case -> Domain`，Application 经 Ports 依赖 Infrastructure。
- `module.ts` 是依赖装配组合根；能力之间不直接 import 内部实现，只经各能力的 `index.ts` 出口和组合根协作。
- 最新 docs 规范要求当前主线与专项文档置于 `docs/`，历史资料进入 `docs/历史文档/`，文件名不带日期前缀，标题下维护变更日志表；是否已迁移必须以实际工作树为准。

### 8.1 有效方案

- **源码优先，文档作为证据。** 旧文档、音频转文本和工作流只能提供需求线索；接口、目录、测试和当前代码决定实施事实。
- **先收敛再删除。** 删除资料前先写新主线文档，再核对引用、保留哈希备份并测试回滚。
- **前端只认 Java 主账本。** 这样 Node 的内部 token、COS 信息和异步执行细节不会泄漏到前端，同时保证状态一致性。
- **P0 先存 JSON 快照。** 对 run、客户池、groups/candidates 先持久化 JSON，避免首版为了规范化拆出大量不稳定表。
- **mock 仅作测试能力。** mock/self-test 保留，可保障本地契约测试和演示；生产路径必须清晰替换为真实 provider。
- **文档移动必须同步引用。** 移动 docs 时不仅移动文件，还要扫描并更新 `README.md`、`AGENTS.md` 和文档内路径。

### 8.2 失败尝试与踩坑

- 首次清理证据目录时使用递归删除，工具因可能清除旧备份而拒绝执行。修正方式是使用新的唯一证据目录，绝不清空既有目录。
- Windows PowerShell 用 `powershell.exe -File ROLLBACK.sh` 会因 `.sh` 扩展名被拒绝。后续通过读取脚本文本、创建 PowerShell ScriptBlock 并在 fixture 中执行来测试回滚。
- PowerShell 使用 `-replace '\'` 会被当作不合法正则。路径分隔符转换改用字符串 `.Replace('\', '/')`。
- PowerShell 双引号字符串中的 `` `v1` `` 会把 `` `v `` 解释为垂直制表符，导致 diff 证据乱码。写带反引号的 Markdown/Diff 时使用单引号字符串或显式转义。
- 原生命令封装函数若把参数命名为 `$args`，可能丢失传给 `git`、`npm` 的实参。改为 `argumentList` 并用 splatting 传递。
- `git check-ignore -v` 会显示 negation 匹配，不能直接当作“文件已忽略”；判断应使用 `git check-ignore -q --no-index` 的退出码。
- `git diff --check` 在 Windows 中可能显示 LF/CRLF 转换警告，但退出码为 0 时不代表格式错误；要同时记录警告和退出码。
