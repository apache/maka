### 1. 问题背景与目标

- 模块 `receptionPrep` 已有骨架（路由/跳转/结构），但：无 UI 设计文档、无共享样式（16 个 scss 各写各的、同值漂移）、依据抽屉（EvidenceDrawer）与 Figma 差距大、mappers.ts 单文件混杂常量/工具/映射。
- 预约助手（`beauty-smart-advisor` 仓库的 `reservationBoard`）有一套成熟的 UI 文档体系与 `_tokens/_mixins` 共享样式，本模块要对齐这套做法。
- UI 同事把 12 张「查看依据」帧全部命名为「依据」，无法区分每张出自哪个页面哪块内容；需要结合接口定义逐一区分并百分百还原。

### 3. 关键决策与理由

| 决策 | 理由 |
| --- | --- |
| 保留 `.scss` 不改纯 CSS | 构建链就是 sass（Taro `sass.data` 向每个 scss 注入 NutUI 变量 import）；改 `.module.css` 要动 30+ import 零收益；纯 CSS 共享值只剩 CSS 变量（老 WebView 红线）或字面量复制 |
| `@import` 而非 `@use` | dart-sass 要求 `@use` 位于文件所有其他规则之前，而 Taro 的 `sass.data` 会注入 `@import` 到最前，`@use` 直接编译报错；仓库先例 `commonFlashNoteItem` 用 `@import '@/...'` |
| 别名导入 `@/subPackage/receptionPrep/styles/common.scss` | 组件重构一层深就断相对路径（实际发生过）；别名不随层级变化；webpackImporter 支持且有仓库先例 |
| common.scss 单文件、只含 $变量+@mixin | css-me 口径：只抽高频复用值/语义稳定结构/整体联动布局；单处颜色（机会卡渐变、#f4f3ff 等）不进 token 防杂物箱 |
| 依据抽屉用数据驱动渲染而非 5 个组件 | EvidenceView 结构（header/context.values/block.tag/blocks）足够表达 5 种入口差异，条目渲染按数据形态分流（waveform→录音对、header→白卡、无 source→引文卡、其余→来源卡） |
| 属性顺序强制但空行不强制 | stylelint-order 的 properties-order fixer 只排属性不插空行，`emptyLineBefore:'always'` 永远报错修不掉；删掉该键后只强制顺序（可 --fix），报错归零 |
| Figma REST 深挖而非截图目测 | `GET /v1/files/:key/nodes?ids=...` 返回完整子树元数据，1px=1rpx 精确值；tree3.json 是截断的空壳不可用 |

### 7. 失败尝试及原因

| 尝试 | 结果 | 原因 |
| --- | --- | --- |
| `@use` 引入 common.scss | 编译报错 | Taro `sass.data` 注入的 `@import` 必须位于最前，`@use` 不能出现在其后 |
| properties-order `emptyLineBefore:'always'` | 两轮 --fix 后仍报"Expected an empty line" | stylelint-order fixer 不支持自动插空行 |
| `emptyLineBefore:'ignore'` | 配置校验直接拒绝 | 合法值仅 always/never/threshold；最终删除该键（缺省不强制） |
| tree3.json 找依据帧内容 | 只有空壳 | 抓取时深度截断；改走 REST nodes API 按帧全量拉取 |
| 相对路径 `../../styles/common.scss` | 组件重构一层深即断 | 已全量改别名导入 |
| 编辑图标排查 | 无需修复 | 代码链路完好，COS 资源 200；用户所见为未重编译旧态 |

### 8. 踩坑经验

1. **灰字不是灰色**：Figma 里"灰字"常是 fill 级 opacity（本模块 85%/45%），提取器要读 `fills[].opacity` 而非只看 color.a；节点级 `opacity` 与 fill 级是两回事。
2. **设计稿隐藏层**：`visible:false` 的组件（如 4 帧标题旁的可信度 chip）是设计遗留，还原前必须甄别，否则多渲染不存在的元素。
3. **同帧内部不一致**：卡片内间距 16 vs 10、描述透明度 85% vs 65%、引文圆角 20 vs 24、重复帧——实现取主流值并把差异记入 03 文档 §5，不逐帧硬凑。
4. **Taro Button 陷阱**：H5 默认 `width:100%`（行内按钮会被挤竖排）、`::after` 自带边框、`disabled="false"` 也会命中置灰样式——重置三件套 + 置灰用「类名 + onClick 守卫」。
5. **VS Code 红波浪线两种来源**：`rgba()` 逗号旧写法（standard 24 强制 `rgb(r g b / α%)`）与注释前空行；`□` 小方块是色块装饰器不是错误字符。
6. **截图/快照超时不代表页面挂了**：先 `evaluate_script` 探 readyState，必要时关页重开+缩小视口（414px）再截；计算样式断言往往比截图更精确。
7. **用户提供的 Figma token 只在单条命令变量里流转**，不落盘、不 echo、不入文档。

### 一、问题背景与目标

接诊准备模块在页面骨架提交（f3ea15bf）后暴露三类问题：

1. **UI 设计稿（项目库 Figma）模糊误导**：面诊关注的「依据」弹窗在 UI 稿中无对应帧，实现为自拟版式；产品经理稿（面诊管家—宏脉SDK）中存在真实设计但从未核对。
2. **接口契约漂移**：Apifox 合并版契约把「接诊准备」目录收拢为 8 条接口（4 条新 BFF），旧 7 条 `/web/face-answer/consultation-preparation/*` 与经营计划 latest/project-evidence 全部下线；前端 service/types/mock 未跟进。
3. **样式治理与规范沉淀**：公共样式需拆分为 token/mixin/入口三件套；组件样式存在索引写死的四色标签、`//` 注释在 CSS 解析器下报错等问题；上述实践需要反哺个人 skills。

目标：以最新实践（receptionPrep）为准，完成契约对齐、样式治理、规范沉淀三件事，并把方法论写入个人 skills。

### 三、关键决策

1. **契约矛盾以 schema 为准**：recommendations 接口描述称"依据内嵌 evidence 数组"但 items schema 未定义该字段——前端按 schema 不造数据，矛盾列待确认清单。
2. **HomingResponse → ApiEnvelope**：`services/request` 的 `HomingResponse` 是私有类型未导出（TS2614），改用 receptionPrep 自己的 `ApiEnvelope<T>`（结构同构）。
3. **sourceChannel 契约为 JSON 数组字符串**（多渠道）：fixture 从对象形式改为数组形式。
4. **标签四色按标签组映射**：demandTags 蓝 / projectTags 紫 / activityTags 品红 / valueTags 金，收口 `TAG_GROUP_TONES` + `TAG_GROUP_ORDER`（展示顺序同 PM 标注 1：阶段→项目→活跃→价值，组内按 sortValue）。其中「再消费」（接待阶段）在四组契约中无显式归属，暂按蓝槽对齐 demandTags——联调确认后只改两张表。
5. **样式注释统一 `/* */`**：`customSyntax: 'postcss-scss'` 是用户本地修改不提交，源码必须用 CSS 合法块注释；验收标准 = postcss 纯 CSS 解析器逐文件通过。
6. **入口零输出断言改压缩编译判空**：`//` 是静默注释不进产物，`/* */` 会留在 expanded 产物——styles.test 改为 compressed 编译后为空串（防全局选择器泄漏的守卫意图不变）。
7. **存量超标不专门重构**：audioEdit `service.ts` 587 行超 400 行阈值，在下次实质改动时顺手拆，不立项。
8. **grilling 七条决策全部按推荐落地**：组件默认纯展示（逻辑上移模块 hooks）；页面编排统一 `hooks/use<Module>.ts`（`index.hook.ts` 属历史命名）；映射收口根 `mappers.ts`（超 400 行按域拆目录）；样式三件套为准（两分册为历史写法不强制迁移）；模块 docs 两册 + README 四段骨架（设计源优先级声明置顶）；验证资产分入库层（page.test.cjs）/归档层（重型脚本）；mock 体系（USE_MOCK 唯一开关 + fixtures 契约同构 → 接口就绪 UI 零改动）。

### 四、核心工作流与方法论

### 4.1 Figma 契约取数（无 MCP 环境）

- 用 Figma REST API：`GET /v1/files/:key/nodes?ids=...` 抽节点树，脚本解引用 `$ref`、打印紧凑摘要；渲染 PNG 走 `/v1/images`（本项目图片 CDN 超时，文本+坐标已足够核对）。
- 归档约定：Figma 导出件与抽取脚本统一放 `E:\guahub\docs\temp\开发文档\03-AI美管家\06-开发迭代\V1.7.2-面诊成交助手\.tmp-figma`（仓库内不放）。
- 教训：多行字符串在 bash 双引号里转义易坏，复杂脚本用 Write 工具写成 .cjs 文件再 `node` 执行；跨目录 require 用 `NODE_PATH=<仓库>/node_modules`。

### 4.2 Apifox 导出契约的正确选项

OpenAPI Spec + **OpenAPI 3.0** + JSON + **目录作为 Tags 导出=是**（否则全项目 paths 混在一起无法按目录过滤）+ 包含 x-apifox 扩展字段（可选）。导出含「迭代分支+主分支合并后」内容，即最全状态。

### 4.3 契约核对流程（已沉淀进 helper-me/02-api）

抽取目标接口 schema dump → 逐接口逐字段比对四个落点（service.ts 路径参数 / types/api.ts 类型 / fixtures.ts 同构性 / mappers.ts 消费点）→ 三类处置（直接改 / 下线标 @deprecated 注明替代 / 契约缺口列待确认）→ 核对记录落 `docs/interface/<主题>-核对-<日期>.md`。教训：契约描述与 schema 可能互相矛盾，以 schema 为准；枚举改名必须全链路核对消费点。

### 七、有效方案及原因 / 失败尝试

**有效**：
- 契约核对用「脚本抽取 dump + 逐字段比对」替代肉眼读导出件，8 条接口一次核清；
- `customSyntax` 写进 stylelint 配置根除编辑器红色报错（vs 逐文件改注释）；
- 样式抽离先脚本统计频次（颜色字面量 / 声明组合 ≥3 次）再决定抽什么，避免过度抽象；
- 纯暂存态验证（`git stash --keep-index`）两次抓到「提交快照不自洽」。

**失败/踩坑**：
- 图片 CDN（Figma images 端点）连接超时，PNG 拉不下来——靠 API 文本+坐标完成核对；
- 首次批量替换 `//`→`/* */` 后漏了 `@include` 后空行（declaration-empty-line-before 8 处报错）与 at-rule 置顶（order/order warning），逐行脚本补齐；
- `git stash --keep-index` 验证暂存态时发现两个非本轮问题：page.test 缺 `useDictionaryBatchMap` 桩（后台合并 b32bb875 引入）、detail 传 `showArchive` 但 CustomerSummary 配套未同提交（用户上次提交切分不自洽）——前者补桩，后者留给用户；
- 仓库 `.tmp-figma/` 被用户清空迁移到 guahub 归档后，仓内脚本路径全部失效——改为从归档目录直接执行。

### 九、遗留问题与待验证假设

**联调待确认**：①「再消费」接待阶段在四类标签组的归属（暂对齐 demandTags 蓝槽）；② recommendations 描述与 schema 的 evidence 矛盾；③ cards 各 cardType payload 契约未展开；④ customerPlan 松散结构；⑤ 标签 tagStatus 是否过滤；⑥ DealTarget 四项数据源切换 reception-plan.dealGoal 的时机。

**遗留工作**：页面数据流从「聚合总入口」迁移到「cards 多态卡片」（联调前必做）；旧 7 条下线接口及其类型/fixture 在联调切换后删除；`styles.test.cjs` 等三个守卫测试已移归档目录，是否回迁由用户定；工作区仍有用户样式重构未提交部分（含 detail/CustomerSummary 的 showArchive 配套切分）。
