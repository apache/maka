# 结论

你看到的不是“缓存”，是**写进 Cursor 安装目录的文件补丁**——它和扩展的生命周期本来就不绑定。另外你这台机器上的补丁，是我上一轮用仓库 CLI `npm run apply` 打上去的，**扩展从头到尾没参与过**（你截图里它显示的是“安装”按钮，即从未装过）。

# 机制

扩展只是“操刀的手”，刀口在安装目录。apply 做了三件事：写 `workbench.desktop.main_translated.js` 翻译副本、改启动器让它加载副本、同步 product.json 校验和。这些文件在 `D:\DevTools\AI\SpaceX\Cursor\resources\app`，而扩展本体在 `~/.cursor/extensions`——卸载扩展只删后者。

扩展对卸载的自愈（`src/extension.ts:422`）是这样的：deactivate 时延迟检查扩展 ID 是否还在列表里——

- ID 消失（运行中卸载）→ 自动 revert + 冷重启
- 仍在但未激活（退出过程/禁用）→ 不动，避免误清补丁
- 正常退出：进程先死，定时器不触发 → 补丁保留（这是刻意设计，否则每次关 Cursor 都还原）

# 你的判断对的部分

确实有一个**架构上盖不住的洞**：Cursor 关闭状态下卸载扩展。此时 deactivate 根本不会执行，下次启动补丁照样加载，而磁盘上已没有任何属于本扩展的代码负责清理——VS Code 扩展 API 没有“卸载后钩子”，注入式汉化方案都躲不开。README 只披露了“卸载时自动移除”，没披露这个前置条件（需在运行中卸载）。最小修正是在 README 卸载章节加一句：关闭状态下卸载不会自动还原，重装扩展后执行「恢复英文界面」即可。埋自检进补丁的方案我评估过，注入环境查不到扩展 ID，属于过度工程，不建议做。

# 你机器上现在的补丁

想恢复英文，一条命令（仓库根目录）：`npm run revert`。或者保留现状继续用汉化，它对扩展安装与否完全无感。
