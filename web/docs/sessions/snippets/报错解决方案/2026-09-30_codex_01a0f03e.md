## 结论

1. **体系诊断**
   - **P0｜测试门禁冲突**：[现有开发规则](C:/Users/802165/.ai/categories/99-归档与淘汰/01-个人开发/gua-helper/references/03-dev/SKILL.md)第 177、211、562 行要求测试随功能入库；[项目约定](E:/Projects/frontend/homing-miniapp-workbench/AGENTS.md)要求结构测试只在本机运行、不暂存。实查 `receptionPrep/tests` 有 55 个本地文件、Git 跟踪 0 个。对以修复为主的工作流，应先统一现有规则：测试照写照跑，提交前检查暂存区与已跟踪测试文件；测试阶段从 `gua-helper` 直达该门禁。
   - **P1｜路由可发现性**：43/240＝18% 是个人 skill 的**使用占比**，不是触发准确率。[`gua-taro`](C:/Users/802165/.ai/categories/99-归档与淘汰/01-个人开发/gua-taro/SKILL.md) 250 行、零触发，description 却堆内部标识，与“小程序取不到时长”等话术错位；这是漏触发嫌疑，须用原话验证。`gua-helper` 还应把“拿 PRD 做模块蓝图”直接指向现有 01-prd 节，并删去与 `gua-review` 重叠的审 PR 入口。
   - **P1｜事实来源**：`gua-taro` 正文仍含具体项目入口、音频及 SSE 实现事实，`gua-css` 正文也有模块名，与“项目事实外置”约定不符。将这些事实移回现有项目资料或 `project-facts.md`，主文只留跨项目判定。
   - **P2｜验证与执行**：9 份 eval 共 29 例未运行，且已有过时预期；Edit 失败率 8% 与 55 轮长会话属执行问题，宜按小补丁记录 diff、测试和续跑检查点。98.4% 缓存重读本身不足以证明成本瓶颈。

2. **description 改写示范**
```yaml
description: Taro 多端实现与排障。Use when “小程序取不到时长”查平台行为；“App 里打开没反应”查内嵌交互；“真机上不一样”查端差异。改完怎么验转 gua-verify-build。
```
```yaml
description: 多端改动的验收门禁。Use when “改完怎么验”选验证级别；“构建哪个环境”选目标；“是不是旧包”核新产物；“能不能算完成”核真实数据与未验项。平台行为修复转 gua-taro。
```
每分支只留一句任务话术；内部标识留正文，明确“实现”与“验收”边界。

3. **反馈闭环**：先对自有库执行 `PRAGMA table_info(tool_usage)` 核列名。每周抽 30 条相关用户原话，人工标注应触发项，排除显式 `$gua-*`，对照实际调用算各 skill 的 TP/FN/FP、召回率和精确率；每轮只改最高漏触发或误触发的一条 description。校准旧 eval 预期后，新会话跑“真实正例＋相邻 skill 负例＋无关负例＋一条行为断言”，留调用 trace，而非只看回答。[OpenAI 官方 eval 指南](https://developers.openai.com/blog/eval-skills)也区分调用过程与输出检查。

4. **精简判断**：暂不合并或退役。逐项触发时机是：`bug` 故障、`css` 样式、`dashboard` 多域看板、`figma-to-page-dev` 设计落地、`format-changed-files` 提交前格式、`helper` 工程决策、`learn` 教学、`performance` 绩效、`project-workflow-skill-builder` 生成项目技能、`review` 审查、`taro` 多端实现、`ui` 业务状态、`verify-build` 改后验收、`writer` 技术写作。相邻可协作，但没有同一触发时机的一对；新 skill 零调用也尚无退役证据。

5. **明确排除**：version/changelog 包装、共享 contexts 层、新增 skill、批量挂载外部技能。
