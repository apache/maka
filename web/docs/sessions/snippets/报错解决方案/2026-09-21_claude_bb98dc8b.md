但**直接跑 `sk-sync.js` 是修不好的**——你打开的这个脚本不是本次问题的所在层。

## 根因：源层悬空，不是镜像层

`categories` 做过一次子分类重构（`04/02-测试调试与代码审查` 拆成 `02-测试与调试` + `03-代码审查与重构`，`07/01-内容与知识交付` → `05-文档与演示交付`），6 个 skill 的真身搬了家，但 `.agents/skills` 里指向旧路径的 junction 没跟着更新，全部悬空。

`sk-sync.js` 只负责把 `.agents/skills` 镜像到 15 端，**它不管源层自身的链接对不对**。它遍历 `srcEntries` 时把悬空条目也当有效，所以会出现这个迷惑行为：

```
阶段1: [将删] .claude/tdd  (指向 .agents/skills/tdd)
阶段2: [将重建] .claude/tdd
```

删掉 90 条断链，再照原样重建 90 条**同样的断链**——白跑一轮，doctor 依旧报异常。识别信号就是：**同一个名字在阶段1"将删"、阶段2"将建"成对出现且数量相等**。

## 实际执行的修复

按 `rebuild → sync → doctor` 顺序：

| 步骤 | 结果 |
|---|---|
| `sk-rebuild.js --dry-run` | 12 个动作（6 删悬空 + 6 指向新真身），警告 0 |
| `sk-rebuild.js` | 执行完毕，**全局联接 26/26** |
| `sk-sync.js` | 阶段1/2 均归零（各端链接路径没变，rebuild 后自动恢复），零动作幂等确认 |
| `sk-doctor.js` | `problems: 49，警告: 0` |

关键点：`.agents/skills` 修好后，**15 端不需要任何改动就自动恢复了**——各端的 junction 指向的是 `.agents/skills/<name>` 这个稳定路径，搬家的是更下一层。所以 sync 阶段是空操作，这正是健康状态的表现。

`✶ Insight ─────────────────────────────────────`
**修复要在正确的抽象层做。** 这套体系是三层：`categories`（真身）→ `.agents/skills`（视图层）→ 15 端（镜像层）。`sk-sync` 是镜像层的工具，源层坏了它无能为力，而且会"忠实地"把坏状态复制一遍——它的幂等性反而掩盖了故障。看到"删了又建同样的东西"这种动作配对，就是走错层的信号。

**junction 对 git 透明，是这套体系的隐形风险。** 记忆里记过：git 在 Windows 上会跟随 junction 递归，一次 `pull` 删除跟踪文件时曾穿透链接把 `categories` 真身删空。所以 `.agents/skills` 和 15 端刻意不入 git，各机必须自建——这也是为什么换机同步后必须补跑 rebuild。

**悬空的成因有两类，识别方式相同。** 一类是真身改名（记忆里记过），一类是父目录搬家（本次）。两者的 junction 都还指着旧路径、真身都还在，处置方式都是 `sk-rebuild`，无需手工 `mklink`。
