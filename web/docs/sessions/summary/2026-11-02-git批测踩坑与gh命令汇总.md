# magpie 批测踩坑与 git/gh 批处理命令
**一句话总结**：批量验证十几支分支能否干净落到最新 main 的命令组合，以及这次连踩的 format-patch / bash 3.x / git apply 输出三个坑。

## 背景
给上游发"这些分支都能干净落进 main（git am 即进）"的清单帖之前，必须实测每支补丁对最新 main 的落地情况。写批测脚本时连续踩了三个坑，导致 13 支分支导出同一份垃圾补丁、误报全员冲突。

## 核心命令
```bash
# 同步上游与自己的 fork
git fetch upstream main && git fetch origin

# 批测前先量化差距：分支落后 tip 几个提交 / 共同祖先在哪
git rev-list --count origin/分支..upstream/main      # 落后 tip 的提交数
git merge-base upstream/main origin/分支             # 共同祖先（即当初的 rebase 基点）

# 判断分支是否已经在最新 tip 上（真·已 rebase）
git merge-base --is-ancestor upstream/main origin/分支 && echo "已在 tip"

# 正确的补丁导出：显式双端点，绝不依赖当前 HEAD
git format-patch upstream/main..origin/分支 --stdout > fix.patch
# ⚠️ 单参数写法 `git format-patch origin/分支 --stdout` 的区间终点是「当前 HEAD」
#    而不是远端分支！HEAD 停在旧分支时会导出一堆无关旧提交

# 真 3way 落地批测（开临时工作树，不污染任何现有分支）
git worktree add /tmp/tip-worktree upstream/main
git -C /tmp/tip-worktree apply --3way --check fix.patch
git worktree remove /tmp/tip-worktree --force

# GitHub：取某 issue 的最后一条评论（实测 REST 忽略 sort/direction，必须全量取尾，待验证）
gh api repos/OWNER/REPO/issues/N/comments?per_page=100 --jq 'last | .user.login + " " + .created_at'

# GitHub：批量拉开口 issue 做分类（按作者/评论数过滤）
gh issue list -R OWNER/REPO --state open --limit 400 \
  --json number,author,comments,title \
  --jq '.[] | select(.author.login != "机器人账号") | "\(.number)|\(.comments|length)|\(.title)"'

# 查某张 issue 对应的修复是否已无声进 main（全历史搜，别带 --since）
git log upstream/main --oneline --grep="#单号"
```

## 关键结论
1. `format-patch origin/分支` 的区间终点是**当前 HEAD**，不是远端分支——HEAD 停在旧分支时，所有分支会导出同一份无关旧提交；批测结果 13 支完全相同就是症状。
2. macOS 自带 bash 是 3.x，**不支持 `declare -A` 关联数组**（直接报 invalid option），批测脚本改用 case 语句或逐行调用。
3. `git apply --3way --check` 成功时也会打印 "Applied patch to 'f' cleanly."；判干净的标准是输出里**没有** "with conflicts" 和 "error:" 行；"Falling back to direct application..." 只是提示，看后继行确认无 error 即可。
4. GitHub REST 的 issue comments 接口实测会忽略 `sort` / `direction` 参数（待验证：可能是行为变更），取最新评论一律 `per_page=100` + jq `last`；REST 评论的作者字段是 `user.login`，GraphQL 才是 `author.login`，写 jq 前先确认用的哪个接口。
5. 上游修代码时常**不引用单号**，判断"我的补丁是否被无声收编"要双层查：先 `--grep="#单号"`，再按报错关键词搜；判定"是否在 tip 上"用 `merge-base --is-ancestor`，比肉眼看日志可靠。

## 下次怎么用
发"这些分支都能干净落进 main"类承诺前，按顺序跑：fetch → `--is-ancestor` 判定 →（不在 tip 上时）显式区间导出 patch → 3way `--check` 批测 → 输出无 conflict/error 才算过。日常想确认某 issue 有没有新回复、自己报的问题是否已被上游修掉，直接套上面两条 gh / git 命令即可。

# 追加：magpie 推荐清单轮的分支对账与批测命令（2026-11-02 晚）

**一句话总结**：多分支 patch 是否还能干净落上最新 main，用 `git merge-tree --write-tree` 秒级预检替代 worktree 逐支试，配合紧格式单号 grep 对账收编、判定闸摘 patch 验 RED。

## 背景
接手一批在途 patch 分支（含别人会话交付的），要判断：哪些已被上游收编、哪些还能干净落地、哪些面已被上游修掉。上游当天前进几十笔，worktree 逐支批测太慢且有踩坑史。

## 核心命令

```bash
# 秒级预检分支能否干净落上最新 main（免 worktree；退出码 0=无冲突）
git merge-tree --write-tree upstream/main origin/<branch>

# 批量预检：循环 + 退出码判定（rc=0 打 OK）
for pair in "单号:分支名" ...; do
  git merge-tree --write-tree upstream/main origin-hunt/$b >/dev/null 2>&1 && echo "OK" || echo "CONFLICT"
done

# 收编对账：紧格式单号 grep（"#N)" 要求右括号紧随，避免误中正文里的数字引用）
git log upstream/main --format='%h|%an|%s' --grep="(#N)"

# cherry 对账：哪些分支有未进 main 的提交（注意：维护者重写吸收的分支会假阳性 +1）
git cherry upstream/main origin/<branch>

# 一次 fetch 全部远端分支到本地引用（注意通配符吃前缀：hunt* 落为 hunt-前缀被剥；fix/xxx 带斜杠需单独 refspec，否则双斜杠 funny ref 被 git 拒收）
git fetch origin '+refs/heads/hunt*:refs/origin-hunt/*' '+refs/heads/fix/*:refs/origin-hunt/fix-*'

# 标准批测：worktree + format-patch 必须两点语法（三点 A...B 是对称差，会把 main 侧提交全打进 patch）
git worktree add /tmp/wt <tip> --detach
git format-patch $(git merge-base origin/<b> upstream/main)..origin/<b> --stdout > p.patch
git -C /tmp/wt am p.patch
# 用完清理：git worktree remove --force /tmp/wt

# 判定闸：摘 patch 验症状仍在（恢复上游原文件、保留新测试，跑 RED 预期 FAIL；若 PASS=上游已修）
git -C /tmp/wt checkout <tip> -- <patch触碰的文件>

# GraphQL 批量拉 issue 状态/末评（25 单/次，比逐单 REST 快且不踩分页）
python3 - <<'PY'
parts=[f'r{i}: issue(number:{n}) {{ number state comments(last:1){{nodes{{author{{login}}}}}} }}' for i,n in enumerate(nums)]
q='query { repository(owner:"org", name:"repo") { '+' '.join(parts)+' } }'
subprocess.run(['gh','api','graphql','-f','query='+q],...)
PY

# 多人共用文档的并发安全写法：python 按行号插入，不用 Edit 的字符串锚点（会撞并发修改）
lines=open(p).readlines(); lines[202:202]=['新行\n']; open(p,'w').write(''.join(lines))
```

## 关键结论
1. **`git merge-tree --write-tree` 是分支级冲突预检的最短路径**：免 worktree、秒级、退出码可脚本化；唯一注意是结果不含测试，冲突为 0 只代表能合上，不代表测试绿。
2. **format-patch 三点 vs 两点是本轮最大的坑**：`A...B`（三点）打的是对称差，会把 main 侧上千提交全打进 patch；永远用 `merge-base..branch`（两点）。
3. **收编判定三层**：单号紧格式 grep（假阳性=正文引用别的单号）→ `git cherry` patch-id（假阳性=被重写吸收）→ issue 末评/分支 head 实测。第三层才是权威：维护者可能 fast-forward 你的分支头原样进 main 而不发帖。
4. **「能自动合并」≠「能直接交付」**：`am -3` 干净只说明 rebase 顺利，接收方的普通 am/merge 流程仍会卡，交付承诺要以对方工具链口径为准。
5. **判定闸（摘 patch 验 RED）双向有用**：既拦「上游已修」的死单，也能救回被纸面规则误杀的单——纸面推断要用一次实际测试验证。

## 下次怎么用
- 维护一批长期分支时：每次动手前先 `merge-tree` 全量预检一遍，秒出哪些分支被上游漂移卡住。
- 判断某个 bug 上游是否已修：找到该分支的 RED 测试，在干净 main 上摘 patch 跑——PASS 即上游已修，出列让位。
- 多来源文档（多个会话/人同写一个 md）：放弃字符串锚点编辑，用 python 行号插入。
