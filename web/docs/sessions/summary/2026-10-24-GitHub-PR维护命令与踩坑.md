# GitHub PR 维护命令与踩坑

**一句话总结**：多轮开源 PR 维护中沉淀的验证纪律（退出码/提交核实/评审真态）与正则 O(n²) 的两种通用修法。

## 背景

连续维护 cherry-studio / maka 的多个在途 PR：修评审 bot 的 findings、解冲突、补 DCO、与并行会话共用 worktree。这轮反复踩中三类坑：验证结果假绿、提交被 hook 静默吞掉、评审状态被 flag 误导。

## 核心命令

```bash
pnpm typecheck > /tmp/tc.log 2>&1; echo $?
# 真实退出码要这么拿：`cmd | tail` 后的 $? 是 tail 的，typecheck 失败也会显示 0（假绿）

git log --oneline -1
# 每次 commit 后立刻核实 SHA——pre-commit hook 可能静默吞掉提交而不报错

npx eslint --fix <改动的.ts文件>
# 提交报 "Stashed changes conflicted with changes made by hook" 时：
# 是 hook 的 import 排序/格式化与暂存区冲突，先手动 fix 再 add + commit

git commit --amend -s --no-verify --no-edit
# hook 本身坏了（如 prek: not found）时补 DCO 签名；--no-verify 只跳过 hook，amend 只改 message 不动内容，安全

gh api graphql --input - <<< "$payload"
# GraphQL 请求传 JSON 走 --input；`gh api -f body=<文件路径>` 会把路径字符串当正文发出去（踩过）

git diff <commitA> <commitB> --stat
# 重造提交历史（如补 DCO 后 rebase）后，用它验证两棵树内容等价

git checkout upstream/main -- <自动生成的文件> && <重新生成脚本>
# 生成文件（如按 classification.json 生成的 schema）冲突时：取上游版再重跑生成器，比手工拼两侧可靠

npx vitest run <具体测试文件路径> -t "<用例名>"
# 只跑目标用例；不带路径的 npx vitest run 会全仓跑，几十万 token 级浪费
```

⚠️ `git push --force <url> <分支>`：只对**自己名下的 fork 分支**用（重写历史后必须 force）。先确认远端 SHA 是自己刚推的，无他人在该分支上工作；协作分支一律 `--force-with-lease`（注意：直接推 URL 不更新本地远端引用，lease 会报 stale info）。

## 关键结论

1. **管道退出码假绿**：`长命令 | tail` 后 `$?` 永远是 tail 的 0。所有"跑完看是否成功"的命令，重定向到文件再单独 `echo $?`。
2. **pre-commit hook 会静默吞 commit**：hook 内部 stash/格式化与暂存区冲突时回滚并中止，但终端只剩几行 Passed。纪律：提交后 `git log --oneline -1` 确认 SHA，不一致就重试（先 `eslint --fix`）。
3. **PR 的 reviewDecision flag 不可靠**：评审被 dismiss 后 flag 留残影（明明 bot APPROVED 却显示 REVIEW_REQUIRED）。用 REST `pulls/{n}/reviews` 看每个 reviewer 的**最新一条**状态才是真态。
4. **评审竞态定性法**：bot 的 CHANGES_REQUESTED 落在你 force push 之后几十秒时，对齐时间戳（CR 提交时刻 vs 推送时刻、CR 正文引用的 head 号、finding 清单是否对应旧 head 已知问题）——大概率是它起跑时读的旧快照，等重跑即可，不要急着再修一轮。
5. **正则扫描 O(n²) 的两个通用修法**：①前置守卫——正则所有分支都以某字符结尾（如 `>`）时，`indexOf(该字符) === -1` 直接跳过 exec；②单调缓存——扫描位置只增时，`indexOf` 的 miss（-1）永久缓存、命中缓存到位置越过命中点。修完用三档递增输入计时验证线性（每翻倍 ~1.3-2x 为线性，~4x 是仍二次）。

## 下次怎么用

- 跑任何"成败判定"的构建/类型/测试命令时，套第 1 条模板取真实退出码。
- 提交前改动含 import 增删/排序的，先 `eslint --fix` 再 `git add`，省掉 hook 冲突往返；提交后 `git log -1` 是肌肉记忆级动作。
- 维护多个 PR 时，用 GraphQL 一次拉全部 PR 的 latestReviews + reviewThreads + mergeStateStatus 做批量巡检，比逐个网页看可靠。
- 给扫描器/解析器做性能修复时，先写三档规模基准（10k/20k/40k）拿修复前数字——修完的"线性"要有对照才有说服力。
