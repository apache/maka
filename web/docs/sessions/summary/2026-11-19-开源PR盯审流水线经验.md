### 1. M7 判据锐化：add/add（尤其同名测试文件）优先怀疑上游同题取代

- **目标位置**：`references/pitfalls.md` M7 行（上游同题取代），改判据/打破动作，不新增模式。
- **现有规则**：M7 判据"dirty 先查是否被取代；开 PR 次日查上游等价实现；被取代就体面关单"——是通用 dirty，没有区分冲突形态的先验。workflow §4 收编判定已有"上游修在与我方不同的层也可能构成取代"（本会话 #24239 的 publish 侧 vs 读侧已被此条覆盖，无需重复）。
- **建议文本**（追加到 M7 打破动作）：「冲突形态区分先验：**add/add（双方各自新增同名文件，尤其实测文件）比普通内容冲突更指向上游同题取代**——先 `git log upstream/<base> -- <path>` 看上游提交意图再决定 rebase 还是让位；上游给同一功能补测试≈同题，上游改的是不相干功能恰好同文件（如两套互补映射）则 rebase 保留双方。」
- **来源证据**：orca #24239 全程（journal `E:\ggbdpq\gh-fork\docs\pr\orca\journal.md` orca-6 条目"教训加强版"段）：merge-tree add/add 于 `structured-agent-session-background-task-channel.test.ts` → 上游 `0b79720c2e`（#22614）已在 channel publish 路径实现 explicit-null 同主题修复 → 关单（评论 5929778868，closed 非 merged）。对照组：orca #24164 与上游 #24066 在 `language-detect.ts` 同区域冲突，意图核查为互补映射 → rebase 保留双方（129/129 绿）。正反两例齐。
- **适用边界**：单会话 2 例（1 正 1 反），先例强度中等；"看意图"是必须步骤，不能只凭 add/add 形态就关单。
- **检验场景**：merge-tree 对某分支报 add/add 于测试文件 T。若上游提交是给同一功能补测试 → 走让位流程并体面关单；若是无关功能恰好同文件 → rebase 保留双方。两种走向都能在 `git log upstream/<base> -- <path>` 的提交意图里找到裁决依据。

### 2. 验证矩阵补一句：类型检查必须覆盖新增测试文件并按 tsconfig 分片跑

- **目标位置**：`references/workflow.md` §3「验证矩阵」段（现有列表已含"类型检查"，但未规定覆盖面与分片口径）。
- **现有规则**：矩阵泛列"vet/lint、类型检查"；M4（测试空洞通过）讲 mock 不达绑定，与本条无关。
- **建议文本**（追加）：「vitest/jest 等测试框架不做类型检查，测试文件红绿都过 ≠ 类型安全：类型检查必须覆盖新增测试文件，多 tsconfig 分片项目（如 tc:web/tc:node）按改动所在片跑对应片。tsc 的 present-property 错误会掩盖 missing-property 错误，修完一处必须重跑到零错才算收。」
- **来源证据**：同一会话三现——①orca-4b：fixture 虚构 `content`/`originalContent` 字段，vitest 红绿两轮都没暴露，`tsc:web` 抓到；②orca-4d：`map.get(k) && Object.fromEntries(...)` 联合类型不收敛，vitest 全绿、tsc 抓到；③#24239 首轮：新测试只跑 tc:web，pullfrog 抓到 tc:node 下 5 错，且"修完前两处后 adapter 缺必填字段才冒头"的 present/missing 掩蔽预判完全应验。journal orca-4b/orca-4d/orca-6 均有记录。
- **适用边界**：TS/JS 项目通用；Go/Rust 无此问题（编译器已查类型）。多分片项目是高发区。
- **检验场景**：新增测试文件里给 stub 写了目标接口不存在的字段，vitest RED→GREEN 全过——按本条跑 tc 应在测试文件上报错。

### 3. 行内回复核验修正：REST 回显的 in_reply_to 可为 null

- **目标位置**：`references/workflow.md` §4「review 与新评论」的回复行（现有文本"…回读 `in_reply_to` 确认挂在原线程"——该核验方法本身不可靠）。
- **现有规则**：现有行推荐的正是这个不可靠方法。
- **建议文本**（改写该句）：「…回读确认挂在原线程——**REST 列表回显的 `in_reply_to` 可为 null（即使线程挂对）**，分组核验以 GraphQL `reviewThreads`（`comments(last:1)` 节点）为准，不要据 null 判 POST 失败而重发。」
- **来源证据**：orca-6 条目处置记录（journal 原文："REST 的 in_reply_to 字段回显 null 是怪癖，分组以 reviewThreads 为准"）；当轮 GraphQL 核验 replyTo 全部正确，POST 本身落库成功。
- **适用边界**：GitHub REST `/pulls/<N>/comments` 列表端点；未穷举所有 GET 场景是否都 null。重发有风险：workflow 铁律"POST 结果不明先 GET 核实，绝不直接重发"本就禁止盲目重发，本条补上"GET 的 in_reply_to=null 不是失败证据"。
- **检验场景**：POST replies 成功（返回 html_url）后，REST GET 列表该条 `in_reply_to=null` → 不判失败、不重发，转 GraphQL reviewThreads 验证线程归属。

## 常用命令（本会话实际执行、有可见结果）

**GraphQL 一次批查 N 仓 × M 个 PR 的状态快照**（盯审开场主力，替代逐 PR REST；skill 现行 §1 用 REST 三端点分页，大批量场景 GraphQL 一次拿全）：

```
query { orca: repository(owner: "<owner>", name: "<repo>") {
          p23645: pullRequest(number: 23645) { ...F } ... } }
fragment F on PullRequest { number state headRefOid mergeable mergeStateStatus updatedAt
  comments(last: 3) { nodes { author { login } createdAt } }
  reviews(last: 4) { nodes { author { login } state submittedAt } }
  reviewThreads(last: 15) { nodes { isResolved comments(last: 1) { nodes { author { login } createdAt } } } } }
```

- 前提：`Authorization: Bearer <token>` POST 到 `https://api.github.com/graphql`，query 写 JSON body 文件再 `-d @file`。
- 两个实测坑：**alias 不能带连字符**（`cc-switch:` 直接 400，报 "malformed: \"-switch\""）；字段是 `mergeStateStatus` 不是 REST 的 `mergeableState`（undefinedField）。
- 成功信号：`data.<alias>.p<N>` 结构；失败看顶层 `errors` 数组的 `extensions.code`。
- 副作用：只读，消耗 GraphQL 点数（比 N×M 次 REST 便宜一个量级）。

**merge-tree 批量探冲突**（skill §1 已记单次形式——用 `headRefOid` 不用分支名，本会话用本地分支名也能跑因为分支与 origin 同步；批量循环形态）：

```
for b in <分支...>; do git -C <仓> merge-tree --write-tree upstream/<base> "$b" >/dev/null 2>&1 \
  && echo "CLEAN $b" || { echo "DIRTY $b"; git -C <仓> merge-tree --write-tree upstream/<base> "$b" | grep CONFLICT; }; done
```

- 成功信号：exit 0 = 文本可合并；DIRTY 输出 CONFLICT 行（add/add 会标 `Add/add`）。
- 前提：先 fetch upstream；旧式三参数有 NUL/grep 二进制坑，用 `--write-tree` 形式（pitfalls 已记）。

**orca tsc OOM 兜底**（repo 专属，已落 `pr/orca/README.md`）：`NODE_OPTIONS=--max-old-space-size=12288 pnpm tc:node`；rebase 全程不 cd：`GIT_EDITOR=true git -C <仓> rebase --continue`（fnm 钩子截断 `cd && git rebase --continue` 两次实录）。
