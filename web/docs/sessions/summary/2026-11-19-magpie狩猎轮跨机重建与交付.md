## 可复用经验与案例

**跨机交接时从 GitHub 侧重建狩猎轮口径（五步法）**——台账在 darwin、会话在 Windows 时的替代路径：

1. `git ls-remote --heads <fork>` 提取全部分支名（命名 `<type>/<单号>-<slug>` 或 `hunt-<日期>-<车道>-<单号>`），单号即已交付清单。
2. 对可疑单逐个查 issue 评论数区分状态：评论=1（只 take，未处置）≥2（take+分析帖，已收口）；**jq 正则用 `[[:space:]]` POSIX 类**，`\s` 在 bash 双引号里转义后全漏报（本会话第一次 take 普查全空就是这个错）。
3. 有 fix/verify 分支 = 已交付；无分支但有分析帖 = 收口（上游已修/等报告者材料/非本仓修法）；无分支且评论=1 = 真正待做。
4. commits API 的 `since` 过滤且默认只列 main 分支——查非 main 分支提交须 `?sha=<branch>` 逐分支查头 commit。
5. 搜索 API 的 `commentator:` 限定符对本仓不可靠（恒返回 0），`involves:` 太宽（643 vs 实际 37），只能逐单查评论。

**承接转发他人补丁的完整形态**（#4854 案例）：skygunner 分支 base 落后三周未收、报告者持续复现 → cherry-pick 保留原 author（勿 --reset-author），rebase 到当前 main 后在新头重新质证消融（原 RED 绑定的树已失效），上游三周间的 API 变更（`regexp.MustCompile`→`lazyre.New`）单独适配不入原提交，帖内 Attribution 双方署名（fix authored by X, rebased and re-verified by ggbdpq）。commit `f979c2502`，author `vincent`，干净仓 `git am` 一步即进。

**#6914 双修法对比帖收口**：同单两条 patch 并存（主动式摘 mark vs 反应式重试摘 mark）不互斥时，不撤不压，发对比帖列两修法代价维度（count_tokens 覆盖 / 接受型上游零损耗），取舍显式归维护者——comment 6988441655。

**主线程验收子智能体交付的最小动作**（宪法新规"不转述全绿"的实践形态）：ls-remote 比对分支头 SHA → `git show HEAD --format='%an <%ae>'` 核 author → sha256sum 本地重算比对帖内值 → 消融红日志抽查（确认是目标测试失败而非空文件）→ 干净仓 `git am` 终验 → 按 id GET 回读帖子长度与关键词。车道 B #4854 验收全绿即此流程产出。

## 常用命令

```bash
# 场景：GitHub 侧查某单我方 take 状态（jq 转义用 POSIX 类）
gh api "repos/OWNER/REPO/issues/N/comments?per_page=100" --jq \
  '[.[] | select(.user.login == "ggbdpq") | select(.body | test("^take[[:space:]]*$"))] | length'
# 成功信号：返回 0 或 1；副作用：只读

# 场景：发 issue 评论（内容落文件，防转义与长度问题）⚠️ 必须用 -F，-f 会把 @路径当字面量发出去
gh api repos/OWNER/REPO/issues/N/comments -F body=@/tmp/post.md --jq '.html_url'
# 回读按 id 直查（.[-1] 顺序不可靠）：
gh api repos/OWNER/REPO/issues/comments/<comment_id> --jq '"\(.id) len=\(.body|length)"'

# 场景：Git Bash 导出远端 ref 的带路径文件（MSYS 转换豁免）
MSYS2_ARG_CONV_EXCL='*' MSYS_NO_PATHCONV=1 git -c core.quotepath=false \
  show "origin/main:<带中文的路径>" > /tmp/out.md

# 场景：Go 依赖被墙（build ok 但 test 全 setup failed）
export GOPROXY=https://goproxy.cn,direct GOTOOLCHAIN=auto && go mod download all
# 成功信号：exit 0；副作用：模块缓存写入 GOMODCACHE

# 场景：patch 的 git am 一步即进终验（干净仓 + 物化基线）
git init -q /tmp/amtest && cd /tmp/amtest && git fetch -q https://github.com/OWNER/REPO.git main \
  && git checkout -q FETCH_HEAD && git am <patch文件> && git log --format='%an <%ae>' -1
# 成功信号：Applying + author 为预期值；注：--zero-commit 补丁改现有文件时空仓套不上，需先物化基线树
```

## 待验证与不适用边界

- **五步法口径是重建不是正本**：本会话实测可收敛"剩余单"到与 darwin 台账一致（25 单全景对上），但淘汰余量、档位过滤的原始记录仍只在 darwin 候选池——后续 darwin 会话需对账补录，本会话不虚构台账（journal/账册未动）。
- **Windows GUI 测试方案只验证了 magpie 一仓**：fnm shim + NODE_PATH 的解法依赖本机 fnm 安装方式，其它仓/其它 node 管理器不保证复用。
- **双修法对比帖的归属惯例未定**：#6914 的处置（保留两帖+对比说明）是主线程临时决定，handbook/11 尚无该形态条文，待维护者实际收编后回看是否固化为规则。
- **600s 子智能体不活跃切断**：三次触发（车道 A 首棒 58 分钟、车道 B 两棒），续跑靠 SendMessage 带进度摘要恢复，上下文可续——但"多久算不活跃"与平台版本相关，未测边界。
