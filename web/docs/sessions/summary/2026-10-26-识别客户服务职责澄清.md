# 识别客户服务职责澄清

**一句话总结**：先确定 Java、Node、工作流分别做什么，再同步接口、回调和数据库文档；文档检查通过不代表代码已实现。

## 背景

AI 识别客户的分工经历多次调整，曾套用“Node 提供核心能力、Java 透传”的音频编辑经验，导致文档出现相互矛盾的职责描述。最终明确：Node 只截取音频前 3～5 分钟并回调 Java，后续转写与识别由 Java 和工作流承接。

## 核心命令

在目标 Git 仓库中执行，搜索词替换为本次被废弃的字段或说法：

```bash
git diff --check # 检查改动中的行尾空格等问题；退出码 0 表示通过
git diff --stat # 查看改动文件和增删规模，确认没有明显扩大范围
git status --short # 确认工作区改动，避免混入无关文件
grep -rn "旧职责描述\|旧接口名" docs README.md # 批量查找遗漏的旧口径；命中后区分历史说明与当前契约
```

不要用 `git diff --check | grep ...` 后的 `$?` 判断 Git 是否通过：它默认表示管道最后一条命令的退出码。本次过滤结果为空时，曾把 `grep` 的退出码 1 误当成检查失败；直接运行 Git 命令才确认退出码为 0。

## 关键结论

1. **按当前需求划职责，不能照搬旧项目。** 最终分工是 Node 用本地 ffmpeg 批量截片、发布产物并发送回调；Java 接收截片后调用已有音频转文本能力，再调用工作流；工作流负责获取顾客列表、调用模型并生成候选。人工确认和正式业务落库归 Java。
2. **工作流编写与工作流调用是两件事。** 前期完成工作流定义，不代表 Node 必须在生产环境调用它。当前 JSON 样例仍由外部传入 `customers`，没有主动获取顾客列表的节点；接入该节点属于待完成项，不能写成已经实现。
3. **修改职责必须同步契约。** Node 的目标回调从候选 `groups` 改为截片 `clips`，派发体不再需要客户池；需求说明、双向接口文档、示例报文与数据库字段语义都要一起核对。
4. **截片完成不等于识别完成。** Node 的 `completed` 只说明截片结束，Java 还要执行转写和识别。主任务不能直接随 Node 回调标记完成；截片结果与最终候选也不宜靠覆盖同一个 JSON 字段来保存。此次文档中的状态与存储设计仍需复核，未完成运行验证。
5. **验收结论要限定范围。** 本次实际修改的是 Markdown，`git diff --check` 通过；没有执行提交，没有修改业务代码、工作流 JSON，也没有执行 MySQL 迁移。当前派发 schema 的 `customerPool` 仍为必填，目标报文不能直接当成已上线接口。

## 下次怎么用

遇到服务分工调整，先列清“谁发起、谁执行、谁回调、谁保存最终结果”，再沿请求、回调、数据库、前端状态逐项同步。最后搜索旧口径并检查 diff，把“目标设计”和“当前实现差距”明确写开；纯文档检查只证明文档改动的格式情况，不证明业务链路可用。
