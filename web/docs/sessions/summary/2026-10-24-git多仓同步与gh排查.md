# Git 多仓同步与 GitHub 回合排查

**一句话总结**：把一个仓库的多个关联 worktree 全部同步到上游最新，并用 gh api 逐条排查 200+ 个参与过的 issue——谁回了话、哪些被合入、哪些石沉大海。

## 背景

本地仓库挂了 4 个关联 worktree（主 clone + 3 个功能目录），各自停在不同分支和旧提交上；同时在 GitHub 上长期参与了一个开源项目，积累了两百多个 issue，不知道哪些有新动静、哪些其实已经被维护者自己修掉了。

## 核心命令

```bash
# 关联 worktree 同步：主 clone 走正路（switch + ff-only）
git fetch upstream main
git -C 主clone switch main
git -C 主clone merge --ff-only upstream/main

# 其余 worktree 里 main 被主 clone 占用（git 硬限制），detach 到远程最新是标准解
git -C 功能目录 checkout --detach upstream/main

# 本地分支停在错误提交上时，删掉重建到指定基线（⚠️ 删分支前确认已推远程）
git worktree remove /tmp/某目录 && git branch -D 某分支
git worktree add -b 新分支 /tmp/某目录 <基线SHA>

# 批测旧 patch 在新基线上还能不能套：干净=不动；3way 可合=观察；失败=真冲突需 rebase
git format-patch -1 <分支> -o /tmp/p
git apply --check /tmp/p/*.patch || git apply --3way --check /tmp/p/*.patch

# 强推原分支名（⚠️ force push；lease 锁定旧值，远端若被别人更新过会拒绝，防误覆盖）
git push --force-with-lease=refs/heads/分支:<旧SHA> origin 本地分支:refs/heads/分支

# 查我参与过的全部 issue 总数 / 其中未关闭数
gh api -X GET search/issues -f q="repo:OWNER/REPO is:issue commenter:ME" -f per_page=1 --jq '.total_count'
gh api -X GET search/issues -f q="repo:OWNER/REPO is:issue is:open commenter:ME" -f per_page=1 --jq '.total_count'

# 逐单查最后评论者：是自己→等对方；不是→有待处理的回合
gh api repos/OWNER/REPO/issues/N/comments --jq '[.[] | {u:.user.login, d:.created_at}] | last'

# 判断上游是否已经自己修掉了某个 issue（词边界，防 #123 误中 #1234）
git log upstream/main -E --oneline --grep '#1234([^0-9]|$)'

# 判断"通报失败的那棵树"是否包含修复（不含→红不说真话）
git merge-base --is-ancestor <通报时SHA> <含修复SHA> && echo "通报树不含修复"

# 查一个目录是什么时候进 git 的（考古归档时间）
git log --diff-filter=A --format='%ad %h' --date=short -- <路径> | tail -1

# 目录重组后：清 Finder 垃圾与空目录，再全仓扫旧路径引用
find . -name '.DS_Store' -delete; find . -type d -empty -delete
rg -ln "旧路径片段" . --glob '!**/归档目录/**'   # 逐文件修引用；归档目录内部的旧路径不修
```

## 关键结论

- **关联 worktree 共享分支引用**：`main` 被主 clone 检出后，其余 worktree `git switch main` 会报 "already used by worktree"——这不是配置问题，`--detach` 到远程最新就是标准解；原分支保留，随时切回。
- **判断"上游是否已修"必须用词边界 grep**：不带边界的 `--grep '#123'` 会命中 #1234，产生大量假阳性；同样的纪律用于「通报失败树是否包含修复」——`merge-base --is-ancestor` 一条命令实证，不靠日期推断。
- **gh 分页语义陷阱**：`?per_page=2` 返回的是**最旧** 2 条而非最新；要最新一条要么翻到末页取 `.[-1]`，要么知道评论 id 后直接按 id GET。POST 的响应 JSON 解析失败≠发送失败，先 GET 评论列表核实再决定，绝不直接重发。
- **heredoc 挂错命令会静默丢内容**：`cat >> a 2>/dev/null || cat >> b <<'EOF'` 的 heredoc 归 b，a 只读空 stdin 建出空文件，条目无声丢失——**文件追加后必须回读行数或尾部**。
- **JSON 往返整型键变字符串**：`json.dump` 的 int 键再 `json.load` 回来是 str，合并两份数据前统一 `{int(k): v for k, v in d.items()}` 归一，否则 KeyError。

## 下次怎么用

- 多仓库 / 多 worktree 的日常同步：先 fetch 盘点（分支/远程/脏文件数），干净的才切换，脏的先 stash 留档；同步后统一做一次「HEAD vs upstream/main」终验。
- 长期参与一个开源项目后想知道"哪些帖子有新回复"： commenter 搜索拉清单 → 逐单看最后评论者 → 分三类（有待处理回合 / 结局已变 / 等回复），配合词边界 grep 排除"其实上游已自修"的。
- 大规模目录重组：先 git mv 保历史，再用 rg 扫旧路径引用逐处修正；归档目录（legacy）删除前确认全部已纳管 git——工作树删了，`git checkout <删除前commit> -- <路径>` 随时整目录找回。
