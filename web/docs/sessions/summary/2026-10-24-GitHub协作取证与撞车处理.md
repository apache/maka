# GitHub 协作取证与撞车处理

**一句话总结**：用 gh api + git 组合命令在不 clone 对方仓库的前提下核实他人 patch 的独立性与冲突点，撞车时不竞争、发覆盖面对照、把取舍留给维护者。

## 背景

在开源仓库的一个 issue 上，另一位贡献者发了与我们已交付 patch 修同一问题的独立修复（在 TA 自己的 fork 分支上）。需要核实：TA 是真独立推导还是基于我们的分支改的？覆盖面是否重叠？两个 patch 能否共存？然后有效回复。

## 核心命令

```bash
# 读 issue 正文与状态（--jq 只取需要的字段，避免刷屏）
gh api repos/OWNER/REPO/issues/2607 --jq '{state, title, user: .user.login, body}'

# 读一个 issue 的全部评论（作者/时间/正文），先看清单再精读
gh api repos/OWNER/REPO/issues/2607/comments --jq '.[] | {id, user: .user.login, created_at, body}'

# 读单条评论（大帖按 id 精读，不用整页拉回来）
gh api repos/OWNER/REPO/issues/comments/6335153526 --jq '.body'

# 不 clone 对方 fork，直接看 TA 分支头提交的完整 diff（files[].patch 就是逐文件 diff）
gh api repos/OTHER_USER/REPO/commits/84c2b3a --jq '{message: .commit.message, parents: [.parents[].sha], files: [.files[] | {filename, patch}]}'
```

```bash
# 判断对方分支的父提交是否在主干上（在 = TA 基于主干；不在 = 需要进一步查来源）
git merge-base --is-ancestor 8a99473e upstream/main && echo "on main"

# 看某文件在主干上近期有没有提交（核实"上游到底修了没有"）
git log --oneline -5 upstream/main -- internal/gateway/chattidy.go

# 不切分支，直接看远端分支上某个函数的现状（验证"当前代码仍是旧形态"）
git show upstream/main:internal/gateway/chattidy.go | sed -n '/func withReasoningOnToolTurns/,/^}/p'

# 发帖前终验：分支真实存在且 SHA 与稿中引用一致（防止帖子里放死链）
git ls-remote https://github.com/USER/REPO.git refs/heads/BRANCH_NAME

# 从文件发评论（长文走 --body-file，避免 shell 转义事故），发完立刻回读核对
gh issue comment 2607 --repo OWNER/REPO --body-file comment.body.md
gh api repos/OWNER/REPO/issues/comments/COMMENT_ID --jq '{head: (.body[:200]), tail: (.body[-160:])}'
```


## 关键结论

1. **判断"真独立"看证据不猜**：两个硬证据——对方 diff 里的基线 blob hash（`index 旧hash..新hash` 行，若旧 hash 和我们改过之后的对不上，说明 TA 没基于我们的代码）+ 父提交是否在主干历史（`merge-base --is-ancestor`）。
2. **撞车处理三步**：确认对方工作真实有效 → 逐面对照覆盖差异（哪些面双方都覆盖、哪些面对方独有、哪些面我方独有）→ 明示文本冲突点（两个 patch 改了同一测试行，后合入者需 rebase）。不竞争、不撤回自己的，取舍交给维护者。
3. **说"上游没修"要有证据且标注方法**：`git log -- <path>` 看文件级提交记录 + `git show` 看函数现状，回复里写明"代码实查"而非"运行复现"，两者证据强度不同，不冒充。
4. **长评论发布纪律**：本地存稿 → 发布前自检（引用的链接/SHA 逐个验证）→ `--body-file` 发布 → GET 回读。POST 响应解析失败 ≠ 没发成功，先 GET 核实再决定是否重发，绝不直接重发。
5. **编辑长文档插入新章节时，锚点不能选在某个段落中间**——新 section 会插进原文内部把那段拦腰截断。插入后回读结构：`grep -n '^## ' 文件` 看章节顺序对不对。

## 下次怎么用

适用场景：审查他人 PR/patch 是否与自己撞车、给开源项目回帖前核实事实、判断上游是否已包含某个修复。

直接套用的取证顺序：
1. `gh api` 拉 issue 全部评论，理清时间线（谁先谁后、有没有互相引用）；
2. 拉对方的 commit diff（不用 clone TA 的 fork）；
3. `merge-base --is-ancestor` + blob hash 定独立性；
4. `git log -- path` 确认上游现状；
5. 写对照回复（事实 + 冲突点 + 留决策给维护者），`--body-file` 发、回读核验。
