# 契约门禁与换行假红

> 来源：qoder-proxy-api 本地多模型网关重构会话（WP0–WP2，仓库 `ggbdpq/qoder-proxy-api`，分支 `feat/wp2-ingress`）。本文只收本轮工具输出能对上的判断。Skill 未改。

## 一句话结论

值得留下的是三条验证口径：Windows 上 `core.autocrlf=true` 会让 LF 格式检查整仓假红；门禁要用规则字面之外的同类违规来探针；会静默丢掉未知字段的解析器不能当契约测试。生产者改了形状之后，断言要打在旧消费者写出的请求体上——这一条现有规则已覆盖，本轮是执行反例。

### 1. Windows 工作区换行假红

- 位置：`gua-dev-tools/modules/quality/references/format.md`「高价值反模式」表加一行。
- 现有规则：该页只约束 Prettier/ESLint 的改动文件格式化，没有「工作区换行和仓库换行不一致」。
- 已写入：仓库存 LF、本机 `core.autocrlf=true` 时，直接对工作区跑 LF 格式检查会把未改文件也报红。先 `git -c core.autocrlf=false archive` 导出 HEAD，再对导出树做格式检查；这才是 Linux CI 看到的内容。`main` 同样全红时，不是本轮引入的。项目约定 CRLF 时不用这条导出结果当标准。
- 证据：本机 `main` 工作区 `pnpm format:check` 报 78 个文件；同一提交按 LF 导出后 `oxfmt --check` 为 `All matched files use the correct format`（先 65，迁目录后 71–73）。对应 PR 的 GitHub Actions `test` job 通过。
- 边界：只适用于「检查器把 CRLF 当成格式错误、仓库对象是 LF」。项目若约定 CRLF，不要用这条导出结果当标准。
- 检验（未执行）：在 `autocrlf=true` 的干净 `main` 上，工作区检查应报红、LF 导出检查应通过。导出仍报红，才是仓库里真有格式问题。

### 2. 门禁探针不要只用规则里的那个词

- 位置：`gua-dev-tools/modules/quality/MODULE.md`「扫描类验证防假零」段末追加一句。不另起一条。
- 现有规则：该段要求扫描脚本打印文件数、命中数并显式退出码，防的是工具失败被看成零命中。同日笔记里的「红操演练」要求注入已知漂移后套件变红，边界写的是一致性套件。都没写：规则文本里点名的那个包通过了，不代表政策里的整类约束生效。
- 已写入：校验「禁止一类依赖 / 一类字段」的门禁时，探针要用规则字面没有写到的同类对象。只注入规则里已经点名的字符串，证的是正则，不是政策。探针必须让进程非零退出；只打印违规但仍 exit 0 的脚本不是门禁。只用于会阻断 CI 的架构、依赖、秘密扫描。
- 证据：`apps/gateway/scripts/architectureCheck.ts` 起初只拦 `zod` 和 `@qpa/contracts`。注入 `import { Hono } from "hono"` 以及给 `package.json` 的 `dependencies` 加上 `hono`，两次都是 exit 0。收成「源码只许 `node:` 与相对路径，且 `dependencies` 为空」之后，上述探针 exit 非 0，干净树 exit 0。
- 边界：日常搜代码不需要探针。只用于会阻断 CI 的架构、依赖、秘密扫描。
- 检验（未执行）：门禁写「禁止 zod」。再注入另一个运行时包名。正确结果是失败；只对 `zod` 失败、对另一个包成功，就是规则写窄了。

### 3. 契约测试要拒绝多余字段

- 位置：`gua-dev-tools/modules/api/MODULE.md`「验证设计」的样本列表加一条。
- 现有规则：样本要含空值、null、缺失字段和多项数组。没有「多出来的字段必须失败」。
- 已写入：解析器若默认剥掉未知字段，夹带 prompt、密钥或漂移字段的样本仍能通过。信任边界上要有一条多余字段必须失败的样本，真实产出的合法样本也要能通过。内部宽松 DTO 不必一律拒绝未知字段。
- 证据：`packages/contracts` 在改成严格对象之前，带 `prompt` 的路由事件和带 `apiKey` 的候选能 `safeParse` 成功。改完后这两条失败用例变绿；骨架 e2e 导出的 8 个真实事件仍然通过（测试名「事件夹带契约外字段被拒绝」「骨架 e2e 产出的 8 个路由事件全部 safeParse 成功」）。
- 边界：只用于信任边界上的契约解析。内部宽松 DTO 不必一律拒绝未知字段。
- 检验（未执行）：给合法样本加一个契约没有的键。正确结果是解析失败。解析成功并只是丢掉该键，测试没有守住边界。

## 可复用经验与案例

**纯移动提交怎么保持 0 行 diff。** 验收要求第一笔提交只有 rename。把 `package.json` 和 `src` 一起 `git mv`，`bin`、`scripts` 的相对路径不用改，`git show --stat -M` 才是 76 files、0 insertions、0 deletions。路径修正放进下一笔。若随后 squash，这一笔在历史里不可见。本仓用 merge commit 保留它。这是该仓验收口径，不推广成所有 PR 的合并方式。

**改生产者之后，旧消费者不会自动读新字段。** WP2 把图片和工具结果放进 Canonical part，针对 Canonical 的往返测试是绿的。Qoder gateway 的 `collectImages` 仍读 `part.source`，`messageText` 只拼接 `type: "text"`，所以上游请求里图片没了、工具结果正文是空的。用户点名后补的测试打在解码后的上游 body：`is_vl`、`image_url`、`tool_call_id` 和正文 `sunny`。先红后绿，见 `test/gateway/gatewayProvider.test.ts`。`modules/api` 已要求追到消费层，`modules/review` R68 已要求 fixture 对齐真实生产者。本轮不新增规则。下次改共享形状，先写旧消费者输出的失败断言，再改映射。

**契约正文互相矛盾时，选定一种并写进 PR，不改仓库外的文档包。** `02-接口契约` 的 409 有三种写法。实现按统一错误信封，`IN_USE` 另带可选 `refs`，决定写在 PR 评论里。文档包不在该 git 仓，本轮没有改它。

## 常用命令

前提：Windows PowerShell，仓库对象是 LF，`git config core.autocrlf` 为 `true`。在仓库根执行。

工作区格式检查不可信时，看 CI 会看到的树：

```powershell
git -c core.autocrlf=false archive -o "$env:TEMP\qpa-lf.tar" HEAD
```

导出到空目录后，用项目本地的格式器对导出树 `--check`。成功信号是「全部文件格式正确」。副作用：只读，不改工作区和索引。`tar` 在 Windows 上不要从管道读 `git archive`，本轮管道方式报 `Failed to open '\\.\tape0'`，改成 `-o` 文件再 `tar -xf` 才成功。

确认一笔提交是纯 rename：

```powershell
git show --stat -M --format=%s HEAD
```

成功信号：变更行统计为 `0 insertions, 0 deletions`。没有 `-M` 时，移动会显示成删除加新增，不能用来证明纯移动。
