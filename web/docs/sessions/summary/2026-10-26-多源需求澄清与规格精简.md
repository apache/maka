# 多源需求澄清与规格精简

**一句话总结**：先确定资料优先级，再明确计数与状态边界，把答案回写成可测试的需求，最后删除重复说明。

## 背景

同一功能的需求清单、PRD和原型存在冲突：有的功能已取消，图片却还保留；有的统计名称相似，实际对象和时间范围不同。最终通过逐题澄清、回写规则与验收条件，再精简文档，形成统一的需求基线。

## 核心命令

在目标Git仓库执行；Python统计命令在 `spec.md` 所在目录执行。

```bash
git status --short # 查看已修改和未跟踪文件，确认改动范围
git diff --check # 检查已跟踪变更中的空白错误；不会检查未跟踪文件
python -X utf8 -c 'from pathlib import Path; t = Path("spec.md").read_text(encoding="utf-8"); print("行数:", len(t.splitlines()), "字符数:", len(t))' # 统计文档篇幅；-X utf8让Python按UTF-8处理标准输入输出
```

## 关键结论

1. **多份资料冲突，先定裁决顺序。** 本次采用清单评审结论优先、PRD其次、原型补展示与交互。根因是资料更新不同步，不能把“原型上还有”直接当成“本期要做”，也不能把示例数字当统计规则。
2. **统计口径至少写清对象、时间和状态。** 待办类别数、AI听记录数、专场卡片数是三种计数；当天摘要可以包含已复盘记录，待复盘列表却只含未复盘记录。名字相近不代表能复用同一集合。
3. **独立操作要有独立状态。** 确认真实成交只保存成交结果，不自动完成复盘；完成复盘也不要求先确认成交。验收应分别覆盖保存、取消、完成和失败，避免一个操作顺带改变另一个状态。
4. **澄清优先问会改变验收的问题。** 一次只问一题，给出不同理解造成的差异及建议答案；已回答的问题直接回写对应FR和Given/When/Then。重点验证阈值是否含边界，例如≤50%、>70%、预约恰好60分钟，以及午夜跨时段。
5. **精简靠去重，验收靠证据。** 每条FR保留规则和1–2条验收，加载、异常与缺失集中写，澄清结果回到同一份Spec。精简后仍逐条检查来源与验收覆盖；外部报表公式未提供时，即使编号和结构检查通过，也不能认定数值验收通过。
