# 列表筛选切换与恢复

## 一句话结论

列表同时支持详情返回恢复和主动切 Tab 清空时，由实际切换事件提交新的查询状态，并检查该动作之后的请求序列。界面上选中了正确条件，仍可能被随后的无筛选请求覆盖。

## Skill 增量建议

- **`gua-dev-tools/modules/ui/references/state.md`「P2 搜索表单契约」**。现有条款覆盖搜索与重置回首页，`modules/dev/references/state-management.md` 已说明查询态归属及作用域清理。可补上恢复与清场共用缓存时的写入时机。
  > 若产品要求切组清空、详情返回保留，首次进入与返回按既有规则恢复，缺少分组字段的缓存按初始化处理。实际切组时成组写入新分组、首页和清除后的条件，同步表单显示。翻页与刷新沿用当前已生效的查询条件。

  **依据与边界**见下方活动卡片案例。适用于明确要求切组清场的列表，每个 Tab 各自保留条件的页面按各自规则恢复。**检验场景（未执行）**。旧缓存无分组时提交条件，当前组的请求带筛选且随后没有无筛选请求覆盖。主动切到另一组，请求回首页且省略已清空条件。返回详情前所在的列表时恢复原查询快照。

- **`gua-dev-tools/modules/bug/MODULE.md`「顺序脚本的失败前沿」**。现有段落覆盖遇错即停和匹配口径一致。可在原段补上允许静默跳过的动作及请求采样边界。
  > 必做的界面动作先确认命中唯一可操作目标。定位失败时令该用例失败，允许跳过的动作显式记录跳过。预期触发请求时，只核对该动作之后新增且匹配的请求。

  **依据与边界**见下方活动查询案例。适用于界面自动化，合法的本地过滤或缓存命中应核对预期界面状态。**检验场景（未执行）**。将带排版空格的按钮文案归一化后，故意用不一致的目标值匹配。用例应停在定位步骤。修正匹配后，断言本次新增的请求包含查询值。

## 可复用经验与案例

- **活动卡片列表的筛选被清空。** 用户要求详情返回沿用原 Tab、页码和条件，主动换 Tab 清空条件并回首页。旧缓存缺 `orgType` 时，子列表把它与当前 Tab 的差异判成切换。浏览器先发出带 `status=FINISHED` 的请求，紧接着又发了一条无筛选请求。修复将新 Tab、首页及条件清理放在父级 `onChange` 成组写入，子列表把缺分组当作初始化，并在翻页时显式带上已生效的 `name`、`status`。历史回执确认筛选、切组清场、重置及从详情返回恢复。该项目的 `status` 是查询契约，卡片编辑与取消仍按其原有 `state` 判断。来源为原会话用户需求 #1、#446，Network #483、#494、#502–505，`activeMain/index.js` 与 `content.js` 历史编辑 #485、#487、#497。
- **活动查询的表单被误诊。** 脚本把按钮文本的空格去掉后仍比较 `查 询`，定位失败被条件调用静默跳过，后来读到的还是首屏无 `name` 的请求。改为匹配 `查询` 后观察到新增请求携带 `name`，并返回对应空结果，前端表单接线由此得到验证。遇到「输入已显示，接口参数没变」时，先确认动作是否执行，再查表单绑定和请求封装。来源为原会话浏览器执行及回执 #605、#619、#621。
