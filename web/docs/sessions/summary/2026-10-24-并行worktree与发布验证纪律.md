# 并行 worktree 与发布验证纪律（magpie 狩猎五轮沉淀）

**一句话总结**：五轮开源仓库贡献（27 次交付）沉淀出的 Git 并行工作流、发布门控和消融验证方法，全部可直接套用到日常开发的多分支与自动化发布场景。

## 背景

连续五轮在 yetone/magpie 仓库做 bug 修复贡献：上游两天内有 37+ 提交大波重构，手里同时挂着 40 个在途 patch，期间发生了重复发帖、push 瞬断、消融假绿三起事故。这轮把事故全部沉淀成了可复用的门控与验证纪律。

## 核心命令

```bash
git fetch upstream main && git rev-parse upstream/main   # 每轮开工先同步并记录基线 SHA
git merge-tree --write-tree upstream/main origin/branch1 # 无损预演合并，输出 CONFLICT 即有冲突（可循环批扫全部分支）
git log --grep='#1234' upstream/main                     # 查上游是否已自修某 issue，防止撞车
git worktree add -b feat-x /tmp/wt-x upstream/main       # 每个子任务独占工作树，互不污染
git worktree remove /tmp/wt-x && git worktree prune      # 用完即清；/tmp 会被系统清理，先推分支再删
git push --force origin new-branch:old-branch            # ⚠️ 强推覆盖远程分支；仅当 rebase 后保住原分支链接时用
git ls-remote origin refs/heads/old-branch               # push 后核验远程 SHA 确实等于本地，再做后续动作
git log -S 'funcName' upstream/main                      # 按符号搜提交历史，定位某字段/函数的引入与退役
shasum -a 256 patch.diff | cut -c1-16                    # 给交付物算指纹，证明帖内贴的与实测的是同一份
GOTOOLCHAIN=auto go test ./internal/pkg/ -run 'TestX' -count=1   # 按声明的 Go 版本跑定向测试
gh api repos/org/repo/issues/1234 --jq '.comments'       # 精准查单条 issue 的评论数，防重复触达
gh api 'repos/org/repo/issues?state=open&per_page=100&page=N'   # 分页拉全量 open issue（search API 限流时更稳）
```

## 关键结论

- **发布链必须逐步门控，任何一步失败就停**：push → `ls-remote` 比对远程 SHA 等于本地 → 查评论数未变 → POST → GET 回读。用 `;` 串联会让 push 失败后照常发帖（真踩过：帖里 head 与远程不一致 1 分钟）。
- **POST 响应解析失败 ≠ 没发成功**：GitHub 响应混入控制字符会让 jq 崩溃，误判后重发就出重复帖。先 GET 评论列表核实，确认未发才重发；解析用 python `json.load` 落文件，不用 `echo | jq`。
- **消融变异点必须落在被测窗口内**：验证"修复起效"时，把修复短路后测试必须红。踩过的坑：注入点插在状态建立之前（不红）、`-run` 模式匹配错测试名（假绿）、单行函数与多行函数的变异语法不同。修法是双保险结构时，要组合禁用两个分支才见红。
- **上游大波重构后，先批扫再 rebase**：`merge-tree` 循环扫所有在途分支找出冲突的少数；rebase 前先在裸 main 上跑测试拿 RED，实证"上游没顺手修掉"才动手，否则让位。
- **概率性失败（race/flake）用三向验证**：原命令复现红 N 次、隔离最小组合复现红、修复后同参数多次全绿——三次独立日志同签名才算定性，单次绿不算。
- **候选/需求池要落成持续维护的表格**：新候选追加在顶部、处置列随进展更新、让位/不接的留在底部作否定先例——上游已修 ×4 的撞车全是靠"先读评论"这一条避免的。

## 下次怎么用

- 多个子任务并行改同一个仓库：每任务一个 worktree，基线统一取上游/主干最新，收口即推即清。
- 自动化发布/发帖脚本：把五步门控做成固定管道，任何一步退出码非零或校验不等就中止。
- 修完 bug 写回归测试后：做一次消融（还原修复保留测试，确认红），证明测试真的守住了这个行为。
- 维护长期需求/候选清单：一个 markdown 表格按处置分区，新条目放最前，否定先例不删。
