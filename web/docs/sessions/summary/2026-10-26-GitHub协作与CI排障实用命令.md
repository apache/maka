# GitHub 协作与 CI 排障实用命令

**一句话总结**：多仓库开源贡献流水线一轮"盯审 + 修复"的实战沉淀——凭证链修复、CI 红的定性方法、本地基线对照判定测试归属、git 历史恢复与多 clone 收敛。

## 背景

给 apache/maka 持续提 PR 的日常：仓库搬家后 push 401、CI 红要分清是自己改坏还是上游传染、本地测试失败要判定是预存病还是回归、工作区被多次重构后要把四个 clone 收敛回主干。这轮全部走通，命令和判定方法可复用。

## 核心命令

```bash
# ---------- 凭证与 API ----------
gh auth status                      # 查 gh CLI 登录态与令牌 scopes
TOKEN=$(gh auth token)              # 令牌只进变量，绝不 echo/落盘
curl -s -H "Authorization: Bearer $TOKEN" "https://api.github.com/repos/<owner>/<repo>/pulls/<n>"   # 单查 PR 状态
curl -s -H "Authorization: Bearer $TOKEN" "https://api.github.com/repos/<owner>/<repo>/commits/<sha>/check-runs?per_page=100"   # 查某提交的 CI 明细
curl -s -H "Authorization: Bearer $TOKEN" "https://api.github.com/repos/<owner>/<repo>/actions/runs?branch=<branch>&per_page=3"  # 按 branch 查 workflow run，conclusion 才是终态（check-runs 的 in_progress 有滞后）
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d @body.json "<api-url>"   # 长文本发评论/开 PR：JSON 先落盘再 -d @file，防引号转义事故
curl -s -L -H "Authorization: Bearer $TOKEN" "https://api.github.com/repos/<owner>/<repo>/actions/jobs/<job_id>/logs" -o ci.log   # 下载 CI 失败日志，grep 失败步骤名定性

# ---------- 修复 push 401（凭证链投毒） ----------
gh auth status                      # 先确认 gh 本体有有效令牌
git config --unset-all credential.https://github.com.helper 2>/dev/null
git config --add credential.https://github.com.helper ''      # 先清空继承链
git config --add credential.https://github.com.helper '!"C:/Program Files/GitHub CLI/gh.exe" auth git-credential'
# ↑ 仓库级把 github.com 凭证指向本机 gh（路径按本机 gh.exe 实际位置改），不动全局配置

# ---------- git 同步与历史 ----------
git fetch upstream main                                        # 同步上游
git log --oneline main..upstream/main | wc -l                  # 数落后多少提交
git merge --ff-only upstream/main                              # 只允许快进，分叉即报错（防误合）
git checkout -- package-lock.json                              # 丢弃 npm 安装噪音后再切分支（脏树会挡 checkout/ff）
git stash push -m "wip" -- <文件...> ; git stash pop            # 基线 A/B 对照：暂存改动跑纯上游基线，再恢复
git log --oneline @{u}..HEAD                                   # 推送前自查未推送提交
git -c core.quotepath=false ls-tree -r --name-only <rev> -- <路径>   # 列历史树（非 ASCII 文件名必须加 -c 关闭转义）
git archive <rev> -- <路径> | tar -x -C <临时目录>              # 从历史整目录恢复文件（unicode 安全，比逐文件 git show 稳）
git show <rev>:<文件> | diff --strip-trailing-cr - <本地文件>   # 与历史逐字节比对（忽略换行符差异）
git worktree list                                              # 查注册 worktree；删用 git worktree remove --force <目录>

# ---------- node / npm ----------
npm install --ignore-scripts --no-audit --no-fund    # 重建依赖；仓库搬家后 workspace symlink 悬空也靠它修
npm --workspace <包名> run build                      # 报 "No workspaces found" = 名字错，查该包 package.json 的 name 字段
npm --workspace <包名> run build && node --test <测试文件>    # 构建与测试必须 && 串联（; 会吞退出码，构建挂了跑旧产物=假绿）
node --test --test-force-exit --test-timeout=90000 <文件或目录>   # 强制退出+单测 90s 超时，防套件被一个挂起测试卡死
npx biome check <改动文件...>                         # 提交前格式/静态检查改动面

# ---------- Windows 进程清理 ----------
for pid in $(tasklist | grep -i "node.exe" | awk '{print $2}'); do taskkill //F //PID $pid; done
# ⚠️ 上面按 PID 精确杀；千万别用 taskkill //F //IM node.exe —— 会无差别杀光机器上所有 node 进程（含无关服务）
```

## 关键结论

1. **push 401 的根因排查顺序**：先 `gh auth status` 确认 gh 本体令牌有效 → 再查 `credential.helper` 链。这次是 GCM 里存了损坏凭证 + 残留 macOS 路径的 helper 串联投毒；修法是仓库级清空继承链后指向本机 gh，全程不动全局配置。
2. **CI 红先定性再动手，三个问题按顺序问**：①失败的 job 的 head_sha 和失败步骤名是什么（别默认红=自己改动）；②PR 的 CI 跑的是 **merge preview 树**（PR+main 合并结果），本地绿≠CI 绿，反之亦然；③上游 main 自己红着时，PR 红大概率是传染，merge latest main 即愈。
3. **本地测试失败用两条判据归因**：①单测隔离重跑——隔离 3/3 绿、全量跑才挂 = 负载敏感，不是回归；②纯基线对照——把改动 stash 后在干净上游 checkout 上重跑同样测试，失败集合一模一样 = 预存病，与改动无关。
4. **"限流/配额"型棘轮台账：本地 `--write` 重定价不等于 CI 放行**——CI 严格模式拿 base 分支实测对比，任何指标**增长**直接拒绝。改动前先确认目标文件是否在受控清单里，能不碰就不碰；真要动，注入/依赖方向要走架构允许的边界而不是硬加重。
5. **仓库搬家后的隐藏坑**：workspace symlink 还指旧家（判别：dist 里文件在但 node_modules 链接指旧路径），`npm install --ignore-scripts` 重建即可；克隆别名的拼写错误目录（make-pr1 这类）往往只剩空壳，清理前用"有无 .git + 未推送提交数 + 脏文件数"三查确认无独有工作再删。
