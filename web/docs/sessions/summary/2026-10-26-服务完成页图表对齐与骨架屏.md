# 服务完成页图表对齐与骨架屏修复

**一句话总结**：Taro 报告页里，骨架屏要挂在"用户能看到的刷新入口"上而不是桥接回调后，图表采样点要用流程槽位区间锁住才不会漂到错误的流程名下面，内层横向滚动用"到边缘才放行"的触摸拦截避免误切外层页签。

## 背景

beauty-smart-advisor 项目 `src/pages/serviceComplete`（服务完成/护理报告页）三连修：护后拍照返回时 summary 生成中轮询要显示骨架屏；本次收获页签的身体放松图表要像专属护理一样横向滚动且流程分段对齐；修完后发现图表的数据点落在错误的流程名区间。三个问题根因都在时序和共享逻辑的模式差异上。

## 关键结论

1. **原生桥接回调时机不可靠，可见性 UI 别挂在它后面。** `hetsdk.startTestProject` 的 Promise 在原生相机页还盖着 H5 页时就 resolve，骨架屏挂在"await 之后刷新"的路径上，在用户看不见时挂载又收掉，回到页面只走 `useDidShow` 的静默刷新。修法：骨架屏状态不按入口区分，统一由"轮询观察到 `status=0` 才挂、出终态（成功/失败/取消）就收"驱动——`useDidShow` 返回时触发的那次刷新必然发生在用户能看到的时刻；summary 已就绪（首次返回 status=1）时不挂，避免闪一帧。

2. **图表点与流程名对不上：采样点映射缺了槽位区间约束。** `ScatterLineCharts` 里 `mapSamplesToAxisSlots` 的第 4 参 `slotRanges`（按时间归属把点锁定在本流程的槽位区间）之前只在专属护理 footer 模式传，default footer 模式没传——槽位被占时分配器向后探测最多 8 槽，采样密集时点逐级漂移跨过流程边界。修法：去掉 `isCarePlanFooter` 门控无条件传入。教训：**同一套数据映射逻辑服务多种 UI 模式时，约束参数漏给一种模式，就只有那种模式"对不上"**。

3. **外层横滑切页与内层横向滚动冲突的标准解法。** 内层 ScrollView 在 `onTouchMove`/`onTouchEnd` 里判断"手势方向上还能滚"（起点 scrollLeft 距边缘 > 4px 阈值）就 `stopPropagation` 消费手势，滚到最左/最右继续滑才放行给外层切页；scrollLeft 用 `onScroll`/`onScrollToUpper`/`onScrollToLower` 三个事件维护。复用专属护理现成的 `shouldTrapCareTableTouchMove` 即可，不用重写。

4. **流程名列宽和图表分段对齐靠"同一份槽位数据"。** `buildDurationWeightedAxis` 产出 `slotCounts`，流程名列宽 = 轨道宽 × slotCount/totalSlots，图表分段内部用同一轴，结构上必然对齐；把这套算法提取成共享函数（`buildTrendProcessColumnLayout`）供两处调用，防止以后改一处漏一处。

5. **工具链坑与验证口径。** ESLint 8.12.0 + 现装 `eslint-plugin-react-hooks` 会在 `react-hooks/exhaustive-deps` 上抛内部错误（`meta.hasSuggestions`），是工具链兼容问题不是代码问题，别顺着报错改代码；本项目验证口径是 touched files 的 `prettier --check`，全仓 `tsc --noEmit` 和格式化由用户自己控制，Agent 不要主动跑。
