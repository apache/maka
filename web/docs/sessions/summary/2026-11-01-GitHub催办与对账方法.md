# GitHub 批量核查 issue 与催办方法

**一句话总结**：用 gh CLI + GraphQL 别名批量核查 issue 状态，用「单号+关键词」双层对账判断 patch 是否被上游收编，再用「刚追平+整批帖」催办公式推动合并——五轮催办 44 单次，38 支进 main。

## 背景

维护一个开源项目的 fork，patch 以 git am 格式贴在 issue 里等维护者收编。维护者忙、没空逐条看 issue，需要定期筛出值得催的单，并准确知道哪些 patch 已经进了 main——既不能漏（错过收编信号），也不能重复推已合并的单。

## 核心命令

```bash
# 批量取 issue 状态+末评：先用 search API 拿全集，再用 GraphQL 别名一次查 25 个
gh api "search/issues?q=repo:OWNER/REPO+is:issue+state:open+commenter:你的用户名&per_page=100" --jq '.items | map(.number) | join(" ")'
# q.json 形如 {"query":"query { repository(owner:\"o\", name:\"r\") { i123: issue(number: 123) { number state comments(last:3){ nodes { author { login } createdAt } } } ... } }"}
gh api graphql --input q.json | jq -r '...'
```

```bash
# 收编对账第一层：主题行精确找单号（git log --grep 会匹配提交正文，交叉引用会污染结果）
git log upstream/main --format="%h %s" | grep -F "(#1234)"

# 对账第二层：关键词兜底——收编提交的主题行可能不带单号（改写吸收形态）
git log upstream/main --format="%h %s" | grep -iE "痛点关键词1|关键词2"
```

```bash
# 查落地提交的作者署名是否保留
git show -s --format="%an | %s%n%b" <sha>
```

```bash
# 拉 issue 评论取末评（REST 按时间【升序】返回，小分页取到的"尾"其实是头部）
gh api "repos/OWNER/REPO/issues/1234/comments?per_page=100" --jq '.[-1] | "\(.user.login) @ \(.created_at[0:16]): \(.body[0:200])"'
```

## 关键结论

1. **收编提交主题行可以不带单号**（改写吸收形态，正文才点名报告者）——只按单号 grep 会误报「未收编」，下一轮重复推荐已合并的单；对账必须「单号 grep + 痛点关键词」两层。
2. **REST comments API 按时间升序返回**：`per_page=6` 之类小分页取到的「尾几条」其实是头部，会漏掉维护者最新回复；取尾一律 `per_page=100` 或 GraphQL `comments(last: N)`。
3. **GitHub 列表里的 "by 某人 was closed" 指的是作者，不是关闭者**——三单看着一样，实际两单是维护者关的重复单、只有一单是自己关的；分清谁关的要查 events API。
4. **催办奏效公式 =「刚追平 + 整批帖」**：发帖前把所有在途分支 rebase 到当日 main，结尾固定「N 个都已 rebase 到当前 main，git am 即进」；谢事实不夸速度，已被处理过的单不在帖里复述（对方只能回 already landed）。
5. **`gh issue close --comment` 的参数是字面文本，不读文件**——关单评论要用 `gh issue comment --body-file` 先发、再 `gh issue close`，否则评论内容就变成文件路径字符串。

## 下次怎么用

- **定期盘点 fork 贡献**：search API 拿自己评论过的 open 单全集 → GraphQL 批量拉末评 → 末评不是维护者的 = 在等他侧 → 排除维护者本人开的自留单（正文只有日志流水、无求助语句的）→ 第三方最新发言的单是最强催点。
- **判断自己的 PR/patch 合了没**：单号 grep + 关键词 grep 双层，命中后 `git show -s --format=%an` 看署名是否保留（author 不变 = git am 直提；author 变成维护者 = 吸收重做，去提交正文找文字署名）。
- **写催办帖**：事由一句开头，每单「编号+一行痛点」，结尾固定收束句；有用户当天在 issue 里 @ 维护者的单排最前。
