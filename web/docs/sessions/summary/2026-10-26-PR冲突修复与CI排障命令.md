# PR 冲突修复与 CI 排障命令

**一句话总结**：维护开源仓库在途 PR 时，用 API 令牌链查状态、merge-tree 预探冲突、按"消费方所在包跑测试"定性本地失败，两次 CI 真红的根因都是流程问题（改动没进提交 / 新代码违反消费方契约），不是代码写错。

## 背景

给 apache/maka 维护 5 个在途 PR：解与 main 的冲突、响应 review 意见、修 CI 红，期间交付 2 个新单；另外把本地仓库迁移到新路径时卡在目录占用。

## 核心命令

```bash
# GitHub API 免 gh CLI：令牌只在本条命令变量里流转，不落盘不回显
TOKEN=$(printf 'protocol=https\nhost=github.com\n' | git credential fill | grep '^password=' | cut -d= -f2-)
curl -s -H "Authorization: Bearer $TOKEN" "https://api.github.com/repos/OWNER/REPO/pulls/123"

# CI 红排查三步：commit 的检查 → job 定位失败步骤 → 拉日志搜错误标记
curl -s -H "Authorization: Bearer $TOKEN" ".../commits/<sha>/check-runs"
curl -s -H "Authorization: Bearer $TOKEN" ".../actions/jobs/<job_id>"
curl -sL -H "Authorization: Bearer $TOKEN" ".../actions/jobs/<job_id>/logs" | grep -n '##\[error\]'

# 不切工作区预探分支与 main 的冲突（输出 CONFLICT 即有冲突，顺带列出文件）
git merge-tree --write-tree <my-branch> upstream/main

# 只跑一个名字匹配的测试（node 原生 test runner）
node --test --test-name-pattern '某个测试名关键字' dist/__tests__/xxx.test.js

# 上游新增依赖/workspace 后：补链接 + 重放补丁，再按依赖序重建
npm install --ignore-scripts --no-audit --no-fund
node scripts/apply-dependency-patches.mjs

# API 写操作（发评论/改正文）：body 用 python json.dump 落文件，手写转义必 400
python -c "import json; json.dump({'body': '评论内容'}, open('c.json','w',encoding='utf-8'), ensure_ascii=False)"
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d @c.json ".../issues/123/comments"

# 迁移含 junction/symlink 的目录（如 node_modules）：/XJ 跳过连接点防递归；退出码 0-7 都算成功
robocopy "源目录" "目标目录" /E /XJ /NFL /NDL /R:1 /W:1

# 建基线对照环境：纯净 main 的 worktree + 共享 node_modules（junction 不占空间）
git worktree add C:/temp/baseline upstream/main
python -c "import _winapi; _winapi.CreateJunction(r'主仓/node_modules', r'基线/node_modules')"
```

⚠️ `git push --force-with-lease origin <分支>`：重写远端历史，仅限自己的 PR 分支且刚推的未审提交；lease 比裸 `--force` 多一层"远端没被别人更新"的保护。
⚠️ `git reset --soft <commit>`：把提交退回暂存区重做，提交内容不丢但历史改变；确认没有别人基于它工作再用。

## 关键结论

1. **PR 维护优先级：review 意见 > CI 红 > 冲突 > 新单**；review 里声称"已修复"的内容一律 `git show`/`git grep` 到 head 上重验，回复文字不可信。
2. **冲突解法三分类**：双方各加→按 union 保留；同区互斥→取一方后重放己方语义；"我方重写了整个文件 + 对方改旧文件"→不做文本并集，把对方语义**移植进重写后的新家**，对方 auto-merge 进来的测试就是现成验收标准。
3. **CI 两次真红的根因都是流程不是代码**：一次是移植改动留在工作区没进提交（只推了后续文件）；一次是新逻辑违反了消费方包里的既有契约测试。推前 `git status` + `git log origin..HEAD` 双查可防第一类。
4. **验证要跑"消费方所在的包"**：改了库函数，它的调用方测试在另一个包里，只跑自己包会漏掉真正踩契约的用例。
5. **本地测试挂 ≠ 回归**：先与纯净 main 的 worktree 同构对照（单跑对单跑、全文件对全文件）；`/tmp` 路径、`path.resolve` 盘符差异都是 Windows 预存病，Linux CI 不受影响。
6. **陈旧 dist 两类病**：已删源文件的 dist 残留（孤儿测试）会引用不存在的导出报错；复合 tsc 工程只删 dist 不删 tsbuildinfo 会整体跳过输出，`test:dist` 报 0 测试的假绿。清 dist 必须用包自带 clean 脚本连 tsbuildinfo 一起删。
7. **目录迁移卡死的根因**：Agent 会话/终端的工作目录被钉在源路径，句柄不释放就搬不动；且 robocopy 中断会留下半份拷贝——重迁前先删目标侧残件，以源目录为准。
8. **写错的评论可救**：`PATCH /repos/{owner}/{repo}/issues/comments/{id}` 直接改；推错历史用 `reset --soft` 重做 + `push --force-with-lease` 收拾。

## 下次怎么用

维护在途 PR 的标准开场：`git fetch upstream` → API 盘点 open PR 的 mergeable/check-runs/最新 review → `merge-tree` 探冲突 → 按"review > CI 红 > 冲突 > 新单"的顺序修。环境异动（上游加了包/改了补丁）后先 `npm install --ignore-scripts` + 补丁脚本 + 按依赖序重建，再跑测试；本地挂单先做同构基线对照再定性，绝不把环境病当回归修。
