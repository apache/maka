# macOS 磁盘空间排查与清理命令沉淀

**一句话总结**：磁盘只剩 12G 的一轮排查清理实录——du 逐层下钻定位到 go-build 119G 等大头，按技术栈清出约 215G（可用 12→244GB），沉淀 go 模块缓存只读权限、pip purge 清不净、zsh glob 中止、GiB≠GB 四个坑。

## 背景

小组件显示 Macintosh HD 可用仅 13.23 GB / 494.38 GB。用 `df` + `du` 从数据盘到家目录逐层下钻，最大头是 `~/Library/Caches/go-build`（119G），其余是各语言包管理器缓存和 `/private/tmp` 里后台应用没清的工作区。清理分三轮：先清可再生缓存（自己执行），再补遗漏（两条失败命令修复），最后清系统区（/tmp 与 updater 缓存）。所有删除目标都是缓存或临时工作区，源码、配置、聊天记录一律未动。

## 排查命令（先量再删）

```bash
# 数据盘水位一行看全：Used/Avail/Capacity；⚠️ df 的 G 是 GiB，macOS 小组件显示的是十进制 GB，227GiB≈244GB，别当异常
df -h /System/Volumes/Data
```

```bash
# 家目录顶层体积排序：-x 不跨文件系统，2>/dev/null 吞掉无权限噪音；大头往往一眼可见
du -xsh ~/* 2>/dev/null | sort -rh | head -25
# 隐藏目录单独扫：npm/pnpm/uv/gradle 这些大头全以 . 开头，上一条看不到
du -xsh ~/.[!.]* 2>/dev/null | sort -rh | head -25
```

```bash
# 对最大目录逐层下钻，直到定位到具体缓存；本次 ~/Library/Caches 下钻两次就锁定了 go-build
du -xsh ~/Library/* 2>/dev/null | sort -rh | head -15
du -xsh ~/Library/Caches/* 2>/dev/null | sort -rh | head -25
```

```bash
# 家目录之外别漏扫：/private/tmp、/Library、/Applications、废纸篓
du -xsh /private/tmp/* 2>/dev/null | sort -rh | head -20
# 本地 Time Machine 快照会吃掉可用空间且 Finder 不显示；本次实测为空
tmutil listlocalsnapshots /
```

```bash
# 删任何来路不明的目录前先做两件事：看 mtime 判断是否还有任务在写、查进程占用
ls -ldT /private/tmp/<目录>          # ⚠️ 实测某目录 22 分钟前还在被写入，等静止再动手
lsof +D /private/tmp 2>/dev/null | head   # 输出只剩系统进程 = 无占用
```

## 按技术栈清理

### Go

```bash
# 先确认缓存实际位置，有人改过 GOCACHE/GOMODCACHE 时别按默认路径猜（本次就翻出一个遗留的 ~/gocache）
go env GOCACHE GOMODCACHE
```

```bash
# 编译缓存：本次最大头，实测 119G；清后首次构建变慢，属正常
go clean -cache
# 模块缓存：默认 ~/go/pkg/mod，实测 7.1G；重新构建时自动重新下载
go clean -modcache
```

```bash
# ⚠️ 坑：go 把模块缓存目录设成只读(555)，rm -rf 会报 Permission denied，
# 末尾连锁出误导性的 "Directory not empty"。任何位置的 go mod 缓存都用这两步删：
chmod -R u+w <目录> && rm -rf <目录>
```

### Node.js（npm / pnpm / yarn / bun）

```bash
# npm 缓存：_cacache 占大头（实测 18G）
npm cache clean --force
```

```bash
# pnpm：只清未被项目引用的包，活跃项目的硬链接不受影响；store 实测 26G
pnpm store prune
# pnpm 元数据缓存直接删
rm -rf ~/Library/Caches/pnpm
# ⚠️ store-dir 配置变过的机器会留游离 store（~/.pnpm-store、项目内 .pnpm-store），
# 先确认当前 store 再删旧的：
pnpm config get store-dir
```

```bash
# yarn v1 / bun
yarn cache clean
bun pm cache rm
```

```bash
# fnm/nvm 管的 Node 版本是工具链不是缓存：default 在用，只删确认不要的旧版本
fnm ls && fnm uninstall v18.20.8
```

### Python

```bash
# ⚠️ 这台机器没有 pip 命令，zsh 的 correct 还会把 pip 纠错成 pip3/pp（输 n 按原样执行）；
# 用 python3 -m 走当前解释器最稳：
python3 -m pip cache purge
# ⚠️ purge 在多版本 Python 下清不干净（实测 882M 只清掉 159 个文件），整目录删才彻底：
rm -rf ~/Library/Caches/pip
# uv 缓存（实测 7.6G）
uv cache clean
```

### Rust / JVM

```bash
# cargo 只删 registry 缓存；~/.cargo 其余是工具链本体，别整个删
rm -rf ~/.cargo/registry/src ~/.cargo/registry/cache
# Gradle 构建缓存，重新构建自动重建（首次构建变慢）
rm -rf ~/.gradle/caches
```

### Electron 应用与浏览器

```bash
# 各应用升级包缓存（kimi/deepseek/notion/zcode/夸克/apifox 等），删了不影响应用本体；
# ⚠️ 这类缓存存在两处，两行都要跑：
rm -rf ~/Library/Caches/*-updater
rm -rf ~/Library/Application\ Support/Caches/*-updater
```

```bash
# playwright 浏览器（实测 2.4G）：近期要跑 UI 测试就别清，重下很贵
npx playwright uninstall --all
```

### /tmp 与后台自动化应用

```bash
# /private/tmp 系统会清 3 天未访问项，但后台任务应用反复触碰就永远留下来（本次 41G，129 个目录）
# 涉及后台应用（如 magpie）的工作区：确认 5 分钟内无新写入 → 退出应用 → 再删
find /private/tmp/<目录> -type f -mmin -5 | head -3   # 空输出 = 已静止
osascript -e 'quit app "magpie"'
rm -rf /private/tmp/magpie-* /private/tmp/hunt*
# ⚠️ 里面若嵌了 go mod 缓存，同样 Permission denied，先 chmod -R u+w 再删
```

### Docker

```bash
# daemon 没运行时磁盘上也躺着 6.4G 的虚拟磁盘镜像；清镜像/容器要先把 Docker 启动起来
docker system prune    # ⚠️ 会删未使用镜像和已停容器，比清缓存激进，确认无要保留的镜像
```

| 位置                                           | 大小   | 原因                                             |
| -------------------------------------------- | ---- | ---------------------------------------------- |
| `/Library/Developer`                         | 1.8G | 是 CommandLineTools，git/编译器依赖                   |
| `~/Library/Containers/com.tencent.xinWeChat` | 3.8G | 聊天记录数据库，清缓存走微信设置页                              |
| `/private/var/folders`                       | 6.2G | 系统每用户缓存，重启自动清                                  |
| `/private/var/vm`                            | 1G   | 虚拟内存交换文件，系统管理                                  |
| `~/.Trash`                                   | 未知   | 终端被 TCC 拦（Operation not permitted），走 Finder 清倒 |
| `~/cc/guahub` 等源码目录                          | 25G  | 工作区不是缓存                                        |

## 清理结果

| 轮次 | 内容                                                              | 回收    |
| -- | --------------------------------------------------------------- | ----- |
| 1  | go clean -cache / npm / uv                                      | ~142G |
| 2  | pnpm 系 + go mod + gradle + bun + cargo + yarn + pip + ~/gocache | ~24G  |
| 3  | /tmp 任务残留 131G→0.2G + 两处 updater 缓存                             | ~49G  |

可用空间：12 GB → 244 GB（df 实测 227GiB，小组件按十进制 GB 显示为 244）。未动的决策项：Xcode 5G（无 iOS 开发数据可卸）、Docker 6.4G、fnm 旧版本。

## 关键结论

- **go mod 缓存只读权限坑出现两次**（`~/gocache` 和 magpie 工作区内嵌缓存同一种死法）：`rm -rf` 报 Permission denied，最后一条错误是误导性的 "Directory not empty"。固定解法 `chmod -R u+w && rm -rf`。
- **pip 自带的 purge 清不干净**：多版本 Python 下实测 882M 只清掉 159 个文件，剩余 793M 要整目录删。且机器上只有 `python3 -m pip`，没有 `pip` 命令。
- **zsh glob 无匹配会中止整条命令**：`rm -rf ~/A/*-updater ~/B/*-updater` 里 A 已被清空时，报 `no matches found` 后 B 也不会执行。混用「可能已空」和「确定存在」的 glob 要拆成两条命令跑。
- **GiB 和 GB 差 7.4%**：df/du 显示 227GiB，小组件显示 244GB，是同一状态的两套单位，不是清完又涨了。
- **删前两查（mtime + lsof）救过一次**：目标目录 22 分钟前还在被写入，等静止、退出所属应用后再删，避免打断在跑的任务。
- **/tmp 的 41G 全是后台自动化应用留下的**：系统 3 天自动清理管不住反复被触碰的目录，治本要在应用侧配任务级清理，否则还会长回来。

## 下次怎么用

- 磁盘告急时按固定顺序下钻：`df` 定水位 → `du -xsh ~/*`、`~/.[!.]*`、`~/Library/*` 三连扫 → 最大目录逐层下钻 → 按上表技术栈清单挨个清，全程只删可再生缓存。
- 删任何目录前过一遍安全三问：`go env` 确认缓存路径没被改过？mtime/lsof 确认没进程在写？是缓存/临时区还是工具链/数据库？
- 遇到 Permission denied 不要硬上 sudo：先想「是不是应用故意设的只读」（go mod 缓存），`chmod -R u+w` 就是正解，sudo 反而绕过了保护。
- 定期（每月）跑一次排查三连 + `pnpm store prune` + updater 缓存两连，把增长按在源头。
