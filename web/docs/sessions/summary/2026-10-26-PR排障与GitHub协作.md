# GitHub PR 排障与协作实战

**一句话总结**：用认证后的 `gh` 查询 PR、review 和 CI，先同步上游 `main`，再按 review 的证据修复、rebase、验证和推送，避免在旧代码上反复等 CI。

## 背景

这次处理了多个 Apache Maka PR：包括 `gh` 登录与代理、fork 同步、PR 合并状态查询、review 返工、CI 失败定位，以及 desktop 架构棘轮和 CLI 测试超时问题。最后确认有些 PR 是 CI 绿但等待 review，有些则被 review 的具体意见阻塞。

## 核心命令

```bash
export HTTPS_PROXY=http://127.0.0.1:<代理端口> HTTP_PROXY=http://127.0.0.1:<代理端口>  # 让 gh/git 通过本机代理访问 GitHub

"/c/Program Files/GitHub CLI/gh.exe" auth status  # 检查 GitHub 账号和 token 权限
"/c/Program Files/GitHub CLI/gh.exe" auth refresh -h github.com -s workflow  # 补充推送 workflow 文件所需权限
"/c/Program Files/GitHub CLI/gh.exe" auth setup-git  # 把 gh token 配成 git HTTPS 凭据助手

gh api repos/apache/maka/pulls/<PR号> --jq '{state,merged,merged_at,mergeable_state}'  # 查询 PR 是否合并、是否冲突

gh pr checks <PR号> -R apache/maka  # 查看 PR 的 CI 检查状态

gh run view <run_id> -R apache/maka --log-failed  # 查看 CI 失败日志

gh api repos/apache/maka/pulls/<PR号>/reviews  # 查看正式 review 和 CHANGES_REQUESTED

gh api repos/apache/maka/pulls/<PR号>/comments  # 查看代码行内评论

gh api repos/apache/maka/issues/<PR号>/comments  # 查看普通评论区消息

gh repo sync <个人账号>/maka --source apache/maka  # 将个人 fork 的 main 同步到上游

git fetch upstream main  # 拉取上游 main 的最新引用
git checkout main  # 切换到本地 main
git merge --ff-only upstream/main  # 只允许无冲突快进本地 main

git checkout -B <PR分支> origin/<PR分支>  # 从远程 PR 分支恢复本地分支

git rebase upstream/main  # 将 PR 分支重放到最新上游 main

git push --force-with-lease origin <PR分支>  # ⚠️ 强推 rebase 结果；只在确认分支归自己所有时使用

npm run astryx:surface-inventory:write  # 重新生成新增 UI 文件的 surface 清单
npm run astryx:surface-inventory  # 验证清单没有过期
npx @biomejs/biome check --write <改动文件>  # 格式化并检查指定文件
npm run build:workspace-deps  # 按依赖顺序构建工作区依赖
npm run build  # 构建当前包
node --test dist/__tests__/<测试文件>.test.js  # 运行编译后的指定测试
```

## 关键结论

1. 收件箱里的 PR 通知不是实时合并状态；合并状态以 `gh api repos/apache/maka/pulls/<PR号>` 为准。
2. `state=closed` 还不够，必须看 `merged_at`；`merged_at` 有值才是合并进目标分支。
3. `mergeable_state=blocked` 通常表示 CI 已过但缺 review 或批准，不等于代码有冲突；`dirty` 才优先处理 rebase。
4. `gh pr checks` 显示 `pending` 时，先用 `gh run view` 看 job 正在排队还是已经进入具体步骤，不要直接判断为失败。
5. 未认证的 GitHub API 很容易触发限流；登录后的 `gh api` 比匿名 `curl` 更适合批量查询。
6. GitHub CLI 不一定读取系统代理；通过代理访问时，要在同一条 shell 会话里设置 `HTTPS_PROXY` 和 `HTTP_PROXY`。
7. 推送内容涉及 `.github/workflows/` 时，token 需要 `workflow` scope；没有该权限时，`git push`、`gh repo sync` 和 API 更新分支都会被拒绝。
8. 公司项目和个人开源项目要用仓库级身份：`git config --local user.email "<个人邮箱>"`，不要改全局配置。
9. rebase 前先执行 `git fetch upstream main`，然后在 `main` 上 `git merge --ff-only upstream/main`；不要在 PR 分支上误执行快进合并。
10. 生成文件冲突不要手工拼接。以当前源码为准，重新运行生成器，再 `git add` 并继续 rebase。
11. desktop 的 renderer 架构检查对 legacy 文件实行单调棘轮：Hook、浏览器 API、依赖和 token 不能增加；改台账不能绕过对 base 源码的重新推导。
12. 这类 legacy 文件应把新增逻辑移到已有 feature 或共享 UI 包，并尽量复用已有 import 语句，避免新增依赖边和 token。
13. review 中指出的 fixture 与生产 wire 数据不一致时，优先修 fixture；测试通过不代表真实路径被覆盖。
14. `waitFor` 用墙上时钟限制测试时，要保留原测试的实际预算；原循环已有较长 sleep 或多次存储读取时，不能机械替换成更短的 5 秒。
15. 轮询超时要传具体 `message`，复杂断言应放进 catch 或保留在失败路径，否则最有价值的状态、请求和运行记录会变成无上下文的 `condition was not met`。

## 下次怎么用

1. 先读 `E:\cc\guahub\sessions\summary` 和项目实战文档，再检查工作区分支是否干净。
2. 执行 `git fetch upstream main`，确认 `main`、`origin/main`、`upstream/main` 的提交位置。
3. 用 `gh api` 查 PR 的 `merged_at`、`mergeable_state`、head SHA 和最新 review，不要只看通知列表。
4. 如果有 `CHANGES_REQUESTED`，先拉三类评论：reviews、inline comments、issue comments；按文件和行号核对当前代码。
5. 修复前确认 PR 分支已 rebase 到最新 `upstream/main`；解决冲突后重新生成清单和其他生成文件。
6. 只跑与改动相关的构建、格式检查和测试；全量测试失败时区分本次改动失败、平台限制和预存失败。
7. 推送后再查新的 CI run，并在 PR 评论中写明提交 SHA、修复点和验证结果。
8. 所有未验证的事项写“待验证”，不要把本地通过写成 CI 全绿，也不要把 CI 绿写成已经合并。
