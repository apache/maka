# 三仓 PR 维护轮命令与结论

**一句话总结**：一次跨 3 个开源仓库、24 个在途 PR 的例行维护轮（重基线 / rebase / 处置评审），沉淀出一套「自查 PR → 判冲突 → 安全改写历史 → 验证推送」的可复用命令与三条防假绿纪律。

## 背景

三个 fork 仓库各有 6~9 个 open PR 长期等审，需要定期：同步上游基线、解冲突、处置机器人与真人评审、确认 CI 真绿。本轮踩到的坑集中在「看起来成功、实际没成功」的假信号上。

## 核心命令

```bash
# 自查全部 open PR（四件套：标题/分支/head SHA/更新时间/mergeable）
gh pr list --repo <org>/<repo> --author <你的用户名> --state open --limit 100 \
  --json number,title,headRefName,headRefOid,updatedAt,mergeable

# 判 CI 绿之前，先核对 run 属于哪次推送：headSha 必须精确等于自己推的完整 SHA
gh run list --repo <org>/<repo> --branch <分支> --limit 3 \
  --json headSha,status,conclusion,databaseId

# 拉 PR 行内审查评论（看 diff_hunk 判断意见是否针对当前代码）
gh api repos/<org>/<repo>/pulls/<n>/comments \
  --jq '.[] | {user:.user.login, path, created_at, diff_hunk:(.diff_hunk[0:120])}'

# 查最新真实 APPROVED（页面上的 review 状态 flag 可能被 dismiss，REST 为准）
gh api repos/<org>/<repo>/pulls/<n>/reviews \
  --jq '[.[]|select(.state=="APPROVED")]|last|{user:.user.login,commit:.commit_id[0:10],submitted:.submitted_at}'

# 不动主工作区改代码：临时 worktree + 用完删除
git -C <仓库> worktree add /tmp/wt-<名字> <起点SHA或分支>
git -C <仓库> worktree list          # 检查残留
git -C <仓库> worktree remove /tmp/wt-<名字>

# 不 checkout 就预判合并冲突（干净则输出 tree 且退出码 0）
git merge-tree --write-tree <base分支> <head分支>

# rebase 后防补丁漂移：逐提交对比旧链 vs 新链，等号=补丁没变
git range-diff <旧base>..<旧head> <新base>..<新head>

# 解完冲突防字段静默丢失：编译过了也要 grep 关键字段有没有被截断
rg -n "<关键字段名>" <改动文件>   # 完整形如 Xxx: value}，残缺形如 Xxx} 就是丢了值

# ⚠️ 强推必须带 lease，期望值用 ls-remote 的完整 40 位 SHA（短 SHA 拼长必报 stale info）
git ls-remote origin <分支>        # 先取远端当前完整 SHA
git push --force-with-lease=<分支>:<远端完整40位SHA> origin "<新完整SHA>:refs/heads/<分支>"
# 风险：仍是改写远端历史；lease 只保证「没人比我先推」，推错分支照样覆盖

# 普通推送也用显式 SHA refspec，不依赖本地分支位置
git push origin "<完整SHA>:refs/heads/<分支>"

# 测试/typecheck 不接管道，落文件再看退出码
go test -count=1 ./pkg/... > /tmp/test.log 2>&1; echo EXIT=$?
grep -E "FAIL|^ok" /tmp/test.log
```

## 关键结论

1. **CI 绿 ≠ 我的提交绿**。旧 run 会挂在分支名下混进列表，判绿前必须核对 run 的 `headSha` 精确等于本次推送的 SHA，否则可能给一个早就红的旧结果「验尸假绿」。
2. **行级零冲突 ≠ 语义零冲突**。双方在同一段结构体字面量里各加字段时，git 能无冲突合并但会静默丢掉一侧（实测出现 `ExecutionSeq}` 这种缺值截断）。合并/rebase 后即使编译通过，也要 `rg` 抽查关键字段完整性，再用 `range-diff` 确认补丁没漂移。
3. **强推的安全姿势是 `--force-with-lease` + `ls-remote` 完整 SHA**。凭记忆或短 SHA 拼 expect 会直接报 stale info；lease 能挡住「覆盖别人刚推的提交」这类事故。
4. **管道会吞退出码**。`go test ... | tail` 里 `$?` 是 tail 的，测试红了也显示 0。固定写法 `> log 2>&1; echo EXIT=$?` 落文件再 grep，才是真结果。
5. **机器人审查报告可能藏在 check run 的 output 里**，`gh pr checks` 这类只看 conclusion 的列表会漏；评审真态用 REST `pulls/{n}/reviews` 核实，不信页面状态 flag。

## 下次怎么用

适合给自己的开源贡献做例行体检，五步一轮：

1. `gh pr list` 拉齐全部 open 单，逐单看 `updatedAt` 之后有无新评论（没变也不跳过）。
2. 对比上游分支（`git fetch upstream`），落后就用 worktree + `merge`/`rebase` 重基线，`merge-tree --write-tree` 先预判。
3. 解冲突后 `rg` 抽字段 + `range-diff` 验证，改动包测试落文件跑（`-count=1` 强制不用缓存）。
4. 推送：普通推显式 SHA；改写历史必须 `--force-with-lease=<分支>:<ls-remote 完整SHA>`。
5. 等 CI 出结果后，逐 run 核对 `headSha` 再宣布绿；同时用 REST reviews 确认审查真态。
