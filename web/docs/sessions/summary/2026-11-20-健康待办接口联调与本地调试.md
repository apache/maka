## Skill 增量建议（均未执行，待确认）

### 1. quality：无框架 TS 纯函数测试用 Node 原生 type-stripping

位置：`modules/quality/MODULE.md` 第 51 行「没有测试框架时复用当前可用工具或最小断言」处扩展。

现有缺口：只定了策略（最小断言），没定可落地的技术路径；无 jest/ts-node 时容易瞎猜或违规装依赖。

建议追加短文本：

> Node ≥23.6 原生剥离类型，无框架可直接跑仓库 TS 纯函数：`.mjs` 测试文件里 `await import(pathToFileURL('…/xx.ts'))`，node 断言库 assert 断言，不用装 ts-node/jest。约束：被测文件运行时只能依赖第三方包（node_modules 可解析）与 `import type`（会被整体擦除）；**凡是无扩展名的运行时相对导入（仓库 bundler 解析惯例）都让 node 解析失败**——纯函数须抽到零运行时相对导入的独立文件。类型无关的 MODULE_TYPELESS_PACKAGE_JSON 警告可忽略。

来源证据：本会话 18/18 测试全绿（`node .tmp-test/health-todo.test.mjs`），适配层为此从 request.ts 拆出零依赖的 adapters.ts。

检验场景：无 jest 仓库要测 TS 适配器——按此法直跑成功即有效；给被测文件加一条无扩展名相对导入再跑，应报错，即验证了约束。

### 2. api：契约「容器形态」矛盾的双形态归一

位置：`modules/api/MODULE.md` 反模式节，接在「同一语义两种键名在 mapper 一处读取」之后。

现有缺口：键名冲突已有规则，**容器形态**冲突（`data` 是数组 vs `data.list`）没有；「异常结构判失败而非伪装空列表」也没写。

建议追加短文本：

> 字段表与响应示例对容器形态各执一词（`data` 数组 vs `data.list`）时，适配层同时接受两种明确形态，其余结构返回失败信号（如 `ok:false`）交给页面走失败态，不得静默当空列表；实测确认真实形态后，提请后端把响应示例改成与字段表一致。响应里 `code !== 0` 同样按失败处理。

来源证据：69477 字段表写 `data: Array`、示例写 `data.list`，实测 data 是数组；normalizeListData 三态用例在 18 项测试中验证（数组过、list 过、`{data:[]}` 判失败）。

检验场景：mock 一个 `{data:[]}` 响应，走适配层应触发页面「加载失败+重试」而非渲染空列表。

### 3. dev/react：进行中去重按请求键，不用布尔标志

位置：`modules/dev/references/react.md`「数据编排 Hook」节，接在自增序号 ref 规则后。

现有缺口：并发竞态的 seq guard 已有（本轮 createSeqGuard 即其落地），但「同一入口 useEffect+useDidShow/useDidShow 类双触发导致的重复请求」怎么去重没有规则；布尔 in-flight 标志的反例是新增的。

建议追加短文本：

> 同参重复触发（挂载 effect 与页面 show 钩子同时发）按**请求键**（如 seniorId）做进行中去重：键相同跳过、键不同放行。不能用布尔 in-flight 标志——参数变化的刷新会被旧请求占位跳过，且完成回调被竞态守卫拦住不清理标志，后续所有刷新死锁。

来源证据：本会话第一版布尔标志实现自查发现死锁（A 在途切 B → B 被跳过 → A 回调不清理标志 → 后续全卡），改按 seniorId 去重后 eslint 通过。

检验场景：A 请求在途时切 B 长者——布尔版 B 不发请求且之后永久卡死；按键版 B 正常发出、A 响应被 seq 丢弃。

### 4. taro：wxa-runner 浏览器联调反馈环

位置：`modules/taro/MODULE.md`「开发顺序」节末尾追加。

现有缺口：taro 模块有构建与验收判定，没有「小程序产物跑进浏览器抓真实请求」的工具链；curl 无登录态只能拿 403 时，这是唯一真实证据来源。

建议追加短文本：

> 联调反馈环：终端 A `npm run <项目构建脚本> -- --watch`，终端 B `npx wxa-runner dev <outputRoot>/ -o`（先核项目 outputRoot，别照搬 dist）；浏览器 Network 抓登录态下的真实请求/响应——curl 只能拿到鉴权失败时，这是唯一真实证据环；响应里的 traceId 直接给后端查日志。已知沙箱兼容缺口：残缺 window 对象（业务代码 `window.addEventListener` 判断为真后崩溃）、子包加载器报 unexpected loadSdkSubPackage（均来自 2026-11-09 wxa-runner 会话，二手）；预览/上传/真机调试仍走微信开发者工具。

来源证据：本会话用它拿到 69477 真实形态（data 数组）与 69476 的 500+traceId；curl 同接口无登录态只返回 code:403。

检验场景：同一接口 curl 得 403、wxa-runner 浏览器里登录后抓到业务响应，即证明该环不可被 curl 替代。

## 可复用经验与案例

- **分条提问的实际效果**：一条 5 模块大消息后端只回了一半（3/5）；改成一个模块一条消息、每问给选项、✅/⏳/❗分级后可逐条引用回复。已闭环项写明证据（实测响应）不再追问，避免反复问。
- **「已发测试」≠「已修复」的实证路径**：后端说已发测试环境，无登录态 curl 只能拿 403；换 wxa-runner 浏览器环才拿到真实响应——一好一坏（measurePlan 200 正常、servicePlan 500），各自形成独立结论。
- **mock 常驻价值**：`USE_MOCK` 开关保留在请求层（false 走真实），接口 500 时前端页面走「加载失败+重试」不白屏；mock 数据同步维护枚举值，切回真身零成本。
- **产品决策即时清码**：核销码「本期不做」确认后立即删 VerifyDrawer、QR 入口、verifyCode 字段（git rm 可回滚），不做「留着以后用」的死代码。
