# 跨端预约冲突验证与归属

## 一句话结论

APP 预约后 Web 重复预约的缺陷，验收要让 APP 实际创建占用、由 Web 提交同一资源的重叠时段，并核对业务拒绝、写入结果和提示次数。Web→Web 复测只能证明当时该环境下的 Web 路径。

## Skill 增量建议

| 项目 | 内容 |
| --- | --- |
| 目标与缺口 | `gua-dev-tools/modules/quality/references/verify.md` 的真实数据验证。现有 L4 要求接真实接口，`bug/MODULE.md` 已要求核对动作后新增请求及参数。可补跨端写入冲突的最小证据组合。 |
| 建议追加 | 跨端占用、配额等写入约束，按缺陷指定的来源端创建基准记录，再由目标端用相同业务键与冲突条件发起写入。核对实际请求、业务响应及回读状态；涉及提示时，记录一次操作对应的请求数和提示数。单端同类复测单独报告。 |
| 证据与边界 | 本次 Web 预约的第一次 `add` 成功，第二次返回 `572014`，原单描述的触发顺序却是 APP→Web。该判据用于共享业务约束，普通单端表单不必补跨端测试。提交前读列表可以改善交互，并发写入是否受约束仍需要服务端证据。 |
| 检验场景 | 只有 Web→Web 重叠被拒时，结论应为「Web→Web 已验证，APP→Web 待验证」。补齐 APP 写入、Web 冲突请求及回读无新增记录后，才能标记该方向通过。此规则检验未执行。 |

## 可复用经验与案例

- **先核对实际提交值，再归因。** 时间控件显示 `10:30`，但 `update` 抓包（请求 270）实际发出 `11:00:00`，与前一段首尾相接。返回成功只说明该次请求被接受，不能用于判断后端是否拒绝重叠。重新从选择面板确认时间后，验证到前端预检弹出冲突提示；该次由前端拦截，仍未覆盖后端 `update` 的重叠分支。现有 `bug/MODULE.md` 已覆盖这条规则，本例作为执行反例。
- **同时观察请求和提示。** 同一次冲突操作的短时 DOM 采样抓到顶部 `message` 和右上角 `notification`，两处展示同一文案。新增 `message.error` 的来源可从页面 diff 确认，右上角通知的具体调用方和部署环境行为未证实。双请求、双提示是两个独立观察项，单凭截图不能互相归因。
- **历史排查的结论限定在证据范围内。** `git show` 核实模块初版保存直接调用新增接口且失败处理为空。模块提交列表与关键字搜索未发现相关实现线索，但历史搜索中的 `-S` 默认按字面匹配，把多个名称用 `\|` 拼起来不能视为正则穷举。前端历史也无法证明同期后端有没有拦截。
- **撤期要核对补丁和工作区两边。** 产品决定延期后，路径限定的 `git stash push -u` 收走了页面、未跟踪的工具文件和临时测试。`git stash show -u --stat` 显示三项均在贮藏中，`git status --short` 显示其他本地改动仍在。相同命令已在既有笔记中归档，本次保留双向回读的结果。

## 待验证与不适用边界

用户提供的原单截图报告 APP→Web 发生重叠，现场复测只证明 Web→Web 被拒。原单发生时后端为何放行、当前 APP→Web 是否通过、修改接口如何处理真实重叠，以及右上角通知的上线行为，均未闭环。历史工具输出可见，当前后端源码与部署态未复查。延期补丁按本轮最后的 Git 工具回读仍在当时的贮藏记录中，本次归档未复查其当前状态。
