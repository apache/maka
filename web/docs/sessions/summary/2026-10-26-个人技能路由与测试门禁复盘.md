# 个人 Skill 路由与测试门禁复盘

**一句话总结**：用真实任务话术改进 Skill 路由，并把“需要做哪些验证”与“测试文件是否入库”分开；静态检查不等于自动触发已验证。

## 背景

个人 Skill 的使用占比只有 43/240，部分 description 写满内部实现名词，难以匹配日常提问。通用测试规则又曾要求测试随代码提交，与项目规定的本机测试策略冲突。

## 核心命令

```bash
git -C "<仓库目录>" status --short -- "<Skills目录>" # 查看本轮 Skill 文件是否还有未提交改动
git -C "<仓库目录>" diff --cached --name-status -- "<Skills目录>" # 单独核对暂存区；--cached 只看待提交快照
rg -n -g SKILL.md "<项目名>|<模块名>" "<Skills目录>" # 查通用规则中残留的项目事实，迁往项目专属资料
```

## 关键结论

1. **18% 是使用占比，不是路由准确率。** 要判断触发是否改善，需用真实用户原话核对“应触发”和“实际触发”，不能只看调用总数。
2. **description 写意图和近邻边界，内部方法名留正文。** “小程序取不到时长”“真机上不一样”比 SDK 方法名更贴近日常提问；审 PR 直接交审查 Skill，不让工程决策 Skill 抢入口。
3. **验证要求与测试资产留存是两回事。** 先按风险决定写、跑哪些测试，再依项目约定决定 tracked 或 local-only。本机测试仍要运行；提交前用暂存区清单确认它没有被加入。
4. **静态通过不等于真实路由通过。** 本轮曾更新规则与 eval 用例并运行静态校验，但没有完成足以支持“自动触发达到 97%”的模型级回归；第二轮合并也不能按目标数量强推。
