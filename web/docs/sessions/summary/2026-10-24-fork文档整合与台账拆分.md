# fork 文档整合与台账拆分

**一句话总结**：把 magpie 的回合处置、第三方补丁对照、文档迁移和台账拆分做成一套可复用流程——核心是"先核实再落笔、行原文不丢、坏档就恢复重跑"。

## 背景

一轮长会话里完成了：magpie 多轮 A 类回合处置与狩猎交付（hunt64–73）、跨仓贡献文档两次迁移（guahub/docs/fork → fork/docs）、接单总台账 182 行按仓拆分，以及 fork/AGENTS.md 工作规范固化。

## 核心命令

```bash
# 批量扫描 issue 最新评论者（回扫 A/C 类，5 线程并发）
gh api "repos/OWNER/REPO/issues/N/comments?per_page=100" \
  --jq 'if length>0 then .[-1].user.login else "(none)" end'

# patch 三级校验：干净可套 / 仅上下文漂移 / 真冲突
git format-patch <基点> -1 --stdout > fix.patch
git apply --check fix.patch || git apply --check --3way fix.patch

# 组合验证：把对方 patch 叠我方 patch，两族测试同树跑
git cherry-pick <对方提交>   # 零冲突即互补可共存
go test -tags nogui -race -count=1 -run 'TestA|TestB' ./internal/...

# rebase PR 分支到新基线；完成后必须用显式 SHA 推送
git rebase --onto <新基线> <旧基点> origin/<分支>
git push origin <新sha>:refs/heads/<分支> \
  --force-with-lease=refs/heads/<分支>:$(git ls-remote origin refs/heads/<分支> | cut -f1)

# 编辑已发布的 GitHub 评论（POST 响应解析失败≠没发，先 GET 核实再 PATCH）
gh api repos/OWNER/REPO/issues/comments/<评论id> -X PATCH -F body=@draft.md

# md 大表格按行拆分（openpyxl/md 通用：收集与写回列起点必须一致）
git checkout -- 坏档文件        # 改坏就恢复重跑，不手工修补
```

## 关键结论

1. **GitHub 评论 POST 响应解析失败 ≠ 没发成功**——先 GET 评论列表核实（看作者与长度），确认未发才重发；本轮一次"解析失败"实际已发出。
2. **rebase 在 detached HEAD 完成后，推送必须用显式 SHA**——本地分支可能停在旧位置，`branch -f` 对已检出分支会失败且易被吞掉，导致把过期版本推上去（本轮倒退约 2 分钟后闭合）。
3. **GitHub 无认领机制，take 不产生排他权**——事实规则是先落地者得；take 只是自设纪律（防多会话撞车+意向信号），交付速度才是护城河。
4. **台账"已发布"必须以 issue 实况核验**——评论数 c=0 加 timeline 一查便知从未发过；被删评论不留痕，无法区分"从未发"与"发后删"。
5. **报告者自带的 patch 不是终点**——跑全量而非定向 `-run`，可能抓出其破坏的既有测试（#3380 实例）。
6. openpyxl 定向更新三坑：收集行与写回的列起点必须一致（min_col=2）；"合计"脚注行会混入 max_row 计数；改坏就 `git checkout --` 恢复重跑。

## 下次怎么用

- **多仓维护轮**：开场全量回扫（A 表 + 近期交付帖逐单取最新评论者），非我方尾评的才需要动作；已关闭单的"回合确认"行直接跳过。
- **第三方 patch 已占坑的单**：走对照矩阵——读 diff → 消融红/恢复绿 → 组合态两族测试 → rebase 可应用性 → 让位帖附验证表；覆盖判定以 diff 为准，不以任务书预设为准。
- **判定设计内**：探针实测证明无缺陷（如三次请求全达上游、标准错误透传），降级诊断帖，不硬凑 patch。
- **大 md 表格拆分**：python 按 `| <数字>` 识别数据行、收集与写回同列起点、行数守恒+去重校验双保险；改坏立即 `git checkout --` 恢复重跑。
