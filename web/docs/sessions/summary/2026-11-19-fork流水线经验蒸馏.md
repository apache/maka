## 可复用经验与案例

- **严格零值门控**（cockpit #2690）：报告者明确警告「不要把缺字段一律填 0%」→ 修法用三条件形状门控（计费周期锚点 + onDemand 双键 + credit bag 来源全缺）才补 0，形状未知保持 None。判定锚点不是 schema 而是报告者自己的同凭据双端对照行为（CC Switch 对同一响应渲染 0%）。模式：缺字段≠零值，补零必须锚定「完整形状 + 外部行为对照」，反例用例守「不发明数据」。适用：任何「字段省略 vs 显式零」歧义的 API 解析面。
- **三层语义漂移检查**（cc-switch #7760）：merge-tree 全净 → 文件交集（`comm -12`）→ 交集内按标识符 `-S` 核对提交命中。本轮第二层唯一命中（Stack mode JSX 搬迁），第三层定案正交（handleFetchModels 零提交命中）。M12 的可执行化序列。
- **开场 GraphQL 一体化批查**：per-repo alias 一次拉 state/head/mss/reviews/threads/comments，配合 fragments 文件拼接。本轮 26 PR + 3 issue 一轮扫完，零新事件判定靠 `updatedAt` 全早于已知时点。模板见命令节。
- **路径迁移后的 worktree 腐烂**：目录迁移使 worktree 记录 prunable（`git worktree list` 显示 `prunable`），`git worktree prune` 一条清掉；快照文档里引用旧扫描 worktree 路径的条目随快照刷新一并清理，长期纪律挪进「开场流程」节防止随快照丢失。

## 常用命令（本会话实际执行、有可见结果）

```bash
# 1. GraphQL 批查（fragments + per-repo alias 一次拉全状态；注意 -F 不是 -f）
gh api graphql -F query=@q1f.graphql          # q1f.graphql = fragments + 查询体拼接

# 2. issue 占用时间线探针（钉 self-assign 时间，比评论区可靠）
gh api repos/<owner>/<repo>/issues/<N>/events \
  --jq '.[] | select(.event == "assigned") | "\(.created_at) \(.actor.login) -> \(.assignee.login)"'

# 3. merge-tree 批量探冲突（rc=0 净 / 非 0 冲突）
for b in <分支...>; do git merge-tree --write-tree upstream/main "origin/$b" >/dev/null 2>&1 && echo "$b clean" || echo "$b CONFLICT"; done

# 4. 分支改动文件 ∩ 上游 range 文件（M12 第二层）
comm -12 <(git diff --name-only upstream/main...origin/<分支> | sort) \
         <(git diff --name-only <旧..新> | sort)

# 5. fork PR 开单（裸分支名 422；cherry/cockpit 双仓实测）
gh pr create --repo <upstream> --base main --head <fork>:<branch> --title "..." --body-file <file>

# 6. Rust 模块级测试（cargo 只接受一个 TESTNAME 位置参数，两个过滤词会报 unexpected argument）
cargo test --lib grok_account
```

前提与副作用：1-4 依赖已 `fetch upstream`/`fetch origin`；5 需要 gh 认证账号（本机 gh 全路径 `"C:\Program Files\GitHub CLI\gh.exe"`）且 body 用文件避免转义；6 前需 `eval "$(fnm env)"` 且在本机 SxS 负缓存环境对重编译的测试 exe 先补旁车 manifest + `touch` exe（cockpit 特有，见其 README）。
