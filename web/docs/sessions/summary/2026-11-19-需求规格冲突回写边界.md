# 需求规格：冲突先待确认，再写入正文

## 一句话结论

用清单定范围、用 PRD 定行为、用原型补已画出的交互。和 PRD 明确句冲突的建议只放待确认表，确认前不写进规格正文，也不改 PRD。用户选定维持原文后，否决方案只留记录。

未改任何 Skill。下列两条现有规则没写到「规格正文」这一层；不追加同义的「不要自行裁决」。

### 1. 冲突建议的存放位置

- 位置：`gua-dev-tools` `modules/prd/MODULE.md`「范围与证据」末尾追加一句。不进 `gua-pr-patch`，也不进 `gua-writer`。
- 现有规则：`references/delivery-workflow.md` §1 已写「PRD/产品确认决定业务行为，原型只证明明确展示的交互」；§5 已写「与已明确需求冲突时请产品确认，不自行裁决，未决项不要宣称解决」。
- 缺口：没规定未确认文本不能变成规格里的规范性需求。本会话曾把「无有效机会时经营计划仍展示」写成正文规则，用户要求先撤回。
- 建议追加：写产品规格时，清单定本期条目。与 PRD 明确句不冲突、且已经确认的口径写入正文。冲突项用四列表待确认：原文、当前建议、影响、确认口径。确认前不标已解决，不改 PRD 行为。选定维持原文后，否决建议只留记录。用户点名的章节号、残留句、清单字段可以改，且只改被点名的字。
- 证据：用户消息「先别全部回写……不要标记为已解决，也不要直接修改 PRD」；随后 X-12、X-13 选口径 A，正文 `FR-071`、`FR-076` 按 PRD 10.4.6 / 10.6.3 执行。PRD 第 9 章标题、9.1 残留句、10.3.2 引用、10.6.5 编号，以及清单 B16/D16，是另一次点名后才改的。

## 可复用经验与案例

### 规格正文和待确认表分开

- 触发：清单、PRD、原型对同一页不一致，需要先出一份可评审的规格。
- 证据：用户两次收紧回写范围。第一次只允许写入与 PRD 不冲突的结论；第二次明确无机会时的成交目标和接待方案按 PRD 整块「暂无可参考内容」。
- 做法：正文只保留已选口径。被否决的降级方案留在「已关闭」记录里，不写成 MUST。
- 取舍：新客详情页会整块空白。用户接受，并说明以后若要优化，单独走 PRD 变更。
- 验证：规格内 `FR-071`、`FR-076` 与 PRD 原句一致。未对照实现代码，也未跑页面。

### 点名勘误不等于授权改行为

- 触发：PRD 引用了错误章节，清单把「接待方案依据」记到「客户经营计划」。
- 做法：只改标题、9.1 残留的「最近沟通时间」、10.3.2 的章节号、10.6.5 的编号，以及清单 B16/D16 的模块名。
- 验证：改完后用 Python 读回 B16/D16，均为「建议接待方案——接待方案依据」。需求含义没有改。

## 常用命令

### 读或改 xlsx

- 场景：读取工具拒绝 `.xlsx`，或要改清单里某一格。
- 前提：本机已有 Python 与 `openpyxl`。路径含中文时先把标准输出设成 UTF-8。
- 命令：

```powershell
python -c "import sys; sys.stdout.reconfigure(encoding='utf-8'); import openpyxl; wb=openpyxl.load_workbook(r'<xlsx>'); ws=wb['<sheet>']; print(ws['B16'].value)"
```

- 成功信号：终端打出单元格原文。写回后要再读一遍同一格。
- 副作用：`save` 会改原文件。只在用户点名该格时写。

### 需求仓第一版提交

- 场景：目录还不是 git 仓库，用户要求把当前内容作第一版提交。
- 前提：先写根 `.gitignore`，至少忽略 `.env`、`.env.local`、`node_modules/`。嵌套目录自带忽略不够覆盖技能目录里的密钥文件。
- 命令：

```powershell
git init
git add -A
git diff --cached --name-only
git commit -m "<用户给出的说明>"
git status
```

- 成功信号：本会话为 `9b196ee`，116 个文件，`nothing to commit, working tree clean`。暂存名单里没有 `.env` 或 `node_modules`。
- 副作用：`git add -A` 会收进未被忽略的全部文件。提交前用名单核对密钥。未推远程。
