# 贡献计分与 gh 排查命令

**一句话总结**：整理 magpie 贡献狩猎里真正可复用的东西——GitHub 贡献计分的实测规则、批量扫描自己参与 issue 的 gh/python 命令、以及 Windows 下 Go 测试环境的两个坑。

## 背景

一轮多波次的 GitHub issue 狩猎收尾后，需要回答三件事：我的补丁到底有多少合进了上游 main、贡献值为什么没涨、以及怎么批量核对两百多个参与 issue 的最新回合。过程中顺带踩了 Windows 环境的几个坑，一并记下。

## 核心命令

### 1. 统计自己在上游 main 的署名提交

```bash
git fetch origin main
# 作者署名的提交（author 邮箱 = 自己）
git log origin/main --author="ggbdpq" --format="%h %as %s"
# co-author 署名的提交（trailer 写在 commit message 里，--grep 能搜到）
git log origin/main --grep="Co-authored-by: ggbdpq" --format="%h %an %as %s"
# 两路去重计数
git log origin/main --author="ggbdpq" --format="%H" > /tmp/a.txt
git log origin/main --grep="Co-authored-by: ggbdpq" --format="%H" >> /tmp/a.txt
sort -u /tmp/a.txt | wc -l
```

### 2. GraphQL 分页批量扫描自己参与的 issue（状态 + 最后评论者 + 时间）

```python
# scan-participants.py —— 3 页搜索拿全，比 REST 逐 issue 查省几十倍调用
import json, subprocess
GH = r"C:\Program Files\GitHub CLI\gh.exe"   # 旧会话 PATH 不刷新时用全路径
Q = """query($q:String!,$cur:String){ search(query:$q, type:ISSUE, first:100, after:$cur) {
  issueCount pageInfo{ hasNextPage endCursor }
  nodes{ ... on Issue{ number state comments(last:1){ nodes{ author{ login } createdAt } } } }
} }"""
rows, cur = [], None
for _ in range(6):
    args = [GH, "api", "graphql", "-f", "query="+Q, "-f", "q=repo:yetone/magpie commenter:ggbdpq"]
    if cur: args += ["-f", "cur="+cur]
    s = json.loads(subprocess.run(args, capture_output=True, text=True, encoding="utf-8").stdout)["data"]["search"]
    rows += [{"n": n["number"], "state": n["state"],
              "last": (n["comments"]["nodes"] or [{}])[0]} for n in s["nodes"]]
    if not s["pageInfo"]["hasNextPage"]: break
    cur = s["pageInfo"]["endCursor"]
```

注意 `createdAt`（驼峰），写成 `created_at` 会静默拿到 None。

### 3. 搜索口径的差异

```bash
gh api "search/issues?q=repo:yetone/magpie+involves:ggbdpq+state:open&per_page=100" --jq '.items[].number'
# involves 含「只发过 issue 没评论过」的单；commenter: 会漏掉这类 author-only 参与
```

### 4. jq 取最后一条评论

```bash
# 正确：.[-1] 取最后一个元素
gh api repos/OWNER/REPO/issues/N/comments --paginate --jq '.[-1] | "\(.user.login) \(.created_at)"'
# 错误：.[-1][] 会把评论对象的每个字段当行遍历，报 expected an object but got: string
```

### 5. 不加 remote 按 URL fetch / 安全强推

```bash
git fetch https://github.com/<user>/<repo>.git <branch>     # 临时取他人 fork，不污染 remote 配置
# ⚠️ 强推会覆盖远端分支；--force-with-lease 带「远端仍是旧 SHA」的前提，别人先推过则拒绝
git push --force-with-lease=<分支>:<旧SHA> https://github.com/<user>/<repo>.git HEAD:refs/heads/<分支>
git ls-remote https://github.com/<user>/<repo>.git <branch>  # 推完终验远端 head
```

### 6. Windows 跑 go test -race

```bash
export PATH="/d/DevTools/Env/mingw64/bin:$PATH"   # gcc 不在默认 PATH
export CGO_ENABLED=1                               # go env 里默认是 0，必须显式开
go test -race -tags nogui -count=1 ./internal/xxx/
```

### 7. openpyxl 改 xlsx（读行定位 → 改单元格 → 存）

```python
import openpyxl
wb = openpyxl.load_workbook(r"E:\...\表.xlsx")
ws = wb["某sheet"]
for r in range(5, ws.max_row + 1):
    if ws.cell(row=r, column=2).value == 目标值:      # 找行
        ws.cell(row=r, column=11, value=新值)          # 改列
wb.save(r"E:\...\表.xlsx")
```

## 关键结论

1. **贡献计分只认 commit，其他都不认**：commit 落在上游仓库默认分支才计分（fork 里的 commit 永远不计，哪怕别人在 fork 里给你写了 co-author）；`Co-authored-by` 里的 `ID+用户名@users.noreply.github.com` 是账号内置地址自动关联、必然计分，普通邮箱（如 gmail）必须先在 Settings → Emails 里验证才计；评论里的文字致谢、@提及、issue 开关状态一概与计分无关。开 issue 本身计 1 次 contribution，评论不计。
2. **`git fetch` 失败要看 stderr，ref 存在≠新鲜**：一次 `git fetch upstream` 静默失败（根本没配这个 remote），而陈旧的 `upstream/main` ref 还在，`rev-parse` 照样有输出——整个基线错了一天（上游实际前进 400+ 提交）。开工基线和发帖前查重必须分层，以刚 fetch 过的 ref 为准。
3. **「工具不可用」的结论要带实测输出**：本机其实有 gcc（在非 PATH 目录）且 `-race` 可跑，三个并行任务只试了 `gcc --version` 就写下「无 C 编译器」，帖子发出去才发现要 PATCH 更正。判断环境能力前先查非 PATH 安装位置和 `go env` 里的显式配置（如 `CGO_ENABLED=0`）。
4. **回归测试回退要连「随签名改的旧测试文件」一起回退**：只回退产品文件时，被新签名改过的既有测试会编译失败——build failed 不是行为级 RED。正确口径：产品文件+被适配的旧测试文件一起回退，只保留新增测试，跑出断言级失败才算数。
5. **上游收编有两种形态，署名都看 commit 不看帖子**：一种是 `git am` 原样收编（author/Co-authored-by 进 git 历史），一种是维护者按你的分析自己写实现（credit 只出现在 commit message 和跟帖文字里，无 trailer）——后者对贡献计分的价值取决于收编进 main 的那个 commit 用不用你的署名。
