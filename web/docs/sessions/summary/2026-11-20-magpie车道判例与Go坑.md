## Skill 增量建议（均未执行修改，待确认）

### 1. gua-pr-patch · references/delivery.md:61 附近（format-patch 陷阱补一变体）

- 现有规则：`-1` 只对单提交分支安全——多提交分支上 `-1` 取栈顶提交。
- 缺口：单提交分支的 `<base> -1` 变体未覆盖。`git format-patch <base> -1 --zero-commit` 把 base 当作要格式化的提交，产出 base 自己的 patch；干净树 am 到 base 必失败。本会话三现（主线程 #5521/#6851、R1 #7139 均首跑中招后改 `format-patch -1 HEAD`）。
- 建议追加（接在该行后）：「单提交分支也别写 `<base> -1`：base 被当成待格式化提交，产出 base 自己的 patch；用 `format-patch -1 HEAD` 或 `<base>..HEAD`。」
- 检验场景：对单提交分支执行 `format-patch <base> -1 --zero-commit`，产出的 patch subject 是 base 的 subject 而非本单的——写错形态可被此断言拦住。

### 2. gua-pr-patch · references/workflow.md:101 附近（超时预算补充休眠截断判据）

- 现有规则：Go 大包全量显式带 `-timeout 45m`（三现 panic 属跑法参数非产品红——重跑出真结果）。
- 缺口：桌面机**休眠会吃掉墙钟预算**——测试健康的跑也会被截断成假 panic。本会话实证：#6851 首跑 45m 被夜间休眠吃掉（截断），120m 重跑 1458s 完整；R1 #6602 过夜墙钟 21022.7s 无 panic（完整但被拉长，须披露）。
- 建议追加：「长跑在桌面机遇到 timeout panic 先分『真慢』与『休眠截断』：加大预算重跑（gateway 级 120m），并以 `panic: test timed out` 计数=0 判定完整性；墙钟被休眠拉长的完整跑照常算数但披露时长。」
- 检验场景：同一 head 两次全量，一次 panic 一次不 panic 且 panic 次数>0 的那轮红名单缺尾部测试——即截断特征。

### 3. gua-pr-patch · 署名铁律（pitfalls.md 或 SKILL.md 署名节）：user.name 复发损坏

- 现有规则：全局 AGENTS.md 有「新 clone 解析异常先 `git config --show-origin user.name user.email` 核对来源」。
- 缺口：本会话实证该损坏会**复发**（开工修好 magpie 主 clone，次日 magpie-pr2 又变回字面量 `user.email`，根因未明）；车道开工自查+提交用 `git -c user.name=ggbdpq -c user.email=ggbdpq@gmail.com commit` 双保险（R2 实证：共享配置坏时其提交仍干净）。
- 建议追加：「共享 clone 的 user.name 会复发损坏（出现过写成字面量 user.email 的案例）：每车道开工自查 `git config user.name`，提交一律加 `-c user.name=ggbdpq -c user.email=ggbdpq@gmail.com` 前缀双保险；push 前 `git log -1 --format='%an <%ae>'` 复核。」
- 检验场景：把本地 user.name 改坏后走一遍自查+`-c` 提交，push 后 GitHub 上 author 仍是 ggbdpq。

## 可复用经验与案例

### Go sync.Map 键字节变异 → HashTrieMap panic（#6986，判定帖 6994205698）

- 触发：把「底层可被改写的字符串」当 sync.Map 键（本例：usage 查询的 memo 缓存账本行串，而行串有意共享打包缓冲）。
- 机理（读 Go 工具链源码钉死）：`internal/sync/hashtriemap.go:169` 的 `expand()` **用键的存活字节重算 stored hash**——键字节被原地改写后，其后插入的「同内容新串」会在 expand 里撞出 `oldHash==newHash`，即 :181 的 `ran out of hash bits while inserting (incorrect use of unsafe or cgo, or data race?)`。
- 探针方法论：**朴素污染测试测不出来**——Load 按“当前字节”的哈希寻路，变异后条目只是失联，行为看起来正常；能稳定观察的是「同内容新串再插入」触发的 expand 撞击（确定性 panic 需哈希前缀巧合，生产上是概率事件：12 次/数月）。
- 修法：缓存边界 `strings.Clone(key/value)`（一行加固）；panic 本身无法确定性复现（报告者/#6123 作者/本会话三方未复现），不发不可红测的 patch。
- 下次复用条件：任何「sync.Map/缓存键来自共享缓冲」的场景出现该 panic 字样时，先查键的字节可变性，再查数据竞争。

### 判定帖出口的实证形态（4 例）

不可真机复现的单（#6986 panic/#6980 跨应用图形冲突/#6862 桥 Plan 流程/#6895 机制考古）统一走判定帖：verified=代码事实带 file:line；分叉摆明；向报告者要的数据列清单（A/B、内层工具列表、dump 模块名等）；Not verified 首位。比硬凑 patch 交付质量高且维护者可读。gua-pr-patch 既有规则已覆盖此出口，此处仅记案例。

## 常用命令

### GitHub issue 末评批量扫描（GraphQL 别名批查）

- 场景：一次核几十个 issue 的 state+末评作者/时间/摘要（老单对账、防竞速）。
- 前提：gh 已认证；**本机无 jq，用 gh 内建 --jq**。
- 命令（/tmp/lastcheck.sh 终版）：

```bash
q='{ repository(owner: "OWNER", name: "REPO") {'
for n in $nums; do q="$q i$n: issue(number: $n) { state comments(last: 1) { nodes { author { login } createdAt body } } }"; done
q="$q } }"
gh api graphql -f query="$q" --jq '.data.repository | to_entries[] | {num: .key, state: .value.state, id: (.value.comments.nodes[0].databaseId // 0), a: (.value.comments.nodes[0].author.login // "NO_COMMENTS"), b: ((.value.comments.nodes[0].body // "")[0:110])}'
```

- 成功信号：每行一个 issue 的 state+末评；NO_COMMENTS 标记零评论单。注意 body 可能为 null（无评论），jq 要 `// ""` 兜底。

### patch 交付验证链（format-patch → 干净树 am → 树比对）

- 场景：patch 帖发布前的「git am 即进」证据。
- 前提：**Windows Git Bash 里 python 读不到 bash 的 /tmp**（python.exe 按 Windows 路径解析 /tmp）——跨 bash/python 的文件一律用 Windows 真实路径（如 C:/Users/<user>/AppData/Local/Temp/...）。
- 命令：

```bash
git format-patch -1 HEAD --zero-commit -o /tmp/amN   # 单提交分支用 -1 HEAD，禁 <base> -1
sha256sum /tmp/amN/*.patch | cut -c1-16               # 帖内 sha256[:16]
git checkout -B amtest <base>                          # base=当前 upstream/main
git -c user.name=ggbdpq -c user.email=ggbdpq@gmail.com am /tmp/amN/*.patch
[ "$(git rev-parse HEAD^{tree})" = "$(git rev-parse <branch>^{tree})" ] && echo TREE-IDENTICAL
git checkout --detach <回到原位> && git branch -D amtest
```

- 成功信号：`TREE-IDENTICAL` + am 退出码 0；失败信号：am exit 128（patch 与 base 不匹配）。

### 长跑测试完整性判定

```bash
go test -tags nogui -timeout 120m -count=1 ./internal/gateway/ 2>&1 | tee run.log
grep -c 'panic: test timed out' run.log   # 必须=0 才算完整跑；>0=截断，加大预算重跑
grep -cE '^--- FAIL' run.log              # 红名单逐个 base/tip 对照归因
```

- 前提：`GOPROXY=https://goproxy.cn,direct` 前缀（直连官方 proxy 超时的机器）；单机同时只跑一套全量。

### ls-remote 陷阱

- `git ls-remote origin <branch1> <branch2>` 的输出**顺序不保证与请求一致**——核对多分支 SHA 时必须连 ref 名整行读，按行序对号会张冠李戴（本会话误读一次导致车道进度误判）。
