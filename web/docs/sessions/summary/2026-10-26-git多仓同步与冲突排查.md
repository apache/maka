# Git 多仓同步与 PR 冲突排查实战

**一句话总结**：一条 fork 仓库日常维护的命令链——同步上游、无副作用预演合并冲突、用 gh API 查 PR/CI 真相，外加两个"代码没错却编译报错"的真根因（tsbuildinfo 增量缓存、ignore-scripts 跳过补丁）。

## 背景

维护一个 fork + 多个本地 clone 的开源仓库（apache/maka），日常要：同步上游到本地和远端 fork、推送 PR 前确认与最新 main 无冲突、判断 CI 红是自己改坏还是上游传染，以及排查一批"类型缺字段/缺导出"的编译假错。

## 核心命令

```bash
# 同步上游并快进本地 main（ff-only 防止意外产生合并提交）
git fetch upstream main && git merge --ff-only upstream/main

# fork 的 main 上有分叉的废弃提交时，对齐到上游（先用 git show 核对再推）
git push --force-with-lease=main:<远端当前sha> origin upstream/main:main
# ⚠️ 强制推送变体：lease 钉住期望的远端 sha，若别人已推进会被拒绝，防误覆盖

# 不碰工作树，预演"我的分支合入最新 main 会不会冲突"（PR 的 CI 跑的就是合并预览树）
git merge-tree --write-tree <我的head> upstream/main
# 只输出一个 tree oid = 无冲突；输出 CONFLICT 块 = 冲突文件清单

# 推送前自证无空白符/文件尾空行问题（CI 的 diff-check 同款，1 秒钟的事）
git diff --check upstream/main HEAD

# 查一个符号的死活：issue 里引用的函数还在不在当前代码里（issue 常漂移）
git log -S <符号名> --oneline --all

# 查 PR 状态与 CI 结论（gh 已登录；--jq 直接出摘要，避免翻原始 JSON）
gh api repos/<owner>/<repo>/pulls/<n> --jq '{head: .head.sha[0:9], ms: .mergeable_state}'
gh api repos/<owner>/<repo>/commits/<sha>/check-runs --jq '[.check_runs[] | {name, c: (.conclusion // .status)}]'

# 查某次合并是谁合的（列表接口不返回 merged_by，要逐 PR 拉）
gh api repos/<owner>/<repo>/pulls/<n> --jq .merged_by.login

# 搜某 issue 是否已被别人的 PR 修掉（含已合并的 Refs 引用）
gh api "search/issues?q=repo:<owner>/<repo>+<issue号>" --jq '.items[] | "\(.number) \(.state) \(.title)"'

# 依赖环境恢复：--ignore-scripts 会跳过 postinstall 补丁脚本，装完必须补跑
npm install --ignore-scripts --no-audit --no-fund && node scripts/apply-dependency-patches.mjs
```

## 关键结论

1. **编译报"类型缺字段/缺导出"而代码明明没错，先查两层**：① 依赖包 dist 陈旧（跨分支切换后按依赖链逐包重建）；② **下游 tsconfig 的 incremental 缓存（`tsconfig.*.tsbuildinfo`）把旧的类型检查结果钉死了**——只重建依赖不够，要把下游的 .tsbuildinfo 和 dist 一起删掉重建才愈（本次 desktop 全线假红的真根因）。
2. `npm install --ignore-scripts` 恢复依赖快，但会跳过 postinstall 的依赖补丁脚本；重装后必须手动补跑补丁脚本，否则 UI/runtime 层报一片假"缺导出"。
3. PR 的 CI 跑的是**合并预览树**（我的分支 + 最新 main 的合并结果）：main 自己红会传染所有 PR；处理顺序 = 看失败 job 的失败步骤名 → 本机同树复跑 → `merge-tree` 判断合并预览，别默认是自己改坏。
4. 接手一个 issue 前查四样：评论区 take、assignee、open PR 正文里的 "Fixes #N"、**已合并 PR 里的 "Refs #N"**——作者合了修复但正文只写 Refs 不写 Fixes 时，issue 会永远挂着"未解决"假象。
5. 测试断言要等**最终可见状态本身**：状态机里"会话 id 已变"和"编辑器内容已更新"不是同一时刻，紧跟 id 的断言会读到旧值（真竞态）；终端输出按宽度折行，长文案断言只匹配短前缀。

## 下次怎么用

- fork 仓库日常节奏：每天 `fetch + ff-only` 同步 → 开分支前 `merge-tree` 探冲突 → 推 PR 前 `diff --check` → CI 红时按"失败步骤名 → 本机复跑 → 合并预览树"的顺序定性。
- 编译假错的标准处置：重建依赖链无效时，删下游 `tsconfig.*.tsbuildinfo` + dist 再建（⚠️ 删 dist 会触发全量重编，大型仓库要几分钟）。
- Windows + Git Bash 的坑：node 脚本里写 `'/tmp/xxx'` 会被解析成 `E:\tmp\xxx`（MSYS 路径转换只作用于原生 exe 的参数，不作用于 node 内部）——跨工具传临时文件路径时写完整的 Windows 路径。
