# GitHub 收编对账与分支重排验证

**一句话总结**：维护 fork 时，用三条 git/gh 命令链搞定「上游收编了对账」「老分支能否安全重排」「补丁真落地了吗」三件高频事。

## 背景

维护一个 fork（上游活跃，每天几十笔提交），手头几十条已交付的补丁分支需要对账「上游收了没有」，重排前还要确认「上游是否已经用别的方式修掉了同一个问题」。这次用一套命令链完成了 70+ 单的对账和十余支分支的重排验证。

## 核心命令

```bash
# 批量查 issue 状态（state/stateReason 一目了然）
for n in 100 101 102; do gh issue view $n -R owner/repo --json number,state,stateReason,title | jq -c '{n:.number,state}'; done

# 读 issue 评论——gh 内置 --jq 在部分查询会报错，落文件后用 python3 解析最稳
gh issue view 123 -R owner/repo --json comments > /tmp/c.json
python3 -c "import json; cs=json.load(open('/tmp/c.json'))['comments']; [print(c['author']['login'],c['createdAt'],c['body'][:200]) for c in cs[-3:]]"

# 收编对账：全历史 grep（不要带 --since，老提交会漏）+ 主题紧格式 (#N) 复验
git log upstream/main --oneline --grep="#123"
# 注意：提交正文里引用 #N 可能只是运行记录（如「reds TestXxx (#123)」），不是修复——看主题和正文区分

# 某提交进了哪个发布版本（--contains 会命中非版本 tag，用 ^v 过滤再按版本排序）
git tag --contains <sha> | grep '^v0.1' | sort -V | head -1

# 两提交的祖先关系：A 是否已在 B 之前落地（收编时间线争议时一锤定音）
git merge-base --is-ancestor A B && echo "A 在 B 之前" || echo "A 不在 B 的历史里"

# 真 3way 落地测试：--check 通过 ≠ 无冲突，实际 am 才暴露真冲突
git worktree add /tmp/verify <上游tip的SHA> --detach
cd /tmp/verify && git fetch origin <分支> && \
  git format-patch <merge-base>..<分支head> --stdout | git am -3   # 干净=补丁在最新 main 上可正常落地
cd / && git worktree remove --force /tmp/verify   # ⚠️ --force 会丢弃该 worktree 未提交改动，确认干净后再用
```

```bash
# 分支重排推送：--force-with-lease 比 --force 安全（远端被别人推过会拒绝），推完必须 ls-remote 核验
git push --force-with-lease origin <分支名> && git ls-remote origin refs/heads/<分支名>

# gh 发评论：-f 会把文件路径当字面文本发出去，必须 --body-file
gh issue comment 123 -R owner/repo --body-file /tmp/post.md

# 排查 git 身份被污染（user.name 的值曾被误设为字面量 "user.email"）
git config --show-origin --get user.name   # 看值和来源文件
git config user.name "你的名字" && git config user.email "你的邮箱"
```

## 关键结论

1. **时间线交叉引用事件 ≠ 收编**。GitHub 的「X mentioned this」「added N commits that reference」只是提及；提交正文里引用 #N 也可能只是预存红运行记录。收编的可靠信号三层：单号 grep（全历史）→ 痛点关键词（上游收编可以不带单号）→ issue 末评实测。
2. **`git apply --check` 通过 ≠ 无冲突**。真冲突只有实际 `git am -3` 落地才暴露；补丁字节没变时，在最新 main 上重跑一次落地测试就是「已追平」的实证。
3. **老分支重排前先做覆盖判定**：把补丁的失败测试放到干净的上游 main 上跑——红了说明问题还在可以重排；绿了说明上游已用别的方式修掉（覆盖者未必引用你的单号），重排就是白做。实测老分支报废率约 2/3。
4. **共享仓库里多进程 fetch 会互相推进 remote-tracking ref**——脚本里引用 `upstream/main` 这类 ref 会拿到别人 fetch 来的新值。解法：全程用显式 SHA 钉死，收尾再 fetch 一次复核。
5. **两不信任**：后台任务停止命令的返回 ≠ 死亡证明（要查状态文件/输出是否停止增长）；gh POST 响应解析失败 ≠ 没发成功（先 GET 核实再决定是否重发）。

## 下次怎么用

- **维护 fork 对账上游**：按「批量查状态 → 全历史 grep 对账 → merge-base/tag 定时间线」的顺序跑，一轮就能把几十条分支的收编状态清干净。
- **重排老分支**：先跑覆盖判定（老补丁测试放干净 main 上），再走真 3way 落地 → 重排 → force-with-lease + ls-remote 的链路。
- **批量改文档/台账**：脚本替换必须带锚点守卫（目标串未命中就报错中止），先跑一行样例再全量——本次守卫两次拦下整批错写。
