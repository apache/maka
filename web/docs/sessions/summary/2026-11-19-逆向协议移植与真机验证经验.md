## 可复用经验与案例

### 1. 账号体系是移植私有协议的第一坑（已实证）

同一厂商的两套站点（国际站 qoder.com 与国内站 qoder.cn）令牌互不通：国际站 Cloud Agents PAT 调国内网关 jobToken 返回 401 "personal token is invalid"；且 `gateway.qoder.com` DNS 不存在（ENOTFOUND），只有 `gateway.qoder.com.cn`。移植任何"客户端同款协议"前，先确认**令牌的签发站点与网关域名的归属关系**，再谈签名算法。

证据：live 冒烟 step1 401 → 双域名探测脚本一次定位；修复后真机全通（jobToken 1440 分钟、14 模型、对话流 200）。

### 2. live 测试脚本必须复用生产请求构建器

手搓请求体与生产代码必然漂移：本次 live 脚本漏填 `messages` 数组，网关只回 id 信封零输出。改为直接调用 `buildChatRequestBody` 后一次通过。失败样本自动脱敏落盘 fixtures（`empty-messages.sse`）——失败即资产。

推广条件：任何"脚本调真实上游"的场景（联调探针、冒烟、压测脚本），请求构造与生产共用同一函数，不复制字段清单。

### 3. 差分基线是移植可信度的最低成本证据

移植自定义 Base64/签名时，写一份参考实现的 Python 版跑同样样本，Node 输出与之逐字节 diff；golden 值内联进测试并注明"由参考实现生成 + 日期"。协议日后漂移时可归因"哪一层变了"。

配套坑：Windows 下 diff 报全行不同但肉眼看相同 = CRLF，用 `diff <(tr -d '\r' < a) <(tr -d '\r' < b)`。

### 4. 内联脚本跨引号嵌套一律落盘执行

本轮 `node -e`/heredoc 多次失败：中文正则转义碎裂（SyntaxError）、`/tmp` 路径 require 解析错位、heredoc 传递损坏（unterminated string）。稳定做法：`Write` 临时 `.mjs` 文件 → `node --check` → 执行 → 删。探针类一次性脚本同样处理（本项目 `test/tmp-probe.mjs` 模式）。

### 5. Git 历史重写的两条路（含失败信号）

- 改**全部/多数提交消息**：`git filter-branch -f --msg-filter 'sed …' <base>..<branch>`，Windows Git Bash 可用；⚠️ 重写历史改 SHA，仅限未推送提交。成功信号：`git log` 确认消息更新、`git diff <old> <new>` 为空（树不变）。
- msg-filter 里**不要**调 `git log`/`git show` 做条件判断（过滤环境下语义不可靠，本次没命中直接空转）；按 stdin 第一行标题匹配即可。
- 改**单个中间提交的消息**：`filter-branch` 没命中后想用 `reset --soft <中间提交>` + 重 add 重建，结果是 "no changes"——中间提交的树已包含其祖先内容，重 add 同文件集无 diff。正确做法：要么 filter-branch 按标题精确匹配，要么整条链从基线 soft reset 后按最终树分批重建（本次最终采用后者，4 个提交一次成型）。

### 6. 提交后 VS Code 源代码管理面板数字过期

CLI 提交后面板仍显示提交前的"未提交"数量（本次显示 48，实际 `git status` 为 0）。以命令行为准，面板点刷新或重载窗口即消失。避免据此误判"还有东西没提交"。

### 7. GitHub API 写中文元数据的正确姿势

`curl -d '中文JSON'` 在 Git Bash/Windows 下编码损坏报 "Problems parsing JSON"。稳定做法：payload 先写临时文件（放 `.git/` 内避免误提交），`curl --data-binary @file -H "Content-Type: application/json"`，响应回读确认后删临时文件。适用于 PATCH repo description、PUT topics、POST release。token 用 `git credential fill` 提取进变量，全程不回显（见下命令节）。

## 常用命令

### 1. GitHub 仓库元数据更新（About 描述 / topics / Release）

- 场景：不用网页、在终端更新仓库元数据。
- 前提：`git credential` 已存 GitHub 凭据（push 过即有）；payload 含中文时必须走文件。
- ⚠️ 直接写远端公开仓库元数据，需确认仓库归属与内容后再执行。

```bash
cat > .git/payload.json << 'EOF'
{"description": "新描述文本"}
EOF
token=$(printf "protocol=https\nhost=github.com\n\n" | git credential fill 2>/dev/null | sed -n 's/^password=//p')
curl -s -X PATCH "https://api.github.com/repos/<owner>/<repo>" \
  -H "Authorization: Bearer $token" \
  -H "Accept: application/vnd.github+json" \
  -H "Content-Type: application/json" \
  --data-binary @.git/payload.json
rm .git/payload.json
```

- 成功信号：响应 JSON 含更新后的 `description`（topics 用 PUT `/topics` 看 `names`；release 用 POST `/releases` 看 `html_url`）。
- 变体：release 带正文时用 Node 把 md 读进 payload JSON 再落盘，避免手工转义。

### 2. CRLF 安全的内容比对

- 场景：Windows 上对比两个进程输出/文件，diff 报全行不同但内容肉眼相同。
- 命令：`diff <(tr -d '\r' < fileA) <(tr -d '\r' < fileB)`
- 成功信号：无输出 = 内容一致。

### 3. 改写未推送提交消息（批量、按 scope 替换）

- 场景：探索期提交后统一 scope 命名（如 kebab → camel）。
- ⚠️ 重写历史改 SHA，仅限未推送分支；推送过的提交不要动。

```bash
FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch -f --msg-filter \
  'sed "s/^refactor(cloud-agents):/refactor(cloudAgents):/"' <base>..<branch>
```

- 成功信号：`git log --oneline` 确认消息更新；`git diff <oldHead> <newHead>` 为空确认只改了消息。

### 4. 从凭据助手无回显取 GitHub token

- 场景：脚本调用 GitHub API 时复用 push 凭据，避免手工粘贴 token。
- 命令：`token=$(printf "protocol=https\nhost=github.com\n\n" | git credential fill 2>/dev/null | sed -n 's/^password=//p')`
- 前提：该 host 已有存储凭据；副作用：无（只读凭据缓存）。
