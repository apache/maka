# AI 会话归档与 C 盘清理实战

**一句话总结**：盘点 Magpie/ZCode 六个 AI 工具的会话数据并归档到 E 盘，同时摸清 C 盘大户——最大单项是 go 构建缓存 20.5 GB，一条 `go clean -cache` 就能回收。

## 背景

C 盘只剩 202 GB 可用，各 AI 编程工具（claude/codex/cursor/factory/kimi/zcode）的会话散落各处，Magpie 网关还在引用它们做统计。目标：把会话归档提炼到 `E:\cc\guahub\sessions`，再分级清理 C 盘。全程先只读盘点、dry-run 出方案，等人工确认才动文件。

## 关键结论

1. **Windows 进程池崩池的根因是缺 `__main__` 保护**。症状是子进程集体报 "attempted to start a new process before bootstrapping"、所有 future 归零。修复一行，扫描从不可用变可用。附带收益：单线程 stat 遍历整个用户目录要 40 分钟，按顶层子目录 8 进程并行只要 2.5 分钟。

2. **AI 工具会话的存放格局**：Magpie 只索引外部 CLI 的 jsonl 文件（清单在 `~/.cache/magpie/sessions.json`，claude/codex/cursor/factory/kimi 全收，.zst 也算）；ZCode 自会话存在 SQLite（`session`/`message`/`part` 三表，`part.data` 是 JSON 正文），Magpie 不索引它，提取要走 DB 副本。归档 776 个会话出 759 篇 md。

3. **活应用的 SQLite 只能 ro+backup 读**，直接连会在 WAL 上打架；备份后 VACUUM 前先看 free pages——ZCode 库 free pages 只有 117（<1 MB），VACUUM 纯属折腾，直接跳过。

4. **C 盘大户排序（本机实测）**：go-build 缓存 20.5 GB > npm cache 6.1 GB > Temp 18.4 GB（其中 VS Code 安装器残留 3.5 GB、cursor-sandbox-cache 6.8 GB）> pnpm store 4.1 GB。对应官方清理命令（方案已核对，执行等确认）：`go clean -cache`、`npm cache clean --force`、`pnpm store prune`（只清未引用包）、`uv cache prune`、`pip cache purge`、`bun pm cache rm`、`go clean -modcache`（2.1 GB，重下耗时，酌情）。

5. **提示词聚类前必须滤系统注入**，否则库全是垃圾：ZCode 往 user 消息里塞 "The TodoWrite tool hasn't been used recently…" 提醒、codex 把工具输出以 `[N] tool …result:` 的 user 角色回灌、审计壳有 `[N] user:` 合成消息。按前缀 + 正则过滤后，8643 条降为 3402 条真实提问。归档幂等靠 manifest 以 `(source, sha256)` 为键跳过已处理，重跑安全。
