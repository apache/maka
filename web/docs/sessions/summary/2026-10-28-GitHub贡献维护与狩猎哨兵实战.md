# GitHub 贡献维护与狩猎哨兵实战

**一句话总结**：multica 仓 9 张在途 PR 的维护轮 + 狩猎接单哨兵化，沉淀出 rebase 验证三铁律、占坑四维排雷法、消融红绿与 CI 判终态的可复用纪律。

## 背景

在 multica-ai/multica 做 PR 维护与 issue 狩猎。上游活跃（日增 10+ 提交）、报告者普遍秒级自开 PR 占坑，两轮狩猎 16 张候选单 14 张死在占坑/已修/信息不足闸上。期间踩了 rebase 语义冲突、xdiff 静默丢行、消融假红、gh 并发限额四个坑，全部闭环。

## 核心命令

```bash
# 零冒号 push：zsh 环境钩子会吞掉命令行里 ":refs/..." 段（报 src refspec does not match any），
# 解法=worktree 内先建本地分支，refspec 只写分支名，--force-with-lease 不带参数（用 remote-tracking 做基线）
git -C <repo> worktree add --detach /tmp/wt-<n> upstream/main
cd /tmp/wt-<n> && git checkout -b <分支> upstream/main   # detached HEAD 上 commit 推无可推
git push --force-with-lease origin <分支>

# rebase 后必查 PR 完整形态：diff HEAD~1 HEAD 只见末位提交；上游挪表格/文档锚点会静默吃掉我方插入行
git diff upstream/main..HEAD --stat
git diff upstream/main..HEAD -- <文件>   # 逐文件核对插入行是否还在

# 占坑四维排雷（接单前全走一遍）
gh search prs --repo <owner>/<repo> --state open "<issue号>"   # 全文检索，正文深处 Closes 也逃不掉
gh api repos/<owner>/<repo>/issues/<n>/comments                # 评论数>0 或评论内贴 PR 链接=疑占坑
git log --oneline upstream/main -- <域文件目录>                 # 上游已修但 issue 未更新的死雷
gh pr view <占坑PR> --json state --jq .state                    # 占坑 PR 关闭未合并时 issue 回池可接

# CI 与 CI 同构的本地 DB（DB-backed 测试本机可验）
docker run -d --name pg -e POSTGRES_USER=multica -e POSTGRES_PASSWORD=<占位符> -e POSTGRES_DB=multica -p 5432:5432 postgres:16
cd server && DATABASE_URL=postgres://multica:<占位符>@localhost:5432/multica go run ./cmd/migrate up
docker rm -f pg   # 用完即删

# CI 判终态：pending 期不数 pass 计数，只 grep 非 pass/skipping 的 lane
gh pr checks <PR号> --repo <owner>/<repo> 2>&1 | grep -vE 'pass|skipping'

# 对外评论一律 body-file + GET 回读逐字节比对（POST 报错≠没发，先 GET 再决定重不重发）
gh pr comment <PR号> --repo <owner>/<repo> --body-file /tmp/cmt.md
gh api repos/<owner>/<repo>/issues/<PR号>/comments --jq '.[-1] | {user: .user.login, body: .body[0:100]}'

# 消融实证：只还原产品文件到父提交、测试保留，测试必须真红且点名行为
git checkout <父提交SHA> -- server/internal/.../产品文件.go
go test ./包路径/ -run TestXxx -count=20 > /tmp/red.log 2>&1; echo $?
git checkout HEAD -- server/internal/.../产品文件.go
```

## 关键结论

- **textual-clean rebase 仍会编译炸**：上游新增调用方撞我方改过签名的函数，git 零冲突但 CI 全红。rebase 后必须本地 `go build ./...` + 改动包测试，不能只看 git 说不冲突。
- **占坑判定绝不能用「issue 零评论」替代**：报告者发 issue 后 25 秒~1 分钟自开 PR 是常态，Closes 声明藏在 PR 正文深处、甚至只贴在 issue 评论里（PR 正文不含 issue 号）。四维全查才安全，命中即弃零痕迹。
- **消融假红的形态是超时而非断言失败**：门控原语（channel 非阻塞接收）吃掉了缓冲信号导致最终等待饿死，测试 10s 超时红——这不是要求的红。真红=0.01s 断言失败且报错信息点名被测行为。见到 timeout 型红先怀疑 harness。
- **上游裸 revert 无理由时绝不盲做第二遍**：先考古原 PR 的 diff/review/关闭时间线，反推回滚理由；理由不可考就发考古评论请维护者表态，方向确认前不认领。本次考古还挖出「revert 16 分钟后 changelog 仍在宣传被撤特性」这类硬证据。
- **判定等审/卡住必须答出阻塞物、归属、下一步**：CHANGES_REQUESTED 针对的 head 已被 force-push 两次=陈旧评审，列证据链 @ 有 merge 权的维护者请重审或 dismiss；纯首审排队则看距上次信号是否满 3 天再 ping，不连发。

## 下次怎么用

- 给活跃上游仓维护在途 PR：每次上游前进后按「rebase → `--stat` 核完整形态 → 本地 build+测试 → 零冒号 push → CI 判终态 → `--body-file` 评论回读」一条龙走。
- 在抢手仓库接 issue：先用四维排雷（约 2 分钟）再决定读全文，避免白读；报告者自带 patch 或「will open a PR shortly」的一律不碰。
- 修竞态/并发 bug：本地起与 CI 同构的 Postgres，测试用「基线必红 → 修复 → 消融复红」三段验证，红必须断言失败型。
- 高频值守可用定时任务 + 文件共享状态（候选池记录已排雷单号/死因/在飞状态）实现无状态哨兵，每轮从文件重建现场，不依赖会话记忆。
