# 测试产物陈旧与扫描假零命中

> 来源：agent-hub 清洗发布 + coding-agent 一致性套件建设会话（2026-10-01 执行，本文 2026-11-19 归档）。

## 一句话结论

本会话两处可晋升为个人规则的真增量：**测试二进制陈旧**（单测绿、集成测试红，报错误导指向环境）与**模式扫描假零命中**（rg 管道把失败吞成空结果，实锤漏检敏感词）——前者是 bug 模块已有"产物陈旧"规则的新形态，后者现有规则完全未覆盖。

## Skill 增量建议（均未执行，待确认）

### 候选 1：bug 模块产物陈旧段追加

- **位置**：`gua-dev-tools/modules/bug/MODULE.md` §平台机制优先于业务代码，现有"另一类伪症状是产物陈旧"段后。
- **现有规则或缺口**：已覆盖"运行产物陈旧"（改完没效果→grep 产物新标识），未覆盖**测试二进制**陈旧。
- **建议追加**：测试二进制同样陈旧且更隐蔽：cargo 集成测试的 `CARGO_BIN_EXE_*` 在编译期烧绝对路径，目录迁移/重命名后 cargo 指纹未判其失效，表现为**单测全绿、集成测试全红**且报错指向环境（如"启动子进程失败 NotFound(3)"）而非产物。修复：`touch tests/<file>.rs` 强制重编译。防复发把新鲜度检查做进执行入口——登记不产生免疫力（同款问题文档登记后一个月内复发）。判定手法：把可疑代码链**逐字复制**成对照测试跑，对照全绿则差异必在未复制处（本次实锁定为产物陈旧而非代码）。
- **来源证据**：rcode 冒烟 7/7 红 + 单测 55 绿；探针四变体全绿排除环境后锁定；`touch` 后 7/7 绿。同款问题 ADR-001 后果节 09-27 已登记、10-01 复发。
- **检验场景**：cargo 仓目录迁移后集成测试报 NotFound 而单测全绿——正确动作是先 touch 重编译；反例是去查 spawn 的环境变量或路径拼写。
- **适用边界**：cargo 项目；其他构建系统（Go test 直接源码编译、dotnet build 产物带探测）形态不同，不照搬。

### 候选 2：quality 模块加扫描验证纪律

- **位置**：`gua-dev-tools/modules/quality/MODULE.md` "两份证据必须分开报告"节后，或通用铁律。
- **现有规则或缺口**：完全未覆盖"扫描类验证的工具静默失败"。
- **建议追加**：模式扫描类验证（敏感词归零、禁用词检查、反例归零）不能只信一次工具调用：rg/grep 的 IO 错误、glob 写法或管道组合会把失败吞成空结果（假零命中）。审计必须独立复核：脚本打印"扫描 N 个文件、命中 M 处"并显式退出码，关键审计加全量人工通读兜底。
- **来源证据**：agent-hub 公开化审计中，rg 组合扫描报零命中，但 Python 全文审计（42 词 × 显式退出码）在 docs/adr 抓到漏网敏感词；同会话内 rg 两次行为不一致（单独 `-c` 正确计数、组合管道漏文件）。注意：漏检的精确根因（rg 行为 vs 管道写法）未完全定谳，但"模式扫描不可作唯一判据"已被实锤支持。
- **检验场景**：审计报"零命中"——正确做法是复核脚本输出"扫描了 N 个文件"且退出码 0；反例是直接信任 rg 管道输出的空结果宣布归零。
- **适用边界**：一切"必须归零/必须全命中"的扫描任务；日常代码搜索不在此列（漏一条再搜就是）。

## 可复用经验与案例

**Epoch 守卫（轮询幂等）**：React StrictMode 双挂载或重复恢复会产生两条并行轮询链。修法：`startPolling` 入口先递增纪元号作废旧链，在途响应按纪元丢弃；unmount 与终态必停 timer。配套 TDD 证据：先升级 E2E 跑出 RED（恢复后停在旧快照 15s 超时），修复转 GREEN。下次遇到"轮询/定时器 + React 18+ StrictMode"直接套用。

**红操演练（套件灵敏度自证）**：一致性/回归套件冻结前手工注入一次已知漂移，套件必须**单点**转红（只红被注入者），回滚后复绿。红过的套件才可信——两次实演练成（注入拒写失效、注入写入不保存，均精准单点命中）。泛化边界：适用于"跨实现一致性"或"防漂移"套件，普通功能测试不必。

**归一化 fail closed**：跨实现比对的允许差异必须逐条锚定规范出处，不可归类的差异一律判漂移——否则为了让所有实现通过不断放宽 normalize，最终 everything passes = nothing is tested。

**Release 编辑事故**：给 GitHub Release 顶部追加口径校准注时，因 Windows Git Bash 的 `/tmp` 与 Python 的临时目录**不是同一个地方**（bash 的 /tmp 是 MSYS 虚拟路径），prepend 静默失效；后续 rm 又删了暂存原文，原 24 行正文丢失，仅存前 3 行。恢复：依仓内 CHANGELOG 同版本小节重建正文 + 页脚重建说明。教训：**gh release edit 前先 `gh release view --json body` 备份到工作目录**（不用 /tmp）；跨工具传文件不用 /tmp。

**敏感清洗两形态**：最隐蔽的泄密不是敏感词直写，而是 ①领域词混进业务文案（SYSTEM_PROMPT 里"美业花店"——前司领域词混进花卉演示文案）；②死代码注释自述来源（零引用的请求层工具注释写着"从 X 时期系统原样迁移"）。审计时死代码比活代码更危险——没人看过它。

## 常用命令

| 场景 | 命令 | 前提与信号 |
| --- | --- | --- |
| Git Bash 下 robocopy 开关被路径转换吃掉 | `MSYS_NO_PATHCONV=1 robocopy src dst /E /XD node_modules .git /XF file` | ✅ 实测：不带前缀报"无效参数 #3"，带前缀成功复制 80 文件 |
| cargo 测试二进制陈旧 | `touch tests/smoke.rs && cargo test --test smoke` | ✅ 7/7 绿；副作用：重编译一个测试目标 |
| 判真伪 diff（autocrlf/写回行尾） | `git -c core.autocrlf=false diff --stat -- <file>` | ✅ 内容零差异时输出为空；`git checkout -- <file>` 清幻影 M |
| 取 GitHub Release 原文 | `gh release view vX.Y --repo owner/repo --json body -q .body` | ✅ 编辑 Release 前必做（备份到工作目录） |
| GitHub 仓改名（含路径派生丑名） | `gh repo rename <new> --repo <owner>/<old> --yes` | ✅ 旧名 301 重定向；`gh repo edit --rename` 不存在（会打印 help） |
| 解除文件跟踪但保留本地 | `git ls-files | grep <pattern> \| xargs -d '\n' git rm -r -q --cached` | ✅ 107 个 .mimosa 解除；需随后 commit |
| 整仓迁移被 EBUSY 挡（VS Code 占句柄） | `tar -C src --exclude=node_modules --exclude=target --exclude=dist -cf - . \| tar -C dst -xf -` | ✅ 四仓迁移成功；.git 一并带走，新址即用；旧目录待锁释放后删 |
| coding-agent 一致性套件（项目入口） | `node conformance/run.mjs all` | 退出码 0=PASS 1=DRIFT 2=INFRA；需五工具链 |

## 待验证与不适用边界

- **rg 假零命中的精确根因未定谳**：实锤的是"模式扫描漏检 + Python 复核抓到"，"rg 吞错误"是推断——下次复现时先跑 `rg --stats` 或分步执行定位。
- **`gh auth refresh -s delete_repo` 未执行**：删除私有仓被 403 拦截后选择了让用户网页自删方案，授权流程未走通验证。
- **`gh repo edit --rename` 无效**是版本事实（会打印 help），`gh repo rename` 有效——但 gh 版本升级后可能变化。
- **Epoch 守卫/红操演练**均来自单项目实践，迁移到其他栈（Vue/非 conformance 场景）前先小步验证。
