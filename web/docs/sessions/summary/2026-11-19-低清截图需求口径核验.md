# 低清截图需求口径核验

## 一句话结论

活动参与率原本符合文档中的绿、蓝、橙规则。一次低清截图误读造成了错误改色，随后已撤回。这份笔记保留改码前的读图核验动作，以及在单文件原型中检索内嵌文本的方法。

## Skill 增量建议

建议在 `gua-dev-tools/references/delivery-workflow.md` 的「1. 范围和证据」冲突处理段补一句。现有规则已区分需求、源码和运行证据，`modules/bug/MODULE.md` 也已要求先复现再改码。此处补的是如何确认低清截图里的原文。

> 截图中的关键字、数值或符号一旦会改变验收结论，先取原图或裁切放大，逐字核对并引用原文。仍无法辨认时，查同一条规则的可检索原文；无法核实的读数标为待确认。

适用于截图文字直接决定阈值、颜色或操作条件的场景。检验场景用本案的 548px 截图，核对者应读出「≥70% 蓝色」，或在字形仍不清时保留待确认。历史工具结果已显示放大后的文字。本轮未执行 Skill 规则检验。

## 可复用经验与案例

- **把圈出的判据和圈出的现象分别核对。** QA 图上半部分是表格，下半部分是预期颜色清单。放大的 `qa_checklist.png` 显示清单写的是「大于等于70%蓝色」。我第一次把「蓝」读成「黄」，又在已经发现分模块原型写「蓝」时采信了未经放大确认的读数，导致误改。遇到类似冲突，先确认自己抄出的原文，再判断是否存在版本或口径差异。
- **原型规则与源码分别有证据。** [分模块原型的业务规则](<E:/cc/web/senior/01-产品原型/v4.44.3-机构端-活动管理/恒泰悦居-活动管理原型-离线总包/机构后台PC-交互原型图-分模块.html>)写明 ≥90% 绿、70% 至不足 90% 蓝、低于 70% 橙。两份单文件原型解码后的 `rateBar` 和 [活动管理.xmind](<E:/cc/web/senior/04-测试用例/v4.44.3-机构端-活动管理/活动管理.xmind>) 的「参与率=实到/报名」子节点也吻合。历史 Git diff 显示 `participationStats/config.js` 撤回了 `#faad14`，恢复 `#1890ff`，该文件只留核对注释。活动评价页按产品确认隐藏「删除」入口，属于另一项变更。

## 常用命令

在 Windows Git Bash 中，对已确认使用长 Base64 块封装正文的本地 HTML 做只读检索。需要 Node.js。替换原型路径和函数名即可。以下是当时成功命令的参数化写法，本轮未重跑。

```bash
node -e '
const fs = require("fs");
const [path, keyword] = process.argv.slice(1);
const html = fs.readFileSync(path, "utf8");
for (const block of html.match(/[A-Za-z0-9+/=]{2000,}/g) || []) {
  const text = Buffer.from(block, "base64").toString("utf8");
  const index = text.indexOf(keyword);
  if (index !== -1) {
    console.log(text.slice(Math.max(0, index - 70), index + 220));
  }
}
' 'E:/path/to/prototype.html' 'function rateBar'
```

历史命中结果包含 `v >= 90 ? '#52c41a' : (v >= 70 ? '#1890ff' : '#fa8c16')`。命令只读文件，不执行 HTML。长块正则是针对这类导出的筛选条件。无输出时只能说明该轮未命中。
