# 验证第三方 patch 分支流程

**一句话总结**：别人在 issue/PR 里甩来一个修复分支或 patch 时，用 git/gh 在隔离 worktree 里全程实测——能应用、真修好、不冲突三个问题各有一套命令，拿数据回复。

## 背景

开源项目 issue 里有人贴了修复分支（他没法开 PR），需要判断：能否干净应用到当前 main、是否真的修好、与我已有的同类 patch 冲不冲突。全程只动隔离副本，主工作树零改动。

## 核心命令

```bash
# 拉别人的分支：临时 URL 直接 fetch，不用加 remote
git fetch https://github.com/<user>/<repo>.git <branch>

# 查对方分支基于哪个提交、离当前 main 多远（太老要多留心）
git merge-base <commit> upstream/main

# 一眼判断上游动没动过某文件：blob hash 相同=内容没变
git rev-parse upstream/main:path/to/file.go <commit>:path/to/file.go

# 干跑 patch：只证明文本能套上，不证明编译和行为
git apply --check --3way /tmp/xxx.patch

# 检查自己旧分支对最新 main 是否需要 rebase
git format-patch <old-base>..<branch> --stdout | git apply --check --3way -

# 建独立 worktree 验证，主工作树完全不动
git worktree add --detach /tmp/verify-xxx upstream/main
cd /tmp/verify-xxx
git cherry-pick <commit>   # 3way 自动合并，且保留原作者署名

# Go 测试先取精确测试名再跑：-run 模式写宽了会假绿
grep -n '^func Test' internal/xxx/yyy_test.go
go test ./internal/xxx -run 'TestA|TestB' -count=1

# 验证矩阵：格式 / 静态检查 / 交叉平台 vet 与编译 / 全包测试
gofmt -l internal/xxx/
go vet ./internal/xxx
GOOS=linux go vet -tags nogui ./internal/xxx
GOOS=linux go build -tags nogui -o /dev/null ./...
go test -tags nogui -count=1 ./internal/xxx/ > /tmp/pkgtest.log 2>&1

# gh 读 issue 与评论、发评论、发后 GET 回读校验
gh issue view 3165 --repo <owner>/<repo> --json state,comments --jq '...'
gh api repos/<owner>/<repo>/issues/3165/comments --paginate --jq '.[] | .body'
gh issue comment 3165 --repo <owner>/<repo> --body-file reply.md
gh api repos/<owner>/<repo>/issues/comments/<comment_id> --jq '.body'

# 清理 worktree：先挪走自己产生的未跟踪文件，别用 --force
mv /tmp/verify-xxx/test.log ~/somewhere/ && git worktree remove /tmp/verify-xxx
```

## 关键结论

1. **"能应用"和"真修好"是两回事**：`git apply --check` 只证明文本可套用，必须再跑测试；消融验证证明修复是必要的——只把产品代码回退（测试保留），相关测试应当回红，恢复后复绿。红→绿→复红→复绿才算闭环。
2. **cherry-pick 是验证第三方 commit 的最优路径**：3way 自动合并，原作者署名自动保留，比手工打 patch 干净得多。
3. **两个 patch 改同一行≠真冲突**：若两边改法相同，cherry-pick 的 3way 会自动消解；"需要 rebase"往往只针对依次 `git am` 的场景，实测一下再下结论。
4. **blob hash 快速判断旧分支是否过时**：`git rev-parse <rev>:<path>` 对比几个关键文件，比整个 rebase 试一遍便宜得多。
5. **worktree remove 遇到未跟踪文件会拒绝**：那通常是自己的测试日志，先 `mv` 挪走再 remove，养成不用 `--force` 绕保护的习惯。

## 下次怎么用

- Review 社区 PR 或 issue 里的 patch：fetch → merge-base 查基线 → `apply --check --3way` 干跑 → worktree 里 cherry-pick → 跑对方声称的测试 → 消融回红 → 验证矩阵 → 组合验证（如果自己有同区域 patch）。回复时附实测命令和输出，比"试过了没问题"有说服力。
- 怀疑自己搁置的旧分支过时：`format-patch | git apply --check --3way -`，通过就无需 rebase。
- 怀疑某个 bug 修复"治标不治本"或"修了不存在的问题"：消融法，回退产品代码看测试是否回红。
