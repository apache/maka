# cc 仓库 .git 膨胀(5.8G)排查与清理

**一句话总结**：.git 异常大时,先用 `count-objects` 和 `rev-list` 对比「总对象数 vs 可达对象数」——cc 仓库 94% 是不可达垃圾,一条 `gc --prune=now` 能收回大头,但真历史里也压着 3.88GiB 文件,gc 后仍会剩 1~1.5G。

## 背景

cc 跨机同步仓的 `.git` 膨胀到 5.8G,想弄清是什么占了空间、能不能安全删。

## 核心命令

```bash
# 确认 .git 总大小,再按子目录拆出大头(结果是 objects/pack 占 5.3G)
du -sh /path/to/repo/.git
du -sh /path/to/repo/.git/* /path/to/repo/.git/objects/* | sort -rh | head -20

# 对象库总览:pack 数量、对象总数、体积
git -C /path/to/repo count-objects -vH
# 关键字段:in-pack(总对象数 121万)、size-pack(pack 体积)、prune-packable(可回收的散对象)

# 可达对象数(7.4万)——和上面 in-pack 一对比,立刻知道 94% 是不可达垃圾
git -C /path/to/repo rev-list --objects --all | wc -l

# 清理前安全检查:确认没有别的引用钉住旧对象
git -C /path/to/repo branch -a && git -C /path/to/repo stash list && git -C /path/to/repo worktree list

# 找历史里的大文件(判断"真历史"有多重):列出可达 blob 中超过 8MB 的及路径
git -C /path/to/repo rev-list --objects --all \
  | git -C /path/to/repo cat-file --batch-check='%(objecttype) %(objectsize) %(rest)' \
  | awk '$1=="blob" && $2>8000000 {printf "%.0fMB %s\n", $2/1048576, $3}' | sort -rn

# 清理(本次未执行,确认后运行) ⚠️ 永久删除所有不可达对象,执行后无法从本地找回
git -C /path/to/repo reflog expire --expire-unreachable=now --all
git -C /path/to/repo gc --prune=now
du -sh /path/to/repo/.git   # 验证清理效果
```

## 关键结论

1. 根因:跨机同步和历史改写攒下多个旧 pack(1.7G/1.5G/1.3G 三个大包),仓库从未跑过有效 gc,120 多万个不可达对象一直没回收。
2. 判别套路:`count-objects -vH` 的 in-pack 对比 `rev-list --objects --all` 行数——差距大就是垃圾膨胀(gc 可解),差距小就是真历史大(只能 filter-repo 改写)。
3. gc 只动 `.git` 对象库,不碰工作区未提交的改动;前提是分支/stash/worktree 都确认过,且本地与远端一致。
4. 底线:可达历史本身有 3.88GiB(node_modules、75MB 分析 JSON、exe、crx 归档都被提交过),gc 救不了这部分;想更小要 `git filter-repo` 改写历史 + 强推,且另一台机器必须重新 clone——收益(约 1G)与折腾度不成比例,先 gc 看结果再说。

## 下次怎么用

任何仓库 `.git` 体积异常时套这套流程:`du` 拆大头 → `count-objects` 看总量 → `rev-list` 算可达 → 对比定位「垃圾 vs 真历史」→ 前者 `reflog expire + gc --prune=now`,后者再评估 filter-repo。gc 属不可逆操作,跑之前先 `branch -a / stash list / worktree list` 三连确认。
