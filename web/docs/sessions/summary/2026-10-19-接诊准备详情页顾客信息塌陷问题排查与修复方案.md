## 结论

**固定高度的纵向 flex 滚动容器，叠加顾客卡默认允许收缩，是目前最符合截图和隔离测试结果的机制。** 当旧内核未正确保护嵌套 flex 卡片的自动最小高度时，顾客卡的白色背景盒会被压扁，卡内年龄、标签等内容向下溢出，随后被下一张白卡遮挡。

`overflow-y: auto` 参与了问题出现的布局条件，但顾客卡本身没有设置 `overflow: hidden`。当前证据支持先控制卡片的收缩，而不是删除滚动能力或给卡片写死高度。同结构的旧版浏览器问题已有[独立历史复现](https://github.com/philipwalton/flexbugs/issues/241)。

这条机制在桌面隔离环境中已得到验证；将其确定为该平板实际内核中的根因，还需要设备端尺寸数据和同页面修复前后的对照。

## 布局链路

### 详情页的高度约束来自两个样式共同作用

入口 `E:\Projects\frontend\homing-miniapp-workbench\src\subPackage\receptionPrep\detail\index.tsx` 的根节点同时使用 `styles.page` 与 `styles.detailPage`。

| 样式位置                                                                                                                                  | 关键声明                                                                                 | 作用                                               |
| ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `E:\Projects\frontend\homing-miniapp-workbench\src\subPackage\receptionPrep\styles\mixins.scss` 中的 `rp-page`                            | `display: flex`、`flex-direction: column`、`min-height: 100vh`、`box-sizing: border-box` | 建立纵向 flex 页面壳                               |
| `E:\Projects\frontend\homing-miniapp-workbench\src\subPackage\receptionPrep\detail\index.module.scss` 中的 `.detailPage`                  | `height: 100vh`、`overflow-x: hidden`、`overflow-y: auto`、`padding-bottom: 180rpx`      | 固定页面盒高并承担内部滚动；内边距占用部分可用空间 |
| `E:\Projects\frontend\homing-miniapp-workbench\src\subPackage\receptionPrep\components\CustomerSummary\index.module.scss` 中的 `.profile` | `display: flex`、`align-items: flex-start`                                               | 顾客卡同时又是横向 flex 容器                       |

顾客卡和业务模块栈是根节点的直接流内子项，会参与纵向 flex 分配。固定定位的底栏等脱离普通流的元素不按同样方式参与分配；React Fragment 本身不额外产生 DOM 包装层。

### 内容为何会和下一模块重叠

当子项的外部基础尺寸总和超过父容器可用高度时，flex 布局会产生负自由空间，并结合 `flex-shrink`、基础尺寸及最小尺寸约束进行收缩。默认允许收缩并不意味着一定会压到内容高度以下；现代内核通常还会应用自动最小尺寸约束。相关规则见 [W3C Flexbox 自动最小尺寸](https://www.w3.org/TR/css-flexbox-1/#min-size-auto)。

历史复现描述的特殊组合与这里一致：父容器有确定高度、纵向 flex 和滚动；子项自身又是 flex 容器，并使用默认的 `flex-shrink: 1` 与 `min-height: auto`。部分旧内核会错误处理子项的自动最小高度，使卡片盒高小于内部内容所需高度。[历史复现中的直接规避方式](https://github.com/philipwalton/flexbugs/issues/241)就是禁止该子项收缩。

顾客卡内容继续绘制在盒子外，下一个兄弟模块仍按已经变矮的卡片盒排列，两者便出现重叠。源码与截图共同支持这一解释，设备端实际绘制关系仍以真机采样为准。

## 对原分析的校正

| 原表述                                                                      | 应保留的结论                                                                                                                                   |
| --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 手机内容未超过 `100vh`，所以没有触发收缩                                    | 缺少该手机的内容总高记录。长详情页在正常设备上同样可以超出一屏；自动最小尺寸保护是否正确才是关键差异之一                                       |
| 内容一超出就会压到刚好塞满，连滚动条都没有                                  | 收缩受最小尺寸约束，结果不一定恰好塞满；后代内容溢出时仍可能有滚动范围。页面主动隐藏了滚动条，应检查 `scrollHeight`、`clientHeight` 和实际滚动 |
| MIUI 10.3.2 / Android 8.1 就能确定使用 2018 年 Chromium 或旧 X5，且不会更新 | 系统版本不等于应用实际使用的浏览器内核版本；内核种类和版本需通过设备 UA、宿主信息或调试工具核验                                                |
| `maxRootSize: 26` 导致 rem 内容相对视口显著变高，因此平板必现               | `config/index.js` 确有 `maxRootSize: 26`、`minRootSize: 20`，但钳制本身不足以推出必然溢出。单位换算、换行、字号和视口高度共同决定内容高度      |
| 恢复后的自然高度应约为 230px                                                | 卡片高度取决于标签、姓名、字体和可用宽度，没有统一的 230px 验收值                                                                              |
| 桌面模拟通过说明小米平板已经修好                                            | 桌面实验只证明这个机制可以产生相同形态，并证明补丁对该条件有效；真机验收单独记录                                                               |

## 可复用经验

排查“卡片塌陷”时，先分别测量外层背景盒与内部内容的边界。盒子变矮而内容仍在，优先检查 flex 收缩和自动最小尺寸；内容边界本身正常但不可见，再追踪裁剪与覆盖关系。

滚动区里的长内容模块通常需要按内容保留高度，可压缩的空白区域再参与 flex 分配。结构断言适合防止约定被删除；尺寸与滚动行为验证用于判断约定是否解决实际问题，两者各自保留证据边界。
