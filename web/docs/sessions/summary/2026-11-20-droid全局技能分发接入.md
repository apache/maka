# droid 全局技能分发接入

> ⚠️ **勘误**：本文核心结论已被同日第二轮排查推翻——junction 对 droid 无实际贡献，两端都走 `~/.agents/skills` 兼容路径。第一轮的错误归因本身是本案例最有价值的部分，原文保留作对照，实证修正见文末章节。

## 一句话结论

factory.ai（droid CLI）读不到全局个人 skills 的根因是分发脚本 `~/.ai/scripts/sk-sync.js` 的 `DIRS` 清单没有 `~/.factory/skills`——不是链接损坏，是从未建链；在清单加一行并实跑 sk-sync 即接入，droid 对 Windows junction 完全兼容（27 条全部读取成功）。

## 排查路径与证据

1. `ls ~/.factory/` 无 `skills/` 目录；其他 15 个 CLI 目录均有 junction 指向 `~/.agents/skills` → 指向"从未分发"而非"断链"。
2. 读 sk-sync.js 的 `DIRS` 硬编码清单（15 个 CLI）确认 `.factory` 缺席 → 根因落在分发侧。
3. droid 日志 `~/.factory/logs/droid-log-single.log` 里 `skills listed count`（desktop daemon 端 51–56）为内置/组织侧技能，个人全局视图为空。
4. 官方约定路径 `~/.factory/skills/<name>/SKILL.md`（docs.factory.com/harness/skills），与现有 junction 架构无冲突。

## 修复与验证

修复：sk-sync.js `DIRS` 数组追加 `path.join(HOME, ".factory", "skills")`。

验证闭环（每步有实测结果）：
- `sk-sync.js --dry-run`：阶段1 将删 0、仅 `.factory` 新建 27 条、其他 CLI 零改动 → 改动面确认。
- 实跑：阶段2 已建 27，阶段3 `.factory/skills 经源 27/27 [OK]`，categories 实体未受损。
- 穿透读 `.factory/skills/ponytail/SKILL.md` 正常（用 `/c/Users/...` 正斜杠路径，反斜杠双引号有误报断链的坑）。
- `droid exec` 探针：droid 列出全部 27 个个人全局 skills + 官方内置 → 端到端通过。

防误判边界：
- **desktop 端与 CLI 端 skills count 口径不同**：desktop daemon 记 `skills listed count`（51–56），CLI exec 记 `skill_loaded_count`（46），内置集与上下文不同，不能跨端比数量判断接入成败；端到端探针（问 droid 列清单）才是可靠判据。
- 新 CLI 接入后应把分发清单数写回记忆（本次 15→16 个 CLI 目录）。

## 常用命令

```bash
# droid 非交互最小会话（验证 skills 加载、跑探针）；注意没有 --mode 选项，直接跟提示词
droid exec "回复两个字:收到"
droid exec "列出你当前所有可用 skills 的名称清单，只列名称，不要其他内容"

# desktop daemon 端 skills 加载数量（CLI 端不写这个键，口径不同不可混用）
grep "skills listed" ~/.factory/logs/droid-log-single.log | tail -2 | grep -o '"count":[0-9]*'

# 分发前确认改动面：只应出现目标 CLI 的"将建"行，阶段1 将删应为 0
node ~/.ai/scripts/sk-sync.js --dry-run
```

- **未验证**：Factory Desktop 端 daemon 是否需重启才刷新新接入的 skills（CLI 端已端到端验证，desktop 端当时只有历史日志）。

## 实证修正（第二轮排查，同日）

**第一轮核心归因被推翻**。追加实验证据：

1. **A/B 实验**：临时 `mv ~/.factory/skills skills.bak` 后，`droid exec` 仍列出全部 27 个个人技能 → CLI 走的是官方文档列出的 "personal compatibility" scope（`~/.agents/skills`），junction 无实际贡献。移回后恢复。
2. **desktop 端一直正常**：接入前的 desktop 会话快照（`~/.factory/sessions/-E-Projects-.../4b778421-….jsonl`）system prompt 含全部 27 个技能清单，且 `Skill "gua-dev-tools" activated` 等五条激活记录齐全——用户当时在该会话里用 `/ponytail /tdd /clife-bug-resolver /gua-dev-tools /diagnosing-bugs` 全部成功。
3. desktop `skills listed count` 51 接入前后不变，与上互证：junction 从未被计入。

**修正后结论**：droid（CLI 0.238.0 与 desktop 1.14.0 内嵌引擎）发现个人技能的实效路径是 `~/.agents/skills` 兼容路径；`~/.factory/skills` junction 是无害的官方标准路径冗余（未来版本若回归标准路径即生效）。原报障现象在现有证据中无法复现，用户确认已消失。

**方法论教训（本案例最值钱的部分）**：

- **"探针能列出技能" ≠ "我的修复生效"**。第一轮验证（droid exec 列出 27 个）给了虚假信心——技能本来就能列出。归因必须做对照组实验：移走自己的改动再测一次，结果不变即说明改动无关。
- **会话快照 > 日志 count**。日志 `skills listed count` 口径混乱：desktop 技能面板查询、app 版本升级（1.12.1→1.13.1 时 56→51）、内置集变化都会扰动，且 desktop 与 CLI 不可跨端比。会话 jsonl 里有 system prompt 技能清单和 `Skill "X" activated` 激活记录，是端到端铁证。
- **排"工具不加载某资源"先查官方 scope 清单**。droid 文档明确列有 compatibility（`.agents`/`.agent`）路径，兼容路径可能让问题根本不存在——别在标准路径上找根因。
