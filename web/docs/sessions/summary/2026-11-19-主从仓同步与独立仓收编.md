# 主从仓同步与独立仓收编

## 1. 一句话结论

本地工作区与远程主仓历史不同源时（本地孤立基线、远程才是活仓），先判定谁包含谁、再以远程为基线覆盖本地，独立仓收编前用 blob 哈希核验"上游删除 vs 本地未提交"，全程防两类执行陷阱：截断输出下结论、命令链回显谎报成功。

背景：2026-10-12 会话，E:\cc（本地孤立基线 ac109bb，无 remote）对齐 github.com/ggbdpq/cc（80+ 提交活仓，哨兵从另一台机器持续推送），随后收编 console/interview/github 三个嵌套仓身份、清理 85.5GB 依赖缓存。

## 2. 可复用经验与案例

### 2.1 主从仓判定（本地与远程历史不同源时）

本地仓没配 remote 不代表它是主仓。判定顺序：`git log --oneline <本地HEAD>..<远程HEAD>` 看双向差异提交数；看远程关键提交的时间戳与内容新鲜度（本例远程今天还有哨兵轮班台账，本地基线停在 10-01）；看远程树里是否已有"整合待办"类提交（远程 728b46da 就记录了"interview/console 收编入 cc、镜像仓删除待办"——待办清单本身就是协作状态的第一手证据）。结论：远程有持续写入者时，远程是真身，本地按 clone 重建，不硬合并（两历史无共同祖先，merge 不可行）。

### 2.2 blob 哈希判定：上游删除 vs 本地未提交（本案例核心技术）

本地有、远程没有的文件有三种命运：上游刻意删除（不推回）、上游改组后旧路径残留（可归档）、本地从未提交的真增量（要抢救）。判定法：把本地文件 `git hash-object` 得 blob 哈希，对照旧基线树的 `git ls-tree -r <commit>` 哈希集合——

- 哈希在旧树集合里 → 曾入库、被上游删掉（git 内容寻址保证字节级一致）；
- 不在 → 从未入库的本地工作。

本例 interview 16 项全部判为"曾入库被上游精简"，避免了把上游刻意删的资料推回远程。对比只跟踪路径名的判断（路径不在旧树 ≠ 没入库过，因为上游可能改过目录结构——本例宝典从根上移进 study/，路径全对不上），内容寻址不受改名影响。

### 2.3 独立仓收编三步核验（subtree 合并后的 .git 残留）

1. `git cat-file -t <旧仓HEAD>` 确认对象存在（在 cc 对象库里）；
2. `git merge-base --is-ancestor <旧仓HEAD> origin/main` 确认全史已吸收；
3. `git -C <旧仓> status --short` 核对"改动"是否只是旧索引与工作区的脱节假象。

三条都过 → `mv <旧仓>/.git` 出仓、`git --git-dir=<移出的.git> remote remove origin`，工作区原地不动。本例 console/interview/github 三仓均如此收编，github 旧仓仅 1 个基线提交且已是 cc 祖先，零内容损失。

**不适用边界**：cc 里"只留 README 存根"的有意独立项目（agent-skills、language、interview/code/* 等）和 fork 接单工作区不能照此收编——判断依据是 cc 是否跟踪该路径的文件（`git ls-files -- <路径>/ | wc -l`），跟踪数大才是"已收编"，1 或 0 是有意独立。

### 2.4 白名单仓里隐藏本地文件：深层 .gitignore，不是 info/exclude

根 .gitignore 用 `*` + 逐级 `!` 白名单制时，`.git/info/exclude` 优先级低于任何 .gitignore 文件，会被根白名单的 `!` 重新放行压住，写了不生效。正确做法：在要隐藏的目录写深层 .gitignore（深目录模式优先于上层），并把该 .gitignore 自身列入其中。本例 maka/opencode/pi 台账（上游贡献池收缩时刻意移出远程、本地要继续用）即如此处理。

### 2.5 执行反例两则（真实踩坑，防再犯）

- **截断输出下结论**：`find /e/cc -name ".git" -type d | head -3` 两次让我误判 console/.git、interview/.git 已移出，实际 deep 列表里都有。任何用于下结论的清点输出不许接 head/tail，落文件再统计。
- **命令链回显谎报**：`mv A B && git remote remove origin 2>/dev/null; echo "已移出并切断"` ——mv 因备份目录不存在而失败（用户已删 86G 备份目录），但 `;` 后的 echo 照样打印成功。多步操作用 `&&` 串联全链，或事后 ls 核验目标状态再报告；回显不是证据。

## 3. 常用命令

均为 2026-10-12 会话实际执行、结果可见的 Windows + Git Bash 环境。

**Git Bash 下调 robocopy（防路径转换）+ 空目录镜像删除大目录**：
```bash
mkdir -p /e/empty-tmp && MSYS2_ARG_CONV_EXCL="*" robocopy 'E:\empty-tmp' 'E:\大目录' /MIR /NFL /NDL /NJH /NJS /NP /R:0 /W:0 && rm -rf 'E:\大目录'的bash路径
```
前提：`MSYS2_ARG_CONV_EXCL="*"` 必加，否则 /E 之类开关被 Git Bash 转成 `E:/` 报 exit 16。副作用：比 rm -rf 快数倍（本例 243 个目录含 85.5GB 零失败），robocopy 退出码 0-7 均为成功。

**导出远程树做全量对比（worktree add 失败时的退路）**：
```bash
git fetch origin main && mkdir -p /tmp/remote-tree && git archive FETCH_HEAD | tar -x -C /tmp/remote-tree
```
成功信号：目录内文件数等于 `git ls-tree -r --name-only FETCH_HEAD | wc -l`。比 `git worktree add` 可靠（后者在共享对象库上偶发 `fatal: Could not reset index file`）。

**blob 级判定本地文件是否曾入库**：
```bash
git ls-tree -r <旧基线commit> | awk '{print $3}' | sort > /tmp/blobs.txt
git hash-object <本地文件>   # 输出哈希 grep /tmp/blobs.txt 命中=曾入库
```
前提：旧基线 commit 对象可访问（本例来自镜像克隆的备份仓，`git --git-dir=...` 可用）。

**暂存区密钥扫描（提交前）**：
```bash
git diff --cached | grep -inE "(sk-[a-zA-Z0-9]{16,}|ghp_[A-Za-z0-9]{20,}|github_pat_|AKIA[0-9A-Z]{8,}|Bearer +[A-Za-z0-9._-]{20,}|api[_-]?key *[:=] *['\"]?[A-Za-z0-9_-]{16,})"
git grep -l "<命中的token>" HEAD --   # 查 token 是否早已在历史里（区分新增暴露 vs 历史遗留）
```
本例扫描逮到一个历史遗留的 GitHub token（HEAD 里 3 个文件早有），避免了误判为本次新增。

**含反斜杠 Windows 路径的批量替换**：
```bash
python -c "p='文件'; s=open(p,encoding='utf-8').read(); open(p,'w',encoding='utf-8',newline='').write(s.replace(r'E:\cc\旧前缀', r'E:\cc\新前缀'))"
```
前提：sed 在双引号里处理反斜杠路径会静默失效（本例连败两次且输出无报错）；python replace 是确定性的，替换后 grep 残留数验证。

## 4. 待验证与不适用边界

- **未闭环**：home 仓历史里遗留一个 GitHub PAT（`ghp_<已脱敏>`，HEAD 3 个文件），会话中建议用户撤销轮换，未见后续——下次碰 home 仓时先查是否已轮换。
- **未闭环**：两个镜像仓（E-cc-interview、E-cc-ggbdpq-agents-console）删除仍卡 `gh auth refresh -h github.com -s delete_repo` 授权；用户已删 86G 备份目录，镜像副本不复存在，删仓前确认无价值历史。
- **收编方法边界**：§2.3 只适用于"已 subtree 合并收编"的仓；对有意独立的项目照做会毁掉其 git 身份。
- **gua-pr-patch 的"测试输出不接 tail/head"已覆盖测试场景**，本对话是同原理在 git 清点场景的延伸判例，不是新规则。
