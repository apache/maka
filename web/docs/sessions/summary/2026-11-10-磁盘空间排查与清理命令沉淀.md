# macOS 磁盘空间排查与清理命令沉淀（完整版）

> 本文件是 [2026-10-24 首轮版](2026-10-24-磁盘空间排查与清理命令沉淀.md) 的完整修订版：补齐 2026-10-24 至 11-10 九轮清理的实测经验（热缓存修剪、车道静默判死、两次盘满救援），命令与结论以本文件为准。

**一句话总结**：2026-10-24 起九轮清理的完整打法——「量→判→删→验→防」五步管线，累计回收约 890GiB（含两次盘满救援），沉淀三条实测定律：热缓存只删 24h 前旧条目、后台车道工作区按「静默>7h」判死、任何删除先过安全三问。

## 全局结论（先读这个）

1. 本机磁盘回涨有三个固定来源，增速可预测、可按节奏清：

| 来源 | 增速（多次实测） | 应对 |
| --- | --- | --- |
| Go 编译缓存 `~/Library/Caches/go-build` | magpie 跑构建时 50–137G/天 | 热构建期：24h 修剪；冷却后：整清 |
| `/private/tmp` 后台车道工作区（`mg*gocache` 等） | 0→204G/3 天 | 静默>7h 判死删除（见第二步） |
| 各 Electron 应用升级包缓存 | ~1G/周 | 两处 glob 每周清 |

2. 永不触碰：源码工作区、工具链本体（fnm 的 Node 版本、`~/.rustup`、`~/.sdkman`）、聊天数据库（微信 Container）、`/Library/Developer`（CommandLineTools）、`/private/var/{folders,vm}`、`~/.Trash`（终端被 TCC 拦，走 Finder）。
3. 删除的唯一门禁是「可再生 + 不热 + 无占用」三条同时成立；任何一条不满足就降级处理（修剪 / 跳过 / 改日再清）。

## 第一步 量：定位大头（先量再删，永不凭印象删）

```bash
# 数据盘水位：Used/Avail/Capacity 一行看全；低于 10GiB 进入紧急流程（见第四步）
df -h /System/Volumes/Data
```

```bash
# 家目录三层扫描（顺序执行，每层只看 head）：顶层可见目录 → 隐藏目录 → Library
# -x 不跨文件系统；2>/dev/null 吞无权限噪音；⚠️ npm/pnpm/uv/gradle 这些大头全以 . 开头，第一层看不到
du -xsh ~/* 2>/dev/null | sort -rh | head -15
du -xsh ~/.[!.]* 2>/dev/null | sort -rh | head -15
du -xsh ~/Library/* 2>/dev/null | sort -rh | head -10
```

```bash
# 对最大目录逐层下钻直到定位到具体缓存；历史上 ~/Library/Caches 与 /private/tmp 各下钻两次即锁定
du -xsh ~/Library/Caches/* /private/tmp/* 2>/dev/null | sort -rh | head -20
# 本地 Time Machine 快照会吃可用空间且 Finder 不显示；本机历次实测为空
tmutil listlocalsnapshots /
```

## 第二步 判：删除前的安全门禁（三条缺一不可）

### 门禁一：可再生吗？

- 缓存（npm/_cacache、go-build、uv、Gradle caches）、升级包（*-updater、*ShipIt）、任务临时区 → 可再生，可删；最坏代价是首次重建变慢。
- 工具链、数据库、源码、配置 → 不可再生，不删（见全局结论 2）。
- ⚠️ 先确认路径再删：有人改过 GOCACHE/GOMODCACHE 时按默认路径猜会漏（本机翻出过遗留的 `~/gocache` 2.2G 和改名遗留的 `~/go/pkg/mod REALCACHE` 1.5G，`go clean` 都管不到后者）：

```bash
# 确认 Go 缓存实际位置，再决定清哪里
go env GOCACHE GOMODCACHE
```

### 门禁二：热吗？

```bash
# 判热：目录里 10 分钟内有新写入 = 热，整清会打断在跑的构建
find ~/Library/Caches/go-build -type f -mmin -10 2>/dev/null | head -2   # 空输出 = 已冷却
```

- **冷却** → `go clean -cache` 整清（实测 54G→8KB）。
- **热** → 只删旧条目。构建缓存是内容寻址的独立文件，并发构建下删旧条目最坏只触发重编译，实测四次安全（137→54G、127→43G、74→4KB、14→3.8G）：

```bash
# 热 go-build 修剪：只删超 24h 的条目，空目录连跑两遍（第一遍删文件后才能发现上层空了）
find ~/Library/Caches/go-build -type f -mmin +1440 -delete 2>/dev/null
find ~/Library/Caches/go-build -type d -empty -delete 2>/dev/null
find ~/Library/Caches/go-build -type d -empty -delete 2>/dev/null
```

- modcache 被在跑构建读取时同理跳过，等冷却。

### 门禁三：被占用吗？（/tmp 车道工作区专属流程）

```bash
# ⚠️ macOS 的 find -newermt 不吃 epoch，判目录静默用基准文件法：
ref=$(mktemp); touch -t "$(date -v-7H +%Y%m%d%H%M.%S)" "$ref"
# 目录内没有任何节点比 7 小时前的基准新 = 静默；有输出 = 活跃车道，自动豁免
find <目录> -newer "$ref" -print -quit 2>/dev/null   # 空输出 = 静默
```

```bash
# 静默车道 gocache 批量判死 + 删除（magpie 车道命名历经 magpie-*/hunt* → mp-* → mg123-*/mg-verify-* → mg-1108*，glob 要追新）
setopt null_glob   # ⚠️ zsh glob 无匹配默认中止整条命令
n=0; for d in /private/tmp/mg*gocache*(N); do
  [ -z "$(find "$d" -newer "$ref" -print -quit 2>/dev/null)" ] && { chmod -R u+w "$d" 2>/dev/null; rm -rf "$d" && n=$((n+1)); }
done; rm "$ref"; echo "已删 $n 个静默车道"
```

- 此规则经用户拍板为常设（四次实测删 29/46/35/171 个，回收 80/115/121/101GiB，活跃车道零误伤）；`/tmp` 超 100G 就该跑一次。
- 非车道类临时目录删前再查进程：`lsof +D /private/tmp 2>/dev/null | head`，只剩系统进程 = 无占用；所属应用还在跑就先退出（`osascript -e 'quit app "magpie"'`）再删。

## 第三步 删：按技术栈清理

### Go

```bash
# 编译缓存（冷却后）：历次大头 74–137G；清后首次构建变慢属正常
go clean -cache
# 模块缓存：默认 ~/go/pkg/mod；重新构建自动重新下载
go clean -modcache
```

```bash
# ⚠️ go 把模块缓存目录设成只读(555)：rm -rf 报 Permission denied，
# 末尾连锁出误导性的 "Directory not empty"。任何位置的 go mod 缓存都先补权限再删：
chmod -R u+w <目录> && rm -rf <目录>
```

### Node.js（npm / pnpm / yarn / bun）

```bash
# npm 缓存主力 _cacache（实测 18G）
npm cache clean --force
# ⚠️ clean 只管 _cacache；~/.npm/_npx（npx 运行缓存，实测 2.1G）不受管，按需整删
rm -rf ~/.npm/_npx
```

```bash
# pnpm：只清无引用包，活跃项目硬链接不受影响；store 实测 26G→10G
# ⚠️ 清不到 10G 以下是常态：剩余被现存工作区（如 /tmp 车道）硬链接占着，车道清完再 prune 才见效
pnpm store prune
# 元数据缓存整删
rm -rf ~/Library/Caches/pnpm
# ⚠️ store-dir 配置变过的机器会留游离 store（~/.pnpm-store、项目内 .pnpm-store），先查再删
pnpm config get store-dir
```

```bash
# yarn v1 直接清
yarn cache clean
# ⚠️ bun pm cache rm 在无 package.json 的目录报错，直接删目录：
rm -rf ~/.bun/install/cache
```

### Python

```bash
# ⚠️ 本机没有 pip 命令（zsh correct 还会把它纠错成 pip3/pp，输 n 按原样执行），用 python3 -m 走当前解释器
python3 -m pip cache purge
# ⚠️ purge 在多版本 Python 下清不干净（实测 882M 只清掉 159 个文件），整目录删才彻底
rm -rf ~/Library/Caches/pip
# uv 缓存（实测 7.6G）
uv cache clean
```

### Rust / JVM

```bash
# cargo 只删 registry 缓存；~/.cargo 其余是工具链本体
rm -rf ~/.cargo/registry/src ~/.cargo/registry/cache
# Gradle 构建缓存，重建自动恢复
rm -rf ~/.gradle/caches
```

### Electron 应用升级包

```bash
# ⚠️ 升级包缓存存在两处，两行都要跑（zsh 混用"可能已空"和"确定存在"的 glob 要拆开或开 null_glob）
setopt null_glob
rm -rf ~/Library/Caches/*-updater ~/Library/"Application Support"/Caches/*-updater ~/Library/Caches/com.microsoft.VSCode.ShipIt
```

### /tmp 与后台自动化应用

见第二步门禁三的批量流程。原则：活跃车道永不碰（用户常态在跑 magpie，车道 gocache 是其验证环境）；`~/.cache/magpie*`、`~/.cache/go-build`（magpie 沙箱私有缓存）、codex-runtimes（Codex 进程活时 3.5G）同属豁免，用户点名"除 magpie 之外"时全部跳过。

### Docker

```bash
# daemon 没运行时磁盘上也躺着 6.4G 虚拟磁盘镜像；清镜像/容器要先启动 Docker
docker system prune   # ⚠️ 会删未使用镜像和已停容器，确认无要保留的镜像
```

## 第四步 验：删除后复算

```bash
# 前后两次 df 对比 = 本轮真实回收量；目标目录 du 复查 = 删干净了没
df -h /System/Volumes/Data
du -xsh <刚删的目录> 2>/dev/null || echo "已删除"
```

```bash
# ⚠️ 单位换算：df/du 的 G 是 GiB，macOS 小组件/Finder 显示十进制 GB，227GiB≈244GB（GiB≈小组件GB×0.93）。
# 两边差 7.4% 是同一状态的两套单位，不是清完又涨了
```

**紧急流程**（可用 <10GiB，本机两次触发：1.5GiB / 753MiB）：盘满会打断在跑构建的写盘——先删最大可删项救急（历次都是车道静默清理一次回收 100GiB+），常规顺序反而可能来不及。

## 不建议动的位置

| 位置 | 大小 | 原因 |
| --- | --- | --- |
| `/Library/Developer` | 1.8G | CommandLineTools，git/编译器依赖 |
| `~/Library/Containers/com.tencent.xinWeChat` | 3.8G | 聊天记录数据库，清缓存走微信设置页 |
| `/private/var/folders` | 6.2G | 系统每用户缓存，重启自动清 |
| `/private/var/vm` | 1G | 虚拟内存交换文件，系统管理 |
| `~/.Trash` | 未知 | 终端被 TCC 拦（Operation not permitted），走 Finder 清倒 |
| `~/Library/Caches/dotslash` 残余 | 254M | 代码签名 .app 受 App Management TCC 保护，`chmod -R u+w` 和 `chflags -R nouchg` 都删不动（EPERM），不值得为此给终端授权 |
| `~/Library/Caches/ms-playwright` | 2.2G | UI 测试浏览器，重下很贵；magpie 任务期必用 |
| `~/Library/Caches/JetBrains` | 660M | 删了要重建索引，收益不值 |

## 长期防复发

1. **节奏**：磁盘健康期（>100GiB）每周跑一次「排查三连 + updater 两处 + pnpm prune」；`/tmp` 超 100G 加跑车道静默清理；go-build 的 24h 修剪可在 magpie 满负荷期安全执行，无需等冷却。
2. **历轮战绩**（有据可查）：10-24 三轮 ~215G（12→227GiB）；11-01 两轮 ~163G；11-05 ~86G；11-06 ~79G；11-07 ~11G；11-08 盘满救援 ~115G；11-09 ~101G；11-10 盘满救援 ~122GiB。合计约 890GiB。
3. **治本在应用侧**：/tmp 的车道工作区是后台应用"自建不自清"造成的，命令行清理只是止血；车道收尾自清或应用级清理配置才是断根。

## 关键坑位表（症状 → 根因 → 解法）

| 症状 | 根因 | 解法 |
| --- | --- | --- |
| `rm -rf` 报 Permission denied，末尾出 "Directory not empty" | go mod 缓存目录被设只读(555) | `chmod -R u+w && rm -rf`，别上 sudo |
| `pip cache purge` 清不干净 | 多版本 Python，purge 只清当前解释器 | 整删 `~/Library/Caches/pip`；命令用 `python3 -m pip` |
| `zsh: no matches found` 后半条命令没执行 | glob 无匹配中止整条命令 | `setopt null_glob`，或把"可能已空"与"确定存在"的 glob 拆成两条 |
| `find -newermt @epoch` 不生效 | macOS/BSD find 不解析 epoch | `touch -t "$(date -v-7H +%Y%m%d%H%M.%S)" ref` + `find <dir> -newer ref` |
| 清完小组件数字没涨 | df 的 GiB vs 小组件的十进制 GB | 换算 GiB≈GB×0.93，两套单位不是两个事实 |
| `bun pm cache rm` 报 no package.json | 该命令要求在项目内运行 | 直接 `rm -rf ~/.bun/install/cache` |
| `gh -f body=@file` 发出字面路径 | gh 对 @路径/emoji 路径不展开 | 用 `--body-file`；发帖后 GET 回读逐字节核对 |
| 热缓存整清后构建报错/变巨慢 | 在跑构建的条目被删 | 先 `find -mmin -10` 判热；热则 24h 修剪不整清 |
| 删签名 .app 缓存 EPERM | App Management TCC 保护 | 放弃（不值得给终端授权），等自然过期 |
| `go clean` 后还有大目录残留 | 改名遗留缓存（如 `mod REALCACHE`） | 清完扫一眼 `~/go/pkg`、`~/Library/Caches` 的大目录，按名核实再删 |

## 下次怎么用（检查单）

1. `df` 定水位 → `du` 三层扫描 → 下钻锁定具体目录。
2. 对每个候选目录过安全三问：可再生？热？被占用？（门禁一/二/三）
3. 按技术栈清单执行删除；go mod 缓存一律先 chmod；/tmp 车道用静默>7h 基准文件法。
4. `df` 复算回收量，验证目标目录已消失。
5. 记录本轮大头与增速，超阈值（/tmp>100G、可用<10GiB）进紧急流程。
6. 全程只删可再生缓存；遇到 Permission denied 先想"应用是不是故意设只读"，sudo 是绕过保护不是解法。
