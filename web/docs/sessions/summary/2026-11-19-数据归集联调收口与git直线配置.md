## 可复用经验与案例

1. **联调问题闭环验证链（三层）**：路由通 → 出数 → 展示。证据：68759 change-log 两天两态——11-12 上午路径 `changeLog→change-log` 修复后接口 code=0 但 `recordId=14624` 查 total=0（当天 updateProjectCost 保存成功过，应有 ≥1 条）；后端重启后同一 recordId 出「共 1 条」完整五字段。教训：报"验证通过"前必须用**历史写库对象**做正向出数复核，不能拿空数据的 recordId 的"不报错"当修复证据。
2. **IAB 自动化填写 React 受控输入（antd InputNumber/textarea）**：Playwright fill 不可靠时，`Object.getOwnPropertyDescriptor(HTMLInputElement.prototype,'value').set.call(el, v)` + `dispatchEvent(new Event('input',{bubbles:true}))`（textarea 用 HTMLTextAreaElement.prototype）。实测：填写金额+原因后走真实保存按钮，toast「保存成功」、写库生效（recordId=14624 同值保存）。属模拟用户输入的注入，不违反黑盒纪律（与 Playwright fill 同本质）；已在 2026-11-12 同值保存链路验证。
3. **git graph 颜色线**：图形工具按父线自动配色，粉色=pull merge 时从远端合进来的那条父线，无特殊语义；用 `git log --graph --oneline` 看拓扑即知（本轮 1d9b5f8 = 本地 c66083e 与远端 panyang 5 提交分叉后的自动 merge）。
4. **铺数复验的意外收益**：切到未铺数年份（2025）卡片变全 0——顺手证明数值是真实随接口联动而非缓存/写死，比只看 2026 有值更有说服力（health_contract 2026 有值/2025 全 0 双态对照）。

## 常用命令

```bash
# 定位 pull.rebase 配置来源（--show-origin 输出 file:<gitconfig 路径>）
git config --show-origin pull.rebase
# 本例发现：系统级 D:/DevTools/Languages/DevOpts/Git/etc/gitconfig 显式 pull.rebase false
# → 每次本地/远端分叉的 pull 自动产生 merge 节点

# 仓库级覆盖为 rebase（写 .git/config，不进仓库文件、不影响其他仓库）
git config pull.rebase true

# 核对分支拓扑（验证 merge 节点来源、分叉点）
git log --oneline --graph --all -18
```

成功信号：之后分叉 pull 时本地提交 rebase 到远端之上，历史单线；副作用=未推送的本地提交被改写（已推送提交 rebase 需 `--force-with-lease`，慎用）。

## 待验证与不适用边界

- **全局 pull.rebase 未配**：`git config --global pull.rebase true` 会改变本机所有仓库（含 fork 贡献仓）的 pull 行为，涉及 gua-pr-patch 仓的历史 merge 习惯，留待用户决定；当前仅数据归集仓库已配。
- **已存在的 merge 节点不处理**：1d9b5f8 已推远端，改写需 force push 会影响协作者（panyang），明确不做。
- IAB 截图 surface preparation timeout 仍间歇复现（本轮 2 次连续超时后放弃，改 DOM 断言+用户手动截图）——与记忆中"间歇可用"结论一致，非稳定通道。
- 健康管理 2025 年数据为空是环境事实（后端只铺了 2026），非接口缺陷；将来 2025 铺数后"全 0"预期失效，勿再当对照样例。
