# 顺序脚本的失败前沿

## 一句话结论

有序、遇错即停的表单脚本里，异常点名的那一步才是失败前沿；它后面的字段仍是脚本没碰到的默认值。本对话里日期截图（迭代跨度）不能证明日期写入失败，因为动作死在更早的处理人等待。日期与处理人在真实创建页上仍未闭环。

## Skill 增量建议

目标：`gua-dev-tools` / `modules/bug/MODULE.md`，放在「根因而非症状」之后，不另开规则、不改主 `SKILL.md`。

现有规则已覆盖、本轮是执行反例，不追加同义条文：

- `modules/quality/references/verify.md`：结构测试全绿不能宣称修好；产物未确认前不叠第二版修改。本对话多次在 FakeDriver 单测全绿后继续改定位器，且 uvicorn 无 `--reload`，旧进程会继续跑旧代码。
- `modules/bug`：先诊断、一次一个根因、症状不等于根因。

缺口：上述规则没有写明「失败前沿」。建议追加：

> **顺序脚本的失败前沿**：fail-fast 的有序动作（表单自动化、批处理）抛在第 N 步时，第 N 步之后的界面仍是未触达的默认值。不要把后段字段的截图当成后段写入逻辑的失败证据。等待与执行必须用同一匹配原语：XPath `text()` 只看直接文本节点，`textContent` 含后代；文案被拆到子节点时，用 `text()` 等待会永远超时。成功判据用已提交的值（隐藏域或控件 API），不用可见文案。后序操作会覆盖该值时，写入放在这些操作之后。

来源：用户贴出的 `ActionError: 动作 [wait_text guantianhao(关天豪)]`；`tapd_automation.py` 里 `build_task_actions` 把 `set_value` 日期排在该 `wait_text` 之后；`_text_contains_xpath` 使用 `normalize-space(text())`，`_click_text_js` 使用 `textContent`。

适用边界：有序且遇错即停的自动化。并行步骤、失败后仍继续的脚本不适用。

检验场景（未执行）：脚本在第 N 步超时，页面第 N+1 个字段仍是进入页时的默认值。正确判断是「第 N 步没过，后面没跑」；错误判断是「去改第 N+1 步的写入」。

`gua-writer`、`gua-pr-patch` 不收录。这不是文档写法，也不是上游 PR。

## 可复用经验与案例

问题：TAPD 创建页预计开始/结束停在迭代跨度（截图为 2026-09-08～2026-09-30），多次修改后仍报错。

关键证据：

| 证据 | 性质 |
| --- | --- |
| 堆栈停在 `wait_text guantianhao(关天豪)`，其前还有过 `wait_value parent_id`（隐藏框被当成可点击）和 `wait_value owner` | 用户贴出的 traceback |
| 日期动作在处理人校验之后 | 源码 `build_task_actions` |
| 空表单上 jQuery UI `datepicker('setDate')` 把 `#StoryBegin` / `#StoryDue` 写成了指定日；未初始化时 `dateFormat` 为 null | 本对话对本地 `/api/probe` 的返回 |
| 选迭代会把日期改成迭代区间；直接改 input value 不会走 datepicker | 同上，空表单探针；有迭代后的页面未被这次探针覆盖 |
| 处理人是隐藏域加一个可见输入；可见文案常被拆开 | `/api/probe` 字段列表 |
| 14 个 FakeDriver/动作序列测试通过 | `unittest discover tests` 退出码 0 |
| 创建请求仍失败，用户截图日期仍是跨度 | 用户报告，发生在测试通过之后 |

根因（已证实的部分）：脚本线性失败。处理人 `wait_text` 用 `text()` 等完整显示名，下拉文案不在单一文本节点里，于是超时；日期代码没执行。隐藏域不能用「可点击」去等。

取舍：成功看隐藏域是否含 nick、日期看 datepicker 提交后的 value。可见文案只适合和点击使用同一 `textContent` 原语时再等。日期写入应放在会改日期的下拉之后。这些修改写进了源码和单测，**没有**在真实创建请求上复验。

下次复用：再看到「后面的格子是错的，但堆栈停在前面某步」，先让该步通过，再看后面。

## 常用命令

Windows，工作目录为该工具仓库。单测只证明动作脚本和假驱动，不证明 TAPD 页面。

```powershell
.\.venv\Scripts\python.exe -m unittest discover tests -v
```

前提：已有 `.venv`。成功信号：`OK` 且失败数为 0。副作用：无。本对话结果：14 通过。

```powershell
netstat -ano | findstr :8801
tasklist /FI "PID eq <pid>"
```

前提：要确认 8801 上是不是仍是旧的 `python.exe`（本服务没有 `--reload`）。成功信号：`LISTENING` 且映像名为预期进程。副作用：无。⚠️ 随后的 `Stop-Process -Id <pid> -Force` 会关掉该进程；只在确认是这个本地服务时使用。本对话曾因此遇到绑定 `10048`（端口仍被占用）。

`pnpm install`（pnpm 12.4.2）本次长时间无输出后被中止，不能当作可用安装命令。当时能装上依赖的是：`python -m venv .venv` 后用该 venv 的 pip 安装 `pyproject.toml` 里的 fastapi / uvicorn / selenium。

## 待验证与不适用边界

未闭环，不能当成已修好：

- 真实点击「创建任务」后，开始和结束是否都变成所选日期，处理人隐藏域是否含 nick。空表单 `setDate` 成功，不能外推到选完迭代之后。
- 配置里的浏览器路径仍指向 Edge；本对话后段堆栈是 `msedgedriver`。一次查找 Chrome/Edge 的命令没有正确展开 `ProgramFiles(x86)`，不能据此说机器没有 Edge。
- pnpm 12 的 Python 依赖安装会不会在本机完成，未再验证。
- 内嵌页 `Date` 偏 UTC、服务端按中国时区给默认日：只在 `/api/config` 的 `today` 上见过返回值，没有用创建结果复核。

不适用：这条经验不用于并行或失败后继续的流程；TAPD 的字段名和 datepicker 写法不写入通用 Skill。
