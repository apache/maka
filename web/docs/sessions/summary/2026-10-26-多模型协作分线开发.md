# 多模型协作分线开发

**一句话总结**：UI 改版与多模型协作可以分线推进；先复用现有能力验证协作闭环，再集成界面，不必等 UI 合入 main。

## 背景

准备在现有模型网关上增加“主控＋不同模型的子 Agent”，同时进行 UI 改版，担心两个需求必须串行开发。本次通过源码与分支核查，整理了独立开发、后续集成的计划和审核提示词，尚未实施协作功能。

## 核心命令

以下 Git 命令均在对话中实际执行有效；一次性路径和提交值已替换为占位符。

```bash
git -C "<仓库目录>" status --short # 开工前检查已有修改和未跟踪文件，避免覆盖他人工作
git -C "<仓库目录>" branch --show-current # 确认当前分支；输出为空时可能处于 detached HEAD
git -C "<仓库目录>" rev-parse HEAD # 记录实际基线提交，不只记分支名
git -C "<仓库目录>" merge-base --is-ancestor "<旧提交>" "<新提交>" # 判断旧提交是否已包含在新提交的历史中
```

`-C` 指定命令作用的仓库，适合同时管理多个 checkout。最后一条命令通常没有正文输出：退出码 0 表示是祖先，1 表示不是，其他非零值需要检查错误；本次祖先关系检查返回 0。上述命令均为只读，不会创建、切换或合并分支。

## 关键结论

1. **UI 合入 main 不是协作功能的技术前置。** UI 线负责布局与交互，协作线先用现有配置入口验证派遣和结果回传；两边都有可验收成果后，再由集成线接入新版界面。
2. **不同分支不等于互不干扰。** 还需要独立工作目录、明确共享文件归属，以及隔离配置、端口和运行数据。工作区干净也不代表没人使用，认领前仍要核对。
3. **先检查已有配置，再增加功能。** 本次核查时，Magpie 已有默认子模型与网关统一子模型；统一目标可能覆盖逐任务模型选择，并不等于按角色分配多个模型。新增角色配置前，应先验证现有能力及优先级。
4. **别把三种需求混成一个。** 独立子 Agent 使用不同模型、同一会话分阶段换模型、调用另一套 coding-agent 客户端，是不同机制。第一期选定一种，不因为参考 Pi 就同时引入全部能力。
5. **配置成功不等于协作成功，计划也不等于交付。** 模型出现在列表中或配置保存成功，还需验证子任务能读取输入、调用正确模型并把结果交回主控；任务格式与后端兼容性也可能限制跨模型。本次只完成方案与审核提示词，没有创建业务开发分支、实施协作功能或完成真实模型联调。

以上项目实现情况是本次对话中的历史核查结论，后续开发前应重新核对，不视为当前版本保证。
