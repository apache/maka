# TDD 交付验证三支柱与 CI 排障(maka 贡献实战)

**一句话总结**:把 magpie 的「消红/兄弟面/真实环境实证」验证三支柱落地到 maka 的 TDD 交付,连出 13 个零 CI 回退的 PR,并用「仓库自带校验器」排查清掉两个 CI 红。

## 背景

在 apache/maka 做贡献(自报 issue→TDD 修复→PR),连续交付后发现两个 PR 的 CI test lane 红;同时总结出一套每单必过的验证纪律,使 29 个 PR 中已出终态的 28 个零 CI 回退。本笔记沉淀真正可复用的命令与结论。

## 核心命令

```bash
# 依赖安装(必须 --ignore-scripts,否则 postinstall 产物缺失)
npm install --ignore-scripts --no-audit --no-fund

# 安装后必须补跑 patches,否则部分包构建失败
node scripts/apply-dependency-patches.mjs

# 构建链缺一环 = 下游 TS2307「Cannot find module」
npm --workspace @maka/core run build    # 顺序:core→storage→mcp→runtime→acp→antigravity→runtime-host→…→ui

# 生成缺失的代码产物(报 model-metadata.generated.js 缺失时)
npm run sync:model-metadata

# 单跑一个测试文件(不接管道 tail,吞退出码出假绿)
npx tsx --test packages/runtime/src/__tests__/xxx.test.ts

# 整仓格式门(本机 biome 段错误 139 的退路=改动文件逐个)
npx biome format packages/x/src/file.ts

# 协议 epoch 守卫(改 protocol/ 后必跑,输出 "epoch moved" 且退出码 0)
node scripts/protocol-epoch-check.mjs --base upstream/main --head HEAD

# 渲染器架构守卫(工作目录必须在 apps/desktop)
cd apps/desktop && node scripts/check-renderer-architecture.mjs --base <merge-base>

# Windows skip 清单:新增带 win32 守卫的测试后必跑,否则 CI 红「inventory is stale」
npm run windows:inventory:write   # 再生 docs/windows-test-inventory.md
npm run windows:inventory         # 自检通过(137 declarations)

# 预存失败定性:对照干净基线(含 untracked 必须 -u)
git stash push -u -- <改动文件>
npx tsx --test <同一套件>          # 失败集合同名同数 = 预存,与改动无关
git stash pop

# 推送到 fork(显式 SHA,不依赖本地分支位置)
git -c credential.helper='!gh auth git-credential' push https://github.com/<fork>.git <SHA>:refs/heads/<分支>

# CI 失败排障:拉失败日志找根因,而不是盯 UI 红点猜
gh run view <runId> --repo <upstream> --log-failed > /tmp/ci.log 2>&1
rg -n "✖|not ok|AssertionError|##\[error\]" /tmp/ci.log | head
gh run rerun <runId> --repo <upstream> --failed   # flake 定性后重跑失败 lane
```

⚠️ `git push` 系列会改远端状态;显式 SHA 推送比分支名安全(不裹挟本地未推提交)。

## 关键结论

1. **消红要打到语义分叉行**:新测试先在未修基线红,变异点必须是语义真正分叉的那一行。首版修法若打挂既有顺序测试,是修法错了——改模型不改测试(实例:completion 标记按 Host 时序在 deferred 通道「中间」,append-to-tail 方案打挂既有测试,最终改 splice 模型)。
2. **「读失败≠空」是跨域复发的反模式**:同一形态在 onboarding 凭据、character-pack、mcp oauth、filesystem pinned read 四个域各杀一次——读失败折叠成空/默认值,轻则误导重试方向,重则引导整文件盲覆写。修法统一=抛「读失败」明确错误(fail-closed),照同文件已有的诚实先例(如 `previous = 'unknown'`)。
3. **CI 红先定性再动手**:三个常见根因——①改动面零交集的时序测试挂(并发 run 争用,rerun 即绿,`gh run rerun --failed`);②新增平台 skip 测试未登记 Windows 清单(真问题,跑 inventory:write);③本机预存失败(用 stash 对照父提交,失败集合同名同数即预存)。直接重试或修根因,不盲猜。
4. **worktree 纪律**:merge main 后必须重建 dist 再跑测试(陈旧 dist 的报错=「新导出名缺失」SyntaxError,易误判为冲突破坏);测试文件的 codegen 产物(.artifacts)有独立生成脚本,缺了也是加载失败不是逻辑错。
5. **注释承诺 vs 实现是审计最高产锚点**:"escapes have to be caught lexically"(自承局限)、"in one synchronous commit"(实现劈开)——注释写明的契约被实现打破,是可直接报确定性缺陷的强信号。

## 下次怎么用

任何 TS monorepo 贡献场景可直接套用:新单按「issue→独立 worktree→TDD 红→消融回红→绿→矩阵(tsc/整仓 format/asf)→推送→PR 四段」;CI 红按「拉 log-failed→rg 定位→分类(我方/预存/flake)→对应处置」;仓库自带的校验器(inventory/epoch/守卫脚本)优先于手工检查——先 `package.json` scripts 里找,再写任何自定义验证。
