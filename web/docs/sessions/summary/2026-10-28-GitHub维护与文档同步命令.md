# GitHub 仓库维护与文档同步的实用命令集
**一句话总结**：批量管理 fork 仓库 PR/issue 的 git/gh 命令组合，加上大体积 Markdown/XLSX 文档程序化维护的验证技巧。

## 背景
维护十几个 fork 仓库的在途 PR 和 300+ issue 的跟踪台账，需要批量检测冲突、rebase 后验证语义无漂移、同步巨型文档且不弄断链接；期间踩了 gh 与 zsh 的几个坑。

## 核心命令

```bash
git merge-tree --write-tree upstream/main origin/<分支>   # 批量预检所有在途分支有无合并冲突（退出码 0 干净 / 1 冲突），比逐个 checkout 快得多
git tag --contains <sha> | grep -E '^v0\.1\.' | sort -V | head -1   # 查某提交首发于哪个版本 tag；必须过滤掉维护者随手打的非版本 tag（如 pf-v2），否则结果被污染
git range-diff <旧base>..<旧head> <新base>..<head>        # rebase 后验证语义零漂移，逐 hunk 对照新旧两版
git -c user.name=xx -c user.email=xx@yy commit -F msg.txt # 临时指定提交身份 + 从文件读提交消息（-F 会保留 # 开头行，-m 不会）
gh issue comment <N> --repo <org/repo> --body-file post.md   # 发 issue 评论的标准姿势；POST 报错≠没发，先 GET 回读再决定重不重发
pip install openpyxl --user --break-system-packages       # macOS 受 PEP 668 保护的系统 Python 装包
git mv 旧路径 新路径                                       # 目录重组必须用 mv 保历史（rename 检测）
```

## 关键结论

- **`gh issue close --comment` 的参数是字面文本，不读 `@file`**——把文件路径传进去，11 条评论全变成路径字符串。安全做法：用 `gh issue comment --body-file` 发正文，再 `gh issue close` 单独关。任何发帖后都要 GET 回读核字数/关键句。
- **`git rebase` 会把提交消息里以 `#` 开头的行当注释剥掉**（如 `#3525 xxx` 整行消失）。补救：`git commit --amend -F 原消息文件` 恢复后逐字节比对。
- **维护巨型 Markdown 表格**：每行追加/改写后用 `awk -F'|' '/关键字/ && /^\|/ {print NF-2}'` 校验列数——行内写 `||` 会被 Markdown 吃成单元格分隔符，列数立刻暴露。
- **文档分层消灭复制粘贴**：公共纪律收进一个共享文件（docs/handbook/12），各仓任务书只留一行链接指针+仓专属内容；入口 README 按项目名路由。九份文件改一遍公共内容从"改九处"变"改一处"。
- **改相对链接后要模拟解析验证**：`os.path.normpath(os.path.join(base, dir, "../../../target"))` 逐个确认文件真实存在，`../../` 和 `../../../` 差一层就全断。

## 下次怎么用
批量维护多个 fork 仓库时：开场先 `merge-tree` 批测一遍冲突面，只对真冲突的分支做 rebase（`range-diff` 验证）；对 GitHub 的发帖/关单动作一律 `--body-file` + 回读；台账类大 Markdown/XLSX 用脚本改、改完必做行列数校验。仓库目录重组用 `git mv`，改完链接跑一遍 normpath 解析检查。
