# 活动管理契约与文案核对

统计排行的取数粒度、页面标题和部署状态各有证据来源。本案最终保留原型标题「热门活动 TOP5」，前端差异只剩注释，并在接口定义及后端核对报告中留下待验证项。

## 可复用经验与案例

- **展示名称与数据粒度分别核对。** 本地 `ActivityStatMapper.topActivities` 按场次排序，先排除 `willnum` 为 0 或空的记录，再 `LIMIT 5`。首次补丁据此把标题改成「热门场次 TOP5」，用户随后引用三端原型和截图，明确沿用「热门活动 TOP5」。最终 `statSummary/index.jsx` 的 diff 只改了该卡片的注释。下次核对统计项，分别记录产品文案、行粒度、排序和过滤，逐项确认哪些需要改。
- **聚合请求带筛选参数时，逐块追参数落点。** 本地 `ActivityStatAppService.join` 对 KPI 和 `typeBars` 使用空日期范围，`joinList` 才接收明细筛选。`summaryKpi` 的 SQL 则拼接了 `activity_date` 条件，与 R-62 的全量口径冲突。前者更新过时注释，后者保留差异，避免前端额外造请求来拼全量。用同一组织、能排除基准记录的两组筛选逐块比较响应，才能验证目标环境。
- **默认分页范围有争议时，先核遗漏参数经过哪一层。** 本地 `ActivityPcQueryMapper` 的默认分支为 `ap.state=1`，覆盖有效报名，`signInState` 另外参与过滤。规则说明 R-77/R-80 写的是默认 `APPLIED`。本轮未取得目标环境的聚合接口响应，保留现有传参和分页。后续用同时含 `APPLIED`、`SIGNED` 的场次对照无状态、`signInState=0`、`signInState=1` 三次响应的行状态及 `page.total`，再判断是否缺少全部有效报名的分页能力。

## 常用命令

在 Git 仓库根目录核对注释补丁和受影响文件的行尾。以下两条均在本对话执行过，此处将路径参数化。

```bash
git diff -- <模块目录>
git ls-files --eol -- <已跟踪文件路径>
```

逐段确认 JSX 文案、请求参数和逻辑是否进入 diff。行尾看工作区一列，例如 `w/crlf`，索引显示 `i/lf` 可与它并存。这两条命令只读，`git diff` 默认查看未暂存改动，本案也以工作区补丁为核对对象。
