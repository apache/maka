# PR 评审修复与消融验证
**一句话总结**:在 apache/maka 维护多个在途 PR 的一天:修掉 bot 评审的 5 条 P2、两次消融验证翻车自纠、定位三类"本地全绿 CI 仍红"的治理门,沉淀 GitHub API 与测试验证的可复用套路。

## 背景
上游仓库节奏极快(维护者当天自修+评审 bot 每轮出具体复现),我的在途 PR 反复吃到"本地全绿、CI 仍红"和"fake 测试全过、真实装配编译失败"的教训,逐个排查修复。

## 核心命令
```bash
# 查自己在某仓库的 open PR(评审状态/可合并性一把拿)
gh pr list --repo OWNER/REPO --author ggbdpq --state open --json number,updatedAt,reviewDecision,mergeable

# 确认 PR 是否真的被合并:squash 合并后 PR 先显示 APPROVED+closed,mergedAt 才是真相
gh pr view N --repo OWNER/REPO --json state,mergedAt,mergeCommit

# 接单前查占坑:有没有别人的 open PR 引用了这个 issue
gh api "search/issues?q=is:pr+is:open+repo:OWNER/REPO+ISSUE号"

# issue 评论按时间【正序】返回:per_page=N 直接取尾拿到的是最老的,必须翻满再取尾
gh api "repos/OWNER/REPO/issues/N/comments?per_page=100" --jq '.[-3:][]'

# 回复 review 线程:in_reply_to 必须写进 JSON body(--input 与 -F 混用会静默丢参数,报 422)
gh api -X POST repos/OWNER/REPO/pulls/N/comments --input body.json

# 分支被已删除 worktree 的残留元数据占用时:先 prune 再 add
git worktree prune && git worktree add /tmp/wt-xxx 分支名

# 消融验证:只回退实现、保留测试——测试必须真的会红,否则它没锁住任何行为
git stash push -- src/实现文件.ts && 构建 && 跑测试(期望红) && git stash pop && 重跑(期望绿)
```

## 关键结论
1. **本地全绿 CI 仍红的三种模式**:①仓库治理门(例:某个 gate 脚本里列出的测试文件必须"触达"对应 CI lane,新测试要注册进清单);②单文件格式化过 ≠ 整仓过,提交前必须整仓跑一次 format;③改协议/接口文件要 bump 兼容版本号或声明兼容,且与 sibling PR 同号撞车时要顺延。排查入口:CI 失败先看 `--log-failed` 定位到具体步骤,再分三类对号。
2. **fake 测试依从实现签名会漏真 bug**:改公共接口(给 fake 补新方法)时,类型对了、fake 全绿,但真实装配路径根本没接上(CI 编译失败+运行时双包装)。修公共接口后必须 grep 所有 fake/mock 实现同步,且至少一个测试走真实装配代码。
3. **消融验证的两个坑**:①消融后要确认构建产物真的变了(旧 dist 会让"红"变成假绿,可 grep 产物里的新符号);②测试场景必须真正经过被测分支(一次消融不红,排查发现场景里先做了清理,重发请求根本没走到 retry 分支)。
4. **重试路径不能有写副作用**:给"已成功操作的查询重放"加补偿时,用"存在才复用"的幂等语义会在记录被删后重新创建它(撤销别人的删除)——重放必须只读,查不到就让它缺席,让调用方的失败守卫兜底。
5. **真实浏览器是唯一裁判**:contenteditable 的光标形态(Shift+Enter 后停在 `\n` 文本节点 offset 0)jsdom 的 Range 桩模拟不出来,Storybook + headless Chromium 实测滚动数字(96→118,还原修法变 89-96)才算验证。

## 下次怎么用
- 给开源仓库提 PR:开工前占坑双查(PR 引用 + assignees 字段);每轮盯 review threads 的 `isResolved`;维护者 bot 的意见都附具体复现/数字,对抗验证成立就照单全修。
- 改公共接口/生命周期:全局 grep 测试里的 fake 实现同步补齐;提交前整仓 format;每个新测试做一次消融,并检查消融后产物真的变化、场景真的走被测路径。
- 修"资源删了又复活"类 bug:先分清恢复路径是写操作还是读操作——重放/补偿场景下只允许读(读不到就让调用方显式失败),写操作会静默撤销他人的删除。
