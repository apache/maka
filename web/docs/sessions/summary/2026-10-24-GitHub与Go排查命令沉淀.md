# GitHub PR 排查与 Go 修复验证命令沉淀

**一句话总结**：一轮开源仓库维护里实测有效的 GitHub API 查询、git 隔离/回退与 Go 测试验证命令，及三个踩过的坑（分页正序陷阱、force-with-lease 基线、big.Float 解析边界）。

## 背景

维护一条有 9 个在途 PR 的开源仓库分支线：批量核对 PR 评审状态、把落后分支 rebase 到上游最新、修两个评审发现的 bug。过程中沉淀出一批跨项目可复用的命令和排查方法。

## 核心命令

```bash
# 在独立 worktree 里改代码，不碰当前工作区分支（收尾用 remove 清理）
git worktree add /tmp/wt-<名字> <分支名>
git worktree remove /tmp/wt-<名字> --force   # ⚠️ --force 会丢弃该 worktree 内未提交改动，先确认 status 干净
```

```bash
# TDD「修前红」复核：只 stash 被修文件，新测试应转红，pop 后转绿
git stash push -- <被修的文件.go>
go test -p 1 -run 'TestXxx' ./包路径/        # 期望 FAIL
git stash pop
```

```bash
# GraphQL 一次聚合查多个 PR 的评审状态（比逐个 REST 快且能拿到线程 resolved 状态）
gh api graphql -f query="$(cat q.graphql)"
# q.graphql 内容形如：
# query { repository(owner: "ORG", name: "REPO") {
#   p1: pullRequest(number: 111) { ...F } p2: pullRequest(number: 222) { ...F }
# } }
# fragment F on PullRequest { number headRefOid reviewDecision mergeable
#   reviews(first: 100) { totalCount nodes { author { login } submittedAt } }
#   reviewThreads(first: 100) { totalCount nodes { id isResolved isOutdated path } } }
```

```bash
# ⚠️ 坑：issues 评论 API 恒为正序，sort/direction 参数被忽略，
# per_page=5 直接取的是最早的 5 条；取最新必须拿末尾
gh api "repos/ORG/REPO/issues/N/comments?per_page=100" --jq '.[-3:][] | "\(.created_at) \(.user.login)"'
```

```bash
# 强推 rebase 后的分支：lease 基线用「远端当前 SHA」显式声明，
# 推前先 fetch（本地 origin 跟踪引用不随 URL 推送更新，stale lease 会被拒）
git fetch origin <分支名>
git push https://github.com/<user>/<repo>.git <新sha>:refs/heads/<分支名> \
  --force-with-lease=refs/heads/<分支名>:<旧sha>   # ⚠️ 强推会覆盖远端历史，确认旧 sha 是你预期的基线
```

```bash
# Go：-p 1 串行编译，避免全并发把编译器搞崩（大仓实测偶发）；-count=1 禁缓存
go test -p 1 -count=1 ./internal/config/ ./sdk/...
# Windows/autocrlf 环境下 gofmt 全文件假阳性，先去掉 \r 再判定
tr -d '\r' < file.go | gofmt -l /dev/stdin
# 构建冒烟：能出二进制即通过
go build -o /tmp/build-check ./cmd/server && rm /tmp/build-check
```

```bash
# 排查「函数到底返回了什么」：写临时探针测试直接打印真值，跑完即删
cat > pkg/probe_test.go <<'EOF'
package pkg
import ("fmt"; "testing")
func TestProbe(t *testing.T) { fmt.Printf("val=%v ok=%v\n", f(), g()) }
EOF
go test -p 1 -run TestProbe -v ./pkg/ ; rm pkg/probe_test.go
```

```bash
# rebase 前扫「同域提交」确认分支没被上游取代、预估冲突面
git log --oneline <我的分支>..upstream/dev -- <我改的文件路径>
```

## 关键结论

- **issues 评论分页是正序陷阱**：GitHub REST 的 issue comments 端点不吃 `sort=created&direction=desc`，`per_page=N` 给的是最早 N 条。用 `.[-N:]` 从尾部取，否则会把 9 月的旧评论当成最新状态。
- **force-with-lease 的基线是本地 origin 远端跟踪引用**：直接 `git push <URL>` 不会更新该引用，lease 判定用的还是旧值，要么被拒（stale info）要么误放行。推前 `git fetch origin <分支>`，或用 `--force-with-lease=<ref>:<精确旧sha>` 显式声明。
- **修 bug 先造能红的最小反馈环，红错了就下探**：本轮一个 404 分类的 bug 连换三种错误构造都没红对，最后写探针直接打印中间分类函数的真值（`isRequestScopedResultError` / `isModelSupportResultError`），才发现错误形态被更早的分类拦住——换用能走到目标分支的形态后才红中真症状。
- **「关键字存在即保留/删除」的 presence-only 判定会悄悄放宽契约**：JSON Schema 转写里越界 `exclusiveMaximum` 改写为上限 edge 时，若 schema 已有另一个更松的 `maximum`（如小数形式），只判断「存在」就删 exclusive 会丢掉更严的 edge。正解是数值比较留严者（`math/big.Float` 512 位精度可精确比较科学计数法）。
- **Go `big.Float.SetString` 对超界指数返回 `(nil, false)` 而非 ±0**：用 `ok` 做 fallback（「解析失败按不覆盖处理」）会误伤合法输入；对 JSON 数字这类语法必然合法的场景，应直接用返回值参与比较，仅防 nil。
- **搜索 API 会假空**：GitHub search API 曾对同一仓库返回 `total_count=0`，而 REST 端点明明有数据。关键判定用 REST 交叉验证，别单信 search。

## 下次怎么用

- 维护有多个在途 PR 的分支：先用 GraphQL 模板批量拉状态定优先级，再对落后分支按 `git log A..B -- <路径>` 判断「被取代 / 有同域冲突 / 无交集」，只对前两类做 rebase。
- Go 仓修 bug：worktree 隔离 → 红测试（stash 复核）→ 修 → `go test -p 1` + `go build` 冒烟 → `gofmt` CRLF 法 → force-with-lease 显式 SHA 推送。
- 任何「函数返回值与预期不符」且读代码看不出原因的场景：直接写探针测试打真值，比反复读代码猜快得多。
