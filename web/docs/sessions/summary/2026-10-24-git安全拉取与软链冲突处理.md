# 有本地改动时安全拉取远程代码（含符号链接坑）

**一句话总结**：在跨机器同步的家目录仓库上，带着几百个未提交改动安全拉取远程代码——fetch 后先算清楚重叠面，按"远程为基准、本机独有信息补回"解决冲突，遇到符号链接导致的合并死锁就用"只清索引 + 临时挪走软链"化解。

## 背景

家目录用 git 在 Mac 和 Windows 之间同步，远程来了新提交，本地堆着工具自动写入的状态文件和一次"技能目录软链化"改造（几百个文件显示为已删除，其实是换成了符号链接）。直接 merge 会失败，更危险的是可能穿过软链把真实文件删掉。

## 核心命令

### 第一步：只读侦察，不动任何东西

```bash
git fetch origin --prune                              # 拉远程引用，不动工作区，可以随便看
git rev-list --left-right --count main...origin/main  # 本地领先/落后几个提交（左边本地，右边远程）
git status --short | grep -v '^??' | cut -c1-2 | sort | uniq -c  # 本地改动类型分布：M 改 / D 删
comm -12 <(git diff --name-only main origin/main | sort) <(git diff --name-only | sort)  # 远程改动 ∩ 本地未提交改动 = 真正会打架的文件
git ls-tree -r --name-only origin/main -- 某目录/     # 目标分支该目录的真实文件清单，比 diff 过滤器可靠（diff 会漏 rename）
```

### 第二步：暂存、合并、恢复

```bash
git stash push -m "说明" -- 某文件    # 只暂存指定文件，其他改动留在工作区；比整体 stash 抗特殊路径
git merge --ff-only origin/main      # 只允许快进合并：要么干净前进，要么明确报错，绝不产生意外合并提交
git stash pop                        # 恢复暂存；有冲突时 stash 条目自动保留，内容不会丢
```

### 第三步：解决冲突的四个常用动作

```bash
git restore --source=HEAD --staged --worktree -- 某文件  # 索引+工作区一键恢复到远程版（"取远程"解决冲突）
git show HEAD:某文件 > 某文件                            # 只取内容覆盖工作区，适合"取远程后再手工补东西"
git restore --staged -- 某文件                           # 只把索引退回 HEAD，工作区改动保留（取消暂存/清除冲突状态）
git rm --cached --ignore-unmatch --pathspec-from-file=清单.txt  # ⚠️ 只从索引删条目，不碰磁盘文件。误用于需要继续跟踪的文件会造成批量"已暂存删除"，务必先核对清单。清单用 git ls-tree -r --name-only 生成，一行一个路径；--ignore-unmatch 让已不存在的路径不报错
```

### 收尾检查

```bash
git diff --name-only --diff-filter=U   # 列出所有未合并（冲突）路径，应为空
git diff --check                       # 检查是否残留冲突标记
```

### zsh 小坑

```bash
g() { git -C ~/某个仓库 "$@"; }   # zsh 的 $变量 不会按空格拆词，G="git -C 路径" 再 $G xxx 会把整串当命令名报 127；要用函数
```

## 关键结论

1. **有未提交改动时拉取的标准姿势**：先 fetch 再对比，`--ff-only` 兜底。重叠面算清楚再决定 stash 什么，别一上来 stash 全部——工作区里有符号链接等特殊路径时，整体 stash 会直接失败。
2. **警惕重命名误判假冲突**：git 按内容相似度（本例 59%）把两个无关文件当成重命名，stash pop 会把 A 文件的本地改动硬套到 B 文件上。先看清两边文件的真实身份，再各自取正确版本，别被冲突标记带偏。
3. **符号链接会让 git 自相矛盾**：status 把"链接之后的路径"判成已删除，merge 的检查却穿透链接看到真实文件。合并前必须确认 merge 不会穿透软链删真实内容——本次最大的坑，差点把技能真身目录删掉。
4. **软链/生成文件导致合并死锁的解法**：`git rm --cached` 清掉索引条目（让 merge 对这些路径无事可做）+ 临时 `mv` 走挡路的软链 + merge + `mv` 回来。最终结果和远程后来提交的 .gitignore 注释不谋而合："git 不识 junction，会形成双份跟踪"——仓库自己的意图就是不再跟踪链接后的内容。
5. **工具自动生成的状态文件跨机同步必然打架**，处理原则：纯时间戳类取较新版本直接覆盖；本机独有的配置条目（如 trusted 项目授权）合并后手工补回，一两行的事，别试图"保住每一字节"。

## 下次怎么用

- **场景 A（通用）**：有未提交改动想 pull——fetch → `rev-list` 看差距 → `comm` 算重叠 → 重叠少就单文件 stash → `merge --ff-only` → pop → 按上表四选一解决冲突 → `--diff-filter=U` 和 `--check` 收尾确认。
- **场景 B（仓库里有软链/junction）**：动手前先 `ls -la` 摸清链接链路，用 `git ls-tree -r --name-only origin/main -- 目录` 确认远程对真身到底删没删；确认"远程删除 = 本地意图"后再上 `rm --cached` + 挪链接的组合拳；合并完抽查真实文件还在不在。
- 拿不准时记住安全底线：fetch、status、diff、ls-tree 全是只读的，随便跑；会改状态的操作（stash、merge、rm、restore）每次只做一步，出错就 `git restore --staged` 退回。
