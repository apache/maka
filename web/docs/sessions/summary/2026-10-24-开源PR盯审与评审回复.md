# 开源 PR 盯审与评审回复

**一句话总结**：维护多个开源在途 PR 时，用 merge-tree 预探冲突、共享 worktree 验证、API 回读核推送，把"依赖审计红""工具链升级潜伏红""评审者漏读代码"三类高频事件标准化处置。

## 背景

同时在两个开源仓（cc-switch、apache/maka）维护约 15 个在途 PR：上游一周连发多个版本，分支陆续落后 base；维护者评审意见有真有漏读；推送和审计在镜像/代理环境下各有坑。本轮把反复出现的问题沉淀成固定处置动作。

## 核心命令

```bash
git fetch upstream && git merge-tree --write-tree upstream/main origin/<branch>
# 不切分支预探合并冲突：退出码 0 = 干净；输出含 CONFLICT 行 = 冲突文件清单

git worktree add --detach /tmp/wt origin/<branch>
# 在独立 worktree 里改 PR 分支，不污染主 clone（主仓被 GitButler/其他工具托管时必用）

git push origin HEAD:refs/heads/<branch>
# ⚠️ detached HEAD 下必须用显式 refspec 推送；写 git push origin <branch> 推的是
# 本地旧分支，还会谎报 "Everything up-to-date"

gh api repos/<owner>/<repo>/branches/<branch> --jq '.commit.sha'
# 推送后回读远端真实 head 落盘验证，不信本地 origin 引用

npm_config_registry=https://registry.npmjs.org node scripts/audit-shipped-dependencies.mjs
# 走 npmmirror 等镜像时 audit 接口 404，--allow-unavailable 的"通过"是假绿；
# 用官方 registry 环境变量前缀重跑才是真审

gh pr comment <PR号> --repo <owner>/<repo> --body-file /tmp/reply.md
# 评论正文从文件读；不要用 --input 传 JSON——gh pr comment 的 --input 吃的是原始文本

git checkout <基线SHA> -- <被修文件> && <重新构建> && <跑测试>
# 已提交分支上复现 TDD 红态：把修复文件退回基线版本再构建，测试必须红；
# 比 rerun-until-red 可靠

gh pr checks <PR号> --repo <owner>/<repo>
gh run view <runId> --repo <owner>/<repo> --log-failed
# CI 汇总一行一个 check；失败日志只看挂掉的步骤
```

## 关键结论

1. **依赖审计红多半是 lockfile 落后，不是 PR 的锅**：分支基线早于新披露的公告就红。解法是把 `upstream/main` 合进分支——合并只移动 merge-base，PR 相对 base 的 diff 不变，零范围污染；验证时必须绕过镜像走官方 registry。
2. **评审者说"这是问题"时，先对抗核实再动手**：本轮一条 P2 指控"空串永久残留配置文件"，逐文件核实后发现修复机制（延迟清扫+按值匹配删除+启动兜底）就在被评审的 head 上，只是不在被指控的文件里。回复带 file:line 证据链和对应测试名即可，不要急着写新代码。
3. **`rust-toolchain.toml` 钉版升级会让老分支潜伏 fmt 红**：CI 上次绿是旧钉版时代的。探测法=对老分支跑 `cargo fmt --check`；再对 upstream/main 同名文件跑一次——上游也红是本机工具链漂移，只有分支红才是真潜伏。
4. **语义冲突两种解法**：双方在同一位置各加测试 → 取并集；上游新测试用了本 PR 恰好替换掉的枚举/接口 → 把测试语义移植到新接口（确认夹具在新语义下断言不变）。
5. **桩测试是假信心**：jsdom 等无真实布局/浏览器环境的桩测不出真实形态（本轮 bot 用真实浏览器一下就测出桩漏掉的形态）。桩测试结论要在 PR 里如实标注"真实环境未验"，请 CI 或维护者补验。

## 下次怎么用

开源 PR 日常维护按此顺序走一遍：`git fetch upstream` → `gh pr list` 盘点 → merge-tree 探冲突（红的合并 base 按语义解）→ `gh pr checks` 看 CI → 新评论逐条对抗核实（属实才修，漏读给证据链回复）→ 任何推送用显式 refspec + API 回读验证。依赖审计红、工具链升级红、评审漏读三类事件直接套上面的对应条目。
