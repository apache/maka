# AI 识别客户服务重构与验证

**一句话总结**：用 Node 原生能力简化启动，按职责拆分任务编排，统一文件名与中文契约注释，并用类型检查和测试确认改动。

## 背景

AI 识别客户从验证进入上线开发，Node 服务需要补齐异步派发、回调和取消能力。开发中发现组合根混入转写轮询、用例文件超过 500 行，以及命名和注释不一致，随后逐步整理。

## 核心命令

在项目根目录运行；Windows Git Bash 下本轮使用 `npm.cmd`。

```bash
node -v # 核对当前终端实际使用的 Node 版本
node --env-file-if-exists=.env --import tsx src/app/server.ts # 开发启动，原生加载可选 .env
node --env-file-if-exists=.env dist/app/server.js # 启动构建产物，需先 build

npm.cmd run type-check # 检查 TypeScript 类型与重命名后的引用
npm.cmd run test:unit # 运行单元测试
npm.cmd run test:contracts # 检查路由、鉴权与响应契约
npm.cmd run build # 编译生产产物
npm.cmd run test:recognition:self # 验证固定 mock 基线，不代表真实云服务联调通过

git status --short # 区分已暂存、未暂存和未跟踪文件
git diff --cached --stat # 查看准备提交的变更范围
git diff --cached --check # 检查暂存区空白错误与冲突标记
git mv <旧路径> <新路径> # 重命名文件，随后必须更新所有 import
git restore --staged <文件> # 只取消暂存，保留本地内容
```

`--env-file-if-exists` 已在本轮 Node v24 环境验证可用；命令行参数不支持时，先核对 Node 版本，不要先写一套环境变量解析器。

## 关键结论

1. **启动入口保持简单。** `server.ts` 负责进程启动，`app.ts` 负责构建 Fastify 应用。Node 原生参数能够加载 `.env` 时，无需额外启动包装和手写解析器。
2. **按职责拆文件，别只凑行数。** `module.ts` 只装配依赖；轮询、超时、取消进入应用流程，HTTP 回调请求进入基础设施。本项目采用 TS 400 行预警、500 行上限，这是项目约定，不是业界统一标准。
3. **幂等规则属于用例。** 是否重复受理由用例判断，路由只负责校验、调用和响应映射。识别 provider 漏配或非法时返回明确错误，避免真实转写后生成假候选；显式 mock 仅供本地验证。
4. **命名和注释都应帮助定位。** 文件采用 `customer.repository.ts`、`run-dispatch.use-case.ts` 等“业务语义 + 架构角色”；核心或复杂函数用中文 JSDoc 写清默认值、失败条件、副作用和不变量。注释只描述当前契约，不记录对话和改造历史。
5. **验证不能靠输出看起来成功。** 本轮最终曾跑通 100 个单测、15 个契约及 30 条 mock 基线。命令接 `tail`、`grep` 后，管道可能掩盖原命令退出码，不能凭末尾摘要或自行打印的“OK”判定通过。正则扫描注释也会漏掉嵌套函数和方法，不能等同逐函数人工审查。提交前检查真实暂存范围，避免混入临时脚本和含 `<凭证>` 的配置。

## 下次怎么用

先看状态和实际入口，再做小范围调整；文件重命名同步更新 import，改 `.env.example` 时同步本地 `.env` 的键顺序和注释位置，同时保留本地值。修改后直接运行对应验证命令并检查退出码，最后检查暂存区再手动提交。文档只写当前用法，已有 Git 历史承载的删除过程无需重复解释。
