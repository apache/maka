# Java 与 Node 职责核对

**一句话总结**：本次把 AI 识别客户的 Java/Node 边界定清，并在 Node 8089 增加了可切换的讯飞 LFASR 与智能体工作流备用适配能力。

## 背景

最初不确定顾客列表、ASR、工作流和大模型应该由 Java 还是 Node 调用。通过本地 Java 项目、ailisten-center 和 Node 当前实现对照，确认生产对外调用以 Java 为主，Node 生产职责收敛为音频截片与回调；Node 侧保留备用适配器，方便本地联调和后续应急。

## 关键结论

1. Java 的 `clife-beautycamp-ailisten-center` 已有成熟的讯飞 LFASR 转写样板：取 token、提交音频拿 `orderId`、回调或轮询查结果、按状态处理并抽取文本。默认转写服务商是 `XUNFEI`，`LARGE_MODEL` 是讯飞大模型转写接口标识。
2. Java 的智能体调用有两种模式：`AiGenericAgentFeign` 的固定接口同步调用，或者 ailisten 的 `agentId -> executeId -> 查询结果` 异步调用。客户识别工作流参考后者更稳。
3. AI 识别客户生产链路按最终澄清划分：Java 负责鉴权、录音和业务账本、顾客列表、ASR、工作流、万象大模型、人工确认和提交分析；Node 只负责截取前 3～5 分钟音频、发布截片并回调 Java。
4. Node 侧已经增加两个备用能力：`workflow_agent` 两段式工作流 provider，以及 `xunfei` LFASR 转写 provider。它们默认不启用，生产仍以 Java 调用为准。
5. 两个 Node 备用适配器都未完成真实接口验证。讯飞上传字段和签名算法当时未经官方文档核对，工作流 HTTP 方法与请求结构也不能仅凭 Java 方法调用推定，均标记为“待验证”。对话中虽出现单元测试 `113/113`、契约测试 `15/15` 的输出，但命令经过管道截断，且 fake fetch 用例只覆盖自定义响应，不能证明真实协议正确，更不能据此宣称可上线。

## 下次怎么用

1. 要确认 Java 是否已有能力，先在 `E:/Projects/backend/java` 搜索业务关键词和 Feign 接口，再查看对应 infrastructure gateway，不要先在 Node 里重复实现。
2. 要接已有异步工作流，优先沿用 `submit -> executeId -> getResult`，把 agentId、地址和 token 放配置，不要硬编码。
3. 要新增 Node 备用 provider，先复用现有 port 和统一结果解析器，再补 fake fetch 单测；验证顺序固定为 `type-check -> build -> test:unit -> test:contracts -> git diff --check`。
4. 生产职责发生变化时，先更新 Java/Node 对接说明，再决定是否保留 Node 备用代码，避免文档和运行链路互相矛盾。
