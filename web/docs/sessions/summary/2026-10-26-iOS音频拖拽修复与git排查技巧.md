# iOS 音频进度条拖拽修复与 git 排查技巧

**一句话总结**：iOS 音频剪辑进度条"残影/停顿/回弹"三类拖拽缺陷的根因定位与修复，外加一套合并影响面分析、stash 基线对照、测试退出码等日常 git 排查技巧。

## 背景

Taro React H5 项目（SDK 内嵌 App）里，iOS 真机拖拽音频进度条出现三种异常：滑块向左回跳的残影、拖拽中音频断续停顿、松手后进度回弹。安卓完全正常，只能靠代码推演 + 真机回归两轮迭代定位。顺带修了文案换行、测试脚本"成功也退出 1"，并做了一次大版本分支合并（约 120 个提交）。

## 核心命令

```bash
# 合并前分析影响面：对方分支领先多少、动了哪些文件
git fetch origin
git log --oneline HEAD..origin/feature/xxx        # 对方领先的提交
git diff --stat HEAD...origin/feature/xxx          # 三节点 diff，只看对方新增改动
git diff HEAD...origin/feature/xxx -- 某目录       # 确认对方是否碰过自己改过的目录

# 预判合并冲突：找出双方都改过的文件（comm 取交集）
comm -12 <(git diff --name-only origin/feature/xxx...HEAD | sort) \
         <(git diff --name-only HEAD...origin/feature/xxx | sort)

# 核对某个提交里文件的历史值（发现"已提交版本含旧 bug"的关键证据）
git show <commit>:src/xxx/constants/playback.ts | grep 关键常量

# 按路径 stash（含未跟踪文件），做干净基线排查"是不是我的改动引起的"
git stash push -u -m "说明" -- path/to/dir1 path/to/file2

# 按作者+月份统计提交量（绩效/复盘数据）
git log --all --author="邮箱" --since="2026-09-01" --until="2026-10-01" --oneline | wc -l
git log --all --author="邮箱" --since=... --until=... --pretty=format: --numstat \
  | awk 'NF==3 {add+=$1; del+=$2; files++} END {print "files:"files, "add:"add, "del:"del}'

# 回归测试退出码验证（成功必须 exit 0）
node src/subPackage/audioEdit/tests/seekGuard.test.cjs; echo "EXIT=$?"

# 全量类型检查时只看 src 的错误，过滤 node_modules 噪音
./node_modules/.bin/tsc --noEmit -p tsconfig.json 2>&1 | grep -c "^src/"
```

## 关键结论

1. **测试"全绿却退出 1"**：`process.exit(status || 1)` 会把成功码 0 吞成 1，CI/脚本永远判失败；用 `status ?? 1`（信号杀死时 status=null 仍退 1）。
2. **残影根因**：seeked 确认容差 0.25s 过宽，慢拖中途迟到的 seek 落点与手指最新目标的差落入容差内被误确认，守卫被撕开，旧进度经 timeupdate/rAF 回写 → 向左回跳。**确认容差 = 误确认后的最大可见伤害**，收紧到 0.05s。
3. **停顿根因**：`audio.seek()` = 写 `currentTime`，落到未缓冲区间触发 waiting，音频原地停声等数据。它发生在 seek 调用瞬间，**与确认容差无关**（改容差停顿不变就是证据）。
4. **停顿修法**：高频拖拽 touchmove 只更新 UI 预览不派发原生 seek，touchEnd/Cancel 才派发一次最终目标——把 N 次缓冲间隙合并为 1 次。松手后那一次是远程音频的物理下限，省不掉。
5. **0 秒也是合法 seek 目标**：对 targetTime<=0 置空意图会让守卫/确认链路对"拖回开头"完全失防，旧进度能把滑块拉离起点。
6. **单位混用**：设计稿 750 的 670/80 不能直接当 CSS px 参与加减；按比例换算 `floor(视口宽 × 670/750)`，375 视口轨道真值 335 而非 295。
7. **文案换行通病**：容器宽度恰好等于文案精确宽度时，vw 取整误差必换行；修法一律 `white-space: nowrap`（三处不同组件同一病根）。
8. **多来源 seek 必须收敛到统一出口**（首拍立即 + 尾随保留最新目标）：否则延迟派发的旧目标会倒退覆盖新目标（如拖完立刻点 ±15，100ms 后旧 seek 把进度写回去）。
9. **合并冲突不一定二选一**：import 冲突先看文件体里两边的东西是否都被使用、功能是否并存——都在就都保留。
10. **merge 前查两处**：对方是否碰了自己有未提交改动的文件（会拒绝合并）；双方都改过的文件（预判冲突）。本地改动先按路径 stash，合并后 pop（pop 冲突手工合并两组内容）。
11. **stash 基线对照法**：怀疑"是不是我的改动引起的"→ 按路径 stash（`-u` 含未跟踪文件）→ 在 HEAD 基线复测 → `git show <commit> --stat` + grep 依赖关系三重证据。这次用它证明了外部播放条的停顿与本次改动零依赖。
12. **公共组件的问题可以决策不修**：影响面不可控时，把根因、修法（单文件 onChanging 预览 + onChange 提交）记录在案，等产品真有诉求再动。
13. **真机-only bug 的迭代纪律**：每轮修复用"红→绿"测试锁住根因参数（断言常量值/行为阈值），真机复测前测试必须全绿；用户手改参数做实验后，测试会立刻红——闸门在替你守门。

## 下次怎么用

- **合并大分支前**：fetch → 三节点 diff 看影响面 → comm 找双方同改文件 → 本地未提交改动按路径 stash → merge → 解决冲突（先看两边是否都在用）→ pop 恢复。
- **排查"是不是我的改动引起的"**：按路径 stash 做基线 → 复测 → 影响面 + 依赖 grep 出证据，不靠猜。
- **修真机-only 的体验 bug**：先把可本地验证的部分抽成纯函数 + 测试锁根因参数；真机只做最终验收，每轮迭代测试必须先全绿。
- **音频/视频类播放器拖拽 seek**：UI 预览与原生 seek 解耦（touchmove 预览、touchEnd 提交）+ 统一派发出口 + 确认容差收紧，这套组合可直接套用。
