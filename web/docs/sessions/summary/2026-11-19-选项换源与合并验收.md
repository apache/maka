## 可复用经验与案例

- **接口换源要跟踪提交体。** 活动创建页的真实查询返回新字符串编码。逆接口排序选择两项后，新增请求中编码与名称仍按选择顺序对应。后端因测试时段非法拒绝创建，因此只证实了请求体，实际落库和读回未闭环。依据为历史 `capacityOptions` 响应及新增请求 #444。
- **先验证报错中的导入能否解析。** 活动页白屏时，实际异步 chunk 已含新函数，同时包含 `Cannot find module '../../common/adapter'`。从导入文件所在目录核算发现多退了一层。改成 `../common/adapter` 后，chunk 包含模块且页面恢复。此前的缓存猜测未获证实。语法解析通过属于语法证据，无法验证该导入能否找到文件。
- **解冲突结束时明确谁执行 PR 合并。** PR #281 的唯一冲突在 `addOrEdit/index.js` 的导入块。保留新选项请求及目标分支新增的参与方式字典请求，按调用关系移除被替代的旧导入。工具记录显示解冲突提交 `83767ffa` 已推回源分支。后续远端查询仍分别指向源分支 `83767ffa` 与 `develop` 的 `5a8b47c7`，且没有执行或核实网页合并。交接时应写明「解冲突结果已推送，请有权限的人在 PR 页点 Merge」，最终以平台已合并状态或目标分支包含预期改动为准。具体步骤已收录在[项目教程第 14 步](E:/Projects/web/kangyang/senior/06-页面开发/v4.44.3-机构端-活动管理/PR代码冲突解决教程.md:34)。

## 常用命令

```bash
# 从任意目录查询 origin 上两个分支的引用，替换仓库目录和源分支
git -C "<仓库目录>" ls-remote origin '<源分支>' develop
```

适合推送解冲突结果后复核远端分支，要求本地仓已配置 `origin` 且凭证可用。成功时返回两个分支的 SHA 和引用名。只读访问远端，使用 `-C` 可绕开本次实际触发的 Git Bash `cd` 钩子。分支指向只能确认各自的提交位置，单凭两个 SHA 无法判定目标分支是否已含源分支的改动。
