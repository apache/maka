# 现象（iOS 真机实测）

拖拽进度条时音频断续停顿；松手后音频停顿一下才从目标位置恢复。安卓表现正常。
此前"向左残影"已修复，不要回退任何既有修复。

# 已确认根因（不需要再猜）

`InnerAudioContext.seek` 在 H5 即 `HTMLMediaElement.currentTime` 写入。播放态下 seek 到
未缓冲区间会触发 waiting，音频停止出声直到缓冲完成。当前拖拽链路：touchmove 每帧
`seekByProgress` → UI 预览即时提交 + 原生 seek 经 100ms 节流派发（首拍立即、尾随保留
最新目标）。长拖一次仍派发约 10 次 seek，iOS 远程音频每次 seek 都是一段缓冲间隙；
松手后尾随 seek 再产生一次。间隙次数 = 节流派发次数 + 1，这是远程音频的物理代价。

# 修复方向（推荐方案 A，可选 B/C 并说明取舍）

A.（推荐）touchEnd 提交：拖拽过程中每帧只做 UI 预览（requestPlaybackSeek 的
syncDisplay 部分），不派发原生 seek；touchEnd 时才 dispatchNativeSeek 最终目标。
把 N 次缓冲间隙合并为松手后的 1 次。注意 seekByProgress 目前同时服务三类调用方，
需要区分：进度条拖拽与手动裁剪拖拽（useManualTrim 的 onSeek）是高频连续拖拽，
±15 秒按钮（seekByOffset）与播放补偿是低频单发——只有高频拖拽源改 touchEnd 提交，
或给 seekByProgress 增加 defer 参数由组件在 touchEnd 触发真正派发。
B. 拖拽期间显式 pause 音频，touchEnd 时 seek + play 恢复：把断续变成一次"故意停顿"，
状态机更复杂（需处理 play 恢复与 intent 补偿链路），仅在 A 不足时考虑。
C. 节流间隔放大到 250\~300ms：改动最小但停顿仍存在，只作兜底对比项。
