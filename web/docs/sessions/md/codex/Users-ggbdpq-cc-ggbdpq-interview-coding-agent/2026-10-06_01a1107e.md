### A1
只读核查完成；未修改、暂存或提交文件，未跑完整 suite。

确认成立的缺陷：

- **P1 数据丢失**：`removeWorktree` 吞掉固化错误后，`merged` 仍回退 `--force`。真实探针：已合并 tip、未提交唯一文件、`index.lock` 导致 `add` 失败，最终返回 `removed`，目录和文件均被删除。
- **P1 假成功**：`discard` 下 worktree remove 和 branch delete 都可失败，仍清空记录并返回成功。
- **P1 运行状态泄漏**：`execute` 在 worktree 准备前设置 running，准备失败直接 return，绕过 `executeTurn.finally`。真实探针得到 `status:error`、`isRunning:true`、`anyRunning:true`。
- **P1 清理绕过**：普通 `remove` 递归删除任务目录，包含未提交产出的 worktree，绕过显式清理并留下 Git 注册元数据。
- **P2 部分完成失真**：HEAD 祖先检查通过，但 upstream 尚未包含任务 tip 时，`branch -d` 拒绝。真实 Git 探针确认目录已消失、分支仍在。
- **P2 旧状态覆盖**：`execute` 先保存新 sessionId，再保存旧 `task` 加路径，覆盖新 sessionId；`tick` 在前一任务 await 后保存旧 due 快照，可恢复已清理的路径或已删除任务。

并发结论：`removeWorktree` 内全部同步、没有 await，因此自身 running 检查与动作间不存在本进程 timer 插入窗口；真正的窗口在 `tick` 的旧 due 快照。

主线程提出的 pending 方案足够小且可行，需守住：

1. 完成身份、固化、祖先和 upstream 检查后，再保存清理 intent。
2. 每一步失败保留可重试状态；最终持久化失败也返回错误，下次核实资源实际存在性后完成。
3. running 释放用 finally，覆盖保存和回调异常。
4. 准备失败或保存路径失败可能已留下资源；清理入口应能根据固定任务位置发现资源，不能仅凭缺失 path 判定 missing。
5. pending 时普通删除和执行拒绝；列表保留 branch 信息并提供重试入口。
6. tick 每个 ID 执行前重新读取最新任务，禁止写回旧快照。

现有“运行中拒绝清理”测试有效：provider 确实阻塞，`waitRunning` 之后断言，再释放并 await execution。最弱断言仍是只检查记录路径；应同时验证真实目录、字节和 Git 分支。
