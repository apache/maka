# gua-arch — 架构决策与工程原则

个人开发的**工程决策层**：判定技术栈、定模块边界、调跨专题原则、过工程决策门。不拥有PRD/API/实现/质量的执行规则——那些已升格为独立 Skill。

## 使用定位

只有以下场景命中本 Skill：

- **架构决策**："这个模块状态归属怎么定""目录边界怎么拆""是该用 Zustand 还是 Context"
- **跨专题工程原则**：需要调用"单一可信来源""状态机""数据所有权""最后写入获胜"等方法论名词
- **技术栈判定**：不确定当前项目用什么栈、是前端还是 Node 服务、Taro 还是纯 React
- **工程决策门**：新模块设计、状态混乱重构、多方协作的入口约定

**排除单一专题**：

- "按 PRD 拆蓝图" → `gua-prd`
- "列表字段对不上" → `gua-api`
- "弹窗残留数据" → `gua-ui`
- "布局高度不对" → `gua-ui`
- "小程序取不到时长" → `gua-taro`
- "组件怎么拆""Hook 依赖怎么写" → `gua-dev`
- "该写什么测试" → `gua-quality`
- "格式化改动" → `gua-quality`
- "构建哪个端""真机验收" → `gua-quality`
- "修这个 bug" → `gua-bug`
- "审这个 PR" → `gua-review`

## What a good test is

Tests verify behavior through public interfaces, not implementation details. Code can change entirely; tests shouldn't. A good test reads like a specification: "user can checkout with valid cart" tells you exactly what capability exists, and it survives refactors because it doesn't care about internal structure.
