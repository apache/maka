## P1 应修项 / P2 建议项

- **[src/core/automation.ts:AutomationRunner.removeWorktree] P1：保存失败后仍可强制删除未提交内容**  
  **问题**｜`status` 异常被吞掉，随后 `merged` 模式仍允许进入强制删除。  
  **证据**｜构造如下状态：任务分支的已提交 tip 已进入主工作区 `HEAD`，worktree 另有未提交修改。`status` 超时／报错被吞掉 → 未固化修改 → 祖先检查通过 → 普通 remove 因 dirty 拒绝 → `--force` 删除修改。这条推理不需要祖先检查出错；Git 明确允许强制移除 dirty worktree。[Git worktree 官方文档](https://git-scm.com/docs/git-worktree#_commands)  
  **影响**｜用户选择“已合并清理”，仍可能丢失没有进入任何提交的产物。  
  **建议修法**｜`merged` 下，`status`、`add`、`commit` 任一步失败立即终止；正常 remove 失败也应保留资源并报告原因。自动强删只用于用户明确选择的 `discard`。

- **[src/core/automation.ts:AutomationRunner.removeWorktree] P2：前置判定与 `branch -d` 判定不一致，并错误表示部分完成**  
  **问题**｜②检查当前 `HEAD`，④的 `-d` 有 upstream 时优先检查 upstream；④失败后却仍返回 `not-merged`，并保留已不存在的路径。  
  **证据**｜任务分支已进入 `HEAD`，但配置了尚未包含它的 upstream：②通过 → ③移除目录 → ④拒绝删除。该反例不需要并发。不能推定自动创建的分支必然存在 upstream，但 Git 配置或用户操作可以造成它。[Git branch 官方文档](https://git-scm.com/docs/git-branch#_options)  
  **影响**｜再次向当前 `HEAD` 合并不能修复 upstream 判定；页面显示失效目录，重试是否能完成取决于缺失路径处理。  
  **建议修法**｜自建分支显式 `--no-track`，并在删除前识别后续配置的 upstream。成功移除目录后，记录“目录已移除、分支待清理”；分支删除失败保留分支并报告真实错误，支持只重试剩余步骤，不能统称 `not-merged`。
