### A2
盘点清楚了，根因明确。先给结论：

**结论**：这是 Git 在 Windows 下默认使用 `schannel`（系统 SSL）做 HTTPS 握手，与当前网络环境（代理/防火墙）不兼容导致的握手失败。不是仓库本身、也不是认证问题——工作树干净，本地领先 5 个提交，纯粹是 TLS 握手层被中断。

**当前事实**：
- 远程：`https://github.com/ggbdpq/dev-docs.git`（仅 HTTPS，无 SSH 备用）
- Git 版本：2.53.0.windows.3
- `http.sslBackend` 未设置 → 默认 `schannel`
- 本地领先 `origin/main` 5 个提交，待推送

`✶ Insight ─────────────────────────────────────`
- Windows 版 Git 有两套 TLS 实现：**schannel**（调用 Windows 系统证书库，与系统代理/防火墙联动紧密）和 **openssl**（自带 CA 证书包，独立于系统）。`failed to receive handshake` 几乎总是 schannel 在握手阶段被中间设备打断，切到 OpenSSL 常能绕开。
- 修复手段分三层风险：① 临时 `-c` 覆盖（零侵入，验证根因）→ ② 全局 `http.sslBackend openssl`（永久，可逆）→ ③ `sslVerify false`（关验证，安全性最差，不建议）。
`─────────────────────────────────────────────────`

我先用**零侵入的临时覆盖**验证根因并完成推送——不写任何配置文件，若成功就坐实了是 schannel 的问题。

### A3
切到 OpenSSL 后端错误形态变了，但**仍然失败**：

```
TLS connect error: error:0A000126:SSL routines::unexpected eof while reading
```

**`unexpected eof while reading`** 是关键信号——这不是证书/后端问题，而是 **TLS 握手在网络上被中间设备强行截断**。两个后端都失败、且都是"握手阶段连接被掐断"，说明根因在**网络层**（代理失效或网络干扰），不是 Git 配置。
