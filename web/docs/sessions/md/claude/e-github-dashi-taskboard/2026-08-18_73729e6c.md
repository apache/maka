## 结论摘要

`spawn EINVAL`（errno `-4071`）的根因是：Node.js 为修复安全漏洞 CVE-2024-27980，自 2024 年起的版本（含你的 v22.23.2）在 Windows 上**禁止不带 `shell: true` 直接 spawn `.cmd`/`.bat` 文件**，违反即抛 `EINVAL`。[dev.mjs:7](scripts/dev.mjs#L7) 原来正是直接 spawn 了 `npm.cmd`。

## 改动内容

```js
const webChild = process.env.npm_execpath
  ? spawn(process.execPath, [process.env.npm_execpath, "run", "dev:web"], {
      stdio: "inherit",
    })
  : spawn(process.platform === "win32" ? "npm.cmd" : "npm", ["run", "dev:web"], {
      stdio: "inherit",
      shell: process.platform === "win32",
    });
```

优先用 `npm run` 注入的 `npm_execpath` 环境变量（指向 npm 的 `cli.js` 入口），通过当前 node 二进制直接运行——与脚本里启动 server 的方式保持一致；仅当脱离 npm 直接 `node scripts/dev.mjs` 时，才回退到 `npm.cmd` + `shell: true`。

`✶ Insight ─────────────────────────────────────`
- **为什么是 EINVAL 而不是 ENOENT**：CVE-2024-27980 之前，Windows 上 spawn `.cmd` 不带 shell 通常报 `ENOENT`；修复后 Node 主动校验并抛 `EINVAL`，这是一个刻意的“快速失败”设计，防止批处理文件被参数注入劫持。
- **`npm_execpath` 是更优解而非 `shell: true`**：`shell: true` 会把参数拼接进 shell 命令行，天然带注入面；而 `npm_execpath` 是 npm 运行脚本时注入的环境变量，用 `node cli.js` 数组参数形式调用，零 shell 解析、跨 npm/pnpm/yarn 通用。
- **顺带的收益**：web 子进程现在和 server 子进程一样以 `process.execPath` 启动，两者信号传递行为完全一致，`SIGINT`/`SIGTERM` 清理逻辑无需再区分处理两种进程类型。
