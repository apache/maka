## 根因分析

**机制：`.detailPage` 是「固定高度 100vh 的 flex column 滚动容器」，子项默认允许收缩（`flex-shrink: 1`）**

- `detail/index.tsx` 根节点 = `styles.page + ' ' + styles.detailPage`：`.page` 来自 `rp-page` mixin（`display: flex; flex-direction: column; min-height: 100vh`），`.detailPage` 又加了 `height: 100vh; overflow-y: auto`。也就是说：**详情页是一个高度锁死的纵向 flex 容器，所有子块都是 flex 子项，默认可以被压缩**。
- 一旦「全部子项自然高度之和 > 100vh」，flex 布局就会先按比例压缩子项（压到刚好塞满，连滚动条都不出现）。压缩后顾客卡盒子只剩一行高，它 `overflow: visible` 的内容（年龄/标签/客户档案胶囊的下沿）向下溢出，正好被下一个兄弟（面诊关注白卡）盖住——和你平板截图完全一致。
- **为什么手机没事**：荣耀 100 Pro 根字号 20px（未触钳制），内容总高没有超出 100vh，压缩根本不触发。**为什么平板必现**：小米平板 4（Android 8.1，系统 WebView 停在 2018 年前后的老 Chromium/旧 X5，国内不会更新）+ Taro `maxRootSize: 26` 钳制，rem 内容相对视口显著变高 → 溢出必然发生 → 进入压缩分支。
- **为什么旧内核会「压过头」**：现代 Chromium 对 flex 子项有 `min-height: auto`（内容高度兜底，不许压到比内容矮），我桌面浏览器 375–800px 全宽度扫描都渲染正确就是这个原因；老内核对这类嵌套 flex 滚动容器的自动最小尺寸计算有历史 bug，兜底不可靠 → 压塌。另一个模型给出的「卡片被压缩后与下一模块重叠」就是同一个机制，我认可。

**为什么之前一直没暴露**：卡片页踩过同一个坑并且已经免疫——`index.module.scss` 里有现成的 `.content > * { flex-shrink: 0 }`（走查 9.24 加的）；**详情页的 `.detailPage` 从来没加过同款规则**，这是唯一的不对称。

**已排除**：`:is/:where/:has`、`aspect-ratio`、`gap`、`inset`、grid、逻辑属性、现代色彩语法全模块 grep 干净；CustomerSummary / CustomerTagRow / mixins 全是老语法；`entrySource=现场设计页` 与数据无关（你已确认接口返回一致）。
