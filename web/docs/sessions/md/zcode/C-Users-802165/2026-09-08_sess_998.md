## 助手最终结论

### A1
这个 ticket 里最值钱的线索是「刷新无效、重启浏览器有效」——刷新会重建页面 JS 内存，但不清理持久层；重启浏览器会清掉一切。所以坏状态几乎可以肯定不在页面内存里，而在这几个“跨刷新存活”的位置之一。按命中概率排查：

**嫌疑清单（按概率排序）**

1. **发版后旧 chunk 404**。如果异常出现的时间点附近有前端发版，这是头号嫌疑：浏览器持有旧 `index.html`（强缓存或 SW 缓存），懒加载的 chunk hash 在新版里已经变了，动态 import 404 → 加载异常。刷新时如果 html 本身被缓存住，刷新照样拿旧入口 → 症状完美吻合。验证：复现时看 Network 面板有没有 404 的 js 请求。
2. **sessionStorage 里的过期/坏状态**。sessionStorage 的生命周期恰好是「刷新保留、关浏览器清除」，和症状完全吻合。典型是登录态：token 过期后刷新逻辑有死角，页面带着坏凭证反复加载失败。验证：复现后把 Application 面板里的 token/时间戳字段篡改成过期值，看能否必现。
3. **Service Worker 缓存了坏响应**。SW 跨刷新存活，只在浏览器重启时重建。验证：Application 面板 Unregister 立刻恢复 → 就是它。
4. **长连接僵尸**（WS/SSE）。纯连接问题刷新就该好，除非重连依赖某个坏存储状态，所以排后面。

**复现策略**：别真的等“长时间”。“长时间未重启”的真实含义几乎总是“跨越了一次发版”或“token 过期了”，直接构造终态就能把偶现变必现——部署一版新构建后点懒加载路由、或手动把 storage 填成过期数据。先让 QA 补一张复现时的 console + Network 截图，基本一眼定案。

**修复（ponytail 落法）**：根因在缓存策略就在共享根因处修——`index.html` 改 no-cache、chunk 保持 hash + 强缓存，这是服务端一行配置。页面侧只加一个几行的全局兜底：捕获 chunk load error 后带防循环标记自动 `location.reload()` 一次，让中招用户自愈。

**TDD 落法**：测试放行为层（Playwright），不测内部函数——先写一个会挂的用例：拦截某个 chunk 请求返回 404 → 断言页面触发自愈/提示而非白屏；token 场景同理，构造过期 storage 后断言走重登录分支。红 → 修 → 绿。
