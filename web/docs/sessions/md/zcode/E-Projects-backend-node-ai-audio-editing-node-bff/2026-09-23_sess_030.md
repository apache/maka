我上一轮的错误在于把"格式解析"和"领域知识"混为一谈。实际上 `mm:ss` 是 ffmpeg `-ss` 的原生词汇，8088 收它不叫领域倒灌；更重要的是你给的那个事实——格式**已经改过一次**（`154` → `"00:01"`，三方讨论定的）——证明波动是常态，把归一化放在信任边界上正是让后续抖动不再变成联调事故。

现在的职责划分：

| 环节 | 归属 |
| --- | --- |
| `audioUrl`/`startTime`/`endTime` 字段名映射 | Java（只改名，不换算、不排序、不去重） |
| 时间解析、终点补全、重叠合并 | 8088 入队校验 |
| EOF 收尾 | 8088 worker（用 ffprobe 实测时长） |

8088 现在接受的形状：`154`、`"20"`、`"31.5"`、`"00:01"`、`"01:01:30"` 全部可用；`"abc"`、`"1:2:3:4"`、负数仍然 400。

两个连带的行为改进（都是这轮想清楚的）：

**`end` 可省略**。中间段自动延伸到下一段起点，末段记 EOF 标记、执行时用 ffprobe 实测时长收尾。这里 8088 比 Java 更权威——它手上是实测值，Java 是库里存的值。所以我把上一轮"由 Java 读录音时长"的方案也推翻了。

**重叠改为合并，不再 400**。用户在波形上勾两句时间重叠的证据是正常操作，重叠语义就是"这段音频都要"，合并成并集才是用户意图。这修掉了真实缺陷。

TDD 过程中又被测试抓到一次：加了合并后，"首尾相接分两段"那条 unit 测试红了。核查确认 `[0,10]+[10,20]` 与 `[0,20]` 解码出的是同一段声音，合并是对的——错的是断言，它断言了"分几段"（实现细节）而非"听到什么"（可见行为）。改断言，没改实现。
