# 2026 年 AI 产品技术栈选型指南

> 更新时间：2026-08-22  
> 适用对象：个人项目、AI Agent 产品、企业 Web/H5、小程序、桌面工具、BFF 与 Node 服务  
> 文档定位：维护老项目、开发新产品和规划 AI Agent 架构时的唯一技术选型入口。结论由 `E:\vibe-engineer`、`E:\projects` 的真实依赖与官方英文文档校准。

## 一、先给结论

1. **个人新 Web 产品默认 React，不再重复选框架。** 采用 TypeScript + Vite；只有需要 SEO、服务端渲染或同仓全栈时才切 Next.js。
2. **TanStack 不是 React、Vue、Svelte 的同级选项。** 它是按需叠加的无头能力层。Query、Router、Table、Form 分别解决不同问题，不默认全装。
3. **Node BFF 默认 Fastify。** Next.js、Nuxt、SvelteKit 先承担自身产品的轻服务端；跨端复用、长连接、Webhook、任务和独立扩缩容出现后，再拆 Fastify。
4. **Vue 用于团队或存量生态明确的业务，不作为个人主线迁移目标。** Vue 全栈对应 Nuxt，不把 Next.js 硬套到 Vue 项目。
5. **Svelte 用 SvelteKit 小步试点。** 当前两个仓库没有可复用的 Svelte 产品经验，不应直接承担高风险、长周期主项目。
6. **小程序、桌面端和企业 Java 服务按平台事实选。** 小程序继续 Taro + React；桌面端继续 Tauri + React；现有领域服务继续 Java/Spring/Feign，Node 不为“技术统一”取代成熟后端。

一句话：**默认栈负责提速，场景分叉负责避坑；没有业务约束时，不为新技术支付迁移税。**

能力投资顺序：先用现有 React/Fastify 能力交付 AI 产品，再补 TanStack Router/Table/Form 与 Next.js；NestJS 等平台复杂度真实出现后再深入；Svelte 先完成一个可上线小产品，Vue 以企业存量维护为主。一次只验证一项新技术。

## 三、60 秒决策树

先判断交付形态，再判断渲染方式，最后才选状态库和组件库。

```text
目标是微信/多端小程序？
├─ 是 → Taro + React + Zustand + NutUI + Sass
└─ 否
   ├─ 需要桌面系统能力、离线文件或本地进程？
   │  └─ 是 → Tauri + React/Vite；Rust command 优先，Node sidecar 按需
   └─ Web
      ├─ SEO、公开内容、首屏服务端渲染是硬需求？
      │  ├─ React 团队 → Next.js
      │  ├─ Vue 团队 → Nuxt
      │  └─ Svelte 试点 → SvelteKit
      └─ 否 → SPA
         ├─ 个人主线/复杂交互/AI 工作台 → React + Vite
         ├─ 团队已有 Vue 资产 → Vue + Vite
         └─ 小型独立产品且允许承担学习成本 → SvelteKit SPA/CSR
```

后端再做一次独立判断：

```text
只有一个 Web 产品，接口简单？
├─ 是 → 先用 Next.js / Nuxt / SvelteKit 自带服务端能力
└─ 否
   ├─ 独立 Node BFF、SSE、Webhook、聚合 API → Fastify
   ├─ 多模块、多团队、DI、队列、权限治理长期存在 → NestJS
   ├─ Edge / 多 JavaScript Runtime → Hono
   └─ 已有企业领域中心 → Spring Boot / 现有 Java 体系
```

## 四、按产品直接选

下表是立项时的主决策表。“后端”一栏表示默认起点，不代表必须拆出独立服务。

| 产品类型 | 前端首选 | 后端首选 | 何时换方案 |
| --- | --- | --- | --- |

| 管理后台、运营平台 | React + Vite；复杂 URL 用 TanStack Router | Fastify BFF 或现有 Java BFF | 团队已有 Vue/Element Plus 资产时用 Vue 3 |
| 官网、博客、文档、带控制台的 SaaS | Next.js | Route Handlers / Server Actions 起步 | 出现多客户端、独立任务或跨产品 API 时拆 Fastify |
| Vue 团队的 SSR/全栈产品 | Nuxt + Vue 3 | Nitro 起步 | 后端成为独立领域服务时拆 Fastify/NestJS/Java |
| 小型内容产品、创意工具、Svelte 学习项目 | SvelteKit | SvelteKit server routes/actions | 复杂企业组件、多人接手或本地复用要求高时回 React/Vue |
| 企业 H5、营销活动、模型展示页 | React + Vite + 移动端组件库 | 现有 BFF | SEO 是核心获客渠道时改 Next.js |
| 微信小程序 | Taro + React + Zustand + NutUI | Java BFF 或 Fastify BFF | 只维护单一微信端且平台能力重时，才评估原生小程序 |
| 桌面 Agent、配置工具、开发者工具 | Tauri + React + Vite | Rust commands；必要时 Node sidecar | 必须依赖 Electron/Node 原生生态时再用 Electron |
| Edge 网关、轻代理、跨 Runtime API | 无前端或任意前端 | Hono | 固定 Node 长进程、插件和成熟服务治理优先时用 Fastify |
| 企业领域中心、复杂交易服务 | Web 框架按前端团队选 | 现有 Spring/Feign/DDD 体系 | 不因前端改框架而迁移领域服务 |
| CLI、批处理、逆向辅助脚本 | 无或最小 Web UI | Node.js + TypeScript + `tsx` | 需要单文件分发、极致启动或系统级能力时评估 Go/Rust |

## 五、React、Vue、Svelte 与 TanStack 的正确关系

这四者解决的问题不同。前三者决定 UI 与应用心智；TanStack 决定某个复杂能力如何实现。

| 选项 | 最适合 | 主要代价 | 本地建议 |
| --- | --- | --- | --- |
| React | 复杂交互、AI 工作台、组件复用、个人长期主线 | 选择空间大，状态和组件边界容易失控 | **默认选择** |
| Vue 3 | 团队已有 Vue 资产、标准业务后台、模板驱动开发 | 与个人 React 资产重复建设 | **团队/存量驱动**，不主动迁移主线 |
| Svelte / SvelteKit | 小团队新产品、内容与交互并重、希望减少运行时样板 | 本地零复用，招聘、组件库和接手风险更高 | **先做一个可上线小项目**，再决定是否升级为主力 |
| TanStack | 服务端状态、类型安全路由、复杂表格/表单、长列表 | 每个库都有独立学习与约束成本 | **逐件引入**，不是全家桶 KPI |

对应的全栈关系应记成：

```text
React  → Next.js
Vue    → Nuxt
Svelte → SvelteKit

TanStack Query/Table/Form/Virtual → 可叠加能力
TanStack Router                   → 当前重点服务 React/Solid SPA
```

## 六、TanStack 按症状引入

不要因为项目使用 React 就自动安装 TanStack 全家桶。达到右侧症状时再引入。

| 工具 | 引入信号 | 不引入时 |
| --- | --- | --- |
| Query | 同一远程数据被多处消费；需要缓存、去重、重试、失效刷新 | 一次性请求用薄 `fetch` 即可 |
| Router | URL 承载复杂筛选；路径和 search params 需要类型安全；路由 loader 需要并行预取 | 简单页面或现有 React Router 项目继续原路由 |
| Table | 服务端分页、多列排序、筛选、列显隐、行选择组合出现 | 简单表格直接用组件库 Table |
| Form | 动态字段、跨步骤校验、字段联动和数组表单明显复杂 | 普通表单用组件库 Form 或局部状态 |
| Virtual | 长列表已经出现真实渲染瓶颈 | 先分页；几十项数据不需要虚拟化 |

硬规则：**服务端数据留在 Query；URL 状态留在 Router；局部 UI 状态留在组件；只有真正跨组件、跨路由的客户端状态才进 Zustand/Pinia。**

## 七、可复制的默认栈

### 7.1 个人 React SPA

```text
React + TypeScript + Vite
Router：TanStack Router（新复杂 SPA）或 React Router（简单/存量）
Server state：TanStack Query（按需）
Client state：useState → Context → Zustand，按作用域逐级升级
Request/schema：Fetch + Zod
UI：Tailwind CSS + shadcn/ui
Quality：TypeScript strict + Oxlint/ESLint + Vitest + 关键路径 Playwright
```

### 7.2 React 全栈与 SEO

```text
Next.js App Router + React + TypeScript
Server Components 默认，Client Components 只包交互岛
Route Handlers / Server Actions 先承接轻后端
Zod 校验外部输入；数据库按项目选 SQLite/PostgreSQL
Vitest + Playwright
```

不要同时再装 React Router，也不要为了“前后端分层好看”立即创建 Fastify 服务。

### 7.3 Vue 业务应用

```text
Vue 3 + TypeScript + Vite + Vue Router
Pinia 只放跨页面客户端状态
远程缓存复杂时加 TanStack Vue Query
Element Plus（后台）/ 现有业务组件库
SSR 或全栈改用 Nuxt
```

### 7.4 Svelte 试点

```text
SvelteKit + TypeScript
优先使用 load、form actions、server routes 和原生状态能力
样式先用 CSS/Tailwind 二选一
只有客户端缓存确有需求时再加 TanStack Svelte Query
```

试点验收不是“写完 Todo”，而是完成一个可部署产品，并走通鉴权、表单、数据加载、错误处理、测试和升级。

### 7.5 独立 Node BFF

```text
Fastify + TypeScript + Zod/JSON Schema
Fetch/官方 SDK + 统一错误映射
简单服务优先 node:test；需要前后端统一体验时用 Vitest
SQLite 起步，明确并发与部署需求后再上 PostgreSQL
```

仓库先保持单包。只有 Web、Server、Contracts 确实需要独立构建和复用时，再升为 pnpm workspace。

## 八、Node 服务框架边界

这张表用来避免把所有服务都做成 NestJS，也避免让 Next.js 承担它不擅长的长期后台任务。

| 框架 | 选择它 | 不选择它 |
| --- | --- | --- |
| Next.js server | 单一 React Web 产品、SEO、页面数据与写操作紧密相连 | 公共 API、多客户端、复杂队列、独立扩缩容 |
| Nuxt/Nitro | 单一 Vue 全栈产品、SSR/SSG/Edge 部署 | 独立领域平台或非 Vue 客户端共享服务 |
| SvelteKit server | 小型 Svelte 全栈产品、表单 action、页面近端 API | 复杂企业集成、多人长期维护的通用服务 |
| Fastify | 独立 Node BFF、SSE、Webhook、API 聚合、插件化但保持轻量 | 业务已要求强 DI、模块治理和大型团队约束 |
| NestJS | 多领域模块、权限、队列、事件、DI、多人协作已成为长期复杂度 | Demo、单 BFF、几个路由的轻服务 |
| Hono | Edge、Serverless、多 JavaScript Runtime、轻网关 | 固定 Node 平台且依赖成熟 Node 插件生态 |
| Express/Koa | 维护既有系统或生态依赖明确 | 新个人项目默认值 |
| Spring Boot / Solon | 企业领域中心、Java 资产、Feign 链路、MCP Java 接入 | 仅为一个前端页面提供薄聚合接口 |

框架升级条件必须来自持续出现的复杂度，而不是预计未来“可能变大”。

## 九、开发与维护护栏

### 9.1 React / Next.js

React 选型成立后，真正决定维护成本的是组件、状态与数据流。

- **组件先组合，后抽象。** 复杂组件优先用 children、显式子组件和 compound components；避免靠一串布尔 props 切换模式。
- **状态保持最小且唯一。** 可由 props、URL 或服务端数据推导的值不重复存储；表单 `record/id/mode` 只保留一个可信来源。
- **Provider 隔离实现。** 共享组件只依赖 `state/actions/meta` 接口，不知道底层是 Zustand、Context 还是服务端状态。
- **请求消灭瀑布。** 独立请求并行启动；只有分支真正需要数据时才 `await`；页面用 Suspense/streaming 切开慢区块。
- **缩小客户端边界。** Next.js 默认服务端组件，只向客户端序列化交互所需的最小数据。
- **控制包体。** 直接导入、重组件动态加载、第三方统计延后；不为简单表达式堆 `memo`。
- **Server Action 等同 API。** 每次调用都重新做鉴权、授权、输入校验和错误映射。

### 9.2 薄请求层

请求层只统一技术问题，不承载页面业务。默认职责如下：

| 负责 | 不负责 |
| --- | --- |
| base URL、headers、token 注入、超时、中止、JSON 解析 | 页面 loading、弹窗开关、表格选择 |
| HTTP 状态与业务错误的统一映射 | 把所有异常吞成一个 toast |
| 上传、下载、流式响应的少量分支 | 为单个接口制造专用抽象 |
| 可选的 Zod 响应校验 | 把远程数据长期复制进 Zustand/Pinia |

维护老项目时沿用现有 Axios/Fetch 封装；只有重复故障集中在共享层时才改共享层，不为“统一技术栈”重写所有请求。

### 9.3 表单与弹窗

```text
open → echo → submit → success → close → cleanup → reopen
```

- 新增入口先清 `record/id`，再 reset，最后写默认值。
- 编辑入口先记录当前 id，再请求详情；异步返回时确认仍是同一次打开，防止慢请求覆盖新弹窗。
- 保存中禁止重复提交；成功后先通知列表刷新，再关闭。
- 关闭后清理表单、校验、record、loading、临时列表、上传和子弹层状态。
- 表格必须覆盖分页或加载更多、空状态、错误态和刷新后的选中态。

### 9.4 AI Agent 产品

AI Agent 产品再增加五条边界：

- **先分应用与平台。** 调用模型完成业务的是 Agent 应用；承载插件、会话分叉、权限和运行时的是 Agent 平台。绝大多数项目先做前者。
- **模型层保持薄。** 单供应商优先官方 SDK；确有多供应商 streaming/tool-call 统一需求时使用 Vercel AI SDK，并在业务侧只保留一个薄 adapter。
- **流式协议可中止、可收口。** SSE 至少定义内容、工具调用、错误和完成事件，处理客户端断开与超时。
- **模型输出永远不可信。** tool-call 参数先过 Zod/JSON Schema，再进入权限、超时、执行和结果记录管道。
- **持久化服从产品能力。** 普通聊天保存消息即可；只有 fork、resume、replay、审计已是需求时，才升级为 append-only 事件日志，并保证模型可见内容可重建。

测试优先离线 mock/replay，线上 smoke test 只覆盖少量真实供应商链路，避免测试成本和模型波动污染日常回归。

只有产品已经需要插件、会话分叉、权限治理和可重放运行时，才进入 Agent 平台阶段。进入后保留四个稳定原语：

- 能力接缝：接口定义、Provider、Consumer 三者分离。
- 工具注册表：统一经过 `pre-execute → execute → post-execute`，集中处理权限、超时和审计。
- 事件日志：模型可见内容必须能够从 append-only 日志重建。
- 配置层叠：默认配置可被用户配置覆盖，但普通 Agent 应用不提前建设插件元框架。

## 十、老项目维护规则

老项目的第一目标是稳定交付，不是追平新项目技术栈。

| 遇到的情况 | 默认处理 | 升级或重构条件 |
| --- | --- | --- |
| React 17、Taro 3.6、NutUI、旧 Node 仍可构建 | 固定现有 package manager、lockfile、Node 和发布链路 | 安全漏洞、平台下线、构建阻断或业务能力无法实现 |
| 项目使用 Axios、Redux、Sass、Ant Design | 沿用并做局部修复 | 替换能消除已测量的故障或维护成本，且有回归保护 |
| 同一问题在多个页面重复出现 | 追到 request、service、hook、公共组件或 BFF 根因处修一次 | 仅在公共修复会破坏兼容性时保留页面级适配 |
| 缺测试但要重构 | 先补当前行为的 characterization test 和一条核心流程检查 | 保护建立后再拆模块或升级依赖 |
| Taro/多端项目改动 | 按受影响端运行现有 build，并人工检查授权、路由、上传、支付等平台能力 | 不用 H5 通过代替小程序验收 |
| 文档与源码冲突 | 以当前 `package.json`、scripts、配置和源码为准，随后修正文档 | 不保留已失真的历史说明 |

维护纪律：功能改动与大版本升级分开提交；不顺手换框架、状态库或组件库；新增依赖前先搜索现有能力；删除兼容代码前先确认调用方与目标运行环境。

## 十一、工程底座与供应链

工具只在能形成门禁时引入，不把清单全部塞进每个项目。

| 能力 | 默认选择 | 最小门禁 |
| --- | --- | --- |
| 类型 | TypeScript strict；外部输入用 Zod/JSON Schema | `typecheck` 必须可独立运行 |
| 静态检查 | 新项目优先 Oxlint；存量沿用 ESLint/Stylelint | 不在功能提交里顺手全仓格式化 |
| 单元测试 | 前端/共享库用 Vitest；简单 Node 服务可用 `node:test` | 覆盖关键分支、转换、权限和数据契约 |
| 端到端 | Playwright | 至少一条登录后核心业务流程 |
| 死代码 | 大仓库按需使用 knip | 先确认动态导入、框架约定和生成代码 |
| Git hooks | lefthook 或项目现有方案 | pre-commit 只跑快速增量检查，完整检查放 CI |
| TS 脚本 | `tsx` | 不为一次性脚本增加应用框架 |

供应链保持四条：提交 lockfile；CI 使用冻结锁文件安装；pnpm 11/12 保持 `strictDepBuilds`，通过 `allowBuilds` 显式审核依赖安装脚本；分发类或高风险项目使用 `minimumReleaseAge` 延迟刚发布的依赖版本。配置以当前 pnpm 官方文档为准，不复制旧 major 的废弃字段。

## 十二、当前不建议做

- 不把 React、Vue、Svelte 三套脚手架同时维护成“默认模板”。
- 不在新项目首日安装 TanStack Query、Router、Table、Form、Virtual 全家桶。
- 不因为 Next.js 能写接口，就把公共 API、队列和长任务永久塞进同一应用。
- 不因为 NestJS 结构完整，就让三五个路由承担 DI 和模块样板税。
- 不把远程数据复制进 Zustand/Pinia，再手写缓存、刷新和重试。
- 不在 Taro 存量项目中追平 React/Vite 最新版本；升级必须另建分支样板并验证多端构建。
- 不把 shadcn/ui 与 Ant Design/Element Plus/NutUI 全量混用。先按产品形态选一个主组件体系。
- 不把 Svelte 当作“更先进的 React”。没有团队与资产复用时，它首先是一笔学习成本。
- 不默认上 monorepo、微前端、微服务、事件溯源或插件平台；真实边界出现后再升级。
- 不把功能开发、依赖大版本升级、状态库迁移和全仓格式化混成一个变更。
- 不为保存“历史信息”继续维护内容重叠的选型文档；事实变化直接更新本文件。

## 十三、立项清单

立项前回答下面 14 个问题。前 6 个决定框架，后 8 个决定依赖、架构和维护方式。

- [ ] 交付端是 Web、H5、小程序、桌面还是 CLI？
- [ ] SEO、SSR、SSG 是否为可量化的硬需求？
- [ ] 是单一 Web 产品，还是多个客户端共享服务？
- [ ] 是否依赖现有 Vue、Taro、Java 或组件库资产？
- [ ] 团队下一年由谁维护，能否接手该框架？
- [ ] 产品是快速验证，还是高风险、长生命周期系统？
- [ ] 哪些状态属于 URL、局部 UI、跨组件客户端状态、服务端状态？
- [ ] 是否真的需要缓存、重试和失效，还是一次 `fetch` 足够？
- [ ] 表格、表单、长列表是否已达到引入 TanStack 对应库的复杂度？
- [ ] 后端是否需要 SSE、Webhook、队列、任务调度或独立扩缩容？
- [ ] 外部接口、配置、用户输入和模型输出是否有运行时校验？
- [ ] 最小质量门禁是否包含类型检查、关键逻辑测试和一条核心 E2E？
- [ ] 存量项目是否保持原构建链路，并把升级与功能改动分开？
- [ ] README 是否包含启动、构建、测试、部署和已知坑？

如果前六项仍答不清，先用默认 React SPA + 薄 Fastify BFF 做可验证版本，不为假设设计平台。
