# 文档维护与结构

> 合并自：原根级 05-文档维护与归档.md 与 handbook/06-文档结构约定.md，2026-10-24。内容归属、命名、维护与归档规则来自前者；三条原则、hub 标准结构、记账口径、接入清单来自后者。旧 `guahub/docs/work/hub/<slug>/`、`<slug>-hub/docs/` 路径已统一改为现行 `hub/<slug>/` 形制。

这套文档服务三个问题：有哪些项目、下一步怎样推进、已有证据在哪里。保留类型优先的目录，以项目名连接手册和事件；新增 fork 时只登记实际需要的内容。各项目特有的规则放在 `hub/<slug>/handbook/`；只有在两个以上项目都适用时，才晋升到 handbook。

## 1. 三条原则

1. **一份事实只放一个地方。** 规则在 handbook，事实在 journal，候选方案在 design，机器状态在 sentinel。别处只放链接，不复制正文。
2. **没有"待分类"目录。** 新文档按角色归位；归不进去就先写进当轮的 journal 条目。
3. **单个文件超过约 45 KB 就分卷**，避免一次读入撑爆上下文；规则类文档超过 30 KB 按主题拆。
   - 本条是分卷阈值的唯一正本；其他文档引用这里，不另立数字。
   - 唯一例外：`journal/编年/` 日分册与 `issues/` 原件（docs_lint 已跳过检查）不受 45 KB 约束；单日分册超过约 80 KB 时按 `-a` / `-b` 拆（规则见 [magpie 编年追加规则](../hub/magpie/journal/编年/README.md)，按日分册的先例是 2026-10-21 编年全录拆分）。
   - 台账文件（[02-接单总台账/](02-接单总台账/README.md)）分卷需要 `scripts/ledger_stats.py` 支持，暂缓分卷，SIZE 告警保留。

## 2. 设计依据与方法选型

2026-10-02 的本地盘点发现：10 个项目使用不同包管理器和贡献通道；手册混在 `pr/`；旧 Windows 路径仍被当作当前入口；全局表有 44 行却标为 35 单。这些问题优先用导航、内容归属和证据规则解决。

| 方法或专有名词 | 本需求中的用法 | 检验动作 |
| --- | --- | --- |
| 第一性原理 / 信息架构（IA） | 从查项目、做贡献、找证据三个任务划分内容 | 新读者能否从总入口找到正确项目和下一步 |
| 单一事实来源（SSOT） / 高内聚低耦合 | 每项事实有一个维护位置，其他页面只链接 | 修改路径、状态或规则时，是否需要重复改多张表 |
| 渐进式披露 / YAGNI | 单文件起步，有真实检索负担再拆分 | 新项目是否出现空台账、空手册或预建分轨 |
| 对抗式审查 / 批判性思维 | 主动寻找自己的结论的反例 | “CI 通过”是否覆盖目标测试；“无人认领”是否检查 assignee |
| 奥卡姆剃刀 / 消融实验 | 在满足检索和留证据的前提下删掉重复摘要 | 去掉一个副本后，读者能否仍找到原事实和验证结果 |
| 不确定性记录 | 将未知落到具体事实、影响和复核入口 | 是否把未查权限、未跑测试、旧快照写成确定事实 |
| 知识蒸馏 | 将事件压缩成规则、适用边界和检测动作 | 教训是否能在下一单开场直接使用，而非只复述故事 |

这里的“知识蒸馏”指文档经验提炼，不指训练学生模型。目录按内容用途分类，方法名用来检查质量。Agent 的上下文按入口、相关手册、目标条目逐层读取；这是对 [Anthropic 上下文工程文档](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)中按需加载思路的本地应用。

## 3. 内容归属

| 内容 | 唯一维护位置 | 更新方式 |
| --- | --- | --- |
| 项目 slug、主 clone、并行目录、主要用途、仓库工具链声明 | [01-接单线程池.md](01-接单线程池.md) | 可更新；附本地或远端核验范围 |
| 当期预算、全局单号、跨仓状态索引 | [02-接单总台账/](02-接单总台账/README.md)（按仓分文件：每仓「活账」节 +「终态归档」节，原 03 归档表已于 2026-10-24 并入） | 可更新；计数不手算，行数与全局号范围由各仓文件的生成块承担（见 [02 铁律](02-接单总台账/README.md#铁律) 与 [12 台账生成统计](12-通用纪律与执行声明.md#台账生成统计)）。活表只留在池在途行；新行只追加在活表锚点处；行进终态（merged/closed/让坑/放弃/被取代）或出池后迁归档并按全局号排序，迁移时行原文不改；状态列更新按下方 §6，重复全局号按先例保留 |
| 项目入口和历史单号到条目的映射 | `hub/<slug>/README.md`（项目卡） | 可更新；轻量项目可暂存少量规则和环境摘要 |
| 已拆出的规则、环境、命令、机制与可复用案例 | `hub/<slug>/handbook/` | 可更新；标平台、日期、源文件与未验证部分 |
| 单次诊断、改动、验证、review、同步和关闭事件 | `hub/<slug>/journal/`（README 索引 + 卷NN 逐单条目 + 在途快照；重度项目多卷，参照 magpie-hub 的编年全录形制） | 历史事件只追加；更正另写新条目并指明旧结论 |
| 跨仓反复出现的失败模式 | [05-失败模式对照.md](05-失败模式对照.md) | 满足既有收录门槛后更新，保留案例来源 |
| 代表性贡献与阶段叙述 | [04-交付总览.md](04-交付总览.md) | 按日期解释价值；状态链接回台账 |
| 已失效调研、退役操作方案、封存的大段记录 | 所属 hub 的 `_archive/`，或原台账中的标日期历史区 | 封存后保留来源、日期与替代入口 |

“只追加”约束事件原文，当前状态摘要和索引可以更新。旧条目中的 open/CI 数字代表记录当时，不代表今日。归档是降低默认阅读优先级，不等于删除文件、撤回 PR 或删除 clone。

## 4. 项目分类与命名

项目主要类别按解决的问题划分，见项目索引；技术栈、平台、贡献通道作为表内属性。一个项目只建一个文档 slug，避免同时放进多个类别目录产生副本。

- slug 沿用已有目录名：`cliproxyapi`、`cockpit-tools`、`multica` 等。展示名、GitHub 仓库名和本地 clone 名可不同，映射放在项目索引。
- 文档与手册命名统一「序号+中文描述」（`01-内容.md`、`02-内容.md`…），数字只表示本目录阅读顺序；现有编号保留，不为外观整齐重编号。
- GitHub PR 使用 `owner/repo#PR号` 定位，issue 使用 `owner/repo#issue号` 并写明类型；完整链接负责消除歧义。全局预算号、项目旧单号只作索引别名。
- 日期用 `YYYY-MM-DD`；短日期在已有历史条目中保留。新记录区分发生日期和核验日期。

## 5. 每个项目的标准结构（`hub/<slug>/`）

```
README.md                 项目卡：梯队、仓库身份、入口、本仓分工（控制在一屏左右；
                          要素含用途、规则来源、通道、台账入口、项目差异、未核验项，
                          占位项只在实际建立项目时填写）
handbook/                    规则（复盘维护）
  README.md
  01-仓规与接单流程.md
  02-本机环境坑.md
  03-会话开场提示词.md     （参考差异卡；2026-10-28 起不作会话入口）
  NN-维护任务书.md         会话入口（每仓唯一，根 README 跨仓项目表直链）
  10-避坑与模式家族.md     （有了再建）
issues/                   原件区（有原件时才建；目前 magpie、multica、orca 有），存放规则见本节末
journal/                  事实（书记维护）
  README.md               索引：分卷表 + 条目 → 卷
  卷01.md 卷02.md …        逐单条目，只追加
  在途快照.md              倒序，最新一节在文首
sentinel/                 哨兵提示词 + 基线 .json（定时任务唯一可写处）
design/                   候选单与方案（有了再建）
_archive/                 只读归档，带 README 说明现行版本在哪
```

上面 handbook/ 下的编号是模板；各仓已有编号保留，不为对齐模板重编号（见 §4）。

原件与产物的存放（2026-11-07 修订；原规则「二进制文件和日志不放 docs/」不再适用）：

- `hub/<slug>/issues/` 是原件区，纯文本证据可以入库：日志、patch、mbox、json、帖稿、回读记录。
- 单个文件超过约 200 KB 时，入库形态改为「摘要 + sha256」，全文放项目 clone 侧的 `artifacts/`（如 `fork/<slug>/artifacts/`）。
- PNG 等二进制文件（含 git bundle）与上游源码副本不入 `issues/`，放 clone 侧的 `artifacts/`。
- 存量待处置：现存的超限文件与二进制由主线程逐项报批处置，本条修订不追溯移动文件。

## 6. 记账口径

- 台账行不删除，全局号与非状态列不改；状态列更新的唯一规则见 [02 铁律 5](02-接单总台账/README.md#铁律)：先留存旧状态，再整格替换，不作历史行批量清洗。行数与全局号区间由各仓文件内的 `scripts/ledger_stats.py` 生成块承担，刷新与验收统一遵循 [12 台账生成统计](12-通用纪律与执行声明.md#台账生成统计)。
- 逐单条目只追加；结局变了，就在最后一卷追加一条更正，并引用原条目。
- 在途快照倒序追加，旧节不改。
- 条目模板：`## <单号> ｜ issue #N → PR #M（全局单 G，YYYY-MM-DD）`，正文依次写动机 / 改动 / 验证（含没跑什么与原因）/ 结局 / 经验一条。单次诊断复杂时按字段展开：

```markdown
### YYYY-MM-DD ｜ owner/repo#编号（PR 或 issue）｜ <事件摘要>

- 索引：<全局预算号 / 本仓旧单号；不适用就省略>。
- 目标与观察：<预期、实际表现、触发条件>。
- 根因与证据：<源码入口、基线 SHA、复现或诊断；推断要标注>。
- 改动与边界：<涉及文件、行为差异、保留的兼容约束>。
- 验证：<环境、命令、退出码、目标用例、红→绿或对照结果>。
- 未验证：<未跑范围、原因、影响、继续条件>。
- 结果与下一步：<记录当时的 PR/CI/review 状态、核验时点、责任人>。
- 可复用经验：<规则 + 适用边界 + 下次检测动作；没有新经验就省略>。
```

选题放弃、占坑和纯维护事件只写发生的事实，不虚构根因或测试。选题仅在全局表留一行即可；产生独立诊断价值时才追加项目条目。性能单另加负载、测量方法、同环境前后结果；不强塞进普通小修。

## 7. 新增项目到成熟项目

1. **调研**：在项目索引登记用途、upstream、origin、本地路径、贡献通道的证据。只有观察记录时不建空项目目录。
2. **第一单**：主 clone 平铺 fork/`<slug>/`，文档按 §5 标准结构建 `hub/<slug>/`（先写项目卡 README 和 handbook/01）；在对应预算线登记，并在 fork/docs 总台账登记项目前缀（如 CC-、CH-）。只写已确认的项目差异；通用过程引用 Skill `gua-pr-patch`（`references/workflow.md`、`references/delivery.md`），不在项目文档里复制。
3. **重复使用**：规则或环境内容已需要在多单复用时，迁到 `hub/<slug>/handbook/`，从入口链接过去。先修引用，再去掉原副本。
4. **检索变慢**：单文件难以定位时才拆。新增项目优先按年份或主题拆一层，不默认复制多轨体系；迁移后保留条目原文、单号和索引。
5. **停止维护**：确认无待回应 review、CI 阻断或承诺后，在项目索引注明停止日期、原因与恢复条件。文件保留，索引链接不失效；关闭远端 PR 仍是单独的外部操作。
6. **接入收尾**：在根 [README 的跨仓项目表](../README.md)和 [08-巡检节奏与分层](08-巡检节奏与分层.md) 各加一行。

阅读顺序：首次使用读总入口 → 项目索引 → 通用流程 → 项目差异；已有 PR 先读全局对应行 → 最新项目事件 → 相关机制。无需每轮加载全部历史。

## 8. 维护与归档触发条件

| 触发 | 更新哪里 | 完成判据 |
| --- | --- | --- |
| 新 clone、hub 迁移、上游改名、工具链要求改变 | 项目索引与相关手册 | 路径实际存在，源文件与表一致 |
| PR head 改变、review 到达、CI 完成、合并或替代关单 | 项目事件 → 全局摘要 | 摘要可追溯到事件，明确核验时点 |
| 发现旧结论错误 | 新事件明确更正 → 更新现行手册 | 原结论仍可追踪，使用入口不再传播错误 |
| 同类失败满足 M1–M13 收录门槛 | [失败模式对照](05-失败模式对照.md)与开场检测动作 | 有案例链接和可执行判据 |
| 调研过期、平台退役、操作 prompt 未再使用 | 历史区或所属 hub 的 `_archive/` | 明确失效范围与替代入口，不把存档视为执行授权 |
| 月末或再次接手一个项目 | 核对该项目待办与导航 | 有未结事项就保留可见入口，无变化无需写重复报告 |

封存文件放所属 hub 的 `_archive/YYYY-MM-DD-主题.md`，大型项目确有需要再加 `_archive/<slug>/`；跨仓公用层（fork/docs）不设 archive（2026-10-25 曾短暂设过仓库级 archive/，同日判废撤销：magpie P0 状态快照迁回 hub/magpie，gh-archive 与 contributions 一并删除）。删除过期文档前必须满足以下条件之一：①内容已迁入所属 hub 的 `_archive/`；②删除提交所在分支已推送到远端（`git branch -r --contains <删除提交>` 有输出）。只存在于本地的 git 历史不算可追回：cc 仓 2026-10-25 以孤儿单提交 `22249b41` 重建，2026-11-07 07:36 再次重置为根提交 `dbdf77a4`，10-25 至 11-07 的历史只在本地未推送分支 `backup-pre-root-20261107`（`f89ff01b`）上；文档里引用的 `05867a9f78`、`960e5bb4e4`、`b3f3a3e50a`、`222bdc82`、`b32e6de4` 在本机均已无法解析（详见 [11 §3](11-事故复盘.md#3-2026-11-07-仓重置的可恢复性影响)）。日期表示快照或原记录的基准日，页首另写封存日期。不要复制仍活跃的台账作为第二个当前状态源。

## 9. 可信度与验收

**事实**附本地文件、Git 对象或远端链接；**推断**写推导依据；**待验证**写影响和复核入口。仓库 manifest 要求与宿主已安装版本分开。`remote HEAD` 只证明本地保存的默认分支信息，GitHub 默认分支和 PR target 仍需用时确认。

总台账的预算记录不等于 PR 数或所有历史贡献总数；CLIProxyAPI 旧单不能直接相加当作战绩。

文档变更用链接目标、实际路径、编号和统计复核；历史正文和代码块与备份比对。只有修改运行行为才进入 TDD：先明确测试的公开边界，再做一条红→绿的纵向切片。文档整理无需为目录形状添加测试框架。

2026-10-28 起手工维护已实测持续出错（断链 75、计数不符 6、快照乱序 2），自动检查已落地：改动 docs 后跑 `python3 scripts/docs_lint.py`（docs 根执行），ERROR（断链、表格列数、台账生成块缺失或失配）清零才算收口；WARN（体积、快照顺序）记待办；可装 `scripts/pre-commit` 钩子自动执行。

交付前做一次消融检查：能删掉的重复状态或规则改成指针；确认项目定位、证据追溯和下一步仍可找到。
