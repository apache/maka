## M1 覆盖面幻觉 —— "没红"≠"绿"

**实例**：①maka #5890：两轮 CI 归因"环境偶发"，其中一条依据是"同内容上轮 CI 绿"——第三轮盯守发现上轮 planner 根本没选 runtime-host 测试面（挂在别的测试上就停了），该测试在 CI **从未绿过**。②orca：vi.mock 对新文件的 named import 绑定不生效，14 个旧用例的"绿"是真实磁盘状态的空洞通过。③maka #5777："父绿子红"的父绿是范围缩减假对照。④"本地过了"≠"构建门过了"（tsc 报错也发射 dist）。⑤CLIProxyAPI #5514："零新评论"的批查只扫了 issue 级端点（`issues/{n}/comments`），**行内 review 评论是另一个端点**（`pulls/{n}/comments` + `pulls/{n}/reviews`）——补扫才发现 4 条 bot 线程；声称的扫描范围≠端点覆盖的范围。

**打破机制**：采信任何"绿"之前问一句——**这个绿覆盖了我声称的范围吗？planner/过滤器/基线真的跑到了目标吗？** 验证分支声称用 `git show <sha>:<path>` 读对象；对照前先验证两侧跑的是同一测试集；扫描类声称先列端点/过滤器清单再核对覆盖。

## M2 观测者污染 —— 测量自身的选择伪装成被测系统的成本

**实例**：①maka startup-profile：FakeBackend"恒定 ~2s/turn"实为打字模拟（9 字符×45ms）× 自家 283 字符种子文本——先做算术（块数×sleep=1.44s）一步命中。②maka #5804：自己 fixture 的 `catchUpModelCallProjection` 单 pass limit=16，装不下 409 行 pad——测量的地基 bug。③orca：SSH Include walker 的 glob 语义争议不照抄 bot 描述，用 `fs.globSync` 探针实测钉行为。

**打破机制**：benchmark 报出数字后，把"观测路径的每一步"列出来问哪个是系统成本、哪个是观测成本；争议语义用探针实测，不引用二手描述。

## M3 环境噪音当回归 —— 定性靠对照，不靠清单

**实例**：cherry 集成 SIGABRT（单次基线绿→误归因→12h 后基线 5/5 崩证明预存）；maka audit 双红（GitHub 通告同步，无 diff 树上复现相同失败）；本机预存挂清单两仓各 5+ 项且持续增长（Node 26 spawn EINVAL、EBUSY、POSIX 路径 fixture……）；CLIProxyAPI：**"v8 迁移警告是上游预存行为"的免责定性被纯 upstream worktree 对照直接推翻**（纯基线 0 条），换输入复现（`git show <旧提交>:config.example.yaml` 临时替换）钉死根因是旧 example 落后新 v8 键位表 34 条——"预存"定性必须基线对照才算数。

**打破机制**：**基线对照 ≥3-5 次采样**（单次绿是运气）；预存失败在 PR 声明"CI 为准"；消融一次只禁一个变量（修复代理自引入的第二 bug 会掩盖归因）。注意：清单是提示不是判决——M1 的教训就是清单外还有"没跑到"。

## M4 测试空洞通过 —— 假绿比没有测试更危险

**实例**：①orca glob：mock 不达新文件绑定，旧用例全假绿，最终改真实文件系统 + 依赖注入 seam。②maka #5889 P3（reviewer 抓）：seed 5 runs < 默认 limit 16，fold 循环测试在旧实现下也绿——守卫不了它声称守卫的回归；修法=测试 seam 传 limit=2，单次实现下 `2 !== 5` 必红。③通用验证法：**故意写错误期望值，确认测试会挂**。④CLIProxyAPI #6249：测试夹具按 issue 文里的高层形状写（auth-JSON `"headers"` 块）不生效，单元层真实契约是 `header:*` 前缀属性——**夹具要用被测层的真实约定，不是报告者视角的形状**；测试红的原因与预期不符时（override 红但报"没覆盖"而非"覆盖错值"），第一反应查夹具。

**打破机制**：新测试落地时做一次"有牙检查"（临时破坏被测行为，必须红）；fixture 规模必须真的越过被测阈值；夹具形状以被测层的代码契约为准，报告者/文档的高层描述先降一级验证再采信。

## M5 私有语义改共享面 —— 收窄自己域的语义，别动别人在读的字段

**实例**：maka #5890 P2（reviewer 抓，P2 级）：为了让 hosted settlement 不被辅助调用的 missing 行打翻，第一版直接改了共享 `COVERAGE_SUMS`——但该字段同时被 pricing-coordinator 返还普通客户端、被 inspector 当"可显示 cache-hit rate"的许可，收窄让真实 unknown-usage 调用对公共 provenance 隐形。正解（reviewer 给出）：账本字段恢复真实，settlement 自己做 run-scoped 检查。

**打破机制**：改任何共享字段/计数器/常量前，rg 它的全部消费方并逐个问"这个语义变化对它意味着什么"；自己的域要特判，就在自己的域加专属查询，不改共享定义。

## M6 上游语义对撞未显式裁决 —— 文本冲突机械解，行为冲突要披露

**实例**：maka #5274 四次追平全撞 staging 域演进：#5815 反转"unchanged 拒发"（遵上游删门+披露）；#5868 持久 owner（快照/活板双语义共存分）；#5868 机械保留的 send 侧检查会恒误拒（非其有意变更，PR ui-gate 胜出+双侧测试佐证）。

**打破机制**：解冲突先分类——上游改的是结构还是行为契约？行为契约变了就遵上游+在 PR 评论显式披露语义变化；"上游机械保留的检查"要用反例推演它是否仍成立，推翻时给出证据链。

## M7 上游同题取代与抢坑时态

**实例**：CLIProxyAPI #6200 被同题严格超集 4.5 小时取代（rebase 必空 diff，留言关单）；#6198 rebase 时发现上游已修；maka epoch 撞号成常态（#5709 三次顺延 199→202）；cc-switch 撞车窗口 2 分钟、抢坑者不发评论。

**打破机制**：mergeable dirty 先 `git log upstream -- <path>` 查等价修复，被取代就 gracious 关单；**开 PR 后次日必查上游有无等价实现**；烈仓排雷翻 open PR 标题列表，不等评论。

## M8 并行写者竞态 —— 一切远端状态在使用瞬间重新核验

**实例**：maka 白天并行会话推进 #5265/#5274 的 head，本地基准整体失效两次；cockpit-tools"被杀"代理实际存活继续写文件；另一会话"all findings addressed"的声称经逐条核验有水分（retrospective 模式三）。

**打破机制**：动手前 `fetch origin` 核对 PR 远端 head，推送前再 fetch 一次；子代理声称的完成态用内容哈希钉住 + 逐字节 diff；声称与事实之间永远隔一层核验。

## M9 守卫判定面本地失配 —— 本机复刻 CI 守卫必须逐字同参同基线

**实例**：maka #5887 epoch 守卫：本机 `--base upstream/main` exit 0，CI 红——本机 fetch 的 base 是旧 tip；CI 的守卫把三个 protocol 文件都算"协议变更"而本机脚本跑法没覆盖。maka #5274 棘轮：CI 的 BASE_SHA 动态取 main tip，本地老基线的余量优势作废（11129 零余量）。

**打破机制**：本机跑守卫前先 `fetch` 并对**当前 main tip** 传参；守卫的文件清单/判定口径以 CI 日志为准逐字对齐；冻结面/账本类守护，改前查当前 tip 的基线值而非自己上次过的。

## M10 环境链错位 —— 半截状态是常态，重建走全套

**实例**：切分支/clone 后幽灵 TS 错误（core→storage→runtime→mcp→runtime-host 依赖链）；`--ignore-scripts` 跳过 postinstall 补丁（@astryxdesign 幽灵 TS2322）；删 dist 不删 tsbuildinfo 产出半截 dist；ui 的 clean 脚本才能删干净；npm JUNCTION 断裂。

**打破机制**：症状=一片"键不存在于类型"时不要逐个读类型——直接走完整重建流程（补丁脚本→依赖链→clean）；判定法：报错文件与 upstream 逐字节一致 + 依赖版本一致 = 环境病。（retrospective 模式六的本仓延续，此处补跨仓流程化。）

## M11 快照腐烂与教训变体泛化失败 —— 蒸馏不到位 = 教训白记

**实例**：①快照腐烂：记忆/恢复模板里的 PR head、预算数、路径两代失效（E:\guahub→gh-fork→type-first），新会话按旧路径直接失败。②变体泛化失败：epoch 守卫"读提交不读暂存区"教训入册后，仍以两个变体再犯（豁免 JSON 带注释头致 JSON.parse 静默失败；staged 声明要显式 `--staged` 标志）——记住了实例没抽象出"守卫读的是 git 对象不是工作区/暂存区，任何未提交的声明对守卫不存在"的一般规则。③retrospective 模式一（#4801→#4816 同病再犯）是同根：教训写下来了，但**开工动作里没有强制消费点**。④CLIProxyAPI：**自己写进台账的状态断言也会错**——09-28 "dev 只有消费端无生产端"误记（单次 grep 下结论）一个月后才被对象级复核纠正；正确姿势 `git log -S "<串>" -- <path>` 钉出身 + `git show <sha>:<path>` 读对象；错误不回写旧条目（只追加），靠新条目显式更正。

**打破机制**：教训入册时强制写"抽象规则 + 检测动作"两层（规则泛化到变体，动作可执行）；快照类信息（head/预算/路径）不进记忆，记忆只存指针 + "去哪读最新"；每个项目的开场固定流程就是教训的消费点，新教训要落成流程步骤而不是只落成文字；**定性断言（预存/已修/已对齐）写进文档时必须带验证命令，否则显式标注"推断"**。

## M12 无冲突语义漂移 —— mergeable clean ≠ 语义安全

**实例**：①CLIProxyAPI v8 模块迁移：rebase 零文本冲突，但分支**新增文件**（测试）import 旧路径 v7——自动合并永远不会触碰新增文件，编译炸（后每单动工前先 grep 旧路径）；②#6198：auto-merge 对"双方各自新增同名函数"不做冲突检测，源文件静默产出重复定义；③维护Ⅴ：三单 mergeable=true，但 dev 对同文件的无关改动（新增 home-options 早退分支）照样可能改变分支代码的运行语义——文件交集清单是语义复查的触发器；④custom 分支同步：rebase 零文本冲突，验证矩阵爆出端口语义冲突（example 端口定制撞上游新模板测试）+ v7 残留（api_tools_quota_test）。四例同一形状：**git 说没冲突，运行时说有**。

**打破机制**：rebase/追平后固定两动作——`git diff upstream/...HEAD --name-only` 逐文件 grep 旧标识符（模块路径/同名函数/键名）→ 跑改动包测试；dev/上游对同文件的任何提交都打开看一眼与 diff 区域的关系；"文本无冲突"只证明能合并，不证明合并后行为正确。

## M13 镜像源漂移 —— 多源逐字一致，校验器是唯一判据

**实例**：①CLIProxyAPI v8 双布局键名对表：同一配置键在三处必须逐字一致（config.example.yaml 的 yaml 键 / v8Paths 的 current 路径 / struct yaml tag）——example 键名与 v8Paths 差一个前缀，flattenV8 不搬 → 残留键触发严格解码报错 + 34 条迁移警告（TestV8Example 当场抓住）；②custom-addon 的 modified-files 归档快照 vs 源码树：rebase 后源码树更新、快照未跟 → verify-archive.ps1 报漂移，拷源码树版本同步；③maka 棘轮账本/冻结面：BASE_SHA 随 main tip 动态取，本地老基线的余量优势作废（与 M9 交叉）。

**打破机制**：改镜像源任一侧，**立即**同步其余侧（不要攒）；有校验器的镜像（verify-archive、TestV8Example 这类"模板/归档/账本守卫"）每次改动后必跑；没有校验器的镜像源，rebase/迁移后手工 diff 一次；新增任何"第二份拷贝"前先问能不能只留单一来源 + 指针。

## M14 状态噪音当改动 —— status 的 M 先与内容对账

**实例**：①home 仓（多机 dotfiles）`.codex/share`：58 个 M 的内容 diff 全空（CRLF 幻影），checkout 还原零损失；②home 仓候选池上游同步：4498 个 M 里 3523 个是 autocrlf 检出翻行尾的幻影，真实变更仅 975 个文件（+24718/−18565），按差集分批还原零失败；③SMB 挂载克隆同步：4400+ "脏文件"剥 CR 哈希逐个验证全为纯行尾差异（sessions/summary/2026-11-01-SMB挂载git克隆同步与CRLF清理）。三例跨 home/cc 两仓与挂载克隆，同根：Windows autocrlf=true 下 clone/checkout/stash 翻行尾，status 标 M 而 git 对象内容零差异。

**打破机制**：批量场景先对账再动手——`status --porcelain` 的 M 数减 `git diff --name-only | wc -l` 即幻影数；逐文件定性用剥 CR 哈希两侧比对（`tr -d '\r' | shasum -a 256`）；还原零信息损失，但避开 Windows 命令行长度上限（约 50 条/批，或 `--pathspec-from-file` + `--pathspec-file-nul`）。根因不治每轮同步再生（autocrlf 检出即翻行尾），根治候选是 vendored 树 `.gitattributes` 标 `-text`（未实施）。fork 侧同根变体已实测：autocrlf 致 `gofmt -l` 全文件假阳性，判定法 `tr -d '\r' < file | gofmt -l /dev/stdin`。

## 跨模式的一条主线（元教训）

**对抗式审查的对象首先是自己的结论。** 上面 14 条里，M1/M3/M4/M8/M9/M11/M12/M14 的共同根因是：把"没有反证"当成了"证据"。反证不会自己出现——它需要主动构造（消融、假红、对照、fetch、打印 failureReason）。本日 #5890 三轮 CI 定性两次反转的成本（每轮 ~30 分钟 + 一次空提交），只有一步是不可省的：**在下结论前，用最便宜的实验拿到裁决性文本**（failureReason 一行打印就终结了三轮争论）。
