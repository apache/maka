# 分工与并行

> 适用于所有直接提 PR 的 fork 项目。magpie 走"patch 附 issue"，规则另见 hub/magpie/；两者的差别见文末。

借鉴 yetone 的做法：**每条线只盯一个信息源、只对一件事负责，做完要闭环。** 不要求开多个 loop；同一个主会话可以依次扮演多个角色，但每个角色只写自己的地方。

## 1. 角色

| 角色 | 由谁担任 | 负责什么 | 只写这里 |
| --- | --- | --- | --- |
| **哨兵** | 定时任务（只读）或主会话开场 | 盯在途 PR 的合并 / 关闭 / 新 review / mergeable、关注 issue 的新回复、base 分支前进 | 项目 `sentinel/` 下的基线文件 |
| **猎手** | 子智能体 | 新单：复现 → 修复 → 本机验证矩阵 → 交回分支与证据 | 自己的 worktree 与分支 |
| **维护** | 子智能体 | 在途 PR：逐条处置 review 和 bot 意见、修 CI 红、rebase 或解冲突 | 自己的 worktree 与对应 PR 分支 |
| **书记** | 主会话 | 每轮收尾记账：逐单条目、在途快照、跨仓总台账 | 项目 `journal/`、fork/docs 总台账 |
| **复盘** | 主会话（每周一次，或翻车当轮） | 把翻车提炼成规则，清理过期内容 | 项目 `hub/<repo>/handbook/`、[handbook/](README.md) |
| **你（人）** | — | 拍板：方向分歧、对外口径、要不要放弃一单；处理 AI 判断不了的 UI / UX 与产品取舍 | `hub/<repo>/journal/`（拍板写进当轮条目） |

一张单的闭环：哨兵发现 → 主会话认领并派单 → 猎手 / 维护在 worktree 里干活并交回 → 主会话复核后推送、开 PR 或回复 → 书记记账 → 复盘把教训晋升为规则 → 下一轮开场读到新规则。

**任何一步没走完，这单就不算结束。** 修完没推、推了没回复、回复了没记账，都算"盘点未完成"。

## 2. 优先级（每轮按序）

1. **维护在途 PR**：review 修复 > 清除阻塞根因 > 超过 3 天无信号时 gentle ping（不连发）。
2. **接新单**：每个项目每轮最多 1 单。

理由：PR 通道的价值在合并，在途 PR 拖久了会冲突、会被取代，比新开一单更亏。

## 3. 并行上限：每个项目最多 2 个子智能体

- 同一个项目同时最多 **2** 个子智能体。常见组合：
  - **A 猎手 + B 维护**（默认）；
  - **A、B 两路猎手**：只在没有待处理 review 时用，且两路领不同 issue、改不同文件。
- 两路不得碰同一个 PR、同一个分支或同一个文件。派单前主会话先查文件交集，有交集就串行。
- 不同项目之间可以并行，但同一台机器同时跑全量测试套件的不超过 1 路（会互相拖慢，导致全部超时）。
- **例外**：magpie 的车道编制见 [hub/magpie/handbook/11 狩猎轮机制](../hub/magpie/handbook/11-狩猎轮机制.md)；maka 有 `maka-pr1..3` 三个并行 clone（见 [maka-hub/AGENTS.md](../../maka-hub/AGENTS.md)），每路子智能体独占一个 clone。两仓的并行上限以上述文档为准。两者的独立 clone 登记在 [01 §2](01-接单线程池.md#2-项目身份与文档入口)。

## 4. 只有主会话做的事

- **认领与占坑**：查 issue 的 assignees 字段、评论区、open PR 标题（抢坑者常常不评论直接开 PR），确认无人占坑后再认领。
- **分配全局单号**：只有主会话从 fork/docs 总台账取号，子智能体不取号（防撞号）。
- **推送、开 PR、对外评论**：子智能体交回结果，主会话复核红绿证据后再动。评论中的链接和 ID 发出前先用 API 核对。
  - 例外（magpie、maka）：按 [fork/AGENTS.md §3](../../AGENTS.md)「发布权按形态分（2026-10-24 定版）」，子智能体自检 → 推 fork → 发帖 → GET 回读，自行发布；主线程只做事后复核（回读已发帖、消融抽验）。
- **合并结论**：PR 是否"完成"由主会话按 API 实测判定，不信子智能体自报。

## 5. worktree 规范

| 项 | 约定 |
| --- | --- |
| 主 clone | 只做 fetch 和读，**不切分支、不 stash、不在上面改代码** |
| 位置 | `/tmp/<repo>-wt-<issue 或 PR 号>`，不在 fork/ 顶层新建目录 |
| 起点 | 新单从 `upstream/<base>` 切新分支；维护单检出该 PR 的远端 head |
| 一一对应 | 一个 worktree = 一个分支 = 一个 PR = 一个子智能体 |
| 基线对照 | 判定"预存失败"时，另建一个指向干净 base 提交的 worktree 跑对照，不用 stash 回退 |
| 收尾 | 推送后执行 `git worktree remove` + `git worktree prune`，并在报告里写明"零残留" |
| 例外 | 项目确实需要独立 clone 时（例如构建链会污染共享 .git），在该项目的 `hub/<repo>/handbook/01` 写明原因与路径 |

## 6. 子智能体交回什么

```
分支 + head SHA
改动摘要（文件 + 一句话原因）
验证矩阵：跑了什么、结果；没跑什么、为什么
review 意见逐条处置表（维护单）
本轮不自信的点
```

## 7. 与 magpie 的差别

| | magpie | 其他 fork 项目 |
| --- | --- | --- |
| 交付形态 | patch 附 issue（上游关闭外部 PR） | 直接提 PR |
| 主要循环 | 发现 → patch → 等维护者采纳 | 发现 → PR → **review / bot / CI 多轮** → 合并 |
| 最重的角色 | 猎手 | **维护**（bot 每次推送都复审，CI 常需维护者批准才跑） |
| 结局记录 | 采纳 / 自实现 / 取代 | merged / closed / superseded |
| 并行 | 多路 hunt | **每个项目最多 2 个子智能体** |
