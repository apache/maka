## 跨仓教训（违反过，勿重犯）

- **git auto-merge 对"双方各自新增同名函数"不做冲突检测**——rebase 后必须 grep 核对（#6198 实录）。
- **上游实现同题不会通知 PR 作者**——交付后隔天查默认分支是否已被等价修复（#6200 被 02548d67 取代关单实录）。
- **合并率指标必须区分"内部消化"与"外部可进"**（minimax-code 40/40 是假信号）。
- **报告者自带根因分析的单性价比最高**；"无法复现"要靠可复核探针 + 回归测试一并交付。
- **让坑也是贡献**：诊断成果写入对应仓 journal，占坑 PR 滞留可回收。
- **修复代理自报的"不自信的点"是下轮被 review 命中的高发区**——写报告时认真列，盯审时优先复核（orca exactly-4096、cherry 零条目保存两例均应验）。
- **验证分支相关声称用 `git show <sha>:<path>` 读对象**，工作树可能不在你以为的分支上（09-30 晚主会话差点误判代理造假实录）。
- **维护者自动审查 bot 要识别**：cc-switch 的 GPT-6 Astra（codex-astra-review）、cherry 的 cherry-ai-bot、orca 的 greptile/pullfrog/coderabbit——意见都要实测核实，几轮下来真 bug 率不低。
- **选题闸「未被占」必须含 issue `assignees` 字段检查**——评论区认领 + open PR 排雷不覆盖维护者 self-assign（cherry #21132 实录：DeJeune 早 3.5 天 self-assign，代理四道闸判"未被占"开 PR 抢跑，靠透明声明评论兜底）。衍生：自动审查 bot/维护者的 assign 不等于在做，3+ 天无动作可 PR + 声明并存，但 assign 事实必须主动披露，不许当没看见。
- **候选池保鲜期以小时计，接单前排雷复查是硬闸**（10-09 接单轮实证）：orca 三单从筛出到动手数小时内全部被 open PR 正面占坑，PR 正文 Fixes #N 搜索一次救回 4 单（含 cherry #21375 维护者 27 分钟 self-assign + 开 PR）——assignees 字段 + timeline 占用事件 + open PR 正文三层都查才叫排雷完。
