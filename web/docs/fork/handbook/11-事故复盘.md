> 合并自：原根级 09-2026-10-13-家目录仓摘帽事故复盘.md 与 handbook/incidents/2026-10-13（两者正文逐字同源，取一）、handbook/incidents/2026-10-18，2026-10-24。两起同根因事故按发生顺序分节；§2 的防护以 §1 的防线为前提，连读。

> 性质：本机数据事故，非任何上游仓库缺陷。影响面为家目录 dotfiles 仓（`~` = `C-Users-ggbdpq`）跟踪文件被批量摘帽，`.zcode` 未跟踪数据真实丢失。

## 1. 2026-10-13 首次摘帽（.ai 技能库 / .zcode 会话丢失）

## 问题表现

- ZCode 通过 magpie 网关使用 codex，23:29 codex 5 小时限额耗尽（收到正确 429），随后 ZCode 退回首启登录界面，全部会话记录消失，全局 skills 真身 `~/.ai`「彻底消失」，`~/.githooks`、`.agents`、`.gemini`、`.kiro` 同批不可见。
- 用户体感为「magpie 删了我的数据」，同型事件已是第 3 次（2026-09-11 另有一次经 junction 删 `.ai` 的前科，见 `.githooks/pre-commit` 注释）。

## 触发条件

- 家目录本身是 git 仓（白名单式 `.gitignore`，`!/.ai/**` 等显式放行）。
- ZCode 定时任务「Ponytail 拉取远程代码并解决冲突」以 `/Users/ggbdpq` 为工作区运行，周期约 30 分钟。
- 事故当晚该任务经 magpie→codex 执行；codex 限额在任务中途耗尽。

## 排查路径（可复核证据）

| 证据 | 命令 | 读数 |
| --- | --- | --- |
| 两次硬重置 | `git -C ~ reflog --date=iso` | 22:58:45、23:29:29 各一次 `reset: moving to FETCH_HEAD`（目标=本地 HEAD，内容无变化） |
| sparse 收窄时点 | `stat -f %Sm ~/.git/info/sparse-checkout` | 23:29:31，锥形只剩 `.codex/vendor_imports/skills/skills/.curated|.experimental` |
| 被摘帽文件 | `git -C ~ ls-files -v` | `.ai/*`、`.zcode/AGENTS.md` 全部为 `S`（skip-worktree） |
| magpie 无责 | `~/.zcode/cli/log/zcode-2026-10-13.jsonl` 首条 | 429「Codex: The usage limit has been reached」，retryable；magpie usage.jsonl 连续服务至 23:30 无异常 |
| zcode 侧佐证 | `~/.zcode/v2/logs/2026-10-13.log` | 23:29:31 起重建 `v2`、报凭据缺失（credential unavailable） |

两个排查弯路记录：①`git status` 不显示被摘帽文件为删除（skip-worktree 语义），一度误判「git 操作无辜」；②`git ls-files | grep '^\.ai/'` 只数到 3 个文件——中文路径被 `core.quotepath` 加了引号转义，真实跟踪量是全部 1890 个 SKILL.md。

## 根因分析

1. **直接原因**：AI 自动化任务在家目录仓执行了 `git fetch` + `git reset --hard FETCH_HEAD` + `git sparse-checkout`（收窄）。sparse 收窄时 git 把锥形外的跟踪文件从工作区移除——`.ai` 技能库、`.githooks` 等并非被删除，而是被「摘帽」（对象仍在库中）。
2. **真实丢失**：`.zcode` 下未跟踪的会话库（`tasks-index.sqlite` 等）、登录凭据、自动化任务定义。删除这些未跟踪文件的确切命令已随 zcode 日志一并丢失，无法钉死到具体一条命令；可确认的是它与上述 git 操作同一窗口（23:29:27–23:29:31）由同一任务会话执行。
3. **边界误判**（为何三次才定位）：表象（限额耗尽 ⇒ 数据消失）把嫌疑引向 magpie；实际上限额只是自动化任务的运行环境，摘帽动作发生在任务「解决冲突」的名义之下。相关性被误读为因果。
4. **既有防线缺口**：`.githooks/pre-commit` 的 `.ai` 删除守卫只拦 `git commit` 时的删除固化，对 `reset --hard` / `sparse-checkout` / 未跟踪文件删除完全无效——而这三类操作不产生 commit。

## 修复方案

- **恢复**：`git -C ~ sparse-checkout disable` 一条命令，`.ai`（245MB / 1890 个 SKILL.md）、`.githooks`、`.agents`、`.gemini`、`.kiro`、`.zcode/AGENTS.md` 全部还原。未跟踪的 `.zcode` 会话与登录态不可本地恢复（无 Time Machine 快照），需重新登录、重建任务。
- **防复发**：`scripts/home-sync.sh`（cc 根，2026-10-23 自 `guahub/scripts/` 上移；commit `b3f3a3e50a`，2026-11-07 实测不可解析，见 §3）——确定性同步脚本，只做 fetch + `--ff-only` / push，分叉即停；发现 sparse 启用自动 disable 并告警；`--commit-all` 替代「提交本地修改」类自动化。脚本头部附 AI 自动化提示词硬约束文本（禁 `reset --hard`/`clean`/`sparse-checkout`/`rm -rf`），供必须保留 AI 任务时逐字引用。

## 验证方式

- `sh ~/cc/scripts/home-sync.sh` → 「同步完成：main @ afdd0239」，语法 `sh -n` 通过。
- 恢复核验：`find ~/.ai -name SKILL.md | wc -l` = 1890；`ls ~/.githooks/pre-commit` 存在且为跟踪文件；`git -C ~ ls-files -v` 中 `.ai`/`.zcode` 行全部为 `H`。
- 残余工作区漂移（`M .codex/config.toml` 等 3 项）为事故后正常改动，随下次 `--commit-all` 入库。

## 预防建议

1. 家目录仓的同步永不交给 AI 代理自由执行 git；定时任务一律调 `home-sync.sh`。
2. `.zcode` 的会话/凭据目录未入版本控制也无快照，属单点；若接受其易失性，至少在 ZCode 自动化提示词中把 `~/.zcode` 列为禁写区。
3. 排查「某工具删了我的文件」类报告时，先查家目录仓的 reflog 与 `info/sparse-checkout` mtime，再怀疑外部进程——本机已有两次前科都落在这一路径上。

## 2. 2026-10-18 二次摘帽：三层防护落地

## 事件

- 2026-10-18 10:33:46 `git reflog`：`reset: moving to FETCH_HEAD`；10:33:50 `.git/info/sparse-checkout` 写入，锥形只剩 `.codex/vendor_imports/skills/skills/.curated|.experimental`；同一分钟 ZCode 重建 `~/.zcode/v2` 并报 `credential unavailable`。
- 摘帽 **17385** 个跟踪文件：`.ai` 15181、`.cursor` 1963、`.codex` 89、`.claude` 77、`.gemini` 28、`.kiro` 3、`.zcode/AGENTS.md` 1。`git status` 不显示删除（skip-worktree 语义）。
- 恢复：`git sparse-checkout disable` 2.2 秒，17385 全回；`.ai` 1891 个 `SKILL.md` / 257MB。
- 真丢失：`~/.zcode` 未跟踪的会话库、凭据、定时任务定义。`tasks-index.sqlite` 被重建为空库（`automations`/`tasks`/`task_groups` 均 0 行）；`tmutil listlocalsnapshots /` 无快照，不可本地恢复。

## 根因：09 的防线没有生效

> 校注（2026-11-07）：本节的「09」指原根级 09 号复盘文档，即本文件 §1。

- §1（原 09）的 `scripts/home-sync.sh` 逻辑正确（ff-only、分叉即停、检测 sparse 自动 disable），但**只有被调用才生效**；本次仍是 ZCode 自动化直接跑裸 git。
- §1（原 09）建议的「提示词硬约束 / `~/.zcode` 禁写区」当时未落地，同类事故第 2 次发生。肇事定时任务的定义已随会话库丢失，短期不会自动复现，但重建任务时若照旧写命令仍会复发。

## 三层防护（本次落地）

| 层 | 机制 | 落点 |
| --- | --- | --- |
| 预防（硬阻断） | `chflags uchg ~/.git/info`，`sparse-checkout` 无法创建模式文件，git 直接 `Operation not permitted` | 文件系统标志，重启后保留 |
| 自愈 | 检测 config / skip-worktree / 模式文件 / 受保护路径删除 → 还原、清模式文件、重新上锁 | `~/.local/bin/home-repo-guard.sh` + LaunchAgent `com.ggbdpq.home-repo-guard`（WatchPaths `~/.git/info` 秒级 + 每 300 秒兜底） |
| 恢复 | 每 20 小时备份 `~/.zcode`，sqlite 用 `.backup` 取一致性快照，排除证书私钥，保留 14 天 | `~/Library/Application Support/ggbdpq/zcode-state/` |

关键不变量：**`.git/info/sparse-checkout` 必须不存在**。实测（11:04）`sparse-checkout set` 被 uchg 挡住时，git 已先把 `core.sparseCheckout` 写成 `true`；旧模式文件若还在，下一次 `reset --hard` / `checkout` 就会按旧锥形清空工作区。因此 guard 与 `home-sync.sh` 都以「模式文件存在」为一级告警条件，而不只看 config。

## 验证证据

| 用例 | 操作 | 结果 |
| --- | --- | --- |
| 硬阻断 | `git sparse-checkout set .codex` | `fatal: Unable to create .../sparse-checkout.lock: Operation not permitted`；S=0，`.ai` 15181 文件不变 |
| 自愈 | 阻断后运行 guard | `core.sparseCheckout=false`，模式文件不存在，`info` 复锁 |
| 删除还原 | `mv .githooks/pre-commit /tmp` → guard | 文件从索引还原，`cmp` 与原文件一致 |
| 备份完整性 | 解包最新 tgz，`pragma integrity_check` | `tasks-index.sqlite`、`cli/db/db.sqlite` 均 `ok` |
| 守护进程 | `launchctl print gui/501/com.ggbdpq.home-repo-guard` | 已加载，`last exit code = 0` |
| 规则层 | `~/.zcode/AGENTS.md` 新增「本机数据边界」 | 禁止写类 git 操作、同步只走 home-sync.sh、`~/.zcode` 禁写 |

## 运维手册

- **临时需要 sparse**：`chflags nouchg ~/.git/info && git sparse-checkout set <path>`；guard 会在 5 分钟内还原并复锁，属预期。
- **还原 `.zcode`**：先退出 ZCode，再把最新 `zcode-state-*.tgz` 解到临时目录后拷回；证书目录未备份，重新登录/生成即可。
- **停用防护**：`launchctl bootout gui/$(id -u)/com.ggbdpq.home-repo-guard`，删 plist，`chflags nouchg ~/.git/info`。
- **日常同步**：仍只走 `sh ~/cc/scripts/home-sync.sh`（已同步支持清理残留模式文件）。

## 残余风险

- 同等权限下的进程可以 `chflags nouchg` 或 `launchctl bootout`，本方案防误操作、不防蓄意绕过。
- `~/.zcode` 备份在本机同一磁盘，整盘故障会同时丢失；跨机冗余需另行同步。
- `git clean -fdx` 在 `$HOME` 仍可删除其他未跟踪数据（`.zcode` 有备份，其余无保护）；这类命令没有任何 hook 能拦，只能靠规则层约束。
