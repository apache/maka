早期轮次的 APPROVED review 出自 cherry-ai-bot（现已不活跃），挂着的旧 approval 不代表当前真态，以上述两条硬规则为准。

逐条处置规则：

- **CR 定性**：拉 `pulls/{n}/comments` 看每条 finding 的 `diff_hunk`——引用当前 head 新代码+新触发器=真 finding（旧 finding 的新变体，复现→根因处修）；只引用旧代码=竞态重放可挂起。review body 的 "repeat invariant from head <旧sha>" 只是场景溯源，不作定性依据。
- **处置方式**：多条 finding 的处置单开子智能体并行（本块对全局「不开子智能体」纪律的例外，2026-10-25~26 四轮实战验证），每单独立 worktree，主线程只做排雷、复核、CI 对照与记账；子代理中断时先盘点现场未提交 diff 续做，不推翻重来。
- **线程**：bot 回复旧线程会 reopen resolved thread，且新线程可能开在「无未解线程」核查之后——每轮 bot 报告后重查 `reviewThreads` 的 unresolved；resolve 前逐条 `git show` 核实声称的修复真的在对应 commit 里。
- **本机陷阱**：pre-commit hook（Oxfmt/ESLint/Bilingual）会静默中止或改格式 commit——commit 后 `git log --oneline -1` 核实 SHA，push 前核对 Signed-off-by；vitest 临时测试/基准必须放仓库内 `__tests__`；`pnpm typecheck` 不接管道（`> log 2>&1; echo $?`）；push 前 `git ls-remote` 核对远端 SHA 防并行撞车。
- **bot 挂起恢复**（2026-10-31~11-06 实证闭环）：cherry-review `action_required`「did not finish…maintainer must recover or rerun」= 基础设施挂起，**恢复权限只在维护者**，推代码或 push 空头提交博新轮无效（十三轮连挂已证）。处置=发 recover 请求帖（@DeJeune，附挂起原文 + CI 全绿清单 + 0 未解线程证据），~5 天零响应后温和跟进一次——10-31 请求 + 11-05 跟进 → 11-06 恢复并转 passed。
- **excluded candidates 留档**：bot 报告按增量范围实名排除的 pre-existing 候选（#21322 11-06 报告排除 2 个：legacy whole-server denial 的 `mcp__<UUID>` 形态不被 `translateLegacyMcpToolRules` 翻译；type-only browser eligibility 变更如 `inMemory`→`stdio` 不迁移被挤开 sibling 的 denial——与 10-25 轮「报而不修」兄弟形态同源）是将来开 issue 的素材，细节落 journal 在途快照；等维护者有信号后再决定是否上报，零信号期不堆叠对外动作。
