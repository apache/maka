# Discord 清单帖模板（整批推荐）

> 用法：整批发 patch 给维护者。**措辞纪律：不说批次字母（A/B/C/D），只说每条多少支**；上一批未审要提一嘴「还在你那边没审，有空时过一眼」。

@yetone <开场：上一批 N 支的处理结果逐支锚点+感谢具体处（引维护者改良/确认动作）；这批 M 支同样已 rebase 到当前 main、六要素重验过（测试、消融回红、兄弟面全查），git am 即进：>

• #<N> <一句话痛点：谁在什么场景撞什么——修法/形态一句带过（报告者分支注明、test-only 注明、留维护者拍板的注明）>
• …（每支一行，行长 1-2 句；判定/验证帖单独一组：无 patch，细节在各自 issue）

M 个都已 rebase 到当前 main，git am 即进；分支、sha256、测试、消融都在各自 issue 里。

## 发帖前硬门
1. 对当时 tip 全量 merge-tree 快扫（CLEAN 则原基线证据仍可用；冲突支先 rebase 复证）
2. 收编双层查终扫（单号 grep+末评形态 lower+contains；**无声收编读 body**）
3. 逐支 issue 末评确认无新回合
4. 与上一条消息隔几小时（r15+r16 同发漏审判例）
## 发帖后
24h 收编对账：窗口单号 grep+末评形态（限维护者）→台账回写结局（SHA/版本/署名形态）

## 结构变体（出处：批 A/B 两条各 20、r16 消息 1/2/3、discord-20261108 剧场制）
- **多消息拆分**：一批 >15 支拆多条消息（各 ~20 支）；消息 1=上一批确认（逐支锚点+谢具体改良），消息 2=新交付，消息 3=分类清单。
- **剧场制**（2026-11-08 定版）：每场 20 单为一个批次；帖稿节名「第 N 场（20 支 = 构成计数）✅ 已发（各 issue 内）」；朴素堆积每支一行「#N 现象——修法」，head/sha256 留在各自 issue 不上帖面；判定/背书/出列各一句一组收尾。
- **已发标记**：用户贴后标题标「✅ 已发 <日期 时间>（Discord 实贴）」。
- **分类清单消息变体（review map，出处 r16）**：待审 patch 按 P1（成本/数据完整性/请求处理）/P2（兼容/配置/同步/可观测）/P3（测试稳定）分级列表，每级带「必过证据门」一句（证据落各自 issue，清单只是入口）；不计入候选数的单独说明。
- **催审段公式**（出处 discord-20261108 17 支帖）：事实语气点名存量（「<日期>那 N 支记下后还没见到进 main 的」）+看到的部分进展致谢（引 sha）+给维护者选项（「想挑着来，给我个优先级标准，我来排好序再报」）——不催进度只摆事实。
