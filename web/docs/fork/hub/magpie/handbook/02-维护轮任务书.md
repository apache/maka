# 维护轮任务书

自动化每 30 分钟触发的「待审 patch 清理」轮（automation-ff5e7ca4，2026-10-27 建）。**维护轮不是狩猎轮：不接新单**，只做两件事——①修复别人指出的 review 意见（P0）；②rebase 落后/冲突的在途分支。

## 开场（主线三查，零工作就不派车）

1. `git fetch upstream main` 记录 SHA，`git log <上轮SHA>..upstream/main --oneline` 看增量。
2. 回合扫描：[../索引/](../journal/索引/README.md) **行尾最新状态标记为 ⏳ 且 GitHub 上 issue 仍 open** 的在途单逐个拉末 2 评论与我方末评对时（行是只增不改，⏳ 会留在已结单行历史段——含 ⏳ 痕迹的行数不是在途实数，口径见索引 README 状态口径）——**维护者/审计者/报告者指出问题（review 意见、修复要求、误读纠错、拒绝理由、让位/收编/关单信号）=P0**；我方末评在位=零动作。通知 API（`/notifications?all=true`）按时间窗过滤可省预算。
3. 批测：在途分支 `git merge-tree --write-tree upstream/main origin/<分支>`——干净=不动；3way 可合=观察；**真冲突、或基线落后 ≥30 提交、或上游新提交触及 patch 目标文件=rebase 车道**。归档分支（已收编/撤回/被取代）不进批测。**上游高频期（如 40+ 笔/2h）"落后 ≥30"会旗标全部在途支，此时按"真冲突或增量 hunk 与 patch 语义相交"执行，纯落后只监控**（2026-10-29 实测判例）。

## 派车（≤2 个子智能体并行，P0 review 修复 > rebase）

> 校注（2026-11-07）：本节编制只适用于维护轮；狩猎轮编制以 [11](11-狩猎轮机制.md) 为准。

- 每路独占 worktree，显式从 upstream/main SHA 切；轮号先查编年当日分册末节取下一个号（防多会话撞号）。
- 任务书必含：读全 issue+评论+代码；TDD（review 修复带"修前会挂"）；消融纪律（先 commit/只回产品文件/基线=分支父提交/看原输出）；矩阵（定向+改动包全量 -tags nogui+gofmt+vet×3+build×3）；Watched 三查；GUI 整包严禁全量跑。
- 发布形态（禁 PR 政策 b91569d3）：review 修复=force-push 原分支名+回帖 @ 提意见者；rebase=回帖（新 head+range-diff+验证表）。三件套+八项 grep 自检+GET 回读。
- `gh issue close --comment` **不读文件**（参数是字面文本）——关单评论用 `gh issue comment --body-file` 先发、`gh issue close` 后关，或干脆只关不评。

## 收口（主线统一记账）

- 记账位置：[../索引/](../journal/索引/README.md) 结局列、编年当日分册、[../账册/成本逐单台账](../journal/账册/成本逐单台账.md) 与 [../账册/采纳统计与快照](../journal/账册/采纳统计与快照.md)（xlsx 总表轮次间增补，防并发写）。文件追加后必须回读；表格行内禁裸 `||`。
- 车道遗留本地分支核验 fork 在位（ls-remote）后 `branch -D` 清理。
- **零产出=正常结果**：编年记一行「巡检零产出」即收口。

## 判例（hunt96 实战沉淀）

- **派车限额连拒**：并发/串行/冷却重试均拒→候选清单落编年留下轮直接派；或查遗留 worktree（干净=复用）后**主线文档化降级自做**（0 车在跑时上限不破）。
- **rebase 帖发后必须 ls-remote 复核落地**——出现过帖中 head 从未推上远端的在案记录（推送失败≠帖子说了算）。
- **分支→单号映射以提交消息内 `(#N)` 为准**，分支名会骗人（hunt52-e 实际是 #3051 非 #3052）。
- **同分支多提交按消息 `(#N)` 全量迁移**，别按"单提交"假设漏迁（hunt65-d 实为 #3287+#3286 双提交）。
- **rebase 会剥提交消息中 `#N` 开头的行**（当注释）——用 `commit --amend -F` 恢复后逐字节比对。
- **消融可能因上游演化不再回红**（如活网关自己喂 keepalive 后 stall 路径不可达）——如实披露"守卫角色收窄"，不谎报全红全绿。
- **docs-only rebase 的相称验证 = markdown 结构检查 + 补丁自带测试**（2026-10-31 #2532 实例）：代码零变化时全量 Go 套件结果与 rebase 前恒同，~8 分钟等待纯属浪费（用户抓包「卡住」后砍掉）；验证范围与变更类型相称。

## Discord 推荐清单（催办帖，2026-10-31 起九轮沉淀；验收闭环六环定版 2026-11-01）

维护轮的延伸产物：从在途单里筛值得去 Discord 提醒维护者的批次。**适用前提=维护者高响应（数小时清一批）+上游快速迭代期；低响应维护者降频减量**。筛选法：search API `is:issue state:open commenter:ggbdpq` 取全集 → GraphQL 批量（25 单/次）拉每单末 3 评 → 末评非维护者=在等他侧 → 排除维护者亲单（避坑清单条 16 自留族）→ **第三方末评=最强催点**。

### 闭环六环（发帖前逐环过，环环有产出；状态只信本轮 GitHub/git 实测，台账当线索不当事实）

> 跨仓通用的验收规则在 Skill `gua-pr-patch`（`references/workflow.md` §2-§4、`references/delivery.md` §1-§5）；历史判例见 [fork/docs/handbook/13](../../../handbook/13-测试验收闭环.md)。本节各环保留 magpie 专属单号、判例与出局清单，故未改写为纯链接（2026-11-07 逐句比对结论）。

**一、对时**：读[台账](../journal/账册/Discord推荐清单台账.md)（上轮结局/出局区/在途卡点）→ `git fetch upstream main` 记 tip → 增量扫（判例：批测基线到发帖窗口 tip 可三动，r9 实测 +21 提交）。

**二、准入（四要素缺一不推，只推用户报的实用 bug）**：①分支链接+patch 文本在 issue（sha256 前 16 存证）；②实际 3way 落地批测追平当前 main（`--check` 过≠无冲突，真冲突靠实际落地暴露）；③git am 即进；④三道测试程序证据在 issue：**消红**（摘掉修复测试回红=改动是成因）、**兄弟面**（rg 全查同族调用方不漏兄弟）、**实证**（真实路径复现；替身够不着如实标 Not verified，不谎报全绿）。出局：亲单自留测试族（条 16 三征）、test-only 无产品面、等真机条件（#2198）、刚被驳回在 rework（#4502）、已让坑（#4558）。

**三、判定先于动手**：新单先判语义与覆盖；老支出帖前必过 **RED-on-clean-main 覆盖判定闸**——把 patch 的 RED 测试放干净 tip 跑，红=面还在→继续，绿=已被上游覆盖→出列写让位。实测报废率 2/3（#2316 被 6f6b7d407 同构覆盖、#3161 被 ef0a5c673 覆盖成 no-op；#3380 判过、#2813 判后转重写）。判例详见 [10 §24](10-避坑清单与模式家族.md) 与 [04 §六被拒三型](04-修法方向最佳实践.md)。

**四、验证链跟证据有效性走**（总纲见 Skill `gua-pr-patch` `references/workflow.md` §4：字节不变是轻量链的必要条件；上游 API/签名、依赖、平台前提或维护者裁决变化且影响旧证据时，升语义复验）——环节跟着变更走，验证承诺的最低门槛永远在。**全链**（判定→rebase→定向+消融→am+sha256→force-with-lease→POST 前 --grep 重查→refresh 帖→回读）只在 patch 字节变化时必须走完，三触发：①新交付；②批测 CONFLICT→rebase 解冲突（旧证据全部失效——#4563 判例：rebase 后必须定向+相邻+全包绿、issue 补 refresh 帖更新 head/sha256，否则「sha256 在 issue 里」指向失配的老 patch）；③驳回后 rework（=重新交付）。**轻量链**（存量单推荐轮）：①issue 末评实测+四要素核验（未收未驳+证据齐全）②收编双层查（单号 grep 全历史+痛点关键词+紧格式 `(#N)`，每轮发帖前最后一遍——条 20）③真 3way 落地批测 am 到当前 tip——**这就是「已 rebase 到当前 main」承诺的实证**，CLEAN 即追平，不必例行 force-push；④定向抽测验新树。消融不重做：它证明「改动是成因」，字节不变且被测代码的上游前提未变则因果不变，issue 里 RED 证据继续有效。分支不动不 push；head/sha256 不变不发 refresh 帖（发了是噪声）。**批测 CONFLICT 自动升级全链，没走完整链的单不进帖——这条线不松**（r8 #2316/#3161 即移出待 rebase）。**r10 校准：严格 `git am` 失败但 `am -3` 自动合+测试全绿 = 纯上下文漂移，仍不进帖**（维护者流程是普通 am——r10 #4611/#4632/#4762/#4765 四支因此出列转 rebase）；`-3` 干净只说明 rebase 会顺利，不等于发布承诺成立。判定闸双向作用（r9 实证）：既拦死单也救活单（#3478/#2547 从纸面「自留/打折」判定里实证 RED 仍在救回）——纸面三征不算数，摘 patch 跑 RED 才算数。无声收编第三形态：分支 head 被原样 fast-forward 进 main 未发帖（#1677）——对账判据加「分支 head == main 内提交」。

**五、发布（尾句承诺挂验证）**：尾句固定「N 个都已 rebase 到当前 main，git am 即进；分支、sha256、测试、消融都在各自 issue 里。」承诺映射：**已 rebase←批测 CLEAN；am 即进←patch+sha256 在 issue；都在 issue←四要素④**。挂不上验证的单不上帖；开头的 N、bullet 数、尾句的 N 三处一致（r9 计数错位判例：第 16 支归属以车道实况为准）。

**六、红线**：没走完整链的单不进帖；报告人分组不失实（维护者亲单≠用户报，亲单单独组「你自己开的几单我们也接了」）；已闭环单不复述；说「分支/补丁」不说「PR」（禁 PR 政策）。

**七、收编对账与记账（11-05 判例）**：维护者批量移植后逐单实测（issue 末评+git 历史双查），**不能只盯当轮**——r9~r12 悬支里躺着 5 支已收未记账（#3473/#4587/#4576/#4436/#4611），轮扫要对**全部 open+我方末评单**跑「state+末评」批查，不只扫台账「悬」标记行；维护者汇总帖与实际可能不符（r15+r16 18 支实测 15 进 v0.1.3052，#5074 漏审零回帖——汇总后逐单核，漏审单轻催或下批带）。**帖稿命名（用户令 11-05）**：今后 Discord 帖稿不再用轮号（r17/r18…），改日期式 `账册/discord-YYYYMMDD.md`；台账节名仍用轮次序号便于索引。

### 复核组（发帖窗口 tip 多动的标配，2026-11-01 r9 首战 14/14 CLEAN）

批测基线到发帖窗口上游前进多笔时，派 N 组复核子智能体（总数 ≤5 顶格；校注：此为维护轮复核组上限，狩猎轮编制以 [11](11-狩猎轮机制.md) 为准）对全部在批支跑「真 3way 落地」重验：①issue 末评实测 ②双层查 ③3way am 到**终态 tip**（收尾再 fetch 一次，以当时 tip 为准）——CLEAN 记录（head 不动不发帖）/CONFLICT 全链修复/同域另路修复停发。**全程显式 SHA 钉死**：共享仓 remote-tracking ref 被并行车道共写会产生「ref 漂移」假象（两车道独立复现同一解法）。r9 首战：tip 三度前进（21882a68d→9097687a3），14/14 CLEAN 零污染，另捞出 #2373 被报告者本人 PR 收编出列。

### 帖稿模板（r9 终稿形态；谢事实不夸速度，不用不实「全收」）

> 现行整批推荐帖模板与发帖前后硬门见 [draft/template/Discord清单帖模板.md](../draft/template/Discord清单帖模板.md)。下方 r9 骨架保留模板未收的内容：「用户报的 / 你自己开的几单」分组、「痛点→解决」双半句、履约句与拍板句等话术。分组中的维护者亲单 2026-10-25 起不再新接（见 [11](11-狩猎轮机制.md)）。

```
@yetone 上轮闭环一句（N 支进了 X，署名照旧，谢谢！）
这批 N 支——X 支用户报的实用 bug，Y 支是你开的单我们也接了——都已 rebase 到今天的 main，git am 即进：

用户报的：
• #N 痛点——解决（必要的一句催点/履约句/方向之争标注）

你自己开的几单我们也接了：
• #N 痛点——解决

[N] 个都已 rebase 到当前 main，git am 即进；分支、sha256、测试、消融都在各自 issue 里。
```

每行骨架=**「痛点→解决」双半句**：前半句用户撞到的事，后半句世界修好后的样子；最强催点排最前（当天有用户在 issue @维护者的单；报告者交付后追帖=离合最近信号）；公开请缨后的交付用**履约句**（「上条说的…我们接了：…」）；方向之争用拍板句（「阈值走哪条路由你拍板」）。「第 N 支已被你收编」式致谢行只用于核实过归属的真实收编。技术细节留 issue，Discord 只指路；竞品在途分支不点名（#3373 jotyy 判例）；第三方修复可推（保作者验证背书形态，#2532/#3020 先例）。

### 话术判例（历史沉淀，全数有效）

- **已闭环单不复述**：帖内某单的段落发出前对时间线——其请求若已被维护者完成（如 r3 已被 review 收编），整段删，否则对方只能回 "already landed"（#4256 判例）。
- **收编确认帖（促关单）比新催办紧迫**：维护者固定模式=合入后留 issue 等报告人确认。确认帖两层证据=①收编提交 `merge-base --is-ancestor <版本tag>` ②其附带定向测试在该版本树全绿；帖尾写「等报告者确认」（不替报告者宣布问题消失），仅维护者未点名等确认的单可直写 can be closed。
- 对账宽松 grep 的假信号：维护者提交正文里的预存红引用（「reds TestTOML…(#4109)」式运行记录）非收编——紧格式 `(#N)` 复验定性（r8 判例）；时间线交叉引用事件（mentioned/added commits）同理≠修复（r9 判例）。
- **驳回/覆盖的公开表述口径**：不公开复盘失败细节（#4106 认账句用户令删除——重做标准进 handbook 即可，不进帖）；没走完链的单不预告（做好了下条说或并进下批头部）。
