## 交付形态与署名

- **禁 PR 政策**（upstream `b91569d3`）下的形态：patch 附 issue（主形态，`<details>` 折叠 format-patch 全文 + fork 分支链接）、分析评论、机理分析、背书、指路、让位。PR 通道仅在政策前用过 2 单（#1335/#1339）。
- **署名三通道**：author 保留（`git am`）/ `Co-authored-by: ggbdpq` / 提交消息尾注 `(#N, ggbdpq)`。更新日志不署名；维护者手工代提时请其保留作者或加 Co-authored-by（在案先例）。
- **分析贡献的署名跟进（2026-10-25 定版，用户规则）**：维护者对"补丁→commit"已书面承诺署名（[#1643](https://github.com/yetone/magpie/issues/1643)：author 保留 / Co-authored-by；已推 main 历史不可改写→评论区贴 commit 清单作署名记录），但"**分析被采纳、实现重写**"的纯分析单在承诺盲区（#2318/#2373/#2377/#2380 四单 author=yetone 零署名，contributors 图只数 commit author→分析单在图面为零）。规则：①**patch 交付永远走 git am 形态**（author=ggbdpq 直进图）；②分析被采纳后（commit 落地且未引用来源），在 issue 发一条 light 溯源帖（"for the record, the root-cause analysis came from our earlier comments here"+引原分析评论+致谢实现，引用 #1643 的署名记录实践），把账落进 issue 历史；③ contributors 图口径=只数 author，Co-authored-by/尾注不进图——署名的硬通货只有 git am 的 author 保留。
- **发帖格式**：五段正文（现象/最小复现/根因/修法/验证）+ Verification 表格（**行间禁空行**，否则 GitHub 不渲染）+ 没跑什么 + 证据尾部，成稿骨架见 [PATCH 帖模板](../draft/template/PATCH帖模板.md)；AI 披露只写一次，口径以 [05 §3.2](05-缺陷狩猎经验.md#32-交付证据尾部版本-c) 为准（2026-10-20 四订：Attribution 单行以 `AI-written` 起句承载披露；帖内嵌 patch 时模型/工具名由 commit 尾注 `Generated-by: <模型> (<工具>)` 承载，帖内只有分支链接时 Attribution 起句改 `written with <model> (<tool>);`）。

## 避坑清单（接单前过一遍）

1. **开场六步**：fetch+ff → 在途 PR 新评论 → merge-tree → issue 增量 → upstream 自修 commit 扫 → **open PR 正文 `Fixes #N` 搜索**（#1320 血案），然后才准动手。
2. **发帖前六问**（#1569 被拒立）：①是否声明过的决策 ②既有测试守护什么 ③维护者近期表态 ④兄弟缺口是漏改还是有意豁免 ⑤影响面有证据不夸大 ⑥最后一刻 fetch+占坑复查。前四问存疑 → 降级疑点评论。
3. **patch 交付必须推 fork 附链接**（#1913 被重实现教训）；标题不带内部前缀；长 body 用 `--body-file`。**链接必须落在稿内**（2026-10-18 #2791 实例：分支推了、稿里忘写，审计与回读都没抓到）——生成稿时分支行是必填字段（`Branch with the commit: [<分支>](https://github.com/ggbdpq/magpie/tree/<分支>) (head `<sha>`).`），发布前 grep `github.com/ggbdpq/magpie/tree` 必须命中，回读核验同查。
4. **ping 纪律**：24h 线；引用 patch 名先回读 issue 原文（#1306 错标）；ping 前查评论数防双重触达。
5. **宣告"无解"前穷尽配置注入面**（#1458 修正）——官方文档里的配置项就是可编程注入点。
6. **红实验**：marker 的 sleep 必须小于等待方 ctx 超时（#1375）；消融摘产品文件用 `--name-status` 列全，测试与产品分开摘（hunt17 定式）；测试引用新常量时加零行为桥接测试文件（2026-10-14 #2017 复验）。
7. **中文 Markdown 禁 perl/sed 批量替换**（2026-10-11 事故），用 Edit/Write 逐处改；破坏性操作前先确认回退源。
8. **限额与并行**：1308 限额错峰派单（整点后 40-60 分钟）+ 探针先行；死亡实例的已提交工作验证后收编；触达类动作先占坑后发射。同机并行会话不并行跑全量套件（上游 LESSONS 10-16：互踩全超时）；全量验证在**最终推送的 head** 上重跑（LESSONS 10-17：四个提交正文记录的验证跑在另一棵树上）。
9. **热路径代价**（LESSONS 10-17 #2551）：在请求热路径上新加检查/兜底，交付必须回答「每个通过请求的代价」——扫描量与 body 大小成正比的检查会吃掉大回复的超时预算。
10. **正文点名的未修兄弟面要落为可追踪项**（LESSONS 10-17）：交付尾部/正文写了「Left: X」，X 就要进台账 follow-up 或在帖内明写建议维护者开 issue——「说了没修」没人跟进，nightly review 会抓（#2634→plugins#176 先例）。
11. **存量影响面**（LESSONS 10-17 #2635）：修法只盖新数据时，交付必须写明**旧数据/旧配置的用户会看到什么**、何时被补上（如「现存条目在下次 sync 时获得该字段」）；迁移式变更写明回退办法。另遵 code-standards 10-18 新规：**magpie 的默认不覆盖用户自设值**——写配置键前列出该设置的所有读取点，带着「用户自设值在场」跑测试。
12. **读上游规则的增量**（2026-10-18）：`git log --oneline -5 -- LESSONS.md docs/code-standards.md` 进开场——LESSONS 每夜复盘、三日规则晋升 standards，新晋升条目与新叙事里的翻车模式是七问第 5/6 问的对照源。
13. **存量 patch 巡检先核对目标文件还在不在**（2026-10-18 #2454 实例）：上游的退役波（如 `be62bcf7` 整删 539 行）会让「站住」的 patch 一夜之间变成 apply 不过——ping 前先 `git apply --check` + 读目标文件现状，目标已删的 patch 按 YAGNI 收窄或重落地，不硬救。
14. **发布链每步门控，POST 后以回读为准**（2026-10-20 双实例）：发布是一串会各自失败的动作——push（SSL 瞬断）、查重、POST（响应 JSON 里混控制字符会让 jq 崩）。任何一步的失败都会被 `;` 串联的后续步骤无视：**#2593 返工帖 POST 响应解析失败→误判未发→23 秒后重发，同内容两帖（6290448904/6290455519）；#2946 rebase 帖 push 瞬断未拦住发帖，帖中 head 与远端不一致约 1 分钟才被 ls-remote 抓到**。规则：①命令用 `&&` 或显式 exit 门控，禁 `;` 串联发布链；②push 后 `ls-remote` 比对 SHA 等于帖中 head 才准 POST；③POST 响应解析失败**不等于没发成功**——先 GET issue 评论列表核实（数评论、找同内容），确认未发才重发，已发就补拿 comment id 做回读，绝不直接重 POST；④响应解析不用易崩的 `echo | jq`，落文件后用 python `json.load`。
15. **可选功能不得阻塞核心路径；锁内禁同步 I/O；真资源场景才算验收**（2026-10-26 上游 #3682 网关故障事故沉淀，yetone 复盘承诺+Nathan 原则"核心线路路径必须少而明确，可选功能不得阻塞转发"，用户令晋升为项目规则**必须严格执行**）：上游 pf-serve（本地脱敏模型，默认关的可选功能）的调用在全局锁内做同步 I/O——模型加载最长 3 分钟+每次识别都在锁里→全部网关请求排队 504（v0.1.1540 看门狗把静默等待变成报错后全面显形）；pf-v2 升级冷启动放大；测试用假 pf-serve 从未跑过"冷启动+多请求并发"故零拦截，一天 20+ 发版无一拦住；/v1/models 与供应商页面两条未经本地模型的线**仍未确认覆盖**（维护者自认）。三条硬规则：①**锁内禁同步 I/O**——patch 自查新代码不得在共享锁内做网络/磁盘/子进程/模型调用；审计构造车道把"可选功能在核心路径持锁/持阻塞调用"列为标准检查面（rg 共享锁 + Lock 区间内的 I/O 调用）；②**可选功能的慢与败不得粘连核心转发**（独立超时、旁路、可降级，Nathan 原则）；③**涉及真实外部资源（模型/子进程/真网络）的功能，验收必须含真资源冷启动+并发请求场景**——假服务绿≠真资源绿（#3682 报告者实测 v0.1.1566 "只是症状减轻"仍为教训：修复验证也要真资源复测）。上游该区 48h 自修中（维护者自任"一条条收拾"），我方以分析/验证协作，不抢 patch。
16. **维护者自动化测试自留单不接**（2026-10-30 #3488 误接教训，用户令晋升）：标题形态 `gui tests: …`/`GUI test …`/`TestXxx … 负载红/偶发红` 且作者=维护者的单，**先默认是他自动化测试的自留跟踪单**——正文只有原始失败日志、后续更新是 "Seen again…" 式自动流水（树 SHA/机器/负载参数）、无 ask 无 @；他自己在该区改树自修，我方 take+patch 反成噪声。#3488 实证：take+诊断+patch+rework+两次 rebase 全部零互动，维护者仍持续自录。**判别三征（≥2 即让位，不 take 不占坑）**：①正文只有日志、没有求助或方向性语句（对比真·测试稳化单：#2984 明写要求找因非重跑、#2965 自诊给两方向、#3051 带诊断线索）；②维护者后续更新纯 Seen again 自录、对已存在的占坑/patch 零回应；③帖内出现他自己的分支名/rebase 记录（他在自己修）。**误接单号铭记（我方回复待清理，逐条 ID 见 journal/账册/自留单回复清理清单.md）**：#3488、#2686、#2547、#2965、#2988、#1375（后段）。**勿删例外（同形态但属正常协作，评论即署名证据，删除=抹账）**：#1228、#1306、#1358、#3051、#3350、#3497、#3498、#3511——均被收编且署名（作者保留/co-authored/commit 明文 credit）。10-27 后新接的测试单在维护者首个互动信号前不追加投入。
17. **REST 评论 API 升序坑，取尾必须 per_page=100**（2026-10-31 三现）：comments REST 端点按时间**升序**返回，`per_page=6` 之类小页的「尾 3 条」实为**头部**——漏掉维护者最新回合=漏 P0（hunt107 差点发生）。取尾一律 `?per_page=100` 取数组尾；或直接 GraphQL `comments(last: N)`。判定「有无新回合」永远以取到真尾为准。
18. **派车任务书的分支名与 head 基线只算线索，车道开工必须 origin 实测**（hunt106 批测实证）：10 支里 9 支 head 已过时（中途被 rebase/强推）、8 支任务书分支名是简称（404）——照任务书直接 checkout/比对会撞错对象。任务书写「基线记录 X」，车道先 `git fetch origin <分支>`+`ls-remote` 实测并以实测为准回填报告；worktree checkout 前先清本地同名分支（hunt105 车道 C 误跑他单分支教训）。
19. **review 回应先实证再表态，错了大方认**（hunt107 #3373 正面判例）：维护者的读码论证比我方更具体时，逐断言用探针/代码路径实测（四断言全实测）后再回帖；成立就大方承认+撤回不实描述（hang fix 无 diff 支持→撤回），不硬辩；实测推翻的部分才给证据。附带两条脚本卫生：①Python 多行中文串内出现半角双引号会截断字符串（SyntaxError 整脚本不执行）——脚本内中文引号一律用「」；②索引/账册批量追加必须带锚点守卫（锚点未命中即中止），hunt107 守卫两次拦下错写（#3747 归属记错 02 表）。
20. **收编对账双层查：单号 grep + 痛点关键词**（2026-10-31 #4495/#3260 两例）：维护者落我方 patch 时**主题行可以不带 `(#N)`**（两笔 author=ggbdpq 直提主题行均无单号，报告者只在提交正文点名）——只按 `git log --grep="#N"` 对账会误报「未收编」，下一轮重复推荐已收编单。对账三层：①单号 grep ②痛点关键词（sampling/portable 靠这层抓回两例）③issue 末评与状态实测。同族教训：上游自修也不引用单号（#3020 漏查判例）、am 冲突本身就是收编信号（#4553 同修双落）。
21. **测试必须校验被测对象真被处理；性能数字后带测试名**（2026-10-31 #4256 尾逗号判例，维护者亲手修我方测试）：perf 测试 fixture 的 JSON 尾逗号让解析直接失败——报告的 65ms 是解析失败耗时，mends 从未发生，测试等于没测还给出假基线（维护者 review 点破）。改法=读回结果断言内容（`arguments == {"a":"xy"}`、条目数、末条完好），不是只比字节或耗时；报告性能数字一律附精确测试名（`TestCRTidyTwentyFourMBLine` 23ms），维护者核对时可直接复跑。附带：消融判读看失败输出的语义，不只看红绿计数。
22. **环境类 patch 的「本地等价形状 RED」有天花板；Not verified 如实标注是驳回后快速重做的前提**（2026-10-31 #4502 真机驳回判例）：FakeWSL 与本地 symlink 都**跟随**链接，9P 对 WSL 内 Linux symlink **不**跟随——本地全绿≠真机绿，放行裸 EEXIST 只把错误挪到写步。维护者驳回帖（6543503078）亲手给了修法 spec（`wsl.exe readlink -f` 解析 + `/mnt/<d>/` 落盘符路径 + 「拒绝链接下全路径」测试替身）。**真机驳回=高质量反馈，正确动作=先实证再按其 spec rework（同分支 squash），见 #19**；因交付帖 Not verified 首位如实标注（无真 WSL），重做方向零歧义。
23. **长车道 POST 前最后一刻重查 upstream；停后台车道要验证死透**（2026-10-31 #4502 双教训）：①维护者驳回→自修窗口可以只有几小时（本轮 13:29「Fixed in v0.1.2403」）——车道任务书的「发布」步必须内嵌 `git fetch upstream main && git log upstream/main --grep="#N" --since=<开工时刻>` 重查，命中即停不发布；开场 fetch 一次对 46 分钟长车道不够（基线 `3ecc02b78` 错过 `73a12e8bf`，rework 帖发在维护者 Fixed 帖后 38 分钟）；②**TaskStop 的返回不构成死亡证明**——`not running (status: running)` 假象下续作实例复活跑完并发布；停车道后必须「stop → 等终止通知或查 STATE 文件 mtime 停止增长 → 确认死透」三步，关键取消动作二次核验后才继续后续流程（发取代帖/改账）。
24. **rebase/refresh 车道除「漂移零」外必须查「方向鲜度」**（2026-11-01 #4063 出局判例）：语义零漂移 ≠ 方向仍成立——上游同域新提交（`79b4be466` 真模型实测推翻主机名 stand-in 方向）可以在 patch 内容一字未动的情况下推翻其修法前提。重排车道每次 rebase 后加一步：`git log <旧base>..tip --oneline -- <patch 触及文件>` 扫主题，同域另路修复/设计转向→停发报告不硬推；发帖前读维护者该 issue 末评语气（Not applied/Not landed=方向否决≠等待 rebase）。三拒形态的系统化沉淀见 [04 §六被拒三型](04-修法方向最佳实践.md)。
25. **每个后台任务独占 worktree+独占日志；跑前核 HEAD**（2026-11-14 R-B 轮 #5197 互踩判例，用户令=永久约束）：同一车道内两个后台任务（go test/审计链/构建）**共用同一 worktree+同一日志文件**→并发互踩，worktree 停在过期 head（fa999bb339），gateway 全量日志来源不可信，该单证据链全部作废重做。硬规则四条：①**同一 worktree 任何时刻至多一个任务在跑**——并行验证一律独立 worktree（`/tmp/<车道>-<单号>-wt`，自建自清）；②**后台命令一律落盘唯一日志**（`<产物目录>/<单号>-<阶段>.log`），禁共享日志、禁无落盘管道 tail（tail 丢详情且 exit code 属尾命令，同日 L18 已犯）；③**启动前核 worktree HEAD==预期分支 head**，对不上=上一个任务没收尾，先清场再开工；④发现互踩的批次**整批作废重跑**，不作废单测补救——污染过的日志不构成证据。
