## 2. 开工先判断：问题、执行路径与贡献状态

- 读取最新 main 的 `AGENTS.md`、`LESSONS.md`、`docs/contributors.md`、`docs/code-standards.md`、`docs/subsystems/README.md`及相关设计页；记录 **实际审计 SHA**，核对 checkout HEAD 与 tracking ref 是否一致。按需读项目 Go Skills，不因 Skill 推荐加依赖或改接口。
- 先判断真实执行路径：插件还是内置、翻译还是直通、本机还是 WSL。只修未执行的内置路径，不算修好已迁移用户；声明实际仍在用的残留路径。
- 重读 issue 正文和评论、已有 patch/分支、维护者认领及当前 main；0 评论不等于无人交付。已有实现或协作者交付时先让位，不制造同题 patch。
- **价值与采纳分开记**：已合入、采纳后重写、插件部分修复、分析在案、明确暂不合、待审 patch、待发布/确认、已关闭分别记录。Open 不等于未合入，合入不等于原 patch 完整通过。
- **署名只认提交。** 在当时的 `upstream/main` 上，Author 或 `Co-authored-by` 有本账号才算署名。维护者没留言，仍可能已经在 main；维护者说合入了，也要打开那一笔，分清原样、维护者补完、还是别人的 patch。正文里的「消融」字样不代替在当前 main 上手拆产品代码后的回红。
- 上游曾把本账号列入 Watched：重点核对测试失敏、漏兄弟路径、失败读取被当空；同条也记录后续改善。它不是封禁，也不是可以忽略的历史背书。交出去之前这三项都要有记录：手拆后新测试回红、没改到的兄弟路径、读失败变成什么。
- 不设 author issue 数量、日产量或“池枯必须挖出新单”的目标。只推进可解释、可复现、收益具体且审查成本相称的改进；零新帖是正常结果。

## 3. Issue 与 patch 的最小交付内容

**对外内容一律英文**（规则见文首 2026-10-17 语言规则；本地记录仍用中文）。标题使用 `subsystem: observable symptom`（英文），不把尚待证明的上游行为写成已发生事实。正文按以下内容组织，不用篇幅代替证据：

1. **来源、环境与收益**：区分本人真实使用、他人报告、代码审计构造；写客户端/版本、供应商类型、main SHA、插件/内置状态。说明谁做什么操作会受影响。引用同族报告不等于本单现场；请求次数不等于计费次数，测试加速时间不等于生产等待。
2. **最小复现**：合法输入、预期契约、实际输出、命令与断言级失败。假服务的形状与拒绝依据须来自真实样本、官方协议或已核实实现；只有类比时明确标注，不由自己规定 fake 的400来证明真实上游必然400。
3. **根因与修法**：沿公开入口追到共享根因，说明前后用户行为、状态与兼容边界。使用函数名和当前 `file:line`，不因兄弟路径不一致就擅自推翻产品取舍。
4. **验证**：对应 §5 写精确 base/head、测试名、命令、输入、输出和退出状态；把历史作者声明、第三方复验、本轮实测分开。绿色、失败、跳过和未运行分别列出。
5. **未验证与待决策**：真实账号、真实客户端、平台、GUI、性能/费用等未证项逐一说明；未完成验收的材料标为本地待发布稿，不催合入。行为有变时同步 owning subsystem 的对应契约。

交付附实际验证的 patch、base/head 与 hash。`git apply --check`只证明文本可套用，不证明编译或行为正确。正式交付优先真实提交导出的 `git format-patch`；尚未获提交授权时保存有效 unified diff，明确没有对应新提交，禁止沿用旧 SHA 冒充新产物。AI 披露写实际工具/模型；模型信息未暴露则如实说明，不猜模型、不套旧尾注。正文充分解释仍不代替提交者自己理解根因与取舍。

### 3.1 发帖前七问（任一不过就不发）

不为做而做；零新帖是正常结果。

1. **来源**：问题来自真实使用、他人报告还是代码审计构造？构造的必须写明，并附确定性复现与影响面。
2. **真实失败**：能拿到真实失败记录吗？只能靠构造复现、又要改变行为的，先开 issue 以提问方式讨论，不直接发 patch。
3. **举证**：在最新 main 上运行新测试，确认断言级失败（RED）。`git apply --check` 和“正文写过”都不算问题仍在的证据。
4. **收益**：谁、做什么操作会受影响，能否说清？说不清收益的不发。
5. **边界**：是否触及维护者已裁决事项、守护区或近 48h 维护者连续自修的区域？是则不做。
6. **兄弟路径与失败读取**：同族调用方是否已 `rg` 全查并记录改/不改理由？读失败会变成什么？
7. **本人能讲清**：不看 AI 的说明，本人能否用三句话讲清改了什么、为什么改、怎么验证？讲不清就不发。每条公开交付发布前由本人读完 diff。

### 3.2 交付证据尾部（版本 C）

正式交付（patch 帖、issue 正文）尾部用下面的英文模板（不译成中文），逐项对应上游 [Watched](https://github.com/yetone/magpie/blob/main/docs/contributors.md#watched) 的三项检查。只写可核验的证据，不写“已通过自检”“符合契约”之类自我评价，不加 ✅ 徽章或规则链接；没有的项如实写“未做/不适用”，不硬填。普通确认、提醒类评论不加尾部。

````markdown
---
**Source**: found by code audit (AI-assisted), not from a real failure I hit. <!-- 或：reported in #1234 / hit in my own use on macOS -->

**Red without the fix** (base `abc1234`): with `internal/x/y.go` reverted and the new test kept,
`go test ./internal/x -run TestFoo` fails:
```
--- FAIL: TestFoo: got "...", want "..."
```
With the fix: `ok`.

**Siblings**: `rg -n "decideFoo\(" internal/` → 5 sites. Changed: a.go, b.go. Left: c.go (passthrough, never sees escaped text).

**When the read fails**: an unreadable `foo.json` now counts as unknown, not as empty (TestFooUnreadable).

**Not verified**: real account, Windows GUI.

**Attribution**: AI-written; I've read the whole diff and the tests pass. Please keep the author (`ggbdpq`) or add `Co-authored-by: ggbdpq <ggbdpq@gmail.com>`.

**Patch**: <details><summary>patch: <commit subject> (#<N>) — git am applies it as is; SHA-256 first 16: <hash 前 16 位></summary>

（fenced format-patch 全文）

</details>
````

- 测试修前就绿的，Red 一项写明“protective only, green before the fix”。
- 最后一句只有本人确实读完 diff、能自己答辩时才写。
- **Attribution 行与「Attribution→Patch 块」次序是 patch 帖必填尾项**（2026-10-18 #2791 实例补入 Attribution；2026-10-20 用户定版 #3039 形态并四订合并单行：Attribution 起句 `AI-written` 承载 AI 披露，不再单设 AI 行；patch 块摘要行写 `git am applies it as is; SHA-256 first 16: <前 16 位>`——发布前 `shasum -a 256 <patch 文件>` 取前 16 位写入，证明帖内贴的与实测通过的是同一份文件。发布前 grep `Co-authored-by: ggbdpq`、`SHA-256 first 16` 与 `AI-written` 三查，回读同查）。
- **AI 披露帖内可见一次（2026-10-17 二次修订，[澄清记录](03-AI披露口径决策.md)；2026-10-20 四订，Attribution 单行）**：模型/工具名在帖内出现且只出现一次。**帖内嵌 patch** 时由 commit 尾注 `Generated-by: <model> (<tool>)` 承载（随代码进历史），尾部不再单设 AI 行，Attribution 行以 `AI-written` 起句承载披露；**帖内不嵌 patch（只有分支链接）**时 commit 尾注对读者不可见，Attribution 行起句改 `written with <model> (<tool>);`。判据是「帖内披露是否可见」，不是「有无 commit」（首版按后者分，分支链接形态的帖整帖无披露，已纠正）。不清楚模型就如实说明，不套旧尾注。

## 4. 找缺陷：有效的套路

以下是取证入口，不是产量排序或发帖配额：

1. **兄弟路径不一致**。同一个概念有两套判定，一处更新了，另一处没更新。
   - C1：`claudeVersion` 只认 opus/sonnet/haiku，`claudeLine` 已经加上了 fable/mythos。
   - C6：模型配置按 `keyAt` 带了 LAN key，MCP 中转的 `through()` 没带。
   - C4：`vendorDot` 的正则和 catalog 里的 `bedrockGeos` 不一致。
   - 做法：`rg` 出一个判定函数的所有调用方和同义实现，逐个对比集合。
2. **规则作用域过宽**。某条规则的理由只适用于一个子集，却作用在了全集上。C2 中，「4.6 没有 xhigh」被套到了所有 adaptive-only 模型上。
3. **厂商默认值变了**。拿官方文档逐字段核对：哪些模型 display 默认是 omitted，哪些参数会被拒、哪些支持 effort。
4. **规范里本没有顺序的列表被当成偏好**。C7 中，RFC 8414 的 `*_supported` 列表本来没有偏好顺序，代码却取了首项。
5. **测试读到了宿主环境**。C3 中测试读了 NO_PROXY、NODE_USE_ENV_PROXY，在开发机上会无故变红。
6. **审最近的 feature commit（提交审计车道，40-60 个）**。读 `git log --oneline -40 upstream/main`（量大可到 -60），挑新加的逻辑，查边界和兄弟场景。commit message 里的「Not changed, found on the way」常常就是线索。**10-14/15 曾发现多个有效问题**（L4 审 22 提交挖出 #2167、X1 审 43 提交挖出 #2251），两个实践：①已审清单显式传给下一路，勿重复挖；②维护者高密度自修区（gateway 两日 152 commits 全带 break-check）零帖是正确产出，静态横查扫尽后就该换执行面实测或换车道。
7. **新报告兄弟面核对**。昨夜新进的 issue 报告是精确线索源：读全文，挖**同函数/同家族没被报的面**。#2250（#2233 的兄弟函数只修了 codexFilesIn）、#2255（#2246 同递归只消费外层）、#2256（#2242 Origin:null 门的同族 `*.localhost` 豁免）全是这么来的。挖到的面要过六问（本体可能是声明过的豁免），不硬凑。
8. **执行面实测**。构造截断 SSE、错误体或工具重放时，先核对真实消费者与请求状态。#2221 是反例：有状态重放的400不能类推到无状态relay；维护者实测200后要求真实失败，缺新证据即暂停。#2222 则有真实孤立call失败依据。构造成功仅证明机制可达，不自动证明现场发生或修复有收益。
9. **在途清单显式传路（2026-10-16）**。派单前汇总同账号近 12h 的 claim/交付评论与已推分支，作为「我方在途清单」写进每路任务书——公司机与本机同账号跑并行车道、同轮双车道也共用账号，无法凭身份区分归属。**线索（消费面/兄弟面指向）与该单的接单权绑定同一路**。hunt31 B/C 同轮撞单 #2492 样本：B 完成等效修复后发现 C 已认领交付，不重复交付、公开自评以先发为准 + 点名对方补丁缺口 + 自家分支留作备份——撞车零成本处置。

10. **选题按命中族排（2026-10-21 复盘，数据见 journal/账册/采纳统计与快照 与索引分表）**。台账 165 单里 patch 被直接拒的只有个位数、且多是「报告被真实上游证伪」而非「patch 质量被拒」——命中率主要由选题决定。证据排序的擅长族，猎手按此优先：
    - **gateway 流式/翻译/失败分类边界**（33 合入，最大仓）：一个确定输入字节序列 → 一个确定的错误分类或路由行为，httptest 全可复现。SSE 半行、截断、空回复、失败原因措辞入分类表、rest 键的作用域（restKey vs restID）。#2446/#2533/#2599/#2972/#2873/#3039。
    - **状态语义与绑定**（compaction 写者、affinity、rest 作用域）：全局状态 map 的键选择与生命周期。#2642（两轮）、#2271/#2727/#2955。low cohesion 的裁剪规则每加一条就多一个洞（#2642 全家）。
    - **provider 账号/额度/凭据语义**（17 合入）：401 刷新、额度窗口、rest 作用域、脱敏、settings 并发写。#2813/#2946/#2973。
    - **测试稳化（维护者亲单，命中率最高，但有两面）**（校注：2026-10-25 起维护者亲单不接，见 [11 选单正典](11-狩猎轮机制.md)；本条保留为历史证据）：固定睡眠→状态等待、时钟冻结、负载窗放宽。#2965/#2988/#3051 全数交付，维护者自己被 CI 噪声困扰，标题常自带诊断。**边界（2026-10-30 #3488 教训，细则晋升 handbook/10 条目 16）**：同形态的「纯日志自留单」（正文只有失败日志、后续 Seen again 自动流水、无 ask 零互动）是他自动化测试的自留跟踪单，不 take 不交 patch——#3488/#2686/#2547/#2965/#2988/#1375 后段误接在案（回复清理清单在 journal/账册/）；勿删例外（#1228/#1306/#1358/#3051/#3350/#3497/#3498/#3511，评论即署名证据）。
    - **审计构造 + 根因实验**：代码审读找出确定性缺陷后，用本地构造环境端到端钉死（#2814/#2946/#2954 的 Bun refs 实验）。
    - **Windows/词法/路径**（历史强项）：#2256/#2259/#2685。
    - **避开的**：报告者自己未复现、无日志无错误体的（#2951/#2952/#2882 七问 Q2 必挂）；真实账号/专属环境依赖的（TUN 真机、Cowork、商汤登录——只能构造性验证）；GUI 视觉交互（维护者自留、本机难自测）；功能请求/设计拍板类；大架构改动（#2945 熔断、#2894 前缀缓存——超出 patch 尺度）。

11. **现场命中验证（2026-11-06 批 1 #4169 判例）**：报告者或第三方提供了现场实测数据（计数/日志/对照表）时，patch 前先把修法路径在他们数据里**走一遍**——触发条件在现场是否成立。#4169 的 backoff 在报告者机器上永不触发（scutil 成功返回空代理），patch 慢化了一个他不有的场景、他有的原样——本地全绿零价值。配套：issue 后续评论的实测数据是裁决输入（MisonL 59 vs 58），接单后重读一遍评论再定修法方向。

历史当轮审过但无发现的区域：`internal/edit`、价格分档 `catalog.Price`、Gemini thinkingLevel 映射、DNS rebinding 的 `ownHost`、DeepSeek reasoning_content、Codex 标题 incomplete、循环检测后的重问。这只是当轮记录，不是永久排除清单；新提交或真实报告触及这些区域时重新核验。

## 5. 验证：公开行为、回红与完整路径

### 5.1 一条公开边界一次闭环

- 新写测试前，列出用户/调用者可观察的公开边界并请用户确认；不为本轮未确认的私有 helper 扩测试。沿用既有测试时注明边界，接口形态待定先解决设计问题。
- 一条测试 → 在明确 base 上断言级 **RED** → 最小实现 → **GREEN**；再做下一条。编译错误、跳过、网络失败不是行为 RED。测试辅助符号的零行为桥接只能帮助编译，不能替代公开调用路径的失败证据。
- 期望值来自协议、已核实客户端实现或独立算例；不复制产品算法或用自己写的正则假扮真实客户端。HTTP/SSE改变要看客户端实际读取什么；UI改变要断言可见行/页头/正确高亮，不只查“某个名字还在字符串里”。
- 复用当前 `httptest`/`testenv` 和公开 Handler；不触真实配置、不访问真实账号的自动化测试。需要跨请求状态时共用同一 Handler。假上游按实际协议回 SSE 或错误形状，不照单全收。

### 5.2 每个保证都要被有意打破

- 保存修复副本，**显式**记录 baseline SHA、产品文件集合和测试文件集合。在隔离副本恢复全部相关产品文件到 baseline、保留测试，再确认同一行为回红；随后恢复修复并复绿。不在共享工作树 `stash`、`reset`、`checkout`，不拿猜测的 `HEAD~1` 当基线。
- 对关键守护分别做 mutation：备份失败是否阻止覆盖/删除，读取失败是否仍成为“未知”，同账号/同协议/相邻出口是否漏修。一次综合失败不能证明每个守护敏感。
- 数据保护的写入、删除各用独立初始状态，核对副本内容；先前创建的 `.bad-*` 不能满足后来删除路径的备份断言。修改/重用断言时说明为何没有掩盖原失败。
- `rg` 全部调用方与同义判定，记录哪些改变、哪些保持：翻译/直通、协议编码器、失败出口、其他 agent/provider、插件/内置、平台和重新读取点。只列相关兄弟面，不为补表扩大功能。
- 测试中的加速退避、固定假响应、合成200条记录等只能说明构造条件下结果；生产次数、费用、发生率与真实客户端效果另行测量。

### 5.3 隔离与质量门

- 工具链服从当前 `go.mod`，使用 `GOTOOLCHAIN=auto`及已有版本；切换 HOME 前固定 `GOPATH`、`GOMODCACHE`、`GOCACHE`。先确认包的 `TestMain/testenv` 是否已隔离，不笼统要求所有测试再换 HOME，也不笼统免除真实配置隔离。真实二进制验证必须用独立配置根。
- 按当前上游 `docs/code-standards.md` 的 Acceptance criteria 执行格式、完整测试、vet、三平台构建和适用GUI验证；涉及并发补相称 `-race`，不靠仅定向绿冒充全仓绿。GUI Go接口测试不是Chromium/WebKit浏览器验证，FakeWSL不是发行版实机验证。
- 现有 main 同样失败只能帮助定位，**不是忽略通行证**。记失败测试、输出、真实根因或对应上游issue；原因不明、套件超时或必要门禁未跑，结论仍为未完成验证。单跑转绿不消除合跑/并发失败。
- 文档/措辞修订使用相称的链接、结构、事实与diff检查，不新增只断言实现字符串的测试。每次只因新改动、新失败或未解疑点扩大验证。

### 5.4 记录本轮，不借历史绿

每条验证保留执行目录、base/head或产物hash、环境、原命令、输入/fixture、逐字输出和exit；分别写 BASELINE、MODIFIED、ABLATION、RESTORED。报告区分本轮实测、历史声明与未跑项。保护性测试若修前也绿，明确它防回归，不能记成RED证据。完成后检查本次设计是否有可删除复杂度，有候选才消融，仍满足验收则删掉；不另起无关重构。

## 6. Git 与 GitHub 操作

> 校注（2026-11-07）：本节「只有当轮明确要求提交时才执行」「推送仅在明确授权后执行」「当轮允许发布」「仅执行本轮明确授权的GitHub操作」等句，2026-10-24 起以 [fork/AGENTS.md](../../../../AGENTS.md) §3「发布权按形态分」定版为准（子智能体自检→推 fork→发帖→GET 回读，主线程事后复核）；本句保留为无自动化授权会话的默认。

- **固定 pr 目录复用**：Windows 第 N 路独占 hub 内的 `magpie-prN` 独立 clone，先核对状态和注册关系、在该 clone 单独 fetch，再 `switch -c` 创建未占用的分支。新建/收口按 [Windows 规范](08-Windows工作区与沙盒规范.md)，不使用 `checkout -B` 覆盖旧分支、不清理未跟踪文件、不在 E 盘根目录新建代码工作树。不要在主 clone 上直接改，那里可能有别的会话的分支。
- 提交：作者用已配置的 ggbdpq，不改 identity。只有当轮明确要求提交时才执行。message 用 `git commit -F <file>`，正文分 What changed 和 Run，写实际执行结果；署名与AI披露遵实际参与者，不挂与当前工具不符的固定bot尾注。
- gh认证/代理/推送通道逐轮核实；历史401或22端口失败不证明当前原因。不改凭证或用户配置，推送仅在明确授权后执行并核对目标fork。
- **查重三步**：`gh issue list --state all --search "<关键词>"`，然后用 `gh pr list --search "<号>"` 查 open PR 的正文引用，最后在**发帖前一刻**重新 `git fetch upstream`。维护者可能在 1 小时内自己修掉。
- 巡检时看 issue 评论的时间戳，不能只看 fetch 增量：GitHub 上可见的 push 时间会晚于 commit date。
- `git rev-parse HEAD upstream/main`可同时显示两个ref，逐个记录其对应含义；不能由tracking最新推导checkout也最新。worktree清理须确认注册关系、无已有修改及删除授权，不用`--force`绕过保护。

- 发布前检查语言：标题、正文、评论与 commit message 均为英文（逐字引用的中文原文除外）；有中文段落就先改写再发。
- 对外更新先重读最新正文与评论，确认内容有新信息且当轮允许发布；缺授权只留本地待发布稿。已确认、已解决、等待真实样本的单不机械按72小时催促；已有合入不重复交产品patch。
- 发布采用 `--input` JSON 或 `-F body=@file`，不用会发送字面量的 `-f body=@file`；发后GET回读body与长度、围栏和patch hash。署名请求在实际交付中说明一次，不附到每条确认/提醒里。仅执行本轮明确授权的GitHub操作，不顺带新建、关闭或定时ping。

## 8. 可复用派单提示词

每路只领独立问题与独立复制品，明确输入、输出和完成判据；共享源码、台账与最终状态由主线程处理。没有有效候选就收口，不为填车道制造任务。**隔离硬规则（2026-11-14 用户令）：每个后台任务独占 worktree（/tmp/<车道>-<单号>-wt）与唯一日志文件（<产物目录>/<单号>-<阶段>.log）；启动前核 worktree HEAD==预期分支 head；发现共用/互踩整批作废重跑。**

```text
任务：完善已有 #ISSUE，不增加新选题。
基线：本轮从上游核验的 MAIN_SHA；记录 checkout HEAD，禁止把旧工作树当最新。
先读：当前main的AGENTS、LESSONS、contributors、code-standards与owning subsystem；按需Go Skills。
先判断：问题来源/真实执行路径/已有交付/维护者裁决；不能支持收益的行为变更先暂停。
测试：写下并请用户确认公开接缝；一测试一修，RED→最小改动→GREEN；各关键守护mutation，恢复后再GREEN。
覆盖：搜索同族调用方、协议、失败出口和读写状态；保留未改语义，拒绝顺带抽象/升级依赖。
交付：patch及hash、base/head、英文issue待发布稿（本地分析与汇报用中文）、精确命令与输出/exit、未跑项；历史绿与本轮实测分开。
权限：仅本地修改，不提交/推送/发帖/关单/定时ping；这些动作需要本轮分别授权。
收口：主线程复核真实证据；必要门禁未过就写未完成验证，不把待发布稿称Ready。
```

> 校注（2026-11-07）：上方「权限」行，2026-10-24 起以 [fork/AGENTS.md](../../../../AGENTS.md) §3「发布权按形态分」定版为准（子智能体自发布、主线程事后复核）；本句保留为无自动化授权会话的默认。
