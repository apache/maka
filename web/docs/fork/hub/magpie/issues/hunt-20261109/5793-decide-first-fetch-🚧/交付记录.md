## 根因与修法

- 根因：plugin 的 config hook 声明 `decide:true` 后、models hook 首答前，`pluginProviderServing` 从空 models 推导不出会话端点 → `DecideOnly()` 误真 → `fetchList`（models.go:469）把 fetch 送进 `fetchDecide` 插件分支（decide.go:898）→ 空决策模型集 → `"X's plugin lists no decision models"`，阻塞了本应先问的 `Account.fetch`（正是它向 host 发 providers RPC 把列表填进来）；`Test`（test.go:48）同形早退 `testDecide`，尾部 decide 探针在列表落地后继续对不标记决策模型的插件报同一句。
- 修法（按报告者建议两点 + 尾部行）：`fetchList` 先问 `Account.fetch` 再落 `DecideOnly` 兜底（有自有 lister 的 provider 从未在旁路端点上服务会话，swap 不动任何既有调用方的答案）；`Test` 对读取为 decision-only 的插件不再早退，fetch 后从 `Find` 并合**端点三字段**（首版整体替换曾回红 `TestProviderTestAsksAnAccountThatServesItsModel`——丢调用方的 AccountModels，已改为只并合 Chat/Responses/Anthropic 并由该测试锁定）；尾部对「列表无决策模型」的插件不再发 decide 行。
- 失败读取语义：`Account.fetch` 失败 → 如实返回插件列表错误（`X couldn't list its models: …`），不再伪装成决策模型错误；插件列表为空 → 返回空（诚实）；插件无标记决策模型 → Test 无 decide 行（无内容可问），有标记则照旧走 `AskSystemOne`。
