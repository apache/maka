## 核实结论

定位属实，我把机制走到了行为层：`heatSplit` 的 kept 路径里 `recentDays`（internal/usage/heatmap.go:345-348）每轮都对 recent 窗口整体跑一次 `pairRowsIn`，且被 gateway 命中的本地 chunk 整包重新解包。本单判为**设计成分**而非机械补丁：「复用未变化 chunk 的配对」的失效语义跨 chunk（fold 折叠、matched/skip、actor/compaction 都不是单 chunk 局部量）。先交机制图与方案取舍，代码未动。核对基线 db7c57670。

## 已核实的机制图

热力图现有三层缓存，各管一段：

1. **整页** `idx.heats`（request_page.go:928）：`heatFresh = 30s`（:744），但版本是 **gateway log snapshot 的 version**——只有 agent 会话文件变化时 30s 内直接回；一条调用穿过 magpie（gateway log 追加）立即击穿。
2. **cut（今天-2 天）之前的日统计** `heatOld`（heatmap.go:357-371）：settled serials 相同且 `heatOldFresh = 10min` 内复用，另有 heatDisk 落盘 + heatAdvance + heatCold 三级兜底。年份的 bulk 不重配——profile 里热点只剩 recent，与此一致。
3. **recent 窗口** `recentDays`：**每次 build 全量重配**。

所以 30s 采样的形态是：agent 经 gateway 活跃 → 每条调用击穿 heats → kept 路径 → recent 全量重配。

本地探针（合成 1k 级历史：6 个 recent + 10 个 settled codex 文件；用仓库现成的测试钩子 `heatPairing`/`pairing`/`pairsOpening`）：

```text
每轮只追加 1 条 gateway 行，连续 3 轮：
  heatSplit paired 9 chunks    ← recent 窗口全部（6 个 codex chunk + gateway 块）
  pairRowsIn = 1 次
  pairsOpening = 6             ← 6 个本地 chunk 全部重新解包，虽然它们没变
gateway 不变、只新增一个 codex 文件：
  pairRowsIn = 0               ← idx.heats 在 heatFresh 内直接回
```

（第二段也说明 pairsOpening=6 在真实家里有代表性：被解包的正是与 gateway id 相交的本地 chunk，而经 magpie 的调用都有 id 相交。）每轮重做的功与 profile 对上：`cloneCodexChunks`（request_page.go:2357）→ `foldCodexRows`（:2358，全部 recent 本地行的 fold 哈希）→ `codexChunkResponsePairs`（codex_identity.go:221，gateway picks + 被命中本地整包解包 :288）→ `matchedBlocks`（:2369）——即 profile 里的 `rowChunk.row`/`runtime.mapassign`/`chunkRows.of`。

## 为什么 pairRowsMemo 不能直接搬到 recentDays

`pairRowsMemo`（request_pairs.go:59）键是 (since, until, serials)。窗口两端稳定（cut 是午夜值、heatmap 的 `Until` 是零值），但 serials 是 `sourceSerial(root, meta, path, size, mtimeNano)`（request_page.go:1312）——活跃工作下 gateway 日志每轮追加、serials 每轮变，memo 必 miss；而 serials 全同的场合 `idx.pages`/`idx.heats` 已经接住（探针第三段）。「整体 memo」在两种情形都无事可做，**真正缺的是每 gateway chunk 粒度的复用**。

## 每 chunk 粒度复用要过的设计关

1. **fold 跨 chunk**：`duplicateSkip = foldCodexRows(chunks)` 是全体本地行的两两折叠；一个本地 chunk 变了，它与别人的折叠关系变、未变 chunk 之间的不变——增量折叠得按 chunk 对缓存，不能按单 chunk。
2. **refSet/rowRef 的身份是 (clone 指针, index)**：每轮 clone 出新指针，缓存的对要按 (serial, index) 存、apply 时重基。
3. **actor/compaction 挂在 gateway 行**（:2370-2373 `setCodexActor`/compactions），可随该 gateway chunk 的对一起缓存。
4. **失效红线**（建议 #4，同意）：跳过配对不得改变 tokens/cost——matched/skip 决定行是否计入、fold 决定重复副本归属。这正是我判它非机械补丁的原因。
5. **收益形状（推断，未实测）**：每轮只重配「变化的 gateway chunk × 与其 id 相交的本地 chunk」，活跃场景通常 1-2 个；profile 里 1.67 CPU-s 的大头（本地解包 + mapassign）应大部分消失。
