## 核实结论

定位属实：**跨查询没有任何目录快照**——`readRequestState`（internal/usage/request_page.go:811）每次 `QueryPage` 都跑一遍 `sessions.CallSourcesAndCodexIdentities`（:812），无 hold 时 `codexFiles`（internal/sessions/sessions.go:836）每次全量走目录。但「跨查询快照复用」的每种形态都在选 staleness 窗口，而现有 `warmListing` 只在 quiet（warm-up，quiet.go:52 的 `warming>0 && asking==0`）生效（sessions.go:840-851）正是维护者已经画过的线。本单判**设计成分**，交机制图 + 量化 + 方案表，代码未动。核对基线 db7c57670。

## 比 profile 多看见的三层

1. **枚举先于缓存**：`queryPageOf` 先 `readRequestState`（:916）再查 `idx.pages`（:924）——**连缓存能命中的查询都先付一次全量枚举**，因为枚举就是失效检查本身（key 含每个 source 的 `path:size:mtimeNano`，:843-845）。
2. **一次刷新两次枚举**：Requests 与 heatmap 是两个独立 handler（internal/gui/usage.go:179,187），各自 `QueryPage` 各自走一遍；`ShareListing` 只有 GUI 的 Sessions 读在用（internal/gui/sessions.go:227,268,660），usage 侧无 hold。
3. **枚举不是 Usage 专属**：Sessions 页 15s 轮询的 allFiles 同样走 `codexFiles`（sessions.go:699）——0.29 CPU-s/30s 是全体读者摊到的总量。

已有的复用都在名字与结构层：`dirent.listings.last`（名字串，internal/dirent/stats.go:74）、`rolloutsSeen`（file 结构的 path/key，sessions.go:972）、`listingBufs`（缓冲，calls.go:1296）——**syscall 每次都跑**（getattrlistbulk 一目录一次，stats.go:47）。

## 量化（本地实测，Apple Silicon，合成 1200 rollouts / 400 天目录）

```text
CallSourcesAndCodexIdentities 首次（冷）1.06s；此后每次 6.7–10.3ms（≈18µs/天目录）
无变化下 heatmap+requests 一轮（两次枚举 + 构建）≈15ms
```

按报告者的上万 rollout（≈3000 天目录，每次枚举约 3 倍于我的合成数）× 读者次数（Sessions 15s 轮询 ×2 + Usage 自动刷新每次 ×2），30s 内 6–14 次枚举 ≈ 0.2–0.7 CPU-s，与报告的 0.29 同量级（外推，未在同一负载复核）。绝对量小，但结构性成本 = 读者数 × 目录数 × 每次都跑。

## 方案表（每格回答「缓存失效时谁买单」）

| 方案 | 收益 | 谁买单 |
| --- | --- | --- |
| a. `warmListing` 式 TTL 快照推广到活跃读 | 每读者枚举在 TTL 内 → 0 | 新文件与追加的可见性延迟 ≤TTL；request key 冻结 → Usage 页 TTL 内不更新。quiet-only 的现状说明这个窗口维护者没有接受过 |
| b. 按目录 mtime 剪枝（只重走变化的目录） | 天目录数 → 变化目录数 | **保正确约束下是死路**：目录 mtime 只反映直接子项增删/改名，活跃 rollout 追加不改目录 mtime、压缩重写老 rollout 也不改——剪枝后冻结的恰是变化最频繁的文件（建议 #2 的担忧成立） |
| c. FS 事件监听（建议 #3） | 变化驱动，无轮询 | 仓库无先例（`log_change_darwin.go` 只是 ctime 读取）；三平台三套 API、丢事件兜底重扫描、合并窗口，全是新面 |
| d. 刷新内合并（小步） | 两次枚举 → 一次 | requests+heatmap 共享一次 requestState（singleflight/极短 TTL）：两个查询拿到同一快照，而今天各自看到自己发起那一刻的状态——race 窗口内几 ms 的可见性差，需维护者拍板 |

另有一个**答案不变的机械候选**可一并评估：把 `idx.heats` 检查（:928）提到 `readRequestState` 之前——heats 命中只看 gateway snapshot version 与 root/meta，都不依赖 codex 枚举，命中路径今天枚举的结果是整段丢弃的。提前后行为相同、每次刷新省一次枚举；但 adopt 的 root/meta 重置语义必须随检查一起前移（价格/供应商变化经 meta 影响热力图重建，:1359-1370），否则会在 heatFresh 内回过期价格的热力图。它不改变 profile 的活跃路径（gateway 变了 heats 必 miss、枚举照付），只省空闲刷新的那一半。
