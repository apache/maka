Both facts hold, and they sit at two different design boundaries — one is Claude Code's own approval semantics, the other is what `info/exclude` can promise — so neither has a patch here that wouldn't be a design call first. What follows is the terrain laid out for that call, with one correction in your favor: writing the non-router entry into local scope is structurally *possible*, unlike the hub case in #6004.

**The approval is documented design, on both ends.** Magpie's docs say "Claude Code, Qoder and CodeBuddy ask the user to approve a project's server before using it" (library.md's Projects row), and Claude Code asks because of what a project file *is*: `.mcp.json` ships with a repository, so anyone who can push to it can add a server — the approval is Claude Code's guard against a third party's configuration running on your machine. `~/.claude.json`'s local scope is exempt because it is the user's own file, not one a repository brought in. So routing-off writing to local scope (your proposal 1) isn't a missing feature so much as a deliberate step across that line: magpie would be placing a library server into the trust-exempt scope to spare an approval. It is *structurally* cleaner than it might look, though — entries are keyed by server name, not one shared key, so two projects adding different servers coexist in one record, and two projects adding the same library server write the same URL and collide harmlessly. Nothing of the #6004 one-key fight. What it costs: a second write surface for `claudeLocal` (adds, not just the offs and hubs it holds now), cleanup symmetry when a project is removed or a server unticked, and the approval gone for every reader of the record — repository-wide, per `claudeRoot`. A middle shape that changes nothing: the card says "Claude Code will ask to approve fs in this project" before the entry is written, which is text, not a patch, and is yours to weigh against the option you proposed.

**`info/exclude` cannot cover tracked files, so "nothing of magpie's goes into the project's git" is conditional on the file being untracked.** That is git's own rule, not a gap in the writing: exclude (and .gitignore) only apply to untracked paths. The docs state the mechanism ("what it placed is listed in the repository's own `info/exclude`"), not the boundary. On the consequences: a tracked `.mcp.json`/`.codex/config.toml` magpie edits shows up in `git status` from then until the project is removed (removal takes its own names back out — `Placed`/`Wrote` are what magpie takes away — so it is a window, not a permanent edit, unless the user commits inside it); and `git worktree remove` refuses a worktree carrying those edits, which is git protecting the same bytes. The detection you propose is cheap and safe: `git ls-files --error-unmatch <rel>` per target file (or one `git ls-files -- <paths>`) at sync time, and it even covers the worktree case, since a tracked file is tracked in every worktree. What to do on a hit is the design call: refuse with the reason, write and surface a problem on the card (the `Problem` channel `syncProject` already carries), or an explicit per-project choice. I'd note only that refusing silently breaks the project's set-up for that agent, so a loud-but-continuing default fits the way the library treats its other "yours to settle" conflicts (agent_skills' `Own: true` problems).

**One more boundary worth naming while this is open**: a tracked `.codex/config.toml` is also the file Codex's project *offs* go through (`[mcp_servers.X] enabled = false`), and, with the router on, Codex's hub entry lives there too — so the tracked-file question is not only about Claude Code's `.mcp.json` and not only about adds.
