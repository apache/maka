## Siblings

- The fork on the request path is `scutil` alone: `readSystem` is wired once (`readSystem = system`) and called once (`refreshSystem`); on macOS `system` is `readTool(parseScutil, "scutil", "--proxy")`, Windows reads the registry, elsewhere there is no fork. No other `exec.Command` sits under `For`/`Dispatch`.
- `System`'s callers are three, all in the package: `For` (per-request proxy pick), `EnvWith` (a CLI's `*_PROXY`), `Describe` (the settings page) — they consume the value, not the pace; what changes for them is only how stale a no-proxy answer can be, bounded by `failKeep` and undone by the first read that finds a proxy.
- The `sysCache` tests that don't reset state pin `at` in the far future and short-circuit before `quiet` is read; the fixtures that do reset now zero `quiet` (boot, stuckread, the new backoff ones).
- Relation to the dead-loopback patch for #6012 ([comment 6780498308](https://github.com/yetone/magpie/issues/6012#issuecomment-6780498308), `34acc14db`): that one changes what a dead loopback answer *is* (a `deadLocal` probe folds it to none, at the read and at the cache hit); this one changes how often an answerless read *happens*. Disjoint faces — applying both takes one doc-comment line of merge and the full package passes with both. With both applied, a proxy app that died with its setting left behind reads as none, and that empty read climbs the same ladder — the same fork-rate face this bug is about; the app coming back is taken at the next due read.

## When the read fails

- A failed read keeps what was read before and holds nobody (#3421): a request waits only until `readWait` after the read began, then takes the previous answer; `failed` is still recorded.
- A read that can't run at all (no `scutil` on the PATH) is a failed read: same shape.
- A read that answers with no proxy is a successful empty read: a fresh, truthful `Proxy{}`, put on the ladder.
- Nothing reads `quiet` before a read ends: the cache starts at `quiet = 0`, so boot paces at `noneKeep` until reads say otherwise.

## Not verified

- The reported machine itself — @MisonL kindly offered to test a revision on it; the probe she used counts `readSystem` calls the same way the new test does, and only the pace changes.
- The atfork abort itself — needs another thread holding a malloc zone lock mid-fork; not injectable in a unit test (as before).
- A live WPAD/PAC setup — the PAC-only shape is taken from @MisonL's transcript (exit 0, `Enable` keys 0), not re-run against a real `wpad.dat`.
