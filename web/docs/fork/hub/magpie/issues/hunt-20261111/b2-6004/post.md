Your reading holds on all three points — I verified each against `87b3af765` (identical here at `87dfc0d0b`; nothing since touches this domain) — and the shape that emerges is narrower than either of the two fixes you propose: under Claude Code's record semantics two projects of one repository cannot each have their own group at all, so the choice is between one project owning the record and a merged group, and the misleading error is the one piece that is wrong regardless of which is picked.

**The shared record.** `claudeRoot` (project_scope.go:83) keys a project by `gitOf(dir).mainTop()` — for `/repo` and `/repo/packages/app` that is the same `/repo`, so both projects read and write the single `projects./repo` record. This is documented design ("a project in a subfolder turns its offs on for the whole repository", library.md's Projects row), but the entry collision you found is not.

**The refusal, precisely.** `syncClaudeLocal` (project_scope.go:229-244): the project's own ledger `rec.Servers` starts from `p.Claude.Servers`; project 2's is empty — its `p.Claude` has never been written. The disk record already holds `mcpServers.magpie` (project 1's, URL ending `~<key(/repo)>`). So `old != nil && !slices.Contains(rec.Servers, hub.Name)` fires and the code says *"Claude Code has a server called magpie for /repo already that isn't magpie's"* — for an entry magpie itself wrote — and drops the hub (`hub = nil`). Project 2's group never takes effect, and the check re-fires on every later sync of that project. One refinement to your step 3: the refusal only kills the hub entry; the off half still runs, so project 2's `disabledMcpServers` addition for B lands in the shared array and works (repository-wide, per the design) — project 2 ends up half-applied: off works, hub entry refused.

**The shared `disabledMcpServers` is gentler than "interfere with each other".** The removal condition is `slices.Contains(rec.Off, n) && !slices.Contains(want, n)` (project_scope.go:255) — a project only ever removes names *it itself* wrote (its own `rec.Off`); another project's additions stay. It is add-only sharing, which is what the documented design wants. Un-offing removes only your own name too.

**Why "merge the groups" cannot work, and "last one wins" is worse than refusing.** The hub entry is one key (`magpie`) whose URL carries one project key (`HubProjectSep + projectKey(p.Dir)`, a hash of the folder); the router routes by what the URL names (mcp_hub.go:204-208). One key holds one URL, so one record holds one project's group — two projects' groups would need either two entries (both local-scope, both live in every folder of the repository, same-named servers twice) or a router-side key that spans projects. And letting the second project overwrite ("yours is magpie's, take it") buys a silent fight: every sync of either project rewrites the URL to its own key, so which group a folder gets depends on which card was touched last — and `clearClaudeLocal` (project_scope.go:281) removes by the ledger's names, so removing project 1 deletes project 2's live entry. Refusing with a true message is the honest state; that is your first proposal.

**So the piece that is a plain defect is the message**: the entry *is* magpie's — another project's — and a one-line check on the stored URL (`strings.Contains(u, gateway.HubMCPPath)`, the same test `projectHubs` already runs at project_scope.go:144-147) can tell the two apart, with the card saying which project holds the record and why this one's group is not applied. Which project owns a repository's record (first-come, or an explicit pick) is a design call on a subsystem landed yesterday, so I leave it — and the message fix with it — to be settled together rather than patch the symptom alone.
