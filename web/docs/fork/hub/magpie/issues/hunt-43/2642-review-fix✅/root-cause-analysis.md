# magpie #2642 根因分析：为什么“修了很多次还是不行”

> 对象：[yetone/magpie#2642](https://github.com/yetone/magpie/issues/2642)，最新反馈 [comment-6251181270](https://github.com/yetone/magpie/issues/2642#issuecomment-6251181270)（v0.1.1285）
> 依据：issue 全部 15 条评论 + `main` 上的 `internal/gateway/native_compaction.go`、`internal/gateway/fallback.go`、`internal/provider/logins.go`（2026-10-18 拉取）
> 选用的思维工具：**第一性原理**（定本质）、**对抗式审查**（逐条攻击隐含假设）、**消融实验**（设计判决性实验）、**奥卡姆剃刀**（选最简解释）、**YAGNI**（质疑 pinning 本身是否必要）、**高内聚低耦合**（定位架构缺陷）、**列出不自信的点**、**蒸馏**（结论）。

---

## 0. 结论（蒸馏版）

**这不是一个单点 bug，而是一个架构矛盾：**

> magpie 的价值前提是“账号可以互换”（无状态池化路由）；而 Codex 原生压缩产出的是“只绑定一个账号、不可迁移的加密状态（`encrypted_content`）”，并且这份状态存在 **Codex 客户端的对话历史里**，不在 magpie 手里。
> 会话一旦带上这个 item，就从“可以随便路由”变成了“必须粘在写入者身上”。这时候任何换号操作都只有两种结果：报错，或者悄悄丢掉上下文。

所以要分三层看：

| 层 | 内容 | 状态 |
|---|---|---|
| **本质层**（修不了，只能绕开） | 已经被原生压缩封存的旧会话，不能迁移到别的账号 | 设计如此。yetone 在 bf931f82c 里明确说过“旧对话仍只能交给原账号” |
| **预防层** | 原生压缩关闭时不再产生封存（#2582） | v0.1.1280 已修 |
| **识别层**（仍有潜在缺陷） | 写入者身份用的是**可变的显示名**，没有用稳定的账号 ID | **未修，最可疑的残留 bug** |

**对 v0.1.1285 这条报错的判断：** 报错文案已经是 1280 之后的新格式（带具体原因和 “Native compaction is off … now”），说明修复确实已经生效。现在命中的是 `checkpointGone()` 最后一个兜底分支 `"%s is no longer signed in to magpie"`：在 `provider.Logins("codex")` 里**找不到名字完全相同**的账号。可能的原因有两个：

1. **（概率最高，奥卡姆剃刀）** 这是 1280 之前就封存的旧会话，而 A 账号已经被退出或移除。这时报错是**符合设计的**，不是回归。用户期待的是“旧会话也能换号”，但修复只是**预防**新问题，**治不了**已经封存的旧会话。修复范围和用户期待之间有错位。
2. **（需要排除）** A 仍然登录着，但它的**显示名变了**，导致身份键对不上，被误判成“已退出”。

“修了很多次还不行”的结构性原因：之前每次修的都是**“写入者为什么从候选池里消失”的某一条旁路**（unlisted、路由组、嵌套组、只剩一个账号……）。矛盾本身一直没动。只要再出现一种让写入者“看起来不在”的情况（这次是 Logins 里查不到），用户看到的就还是同一句话：**“这个会话继续不了”**。

## 1. 时间线：每次修复覆盖了什么、漏了什么

| 时间 / 版本 | 变更 | 解决的路径 | 没覆盖的 |
|---|---|---|---|
| 09-25 `5420466d` | 清单里没列该模型的账号降级到 last-resort `left` 池 | 避免 Free 号挡在 Plus 号前面 | 和后面的 pinning 产生接缝 |
| 10-02 `01d59581` (#474) | Names & levels 按账号配置模型（硬排除） | — | — |
| 10-15 `82f48f09` (#1099, v0.1.1243) | **引入原生压缩和 pinning**：封存只给写入者 | 不再静默丢上下文 | 只在“已过滤的候选”里找写入者，这是**问题的起点** |
| 10-15 `4ad929fd4` (#2271) | fallback 封存也记录写入者 | 漏记的问题 | — |
| 10-16 `440f66701` (#2517) | 写入者额度用满时给 429 专用文案 | 诊断 | — |
| 10-17 `bf931f82c` (v0.1.1280) | ① #2582：关闭开关时不再原生压缩 ② unlisted 的写入者作为 last resort 去试（含路由组/嵌套） ③ 只剩一个账号时也限定到写入者 ④ 报错写明具体原因 | 新会话不再被锁；“开着却被拒”这条路径 | **已封存的旧会话**；**身份键稳定性** |
| 10-17 `717b69f78` (#2639) | 路由页说明这是压缩绑定 | 可观测性 | — |
| 10-18 用户 v0.1.1285 | 报错变成 “X is no longer signed in to magpie” | — | ← 当前位置 |

**规律：** pinning 的实现方式是“先按各种规则裁剪候选，再在剩下的里面找写入者”（`checkpointReaders` → `keepCandidates`）。之后每加一种裁剪候选的机制（降级、硬排除、暂停、路由组、额度、登录状态……），都会多出一个“写入者被裁掉 → 400”的洞。这是**低内聚**：会话粘滞这个约束被分散到了路由裁剪的残差里，没有被当成一等约束来处理。

## 2. 第一性原理拆解

**已知事实（有代码或评论佐证）：**

- **F1** Codex 压缩后，早期上下文**只存在于** compaction item 的 `encrypted_content` 里，这个 item 会随每一轮请求一起发出。
- **F2** magpie 自己读不了这段密文，只在 `compactions.json` 里记录 `sha256(enc) → {Who, Provider, Model, At}`，保留 30 天，最多 1024 条（`wroteCheckpoint` / `checkpointFor`）。
- **F3** 写入者身份 `Who` = `candidate.who()` = `restKey()` = `provider.ID + "@" + strings.ToLower(Account.User)`（`fallback.go:102`）。
- **F4** `Account.User` 是**派生出来的显示名**，不是稳定 ID：
  - `codexUser()`：Team / Business / Enterprise / Edu 席位会变成 `email · Team`；
  - `codexName()` / `nameAlike()`：同一个邮箱出现第二个席位时，会改名为 `email · <workspace前8位>`。
- **F5** 报错分支 `checkpointGone()`：遍历 `provider.Logins(agent)`，用 `strings.EqualFold(l.User, user)` 按**名字**匹配，匹配不到就走兜底的 “no longer signed in”。
- **F6** “只有写入者能解密”这件事 **没有用真实账号验证过**（yetone 原话：“这次没有用真实账号验证，测试都用的是模拟的后端”；另有用户说其它账号也能读）。

**推导：**

- 如果 F6 成立（确实只有写入者能读）：已封存会话 ≡ 账号粘滞。这时能动的旋钮只有三个：**不产生封存**（预防，已做）、**保住写入者**（运维/UX）、**从别处找回明文**（客户端 rollout）。没有第四个。
- 如果 F6 不成立（其它账号也能读）：**整套 pinning 都是不必要的约束（YAGNI）**，#2642、#2517、#2639 这一串问题都是它自己造出来的。

所以 **F6 是整个问题的支点**，应该最先验证（见 §4 的 E1）。

## 3. 对抗式审查：逐条攻击隐含假设

| # | 隐含假设 | 攻击 | 后果 |
|---|---|---|---|
| A | “只有写入者能读封存” | 从未在真实 ChatGPT 后端验证过；OpenAI API 的加密 reasoning 通常是按 org/项目维度加密的，ChatGPT 后端是按 user、workspace 还是 account 维度，未知 | 如果是错的，pinning 应该删除，改成“直接发，后端拒了再报错” |
| B | “1280 修复后不会再产生新封存” | 这条会话的封存时间 `At` 还没核对。如果晚于升级时间，说明 #2582 还有漏掉的产生路径（比如 Codex 直接走 backend 的 compact 端点、路由组路径、开关曾被打开过） | 那就是真回归，不是旧会话问题 |
| C | “no longer signed in 就是真的退出了” | 身份按可变显示名匹配（F3–F5）：升级或降级 Team、同邮箱新增席位、改名逻辑调整，都会让 `Who` 对不上 | 账号明明在，却被告知“请重新登录”，重新登录可能也没用（名字还是对不上），**这和 #2642 最初的“开着却被说关着”是同一类假指引** |
| D | “用户说的‘切号’是在 magpie 里切路由” | 用户也可能是在 **Codex Desktop 里重新登录 B**，而 magpie 会把 Codex 自己的 `auth.json` 登录当作一个账号。这样操作可能让 A 从已保存列表里消失或改名 | 需要问清楚用户具体做了什么 |
| E | “报错写清楚了就算修好” | 对用户来说，结果还是“这个会话继续不了”。诊断变好了，结果没变 | 修复范围需要跟用户明确沟通：旧会话不保证能换号 |

## 4. 消融 / 判决性实验（从便宜到贵）

> 每个实验都是“改一个变量、看结果分叉”，用来把上面的分支一刀切开。

**E1（最关键）验证密文能不能迁移**
把带 `encrypted_content` 的同一个请求体，绕过 magpie 直接用 **B 账号的 token** 发给 ChatGPT 后端。
- 返回 200 且上下文还在 → 假设 A 不成立，**建议删掉 pinning**（YAGNI），整个问题族就没了。
- 返回 400（比如 invalid / could not decrypt）→ 绑定确认，后面按“粘滞”的思路设计。
- 返回 200 但上下文丢了 → 最危险的情况，说明 pinning 是必要的。

**E2 确认封存时间**
从 Codex 本地会话文件（`~/.codex/sessions/**/rollout-*.jsonl`）里取最后一个 compaction 的 `encrypted_content`，计算 sha256，然后去 magpie 配置目录（和 providers 文件同目录）的 `compactions.json` 里查对应条目：
```bash
ENC=$(rg -o '"encrypted_content":"gAAAA[^"]*"' <rollout文件> | tail -1 | sed 's/.*:"//;s/"$//')
H=$(printf %s "$ENC" | shasum -a 256 | cut -d' ' -f1)
jq --arg h "$H" '.[$h]' <magpie配置目录>/compactions.json   # 看 Who / At / Model
```
- `At` 早于升级到 1280 的时间 → 旧会话，符合设计。
- `At` 晚于升级时间 → #2582 有漏网路径，是真回归。

**E3 身份键对不对得上**
拿 E2 查到的 `Who`，去掉 `codex@` 前缀，和 magpie 账号列表里的名字**逐字符**比较（注意 ` · Team`、` · xxxxxxxx` 这类后缀）。
- 完全一致但账号不在列表里 → 确实退出了。
- 列表里有同一个邮箱但名字带后缀 → **假设 C 成立，这是身份键 bug**。

**E4 恢复写入者**
在 magpie 里重新登录 A，其它账号保持开启，再继续这个会话。
- 能继续 → 结论 1 成立（运维问题）。
- 还是同样的报错 → 进一步证实身份键不稳定。

**E5 新会话对照组**
开一个新会话，确认 Providers → codex 的原生压缩是**关**，手动 `/compact`，然后切换到 B。
- 能继续 → 预防层工作正常。
- 不能继续 → #2582 回归。

## 5. 奥卡姆剃刀：对 1285 报错的最简解释

> 这是 1280 之前由 A 原生封存的旧会话；A 现在不在 magpie 的已登录列表里；magpie 按设计拒绝。

这个解释不需要假设任何新 bug。只有当 E2 显示封存发生在升级之后，或者 E3 显示名字对不上时，才需要引入更复杂的解释。

## 6. 架构建议（给维护者 / PR 方向）

按价值从高到低：

1. **先做 E1，决定 pinning 要不要留（YAGNI）。** 这是唯一一个可能让整类问题直接消失的动作。
2. **身份用稳定键（高内聚）。** 记录写入者时，同时存 `chatgpt_account_id`（`codexWho()` 已经能读出 workspace）和 email；匹配时优先用 account_id，显示名只用来展示。这样可以修掉 §3-C。
3. **把粘滞做成一等约束，而不是候选裁剪后的残差（低耦合）。** 现在的写法是“裁剪候选 → 在剩下的里面找写入者 → 找不到就 400”，每加一种裁剪规则就多一个洞。改成：带封存的请求**先从账号注册表里直接解析出写入者**，再检查它的状态（开/关/暂停/额度/登录），通过就只发给它。这样所有路由裁剪规则都不会再影响它。
4. **生命周期守卫。** 用户退出、移除、暂停某个账号之前，提示“有 N 个会话被它的原生压缩绑定，退出后这些会话将无法继续”。把报错从事后提前到事前。
5. **逃生口（可选，需要验证可行性）。** Codex 本地 rollout 里通常保留着压缩前的明文条目，可以提供“从本地 rollout 重建上下文、在新会话里续上”的工具，或者至少在文档里写清楚这条路。
6. **对用户沟通修复边界。** 明确告诉用户：1280 修复的是新会话；旧的已封存会话只能回到原账号，或者重开。

## 8. 不自信的点（按影响排序）

| 点 | 置信度 | 说明 |
|---|---|---|
| 封存是否真的只能由写入者解密 | **低** | 没有任何一方用真实账号验证过；这是整个分析的支点 |
| 1285 这个会话是 1280 之前封存的 | 中 | 只是从 “Native compaction is off … **now**” 的措辞和最简解释推断，需要 E2 证实 |
| 显示名变化导致身份失配 | 中低 | 代码路径上确实可能发生（F3–F5），但不知道报告者的账号有没有发生改名；截图里第一处的 email 和后面打码的可能是同一个 |
| 用户的“切号”操作具体是什么 | 低 | 评论里只说“切换路由到其他账号”，没有说明是不是动了 A 的登录状态 |
| Codex rollout 里保留压缩前的明文 | 中低 | 基于对 Codex rollout 格式的了解，没有在这个版本上核实 |
| #2582 是否覆盖了所有原生封存的产生路径 | 中 | 只看了 `nativeCompactionFor` / `keepsCompaction`，没有完整审计 `codexBackend` 的 compact 端点 |
| 代码引用的行号 | 中 | 基于 2026-10-18 拉取的 `main`，之后可能有变化 |
