    sessions: a Codex rollout magpie rewrites keeps every line where it was
    
    xybio (Discord #feedback): the Codex app often wouldn't reopen recent
    threads: "invalid paginated history lineage for <id>: cutoff byte offset
    is past the source rollout". Codex 0.162 keeps a fork's place in its
    parent by byte (session_meta.history_base.end_byte_offset, checked by
    rollout_lineage.rs validate_cutoff_bounds), and its state database keeps
    turns and how far it has read by byte too. PortCodexRollouts (since
    4896fc3ba, 10-21) wrote magpie's compaction item as Codex's summary
    message, and since 79c8667c9 dropped Claude's sealed reasoning: both
    shorter lines, so a parent shrank and every fork made before the pass
    named a byte past its end.
    
    Now every rewritten line keeps its length (fitLine): a shorter one is
    padded with spaces after its JSON, which serde_json skips; a longer one
    (a short summary under Codex's prefix) is left as it was in a paginated
    rollout, and written as before in a legacy one, where Codex keeps no
    place by byte. MoveCodexProvider, the sibling that rewrites session_meta,
    pads the same way and refuses a longer provider id for a paginated
    rollout. Forks already broken are repaired once per Codex home
    (repairLineages): every line kept its count, and Codex names each line's
    ordinal, so a fork's end_byte_offset is set again to where its parent's
    line end_ordinal_exclusive-1 ends now, in a first line kept as long.
