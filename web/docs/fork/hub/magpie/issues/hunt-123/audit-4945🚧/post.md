**Root cause, confirmed from the code.** In the current tree a Messages request relayed to a Messages upstream reaches `passthrough`'s Anthropic case and is forwarded with its tool exchanges untouched (`internal/gateway/gateway.go`), and a translated build goes through `build` → `anthropicBody` — neither site reshapes a parallel `tool_use` exchange today. DeepSeek's Anthropic-format endpoint rejects that exchange: deepseek-ai/DeepSeek-V3#967 reproduces the same 400 with the raw SDK, both with the results in one user message and one message per result, and the diagnosis there is that Anthropic matches only the last `tool_use` while DeepSeek validates every id and its matcher fails N>1 — so the only shape it answers is one `tool_use` per assistant message with its result right after. That matches the report exactly: sequential calls work, every parallel-call turn 400s.

**Review of the branch.** Four files, +298/−1. `splitParallelToolUses` is conservative: it splits only an exchange the next user message fully answers (every call id has exactly one result in it; no duplicate answers, no orphans); an exchange of one call, a call left unanswered, or a result answering a foreign call goes byte for byte, and the user's text beside the results rides after the last result. It is applied under the same `anthropicReplaysThinking` gate as `withThinkingOnToolTurns`, at both sites (the relayed body and the translated build), ordered before that mend so each split assistant turn then gets its thinking block. The gate excludes `api.anthropic.com` and `claude-*` models, so Claude and every other Messages upstream keep the parallel shape. The branch touches nothing that landed after its base (`8abdf53a8`), so it applies cleanly to the current tip.
