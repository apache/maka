I went through the three reporters' traces against the source at main (7785c4278) now that c875e66c2 (v0.1.2667) is in, to write down where each observed sequence stands. Credit where the reading follows others: the gate and the carry were traced by zane668, the Messages repro is ZanderH-code's, and the traces and the live matrix are fewensa's.

**How one machinery covers every sequence here**

- fewensa's A and B (a Responses client) run on the older gate, b59e4b747 (#3887, Oct 27, before this was filed): a refusal matching `foreignReasoning` (affinity.go — OpenAI's and Codex's "could not be verified", xAI's "Could not decrypt", Azure's "invalid encrypted summary", a relay's compaction blob) is asked again without the seals (`withoutSeals`, OpenAI's compaction then via `withoutCompaction`), the removed hashes are remembered per conversation and key or account (`refusedSeals`), and later turns to that account leave them out up front (`withoutRefused` before each try, gateway.go). One 400, then clean — which is what the traces show, and unchanged by this issue's fix.
- fewensa's C (a 400 on the same account with `affinity.kept: true`) fits the same memory: the affinity record names the immediately preceding try, not where each seal in the history came from. The history still carried items sealed on an earlier turn by another account or vendor, so this was the first time that conversation-and-account pair met them; it refused once, learned the hashes, and the retry without them succeeded. A recent switch is therefore not expected to be visible before every first refusal.
- zane668's Pi case and ZanderH-code's Messages case (a final 400 tagged `other`) were exactly the gate zane668 found: `failForeign` was reachable only for a Responses client, and since 9da9bfabd a non-Responses client holds a Responses upstream's sealed reasoning in its calls' ids (`<id>__rk16__<key>`), replayed on every later turn to whichever Responses upstream came next. c875e66c2 widened the gate (the `from != provider.Responses` branch in gateway.go's serve loop): `refuseCarried` remembers what the request's calls carried as refused by that key or account, the translation leaves those items out of this and every later request to it (`withoutRefusedCarry`, scoped to the try's provider through `withSealScope`), and the try reads `fail: foreign`. The `other` tag falls away with it — the refusal text always matched `foreignReasoning`; only the client condition kept it out of the foreign path.

**What remains, and why it is the design**

The issue's expected behavior — never sending incompatible sealed reasoning in the first place — is not what main does. Sealed items carry no sealer identity: `Part.SealedBy` records only the API (ir.go), not the key or account, and a client-carried Responses history is opaque bytes to magpie. So the first meeting of a conversation-and-account pair with foreign seals is learned from the refusal; every later turn there is clean up front. fewensa's v0.1.2850 table is this shape exactly: 34 first-contact refusals, all `400` `fail=foreign` -> 200 on the same account, no unrecovered failure. Removing even that one attempt would take recording which key or account sealed each item as magpie serves it — the carried items' signature cache and the relayed responses both pass through its hands — and leaving foreign ones out before any try. That is a larger change than the refusal memory, and since the fix landed nobody has asked for it; as it stands the residual is one wasted attempt on first contact, never a lost conversation.
