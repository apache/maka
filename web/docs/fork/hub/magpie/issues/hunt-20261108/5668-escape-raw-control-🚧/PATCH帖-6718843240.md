@yetone — a turn dies over one byte magpie can spell. @AnxForever reported it (#5668): Codex on a long thread sends 6.8–7.5 MB bodies, one of them carries a raw control byte (0x00–0x1F) inside a string — a tool result that read a binary file whole, most likely — and the gateway refuses the whole turn with its own 141-byte 400, `invalid request: invalid character '\x00' in string literal`, before anything is routed: no usage row, the turn lost. Same thread, same path, same account parse fine a minute earlier, so the zstd decode was never in question — the byte rides inside the decoded body.

**Root cause**: `decodeRequest` (internal/gateway/gateway.go:9180) is the one JSON gate a client request passes before fields are rewritten or it is routed — `handle`, `countTokens`, `gemini` and the Codex backend's own `/responses` all read through it (`handle` and `codexBackend` via `requestModel`). encoding/json refuses a raw control byte inside a string literal, and the refusal surfaced as magpie's own `writeError`. Any other door that read the request itself refused the same way (`ollamaChat`'s own `json.Unmarshal`).

**The fix**: following the reporter's own analysis — their `escapeRawControl` sketch — but landed at the shared root, so every door gets it at once rather than `requestModel` and Gemini's decode separately: on a failed parse, and only then, the body is walked once (tracking in-string / escaped), its strings' raw control bytes are escaped as `\u00XX`, the copy is parsed again, and what parses is the body routed, with one line logged (how many, the offset of the first, an excerpt). `decodeRequest` now returns the body it accepted, so the mended copy — not the raw bytes — is what goes upstream or into a translation; the translators read what it hands them, so a turn that needed no escape goes out byte for byte as before. If the copy still does not parse, the first parse's error is returned, not the repair's — the client is told of the body it sent. A control byte outside a string is a broken structure escaping cannot mend, and that refusal stays. A body that parses is never walked, copied or logged: the fallback costs one failed parse, nothing more. Ollama's `/api/chat` and `/api/generate` (whose own `json.Unmarshal` refused identically, and which route a rebuild of what they decoded) read through `decodeRequest` now too. Our hunt process ships the first finished patch, so this was written independently of the reporter's code; that it matches their sketch (walk `inString`/`escaped`, escape `< 0x20` inside strings, fall back to the original error) is independent corroboration of the same diagnosis.
