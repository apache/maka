@yetone A client that keeps the searches of its turns as `web_search_call` items and sends them back with the next request loses them on the way to a Chat upstream: magpie parsed the query and the pages found out of the item, then dropped them again — only a search beside Claude's signed thinking went back — so the model read nothing of what had been searched, and on a long agent session it searched the same things again and told the user it had to double-check. Reported by @wudilyy999 (0.1.3327, Codex → magpie Responses→Chat → a chat upstream) with a synthetic reproduction on an isolated portable copy against a local mock upstream, and a real-chain read-back where a code kept only in the history's `web_search_call.action` comes back `MISSING` while one in a `function_call_output` comes back.

**Root cause**: the parse keeps what the item holds — `web_search_call` with a query becomes an assistant message of `Search` parts, query and the URLs of its sources (`responses.go:495`) — but `searchRoundsBack` (`responses.go:639`), which puts magpie's own search rounds back for a Claude reply, takes the parts back out of every message that has no Claude signed thinking beside it (`DeleteFunc(isSearch)`), as it had always done. That branch is every plain search history's fate: the round-trip the item records survives, the search itself is gone.

**The fix**: such a search goes as text — `Searched the web for: <query>` with `Pages found:` and the URLs — which is exactly what the client kept of it, in the assistant message where the search happened, the same words the signed-thinking path puts in a tool result today. No call is made up for it: no result of its own is kept to answer one (a strict upstream refuses a `tool_calls` with nothing answering it), and what the pages *said* was never kept, so none is written — the reporter's own boundary, kept. The round beside Claude's signed thinking is split into call and result as it was, byte for byte (its result text now comes from the one `searchSaid` helper, same words), and a request with no search in it never enters the function. One difference from the sibling that drops `web_search_call` items on a Responses relay (`withoutSearchCalls`, `responses.go:1004`): that one is left as it is — its input is relayed, not translated, the provider's own chat translation is what turned such an item into a call nothing answers (mxmllln's 400), and the summary requests it serves are told what was found by the reply that followed the search. A provider-side note on that path can be a turn of its own if you want one.
