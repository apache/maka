@yetone @CnsMaple's #5638: a standard MCP SDK client (the official `@modelcontextprotocol/client` 2.2.0 Streamable HTTP transport, what dsh bundles) connecting to `/mcp/magpie/hub/<agent>` gets capabilities but **zero tools** from `tools/list`, while the same hub lists `magpie-browser__browser` to a hand-rolled curl sequence. Every standard-SDK consumer behind the router ends up with no tool at all, and the reporter had to fall back to a direct stdio entry.

One finding up front, following the reporter's own wire trace: the `405` on the GET stream is **not** what empties the list. It is the answer the spec allows a server that offers no server-to-client stream, the SDK treats it as benign, and replaying the SDK's exact sequence (`initialize` → `notifications/initialized` → `GET` 405 → `tools/list`) against current main lists the tools fine. What the trace actually pins down is *when* a standard client talks to the hub: the agent connects the moment magpie rewrites its config, so its `initialize` and `tools/list` land while the agent's only ticked server is starting for the first time — and the empty list is what the hub answers while that first start is failing.

**Root cause**: `backend.start` bounds a stdio server's initialize handshake by `stdioStep` (30s) (internal/library/mcp_hub.go:500), and `backend.tools` made exactly **one** connect attempt, returning the failure at once (internal/library/mcp_hub.go:596 before the fix). `theHub.Tools` leaves a server out when its list fails, so `tools/list` answers `{"tools":[]}` with 200 and no error. A failed start is retried by the *next* `tools/list` — which is why a manual curl minutes later works (a warm start fits the budget). The reporter's SDK `tools/list` isn't that next one: it arrives seconds after `initialize`, waits on the very start that then runs out of its budget, inherits the failure, and empties the whole list. That is the only path in the current code where one client gets `[]` and another gets the tools.

**The fix**: `start` now records when its failure was its budget running out (`b.slow`, internal/library/mcp_hub.go:516), and `tools` keeps trying such starts within its own budget (`hubListWait`, 40s) instead of giving up at the first one; the page-by-page ask is factored out unchanged (`listTools`). A start that can't succeed at all (`not found`, `exited`) is still answered at once, so an agent whose command is missing isn't held for the list's whole budget. A tool *call* is left as it was: it answers with the error naming the server (what `TestHubMCPServerDown` pins). Protocol semantics unchanged — GET stays 405.
