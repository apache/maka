@yetone A request whose body passes 32 MiB kills the whole shared plugin host — @1007cordon-ux saw `plugin: host starts` 268 times in 2.5 hours, every plugin's provider going down together with "connection lost mid-reply (the plugin host sent a line longer than 33554432 bytes)".

**Root cause**: a gateway begin answered its RPC with the whole request body on one line (host.js `gatewayBegin` → `send`), even when no hook changed the body — or one timed out and magpie kept the request. The host reads at most `maxWireLine` (32 MiB) a line from the child (host.go), and a body over the cap ends that line in `errLineTooLong`, which fails and kills the host; every plugin on the shared host loses its provider, and the next request starts a host and sends the same body again — the loop.

**The fix**, following the reporter's own analysis: a begin whose hooks left the request as it came now answers with the run's identity alone — `{id, token, unchanged: true}` — and Go keeps the bytes it already has (gateway.go). That is the根治 and the performance win at once: nothing the size of the request crosses the wire, and the every-request copy it also removes is #5168's. For a hook that really rewrites an oversized body, the reporter's second option is in as a second line of defence: the wire checks the serialized result against `WIRE_LINE_MAX` (matching Go's cap, 64 KiB for the envelope) and gives that request's hooks up — keeping the request, as a timed-out hook does. The report's optional third idea (skipping the hooks for oversized bodies) is covered by that same check. The chunked framing of fetch replies was not reused for results: an RPC result is one message, not a stream, and framing it would rebuild the protocol; the source-side checks remove the only line that could legitimately be huge. `host.js` ships inside the binary (`go:embed`), so there is no old-host/new-Go mix to agree on; the field is additive regardless. The `errLineTooLong` kill stays — a child that never ends a line is still broken.

The report could not catch an actual over-32-MiB body; the tests build one (32 MiB + 4 KiB) and reproduce the loop: before the fix the three large-body tests fail with the shared host killed and restarted, after the fix they pass with the same host answering follow-up requests.
