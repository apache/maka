@yetone the listening mode the reporter asks for — "magpie 网关监听方式为 wsl 监听" — already exists by design, and it is exactly the NAT-mode path: on Windows, while the gateway listens on loopback, `serveWSL` (internal/gateway/wsl.go:214, started at gateway.go:875) also serves it in plain HTTP at every address Windows has on a WSL network (`WSLNets`, internal/gateway/wsl.go:39-44 — the `vEthernet (WSL…)` adapters, re-read every 10s because the WSL VM brings its adapter up and down). That address is where a NAT-mode distro reaches Windows (`wslrun.HostAt`, internal/wslrun/wslrun.go:357-368; a bridged distro reaches Windows on the bridge's adapter instead — cff530079), and it is what magpie writes into the distro's agents' configs (`place.gw`, internal/agent/wsl.go:166), with the gateway's WSL key rather than the loopback one (`keyAt`, internal/agent/gatewaykey.go:19; `gateway.WSLKey`, internal/gateway/wsl.go:82 — a `wsl-` secret in magpie's folder, `-<agent>` suffixed where the agent's key names it). A request arriving there with the WSL key from inside that network counts as this computer's. This is documented as "WSL under NAT" in docs/subsystems/gateway-routing.md and as "WSL twins" in docs/subsystems/agent-wiring.md ("The gateway address and key follow the distro's networking: mirrored or NAT … under NAT … the gateway listens at that address itself"). So a Codex living in the distro (a `codex@wsl:<distro>` twin on the Agents page) under NAT mode should already be wired to an address that works — no new listening mode is needed.

**Where it can still fail, by design's own gates** (what decides which one is the reporter's):

- **Windows' firewall.** The docs' own caveat: "Windows' firewall still decides whether WSL gets in: WSL's network is a Public one." An inbound rule for magpie on the Public profile is the first thing to check when the address is right and nothing answers.
- **The twin was never wired.** With Settings' Detect agents in WSL off, magpie starts no wsl.exe at all (#4872); with no distro registered it probes nothing either (e6cdeac9c); and a distro stopped at probe time is listed asleep until it runs. The ChatGPT app's own "WSL mode" also manages how it launches `codex` in the distro — whether it reads the `~/.codex/config.toml` magpie writes there is exactly what the data below decides.
- **A stale address.** The NAT address moves when WSL restarts; magpie rewrites it on every Sync, and the Agents page marks a twin whose config points somewhere nothing answers as `unreachable` drift (#1013), naming what has to listen there.
