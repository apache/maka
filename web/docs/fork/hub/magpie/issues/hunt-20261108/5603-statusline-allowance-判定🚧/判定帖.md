**The ruling to make** — the reporter's final shape (read the windows from the status line JSON magpie itself receives) works with what the tree already has, but it needs three decisions:

1. **Which account a reading belongs to.** A status line session need not be routed through magpie at all (a Usage only account never is), so `session_id` — the only key the command reads today — maps to nothing. The clean fit is the token itself: the status line command inherits `CLAUDE_CODE_OAUTH_TOKEN` from the session it runs under, and magpie already keeps a hash of each saved setup-token (`claudeTokenVersion`, claude_setup_token.go:51) — the command can hash what its environment carries and report the match, the token never leaving the process.
2. **The path up.** The gateway's `/v1/magpie/statusline` already receives the whole status line JSON by POST (internal/gateway/statusline.go) and throws the `rate_limits` away; the local command would POST the reading (fingerprint, `five_hour`, `seven_day`) beside its GETs, and the gateway keeps it where a reply's headers are kept now, so the card picks it up unchanged.
3. **Who may write it.** It is a new write on a read-only surface (the status line asks `/v1/magpie/quotas?kept=1` today); local-only, or behind the gateway key, and whether a fingerprint plus two numbers is all it takes.

The alternative shape — magpie driving one read itself through a dedicated Claude Code run — is what the warm-up already is, and the reporter's own rounds show its two obstacles: the vendor turns a bare token call away (their 429), and the warm-up's run on a setup-token account sends nothing on their machine (their observation above). If that second obstacle is confirmed on another setup-token host, the warm-up needs fixing before this shape can carry the card; the status line shape needs nothing fixed first.
