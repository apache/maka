@yetone @ProgramerLiang's report on #5452, located line by line: a PDF reached the model only when the request was relayed as sent — the moment magpie translated it, the file was lost. The Responses `input_file` and the Messages `document` were dropped whole, and the Chat `file` became the placeholder text `[attachment application/pdf]`. A ChatGPT API account speaks only Responses and only streams, so a Chat request to it always translated and its file always became the note; a non-streaming Responses request to a stream-only account lost its `input_file` while the same request streamed arrived whole.

**The fix**: the parts parse into file parts now — the Responses `input_file` (a standalone input item, its `file_data` and `filename` flat on the item, or a message block via the Chat file parser) and the Messages `document` — and the Responses and Messages encoders write inline data in their own tongue (`input_file` / `document`), where Gemini's inline data already rode. A file only *referenced* — a Gemini `fileUri` on the vendor's storage, or another host's file id — is still told of: Responses' `file_id` is OpenAI's own and Anthropic's url source takes http(s), not a cloud-storage scheme. The Chat encoder keeps telling of the file rather than carrying it (#934: Chat upstreams' file support is uneven, and a 400 there loses the whole turn); the Claude subscription line renders text to its CLI, which carries no PDF either way. Those two stay as the report's table had them.
