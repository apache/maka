# #5567 根因与修法（车道 B）

Issue: yetone/magpie#5567（becausemadoka，OPEN，0 评论）
报告环境: magpie 0.1.3194 Windows + Command Code 0.1.60，模型 `auto/deepseek-v4.1-flash`（1M 窗口路由组）
take: issuecomment-6700807195（2026-11-07）

## 根因（代码核实，与报告一致）

`internal/agent/commandcode.go` 的 `ccProviderJSONAt` 写 `~/.commandcode/providers.json` 的 `provider.magpie.models` 时只写 `name` / `reasoning` / `reasoningEfforts`（修复前 L151-175），`catalog.Model.Context` 与 `.Output` 从不读。

数据链（报告者引文逐条核实）：
- Command Code 读窗口/输出**只看 providers.json**：`parseModel2` 取 `raw.contextWindow ?? limit?.context` 与 `raw.maxOutput ?? limit?.output`；`getContextLimit` 三级 fallback：providers.json → 内嵌 catalog（按裸厂商 id 精确匹配，`magpie/auto/deepseek-v4.1-flash` 永远匹配不到 `deepseek/deepseek-v4.1-flash`，仅大小写/日期后缀宽容）→ `DEFAULT_CONTEXT_LIMIT = 2e5`。
- 它不会 interrogate 网关 `/v1/models`，自身无法发现真值。
- 同模型 dsh 侧（`dshPiModel`，`contextWindow`/`maxTokens`）两值都有且逐模型不同（1048576/393216 vs 1000000/32768 vs 258624/32000），证明数据在 magpie 已知。
- 结果：1M 模型被 Command Code 当 200K，过早 compact。

## 修法

`ccProviderJSONAt` 镜像 `piModelJSON`（internal/agent/agents.go:847-854）的两个 guard 块，键名用 Command Code 自己的 BYOK 字段名 `contextWindow` / `maxOutput`（报告者 parseModel2 引文证明两种拼法均收，选与包内平铺风格一致的这组；`maxOutput` 是 Command Code 原生名，不用 dsh 的 `maxTokens`）：

```go
if m.Context > 0 {
    e["contextWindow"] = m.Context
}
if m.Output > 0 {
    e["maxOutput"] = maxTokens(m)
}
```

- `maxTokens(m)` = `provider.OutputWithin(m.Context, m.Output)`（internal/agent/route.go:446）：output 压在 window 内（models.dev 有 output>window 的条目，#1438/#338），与全部兄弟 writer 同一函数。
- guard 与 pi/cline 完全同构（`Context>0` / `Output>0`），零值不写键，不产生 `contextWindow: 0` 类脏键。
- 失败读取语义：只增键不删键；存量用户已写的 providers.json 在下一次 Sync / model 选择时被 `theirsKept(..., "models")` 整 map 重写为 magpie 版（`models` 在 `whole` 参数里，internal/agent/sync.go:146-175），新字段随之补上——同时这正是报告者 workaround 之痛的机制证据（手改会被洗，magpie 写才保得住）。
- 不触碰：efforts/reasoning 三分支逻辑、Check/Notice/Fields、其它任何 writer。
