## 根因（三层，全部实证于当前 main）

1. **循环机制**：ZCode 账户级 429 `[1302][您的账户已达到速率限制，请您控制请求频率][request-id]` 被分类 `failRate`（速率词）→ `passing()`（fallback.go:2172-2176）把它当"片刻可过"做 1/2/4s×3 同位重试 + `busy()`（patience.go:77-78）把它当"片刻可过"进 patience 轮询（12 轮，2s→30s）——`"magpie keeps asking, so the 429 comes back in a loop. dsh shows no error"`（yetone 转的新报告）即此两腿。
2. **为何 wall 判定漏网**：`wallCodes`（plugins#512 SenseTime 先例）就是为这个场景设的——"no moment clears it: the same-one retries and a patience's rounds sent the whole request again eight times in 38s"（注释原文），出口="The next account is asked, or the agent has the error at once"。1302 漏网因 `walled()` 只读 `error.code` 字段，而插件形态下 code 可能只在 message 文本（erlinerd 证实 200-envelope 派生形态无独立 code 可读——"the code reaches magpie as `[1302]` inside the message text"）。
3. **1302 是 wall 非 rate 的证据**：erlinerd 实测"rested, retried, 429 again"（rest 后重试仍 429，502 案例 spacing 分钟级 121ms–2m3.5s 全败）；两案例单次尝试时长 16.253s/40.237s；同型先例 plugins#512 的 SenseTime「您的模型请求频率超限，请稍后重试」字面同为速率语、行为同为持续拒绝，已被定为 wall。
