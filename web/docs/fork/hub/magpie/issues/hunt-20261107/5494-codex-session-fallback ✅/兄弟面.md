## Codex 线程迁移/交还族逐个对比（codex.go）

| 函数 | 读什么 | 与本改动的关系 |
| --- | --- | --- |
| `bringBack`（771-800，**本单改动**） | config 读值 + stash codex.provider | 修复点 |
| `bringOver`（890-935） | stash codex.provider 为迁入源 | 方向相反（迁入），守卫 `CodexProviderIn==magpieID`；不受影响 |
| `bringOfficial`（989-1024） | config 读值 + stash | 只动 ccSwitchOfficial/CC Switch mirror 的线程；修复的排除集 `src != ccSwitchOfficial` 保证与其互斥，不抢线程 |
| `bringBeside`（1047-1110） | stash codex.provider 为 beside 搬运源 | **被修法的第二半（清 openai_base_url 残留）保护**：残留线在时它会把 bringBack 刚归还的线程再搬去 openai（RED 调试实证）；清线后其守卫 `!viaBase()` 直接 return。**同时 src 分支加了 beside 活性守卫 `!joined() && !beside()`**：真 beside/join 接线（stash 有 codex.beside/joined=1，Join 写入）下 bringBack 让位——线程归 bringBeside 搬、giveBeside 在 Disconnect 归还（`TestCodexBesideBringsTakenProvidersThreads`、`TestCodexMirrorAtTopJoinsWithItsThreads` 实证首版无守卫即红，加守卫后绿）。真 beside 模式 bringBack 迁移动作为 0、不清线，行为不变 |
| `giveBeside`（1110+） | stash codex.brought 记录 | 只归还 bringBeside 自己搬过并记录的线程；与修复无交集 |
| `lendOwn`/`giveLent`（1450-1530） | config 读值 / stash codex.lent 记录 | lendOwn 是接管方向（openai 线程借给用户渠道），giveLent 按 lent 记录归还；两向都有记录兜底，不受 bringBack 目标变化影响 |
| `Unwire`（1889-1923）/`unroute`（1629-1693） | unstash 恢复 config | 既有恢复路径不动；Unwire 在 bringBack 前 `forget(codex.provider)` → bringBack 走 fallback（config 已被 unroute 恢复，to 本来就对）——修复对正常 Disconnect 路径零行为变化 |

`CodexProviderIn`（126）只读；五个迁移函数（Relabel/RetagPaged/Move/MovePacked/MoveRecent）按 from→to 执行，全部有 trash 备份与 ErrActive 保护，不感知目标来源——调用方语义变化不触碰它们。`codexProviders`（184）只是列表展示用读值。

## 其它 agent 的同型排查

- `grep -rn "stashShared()\[" internal/agent/*.go`：stash 读写遍布 claude/qwen/zed 等，但「provider 绑定的会话线程批量迁移」机制只有 codex 有（其它 agent 的配置无 per-thread provider 绑定，无同型缺档）。

## 失败读取语义

- stash 无 codex.provider（旧版 magpie 的迁移、stash 被 forget、全新用户）：修复分支不进，行为与现状逐字节一致。
- src 指向已删除的渠道：线程回到该渠道名下（Codex 该渠道不在 config 时列表不显示，切回即见）——归属正确优于「塞进当前渠道」；trash 备份仍在。
- DelTOMLTop openai_base_url 失败：仅记日志（"dropping the base URL the takeover left"），迁移本身已完成；下一 Sync bringBack 无动作，bringBeside 可能再搬——与现状同态，不比现状差。
