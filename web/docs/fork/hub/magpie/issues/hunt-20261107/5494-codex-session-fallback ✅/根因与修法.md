## 假设清单（代码核实后全部证实/修正）

1. **接管迁入有来源记录**：证实。`codex.go` Fields Set（接管 magpie 模型）时 `stash(codex.provider: get("model_provider"))`（~1846），`bringOver` 以 `from := stashShared()[at.key("codex.provider")]` 把来源渠道（CC Switch 的 custom）的线程迁到 magpie——测试日志 `1 thread(s) started on custom moved to magpie` 与报告者 242+1626 条日志同形。
2. **交还迁回用「当前读值」而非来源**：证实，本单根因。`bringBack` 的 `to := sessions.CodexProviderIn(dir)` 读 config.toml 的 model_provider（键不存在 → Codex 默认 "openai"）。接管经 asProvider 模式（model_provider=magpie）时退出只有 Unwire/Disconnect 路径会经 `unroute → unstash(codex.provider)` 把 custom 写回 config；**切换回来晚于 magpie 离开 config**（hand edit、CC Switch 再选一次、Sync 自身的 defer bringBack）时 config 无键 → to=openai → 全部 magpie 线程错挂 openai——日志 `moved back to openai` 与报告者逐字同形。
3. **还有第二个错挂源**：新发现。asProvider 接管在写 model_provider=magpie 的同时写 `openai_base_url = 网关`（codex.go ~1844）。交还若错过 Disconnect，openai_base_url 残留 → `bringBeside` 的 beside 模式判定（`viaBase() && model_provider=="" && CodexProviderIn=="openai"`）误真 → 把 stash 来源渠道（custom）名下的线程再搬到 openai（"moved to OpenAI, where Codex resumes them beside its sign-in"）——会抵消只修 bringBack 的效果（RED 调试中实证）。真 beside 模式不受影响：它没有 asProvider 接管，magpie 名下无线程，bringBack 迁移动作为 0，不触发清理。
4. 「切回原渠道后旧会话无法继续/选择模型」（issue 第二半段）：同根因的直接后果，非独立面。Codex 0.166+ 的 resume/provider 列表按线程所属 provider 锁定——错挂 openai 的线程在 custom 渠道下必然 mismatch（"This chat uses openai, but your current provider is custom"，报告者 15:48 实测）。修好归属即消除。
5. 「已发生错误迁移的存量修复」（诉求 3）：**不在本单范围**。现状迁移在 magpie trash 有完整备份（`settings.Dir()/trash/codex-provider/<ts>-<id>/` 含 move.json 记录 from/to/files），存在按备份回滚的原地修复路径，但需要独立的设计与批量工具，帖内说明留给维护者/后续单。

## 修法（internal/agent/codex.go，bringBack 两处）

```go
if src := stashShared()[at.key("codex.provider")]; src != "" && src != magpieID && src != ccSwitchOfficial {
    if to != src {
        to = src
        if viaBase() {  // 接管写的另一根线（openai_base_url）随收尾一起拔掉，
            forget(at.key("codex.failover"))  // 否则 bringBeside 会把刚归还的线程
            edit.DelTOMLTop(path, "openai_base_url")  // 再搬到 openai（假设 3）
        }
    }
}
```

- 目标优先 stash 来源（src 的排除集与 bringOver 的 from 守卫一致：magpie 自己、ccSwitchOfficial）；stash 无记录（旧版迁移/已 forget）→ fallback 现状行为（config 读值），不比现状差。
- **beside 活性守卫 `!joined() && !beside()`**：真 beside/join 接线（Join 写 stash codex.joined/beside=1）下 bringBack 让位——那时线程在 bringBeside 的 beside 语义管辖内（搬 openAI 经 magpie resume，Disconnect 时 giveBeside 归还），src 生效会先于 bringBeside 把线程抽回来源并清掉活着的 beside 线（首版实现即红 `TestCodexBesideBringsTakenProvidersThreads`/`TestCodexMirrorAtTopJoinsWithItsThreads`，加守卫后全绿）。#5494 场景是 asProvider 接管，stash 无这两个标记 → 守卫放行。
- 迁移实际发生（to != src）才清 beside 残留线：真 beside 模式（Join，无线程迁移）完全不动；正常 Unwire 路径 stash 已被 forget（1911）走 fallback，行为不变（unroute 已恢复 config，to 本来就对）。
- 幂等：迁移发生后下一 Sync bringBack 无动作（线程已不在 magpie），不再清理、不再迁移。
- 报告者诉求 4（不批量改 openai 会话）：本修复只改「magpie 名下线程」的归属目标，openai/custom/其它渠道的线程一个不动；且同一轮接管只有单一 stash 来源，不存在「全部 openai → custom」的误伤面。
