@yetone The mismatched pair @franklooo captured is real on the version they ran, and it is already mended on current main — 0.1.2738 predates the fix.

**Root cause**: on a Messages reply relayed as it came, `anthropicTextCalls` (`internal/gateway/textcalls_anthropic.go`) — the filter that turns calls a model wrote into its text into `tool_use` blocks — holds an empty text block's `content_block_start` while nothing of the block has gone on, and releases it when the block's first words arrive. On 0.1.2738 that filter gathered each event line by line, so an upstream that flushed an event's `event:` line in a read of its own had the lone line dispatched bare (the read's empty tail was taken for the blank line that ends an event), and the start's data, arriving in a read of its own, was held without its name. Released later, the start's data reached the client right after the next frame's bare `event:` line — and an SSE parser names the event it dispatches with the last `event:` line it read, so the start went out as `event: content_block_delta` carrying `content_block_start`'s data. That is the pair in the report, and why it was rare: it took the vendor splitting its writes between the two lines. It is the same reader #4868 mended.

**The fix**: already on main — f168dd278 ("a relayed Messages stream is read in whole events, however its reads are cut", #4868), first shipped in **v0.1.2861**. The filter now assembles whole events whatever the read boundaries, and the held start is kept verbatim, its `event:` line included, so the released frame names itself as its data says. Anything past v0.1.2861 (current is v0.1.3260) has it; upgrading from 0.1.2738 ends this.
