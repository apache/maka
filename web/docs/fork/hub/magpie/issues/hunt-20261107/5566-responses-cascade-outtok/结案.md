# #5566 结案档案

单：Remote Magpie cascade skips the output-token default after Responses tool conversion
帖：https://github.com/yetone/magpie/issues/5566（PATCH 帖 #issuecomment-6701456032）
take：#issuecomment-6700844205（10:17，帖前重查仅此一条评论，无竞速）

## 根因

- `fillsOutput`（internal/gateway/maxoutput.go:263）以 `!p.IsRemoteMagpie()` 排除远端 magpie 目的地，理由是「another magpie fills its own」。
- 该假设仅在请求可原样 relay 时成立。`fillsOutput` 唯一调用方在 `forwardTranslated`（gateway.go:7584）——本跳翻译时才咨询。`searchedForIt`（原生 web_search 声明）触发 B 端翻译后，tools 已转换的规范化 body 让 A 走 passthrough，A 的转换期填充永不运行，其 ceiling 只降不升。两跳都无人填 → vendor 默认 1024 截断（Codex: `Incomplete response returned, reason: max_output_tokens`）。

## 修复

删去 `!p.IsRemoteMagpie()` 一项（跟随报告者自身分析）。填充仍只在翻译路径发生：整转 relay 不受影响（本跳不盖章，A 翻译时自行填）；盖的值来自 B 缓存的远端目录（askedOutput）；客户端显式正值仍优先（`req.MaxTokens <= 0` 门）；vendor 拒绝填充值仍走 outputFillRefused/markUnfit 停填。

- 回红实测：`--- FAIL: TestRemoteMagpieCascadeAsksItsOutputLimit (0.56s)`，两跳 `max_output_tokens 0`（hop[0] model=relay/m1、vendor[0] model=m1）。
- 恢复修复后 GREEN（5.4s）。

## 兄弟面 rg 全查

- `fillsOutput` 全仓唯一调用 gateway.go:7584（forwardTranslated 内）；relay 路径不咨询，改动不触及 relay。
- gateway 包内 IsRemoteMagpie 其余引用逐一比对：video/draw/embeddings/user_agent/billing_line/decide 等与本改动无关；forwardTranslated 内 7525/7544（service tier）与 7636（Chat web_search_options）及 forwardOnce 5810（caller 头）均与 output 填充正交。
- 相邻机制不改的理由：withOwnOutput 由 shortByDefault（仅 api.deepseek.com 主机）门控；Anthropic 分支 fillsOutput 本就为 true（改动前远端 magpie 也填）；anthropic.go:1029 defaultMaxTokens 仅在未填充时兜底；responses.go builder 仅输出正值——填充后为正，行为不变。
- 无既有测试钉死旧行为（remote magpie 测试族无「翻译后不带 max_output_tokens」断言）。
