# #5561 根因与修复（车道 C，2026-11-07）

## 判定面：口径源头在哪一层

**在前端 renderCtx 的 series 归属逻辑（口径源头即此处），不在 Go 后端，也不在显示层。** 依据：

1. Usage → Context 的会话曲线数据由 Go `contextOfRecs`（internal/gui/context.go:416）算好经 ctxJSON 下发（context.js:1152 `series: s.points`）——Usage 口径源头在 Go，**本单不动它**（它是参照权威）。
2. Routing 页卡片的「本会话」线由前端 `renderCtx`（client.js）从请求列表自算 series——归属逻辑本来就住在这里。修这里的筛选=修口径源头，非显示层遮症状。
3. 前端记录已携带判定所需字段：`Route.Sub`（trace.go:104 `json:"sub,omitempty"`）、`Prompt.Parts`（prompt.go:54，tools 判定=parts 有 kind "tools"）——无需动 Go 加字段。

## Go 侧权威口径（contextOfRecs，对齐目标）

- `!r.Asked || r.Kind != "" || !r.Tools && tooled[ctxKey(r)]` → 不进曲线（context.go:466 起）：side call（kind）+ 带工具会话里的无工具请求（toolSessions：会话内有 Kind==""/Sub==""/Tools 的请求即为带工具会话；无工具者是 agent 挂在会话 id 下的旁路调用——Claude Code auto-mode classifier、标题、配额检查——其 prompt tokens 不能代表对话，e98440ae 先例）。
- `key := sessionOfRec(r); if key == "" || r.Sub != "" { continue }`（context.go:492）：子代理的 prompt 是它自己对话的，不进主会话曲线。
- 先例提交 e98440ae（TestContextSideCallsAreNoCompaction）。

## 修复前形状（=报告者所见）

client.js renderCtx 的 same 筛选只查 `x.prompt && x.agent === r.agent && !x.kind && 会话归属`：子代理请求（sub 非空，session 同主对话）与无工具辅助请求全部混入主对话曲线 → 96K–108K 的主对话线上出现 298K/7K/13K 的假升降（#5561 报告者的"反复升降"）。

renderCtxSessions（e1aec5389 的会话条块）取 `g.last`（会话内最新请求，无论来源）作为会话读数 → 子代理最后发完时块显示 298K，读作主会话的——同根因兄弟面。

## 修复（internal/gui/assets/plugins/routing/client.js，f13f430aa）

1. renderCtx：会话线归属对齐 contextOfRecs——
   - `inSession`：同 agent、!kind、同会话（原 same 保留）；
   - `withTools(x)`：prompt.parts 有 "tools"；
   - `tooled`：会话内有 !sub && withTools 的请求（对齐 toolSessions）；
   - `same`：`(x.sub||"") === (r.sub||"") && (!tooled || withTools(x))`——主对话线只收主对话轮；子代理线按各自 sub 独立（子代理自身查看保留）；带工具会话的无工具请求不进线；
   - r 自己只在过口径时才补进线（口径外请求显示所属会话线而无自己的点，其 tokens 仍是卡片主题数字）——被排除的请求不再以孤点接在会话线尾（那会画出 7.2K 接 108K 的假压缩）。
2. renderCtxSessions：块读数取 `g.rows.find((x) => !x.sub && (!tooled || withTools(x)))`（会话自己最新一轮）而非 `g.last`。
