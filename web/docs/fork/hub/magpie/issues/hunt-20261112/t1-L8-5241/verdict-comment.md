Nothing here is a config corruption — every piece of it is one of magpie's own Codex states, and the one genuine defect on this path (the desktop app left on an account that ran out, while magpie had already switched to another) was fixed the day after this was filed, first in v0.1.3002. What each piece is:

**`model_provider = "magpie"` coming and going is magpie's own contract, not a loss.** The top-level `model_provider = "magpie"` is written only while magpie is Codex's provider — the takeover for an account out of allowance — and taken out again whenever magpie steps back beside the ChatGPT sign-in, which is the signed-in state with room (`internal/agent/codex.go:66-74`: "takes model_provider out whenever it steps out as the provider (disconnected, unwired, joined beside the sign-in)"). The step-out is the branch at `codex.go:1728` (`chatgpt && !out() && ours`), which removes `model_provider` and `model_catalog_json` and keeps `openai_base_url` — your screenshot still has it, so routing through magpie was never lost with the line; what the line marks is which of the two states you are in. With more than one account, magpie rotates the sign-in, so this rewrite fires at every switch and every model move — which reads as "每次更新模型后就会丢失" (lost after every model update).

**The app "automatically using an account" is the rotation.** With several Codex subscriptions, magpie signs the CODEX_HOME in to the next account that has room, "as switching it on the Accounts page would" (`internal/provider/codex_switch.go:3-12`), and the ChatGPT desktop app follows auth.json — its account changes under you by design (#208, #209, #530: the sign-in follows Smart). The known failure of that rotation: the app's app-server keeps the account it started on, and once that one runs out the app greys Send for every model, magpie's included, while magpie reads only the account now signed in, which has room. That exact case was reported on Discord (nb5p) and fixed in `3d0d79060` — the app left on a spent account is restarted onto the account Codex is signed in to — first in **v0.1.3002, Nov 5, about eleven hours after this issue was filed**. If the magpie you were on predates that, the greying never clears by itself, which is your "GPT 无法使用" (GPT unusable); on anything ≥ v0.1.3002 the app is restarted onto the room account instead.

**Why the hand-added line "works", and why the row then reads 已不经过 magpie：配置已变更 (no longer through magpie: the config was changed).** Hand-adding `model_provider = "magpie"` puts Codex back in the provider state, which is past the account's Send gate — the takeover exists for exactly that (codex.out, `codex.go:1758`) — so the app sends again. But the provider state is a pair: magpie writes `model_catalog_json` beside `model_provider`, and the step-out removes both. A `model_provider` of magpie's without a catalog of magpie's fails Codex's wiring check ("Codex's model_catalog_json is no longer magpie's list", `codex.go:2186`), and that check is what the Agents page shows as "{agent} no longer goes through magpie — its config was changed" (`internal/gui/assets/i18n.js:842`) with 重新接入 (reconnect). And the line fights the Sync: with room on the signed-in account, a top `model_provider` of magpie's is magpie's own to take down (`ours` in the same branch), so the next switch removes it again — the oscillation you keep seeing.

**The two states that hold still, if you want either:**

- Keep the ChatGPT identity and let magpie rotate accounts: run ≥ v0.1.3002 (current is far past it) and leave the config to magpie — the line will come and go with the takeover, the app is restarted onto the account with room, and routing through `openai_base_url` never stops.
- Want `model_provider = "magpie"` to stay for good: set Codex's sign-in to magpie's API on the Agents page — magpie then stays Codex's provider through a sign-in with room too (`requires_openai_auth` follows the room, `codex.go:635`), which is the state whose trade #5702 and #6037 documented (on a used-up account the ChatGPT mode parks until reset).

Hand-editing the line back is the one path that ends in the red row, by design.
