**1. Ping keepalive.** Confirmed absent: magpie sends no websocket ping (it answers the backend's pings, which `coder/websocket` does automatically; `rg '\.Ping\(' internal/` finds none on the codex sockets). Worth knowing what the reference does: Codex's own client doesn't send pings either — `codex-rs/codex-api/src/endpoint/responses_websocket.rs` only answers server pings inside its pump task and instead wraps reads in an `idle_timeout` that errors a silent connection out ("idle timeout waiting for websocket"), and `core/src/client.rs` recovers at reuse time (`is_closed → connection_closed`, fresh connection, `force_http_fallback`). So the drop you hit would land in Codex CLI on the same path too; a keepalive ping would be a deliberate divergence from the reference client, in a subsystem that landed days ago (#5781, 11-09/11-10). That design call belongs to the maintainer — if it lands, the natural shape is a periodic ping (or Codex's own alternative, an explicit idle timeout with a retryable error) covering kept sockets too, since a kept socket idling toward `codexKeepIdle` dies the same death and is only detected at its next turn.

**2. Transport option.** It exists for key providers: `magpie provider set <id> socket=` — `""` is HTTP alone, `auto` tries the socket and falls back, `on` always tries (`provider.go`, #5781). A ChatGPT subscription provider is different: its turns are socket-first by design (`SocketTurn` → `codexTurnURL`), with HTTP as the automatic fallback when the handshake is refused or the message can't go over the socket. There is no off switch for a subscription account today; adding one is the same maintainer call as above. Note the fallback path already means the wire can carry the turn either way, so it would be consistent with what's there.

**3. Transparent retry before any output.** Already in, before the reply is handed on: a kept socket that fails before anything is relayed retries the turn on a fresh socket and then over HTTP (`errCodexSocketAgain`/`errCodexSocketFallBack`), and a handshake failure falls back to HTTP. After the first event your `ttft_ms` shows, the turn has begun for the client — replaying it would repeat output Codex has already accounted, and the reference client doesn't do it either (it resets at the next turn's reuse). Not a safe face for a transparent retry.

Making a severed reply filterable in the Requests page is the same family as #3358 (stop reasons and failure flags in usage rows); that's a product decision on the usage schema, left to the maintainer rather than patched here.
