The exact error is already fixed upstream — same vendor, same words, same param: Command Code answering a compaction 400 `unsupported_input_item` (param `input`) because its `/responses` takes messages, function calls, their outputs and reasoning only. The fix landed in `ff415f39c`, first released in **v0.1.3139** (Nov 6, five days before this was filed), closing #5181 and #5259 — #5259 is the same Command Code refusing the same error text byte for byte, on a Codex subagent's compaction. Your 0.1.3318 is past v0.1.3139, so the compaction path in your build carries that fix.

**What that fix does on the compaction path.** A Codex compaction arrives as a `compaction_trigger` item in the input; for a magpie model magpie swaps the trigger for a summary request (`codexInputAs`, `internal/gateway/codex_backend.go:2652`) and asks the provider to summarise the conversation. When that summary ask is refused with `unsupported_input_item` — as the 400 itself, wrapped by another magpie in front (its 400 or its 502), or inside the summary's stream as an `error` / `response.failed` event (`inputKindRefused`, `codex_backend.go:4106`) — magpie asks again with the conversation as plain text, which Command Code takes; when the text ask is refused too, magpie writes the summary itself. The compaction completes either way and the refusal never reaches Codex. I re-ran the fix's own tests on today's tip (`9c33839de`): `go test ./internal/gateway -run 'TestCodexCompactUnsupportedInput|TestCodexCompact|AgentMessage' -count=1` — ok, all five refusal shapes plus the local-summary floor green.

**Why you can still see it, two candidates — and your own notes point at the first:**

1. **A request that never enters the compaction path.** The ask-again-as-text fallback lives entirely inside `codexCompact` (`codex_backend.go:3759`), which only runs for input carrying a `compaction_trigger`. A request without one goes out as a plain relayed turn (`s.serveAgent`, `codex_backend.go:225/298/310`), and a 400 there is handed back to Codex as it came — no fallback. Your middleware report names exactly this scene: `collab_spawn` / `agent_created_thread` inherit the parent thread's history, whose `agent_message`, `custom_tool_call(_output)` and other vendor-only items replay inside an ordinary request — `codexInputAs` keeps every non-trigger item as it came (`codex_backend.go:2641` restores only magpie's own `magpie1:` compactions), Command Code refuses the kinds it doesn't take, and Codex shows the refusal. The "stream disconnected before completion" wording is Codex's own for a streamed reply that broke off under it. Regular 400k-token conversations don't fail because their items are all kinds Command Code accepts; inherited ones fail because the parent's items aren't.
2. **Command Code changed under you.** The fallback has existed since Nov 6, and you wrote the trouble started Nov 10 (「这个问题是昨天才出现的」— "this only appeared yesterday") on the same 0.1.3318. If the compaction path had always been missing the fallback you'd have seen this before Nov 6 too; a vendor that started refusing — or started cutting streams over — something it previously accepted fits "only yesterday" better.

**What would tell the two apart.** magpie logs every compaction fallback: `codex compaction: … answered 400 (…); asking again with the conversation as text`. Reproduce once with app.log at hand — those lines present means the compaction path did its work and the failing request was a different one; no such lines means the request that failed never carried a trigger, which is candidate 1. Either way, first re-test on a current release: 0.1.3318 is about six hundred builds behind tip, and the compaction path gained more in between (e.g. #5067 — a summary refused as system messages is asked again with the roles as sent, `1ad9d157f`).

**On your middleware report, for the record:** suggestion 1 (filter items in magpie's own summary ask) is already the state on tip — the summary ask goes out as messages-as-text with the local-summary floor beneath it; suggestion 3 (keep `magpie1:` compactions, drop foreign ciphertext) is also magpie's existing behavior on this path (`codex_backend.go:2641`). Suggestions 2 and 4 (declared per-provider item support, a built-in switch) are the maintainer's calls. The genuine gap your report surfaces is candidate 1 above — the no-trigger relayed path with inherited vendor-only items, which nothing covers today; if your app.log points there, a dedicated issue for that seam (relay-side conversion of `agent_message` / `custom_tool_call` items, as your middleware does) would give it a clean home.
