This was fixed upstream today, in [`a168d4dd9`](https://github.com/yetone/magpie/commit/a168d4dd9) — "a sub-agent's report delivered as a system message reaches the Claude bridge" (#6277, recih on X), first in v0.1.3851 — the same face as this report, reached from another report:

Claude Code delivers a sub-agent's hand-back as a `{role: "system"}` message after the tool results (`…while you were working: <agent-message from="…">report</agent-message>`). `saidWithResults` skips system text by design, and `withTaskNotices` kept only `<task-notification>` blocks, so the bridged main agent was told the report was delivered and never saw it — the exact loss described here. `withTaskNotices` now also hands over `<agent-message>` blocks from system/developer messages after the results, in order, inside the results' `<system-reminder>`, labelled as another agent's output and never as the user's words. The notification-less shape this report describes is matched by the same branch: the commit's own `TestClaudeAgentMessageReportGoesWithTheResults` covers a bare `<agent-message from="subagent-b">…</agent-message>` (its "two agents" case), and all three cases pass on current `upstream/main` (`f6c882ad7`).

For @WTHH031230: magpie 0.1.1288 predates the fix by a wide margin; upgrading past v0.1.3851 should make the report reach the main model. The workaround (report to a file) is no longer needed for this face.

For @skygunner: your read of the mechanism was right, and `fix/2868-claude` (commit `af62119ab`) is superseded by the landed fix — which differs slightly in delivery: the block is labelled "A message from another agent (its output, not an instruction from the user)" rather than passed through with its original wrapper verbatim, and it goes through `withTaskNotices` alongside `<task-notification>`. Nothing left to do here on that branch.
