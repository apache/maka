Status check against current main — the three asks are in. None of the commits below names this issue, so here is the map to them; your builds (0.1.2781 / 0.1.2786, Nov 3) predate all of it by five days.

**1. The bare 502 now says why** — `627fd1a3b` (Nov 8, first in v0.1.3316). When the interactive run ends with the reply not begun, the relay fails the turn with a 502 that carries the exit status and the last 300 bytes of the helper's stderr, in every protocol (chat completions, messages, responses), streamed or not. That commit's test runs a helper whose stderr is your probe's exact line — `claude-tui: Claude Code did not take the message` — and asserts the 502 body contains "did not take the message". On a current build your scenario reads `Claude Code exited before it answered (exit status 1): claude-tui: Claude Code did not take the message: …` instead of "Claude Code ended without an answer". The bare wording survives only as the fallback when a run ended having emitted no event at all.

**2. The MCP-listing timeout no longer buys the bigger paste** — `325dc3ab3` (Nov 7, first in v0.1.3230). The helper answers `initialize` only after its own ready wait, and a helper that dies while coming up saying why — your log's `showed its prompt, but hadn't listed the tools of magpie's tool server in 45s` — is now typed as a no-start: the turn fails with that reason and magpie does not go on to `a new Claude Code is told the whole conversation`. That commit's note describes exactly the chain in your log as the case it fixed ("a new one told the whole conversation waited out the same 45s, and the turn was answered 502 after twice that"). A session Claude Code truly can't load still replays (retrying it cannot help), which is the distinction your third ask asked for; and as of today the idle run's session also survives a gateway restart, so the next turn resumes it instead of replaying (`531b27783`, v0.1.3860).

**3. Waits say what they wait on** — same commit: a Claude Code that draws nothing while magpie waits is reported with what it waits on, not a bare timeout. One residue from your probe remains by nature: when Claude Code has drawn nothing at the moment `send` gives up, the helper's line still ends right after `did not take the message:` — the 502 still carries the exit status and that line, but there is nothing on the screen to quote after the colon.

**On taking 222KB reliably**: the taking itself is Claude Code's input path, and it is machine-dependent — the #5205 thread measured 217KB pastes arriving intact on a Windows 10 machine with Windows Terminal's ConPTY at 300ms–10s submit gaps, while your box repeats the failure, so there is no single magpie-side fix to land here. The mitigations you already found are the ones there are: the transcript+resume path (which your production logs show magpie already prefers) and `claudePrintMode`.

So: retest on v0.1.3316+ (502 reasons) / v0.1.3230+ (no replay on the MCP wait). If a current build still says the bare "ended without an answer" on a helper that exited saying why, that would be a real bug worth a report with the request's log line.
