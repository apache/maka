@yetone Following @paul-tian's source analysis, this patch addresses the **Until used up (`drain`)** part of this report: a busy account with allowance left waits near its cap instead of being moved behind the remaining candidates. The reported live trace was captured under **In order**, not drain; this patch does not change In order, add a configurable near-cap policy, or add new trace reasons.

**Root cause:** `Server.serve` in `internal/gateway/gateway.go` moves a busy near-cap candidate to the end before making an upstream attempt. That happens after the routing strategy has ordered the pool, overriding drain's promise. Checking only the outer request's routing would also miss a drain provider reached as a fallback or a drain group nested beneath another routing mode.

**The fix:** keep the drain choice on each planned candidate (`perKeyBarred` and `planLevel` in `fallback.go`), then suppress only the near-cap spillover for that candidate. Serialization, usage refresh, cap recheck, actual-exhaustion failover and existing failure handling remain. Explicit concurrency/RPM failover retains its existing behavior. Candidate reordering, affinity and patience retries copy the candidate and preserve this choice. The product contract in `docs/subsystems/gateway-routing.md` describes the behavior.
