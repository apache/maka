## 2. 仓库规则（硬约束）

- **不收外部 PR**（b91569d3）。交付形态是 issue，正文附带已验证的 patch：`git format-patch -1 --stdout` 的全文放在 `<details>` 里。
- 开工前必读：`AGENTS.md`、`LESSONS.md`、`docs/code-standards.md`、`docs/subsystems/README.md`，以及要改的子系统的设计页。
- 改了行为，要同步改 `docs/subsystems/<子系统>.md` 里对应的一行（C5 改了 gateway-routing.md，C6 改了 library.md）。
- 内建订阅凡是已经迁到社区插件的（见 AGENTS.md 表格），先判断用户是否已迁移。只修内建代码，对已迁移的用户不生效。

## 3. Issue 格式（已被维护者接受 20+ 次，10-14/15 两波 14 帖全数走此格式）

- 标题：`子系统: 一行现象`，例如 `mcpauth: …时，MCP 登录用首项注册而失败`。
- 正文五段：**现象**、**最小复现**（附红测试的失败输出）、**根因**（文件 + 函数 + 关键几行）、**修法**、**验证**。验证用表格写（**行间禁空行**，否则 GitHub 不渲染），最后单列一条 **没跑什么**。
- 坦白影响面。比如 C7 写明了「没找到会这样排序的公开服务器」。说清楚哪些没验证，反而更容易被信任和合入。
- 改了现有断言要点名，并说明可能被维护者否掉的条件（C2 和 C5 都这样写了）。
- 发帖组装时防两处事故：草稿正文与「补丁与分支」section 不要重复嵌同一份 patch（发 #2198 时组装脚本去重过一次）；发完做远程核验（拉回 body 查表格断裂/details/围栏配对/UTF-8）。

## 4. 找缺陷：有效的套路

按命中率从高到低：

1. **兄弟路径不一致**。同一个概念有两套判定，一处更新了，另一处没更新。
   - C1：`claudeVersion` 只认 opus/sonnet/haiku，`claudeLine` 已经加上了 fable/mythos。
   - C6：模型配置按 `keyAt` 带了 LAN key，MCP 中转的 `through()` 没带。
   - C4：`vendorDot` 的正则和 catalog 里的 `bedrockGeos` 不一致。
   - 做法：`rg` 出一个判定函数的所有调用方和同义实现，逐个对比集合。
2. **规则作用域过宽**。某条规则的理由只适用于一个子集，却作用在了全集上。C2 中，「4.6 没有 xhigh」被套到了所有 adaptive-only 模型上。
3. **厂商默认值变了**。拿官方文档逐字段核对：哪些模型 display 默认是 omitted，哪些参数会被拒、哪些支持 effort。
4. **规范里本没有顺序的列表被当成偏好**。C7 中，RFC 8414 的 `*_supported` 列表本来没有偏好顺序，代码却取了首项。
5. **测试读到了宿主环境**。C3 中测试读了 NO_PROXY、NODE_USE_ENV_PROXY，在开发机上会无故变红。
6. **审最近的 feature commit（提交审计车道，40-60 个）**。读 `git log --oneline -40 upstream/main`（量大可到 -60），挑新加的逻辑，查边界和兄弟场景。commit message 里的「Not changed, found on the way」常常就是线索。**10-14/15 实证为最高产车道**（L4 审 22 提交挖出 #2167、X1 审 43 提交挖出 #2251），两个实践：①已审清单显式传给下一路，勿重复挖；②维护者高密度自修区（gateway 两日 152 commits 全带 break-check）零帖是正确产出，静态横查扫尽后就该换执行面实测或换车道。
7. **新报告兄弟面挖掘（10-15 实证第二高产）**。昨夜新进的 issue 报告是精确线索源：读全文，挖**同函数/同家族没被报的面**。#2250（#2233 的兄弟函数只修了 codexFilesIn）、#2255（#2246 同递归只消费外层）、#2256（#2242 Origin:null 门的同族 `*.localhost` 豁免）全是这么来的。挖到的面要过六问（本体可能是声明过的豁免），不硬凑。
8. **执行面实测**。静态横查扫尽后（每个候选都能在代码或 commit message 找到已声明理由时），换构造对抗性流量实测：截断的 SSE 终止事件、同 call_id 双份回答（vercel/ai#13307 的 approval 重放形状）、format 拒绝循环的 body 漂移。#2221/#2222 就是这么落地的——静态横查把这两个都标成"无证据"，构造出重放序列后才落地。
9. **在途清单显式传路（2026-10-16）**。派单前汇总同账号近 12h 的 claim/交付评论与已推分支，作为「我方在途清单」写进每路任务书——公司机与本机同账号跑并行车道、同轮双车道也共用账号，无法凭身份区分归属。**线索（消费面/兄弟面指向）与该单的接单权绑定同一路**。hunt31 B/C 同轮撞单 #2492 样本：B 完成等效修复后发现 C 已认领交付，不重复交付、公开自评以先发为准 + 点名对方补丁缺口 + 自家分支留作备份——撞车零成本处置。

产出低的区域（已经审过，没有收获）：`internal/edit`、价格分档 `catalog.Price`、Gemini thinkingLevel 映射、DNS rebinding 的 `ownHost`、DeepSeek reasoning_content、Codex 标题 incomplete、循环检测后的重问。这些代码测试很密，没必要重复审。

## 5. 验证：一次做对

- **先红后绿**。在旧代码上跑出失败，失败信息要能说明根因；修完转绿。复核方法：`git stash -- <被修文件>`，再跑一次确认是红的，然后 `stash pop`。
- **走完整服务链路**。用 `httptest` 起假厂商服务，`New().Handler()` 或者 `lanGuard(New().Handler())`。
  - 假厂商要回 **SSE**：magpie 向上游是流式请求，假服务只回 JSON 会得到 502。
  - 测试辅助函数 `post` 每次调用都会新建 gateway。要验证跨请求的状态（比如 unfit 记忆），就共用一个 Handler。
- **假服务要按真实服务的方式拒绝**。C7 的初版 fake 照单全收 `private_key_jwt`，测试红的原因是错的。改成按 RFC 7591 回 `invalid_client_metadata` 之后，测试才因为正确的原因变红。
- **Mac 侧隔离实例端到端（2026-10-14 增补，#1916 复验沉淀）**：安装版二进制可用环境变量起隔离网关——`XDG_CONFIG_HOME=<dir> MAGPIE_ADDR=127.0.0.1:<port> magpie web --gateway --no-open`。三个坑：配置目录是 `$XDG_CONFIG_HOME/magpie` **子目录**；`--addr` 只管 web UI，网关端口必须 `MAGPIE_ADDR`；localhost 网关免鉴权。配合本地假厂商即可验证真实 HTTP 服务链路（单元测试覆盖不到的接线）。假厂商可以装"陷阱"：收到未修复形状就回上游原文错误——经真实网关打到它返回 200，即证明转换/修补在链路里发生了。
- **回归测试引用新符号时的红（2026-10-14 增补）**：修复提交的测试若引用该提交才引入的常量/函数，纯测试文件在旧树上编译不过——在旧树加一个只含这些符号、零行为的桥接 `_test.go`，即可复现断言级红（#2017 复验：`autoResetAny`/`autoResetWeek` 两常量）。
- **消融基线必须显式解析为修复提交的父（2026-10-15 增补）**：抽查已提交的修复时，`git checkout HEAD~1 -- <产品文件>` 在多提交分支上会踩空——HEAD~1 恰好是修复提交本身时就变成"修复对照修复"，永远绿（审 #2255 时踩过一次）。基线写 `<修复SHA>~1` 或直接用修复前的 SHA；核对方式：消融跑红时，失败断言应与 issue/报告声称的失败信息同形。
- **沙盒 HOME**：Windows 新沙盒统一为 `E:\magpie-sandboxes\<任务>-<UUID>`，不能继续在 E 盘根目录散建；运行前核对没有 Git 祖先，进程级重定向 HOME/USERPROFILE/APPDATA/LOCALAPPDATA/TEMP/TMP/XDG，固定既有 Go 缓存。证据保存到 hub 的 `docs\issues\<任务>`（2026-10-16 前 在 `magpie-hunt-issues\<任务>`）；旧目录不移动。完整规则见 [Windows 规范](08-Windows工作区与沙盒规范.md)。下面 `/tmp/sbx.sh` 是历史 Unix 验证示例，不用于 Windows：
  ```sh
  /tmp/sbx.sh test -tags nogui -count=1 -run 'TestX' ./internal/<pkg>/
  /tmp/sbx.sh test -tags nogui -count=1 ./...
  ```
- **消融必须摘全部产品文件（2026-10-16，三度再现）**：修复跨多文件时只摘部分会 build failed ≠ 断言红；按 `git show <fix> --name-only` 列出的全部产品文件（测试文件除外）一并摘回父版本，新测试保留；**消融验证通过后才清场**（主线程两次把清场排在消融前，靠分支 ref 无损重来）。
- **go test 不需要 HOME 重定向（hunt28-D 实证）**：GOTOOLCHAIN=auto 叠加进程级 HOME 重定向会把工具链下载挪进沙盒且断流；仓内测试自带 testenv 沙盒，去掉 HOME 重定向即正常——只有跑真实 magpie 二进制才需要重定向。
- **三平台 vet 和 build**（linux 必须带 nogui）：
  ```sh
  gofmt -l internal/
  go vet ./... && GOOS=linux go vet -tags nogui ./... && GOOS=windows go vet ./...
  go build -o /dev/null . && GOOS=linux go build -tags nogui -o /dev/null . && GOOS=windows go build -o /dev/null .
  ```
- **已知的环境红**，忽略即可，但要在 issue 里写明：`TestOffline`（本机网络），`trayimage_darwin.go` 的 cgo `-Wenum-conversion` 警告。
- WSL 相关的问题在 mac 上也能测：用 `agent.FakeWSL(probes, roots)`。probe 里写 `route:default via 172.20.0.1 dev eth0` 和 `net:nat`，就能模拟 NAT 网络。

## 6. Git 与 GitHub 操作

- **固定 pr 目录复用**：Windows 第 N 路独占 hub 内的 `magpie-prN` 独立 clone，先核对状态和注册关系、在该 clone 单独 fetch，再 `switch -c` 创建未占用的分支。新建/收口按 [Windows 规范](08-Windows工作区与沙盒规范.md)，不使用 `checkout -B` 覆盖旧分支、不清理未跟踪文件、不在 E 盘根目录新建代码工作树。不要在主 clone 上直接改，那里可能有别的会话的分支。
- 提交：作者用已配置的 ggbdpq，不改 identity。message 用 `git commit -F - <<'EOF'` 写，格式参照仓内风格：`子系统: 一句话`，正文分 What changed 和 Run 两部分，末尾加 trailer `Co-authored-by: factory-droid[bot] <138933559+factory-droid[bot]@users.noreply.github.com>`。
- gh 命令遇到 401，就加 `env -u GITHUB_TOKEN gh …`。推 fork 只能走 `ssh://git@ssh.github.com:443/`：OAuth 令牌缺 workflow scope，SSH 22 端口经代理会断。
- **查重三步**：`gh issue list --state all --search "<关键词>"`，然后用 `gh pr list --search "<号>"` 查 open PR 的正文引用，最后在**发帖前一刻**重新 `git fetch upstream`。维护者可能在 1 小时内自己修掉。
- 巡检时看 issue 评论的时间戳，不能只看 fetch 增量：GitHub 上可见的 push 时间会晚于 commit date。
- 小坑：`git rev-parse` 一次传多个参数会出错，改成循环逐个解析；worktree 清理必须先确认注册关系、无已有修改且得到授权，不能靠 `--force` 绕过保护；多个 patch 能否同时打，用 `git apply --check` 验证。

## 8. 并行狩猎提示词（1 个主线程 + 最多 3 个子智能体）

> **Mac 变体（2026-10-15 起，已四波实证）**：Mac 侧不用 prN clone，用 /tmp 分离 worktree——`git -C <主clone> worktree add -b huntNN/<lane> /tmp/magpie-huntNN-<lane> upstream/main`，每路独占一个，改动提交在各自分支，交付后推 fork（分支名带车道与 slug：`huntNN-x2-<slug>`）。四路并发时把「已发帖清单 + 已排除候选及证据」显式写进每路任务书（防重复挖与重复发）；零帖是合法产出（gateway 高密度自修区曾两日 152 commits 全带 break-check）。收口：worktree 核对干净后 remove，分支保留在主 clone。Windows 侧仍按下方 prN 流程。
>
> 你是 yetone/magpie 的缺陷猎手主线程，Windows 工作区是 `E:\cc\guahub\fork\magpie-hub`。先读 `docs/08-Windows工作区与沙盒规范.md`、`docs/05-缺陷狩猎经验.md`，以及被分配 clone 下的 AGENTS.md、LESSONS.md、docs/code-standards.md、docs/subsystems/README.md。
>
> **主线程**：按 Windows 规范在明确的绝对仓库路径 fetch，确认上游 SHA；用 gh 列出近 7 天的 issue、PR 和 commit，作为查重基线。最多派出 3 个子智能体，分别独占现有 pr1/2/3 clone；每个 clone 单独 fetch，再从自己的 upstream/main 创建未占用的 `hunt/<区>-<slug>` 分支，不增建散落目录：
> - A：gateway 协议翻译（anthropic/chat/responses/gemini、effort、thinking、工具）；
> - B：provider、accounts、usage、catalog（计费、额度、模型识别正则）；
> - C：agent 配置写入、library、容器与安全边界（lan/cors/mcp/mcpauth/sessions/gui API）。
>
> **子智能体**：用「兄弟路径不一致、规则作用域过宽、厂商默认值、规范顺序、环境泄漏」五个套路找缺陷，并对照官方文档。每个缺陷都必须有修前红测试（走 httptest 全链路，沙盒 HOME），通过三平台 vet/build 和全量测试，然后提交并导出 format-patch，按五段格式写中文 issue 草稿到 `docs/issues/`。每个子智能体最多交 2 个；拿不准的写成「疑点」，不要硬凑。不发帖，不推送，不碰别区的文件。
>
> **主线程收口**：逐个复核红测试，查重，重新 fetch，确认 patch 能 apply；然后用 `env -u GITHUB_TOKEN gh issue create` 发帖，最后汇报一张表（编号、现象、影响面、验证、没跑什么）。
