I walked the whole cycle source down in code and ran an isomorphic experiment locally; here is what the ~86 s burst can and cannot be.

**1. The host itself has no idle work.** `internal/plugin/host.js` is purely stdin-driven: its only timers are request-scoped (`Late` timeouts at line 363, gateway TTLs, the renew lock's backoff at 2404) — nothing periodic. `pi.js` has none either. With `preset: all` (your plugins.yml), every built-in plugin is a Go package under `plugins/` (`plugins/all/all.go`); none of them runs in the host process. So an idle `magpie-bun.exe` sitting at exactly 0% between bursts is what the code predicts — something has to ask it.

**2. Magpie has no timer anywhere near 86 s.** I enumerated every periodic task in the repo (`time.NewTicker`/`time.After`/`time.Tick`, every `setInterval` in the webview assets, every duration constant): the full grid is 1 s / 2 s / 5 s / 10 s / 15 s / 20 s / 30 s / 60 s / 2 m / 3 m / 5 m / 45 m / 1 h / 6 h. Nothing lands in 74–92 s, and none of the standing timers touches the host. The only foreground-gated timer in the page is the 15 s drift check (`app.js:24088`), and it only compares agent config files locally. `KeepUpdated`'s 30 s-then-hourly look (`plugin/updates.go`) explains your 13:56:04 host restart (12:55:26 start + 1 h + the install), but it is a different face than the cycle.

**3. The one chain that does reach the host periodically is visibility-driven.** The page re-reads the state when the window becomes visible or focused (`app.js:24084`, `24158`: `visibilitychange`/`focus` → `loadBack()` → `load()` → `GET /api/state`). `GET /api/state` calls `provider.FetchNewSoon` every time (`gui/api.go:1052`, throttled to one per 15 s, `models.go:503`), which runs `FetchNew`; an account whose vendor list is missing or last failed is fetched again once `newFetchRetry` (exactly 1 minute, `models.go:492`) has passed. A **plugin** account's fetch is `plugin.Providers` (`provider/plugins.go:502`) — the host's `providers` RPC, which runs every plugin's models hook in parallel, each bounded by `listWait` = 20 s (`host.go:1059`). A vendor that is slow or unreachable (proxy needed, reset connections) burns seconds of JS + TLS retries there; two hooks in parallel are your 100–200% of one core, and 8–11 s fits under the 20 s cap. The numbers line up: 60 s retry + the 15 s throttle + phase jitter puts successive bursts at roughly 74–92 s, mean ≈ 86 s. Minimized, a WebView2 page stops getting `visibilitychange`/`focus`, the chain goes quiet — and your two stray bursts at 14:46:52/14:47:11 are what a brief re-visibility (taskbar/alt-tab while you were sampling) would produce.

**4. What I measured locally.** I built this commit on macOS and let it make the same isomorphic state as yours (the Grok and ZCode sign-ins moved onto `@magpie-community/opencode-grok-auth` / `-zcode-auth`, one host process running `host-<sha>.js`):

| Check | Result |
|---|---|
| Host idle, window up, 300 s sampled at 1 Hz | 0% every second (one 1% tick) |
| Hide + re-show the window (fires `visibilitychange`/`focus`) | no burst — both vendors answered, no account was due, `FetchNew` had nothing to ask |
| `magpie provider refresh grok` (forces the providers RPC) | 1.0 s wall, host peak 1% — the RPC is cheap when the vendor answers |

So the burst needs both halves you have and my box doesn't: a vendor whose list fetch fails or stalls, and an account that is therefore due. The part I could not pin from code is what re-fires `focus`/`visibilitychange` roughly every 86 s while the window rests in the foreground on Windows; I did not have a Windows machine to capture that, and everything above the arrow is code-verified while this one link is inference.

**5. Where I would fix it, and how to confirm.** Two cheap cuts, either alone should flatten the cycle: (a) `provider/plugins.go` — a plugin account's `a.fetch` re-runs the whole `plugin.Providers` listing every time; a short-TTL cache (30–60 s), or asking only the plugin that owns the due account, removes the repeated host work; (b) `models.go` — give `newFetchRetry` a backoff for accounts that keep failing instead of a flat 60 s. To confirm on your machine, the decisive capture is which RPC arrives at the host each burst: a temporary log line in `host.js`'s loop (`method` + duration, `host.js:2912`) or `host.go`'s `dispatch` (`host.go:1164`) would name it within one cycle — and if it turns out to be something other than `providers`, that log will say so directly.
