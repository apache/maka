Found it — the 100K was a cap that `@magpie-community/opencode-workbuddy-auth` 0.2.7 itself reported for this model, and 0.2.8 removed it. Nothing in magpie's override chain was stuck: the whole story played out in [plugins#561](https://github.com/magpie-community/plugins/issues/561), filed and resolved that same evening.

**Where the 100000 came from (your Q1).** Not models.dev, not an alias fallback, and not the unknown-model default — models.dev and WorkBuddy's own config both say 1000000, exactly as you checked. It was a deliberate cap in plugin 0.2.7, added as a guard after #561 reported copilot.tencent.com refusing this model above 100k ("prompt is too long: 100001 tokens > 100000 maximum"). Yetone later confirmed there: "You're right, the cap was wrong. It came from one error text I could not check myself", and 0.2.8 removes it — the vendor's own refusal now names 1,048,576 as the ceiling. Your 541K requests returning 200 while the list said 100K is what a metadata-only cap looks like: it changed the window magpie tells clients (so clients compact at 100k) and never blocked anything at the gateway. Someone else's same-day measurement in #561 shows the same shape: 153k and 203k-token prompts answered 200 while the list said 100k.

**Why the provider-level "context window = 1m" did not apply (your Q2).** That is magpie's documented resolution order, not a broken override. `Provider.WindowOf` (internal/provider/models.go) resolves a model's window as: a value set on one model wins outright, larger or not; a value set on the whole provider is deliberately kept within the model's own window where the provider states it (#2112 — the provider-level field is a spend-less knob, and telling an agent a window above what the vendor accepts is the over-ask 400 case #2112 fixed); models.dev's value never caps what you set, but the plugin's live list is the provider's own word, and it does cap. So while 0.2.7 reported 100000, your 1m landed as min(1m, 100000) = 100000 — and `maxTokens` read 100000 for the same reason, since a published reply limit is kept within the window (`OutputWithin`). Your own update is the mechanism working: once 0.2.8 restored 1000000, the route picked up exactly your 1m / 128k. The 10-26 → 10-31 change was the plugin moving to 0.2.7 in between (it shipped that evening; your 22:52:06 line shows the follow-up 0.2.7 → 0.2.8 raise undoing it), not any magpie release — no magpie setting or release changed in that window, which is also why 10-26 could still write `contextWindow: 1000000`. Hand edits to cordis.patch.yml are rewritten from the effective values on every sync by design, which is why this could only be fixed at the source.

**Per-model override (your Q3).** The same provider → Advanced → Context window field already takes per-model entries inline: a bare value is the default for every model of the provider, and `model-id=value` overrides one, e.g. `272k, deepseek-v4.1-flash=1m` — the id spelled exactly as the provider lists it (a suffix like `:1017` only belongs there when that exact spelling is a listed id). Same thing from the CLI: `magpie model spec workbuddy/deepseek-v4.1-flash --context 1m`. A model's own value beats everything including the vendor's word — that is the supported way to rise above it. `magpie model spec workbuddy/deepseek-v4.1-flash` also tells you where each value now in force comes from (yours / the provider's / the vendor's list / models.dev). The per-model row in "Names & reasoning levels" showing the source (`Auto (1M)` / `Provider (272K)`) is the GUI piece tracked in #2326 / #3014.

**Your last two questions.** (a) Yes — a provider-level window is kept within the model's own window where the provider states it (min), by design, for the #2112 reason; going above a vendor's word is what the per-model setting is for. (b) The 20:42 drop was neither a fresh vendor metadata pull nor an alias re-resolution — it was 0.2.7's cap arriving on your machine; the list changes later that evening (`auto/deepseek-v4.1-flash` disappearing) came with the 0.2.8 rollout, not with the cap.

No core change is needed here: the chain did what it documents, and loosening the provider-level clamp would reintroduce the over-ask 400s #2112 exists for. If the plugin ever reports a wrong word for a model again, `magpie model spec --context` pins that model above any vendor word until the source is fixed.
