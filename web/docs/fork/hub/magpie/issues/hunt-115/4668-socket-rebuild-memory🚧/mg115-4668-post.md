Thanks for the report — the socket numbers you pulled out of `app.log` made this one easy to chase.

**What was rebuilding what**

Every continued turn names the reply before it (`previous_response_id`) and sends only what came after, so magpie keeps the conversation for the socket and builds the whole body back — that is what "sent on as whole requests" counts, and with your tool outputs the body is tens of MB every turn. Three parts of that path held far more than they had to, and three commits on main since your build (0.1.2477) fix them; they are likely most of what you saw:

- `a51776f9c` — the rebuilt body went through `json.Marshal` twice, about five copies of a long conversation per turn.
- `ec0a11d47` — each kept reply held its input as views into the `response.create` frame it was decoded from, so every reply a socket kept pinned that whole frame: ~39 MB of live heap on a long session, for the socket's life. This is your high-water mark that never came back — the bytes were live, so no collection could take them, and the gateway's idle release (`debug.FreeOSMemory` after 30 s of nothing in flight) had nothing freed to hand to the OS.
- `ed5872d18` — the same pinning on the HTTP path's `previous_response_id`.

**What this patch adds**

One more body-sized copy survived all three: after the turn rebuilt the body and put it in the request, `readRequestBody` read it out of that request again, byte by byte, into a new slice — a second copy of tens of MB on every turn. The body is already whole in memory and sent as it is (a turn carries no `Content-Encoding`), so `readRequestBody` now takes a whole-in-memory body as it is instead of reading it out; the socket's turns get that, and so does the request `codexOwnOffMagpie` builds for a thread Codex started on magpie — the one sibling with the same shape (the other in-memory bodies in the gateway go straight to a provider transport and were never re-read). The socket's ended line also says the longest turn's body now, so the socket that set a peak shows up in the line you were reading.

**On the plugin host**

The 1.5–2.6 GB of `magpie-bun` is not covered here. When any gateway JS middleware is on, the whole body is handed to each middleware run as a JS string (`run.Request`), one copy inside the JavaScriptCore heap per turn — your plugins not touching Codex requests doesn't keep the body from reaching them. Whether that hand-over can be made cheaper, or skipped for bodies no middleware wants (your question 2), is a design call I'd rather leave to yetone. Your question 3 is already answered on main for the heap magpie can free: the gateway hands memory back after 30 s idle — what it couldn't was the pinned live heap above, which the three commits release.
