你好！只看截图里的 "41% CPU" 还没法定案——magpie 空闲时实测基本是 0%（我们刚在干净环境里采样验证过），所以 41% 大概率是某条特定路径被你的使用状态触发了。我们在 issue 区已经钉了几条类似路径，你可以花一分钟对号入座：

**先看两个最容易中的：**

1. **版本旧 + 开了 Privacy 脱敏**：旧版本对一个很长的会话每个请求都会全量重扫一遍（一个 555KB 的请求体能吃掉近 2 分钟的 CPU）。这个已经修了（v0.1.2622，560KB 从分钟级降到 0.2 秒）。自查：设置里看下版本号；如果 Privacy（脱敏）开着且版本低于 0.1.2622，先升级试试——大概率直接解决。

2. **Codex 用户 + 每 10 分钟一阵的高峰**：magpie 会定期（每 10 分钟，首次在启动 2 分钟后）整理 Codex 的 session 文件，`~/.codex` 很大的时候每次整理能高 CPU 好一阵，而且**最小化窗口也不会停**。自查：任务管理器里看曲线是不是"每 10 分钟一阵"；再看看 `C:\Users\<你>\.codex`（或 `~/.codex`）有多大。

**如果是"持续平线"而不是一阵一阵：**

3. **用量/日志积累**：历史记录文件越大，托盘用量卡片和统计页刷新越贵，而且每次请求都可能扫一遍近 30 天的历史。自查：看看 magpie 配置目录里 `usage.jsonl` 和 `routing` 文件夹的大小（Windows 在 `%APPDATA%\magpie`，macOS/Linux 在 `~/.config/magpie`）；试着把托盘的用量显示关掉一分钟，看 CPU 有没有回落。

**再帮我确认几件事（都很快）：**

- **版本号**（`magpie -v` 或设置→关于）和**系统**（Windows/macOS/Linux？）
- **41% 的是哪个进程**：任务管理器"详细信息"页里有 `magpie.exe`、`magpie-bun.exe`（插件宿主）和 WebView2 渲染进程好几个，PID 37060 是哪个？
- **41% 是一直稳定，还是一阵一阵？** 鼠标悬在曲线上看 1 分钟就能看出来；另外试试**最小化窗口 1 分钟**，看会不会回落（有一条已知路径是窗口在前台才触发的）。
- 高 CPU 的时候**有没有 agent 正在跑**？

如果方便的话，跑一下这个命令把生成的文件发我，它能直接告诉我们 CPU 时间花在哪（这是 magpie 内置的性能采样）：

```
magpie cpu --seconds 60
```

有这几样东西基本就能定位到具体原因了，谢谢配合！
