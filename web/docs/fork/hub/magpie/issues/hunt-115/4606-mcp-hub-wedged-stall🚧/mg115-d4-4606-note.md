## 根因（消费链）

`tools/call` → `hubMCPCall`（gateway/hub_mcp.go）→ 每 call 调 `hubTools` → `theHub.Tools`（library/mcp_hub.go）逐 upstream 开 goroutine `backendOf(s).tools(ctx)` → `wg.Wait()` 等全部 → `hubNamed` 后按名字找工具。wedged upstream 永远列不出工具（`b.listed` 恒 false），所以它的 goroutine 每次 reconcile 都重新 `connect` → `start` → `dialHub`（stdioStep 30s / remoteStep 60s，Background ctx）——**每次 ask 重新付费**，`wg.Wait()` 把健康上游的 listing 和所有 tools/call 一起拖过客户端超时（30s 常见 < magpie 内部 40/50s 预算）。§15 三硬规则命中第②条：可选聚合的慢与败粘连核心转发。

## 修法（两片独立、同瓶颈口收口）

1. gateway：每 agent 最近一次 listing 的命名工具表（`hubTables`）留存；`tools/call` 先查表命中即跑，未命中才同步 reconcile（结果回存）。`tools/list` 语义不动（冷启动上游仍在首个 listing 的预算内等它——`hubListWait=40s` 的设计意图），表在每次 listing/reconcile 时刷新。
2. library：`backend` 增加连续失败计数 `fails` + `retryAt`；dial 失败后按 `hubRetryWait`（1s 起倍增、封顶 1min）停泊，停泊期内 ask 立即拿到 `b.err`，窗口过了才再拨一次；成功清零。`connect` 只有 `backend.tools`/`backend.call` 两个调用方（rg 全查），call 侧 wedged 上游自己的工具也变成快速失败并报名。

修法五问：Q1 认知层（last-known-good 表 + 失败停泊状态，动作只消费）；Q2 收口（`hubTools` 是 tools/list+tools/call 唯一入口，`connect` 是全部 dial 入口）；Q3 fail-closed 带名（停泊即"左出、命名原因"，沿用接口既有契约"a server that couldn't be reached by ctx's end is left out, and listed once it has"）；Q4 实问（表就是服务器实际列出的）；Q5 seam（gateway 用既有 `fakeHub` 加 `toolsFunc` 钩子；library 用真子进程 `fakeStdio("exit")` + `MAGPIE_FAKE_MCP_LOG` 数启动）。

## 边界与不确定项
