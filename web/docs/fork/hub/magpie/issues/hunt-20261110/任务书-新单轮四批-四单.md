## 四单分配

### 车道 6：#5969（Claude Desktop 重启后默认 autoCompactWindow=272000 重新写入，覆盖用户整窗设置）
- 档1/2 边缘：用户已在全局 settings.json 声明大窗口+按窗口百分比自动压缩，magpie/Claude Desktop 重启后顶层被重写回 272000 默认——**用户自设值被默认覆盖**（10 §11 硬规正中）。
- 诊断先行：写入者是 magpie 还是 Claude Desktop 自身（同 #5782 的归属取证法）；magpie 侧修法=尊重用户已声明值（有自设值在场不写默认），归属在 Claude Desktop 则判定帖。
- 报告者 Windows+非 Claude 模型路由；fixture 带「用户自设值在场」。

### 车道 7：#5935（Windows 开机自启偶发连官方账号额度而非用户 API 供应商——计费错账号）
- 档2 计费归属：自启竞速下启动早期请求走了官方额度。报告者标注「偶发」——启动时序竞速形态，fixture 驱动启动序复现（不靠真机重试碰运气）。
- 诊断先行：启动早期哪条链路会落到官方账号（默认 pick/默认 provider 未就绪时的 fallback？）；修法=启动就绪门或默认路由显式化，以读源码判断为准；「偶发」的竞速窗口要在帖内讲清。

### 车道 8：#5895（已删除的 WorkBuddy 账号仍被 Routing 页列出并计 available）
- 档2 账号面：插件账号删除后 Routing › Accounts and keys 仍列出且算 available——删除传播缺口。
- 方向：删除事件→路由可见名单的传播链（rg 删除写点→读取点）；修前红=删除后仍 available 的 fixture。

### 车道 9：#5876（Kimi Code 7d 窗口用尽后每请求 400 "text content is empty"——额度/失败分类）
- 档2：routing=weight 组内 Kimi Code 池 7d 100% 用尽后，落在 kimi-code-cn/k3.1-pro 的每请求 400 "text content is empty"——上游对额度用尽的答复形状未被分类（应 rest/failover 而非反复撞）。
- 方向：失败分类族（#5111/#5006/#393 先例）——400 empty content 与 Kimi 额度用尽的关联实证（fixture 对齐报告者 quota 7d 100% 状态）；修=词表/分类进 retryable/failWords 相应档，注意 #5692 的 opt-in 边界不越。
