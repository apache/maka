### magpie version

0.1.3536 (hung while being replaced by 0.1.3538); same signature earlier on 0.1.3005 (→ 0.1.3007)

### Where

GUI (desktop app serving the gateway on `127.0.0.1:3425`)

### OS

Windows 11 build 26300 (10.0.26300), WebView2 Runtime 157.0.4341.42

### Steps to reproduce

1. Run the desktop app with auto-update on, so it serves the local gateway (`127.0.0.1:3425`) for coding agents (OpenCode, Hermes).
2. Leave it running while new builds arrive. Here it self-updated 356 times between 10-31 and 11-10.
3. Now and then, when an update replaces the running app, the old process doesn't exit. Windows reports it as "not responding" and the gateway is down until the user kills the process in Task Manager.

Not reproducible on demand. It happened 2 times in ~356 updates in the logs I still have, plus a third Windows hang record from before that.

### What happened, and what you expected

When an update hands over, the old app (by then renamed `magpie-windows-amd64.exe.old*`) begins to exit but never finishes. It keeps `127.0.0.1:3425` bound and stops answering. The new build can't take over:

```
2026/11/10 15:54:52 magpie 0.1.3538 started (app, pid 51232, windows/amd64)
2026/11/10 15:54:53 gateway: http://127.0.0.1:3425 is taken but doesn't answer as magpie yet; this magpie serves the gateway once it is free
2026/11/10 15:54:53 magpie: failed to notify first instance: unable to notify other instance
```

The gateway stays down until the old process is killed by hand:

| date (UTC+8) | hung process (Windows Application Hang / WER `AppHangB1`) | gateway down |
|---|---|---|
| 2026-10-16 22:47 | `magpie-windows-amd64.exe.old-4` 0.1.1270 | unknown (log already rotated) |
| 2026-11-05 10:56 → 11:26 | `magpie-windows-amd64.exe.old` 0.1.3005 | ~30 min |
| 2026-11-10 15:54 → 16:02 | `magpie-windows-amd64.exe.old-2` 0.1.3536 | ~8 min |

Expected: the old process exits, or at least releases the port, so the new build takes over within seconds. If the exit can stall, a watchdog in the new instance or the updater should kill the old pid after a timeout.

The gateway goroutines (`gateway.(*tlsListener).Accept`, `net/http.(*Server).Serve`) are still parked, which is why `:3425` stays bound.

My reading (unverified): while the main thread runs `ExitProcess`, a Win32/WebView2 callback, most likely from the Wails v3 beta.24 window or the asset server (goroutine 17618 is blocked in `InvokeSync` on the main thread), fires on that thread and calls into Go. The Go runtime throws, and the process is left half-dead. Possible fixes:

- Tear down the Wails app/WebView2 (and close the gateway listener) before `os.Exit` on the update/handover path.
- Close `:3425` first in the handover, so a stuck exit can't keep the gateway down.
- Have the new instance (it already sees "taken but doesn't answer") kill the `.old*` pid after N seconds.
