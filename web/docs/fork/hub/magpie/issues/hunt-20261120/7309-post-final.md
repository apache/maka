**What the fix does** (theirs), for both cases in the report and the follow-up:

- **Case 1 — a slow health answer kills magpie's own bili.** `biliServer` now carries a `done` channel closed once the bili it started has exited. A failed health check no longer cancels a bili that is still running: a big session store's synchronous save holds bili's health check for seconds, and ending it there drops every request going through it (the old code cancelled on the second missed check). bili's own watchdog (`src/event-loop-watchdog.ts`) ends a truly wedged one after five minutes and the next tick starts a new one; the startup wait keeps a bili that is still opening the store instead of cancelling it at `biliWait`.
- **Case 2 — a second start on a port another bili holds.** `biliHeld` (a dial to `biliOrigin`) says something already listens there, answering or not; `biliServe` refuses to start a second bili in that case with a named error, instead of loading the same session store only to fail to listen.
