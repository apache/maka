## 仓库隔离规则（必读）

| 远端 | 地址 | 用途 |
| --- | --- | --- |
| upstream | router-for-me/CLIProxyAPI | 项目本体，PR 目标 |
| origin | ggbdpq/CLIProxyAPI | 我的 fork，PR 分支推这里 |

- **分支策略**：本地 `main` 只跟踪 upstream/main（`git fetch upstream && git merge --ff-only upstream/main`）；`custom` 是个人定制分支（课程文档、数据管理面板等），**永不合并进任何 PR 分支**。
- **每个 PR**：从 `upstream/dev` 切新分支（不是 main），只 `git add <指定文件>`（不用 `git add -A`），防止 untracked 的 custom 产物（如 `custom-addon/`）混入。分支命名遵 [12 §命名规范](../../../handbook/12-通用纪律与执行声明.md)：`fix/<单号>-<slug>`（type 按性质），subject `fix(<scope>): <summary> (#N)`。
- `gh` CLI 两平台均已认证（mac：`/opt/homebrew/bin/gh` 直接用；Windows 完整路径见 [02-本机环境坑](02-本机环境坑.md)）：API 读写全走 gh；`git credential fill` 不用（Windows 沙箱会卡死）；API 写操作 payload 先写 body 文件再提交。open PR 列表接口按更新时间只回前 100 条，老 PR 会掉出列表，在途单逐条 `pulls/{n}` 核实 state（10-01 实测：4 条 9 月 PR 从列表消失，逐条查证仍 open）。
- 认领方式：该项目无 take 机器人，惯例是在 issue 下评论实现方案声明意图（HTTP 201 即成功）。

> 开工/解冲突/定性失败前，先扫跨仓失败模式目录 [`handbook/05-失败模式对照.md`](../../../handbook/05-失败模式对照.md)（M1-M13；本仓高频：M12 无冲突语义漂移、M7 上游同题取代、M13 镜像源漂移）。

- **PR base 一律开到 `upstream/dev`**（不是 main！）。项目有 bot 自动把开到 main 的 PR 改 base 到 dev，且 dev 常态领先 main 十几个提交——开错 base 会立刻撞脏合并状态。分支从 `upstream/dev` 切。翻译器目录命名是「目录名=响应目标」：`openai/claude/` 是 Claude 客户端↔OpenAI 上游，`claude/openai/` 才是 OpenAI 客户端↔Claude 上游。

## translator 禁手

AGENTS.md 有 translator 条款：只动 `internal/translator/` 的任务，无 upstream 写权限时的正规姿势是「开 issue 写清目标/理由/实现代码，然后**停手**」，维护者团队自己改（`pr-path-guard.yml` 会机械拦截 translator-only PR，build 再绿也红）。在他人 issue 下评论方案后直接开 PR 越过了规则字面——PR 可以挂出去当「可审的实现提案」（mergeable_state=unstable 说明该 guard 非必需 check，维护者仍可合并），但接受与否完全看维护者，且 PR 区要主动说明红叉是 path-guard 预期行为（PR-001/PR-002 实测，2026-09-03 复盘更正；#5432 于 2026-09-21 被合并，该路径首次走通）。

## 接单开场固定流程

1. `git fetch upstream dev && git fetch origin`，同步本地 main（ff-only）。
2. 查在途 PR 是否已合并（merged→移出台账"在途"区）。
3. 扫新评论/修复建议：**三个端点都要扫**——`issues/{n}/comments` + `pulls/{n}/comments` + `pulls/{n}/reviews`（行内 review 评论与 reviews 是另外两个端点，只扫 issue 级会漏，维护Ⅵ 实录）。
4. 查 mergeable_state 是否 dirty（撞了 dev 的新提交就 rebase；文件交集清单触发语义复查，mergeable clean≠语义安全，M12）。
5. 查是否被别人的 PR 解决（search 同关键词的 open PR，正文含 Fixes #N = 占坑；上游在 dev 直接实现同题不会通知作者，M7）。
6. 以上清完再开新单；base 一律 `upstream/dev`。

优先级：review 意见 > CI 失败 > rebase > 新单。接单四道闸：未认领、≤200 行、本机可验证、知识有交集。
