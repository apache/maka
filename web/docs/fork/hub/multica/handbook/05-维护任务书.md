逐 PR：落后 rebase，冲突按语义解；审查意见逐条处置——维护者给二选一路线时先做裁决再动手（依据=issue 原文事实+源码实测，先例：#9233 走窄口径 (b)、#9240 按建议改测试门控）。**rebase 铁律四条（10-25/26/30 三轮实测教训）**：

1. 解完冲突后必须 `git diff upstream/main..<head> --stat` 核对 PR 完整形态——`diff HEAD~1 HEAD` 只见末位提交（#9019 双提交分支曾因此误判丢码）；上游挪动文档/表格锚点会**静默丢弃**我方插入行（#9008 环境变量表 5 行），丢失行从 pre-rebase 提交取回、重放到新位置。
2. textual-clean rebase 仍可能语义冲突：rebase 后本地 `cd server && go build ./...` + 改动包测试（先例 #8930：上游新增调用方撞本单改过签名的函数，文本零冲突、CI 编译红；再例 #9233 四度：上游 #9713 同点提取新函数，解法=保留我方结构+解析行升级上游新函数）。
3. 冲突块 HEAD 侧为空=上游删除意向，随上游删；同文件上游改动与我方区域不相交则不动、不为了刷 base 无谓 force-push（先例 #8986：上游只改 flag 帮助文案）。
4. worktree `checkout -B` 的分支名必须先 `gh pr view --json headRefName` 取实际名，不从 PR 标题猜（10-30 #9233 实测：按标题猜名推送落成远端 new branch、PR 未更新；探针=push 输出 `[new branch]`，更新既有分支是 forced update）。

验证：改动包测试 + CI 全绿再报；本地 DB 可自建（`docker run -d --name multica-pg -e POSTGRES_USER=multica -e POSTGRES_PASSWORD=multica -e POSTGRES_DB=multica -p 5432:5432 postgres:16`，`cd server && DATABASE_URL=postgres://multica:multica@localhost:5432/multica go run ./cmd/migrate up`，与 CI 容器同构）；CI pending 期判终态用「非 pass/skipping 的 lane」grep，不数 pass 计数。评论与帖文正文传文件一律 `gh api -F body=@<文件>`（**`-f` 不展开 `@file`，会把字面路径当正文发出——三次实证，最近 2026-11-05 r58**；`gh pr edit --body-file` 不受影响）；发后 GET 回读（长度+关键串断言）。worktree 配方：`git worktree add /tmp/mc-rb-<n>` → **先 `checkout -B <分支>` 再动手**（detached HEAD 上 commit 推无可推）→ push 用零冒号形式 `git push --force-with-lease origin <分支>`。用完的 worktree/容器本轮删。不谎报、没跑的列 not run。记账：`docs/hub/multica/journal/`（卷内文末追加 + `journal/在途快照.md` 文首倒序加节）+ 总台账 `docs/handbook/02-接单总台账/multica.md` 对应行（终态迁归档表）。
