## 1. 选题杠杆（自 maka/magpie：命中率主要由选题决定）

magpie 165 单复盘：patch 被直接拒的只有个位数，且多因「报告被上游证伪」而非质量——**选题决定命中率**。multica 已实证的命中族（首单交付后回填本表，maka 擅长清单机制）：

| 优先 | 族 | multica 实证 |
| --- | --- | --- |
| 1 | execenv/runtime 同构域（Codex↔Hermes↔其它 runtime 镜像移植） | #9610（Codex managed policy→Hermes）、#8930、#9008 |
| 2 | DB 事务与竞态守卫（同函数守卫不对称收紧=零争议形态，maka #6351 实证） | #9240、#9019 |
| 3 | CLI/API 输出契约（机读可断言的面） | #8986、#9568 |
| 4 | 测试稳化（维护者亲单、命中率最高，maka/magpie 双实证） | 待首单 |

排除项（两仓一致的弱项）：Windows 专属（mac 本机不可验）、需真金白银资源、产品形态决策（只给两条路请维护者拍板）、报告者未复现且无日志的单。

**高产区三信号（maka 审计车道实证）**：①报告者高质量单（带 task UUID/日志/时间线）；②open issue 聚簇域（同一子系统连开多张=上游活跃面）；③刚合并的新鲜面（`git log --oneline -40 upstream/main` 审最近 feature commit，新逻辑的边界与兄弟场景最易漏，magpie hunt 车道实证有效）。**「读失败当空」家族跨仓 4+ 杀（maka #6318/#6347/#6350/#6290 族）**：读不到文件/配置/记录时当成空值、相等或默认继续走——接单时先问「这里读失败会变成什么」。

**扫描纪律（multica 已有占坑四查之外的增补）**：报告者名下 open PR 必查（本仓报告者秒级自开 PR 是结构性常态，#9110/#9079 两次实锤）；上游已修检查不只搜 open PR，merged PR+未更新 issue 同样致命（#9268 教训，`git log upstream/main -- <域文件>` 兜底）。

## 2. 交付纪律（自 magpie §5 蒸馏，tdd/diagnosing-bugs skill 同源）

- **先建反馈回路再动手**（diagnosing-bugs 核心）：动手前先有「一条会红的命令」（修前必红的测试/复现脚本），没有红信号就不进假设。marker sleep 必须 < 等待方 ctx 超时（#1375 家族血训，multica #9240 已用 pg_stat_activity 状态等待替代 sleep）。
- **红绿在 seam 上**（tdd 核心）：测试走公共入口不测私有实现；守卫类测试必须做「基线必红」实证，只看守卫侧绿不算数（multica M4 假绿大课，02 文末已载）。
- **消融三定式**：消融前先 commit；基线=分支父提交（不是 HEAD~ 猜测）；显式摘**全部**产品文件、测试保留，原始输出逐行看。变异点放语义真正分叉的那一行。
- **兄弟面 rg 全查**：同判定的全部调用方逐个对比，改/不改都写理由——这是 review 点查项。
- **发帖前七问（magpie §3.1，PR 形态适配）**：来源真实？真实失败记录？基线断言级 RED？收益说得清？不触维护者已裁决/近 48h 自修区？兄弟路径与失败读取有答案？本人能三句话讲清？任一不过就不发。
- **验证矩阵与诚实表**：改动包全量+`-race` 相称+`go vet`+`gofmt -l` 净；RC 落文件取不接管道（zsh 假绿陷阱，02 已载）；没跑的标 not run，绝不谎报全绿。DB-backed 本机可验（2026-10-04 起 postgres:16 就绪，见 02 文末；01 的「DB 单接不了」已过时以此为准）。
- **存量影响面**：修法只盖新数据时，交付写明旧数据用户会看到什么、何时被补上（magpie #2635）。
- **热路径代价**：请求热路径上新加检查，交付必须回答「每个通过请求的代价」（magpie #2551）。

## 3. 避坑清单（跨仓血训精选，接单前过一遍）

1. **发布链每步门控，POST 报错≠没发**（magpie #2593/#2946 双案）：命令 `&&` 门控禁 `;` 串联；push 后 `ls-remote` 比对 SHA 才 POST；POST 响应解析失败先 GET 核实再决定重发，绝不直接重 POST。Agent 启动报错≠没启动（调用可能已在服务端执行）。
2. **撞车零成本处置**：已发的 patch/PR 留作独立佐证不撤回；公开自评以先发为准，点名对方补丁缺口，自家分支留作备份。
3. **同账号并行在途清单显式传路**：派单前汇总近 12h 的 claim/交付评论写进每路任务书，线索与接单权绑定同一路（magpie hunt31 撞单教训）。
4. **多 clone/多会话提交前 `git status`**：确认没有裹挟他人暂存。
5. **ping 纪律**：超 3 天无信号才 ping、不连发（校注 2026-11-07：原文写「24h 线」，与本页 §4「超 3 天」及 [handbook/07 §2](../../../handbook/07-分工与并行.md#2-优先级每轮按序)、[handbook/09](../../../handbook/09-提示词.md) 的「超 3 天无信号 gentle ping」冲突，按 3 天统一；本仓 journal 实操也按「3 天线」判定，见卷03 r28/r45/r54）；ping 前查评论数防双重触达；引用 patch/PR 名先回读 issue 原文核对（#1306 错标）。
6. **老单行号一周必漂移**：动手前重核（本仓上游 0.7.1 一天 +10 提交实证）。
7. **正文点名的未修兄弟面落为可追踪项**：交付写了「Left: X」就进候选池 follow-up，不然没人跟进（magpie #2634）。
8. **收尾卫生**：本轮创建的 worktree/容器/临时件本轮删；`git worktree remove` 后确认注册已清。

## 4. 维护闭环（在途单的合并率杠杆）

- **评审意见修复优先于一切新单**（maka 铁律）：review 回复带修复 SHA+证据，逐条 resolve；CHANGES_REQUESTED 过时（阻塞者未归+发现已修+后续零发现）列证据链请重审（multica 03-开场提示词已有流程）。
- **维护者取向侦察**：同题竞品并存时公开让位或等裁决，不并排堆 PR（#8992 产品裁决关单+竞品 #8991 同关的教训：维护者会整族裁决，别硬推）。
- **裁决先行**：修法有多路线时在认领评论公开声明选择与理由——降低维护者 review 成本=提高合并率。
- **gentle ping**：超 3 天无信号 ping 一次，重申 mergeable/CI 状态与可调整意愿（现役 6 张的等审节奏已验证）。
