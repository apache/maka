## 案例 1 ｜ #4481：statusline 的 Windows 路径缩写

### 选题转折

同一批候选里有个更"简单"的 #4002（纯补测试），但已有人留言带计划认领。选了没人认领、且我作为 Windows 用户能直接复现验证的 #3825。**选题比解题更影响成功率：放弃已认领的单，是新手最容易忍住不做的一步。**

### 关键转折

**转折 1：行号是错的，行为是对的。**
issue 说问题在 `pi-transcript.ts:1520`，实际代码已经漂到 1925 行。如果按行号找代码找不到就放弃，这单就没了。核对 issue 的正确姿势：拿它的**行为描述**（"`cwd.startsWith(home + '/')` 在 Windows 永远为 false"）去代码里找，行为一致就是真问题。

**转折 2：测试注入点是自己长出来的。**
`shortenCwd` 早就有 `homeDir?: string` 可选参数——某人当初为可测试性预留了注入点，但从没导出过。发现这种残留意味着：不用 mock `os.homedir`、不用造测试夹具，**导出函数 + 传参**就是完整测试路径。动手前先问：这个函数身上有没有前人留的"测试钩子"。

**转折 3：一行 stdlib 替掉手写匹配，还顺带修了两个潜在 bug。**
原实现 `cwd.startsWith(home + '/')`。换成 `path.relative(home, cwd)` 后免费获得两样东西：Windows 盘符和大小写不敏感比较（`path.win32` 内建），以及规范的"不在 home 下"判定（结果以 `..` 开头或是绝对路径就回退）。修法清单里凡是自己要写字符串前缀比较的，先查 stdlib 有没有语义等价的函数。

**转折 4：命名冲突让方案改了形状。**
最初想 `import { sep } from 'node:path'` 来判断 `..` 前缀，但这个模块的模块级已经有一个 `sep` 常量（状态栏的 ` · ` 分隔符）。与其引入遮蔽，改成显式 `rel.startsWith('../') || rel.startsWith('..\\')`——更直白，也免了跨平台 `sep` 的心智负担。**导入 stdlib 符号前先 grep 模块级有没有撞名。**

**转折 5：平台相关测试用 skip 守卫拆开跑。**
`path.relative` 是宿主相关的：POSIX 用例在 Windows 上跑必挂（反之亦然）。用 `{ skip: process.platform === 'win32' }` 让每个平台跑自己的部分，Windows 用例在项目自己的 Windows 测试通道生效。

**转折 6：套件红了不等于你的代码错了。**
完整 cli 套件有一个失败：`runtime-host-update-reconciliation` 的 `fsync EPERM`。定性三步——grep 导入关系（失败模块不 import 我改的文件，零关系）→ 单跑确认 → 查到 open issue #3898 正是追踪这个 Windows 目录同步缺口。结论写进 PR 的 Verification 表，**不藏着也不谎报全绿**。附带教训：后台跑 `npm test | tail -30` 会把测试摘要吞掉，重要输出落文件。

### 交付内容

| 文件 | 改动 |
| --- | --- |
| `packages/cli/src/pi-transcript.ts` | `shortenCwd` 改走 `path.relative`，拒绝 `..`/绝对结果，导出；文档注释补平台语义 |
| `packages/cli/src/__tests__/pi-transcript.test.ts` | 新增 5 个聚焦用例（POSIX 2 + Windows 3，平台 skip 守卫），测试名带 `(#3825)` |

### 可迁移模式

1. issue 行号不可信，行为描述可信。
2. `homeDir?` 这类"孤儿参数"是现成的测试注入点。
3. 平台语义函数（path/fs）的测试必须按平台拆分守卫。
4. 环境失败定性三步：查导入关系 → 单文件重跑 → 查仓库已知 issue。

## 案例 2 ｜ #4485：快捷键标签的平台正确显示

### 选题转折

四道闸里最重的一条：issue 作者把涉及文件和行号全标好了，看起来"照着改就行"。**正是这种单子最容易翻车**——照 issue 抄会改出真 bug（见转折 3）。issue 越详细，越要亲自画数据流。

### 关键转折

**转折 1（本单最大价值）：issue 的修复建议以偏概全。**
issue 列了 8 个文件 30 处 `⌘`，建议"避免在 shell-copy.ts 硬编码"。逐一定性后：16 处是注释，键盘帮助面板走的 `<Kbd>` 组件**本身已平台感知**（`mod` token 在非 Mac 渲染 `Ctrl`，还带 Client Hints 检测）——issue 里说"帮助面板硬编码"的那一半根本没坏。真实病灶只有 2 处绕过 Kbd 的裸字符串。**照 issue 全改会把没坏的东西改坏（见转折 3），把 PR 从 30 处扩散成灾难。**

**转折 2：先画数据流，再定改动面。**
显示串的完整链路是 `shell-copy 数据 → ASTRYX_KEY_TOKENS 解析 → <Kbd> 渲染`。画出来才发现 `keyboardHelp` 的 keys 数组是**双用途数据**：既被面板展示、又被解析成 `mod` 注册热键。改成 `Ctrl` 字符串会解析失败、热键注册坏掉。结论：这份数据**刻意不动**，并把理由写成代码注释放在数据旁边——防止下一个读 issue 的人来"修好"它。

**转折 3：修复位置跟着测试设施走。**
纯函数 `isAppleShortcutPlatform` 放 `@maka/ui` 的 `utils.ts`（有 build+test 链，278 个用例的套件），desktop 渲染层放同样代码却**没有 node 测试跑道**（desktop 的 node --test 只覆盖 main 进程）。同一个函数，放对包就有真测试，放错包只能靠 typecheck。写代码前先确认"这段逻辑的验证跑道在哪"。

**转折 4：复用设计系统的既有约定，不另发明。**
平台检测没有自创 UserAgent 正则，而是沿用 Kbd 内部的 `navigator.platform` 回退（`/Mac|iPhone|iPad|iPod/`），并在文档注释里说明"和 Kbd 的输出保持一致"——两套显示逻辑共享同一套判定，才不会出现面板显示 Ctrl、旁边提示写 ⌘ 的精分现场。

### 交付内容

| 文件 | 改动 |
| --- | --- |
| `packages/ui/src/utils.ts` | 新增 `isAppleShortcutPlatform` 纯函数 |
| `packages/ui/src/__tests__/utils.test.ts` | 新文件，7 个断言（MacIntel/iPhone/iPad/Win32/Linux/空/undefined） |
| `packages/ui/src/session-sidebar-nav.tsx` | kbd 由 `NEW_TASK_KEYS` 常量驱动，⌘ N → Ctrl N（非 Mac） |
| `apps/desktop/src/renderer/locales/shell-copy.ts` | 6 条 hint（中英双语）走 `platformHint`；注释说明 keys 数组为何保持 ⌘/⇧ |

### 可迁移模式

1. 显示 bug 先画"数据 → 解析 → 渲染"全链路，把每一环定性（谁展示、谁解析、谁注册）。
2. 双用途数据（既显示又解析）不能只按显示需求改。
3. grep 全部可疑符号（如 `⌘`）后逐个分类：注释 / 逻辑 / 显示串，只改第三类。
4. 纯逻辑放进有测试跑道的包，渲染残壳留在原地。
5. 仓库 grep 输出 `git grep` 式先跑一遍 issue 给的"漂移配方"，能直接定位 issue 没写全的角落。

## 跨案例的元经验

1. **issue 是线索不是图纸。** 两单的 issue 都给了错误或过期的信息（行号漂移、修复建议以偏概全），真正可信的是对着当前代码画出的数据流。维护者评审时看的也是你对消费链的理解深度。
2. **最小改动 ≠ 最小 diff，而是最小认知负担。** #4481 的显式 `'../'` 前缀检查比 `sep` 导入多几个字符但少一层心智；#4485 给 keys 数组加"为什么不动"的注释比删掉它更防回归。
3. **验证的诚实度就是贡献者的信用。** 两单都在 PR 里如实写了"哪里没测到、哪个失败与本改动无关及证据"。同仓库的快速合并案例（#3523/#3555 当天合并）共同的格式就是「声明 → 命令 → 结果」三列表。
4. **每单结束后问一句：这次的弯路，下次在哪个环节就能避开？** 答案写进 [06-接单全流程.md](06-接单全流程.md) 的沉淀区，形成闭环。
