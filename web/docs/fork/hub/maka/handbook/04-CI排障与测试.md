# CI 排障与测试（平台失败 \/ 犯错清单）

## CLI 测试构建与平台失败排除

`packages/cli` 的测试不在源码上跑，走 dist：改完代码要**先构建再测**，否则测的是旧代码。

## 构建与测试链

```bash
cd packages/cli
npm run build:workspace-deps   # 依次构建 core / storage / mcp / runtime / runtime-host / eval
npm run build                  # tsc 编译 cli 本体（含 dist/__tests__）
node --test dist/__tests__/runtime-host-run-command.test.js   # 单文件快速验证
npm run test:dist              # 全量套件（Linux CI 上 723+ 用例）
```

注意：

- `build:workspace-deps` 可能因 `@maka/eval` 构建退出码非 0 而中断，但所需依赖的 dist 已产出，`npm run build` 能过就继续，不必死磕。
- `packages/core` 没构建过时其他包的类型解析会大面积报 `Cannot find module '@maka/core/events'`——先 `cd packages/core && npm run build`。
- 快速迭代时也可以 `npx tsx --test src/__tests__/xxx.test.ts` 直接跑源码（packages/ui 就是这么测的），但 cli 的源码 import 了 workspace 包，一样需要依赖 dist 存在。

## Windows 本地的 43 个预存在失败

全量套件在 Windows 本地有约 43 个失败，**与改动无关**，是平台/权限问题，按错误特征排除：

| 错误特征 | 性质 |
| --- | --- |
| `EPERM: operation not permitted, fsync` | Windows 文件锁 |
| `EPERM: operation not permitted, symlink` | 非管理员建 symlink 需要特权 |
| `LaunchAgent` / `launchctl` / darwin-only 用例 | macOS 专属 |
| `TypeError: The OS account home must be absolute` | 环境差异 |
| `The candidate Runtime Host service is still running` | 进程残留 |

排除法：失败清单里没有你改动的测试文件，且错误类型全部落在上表 → 与本次改动无关，CI（Linux）会正常通过。改动的文件必须单独跑到全绿。

## 本次踩的坑：durable 用例少 `graph: true`

`packages/cli/src/__tests__/runtime-host-run-command.test.ts` 里同一个断言有两条路径：

| fixture 字段 | 模拟 | 需要的参数 |
| --- | --- | --- |
| `turnEvents` | live 事件流 | 直接跑 |
| `finalMessages` | 持久化转录（Graph 轮次） | fixture 加 `graph: true`，命令行加 `--graph` |

durable 用例漏了 `graph: true` 时，run 根本不读 finalMessages，直接走默认完成路径返回 **exit 0**——断言"期望 exit 1"会失败，且看起来像代码逻辑错了，实际是测试没走到目标路径。

## 格式

提交前对改动文件跑：

```bash
npx @biomejs/biome check --write <改动文件>
```

 Biome 报的 format 类错误用 `--write` 自动修；修完重跑一遍确认 `No fixes applied`。

## 2026-09-13 追加：环境噪音对照定性法（一次到位版）

Windows 本机预存失败清单再扩充：sqlite `EBUSY unlink`（conversation-copy 13 连）、symlink EPERM（foreign-session-store）、Storybook 滚动几何、linkedom 下 button click 不触发 form submit。

**stash 对照定性法**（PR-036 起标准化）：

```bash
git stash push -- <嫌疑文件>
<重建 + 重跑同一套件>
git stash pop && <重建>
```

对照失败集合逐位一致 = 预存铁证，一份证据同时写进自检和 PR 表格（#5125 的 conversation-copy 13×EBUSY 就这么定性的，PR 里如实记录）。

新坑两条：
- **linkedom 里 button click 不触发 form 提交**：测 React `onSubmit` 直接对 `<form>` 派发 `submit` 事件（`{bubbles: true, cancelable: true}`）。
- **grep 假阴性 ≠ 漂移证据**：`10 * 60_000` 的数字分隔符让三轮搜索扑空，差点把准确文档误报成漂移——换词根、搜引入提交的 diff、读实现，三步齐了再下结论。

## 排查 SOP（两次实战验证有效）

1. **先拉 check-runs 实时状态**，区分 `queued`（排队，不是失败）、
   `failure`（真挂）、`Review required`（分支保护常态，每条 PR 都有）。
2. **失败 job 的日志抓三样**：`##[error]` 前后 20 行、`✘`/`not ok` 清单、
   失败步骤名（`/actions/runs/{id}/jobs` 先拿 job id 再拉日志）。
3. **定性三板斧**：改动的文件与失败测试是否零重叠（对**新鲜** upstream/main
   做 diff，本地 main 陈旧会污染对照）→ stash 前后同跑对照 → 仓库搜同款前科
   （`search/issues?q=...`，e2e 的 flaky 往往有前科 issue）。
4. **无写权限时的出口**：PR 留言附证据链请维护者 re-run，别自己硬修
   与改动面无关的东西。

## 本轮新增的犯错与教训

| # | 犯的错 | 教训 |
| --- | --- | --- |
| 1 | 改完只跑 build+test，漏跑 format:check，CI 红了才补 | 验证矩阵是全量清单，**不许因为"这次改动小"跳项**；biome 对 apps/desktop 免格式化但对 packages/* 严格，别拿上一轮的豁免经验外推 |
| 2 | `git checkout <tree-ish> -- <path>` 会**自动暂存**该文件，混进了不相关提交 | 事后 `reset --soft` + `restore --staged` + `push --force-with-lease` 重整；惯用法改为：临时借上游文件时先 `git stash push -- <path>` 或用 `git show <ref>:<path> >` 重定向 |
| 3 | 分支被公司 rebase 到更新 main 后，本地旧的依赖 dist 造成幽灵类型错误（7 个错全在不相关文件） | **切分支 = 重建被依赖包**（cli 的 `build:workspace-deps` + ui build），再跑 typecheck；症状特征：错误集中在引用 `@maka/*` 新 API 的文件 |
| 4 | 用 `Date.now()` 快照做秒表起点，Storybook 夹具 `createdAt: 1` 渲染出五位数小时 | 夹具的假数据要跟着新语义复核一遍；"视觉检查"不是走过场——这次的夹具 bug 就是截图抓出来的 |
| 5 | `npx tsc` 在 fnm 环境下拉到假的 `tsc@2.0.4` npm 包 | 永远用 `node_modules/.bin/tsc` 绝对路径 |
| 6 | `cd` 进仓库触发 fnm 钩子以退出码 1 截断 `&&` 链（一天内踩中 4 次） | 能不 cd 就不 cd：`git -C`、`npm --prefix`、`tsc -p <绝对路径>`、`node <绝对路径>` 全套替代 |
| 7 | effect 依赖整个 snapshot 导致秒表每次刷新归零；闭包丢 TS 窄化（composition/graphStore） | effect 依赖收到最小标识（`snapshot?.graphId`）；进闭包的外层 `let` 先收进 `const` 局部别名 |
| 8 | reviewer 指出"正文与 diff 矛盾"（Summary 说退出码不变、Checklist 勾了 Behavior change: Yes） | **PR 正文也是文档**，推完代码必须重读一遍正文与 diff 是否互证；数量断言（改了几个文件、几条用例）逐个数 |

## 追加（同日）：raw 图片 404

PR 评论里嵌 `raw.githubusercontent.com/<owner>/<repo>/<branch>/<file>` 图片 404——
**路径漏了子目录**。文件实际在 `e2e-evidence/` 子目录，URL 却指向根路径。
排查口诀：`git ls-tree -r <ref> --name-only | grep png` 拿到完整路径，再拼 URL，
并用 `curl -o /dev/null -w "%{http_code}"` 验证 200 后再发评论。
（另：GitHub 上传 issues 图片资产的非官方端点对脚本一律回 `Bad Size`，别耗在上面——
推到 fork 的证据分支 + raw URL 是正路。）

## 追加（同日）：扫描器误报——`.exec(` 不等于命令注入

Mimosa 安全扫描在 `packages/storage/src/context-offload-snapshot.ts:96` 与
`file-session-repository.ts:1228` 报了两条「命令注入」红标。逐条核实为**误报**：

| 标记点 | 实际代码 | 真实身份 |
| --- | --- | --- |
| context-offload-snapshot.ts:96 | `target.exec('PRAGMA foreign_keys = ON')` | better-sqlite3 的 **SQL 执行**，静态语句；动态部分走 `.prepare(...).run(sessionId)` 参数化 |
| file-session-repository.ts:1228 | `/^r([1-9][0-9]*)$/u.exec(revision)` | **RegExp.prototype.exec**，纯正则匹配，非匹配即抛 TypeError |

三条证据：两文件 grep `spawn|execSync|execFile|child_process` **零命中**（无任何 OS 进程
能力）；两文件均在 upstream/main 上由历史提交引入（cde24236d / #4662），**不在本轮任何
PR diff 内**；reviewer 建议里的 `subprocess.run(..., shell=False)` 是 Python API，对本
TypeScript + better-sqlite3 代码库不适用。

**教训**：这个代码库的 storage 层大量使用 better-sqlite3 的 `.exec()` 与正则的
`.exec()`——扫描器按 `.exec(` + 字符串拼接报「命令注入」时，先分辨 exec 的**宿主对象**
（DB？正则？子进程？），再决定是否处置。真命令注入的必要条件是存在
`child_process` 家族的调用，grep 一次即可排除或确认。
