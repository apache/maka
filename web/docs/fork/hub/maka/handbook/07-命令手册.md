## 一、开工同步（每天干活第一步，不是每单一次）

```bash
# 同步上游最新代码（只更新远端引用，不动工作区、不动本地 main）
git -C "/Users/ggbdpq/cc/code/fork/maka-hub/maka" fetch upstream main

# 新分支一律从 upstream/main 切，起点必须显式写；绝不从本地落后的 main 切
git -C "/Users/ggbdpq/cc/code/fork/maka-hub/maka" checkout -b <fix|docs>/短横线描述 upstream/main
```

分支已存在需刷新时（rebase 到最新）：

```bash
git -C "/Users/ggbdpq/cc/code/fork/maka-hub/maka" checkout <分支>
git -C "/Users/ggbdpq/cc/code/fork/maka-hub/maka" rebase upstream/main
git -C "/Users/ggbdpq/cc/code/fork/maka-hub/maka" push --force-with-lease origin <分支>
```

## 二、环境自检与修复

```bash
git -C "/Users/ggbdpq/cc/code/fork/maka-hub/maka" status          # git 活着，能出结果
node -v                                          # ≥ 22.19.0（mac 本机 v24.21.0）
ls node_modules/.bin | wc -l                     # 在仓库根执行；等于 0 = 半截安装
npm install --ignore-scripts --no-audit --no-fund  # 补装半截 node_modules，约 1 分钟
```

**（Windows）**&#x5FC5;须 cd 时先执行（否则 fnm 钩子报错且以退出码 1 截断 `&&` 链；mac 无此坑）：

```bash
eval "$(fnm env)" 2>/dev/null
```

测试卡在 `Downloading Electron binary...`（上游 bump electron 后，`--ignore-scripts` 跳过了二进制下载）：

```bash
ELECTRON_MIRROR="https://npmmirror.com/mirrors/electron/" node node_modules/electron/install.js
```

mac 上 electron 二进制下载失败（网络瞬断连败）也可直接退 `--ignore-scripts` 安装——测试/typecheck 不需要 electron 二进制（2026-10-02 实测）。mac 的 clone 环境重建依据见本节下方与 [10-02 评审维护台账](../journal/13-评审维护-卷04.md)中的“#5274 第六次追平收口”记录；不依赖外部记忆名定位。

### macOS 重建记录（2026-10-02，本轮未重跑）

依据上述台账：安装使用 `--ignore-scripts` 时，必须补跑仓库实际存在的 `node scripts/apply-dependency-patches.mjs`；该脚本没有同名 npm script 包装。依赖产物按 `core → storage → runtime → mcp → computer-use → runtime-host → ui` 的顺序重建，其中 computer-use 不能漏。

这条顺序和“测试/typecheck 不依赖 Electron 二进制”的判断来自 #5274 当次验证，不能推出所有任务都无需 Electron。具体 build 命令先读目标分支的 package.json；桌面运行与端到端测试按所需环境准备。本轮仅核对文档来源，没有复跑安装或构建。

## 三、认领与评论（take / untake / gentle ping）

```bash
# 取令牌（只在变量里流转）；然后发认领评论，正文必须恰好一个词 take（放弃用 untake）
TOKEN=$(printf "protocol=https\nhost=github.com\n\n" | git credential fill | sed -n 's/^password=//p')
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Accept: application/vnd.github+json" \
  "https://api.github.com/repos/apache/maka/issues/<编号>/comments" -d '{"body":"take"}'
```

## 四、查询（全部走 api.github.com，网页抓取会超时）

```bash
# PR 状态（open/merged、head SHA、评论数）
curl -s "https://api.github.com/repos/apache/maka/pulls/<编号>" | python -m json.tool | head -30

# review 意见列表 / issue 区评论列表
curl -s "https://api.github.com/repos/apache/maka/pulls/<编号>/reviews"
curl -s "https://api.github.com/repos/apache/maka/issues/<编号>/comments"

# 某个 head SHA 的 CI 检查结果（红叉定性第一步）
curl -s "https://api.github.com/repos/apache/maka/commits/<head SHA>/check-runs" \
  -H "Accept: application/vnd.github+json"

# 判断某组是否被人认领：看 issue 评论 + assignee，0 评论 ≠ 没人认领
curl -s "https://api.github.com/repos/apache/maka/issues/<编号>/comments?per_page=20"
```

CI 红叉定性三步：先分清 queued/failure/分支保护（queued 不是失败）→ 抓失败日志 `##[error]` 前后 20 行 → 与失败测试零重叠要用**新鲜 fetch 的** upstream/main 做 diff。完整 SOP 见 [04-CI排障与测试.md](04-CI排障与测试.md)。

## 六、提交与推送


## 七、开 PR

```bash
TOKEN=$(printf "protocol=https\nhost=github.com\n\n" | git credential fill | sed -n 's/^password=//p')
# 先把 PR 正文写进 body.json 再引用，避免 shell 转义地狱（python -c 'import json;print(...)' 生成）
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Accept: application/vnd.github+json" \
  "https://api.github.com/repos/apache/maka/pulls" \
  -d @body.json
# body.json: {"title":"...","head":"ggbdpq:<分支名>","base":"main","body":"<四段正文：Summary/Verification/AI use/Checklist>"}
```

PR 正文验证表用「声明 → 验证命令 → 结果」三列格式（#3523/#3555 提炼的快速合并格式）。

## 八、gh CLI（日常主路径，2026-10-02 核验）

- 本机已装并**已认证**（keyring 存储，scopes：repo、read:org、admin:public_key）——明文令牌不再经手；第三/七节的 curl 路径保留作兜底：

```bash
gh auth status        # 核验认证状态
gh api repos/apache/maka/pulls/<编号> --jq '.state'     # API 查询
gh pr checks <编号> --repo apache/maka                  # CI 检查终态
gh pr view <编号> --repo apache/maka                    # PR 详情
```

- 实测坑：`gh api --jq` 里 `last(3)` 不可用（"cannot iterate over: number"），用 `.[-3:][]` 切片；comments 端点必须带 `per_page=100`——默认 30 条/页会静默截断，三端点巡检曾因此漏看最新评论（分页假象）。
