# 日常查询与同步推送

## 查询 PR 状态与 CI 排障

## 匿名 API 会限流

`curl https://api.github.com/repos/...` 不带认证，限额 60 次/小时且按 IP 计——挂代理时是**代理出口的共享 IP**，很容易被别人用光，报 `API rate limit exceeded for x.x.x.x`。

解法：gh 登录后一律走认证请求（5000 次/小时）：

```bash
gh api repos/apache/maka/pulls/4514 --jq '{state, merged, mergeable_state}'
```

## 区分 PR 和 issue

同一编号两个端点返回不同内容。issue 端点对 PR 也返回 200（多了 `pull_request` 字段），所以判断类型：

```bash
gh api repos/apache/maka/issues/4516 --jq 'has("pull_request")'
```

`false` = issue，`true` = PR。本次 #4516 就是 issue（不是 PR），编号连续但类型不同。

## 批量查 PR 卡点

一次拿到分支名、落后多少、可合并状态：

```bash
gh api repos/apache/maka/pulls/4514 --jq '"\(.head.ref) behind=\(.behind_by) mergeable=\(.mergeable) mergeable_state=\(.mergeable_state)"'
```

注意：`mergeable`/`behind_by` 是异步计算的，刚创建的 PR 首次查询返回 `null`/`unknown`，隔几秒重查即可。

CI 检查项一览（test/label 等每个 job 一行）：

```bash
gh pr checks 4514 -R apache/maka
```

`pending 0` 长时间不动大概率是**排队等 runner**，不是失败——去下一节的 run 详情看进度。

## 看 CI 挂在哪一步、拉失败日志

```bash
## 从 pr checks 输出里拿到 run ID（URL 最后一段），看整个 run
gh run view <run_id> -R apache/maka

## 只看失败 job 的当前步骤
gh run view --job=<job_id> -R apache/maka

## 失败日志，过滤出报错行（日志开头几十行都是环境准备，别浪费时间读）
gh run view <run_id> -R apache/maka --log-failed | grep -E "##\[error\]|AssertionError|error TS" | head -20
```

看某个步骤（如 `Check renderer architecture`）的完整输出：

```bash
gh run view <run_id> -R apache/maka --log-failed | grep "步骤名" | tail -30
```

## 排障顺序（本次验证有效）

1. `gh pr checks` 看哪个 job 挂、跑了多久（15 秒挂=确定性失败，5 分钟挂=跑得深后挂，20 分钟 pending=排队）。
2. `--log-failed` 拿报错原文，先定位**步骤名**再定位**断言内容**。
3. 同仓库多个 PR 挂同一步骤 → 先怀疑 main 本身红了，查 main 最近有没有 `fix(ci)` 类提交。

## 2026-09-13 追加：占坑判定与跨 fork API 细节

- **间接占坑判定**：issue 无评论无 assignee ≠ 没人做。全仓搜同名 PR（`search/issues q=repo:apache/maka is:pr <关键词>`），open PR 正文出现 `Fixes #N` 就是占坑——#5231 差点撞 #5233，排雷查在先才没白干。
- **跨 fork 开 PR**：API `head` 字段必须带 fork 前缀 `ggbdpq:分支名`，裸分支名报 422 invalid。
- **修正已发评论**：`PATCH /repos/.../pulls/comments/{id}`（行内）或 `/issues/comments/{id}`（会话级），body 整体替换。
- **长 PR 找自己回复的锚点**：`GET pulls/{n}/comments?sort=created&direction=desc` 按 `in_reply_to` 归组，先查目标评论 id 再回复。

## fork 同步与 PR 分支 rebase 推送

## 场景

自己的 PR 基于旧 main，main 期间又合了新提交（尤其是 CI 修复），PR 的 test 全挂。解法 = 同步 fork + rebase 分支到新 main + 强推。

## 同步 fork

GitHub 端（把 fork 的 main 快进到上游）：

```bash
gh repo sync ggbdpq/maka --source apache/maka
```

本地端（已在 fork 仓库、main 分支）：

```bash
git fetch upstream main        # 首次需 git remote add upstream https://github.com/apache/maka
git merge --ff-only upstream/main
```

## rebase PR 分支

```bash
git checkout -B <分支名> origin/<分支名>
git rebase main
git push --force-with-lease origin <分支名>
```

单提交 PR rebase 后仍是单提交，比 GitHub 的"Update branch"（产生 merge commit）干净。`--force-with-lease` 防止覆盖别人推的新提交。

## workflow scope 拦截（本次踩过）

**症状**：rebase 后推送报 `refusing to allow an OAuth App to create or update workflow .github/workflows/ci.yml without workflow scope`。

**原因**：rebase 后分支携带了 main 上改过 `.github/workflows/` 的提交，推送 diff 里含 workflow 变更。即使本地没改 workflow 文件也会拦——它看的是 ref 的新旧差量。

**三处都会拦**：`git push`、`gh repo sync`、`gh api -X PUT .../update-branch`（服务端更新也一样，因为合并提交用你的 token 身份创建）。

**解法**：`gh auth refresh -h github.com -s workflow` 补授权（见 [01-环境搭建.md](01-环境搭建.md)），没有绕过方案。

## 改完 CI 没反应？

强推会自动触发新一轮 CI，不用手动 re-run。`gh pr checks` 里新 run 的 run_id 会变；等结果时注意 pending 可能是排队，用 `gh api repos/apache/maka/actions/runs/<run_id> --jq '.status'` 区分 `queued`/`in_progress`。


## gh api 评论正文：一律 --input JSON（三中招后升级为铁律）

`gh api ... -f body=@file` **不展开 `@file`**——把字面文件名字符串当正文发上榜（2026-11-01 一次十条全中，靠 GET 回读逐字节比对兜住后 PATCH 修复）。正确形态：

```bash
python3 -c "import json; json.dump({'body': open('body.md').read()}, open('body.json','w'), ensure_ascii=False)"
gh api repos/apache/maka/issues/<N>/comments --input body.json --jq '.id'
```

发出后必须 GET 回读逐字节比对。PATCH 修正时 path 只收一个参数（`repos/.../comments/<id>` 一段写全，拆两段报 `accepts 1 arg(s), received 2`）。

## 单条评论 GET 404 是幻影，列表端点 sort 疑不生效

POST 后立刻单条 GET（`issues/comments/<id>`）可能 404（传播延迟），不代表没发出去——用列表路由 `issues/<N>/comments` 按 comment id 匹配核「在榜」，绝不因 404 重发。另：issues comments 与 reviews 两个列表端点的 `sort`/`direction` 参数疑似不生效（回显最旧），拿「最新一条」用 GraphQL `comments(last: 1)` / `reviews(last: 1)`（11-01 #6399 两条实锤）。

## mergeable UNKNOWN 是算态瞬态（maka 口径）

`gh pr list` 批量返回 UNKNOWN 不代表真冲突：分片 alias GraphQL 逐单重探（python 模板替换拼 alias 块，发送前 `assert query.count('{')==query.count('}')` 防括号失衡；f-string 手拼括号会算错账），maka 实测全部复位 MERGEABLE。multica 的「UNKNOWN 卡 14h 不自愈、以 merge-tree 探针为准」口径**不适用**本仓。只有逐单查回 CONFLICTING 才动手 merge（11-05 #6246 唯一一例）。

## 并行 clone 开工先对账远端 head

多 clone（maka-pr1~3）动手前先 `git ls-remote <fork-url> refs/heads/<分支>` 看远端真 head，再 `git fetch origin <分支>`（单 refspec）。两个实锤（11-05 #6246）：①复合 refspec（`fetch origin <分支> upstream main`）一个 ref 不存在就整条 fatal，origin ref 留在旧值，merge 建在陈旧基上（作废过本地 merge commit）；②fetch 分支会覆盖 FETCH_HEAD，随后 `merge FETCH_HEAD` 合的是分支自己（Already up to date 假象）——更新基一律 `git fetch upstream main` + `git merge upstream/main`。
