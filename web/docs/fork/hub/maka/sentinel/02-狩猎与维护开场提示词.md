# 02-狩猎与维护开场提示词(maka 版,2026-10-25 定版)

> 供新对话注入:贴进新会话即承接"接单+维护老单"双线。编制思想源自 magpie handbook/06(先做完先发布/主线程不接单/子智能体任务书 v3),机制全部换 maka 实测版。质量规则唯一入口 [handbook/05](../handbook/05-review意见处理.md)+[handbook/11](../handbook/11-擅长问题清单.md);状态只信本轮 GitHub 实测,台账只当历史索引。

```text
你在 apache/maka 贡献工作区执行"盯审维护+狩猎接单"双线。上游 apache/maka,PR 制(base main),fork ggbdpq/maka。
加载 skills:ponytail、tdd、diagnosing-bugs。主 clone /Users/ggbdpq/cc/code/fork/maka-hub/maka(GitButler 托管,绝不动其工作树;git 一律 git -C 绝对路径;另有 maka-pr1/2/3 可用)。临时 worktree 一律 /private/tmp 并收尾删除;同机可能有多会话并行——开工前查 /tmp/maka-* worktree mtime 与目标 issue 近 10 分钟 ggbdpq 评论,有并行迹象退监督位只读复核。

== 开场(哨兵回合,全量不抽样)==
1. git -C <主clone> fetch upstream main,记录 SHA;gh pr list --repo apache/maka --author ggbdpq --state open 逐单四件套:reviews 全量+reviewThreads(isResolved)+reviewDecision+CI——updatedAt 没变不能跳过,未解线程是存量不是增量。
2. review/bot 意见=最高优先,处理完才开新单。维护老单节奏:落后就 merge main 解冲突(见下口诀);合并 3 天无审核信号 gentle ping(不连发);已修未 resolve 的线程回复修复 SHA 后 resolveReviewThread(回复必须把 in_reply_to 写进 JSON body,-F 与 --input 混用静默失效;写完 body 文件别忘 POST;GraphQL thread id 先查再 resolve 别猜)。
3. 读完 journal/13-评审维护.md 活卷尾部+journal/候选池.md(排除区必读)再动手,防与并行会话/昨班重复。

== maka 硬机制口诀(违者 CI 必红,全部实测吃过)==
- protocol-epoch:改 packages/runtime-host/src/protocol/ 必 bump RUNTIME_HOST_COMPATIBILITY_EPOCH(protocol/index.ts,main 当前值+1;sibling 同号撞车时顺延再+1)或加 protocol-compatible-changes/<slug>.json 声明 wire 不可观察;guard 按 HEAD 提交对象读,未提交改动不可见;响应加可选字段=可观察(exact-keys 解码拒收)只能 bump。
- 测试注册:check:release 列出的测试文件必须触达 releaseContract lane(RELEASE_CONTRACT_FILES 注册)。
- 格式:提交前整仓 npm run format:check(单文件 biome 过≠整仓过)。
- 渲染器棘轮:legacyAppShell.files 冻结清单零触碰;改动挪 features 层用 composition 注入(#6100 零债务先例);守卫在 apps/desktop/scripts/check-renderer-architecture.mjs --base upstream/main。
- 依赖:npm install --ignore-scripts 后必跑 node scripts/apply-dependency-patches.mjs;构建链 core→storage→runtime→mcp→(acp-executor-plugin→antigravity-acp-plugin)→runtime-host→(eval→maka-agent=cli)→ui;多 worktree 后台并行 npm 会互踩假失败,复验一律前台串行。
- 提交:作者 ggbdpq <ggbdpq@gmail.com>,消息 -F 文件,尾注 Generated-by: GLM-5.3-Flash (ZCode);推送 git -c credential.helper='!gh auth git-credential' push https://github.com/ggbdpq/maka.git <分支>;对外(PR/issue/评论)一律英文,本地报告中文。

== 维护线(在途 PR,当前基线见台账,动手前实查)==
六单常态:#6246(#5109 attachments)/#6245/#6200/#6100/#6036/#5265+新单。每单:CI 全绿+零未解线程=纯等审零动作;Astro-Han(bot)意见逐条对抗验证——它的 P2 附具体复现/数字,照单全修后回复 SHA+resolve;#6200 的 undici 红=上游 #6236 破损(audit+test 同因 ELSPROBLEMS),已披露等上游,不从 feature 分支改 overrides。

== 狩猎线(接单,车道按序降级)==
车道A 候选池:读 journal/候选池.md 第一梯队→REST 直查占坑三查(assignees+评论区 take/调查意图+关联 open PR;search API 本仓假空一律 REST;take 无排他权,认领者一周无 PR 可评估竞争接手)。
车道B 增量扫:REST issues?state=open&per_page=100 新单→四道闸(未被认领/≤200 行/macOS 本机可验证/与擅长族交集,见 guide/11)。
车道C 兄弟面:新报告的缺陷在熟面的同型反模式(rg 全查)。
车道D 实证 flake:main 上单跑+并发压 spawn 重套件各 N 轮(先做阳性对照——已知 flake 复现不了说明 rig 无效或已修)。
车道E 审计构造(池枯主力,2026-10-25 验证可行):派只读审计子智能体攻熟面(revision/catalog、cli/tui 已各出 1 单),锚点=「函数注释承诺 vs 实现」「共享 id 多条目」「读取失败被当空/无/相等」;确定性 3/3 红才算发现,主线程独立复核后发英文 issue(AI 审计披露)→take→修→PR。
命中后:发 issue(What happened/确定性 repro/Root cause/Suggested fix+Source 披露)→评论正文恰为 take→从 upstream/main 切 worktree→TDD(测试落正式测试文件,红→修→绿)→验证矩阵(定向+相邻套件+tsc+整仓 format:check+asf)→单提交推送→PR 四段(Summary/Verification 表/AI use/Checklist)+Fixes #N。

== 纪律(magpie 七问 maka 化,任一不过即弃;零新单是正常结果)==
真实失败可确定性复现;收益说得清谁做什么操作受影响;不碰维护者 48h 自修区/已认领/方案拍板单;兄弟路径 rg 全查记录改/不改理由;失败读取变成什么要回答;本人能三句话讲清改了什么为什么怎么验证;不为发帖量开工——被低价值关闭的单如实登记。

== 收尾 ==
记账:journal/12-认领轨(新单)/13-评审维护(维护轮)+候选池处置列+handbook/02-接单总台账/maka.md(全局号=最大+1,追加后回读);worktree 清理;报告:实际完成/未跑项/必附本轮不自信的点。
```
