# 前端核心8题

围绕 AI 产品前端准备；这是岗位优先级，不是已发生的错题榜。先闭卷答，再看骨架，每次只练两题。实际回答与复测写入[模拟记录](../04-表达与模拟/05-模拟面试记录.md)；归属与数字以[事实基线](../00-事实与简历/00-个人事实基线.md)和[证据登记](../00-事实与简历/05-项目归属与量化证据.md)为准。

## F01 Promise、await 与同步计算怎样影响页面响应？

**骨架**：Promise 执行器同步执行，then 回调异步调度；await 后续逻辑异步恢复。独立请求可并行，存在依赖时保持顺序；耗时同步计算仍会占用主线程。

**失败追问**：把耗时计算包进 async 函数，页面为什么仍卡住？两个请求部分失败时如何呈现？

**本人证据／边界**：[P02 音频任务](../01-AI项目与Agent工程/02-AI音频编辑-Node-BFF.md)用于解释等待、状态查询与任务执行的区别，不称本轮新增并发优化。

**学习演算**：先同步输出 A，Promise 执行器输出 B，then 排入微任务，随后同步输出 C；当前任务结束后才输出 then 中的 D。await 一个已完成 Promise 也会把后续逻辑异步恢复，不能拿它当“让浏览器必定绘制一次”。反复排微任务仍可能推迟后续任务与绘制。

**取舍与检查**：画像与商品列表互不依赖时同时发起；商品必须用画像结果则顺序执行。Promise.all 因一项失败而拒绝，不会自动取消另外一项。学习例中两块可独立展示时保留各自成功／失败状态；必须一致的汇总不能用缺项结果冒充完整。说出能检查的顺序和失败显示，比背 API 名称更有效。

## F02 React render、事件处理与 Effect 各负责什么？

**骨架**：render 计算 UI；事件处理响应用户动作；Effect 同步外部系统并清理副作用。Hooks 保持调用顺序；Effect 依赖变化先清理旧逻辑，不保证总在绘制后执行。

**失败追问**：为什么不在 render 发请求？Strict Mode 暴露重复订阅时应该修什么？

**本人证据／边界**：[React/TS 要点](../02-传统前端基本盘/01-React-TypeScript.md)、[P04 接诊准备](../01-AI项目与Agent工程/04-面诊成交助手-证据溯源.md)。解释机制与实际实现分开，不把精读同事代码称为原创。

**学习演算**：render 算出“当前房间”，Effect 建连接；房间从 A 改到 B 时先清理 A，再连接 B。开发检查出现连接、清理、再连接，应保证最后只有一个有效订阅，而不是关闭 Strict Mode 掩盖重复资源。

**递进回答**：点击购买产生的动作放事件处理器；订阅随组件出现而建立才用 Effect。普通派生值可在 render 计算，不必 Effect 再 setState。若 Effect 里发请求，要处理卸载与旧结果；“依赖为空只跑一次”忽略了重新挂载和开发检查。验收可反复打开关闭页面，观察订阅数量及旧事件是否还影响新页面。

## F03 快速切顾客时，怎样避免旧响应覆盖新页面？

**骨架**：明确请求属于哪个顾客；切换时更新查询键、清理失效状态。取消减少无用工作，请求身份校验防止晚到响应写错位置；缓存命中也需核对归属。

**失败追问**：取消没有生效、A 的响应晚于 B 返回，如何证明页面不串人？

**本人证据／边界**：[P04](../01-AI项目与Agent工程/04-面诊成交助手-证据溯源.md)有顾客维度缓存与竞态验收记录；具体 guard、取消路径及当前故障测试须回到证据，不临场杜撰。

**学习演算**：请求 A 代次 1 → 切 B 代次 2 → B 先返回 → A 后返回。只有响应的身份和代次均属于当前请求，才能更新当前视图。旧响应可以按约定留在自己的缓存里，但不能写进 B 页面。仅比 customerId 无法区分 A 的两次请求；Abort 也不证明服务端停止执行。

**最小反例**：控制 A 慢、B 快，最后应只显示 B 的姓名与依据；再测 A→B→A，第二次 A 先返回、第一次 A 后返回。日志保留脱敏请求代次，不输出顾客隐私。防抖减少发请求频次，身份隔离保护正确性；两个措施职责不同。

## F04 页面、组件与 store 谁拥有状态？

**骨架**：按生命周期、共享范围与更新责任确定所有者；单一事实只维护一处。简单局部状态用 state，关联转换可用 reducer；区分加载、完整、部分、空数据与错误，避免无效组合。

**失败追问**：弹窗关闭、切顾客或保存失败后，哪些状态保留、哪些清空？多个布尔值同时为真怎么办？

**本人证据／边界**：[P04](../01-AI项目与Agent工程/04-面诊成交助手-证据溯源.md)的完整／部分／空数据和缓存；[复杂业务要点](../02-传统前端基本盘/05-可视化与复杂业务.md)。联合状态模型是解释或设计手段，不自动成为旧项目代码事实。

**学习演算**：加载、成功、失败属于同一生命周期时，用一个判别状态表达允许组合；弹窗开关与数据是否空可能是独立维度，不能为整齐硬塞成一个巨型枚举。先列关闭、重开、切顾客和失败事件，再确定转换。

**取舍**：列表数据只有一个拥有者，弹窗成功后向它请求刷新；draft 是用户未确认的编辑，可与服务端快照并存，但要标清二者身份。局部输入不必因“复用”进入全局 store；跨多个区域协调同一生命周期时再提升。验证关闭重开能清理临时错误，保存失败能保留可重试草稿，避免用“全部重置”丢掉用户输入。

## F05 TypeScript 为什么不能代替 API 校验？

**骨架**：类型约束编译期，外部输入仍需运行时校验与缩窄；unknown 先判断再使用。DTO 保留接口语义，mapper 处理空值与枚举，ViewModel 服务界面，组件不重复猜字段。

**失败追问**：后端返回未声明枚举或缺字段，类型断言为什么救不了页面？默认值会不会掩盖错误？

**本人证据／边界**：[P04 mapper](../01-AI项目与Agent工程/04-面诊成交助手-证据溯源.md)；Mock 与真实数据共用映射。不能从“使用 TS”推导全部接口已被严格校验。

**学习演算**：DTO 的金额可能为 null，页面却执行 toFixed；`as {amount:number}` 只改变编译器判断，不改变返回值。先区分字段缺失、null、0，再决定“未知”“不适用”或有效零值，不能全部 `|| 0`。非法枚举应报结构错误或明确降级。

**递进回答**：边界校验不是每个按钮各写一套。入口先按契约验证，mapper 转换合法数据，组件只读 ViewModel；既不将接口字段遍布 UI，也不隐藏契约错误。新枚举加入判别联合时用穷尽检查找到遗漏分支。学习验证给出合法、缺字段、非法枚举三个输入；P04 共用 mapper 并不等于已有这些严格测试。

## F06 顾客缓存怎样设计 key 与失效？

**骨架**：查询键包含影响结果的业务维度；身份、顾客或数据变化时明确失效和重取。业务缓存与 HTTP 缓存分别讨论；no-cache 是重新验证，no-store 是不存储。

**失败追问**：切账号、换顾客或保存成功后，旧缓存怎样避免继续展示？缓存命中是否等于数据仍有效？

**本人证据／边界**：[P04 顾客缓存](../01-AI项目与Agent工程/04-面诊成交助手-证据溯源.md)、[网络要点](../02-传统前端基本盘/04-浏览器网络与安全.md)。TTL、容量和命中率未测量时不补数字。

**学习演算**：键只有 customerId，却忽略登录身份、品牌或分析版本，可能复用不属于当前上下文的结果。先写出“哪些输入能改变结果”，再组成稳定查询键；不要把随机时间戳加入 key 导致每次都失去复用。

**失败路径**：保存成功后失效相关结果，再按刷新策略重取；账号退出后敏感缓存清理，重新进入也要重新确认授权。请求已经在路上时，清缓存不能阻止它回填旧数据，还要配合请求代次或失效标记。TTL 只能表达时间策略，不能推导权限有效。当前项目容量、TTL 与命中率未证明，面试给设计条件而不是补猜参数。

## F07 隐藏按钮、CORS 与后端授权能互相替代吗？

**骨架**：隐藏按钮改善交互；后端按资源与动作授权。CORS 是浏览器跨源读取策略，HTTPS 保护传输；两者都不替代业务权限。区分 XSS 与 CSRF，凭证和日志按信任边界处理。

**失败追问**：直接调用接口、权限变化或不可信内容进入页面时，保护在哪里生效？

**本人证据／边界**：[P08 权限与请求层](../02-传统前端基本盘/06-SSAP-BCP-DOMP深挖弹药.md)、[网络与安全](../02-传统前端基本盘/04-浏览器网络与安全.md)。接入鉴权不等于独立原创完整安全体系。

**学习演算**：没有编辑按钮的用户手动构造 PATCH 请求，后端应按身份、目标资源和动作拒绝。给按钮加 v-action 不能替代这一层。CORS 即使拦读取，也不能当接口私密性或 CSRF 的完整保护。

**进一步追问**：LLM 回复被当原始 HTML 插入时，风险源是跨信任边界的数据成为可执行内容；文本转义、Markdown 配置与 URL 协议校验分别处理。XSS 还可能利用用户已有权限，不能把 token 改存位置说成免疫。先确认 Cookie 或 bearer token 的真实认证模式，再讨论 CSRF 与凭证管理；日志脱敏和后端授权需要分别证明。

## F08 页面卡顿怎样定位？什么时候用 memo 或虚拟化？

**骨架**：先区分加载、网络、同步计算与渲染瓶颈，再固定条件测量；减少实际无用工作。memo 缓存与虚拟化有适用前提；LCP、INP、CLS 分别观察加载、交互和布局。

**失败追问**：加 useMemo 后仍卡，下一步查什么？优化是否只是转移成本？

**本人证据／边界**：[性能要点](../02-传统前端基本盘/02-Web性能优化.md)、P02 波形与 P08 图表故事。无原始前后对照不报提升百分比；Transition 不延迟回调内同步计算。

**学习演算**：父组件每次输入都重新创建大数组；子组件虽 memo，props 仍变化。如果真正耗时是全量数据转换，应先减少转换次数或数据量。若是大量节点布局，才考虑虚拟化；如果网络慢，memo 不会缩短响应等待。

**取舍与消融**：同构建、同设备、同数据比较改前改后，观察时间线与输入反馈，再移除新增缓存复测。没有差异就删缓存，有差异才保留。虚拟化会增加滚动、焦点与行高维护成本；小列表无需套用。LCP 好不代表交互不卡，INP 也不涵盖所有网络完成时间；不要拿一次 Lighthouse 分数代替真实用户全生命周期体验。
