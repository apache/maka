## 一、第 1 周素材：流式传输层

### 1.1 useSSE.ts 的 run() 主流程（全文 369 行；run 本体 L206-351，收尾区 L186-368 含 abortTask L187-194 / cancel L196-201）

精读六要点（每点都是面试题）：

1. **runId 哨兵**：每次 run() 令 `activeRunIdRef.current += 1`（L134），所有异步回调（success/fail/onChunkReceived/Promise.catch）第一行都查 `runId !== activeRunIdRef.current` 即丢弃——单页多流的竞态解法。
2. **abortTask 与 cancel 分离**：`abortTask` 只杀传输与缓冲（发新请求前用）；`cancel` 额外清 content 回 idle（用户主动停止用）。finish 分支注释明说"不要调用 cancel"——否则正常结束会清空答案。
3. **finish 双通道验证**：应用层 `parsed.finish === true` 是唯一成功凭证；HTTP `success` 只代表字节收完。success 回调里复查 `gotFinishFlagRef`（L145，复查点 L245-252），流被服务端中途掐断（无 finish 帧）按失败上报，优先展示流内 `errMessage`。
4. **isAbortError 三通道归类**：微信真机上 abort 同时触发 `fail` 回调和 Promise reject（`(in promise) request:fail abort`），两处都靠 `/abort|aborted|interrupted/i`（L23-26）归类为非业务错误。
5. **缓冲按行切分**：`bufferRef` 只保留最后一个 `\n` 之后的残包，`lastIndexOf('\n')` 之前的完整行交给 `extractJsonLines`；单行 parse 失败只忽略该行。与 UTF-8 边界解码器（safeEnd 尾字节回挂 L84/L94）配合解决"半个汉字跨 chunk"。
6. **削峰合流**：content 不逐 chunk setState，先进 `pendingPieceRef`（L140），`FLUSH_MS` 时间窗统一 flush（`scheduleFlush` L169 / `flushNow` L156）。削峰窗口按端差异化：`FLUSH_MS = IS_WEAPP ? 48 : 16`（L6）——weapp setData 贵用 48ms，H5 用 16ms。另有围栏清理（L318-320）：剥掉模型偶发的 ``` / `markdown` 前缀。

### 1.2 chatSessionManager.ts（全文 245 行）——多会话连接表 + 事件翻译层

- **连接表**：模块级 `const connections = new Map<string, Taro.RequestTask>()`（L104）。`startStream` 开头先 `cancelStream(sessionId)`（L112）保证同会话单流；取消哨兵是 `if (!connections.has(sessionId)) return`（L163，先 delete 再 abort，迟到 chunk 一律丢弃）——与 useSSE 的 runId 是同一问题的两种解法。
- **事件翻译层**（onChunkReceived L162-230；message 分支 L192-197，关键教学点）：把 LangChain 风格事件帧归一化：

```ts
if (parsed.event === 'message' || parsed.event === 'messages') {
  const eventData0 = parsed.eventData?.[0];
  reasoning_content = eventData0?.additional_kwargs?.reasoning_content;  // 深度思考原文
  finish_reason = eventData0?.response_metadata?.finish_reason === 'tool_calls'; // 一轮思考结束（供分组）
  tool_calls = eventData0?.tool_call_chunks || [];                       // 工具调用流
}
callbacks.onMessage?.({ content, reasoningContent, finishReason, toolCalls, executeId, ...parsed });
```

  `requestId` 标识一轮问答，`executeId` 标识一次工具执行——多步规划中同一 requestId 下有多个 executeId。
- **finish 后主动 `task.abort()`**（L215-218）：服务端已宣告结束就不等 HTTP 自然收尾，尽快释放小程序并发请求配额。
- **双入口取舍**：useSSE（单页面局部流，runId）与 chatSessionManager（多会话全局流，连接表）各自成套，解码器/行解析器重复实现——教学时讲"这是一个可收敛的重复"，也是你 vibe 项目里可以做得更好的点。

### 1.3 旧版 aiPackage 对照（演进故事，面试金句素材）

`src/aiPackage/aiCustom/`（旧版 DeepSeek 单帧报告流）vs 新版：

## 四、面试增量弹药（8 个可讲点）

1. **旧版→新版演进表**（§1.3）——"每层重构对应一次真实故障"的技术叙事。
2. **finish 双通道验证**（§1.1 要点 3）——HTTP success ≠ 协议完成，无 finish 帧按失败上报。

4. **ADR 的"不做竞态防护"写法**（§3.1）——决策 + 理由 + 重评触发条件，比"我们加了锁"高一个段位。
5. **两层 BFF 状态映射**（§3.3 要点 3）——Node completed → Java confirmed/timeout → 前端 success/failed，多级 BFF 的状态字典教训。
6. **流式分段折叠 collapseSingletons**（parser.ts:140-158）——同类型后续段折叠回首次出现位置、固定 key，让 React 流式期间复用同一组件实例而不是越渲越多；配套 `trailingPartialMarkerLength`（parser.ts:57-70）把流尾半截分隔符暂时藏起，防 markdown 把 `------step-st` 渲染成 `<hr>` 抖动。
7. **乐观会话迁移链**（useChat.ts:18 `PENDING_SESSION_ID='__pending__'`）——先在临时会话下乐观渲染，真实 sessionId 返回后 `migrateSessionData` 整体搬移，且迁移顺带 `cancelStream(fromId)`（createChatSlice.ts:315）——乐观 UI + ID 迁移 + 流取消三者联动。
8. **削峰窗口按端调参**（useSSE.ts:6）——`FLUSH_MS = IS_WEAPP ? 48 : 16`，"削峰合流"之外还有按端调参的证据。
