# qoder-proxy-api：叙事三级与对抗十问

用途：P05 公开备用的唯一三层长稿；需要公开源码或文本协议证据时回查，不每日全量练十问。

P05，协议适配层。[事实与归属](../00-事实与简历/00-个人事实基线.md)、[E03 与验证范围](../00-事实与简历/05-项目归属与量化证据.md)是维护入口。本稿基于 `47b1af6` / tag v0.3.0；包元数据与 Changelog 尚未对齐，不混称同一版本。

## 30 秒（开场）

我做了一个本地协议网关，把 Gateway、CLI 子进程和 Cloud Agents 三类上游统一为 Canonical Request/Event，再输出 Chat、Responses、Messages 的文本兼容接口。重点是隔离上游差异，并用同一事件流处理流式与非流式响应；工具闭环和多模态不宣称完整兼容。

## 2 分钟（标准展开）

三条上游的认证、事件形状和会话语义不同，直接在每个下游端点处理，会重复路由、聚合和错误逻辑。我将请求与执行上下文分开：Provider 产出统一事件，协议适配器负责文本 wire 输出，非流式复用同一事件流聚合。模型别名明确指定 Provider 和目标 model，上游失败不自动换链路，避免混淆账号、额度和错误来源。

验证用 fake 上游、共享合同、旧行为 golden 和抓包回放；本轮无凭证离线测试结果见 E03。边界也从代码确定：内部能表达 tool/thinking 不代表下游已经输出；CLI 当前先收集完整 stdout 再输出 SSE。Gateway 涉及私有协议，注释与矩阵的当前真机口径存在冲突，所以继续按 experimental 表述，不用离线通过证明真实兼容。

## 5—8分钟独立口述稿

这是本人试讲后要校准的目标时长，尚无实际计时成绩；每次只选一份，占用既有项目练习时段。以下可脱离短稿口述，必要时停在证据与限制处接受追问。

我研究的场景是：同样一次文本对话，上游可能走Gateway、CLI子进程或Cloud Agents，下游却希望用自己熟悉的Chat、Responses或Messages接口。问题不是换一个URL就完成了，不同链路的认证、会话、事件和结束语义都有差异。项目的目标是把这些差异约束在适配层，给文本调用方一条可以核对的链路。它是本地协议研究项目；我先声明文本兼容范围，完整工具往返和多模态不在当前承诺里。

约束决定了设计边界。我没有把每一种上游与每一种下游分别写成一条独立通道，而是在中间引入Canonical Request和Event。请求描述要做什么，ProviderContext承载执行时需要的上下文，Provider产出统一事件，协议层负责对应的wire格式。这样讨论一次上游变化时，可以先定位是请求转换、认证、事件归一还是下游序列化。M加N只是结构上的关系，并不是我测得维护成本降低的比例；如果只接一个简单文本接口，更小的转发方案可能已经够用。

一条正常请求从模型别名开始。别名明确决定Provider和目标model，再把下游请求转成内部合同，交给选中的链路。上游的文本增量进入统一事件流，Chat、Responses和Messages各按自己的输出形状序列化；非流式也消费这条事件流再聚合，避免另外复制一份执行路径。内部事件还能表达thinking和tool，但当前下游输出主要处理文本、usage和error，所以不能看到一个tool类型就宣布客户端工具循环已经兼容。请求字段是否丢失、事件是否落到wire上，都需要沿源码逐段核对。

这里一个容易误讲的点是CLI。进程的stdout可以分块到达，但当前实现先收集完整stdout，等子进程结束后才解析并向下游写事件。下游看到SSE形式，不等于生成期间就能收到首个token。判断实时性要观察首次上游数据、子进程关闭和首次下游内容三个时点，不能只看Content-Type。Gateway则涉及私有协议，源码有历史真机注释，当前矩阵又保留未核验口径；我把它继续列为experimental，不拿旧时点的记录替当前版本保证。

失败路径也必须分清。模型路由没有在某条链路失败后自动切到另一条Provider，避免把不同账号、额度和失败来源混起来。Gateway认证中refresh失败后尝试cold exchange，是同一链路的认证回退，与执行请求自动换Provider不是一回事。文本已经输出后再出错，协议层还要说明错误怎样传递、聚合是否保留部分内容。客户端断开与取消要追踪到具体调用链，不能仅因为内部有signal，就推断每种上游都完成停止和资源清理。真实取消效果仍需要对应链路证据。

验证采取分级，而不是汇总一个“通过”。fake上游用于控制事件与失败，共享合同检查Provider的约定，golden约束旧行为，抓包回放核对历史形状。E03登记了2026年10月2日在工作区副本、无凭证环境下Node离线89项通过，能支撑对应的本地行为；它不等于当前Gateway真机、IDE工具闭环或生产并发。架构脚本目前打印检查结果，遇到违规也没有非零退出，因此CI里的检查步骤不能被我讲成已经硬阻断越界依赖。

还有一个检查方法是从反例反推合同：假上游先给一段文本，再给错误，观察流式客户端是否收到对应错误，以及非流式聚合怎样结束。当前聚合器遇到error会抛出错误，不能把已经收集的部分文本自动讲成成功响应。结束事件、空输出和usage缺失也要各自说明；某些链路没有实际usage，输出零值不等于真实消耗为零。这里讲的是源码行为与验收思路，不是新增真机结果。

最后是取舍和限制。统一合同让语义有集中核对点，但也可能在归一化时丢掉上游特性；我选择先把文本子集讲准确，而不是把内部丰富事件当完整兼容。当前tag是v0.3.0，package和Changelog登记仍不一致，引用证据时我给提交号，不混用版本。下一步若确有兼容需求，应先定义一个真实客户端用例、观测输入输出与失败，再补对应适配；本月源码改造暂停，公开主页只保留可核验内容。我能现场走读合同、输出和测试边界，未验证部分会直接说明。

## 原理推导与可检查反例

**合同隔离是否值得**：把新增Provider当作反事实问题：若其私有事件变化，只应先触达该normalize与对应合同检查；若下游新增一个文本wire格式，应先触达protocols。实际影响仍可能穿过共享合同，所以不能承诺“上游变更绝对无感”。这里没有做维护收益消融，只给代码依赖和变更范围的检查方法。

**流式与非流式怎样对照**：学习验收用同一fake事件序列 `text.delta→text.delta→message.end`，检查文本拼接与结束。再把最后一项换成error：`aggregate.ts`会抛出error，不返回普通成功结果；流式端应核对相应错误wire。这个对照让“复用事件流”落到可判定输出，而不把三种协议的字段与语义强行称为完全一致。

**CLI实时性怎样证伪**：检查 `runCliProcess` 的stdout缓冲与close后的resolve，再看 `cli/index.ts` 在await后解析。若未来要声称实时，验收必须让子进程先输出、延迟结束，观察下游首内容早于close；当前实现不满足这条声明。这里只列验收，不启动真实CLI，也不把可改方案写成已实现。

**三个层次的追问**：先解释“请求如何到达选中链路”；再解释“文本后错误在哪一层处理”；最后问“删掉Canonical，哪些重复语义重新出现，哪些能力其实仍未支持”。回答落在一条源码路径和一个反例，未知usage、私有协议与工具闭环直接归T04。架构违规应非零退出是待实现验收，现状只打印结果。

## 原始参考

[WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream)定义文本事件的帧边界，不保证交付时延；[Node child_process close](https://nodejs.org/api/child_process.html#event-close)解释进程退出与stdio关闭的区别；[RFC 9110重试语义](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)用于讨论重复执行风险。2026-10-02核验官方来源；当前CLI缓冲、聚合抛错与路由策略以本项目源码为证，官方资料不替代真实上游验证。

## 对抗十问（先闭卷，再看提示）

1. **Canonical 是否过度设计？** 看是否消除了多处重复语义；M+N 是结构描述，不是已测维护收益。只需单一文本转发时可采用更小方案。
2. **为什么自己解 SSE？** 需要控制字节、行、帧和结束边界；已有测试证明特定边界，不证明 SDK 都不适用。
3. **认证回退等于切换 Provider 吗？** 不等于。`src/providers/gateway/auth.ts` 的 refresh 失败后 cold exchange 属于同一链路认证回退；模型路由没有失败后自动换 Provider。
4. **私有协议变了怎么办？** 局部核对适配器并刷新证据；稳定性仍取决于上游，不保证下游绝对无感。
5. **verified 与 fixture verified 区别？** 前者需对应实际链路与时点，后者来自回放/参考值；合成测试不等于当前真机。
6. **为什么不直接用现成网关？** 本项目用于研究契约隔离；生产采用什么要按需求评估，不从个人实验推导产品优势。
7. **离线测试证明 Claude Code 工具循环吗？** 不证明。下游主要消费文本/usage/error，tool 往返、image 和当前客户端端到端仍属 T04。
8. **三条链路都是真实时流吗？** 不是；CLI 等完整 stdout。下游 Content-Type 或 SSE 帧不能替代时序测量。
9. **架构检查真的会让违规失败吗？** 当前不会，脚本只打印；不能把 CI step 的名字当保护效果。
10. **AI 参与后你能证明什么？** 能现场解释合同、测试断言和边界，给出提交与结果；不靠代码风格推定作者或独立原创。

## 事实、推断与待核验

- **事实**：源码三 Provider、三文本端点；本轮离线结果以 E03 为准，未调用真实上游。
- **推断**：契约隔离可能缩小变更影响，但本轮没有维护成本或性能对照实验。
- **待核验 T04**：Gateway 当前真机、下游工具/多模态、usage 真实口径、版本登记和架构硬阻断。不得写成已完成。
