# coding-agent：叙事三级与对抗十问

用途：P12 Agent Runtime、工具与一致性追问的证据长稿；按需回查，不把扩展新实践作为本轮日练任务。

P12，规范驱动的 Agent Runtime 实验。[事实与归属](../00-事实与简历/00-个人事实基线.md)、[E11](../00-事实与简历/05-项目归属与量化证据.md)是维护入口。源码 `2750877` / tag v0.6.0；runtime 元数据仍为 0.5.0。三场景 frozen，SC-004-A 为 draft，以场景源码为准。

## 30 秒（开场）

coding-agent 将行为规范与语言实现分开：七主题规范、TypeScript/Python/Go/Rust/C# 五实现，以及四个离线一致性场景。各实现对统一期望判定，当前验证的是关键边界，不是全部功能完全等价，也不是操作系统沙箱。

## 2 分钟（标准展开）

困难不是写出五份能运行的代码，而是让不同实现遵循同一行为约束。规范负责裁决，adapter 启动并采集，normalizer 转成观测项，diff 对 scenario.expect 判定。假 provider 控制工具往返，当前主要观察退出码、模型请求数、部分工具文案、输出标记和指定文件终态。编译型适配器先检查产物新鲜度，缺失或陈旧时重建，避免用陈旧二进制解释源码行为。

这四场景只是有限证据：输入契约、Plan Mode、补丁预验等被选中，取消、完整事件顺序、Anthropic 分片和会话恢复没有被四场景完整覆盖。补丁先全预验再逐文件写入，因此预验失败零写入；写盘失败不回滚，同文件多编辑还有后写覆盖前写的边界。本轮 TS 测试与探针见 E11，不写成五语言全套重跑或事务原子性证明。

## 5—8分钟独立口述稿

这是本人试讲后要校准的目标时长，尚无实际计时成绩；每次只选一份，占用既有项目练习时段。以下可脱离短稿口述，必要时停在证据与限制处接受追问。

coding-agent研究的问题是：当同一个Agent Runtime有多种语言实现时，怎样知道它们遵守同一行为约束。五份代码都能编译、都能回答一句话，并不能证明权限、工具、会话与事件语义一致。这个公开实验把规范、实现和一致性判定分开，希望用可执行场景暴露分歧。它目前有七主题规范和TypeScript、Python、Go、Rust、C#五实现，验证范围是被场景选中的关键边界，不是全部功能等价，也不是操作系统安全沙箱。

约束先于实现。规范描述loop、tool、session、context、permission、provider和event，语言实现对照这些约束，场景再定义输入与期望。参考实现有助于理解，但它也可能出错；多个实现恰好一致，也可能只是共同复制了同一个缺陷。遇到规范与实现冲突，应该说明裁决依据，而不是按多数行为决定正确。维护五实现有成本，只有研究语言中立语义时才有相应价值，不能因此说生产项目也必须做五份。

正常判定链路是adapter启动目标实现并采集，normalizer提取约定观测，diff对scenario.expect判断。fake provider控制工具往返，让场景不依赖真实上游。当前观测主要包含退出码、模型请求数、部分工具文案、输出标记和指定文件终态。编译型适配器会检查产物新鲜度，缺失或陈旧时重建，避免让旧二进制代表当前源码。这里比较的是每个实现对同一组期望，而不是五份完整日志两两比较；归一化留下什么，也决定判定看得见什么。

现有四场景是有限的切面。SC-001、SC-002A和SC-002B为frozen，SC-004-A仍是draft；旧Release更强的总体表述不能覆盖当前场景状态。取消、完整事件顺序、Anthropic分片和会话恢复，并没有因这四场景通过而得到完整覆盖。权限确认同样只是Runtime的行为控制，always或yolo表示会话放行，不会自动提供进程隔离、路径隔离与资源限制。把确认模式讲成沙箱，会把工程交互误当系统安全保证。

补丁工具是失败路径最清楚的例子。TypeScript实现先对所有编辑做预验，再逐文件写入，因此预验不通过时可以零写入。但后续写盘是另一阶段，一旦前一个文件写成功、后一个文件I/O失败，当前没有事务回滚。对同一文件多个编辑还存在分别从原内容计算、后写覆盖前写的边界。准确的表述是预验保护了一类失败，不是整个批次原子。即使工具最后报错，也要查看文件状态，不能把失败退出等同于没有产生副作用。

测试本身也可能假绿。SC-001的path参数与工具要求的file_path不匹配，工具原本就可能没有执行目标写入，后面的文件不变检查于是辨别力不足。SC-002A只采最终结果，没有审批前快照，因此不能完整证明确认前零写入。这两个反例说明，fail closed可以保守处理被观察到的差异，但无法补上没观察的时点或错误输入。要增强证据，先修正工具参数和观测点，定义一个错误实现必须失败的验收，而不是简单增加通过用例数量。

实际验证按E11登记：2026年10月2日的工作区副本用Node跑了TypeScript补丁与Plan Mode五项、TS四场景，并用边界探针复现前述问题。本轮没有重跑五语言全套，CI配置四场景乘五runtime也不是当前远端通过证据。这些结果支持选定TS行为和已复现限制；新一轮要证明跨语言当前一致，还需要相同提交、环境、输入和观测范围。不能把一份TS结果写成所有实现都已验证，更不能用结果数替代完整覆盖率。

如果面试官要求证明权限边界，我会先描述一个错误实现：它在确认前已经写入，确认后仍输出正确结果。只看最终文件会漏掉这个错误，所以需要观察副作用发生时点。这个方案是在讨论如何提高断言辨别力，不是我已经完成新一轮修复或获得全语言验证。

最后的取舍是规范必须可裁决，测试必须能发现错误，结论必须带范围。将来若处理补丁I/O，需要先决定原子写入、恢复或明确部分成功语义，再针对目标实现验收；本月只登记为T13，源码改造暂停。我能沿规范、adapter、观测和diff说明为什么一次通过成立、又在哪些地方不能成立。对未覆盖的能力，我会转成学习设计并说明还要检查什么，不把计划当作已经完成的安全或一致性能力。

## 一致性判定的原理与反例

**“相同”要先定义观察**：若normalizer只保留请求数和最终文件，两份实现可以在事件顺序、确认时点和取消行为上不同，却得到相同结果。场景通过的准确结论是满足被声明的expect；没采到的行为没有被证明。学习追问：删掉某个观察后，哪个错误实现又能通过？这比用语言数量宣称一致性更能说明测试能力。

**预验与提交是两个阶段**：当前补丁先检查所有输入，预验失败不开始写盘；提交阶段每个writeFile仍可能失败。可检查反例包含后一个目标不可写，以及同文件两次编辑；前者观察已写文件，后者观察两项编辑是否同时保留。E11已登记TS探针反证，不能因场景名含atomicity就改称事务。如何做原子提交或补偿是后续设计，本文未选择或实现新方案。

**TDD怎样用于增强判定**：学习方案先把SC-001工具参数对齐真实file_path，再检查Plan Mode下的请求、执行与文件；SC-002A则增加确认前观察。验收应让“确认前偷写”的实现失败，而不是只增加一次最终快照。先确认检查因目标缺口失败，再最小修复并重验，才有意义；本轮未动源码或新增框架。精确场景文件为 `SC-002A-apply-patch-success.mjs`、`SC-002B-apply-patch-atomicity.mjs`。

**分层追问**：先说谁裁决规范；再说adapter与normalizer分别留下什么；最后指出一个已登记假绿与一个未覆盖行为。对五语言全套、系统沙箱和补丁回滚只说明缺什么证据，不把frozen标签当覆盖率，也不把draft场景称成熟证明。

## 对抗十问（先闭卷，再看提示）

1. **五语言是不是五次翻译？** 要看规范与可执行断言如何约束语义；相同测试通过仍可能有共同缺陷，不能据此证明全部等价。
2. **为什么不只留 TS？** 多实现可暴露平台与规范歧义，但维护成本也增加；这是实验取舍，不是生产必需。
3. **五实现值得维护吗？** 以语言中立规范的验证目标衡量；没有测量就不宣称确定收益，也不把消融判断当实际实验。
4. **和集成测试区别？** 本套件为多个实现使用共同场景与期望；它同样受场景覆盖和断言辨别力限制。
5. **为什么参考实现不能直接当规范？** 实现也可能错，冲突需显式裁决；不能把多数实现行为自动当正确。
6. **fail closed 能消除假绿吗？** 对被观测的未知差异保守判定；没观测的写入时点、遗漏场景和参数错误仍可导致假绿。
7. **四场景覆盖哪些边界？** SC-001/002A/002B frozen，004-A draft；分别展开具体 expect，不称“生命周期最小完备证明”。
8. **权限确认等于沙箱吗？** 不等于；路径守卫主要提示，always/yolo 是会话放行，不是 OS 隔离。
9. **补丁能保证原子吗？** 只能说预验失败零写入；本轮探针复现后续 I/O 不回滚、同文件多编辑覆盖，不能声称事务原子。
10. **下一步怎么增强证据？** 修正场景参数、采确认前状态、测试失败回滚，再重跑相关实现；这是 T13 计划，本轮未实施源仓修复。

## 事实、推断与待核验

- **事实**：五实现、七主题、四场景与实际成熟度；本轮 TS 单测/场景/边界探针见 E11。
- **推断**：规范驱动有助于暴露漂移；没有全行为覆盖或安全隔离证明。
- **待核验 T13**：增强观测、五语言当前全套、补丁写盘故障与同文件多编辑。旧 Release 的强声明不能覆盖源码反证。
