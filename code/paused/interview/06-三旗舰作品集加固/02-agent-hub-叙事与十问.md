# agent-hub：叙事三级与对抗十问

用途：P11 流式 UI 或生成界面追问的个人公开演示长稿；按 JD 使用，不替代公司主讲实绩或加入全部项目日练。

P11，AI 应用工程演示。[事实与归属](../00-事实与简历/00-个人事实基线.md)、[E10](../00-事实与简历/05-项目归属与量化证据.md)是维护入口。源码基于 `d0b6873` / v0.1.1。讲述只展开流式、结构化卡片、证据展示、任务刷新恢复四条主线。

## 30 秒（开场）

agent-hub 是花卉选购场景的 AI 应用演示，把流式输出接到固定卡片、证据展示和任务恢复上。公开仓有契约、API、浏览器三层 CI，默认 mock 无需 API Key。它展示工程链路，不证明真实推荐质量、可信度算法或生产规模。

## 2 分钟（标准展开）

流式部分用 fetch 接收 POST 响应，先由 TextDecoder streaming 处理跨 chunk UTF-8，再按 SSE 帧解码；进入 store 前校验事件并归约有序 segment。卡片使用固定花束 schema 与固定组件，校验已声明字段，未知事件类型拒绝，额外字段默认剥离或忽略，不能说所有额外字段都会报错。

证据由服务端按场景附加 ID，随事件推送；抽屉从已接收数据展示来源、原文和分数。目前分数是演示 fixture，80 的阈值写在前端，没有检索或可信度计算。任务页面只保存 taskId，刷新后读取远端快照，对在途任务续轮询；epoch 避免旧轮询继续排程。公开 CI 与本轮局部测试分别记在 E10。页面刷新恢复不等于服务重启续跑，不能把后台仍运行的演示推导成持久化 worker 能力。

## 5—8分钟独立口述稿

这是本人试讲后要校准的目标时长，尚无实际计时成绩；每次只选一份，占用既有项目练习时段。以下可脱离短稿口述，必要时停在证据与限制处接受追问。

agent-hub选择的是花卉选购场景。我关心用户收到的并不只是一段回答，还可能包含花束卡片、依据和异步任务。如果只把所有内容拼成聊天文本，用户很难知道哪些是可操作数据、哪些只是解释，也很难判断生成失败以后还能不能继续使用。这个公开仓用默认mock把工程链路做成可演示状态；它验证的是事件、校验与界面行为，不把演示推荐称为真实业务效果，也不把公司团队的对话内核归为个人原创。

最先明确的约束是固定卡片和明确状态。模型不能任意生成组件代码，花束数据只能进入已声明schema和已知组件；Evidence负责展示来源和原文，分值先按演示fixture处理；异步任务可以凭taskId回查，但页面恢复与后台续跑分开说明。这些限制缩小了需要保证的范围。它不是任意动态UI，也不宣称完整实现官方A2UI；这里借助固定类型把结构化结果转成可检查的界面。

正常流式链路是POST请求进入服务，响应由fetch读取，先用TextDecoder的streaming模式恢复可能跨chunk的UTF-8字符，再把文本恢复为SSE帧。帧中的data还要经过JSON解析和事件schema校验，才能进入store归约成有序segment。字节块、事件帧和业务对象是不同边界，一次读取可能只有半帧，也可能含多帧。这样做的目的不是宣称自己写的解析器比标准组件更强，而是让每层的错误和观察点分开。EventSource可以关闭，当前采用fetch主要是POST数据、header和取消信号集成的需求。

结构化卡片还有下一道边界。服务端只有在card围栏闭合且解析校验成功后，才把对应内容作为卡片；非法或未闭合内容降级为文本。前端用固定组件承载合法数据。未知事件type或非法声明值会被拒绝，额外字段却默认被剥离或忽略，不能把这套行为统称为所有异常字段都会报错。合法卡片也未必推荐正确；类型校验能约束形状，不能替代库存、价格、权限或推荐质量的业务核对。涉及动作时还要看实际确认与服务端能力，按钮状态不能证明生产幂等。

依据展示同样有明确上限。服务端按场景附加Evidence ID，客户端抽屉展示已接收的来源、原文和分数。当前88、72、91是固定fixture值，80的展示阈值也写在前端，没有检索排序或分数校准算法。我会用它说明高低分分支和证据可见性，而不会解释成88%的正确率。排查引用问题还要同时看请求对象、结论、Evidence ID和原文，抽屉能打开只能证明呈现，不能证明原文真的支持结论。

任务链路独立于聊天展示。页面保存taskId，刷新后读取服务端快照，对在途任务继续轮询；epoch用于防止旧轮询继续排程。这能恢复用户对任务的观察，但不等于服务重启以后继续工作。当前后端启动会读回快照，没有为queued或running重新安排执行，因此“状态还在”可能只说明记录存在。重试也是重新创建任务，没有独立retry接口。我在讲失败时会问：旧请求晚到是否影响新页面，终态如何呈现，工作退出后谁负责继续；未做的恢复能力不会靠一个running字段补出来。

验证也按时点和范围分开。仓库有shared契约、API和浏览器CI；E10关联了当前提交的历史公开Success，Release记录17项shared、29项API和3项E2E。本轮登记的局部检查是SSE与bones的12项，没有把它写成完整套件重跑。测试仍有边界：任务存在随机失败分支，E2E不能因此被称为每次都稳定完成；两端fixture都通过，也不足以证明nullable、coercion和extra的所有语义一致。接入真实模型还需要新的输入分布、质量与故障证据，mock结果不能替代。

这个项目的取舍是先让最小链路可读、可演示、可检查，保留模型质量、证据算法、并发和后端重启续跑的限制。支付等演示也不能由沙箱推导到商用保证。我可以沿SSE解码、schema、store、卡片与任务页面逐段走读，并给出提交和历史验证范围；若面试转向生产化，我会明确改成设计讨论，说明需要哪类观察。本月仍以复习和投递为主，不为长稿扩展新的实践，也不把个人演示改写成公司全链路实绩。

### 联调时先检查三个边界

从旧笔记保留的故障经验，历史过程与当前源码状态分级登记在[证据台账的 P11 章节](../00-事实与简历/05-项目归属与量化证据.md#p11-模式来源与联调经验)：

- **帧不等于事件对象**：`services/agent.ts` 先 `JSON.parse(frame.data)`，损坏 JSON 报协议错误；`stores/chat.ts` 再做 schema 校验，不能直接把 `{event, data}` 当业务事件。
- **缺省不等于可空**：`.optional()` 接受字段缺省，`.nullish()` 还接受 `null`；任务 `result/failReason` 和订单 `paidAt` 对齐 Python `None`，不因此放宽必填业务字段。
- **store 初始化器不是组件**：AbortController 存普通闭包变量，不能在 Zustand `create()` 初始化器调用 `useRef`。

## 四条主线的推导与检查

**SSE分层的必要性**：字节解码解决跨UTF-8，帧解析解决事件完整性，JSON解决语法，schema解决已知形状，store解决状态归属。学习反例把一个合法事件拆成多个输入，再将两个事件合在一次输入，最终业务序列应一致；损坏JSON与未知type则应停在对应边界。E10只有指定局部测试结果，不能借这组建议宣称所有拆分方式已穷举。

**固定卡片为何更小**：让模型提供声明数据，由固定组件负责渲染，减少任意代码进入页面的范围。可检查样例是必填字段缺失、未知卡片类型和额外无关字段：前两项与extra要各按schema策略判断。Zod默认strip与Pydantic默认ignore不意味着两端完全等价；业务字段约束、coercion与nullable还需逐例核对。非法围栏降级文本也应让用户知道无法获得完整卡片，不靠猜测补字段。

**Evidence如何避免假确定性**：当前能检查ID是否连接到已接收Evidence、来源与原文是否展示、阈值分支怎样出现。它不能检查一个尚不存在的可信度算法。学习反例是合法ID连接了错误对象，UI格式仍可能正确；下一层验收需观察结论与证据归属。88分不换算概率，低分提示也不自动证明高分内容可信。

**任务恢复为何拆开**：页面刷新案例检查taskId回读和续轮询；后端重启案例检查未终结任务是否真的有执行者。源码 `main.py` 调用 `restore_snapshots()`，实际只读回记录，不能凭“恢复在途任务”的注释升级结论。`tasks-page.tsx` 的epoch会在响应到达后检查，防旧链更新及继续排程，但它不是服务端任务锁，也不证明旧工作已被取消。

### 分层追问

开口层：用一句话分别说“事件可消费”“数据可渲染”“依据可核对”“状态可回查”。机制层：任选一条走到源码，不同时讲四条。深挖层：构造“字段全合法但推荐错误”或“running快照存在但无人执行”的反例，说明哪个检查能发现、哪个现有检查看不见。若问真实质量、并发或持续恢复，转为T12设计讨论；本月没有新增服务或完整测试重跑。

## 对抗十问（先闭卷，再看提示）

1. **和聊天页面区别在哪？** 解释事件、校验、状态与动作边界；不把未做的消融实验说成已验证。
2. **模型能任意生成 UI 吗？** 只能进入固定卡片数据；字段合法不等于推荐正确，也不等于脚本/业务语义全部可信。
3. **为什么不用 EventSource？** 本链路要 POST JSON、自定义 header 和 AbortSignal 集成；EventSource 自身可以 close()，不能说完全不能中断。
4. **为什么 chunk 不能直接 parse？** 字节可能切在多字节字符或帧中间，逐层恢复边界后再 parse/schema；不要混用字符与网络帧。
5. **88 分怎么来的？** fixture 固定值，不是算法计算。80 阈值也固定在前端，当前不能称运营可调。
6. **布尔 loading 为什么不够？** 六状态与动作条件需要表达不同终态；当前重试是重新创建任务，没有独立 retry API。
7. **刷新与后端重启恢复相同吗？** 不同；页面刷新时后台仍运行，服务重启只读快照，没有续启 running/queued 工作。
8. **支付演示能直接商用吗？** 不能。沙箱不证明真实验签、持久化、并发幂等、金额核对或商户接入，非主线能力。
9. **两端 fixture 都通过就语义等价吗？** 不足以证明 coercion、extra、nullable 等全部行为一致，仍需逐边界断言。
10. **怎样说明个人与公司边界？** 按证据台账的模式来源表说明卡片、依据与任务的职责；团队流式内核与对话交互主体为同事。公共仓证明演示实现，不改写公司归属，也不公开内部资料。

## 事实、推断与待核验

- **事实**：固定 schema、fixture Evidence、页面刷新续追；本轮局部测试与历史 CI 范围见 E10。
- **推断**：这些分层可迁移到其他业务；没有因此证明公司全链路均由本人实现或真实推荐有效。
- **待核验 T12**：生产模型质量、证据评分、后端重启续跑、稳定失败分支与并发。公司材料是职责底稿，不能作为公开仓生产成效证明。
