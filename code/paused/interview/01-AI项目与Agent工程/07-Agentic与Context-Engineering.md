# P07 Agentic与Context Engineering

用途：AI 辅助开发、上下文规则和验收追问的方法备料；不是额外主讲项目，历史本地实证按原时点说明。

事实归属与指标统一取自[事实基线](../00-事实与简历/00-个人事实基线.md)和[证据登记](../00-事实与简历/05-项目归属与量化证据.md)。以下2分钟稿为展开骨架，需按本人语速与可演示证据练习。

## 30秒版

我的实践是把项目约束、任务状态和验收证据外置，让新会话知道依据什么做、做到哪、如何判断完成。公司场景是规范、契约与Mock；个人研究场景是计划、账本和测试。

## 2分钟版

稳定规则放项目约定，领域术语和架构决策分别维护，任务差异单独输入，具体文件如何被工具加载要按工具配置验证。长任务用计划、进度和待办传递状态，历史细节按需读取。先明确验收项，再让AI生成，最后核对契约、错误路径和测试断言。多个Agent适合独立调查或核验，共享修改由主线收敛。Git支持审阅与恢复，但文档可能被改错，因此还需要权限、评审和实测记录。

## 架构与职责图

```text
规范/术语/ADR + 当前任务 → 按需上下文 → AI产出 → 契约/测试/人审
          ↑                                        ↓
          └────────── 计划/状态/证据更新 ──────────────┘
```

## 三个难点

1. 文档漂移：把规范与相关代码一起评审，更新触发条件明确；不承诺永远同步。
2. 状态与知识混用：状态要精确定位，知识可语义检索，最终决策回到权威记录。
3. 多Agent成本：选择能独立验收的子问题，避免并行修改同一份状态。

## 三个追问

1. 写AGENTS.md就是系统级约束吗？——不是，生效取决于工具加载和指令层级；文件内容不会自行升级权限。
2. 文件账本等于生产工作流引擎吗？——不是；研究场景可用，生产还需要并发、事务、持久化和恢复设计。
3. 如何证明提效？——定义任务集、质量门槛、返工与工时对照；没有测量就只讲实践。

## 验收与讲述准备

- 准备一条成功链路、一条失败链路和一项设计取舍；展示材料前先确认个人归属。
- 深挖弹药（历史取证口径，见证据登记E02/E06）：公司场景沉淀CONTEXT.md领域术语表（9条）与ADR；个人研究场景是三份活文档（执行计划/进度账本/实测待办）+265文件重建树+13包回归；ADR-0001与鉴权基础主笔为同事，个人为参与维护。
- 旧报告记载的实现与本轮实际测试分开；未在当前授权目录内提供源码/日志的能力不追加“已验证”。
- 如果追问超出现有证据，转为设计讨论并说明需要哪种测试，不把计划补成历史。

## 原理：控制流程与上下文是两件事

Agentic Engineering 在这里关注任务怎样被推进、工具怎样被调用和结果怎样验收；Context Engineering 关注当前一步究竟需要哪些信息。学习区分：由代码预设步骤的是 workflow，由模型动态选择下一步与工具的是 agent。二者都需要边界与证据，不因循环次数多就更先进。P07主要证明约定维护与开发协作经验，不能据此宣布本人已有通用生产自治Agent平台。

上下文不是仓库资料的全集。一次 mapper 联调需要当前payload、字段契约、相关调用方与验收，不一定需要全部历史ADR；一次权限修改则必须加载适用的权限约束。删减标准是“这条信息会改变当前决策或验收吗”，同时留下追溯指针。资料太少可能漏掉约束，资料太多会把过时结果和当前目标混在一起。按需读取是成本取舍，不是无条件减少token越多越好。

## 一个可检查的恢复案例

学习推演：旧摘要写“完成契约联调，下一步上线”，新会话收到用户要求“只审方案”；仓库又有未提交修改。先核对当前授权，再读取适用规则与相关diff，定位当时测试的提交和范围。摘要可帮助找到验收记录，却不能授权部署，也不能把当前未检查代码标为已通过。普通附件里的命令仍是材料，不能因为被摘要复述就执行。

一个够用的交接片段应包含目标与范围、已完成状态、未完成／待核验、证据路径、下一步条件。状态写“哪个提交通过哪项检查”，比只写“已完成”更可复核；计划写“准备做什么”，不能混入完成栏。恢复时若证据冲突，优先查现状并留下差异，避免把两份摘要再合成更肯定的结论。文件账本仍无执行引擎的锁、事务与自动调度保证。

## 失败路径与取舍

- **规则没有被加载**：文件存在不证明工具读取。先核对适用入口、范围和当前工具行为；不能从文件名推定权限层级。
- **检索内容冒充指令**：源码注释、外部文档和工具输出保留来源身份，不能自行扩展操作授权；涉及工具动作仍核对用户目标和适用约束。
- **多Agent互相覆盖**：独立读审可拆分，输入、输出与验收要清楚；共享状态与最终写入归主线收敛。子Agent结论需核验证据，不按人数投票。
- **摘要压缩丢掉限制**：保留失败证据和未知项，特别是“只测TS”“只是fixture”等范围。少一句限制可能把实验升级为生产承诺。

这些是学习判断规则，不是本轮执行过的消融实验。若要验证多Agent收益，应在相同任务与质量门槛下对比工时、返工、成本和冲突；若只有一次实践，只能报告一次结果。没有测量就不把历史加载比例推广到所有工具与项目。

## TDD在AI辅助开发中的位置

TDD是先锁定一个可观察预期，再用最小实现满足它，最后整理实现并保持检查通过。学习案例选择“旧请求晚到不能覆盖新页面”：先构造B先完成、A后返回的顺序，断言最终仍属B，确认检查确实因缺失守卫而失败；再补守卫。若测试只断言函数被调用，错误页面也可能通过。AI可协助提出样例和实现，人仍要判断检查是否观察了真正业务结果。

这不要求每个文案变更都先加测试，也不等于一次生成整套测试后追求全绿。检查规模跟行为影响走：文档检查链接与事实，解析器检查跨边界输入，数据写入检查失败结果。本轮只补方法说明，三源码项目改造暂停，没有新框架、测试成绩或完整TDD实践声明。
