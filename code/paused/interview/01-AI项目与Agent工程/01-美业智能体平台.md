# P01 美业智能体平台

用途：按 JD 的平台业务模块或结构化卡片追问回查；本轮不作为日练主讲。

事实归属与指标统一取自[事实基线](../00-事实与简历/00-个人事实基线.md)和[证据登记](../00-事实与简历/05-项目归属与量化证据.md)。以下2分钟稿为展开骨架，需按本人语速与可演示证据练习。

## 30秒版

我负责平台中预约、顾客回访、护理报告，以及品牌端结构化卡片和接口接入。我的重点是把AI建议变成可核对、可执行的业务界面；模型分析和对话内核是团队协作能力。

## 2分钟版

平台服务美容师、顾问、店长及顾客，不是单一聊天窗口。我的工作先从具体动作出发：预约需要资源与时段，回访需要待办类型和时间，护理报告需要一致的数据口径，推荐需要可交互商品卡片。通过映射层将接口数据与UI分开，页面处理生成中、空值和失败，再衔接人工确认或记录回写。我没有实现整个智能体内核，也不把使用团队鉴权组件写成原创基础设施。

## 架构与职责图

```text
团队AI/业务服务 → 契约与mapper → 卡片/预约/回访/报告 → 人工动作 → 业务记录
```

## 三个难点

1. 接口字段分散：集中维护类型、枚举与mapper，避免每个页面重新解释数据。
2. 生成任务与页面生命周期不同：加载、生成中、失败和返回刷新分别管理。
3. 跨端主题与交互：复用卡片结构，主题用变量，平板和小程序交互单独验收。

## 三个追问

1. 你负责整个智能体吗？——负责业务UI与若干服务；SSE内核和深度思考组件归团队同事。
2. A2UI是采用某个标准协议吗？——这里首先是项目内组件与结构化渲染模式，协议一致性需要另行验证。
3. 怎样证明效果？——展示已交付流程及验收记录，不用无测量的转化率或采纳率。

## 验收与讲述准备

- 准备一条成功链路、一条失败链路和一项设计取舍；展示材料前先确认个人归属。
- 深挖弹药（历史取证口径，见证据登记E02）：预约助手88次提交为模块主要作者、ScheduleTimeline 24次独写；本人模块集中在预约/回访/护理报告与品牌端卡片；skincare-coach-ai与网咨助手本人提交为0，属同事主笔区，不展开为个人作品。
- 旧报告记载的实现与本轮实际测试分开；未在当前授权目录内提供源码/日志的能力不追加“已验证”。
- 如果追问超出现有证据，转为设计讨论并说明需要哪种测试，不把计划补成历史。

## 递进深挖：从业务动作定位组件边界

讲平台时先选一个本人模块。不要从“平台用了多少 Agent”开场，否则追问很快落到没有原创归属的对话内核。预约看板适合状态与交互题，回访适合字段映射题，商品卡片适合结构化输出题。

| 本人范围，历史 E02 | 要解释的关键边界 | 可以准备的物证 | 不能顺势扩大的声明 |
|---|---|---|---|
| 预约助手与资源时间轴 | 日历视图表达资源和时段；后端负责最终预约是否有效 | 一个拖动或编辑流程、冲突响应、对应贡献路径 | 前端校验消除了服务端并发冲突 |
| 我的顾客与回访待办 | 后端待办类型到业务标签、时间偏移和操作入口的映射 | `relationType` 五类与 `offsetDays` 历史记录 | 本人实现了话术生成算法 |
| 护理报告 | 原始评价数据到报告展示的归一化 | 正常、缺字段、无评价的对照材料 | 所有报告字段均由本人定义 |
| 品牌端商品卡片与 BottomSheet | 后端结构化数据转为固定组件和人工动作 | 场景枚举、价格格式化、半屏关闭重开 | 任意模型输出都能安全变成任意 UI |

**案例展开，R 级历史经验**：回访待办里的 `offsetDays` 曾有数字、数字字符串、带“天”的文案三种输入形态。讲述重点是先界定可接受输入，再集中归一化；组件拿统一时间含义，不自行反复拆字符串。原底稿记录了这一处理，但当前没有重跑公司源码。不能把历史兼容范围无限扩大为“接受所有自然语言时间”。

**反例推演**：值是 `0`、空串或非法负数时，直接 `Number(value) || 默认值` 会把合法零值和失败混在一起。应分别问业务零值是否有效、缺失是否有默认值、非法值怎样降级。这是复习时的契约设计练习，不是声称旧模块已经覆盖这三个边界。

## 失败路径与状态所有权

| 追问场景，学习推演 | 怎样拆问题 | 最小验证条件 |
|---|---|---|
| 预约保存时资源被别人占用 | 页面上的可选状态只是快照；提交结果由服务端裁决，冲突后刷新相关资源 | 两客户端并发提交，冲突客户端不显示成功 |
| 关闭回访弹窗后再次打开 | 弹窗草稿属于本次交互；业务记录属于顾客；明确哪些字段清场、哪些重取 | A 顾客关闭后开 B 顾客，没有 A 的草稿或加载结果 |
| 商品卡片缺价格或未知场景 | 缺失字段与值为零分开；未知场景采用明确占位或拒绝渲染 | UI 不编造价格，不把未知枚举映射成默认推荐 |
| AI 生成中切换页面 | 组件生命周期、请求生命周期与后台任务生命周期分开 | 旧响应不能更新新页面；离开页面不被说成已取消后台任务 |

共享的是 mapper、契约及确有共性的卡片骨架；预约时间轴与护理报告布局没有必要塞进一个通用大组件。高内聚低耦合在这里是“变更理由相同的放一起”，不是目录层级越多越好。协议解析由团队内核负责，业务组件只消费确认后的数据；这条职责边界与 E07 一致。

## 对抗式追问与闭卷练习

先遮住本卡，用 90 秒画出“接口字段→mapper→业务动作”。随后挑一项继续回答：为什么不在组件里映射？上游改枚举时哪一层变化？两人同时预约时前端能保证什么？关闭弹窗为什么可能仍有请求返回？每个回答至少带一个具体字段或操作和一个失败条件。

若面试官说“这都是普通前端，AI 在哪里”，回答：AI 改变的是建议来源和生成时机，我的工程价值仍是把不确定输出组织为用户可核对的业务动作。不要为了 AI 标签把本人范围改成模型训练、对话内核或后台评分。

本卡的不自信点是当前公司模块的精确枚举、预约并发处理和跨端验收结果；只有历史证据，没有本轮源码与故障测试。需要讲底层算法时先划清学习理解与本人交付，再引用[待核验清单](../00-事实与简历/06-待核验清单.md)。
