# P02 AI音频编辑与Node BFF

用途：AI 产品前端主讲二；先讲用户操作、任务状态与失败路径，再按追问展开 Node 服务链。

事实归属与指标统一取自[事实基线](../00-事实与简历/00-个人事实基线.md)和[证据登记](../00-事实与简历/05-项目归属与量化证据.md)。以下2分钟稿为展开骨架，需按本人语速与可演示证据练习。

## 30秒版

我独立负责音频编辑小程序子包，主导Node BFF。主链是小程序创建任务、Java承接业务、Node调用ffmpeg处理音频并写入COS，再由回调和轮询呈现状态，用户精修后确认保存。

## 2分钟版

难点不是调用一次ffmpeg，而是长任务横跨页面、业务服务和处理服务。前端根据任务状态展示波形、裁剪与失败反馈，重进页面通过audioId查回详情。Node管理源文件下载、处理、上传和回调，保存快照并处理超时与临时文件。我还做Java Mock BFF，让正式接口未就绪时也能按约定联调。恢复界面状态、进程重启后重跑与从处理中间点续跑是不同能力，现有材料不足以把它们统称为完全断点续跑。

## 架构与职责图

```text
小程序 → Java任务接口 → Node BFF → ffmpeg/ffprobe → COS
   ↑            ↑              ↓
详情轮询 ← 任务状态记录 ← 状态回调 → 人工确认保存
```

## 三个难点

1. 状态跨服务：以业务任务详情为页面依据，回调负责回写，轮询负责查询；前端轮询不自动修复服务端丢失回调。
2. 大文件与波形：按接口用途区分超时，处理分块上传、波形显示和裁剪边界。
3. 资源回收：任务成功、失败、超时、取消均应检查文件和子进程生命周期。

## 三个追问

1. jobId/runId/audioId怎样区分？——audioId恢复详情有旧记录；具体jobId/runId字段和幂等实现列T06，不临场杜撰。
2. 重复或乱序回调怎么办？——设计上可用尝试号、状态版本、终态约束；本项目是否已实现需源码与故障测试。
3. 为什么拆8089？——音频工具处理与客户识别流程职责不同，共享底层音频能力，避免业务逻辑相互侵入。

## 验收与讲述准备

- 准备一条成功链路、一条失败链路和一项设计取舍；展示材料前先确认个人归属。
- 深挖弹药（历史取证口径，见证据登记E02）：接口超时按"最长合理耗时"分三档——普通接口15s、波形处理10min、轮询间隔3s；波形组件族12个组件复用；Node BFF与前端提交数为仓库第一贡献者。
- 旧报告记载的实现与本轮实际测试分开；未在当前授权目录内提供源码/日志的能力不追加“已验证”。
- 如果追问超出现有证据，转为设计讨论并说明需要哪种测试，不把计划补成历史。

## 5—8分钟口述底稿

以下是完整展开稿。事实沿用 E02 的历史职责材料；故障处理设计明确用“如果”“我会”表达。时间按实际录音校准，可在架构段或取舍段结束，不把标题时长当作已经练习达标。

### 业务与本人职责

这个项目面向门店咨询和运营人员，录音进入 AI 处理后，用户还需要看波形、试听、裁剪，再确认保存。产品的关键不是展示一个“AI 已完成”的提示，而是让生成结果进入人工精修流程。我独立负责小程序音频编辑子包，主导 Node BFF，也独立开发了 Java Mock BFF。识别或生成能力与业务服务有团队分工，我不把 ffmpeg 工具调用说成训练过音频模型。

### 主链和数据所有权

主链是小程序请求 Java 创建任务，Java 承接业务任务，Node 下载源音频、调度 ffmpeg 和 ffprobe、把结果写入 COS，再回调业务侧；前端查询任务详情，呈现可编辑结果，最后由用户确认保存。这里有三种不同的数据：业务任务和确认记录、处理服务的运行状态、页面播放与裁剪草稿。页面以业务详情解释当前状态；播放位置和临时裁剪不能反过来充当任务已完成的证据。Node 的回调负责把处理结果传回业务系统，前端轮询只是读取，不能自动补救服务端丢失的回调。

正式接口未就绪时，我还开发 Java Mock BFF 支持按契约联调。它的价值是让前端先验证请求、状态映射和交互，不让开发完全卡在上游排期；代价是 Mock 与真实接口可能漂移，所以仍要逐字段核对。模拟返回成功不证明真实音频处理成功，Mock 里的顺序也不能替代乱序和超时测试。

### 前端如何把长任务变成可操作界面

历史材料记录了 Java 状态到页面状态的集中映射，以及波形、播放、手动裁剪和预览组件。这样用户看到的是可理解的业务阶段，而不是每个 worker 的内部步骤。波形未就绪时，不能让用户对不存在的峰值做裁剪；裁剪还要解释时间单位、容器坐标和左右边界，不能只保证“画得出来”。旧记录中普通接口和波形接口的超时不同，这是根据动作预期耗时分层；轮询的三秒是查询间隔，不是任务必须在三秒内完成。具体常量属于历史快照，投递前应重新核实。

### Node 编排和失败路径

Node 在这里主要做异步 I/O、任务编排和子进程管理，重的音频计算交给 ffmpeg 进程；“Node 非阻塞”不代表 CPU、内存、磁盘和带宽无限。我会沿下载、探测、处理、上传、回调逐步问：失败时是否还有有效产物，重试会不会重复执行，临时文件何时可以删，进程是否真正退出。例如上传成功、回调超时，如果无脑重跑整个处理链，会浪费计算并可能生成第二份结果。合理设计是区分处理完成与业务回写完成，保存必要结果标识，再重试回写；这属于故障推演，目前没有源码证据证明旧服务已经实现相同策略。

### 恢复语义与方案取舍

前端重进页面可以用 audioId 重拉详情；历史材料也提到本地任务快照。但是页面恢复、服务重启后重新调度、ffmpeg 从处理中间点继续，是三种能力。我能讲页面重拉详情与保存快照的历史记录，但材料不足以确认服务重启会重新执行在途任务，更不能说完全断点续跑。要证明重启恢复，需要处理中杀掉服务、保留快照、重启后看任务是否重新调度并最终回写；仅看到页面恢复转圈不能证明 worker 恢复。回调加轮询是业务已有链路上的选择，不必为了长任务就引入 WebSocket；若需求变成高频双向控制，再比较新方案的连接和运维成本。

### 如何证明质量与个人价值

我准备的证据是本人模块贡献、状态映射、关键交互和一条完整处理链，数字统一从 E02 的登记取。现在不能提供当前业务源码及故障测试，我会坦率说明验证边界，不报没有基线的性能提升比例。被追问“AI 写了多少”时，我拿一个状态变化或失败路径讲出需求、代码位置和验证条件；代码生成方式不能替代我对结果负责。这个案例最能证明的是，我能把 AI 任务接进业务，管理用户交互和 Node 处理链的边界，并知道还要补哪些故障证据。

## 故障矩阵：把追问转成可验证条件

以下是学习推演，不是已完成测试清单。

| 注入点 | 不能混为一谈的状态 | 观察和判定 |
|---|---|---|
| URL 不可下载或格式不可识别 | 输入失败与处理失败 | 不派生成功结果，错误能定位到下载或探测阶段 |
| ffmpeg 超时或收到取消 | 已发终止信号与进程已结束 | 检查退出、日志管道和资源回收，不只检查取消按钮变灰 |
| COS 上传失败 | 本地处理成功与对用户可用 | 不发布无效结果地址；重试范围由保留产物决定 |
| 回调重复或乱序 | 同一次运行与后续尝试 | 需要业务身份、尝试号或版本约束；具体字段列 T06 |
| 用户关闭页面再进入 | 页面轮询停止与后台任务取消 | 按 audioId 查详情，确认新页面只接收当前任务结果 |

**追问“幂等就是不重复执行吗”**：先定义同一请求身份、保留多久、并发请求怎样竞争以及返回什么。仅在内存里记一个标志，进程重启后就可能失效；同状态重复回调也不能证明整条处理链恰好执行一次。具体方案要由业务存储和当前源码回答。

**追问“为什么不用消息队列”**：先看已有任务吞吐、积压、重试和持久化是否满足要求。消息队列增加投递与消费语义，不会自动解决重复处理或错误回写。没有积压和恢复证据，不能借架构名词代替判断。

## 官方参考与闭卷落点

- [Node.js child_process](https://nodejs.org/api/child_process.html)：重点读 `spawn`、`error`、`exit`、`close`。`close` 还涉及 stdio 关闭；参数不要拼进 shell，子进程日志必须消费或明确忽略，才能避免管道阻塞。复习时画出“发信号→退出→流关闭→清理”的区别。
- [ffprobe](https://ffmpeg.org/ffprobe.html)：看 `-show_format`、`-show_streams`、`-show_entries`，理解容器、流和输出字段。练习用一份本地音频解释为何文件后缀不足以确定可处理格式；当前没有运行新的音频实验。
