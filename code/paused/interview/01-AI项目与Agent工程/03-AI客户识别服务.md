# P03 AI客户识别服务

用途：P02 的服务拆分、输入快照与外部能力接入追问备料；按需回查，不另列日练。

事实归属与指标统一取自[事实基线](../00-事实与简历/00-个人事实基线.md)和[证据登记](../00-事实与简历/05-项目归属与量化证据.md)。以下2分钟稿为展开骨架，需按本人语速与可演示证据练习。

## 30秒版

我开发了从音频编辑服务拆分出的客户识别服务，重点是流程编排、输入快照、面诊来源与provider适配。识别算法属于外部能力，我负责把它组织为可追踪、可测试的服务。

## 2分钟版

服务按识别运行、客户池、面诊输入源、识别器和转写通道分能力。HTTP接入与应用、领域、基础设施职责分开，通过适配层承接不同provider和存储实现，共享audio-runtime中的音频处理与对象存储能力。输入快照记录“这一轮实际输入什么”，便于区分数据源变化和provider变化。旧报告记载契约、单元、冒烟、规模与属性测试，但本轮未重跑业务测试；review/retry的接口与重试语义仍需回源码确认。

## 架构与职责图

```text
面诊输入源 → 输入快照 → 识别运行 → provider/转写通道 → 运行记录/业务消费
                         ↓
               共享audio-runtime与存储适配
```

## 三个难点

1. 能力边界：流程决定调用顺序，provider实现外部调用，HTTP层不承载识别规则。
2. 可重现性：保存实际输入与版本线索，区分输入变化、模型变化和代码变化。
3. 共享与独立：共享底层音频能力，不让识别域反向耦合音频编辑的业务接口。

## 三个追问

1. 输入快照能保证相同输出吗？——只能帮助重现输入条件，模型随机性和版本变化还需记录。
2. review/retry是否上线？——旧文档提到设计，精确契约及实测列T06，现场只展开已能证明的部分。
3. 属性测试测什么？——输入组合与不变量，不是证明模型识别准确率。

## 验收与讲述准备

- 准备一条成功链路、一条失败链路和一项设计取舍；展示材料前先确认个人归属。
- 旧报告记载的实现与本轮实际测试分开；未在当前授权目录内提供源码/日志的能力不追加“已验证”。
- 如果追问超出现有证据，转为设计讨论并说明需要哪种测试，不把计划补成历史。

## 递进深挖：为什么拆服务，边界落在哪里

历史资料说识别能力从音频编辑服务演进出来，工具处理与客户识别流程开始有不同的业务责任。口述时先讲这个变化，再讲 capabilities 和端口适配器。仅“代码变多”不足以证明应该拆服务：拆分也增加部署、鉴权、接口和共享代码版本成本。

| 责任 | 该层决定什么 | 不该顺手承担什么 |
|---|---|---|
| HTTP 接入 | 请求结构、调用者身份、响应与错误格式 | 模型选择规则、客户确认规则 |
| 识别运行编排 | 输入快照、调用顺序、运行状态及结果交接 | 供应商 HTTP 字段在整个领域传播 |
| provider／转写适配 | 外部协议、超时、错误到内部结果的转换 | 将供应商默认值直接当业务结论 |
| 客户池与面诊输入源 | 业务输入来源和消费语义 | 与音频编辑页面状态互相依赖 |
| audio-runtime | 可复用的音频与存储基础能力 | 把两个业务域拼成一个全局万能服务 |

表格是复习时的职责解释；具体文件职责仍需回源码核验。旧材料登记了这些能力域及层次，不证明所有实现都遵循理想依赖方向，也不证明两服务生产隔离、独立扩缩容已经实测。

## 一个可展开的案例：结果不对，到底是哪一步不对

**已知历史事实，E02/R**：服务维护 run 级输入快照，并适配面诊输入源、识别器和转写通道。它回答的第一个问题是“这一轮喂入了什么”，不是“结果必然正确”。

**学习推演**：顾问发现客户匹配错了，先比较输入音频、截片参数、面诊材料、provider／通道及版本线索。如果这两轮输入不同，不能归因于代码；如果输入相同但模型版本不同，也不能直接归因于随机性。能够冻结的条件冻结，不能冻结的条件记录差异；没有原始输入和关联标识时，所谓“可复现”只是猜测。

最小充分快照是支持诊断所需的输入与配置，不是把所有客户原文永久复制一遍。素材敏感时还要回答访问范围、保留时间和脱敏；本库没有这些公司策略的当前证据，因此把它们当设计要求，不宣称已经落地。快照可用于重放输入，结果验收仍需样本标注和错误分类，不能靠“属性测试通过”替代识别质量评测。

## 失败路径与测试分层

以下测试条件用于理解工程边界，尚未在本轮执行。

| 层次 | 可构造输入／故障 | 要证明的条件 | 证明不了什么 |
|---|---|---|---|
| 契约 | 缺字段、错误枚举、外部响应变化 | 无效结构在边界被识别，错误可归类 | 识别准确率 |
| 单元 | 固定 provider 结果、同输入参数 | 编排与映射确定，业务规则不泄漏到 HTTP 层 | 外部能力可用性 |
| 属性 | 任意截片边界、空片段、乱序参数 | 已定义的不变量保持，例如区间不越界 | 所有业务组合永远正确 |
| 冒烟 | 一条可控端到端输入 | 接入、运行、消费能连通 | 规模与持续稳定性 |
| 容量／故障 | 外部超时、失败重试、并发增大 | 超时边界、资源有界和错误归因 | 无真实测量时的生产吞吐 |

provider 超时以后重试，至少要问外部调用有没有副作用、上一轮是否仍在执行、重试预算怎样限制。若 review 和 retry 是独立动作，不能把“重新请求”默认当成覆盖原结果；运行身份、审阅结论和新尝试应该可区分。现有资料不足以确认精确契约，这仍列 T06。

## 对抗式追问与学习验收

“新增 provider 真的是零改动吗？”——适配层减少影响范围，新增配置、测试和运维往往仍要改；我不会以接口抽象保证零改动。“为何不用一个函数完成？”——小流程可以先用函数，直到外部协议、存储或生命周期出现真实变化，再围绕变化点隔离。“如何评价识别效果？”——需要定义样本、标签、误匹配和漏匹配成本，比较同条件结果；本项目没有可引用的当前准确率。

闭卷用 3 分钟画出一次 run，并指出在哪保存输入、在哪调用外部能力、在哪交给业务确认。然后换一个 provider 超时的反例，说明哪些记录要留下，哪些资源要回收；答不出具体运行身份时，记为待核验，不自己创造字段名。

## 一手参考

- [Alistair Cockburn：Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture)：读端口与适配器如何让应用脱离外部技术；用 provider 替换解释思想，不以目录分层数量判断架构质量。
- [Fastify：Validation and Serialization](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)：检查请求验证与响应 schema 的职责，理解接口契约为何要在边界核对。框架文档不是本项目的契约证据。
- [fast-check：Why Property-Based Testing](https://fast-check.dev/docs/introduction/why-property-based/)：理解生成输入和缩小反例；练习为截片参数写一个明确不变量，避免把“没有抛异常”当成唯一正确性标准。
