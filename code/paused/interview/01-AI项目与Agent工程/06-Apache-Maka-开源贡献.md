# P06 Apache Maka（孵化中）开源贡献

用途：开源协作、review 或性能测量追问的公开备料；按需选择具体 PR，不作为额外日练项目。

事实归属与指标统一取自[事实基线](../00-事实与简历/00-个人事实基线.md)和[证据登记](../00-事实与简历/05-项目归属与量化证据.md)。以下2分钟稿为展开骨架，需按本人语速与可演示证据练习。

## 30秒版

我作为社区贡献者参与AI Agent工作区的问题修复、测试与文档审计，围绕结构化消息、重放和会话处理接受维护者评审。价值在明确范围、验证修改和处理反馈，而不是把合并数量当架构所有权。

## 2分钟版

社区代码有自己的契约和维护者判断。我先根据issue或文档建立调用链理解，选定最小修改范围，补充测试，再提交PR并逐条回应review。旧材料中的#4815案例涉及结构化消息准入、持久化和重放可见性，多轮反馈推动实现与测试边界收敛。AI可以帮助分析和编码，但提交者仍负责证据与结果。历史PR数量放在证据登记，不在每份话术重复维护，也不把所有关闭PR解释为质量无拒。

## 架构与职责图

```text
Issue/文档差异 → 调用链与契约 → 最小补丁/测试 → PR → Review/CI → 维护者决定
```

## 三个难点

1. 陌生系统：先找边界、持久化与重放路径，再决定修改点。
2. 评审收敛：意见、改动与测试一一对应，区分已回应和已被维护者接受。
3. 验证独立性：AI预审提供线索，测试结果与社区评审提供不同视角。

## 三个追问

1. 你设计整个Agent运行时吗？——没有，我是具体模块的贡献者。
2. 多少PR已合并？——数字以E04指定快照为准，投递前刷新，不沿用“最新/全部”。
3. AI生成算什么贡献？——本人负责选题、判断、验证、署名与回应，工具只是生产方式。

## 性能测量方法论（2分钟延伸话术）

四条 CI/perf PR（#5791/#5800/#5804/#5805，E04 指定核验快照中为 open；开放不等于已被 review 或接受）合起来讲一个方法论故事，用于"性能优化怎么做"类追问的差异化回答：

1. **先有预算线，再谈优化**（#5800）：两个传输优化分别落地并分析过，但"长会话 @30ms RTT：打开到可见尾部 p95 ≤ 800ms"这条预算线从未被端到端计时——优化没有组合测量等于没验收。测量脚本对每个 RPC 建模真实往返（请求飞行 + 服务端 CPU + 响应飞行），走生产订阅路径解码。
2. **测量必须可重复，锚点分开计时**（#5791）：启动剖析没有可重复的本地测量就没有基线。脚本用真实组合路径种子化 fixture，把 open（组合构建）/recover（五阶段模块恢复）/firstQuery（恢复后首个查询）/close（有序关闭）四个锚点分别计时，报每轮表和中位数——不报一个混在一起的"启动时间"。
3. **在正确的层计时**（#5804）：提案将计时放在渲染进程，从合成点击取样到 requestAnimationFrame 回调，减少测试框架往返的污染；同时断言有界挂载（DOM 行 ≤50）。rAF回调发生在下一次重绘前，这个锚点不证明像素已实际呈现；时间达标但全量挂载也不满足原预算。
4. **基准会腐烂，退役要有纪律**（#5805）：被测契约演进（transcript 迁到 RuntimeEvent ledger）后旧基准必崩。先本地复现、定位到被移除的 API，再判定"退役而非修复"——两个独立理由：无等价 API 替换；旧种子路径写的数据永远到不了新 reader 的分页源，指向新 reader 只会分页出空数据。

**一句话收束**："我做性能不是从优化手段开始的，是从预算和测量开始的——没有可重复测量的优化无法验收，没有分层锚点的测量无法归因，被测契约演进后基准本身也要治理。"追问细节时只展开能对应 PR 描述的部分，不扩大范围。

## 深挖（证据与反例）

- [#4815](https://github.com/apache/maka/pull/4815)：指出文本准入与结构化引用/附件在重放中为何必须一致；PR 中的红绿结果是提交者记录，本轮未重跑 Maka。
- 反例：关闭未合并不是合并；open 不等于已审核；单个 PR 的 AI 尾注不证明全体提交的工具使用情况。
- 事实是公开状态与 PR 内容；方法效果需具体测试/基线。没有测量时不补性能收益数字。

## 验收与讲述准备

- 准备一条成功链路、一条失败链路和一项设计取舍；展示材料前先确认个人归属。
- 状态引用 E04 指定核验快照，不另维护数字；该快照确认 #4815 已合并，围绕结构化消息准入与重放可见性。#5791/#5800/#5804/#5805 在该快照中是开放的测量提案；能讲方法与提交内容，不能说已进入主线或取得生产收益。
- 旧报告记载的实现与本轮实际测试分开；未在当前授权目录内提供源码/日志的能力不追加“已验证”。
- 如果追问超出现有证据，转为设计讨论并说明需要哪种测试，不把计划补成历史。

## 递进深挖：#4815 的内容为何不能只改一个按钮

技术内容来自 [#4815 原始 PR](https://github.com/apache/maka/pull/4815)，状态与数量统一服从 E04；网页缓存可能早于登记快照。本节把公开问题抽象成复习案例，本轮没有运行 Maka 套件，也不把自动 review 当成人工认可。

该 PR 面对的是有引用或附件、内联文字却为空的消息。问题同时涉及入口接纳和持久化后的重放可见性，单独改发送按钮或一个解码器可能遗漏另一跳。原 PR 记录了契约扩展、审查与红绿验证；完整历史看原文，下面的追问表用于学习方法，不声称每一项都在本轮重跑。

| 递进追问 | 应展开的证据与判断 |
|---|---|
| 怎么从症状找到根因？ | 沿接纳、持久化、读回、模型投影定位内容丢失点；找到调用共用判定的边界 |
| 为什么局部单测会漏？ | 单测可能只解码提交帧，没有再序列化队列快照或走生产接纳层；测试边界比用户路径短 |
| 放宽规则会带来什么回归？ | 全空消息仍应拒绝；历史已接纳内容不能在重放时被新规则过滤；兼容判断要覆盖新旧版本 |
| 为什么 review 有价值？ | 反馈能揭示遗漏的读回路径；贡献者必须核查、补验证并回应，不能只复制意见 |

为避免把一个 PR 描述误当亲自复现报告，现场用“PR 记录了”“我当时针对该边界提交了”讲技术经过；具体复盘要带当时 head、讨论和验证范围。审查者指出的问题与贡献者最终改动分开归属，不把协作反馈据为独创结论。

## 红绿验证、消融与评审的区别

**红绿验证**回答“这个检查能否识别原问题”：保留相同输入和断言，旧实现应失败、修改后应通过。只看新测试通过，可能断言根本没覆盖症状。

**消融实验**回答“哪部分变化有必要”：在可回滚副本里移除某一改动，固定输入、构建产物和其他条件，观察相同失败是否回归。结果只支持这一输入下的必要性，不证明该方案唯一或所有场景正确。PR 原文有针对修复的红绿记录；这是提交者历史记录，本轮未执行消融。

**对抗式审查**回答“哪里可能没有被覆盖”：从用户端往持久化与读回反推、从错误分支往共享调用方推，寻找测试没走到的一跳。自动审查可以提供反例线索，最终仍需源码和测试核对；GitHub 上 comment、approve、request changes 的含义也不同。[GitHub 官方 review 说明](https://docs.github.com/en/pull-requests/reference/pull-request-reviews)

闭卷练习时不要背工具名：用 3 分钟画一次“只有引用、没有文字”的输入穿过系统；再解释旧代码如何失败、补丁改哪一共享判断、哪个读回检查可能遗漏。答不出调用边界就回看 PR，不能用“CI 全绿”代替解释。

## 性能追问的进一步展开

把前面的四条性能提案按“预算→测量→归因→退役”讲，不复述四个 PR 标题。下列是学习推演，新增样本和结论尚未实测。

| 面试官质疑 | 应怎样回答 |
|---|---|
| 你的 p95 怎样算，样本够吗？ | 明确每个样本的起止、轮数、冷暖状态和异常规则；少量样本 p95 易跳变，不能报稳定收益 |
| 改完快了是不是网络恰好更好？ | 固定 fixture、机器与模拟 RTT，比较相同锚点；变更与对照至少保持输入一致 |
| 延迟达标为何还看 DOM 数？ | 一次时间达标可能掩盖全量挂载；资源规模约束和延迟预算是不同验收条件 |
| 旧基准挂了为什么不随便换 API？ | 新 reader 若读不到旧种子的数据，测到空集就失去代表性；先核对数据源与契约再决定修复或退役 |

官方参考只用来学习工具，不为生产收益背书：[Node.js Performance hooks](https://nodejs.org/api/perf_hooks.html) 用于理解进程内计时点；[W3C High Resolution Time](https://www.w3.org/TR/hr-time-3/) 用于理解单调时钟和浏览器计时基准；[MDN requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)说明回调在重绘前调用。复习时说明观测位置为何会影响结果，不把测试框架往返混入用户交互耗时。

## 兼容性与协作的反例练习

以下是设计推演。新客户端接受结构化消息，旧客户端仍要求文字，即使 JSON 形状没有变化，行为契约也可能变化。判断兼容性时要问是谁发送、谁读回、历史记录能否重新解释；只做新版本自发自收不足以证明混合版本安全。验证至少区分旧写新读、新写旧读和历史数据重放，具体部署允许哪些组合由维护者确认。

收到 review 后，先把反馈转成触发条件和调用边界，再判断是必改问题还是信息不足。若审查只是静态推导，应说清尚未运行的路径；若不同意，也应给反例或部署约束，而不是用“我本地能跑”终止讨论。补丁改变以后，再核对旧评论针对的 head 是否仍适用，避免修复已经失效的问题。

这项练习的验收是能解释一个兼容失败和一个审查盲点，指出需要哪条证据才能消除不确定性。它不要求把协议纪元、版本握手或全套迁移机制强加给所有项目；只有真实跨版本交换或数据重放需求，相关机制才有意义。

准备一条 review 回应时，保留问题指向的版本、接受或不接受的理由、对应改动和验证范围。回复“已处理”不说明解决了什么；指出哪条失败路径现在被覆盖，维护者才有条件复核。这是可执行的协作习惯，不是新增一套必须长期维护的评审系统。

## 当前可讲与不自信点

能讲：具体问题、补丁边界、公开讨论和验证方法；状态只引用 E04。不能讲：负责整个运行时、所有提交均被接受、开放提案已经带来生产收益。当前不自信的是各 PR 后续 head 的行为、完整套件现状和线上性能基线；没有复核就不更新完成度。
