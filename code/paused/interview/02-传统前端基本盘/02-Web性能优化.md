# Web性能优化

## 先测量，再优化

先定位加载、主线程计算、渲染或网络中的主要瓶颈。固定设备、数据量、网络条件和统计区间；实验室单次结果与真实用户分位数分开。

当前Core Web Vitals使用 **LCP、INP、CLS**，旧资料的FID仅作历史知识。LCP关注主要内容呈现，INP关注交互响应，CLS关注布局稳定。[指标定义](https://web.dev/articles/vitals)

## 方案与取舍

- 加载：路由拆分、按需依赖和缓存；检查请求瀑布而不是只看包大小。
- 交互：先减少同步工作、重复计算和无效渲染；必要时分片或Worker。
- 布局：为图片/异步内容预留尺寸；骨架与最终布局应一致。
- 大列表和图表：分页、虚拟化、图表实例清理；根据数据规模选择，避免先套优化。

## 本人案例

P08图表分层、P01平板排期、P02波形与裁剪可展开实现；缺少原始测量时只讲问题、动作和验收，不讲44%/30%等收益。准备复现输入、Profile和优化前后同条件记录。

## 一个可演算的定位过程

**学习推演**：输入筛选词后，接口已返回但页面晚出结果。先在 Performance 中按时间线区分网络等待、JS 计算、React commit 与布局绘制；若是图表转换占用一段同步任务，减少依赖不会直接减少转换成本。先避免重复转换，再比较采样、分片或 Worker；Worker 还要付消息传输成本，且不能直接操作 DOM。长任务为何阻塞交互见 [web.dev 长任务指南](https://web.dev/articles/optimize-long-tasks)。

memo 只在昂贵组件重复收到相同 props 时值得考虑；每次创建新对象可能使缓存失效，内部 state 或所订阅 Context 改变仍会更新。自定义深比较本身也可能更慢，不能跳过会影响事件行为的函数。启用 React Compiler 的项目还要确认已有自动优化，避免重复堆缓存。机制边界见 [React memo](https://react.dev/reference/react/memo)。

**验收**：用同一构建、设备、数据和操作复测，记录输入反馈、CPU 时间及内存，检查卸载是否释放图表实例。再去掉新增缓存做消融：若体验与耗时无差别就删；若退化才保留。虚拟化减少挂载节点，不会自动减少全量数据计算；分页、较少 DOM 已满足时不引入它。

追问“提升多少”先给测量定义与原始记录；当前 P02/P08 缺收益底稿，讲定位方法与动作，不把此推演写成已完成优化。
