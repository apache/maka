# 前端工程化

## 回答主线

工程化服务交付：安装可复现、构建可诊断、测试有约束、发布可回退。工具清单不是成果。

- 依赖与构建：锁文件、脚本入口、环境变量与产物；Monorepo按共享需求引入，不因新潮拆包。
- 类型与规范：TS/Lint/格式检查分工；接口schema的运行时校验补足类型擦除。
- 测试：纯函数测规则，接口测契约，页面测状态，关键业务测集成链路。Mock通过不等于生产通过。
- 提交与发布：小变更、可读diff、CI结果、环境配置与回滚；敏感配置与代码分离。
- 上下文：规范和验收项随相关实现一起评审；文档是约束载体，不保证AI天然遵循。

## 项目落点

P02的Java Mock BFF支持并行联调；P07的SQLite网关按规则命中返回模拟数据；P04的Mock与真实数据共用mapper。旧PLM/Babel/微前端素材中的个人归属待核，不直接用于“我主导过”的回答。

## 沿一次交付链解释工具价值

**学习推演**：本机能构建、CI 失败，先核对 Node/包管理器版本、锁文件、安装命令与环境变量，再看源码错误。锁文件约束依赖解析，不能保证操作系统和外部服务相同；`npm ci` 在清单与锁文件不一致时失败，而不是悄悄改锁。项目采用 pnpm 时沿用其冻结锁流程，不混换包管理器。[npm ci 官方说明](https://docs.npmjs.com/cli/v11/commands/npm-ci/)

前端环境变量最终可能进入产物。Vite 的 `VITE_` 暴露字段适合公开地址等配置，不能放服务端密钥；运行时服务配置与构建时替换需要分开。[Vite 环境变量](https://vite.dev/guide/env-and-mode)

P02 的 Java Mock BFF 是已登记联调经历，可解释“后端未就绪仍按契约开发”；成功、业务失败和畸形字段都应进入联调检查。Mock 与真实共用 mapper 能减少分叉，但不证明真实鉴权、网络、回调时序都正确。

取舍追问：是否所有仓库都拆 Monorepo？先看共享包的真实变更耦合；只有文档复用不必增加包管理复杂度。是否每个函数写测试？优先锁定金额、状态转换、契约和数据丢失风险；格式与无行为文档修改用相称检查。发布回答应能指到目标环境、产物标识和回退步骤，不能只说“CI 是绿的”。
