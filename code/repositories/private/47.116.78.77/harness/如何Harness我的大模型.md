## 第 3 页｜01 什么是 Harness

### Harness：管理和增强 Agent 的工程化运行时框架

它把记忆、工具调用、任务规划这些「工程能力」附加到基础大模型上，把模型从单纯的聊天引擎，变成能可靠完成复杂任务的执行工具。

- **大模型 / Chat Engine**：负责基础推理与生成。
- **Memory**：长期记忆、上下文管理。
- **Tools**：工具调用、环境交互。
- **Planning**：任务规划与分解。
- **Ops**：审批策略、可观测性。

一个类比：Harness 是给 Agent 配备的「装备和控制系统」。模型负责思考和提出 action，Harness 负责让它能记住、能动手、能被看见。

- 没有 Harness：模型只能回答，回答完就忘。
- 有了 Harness：模型会执行代码、读写文件、跨会话记住项目，并且每一步都留下可检查的痕迹。

## 第 4 页｜Harness 让「只会聊天」的模型多出四种能力

### 1. 记忆

**长期记忆与上下文管理**

支持跨会话的记忆存储和检索。上下文过长时自动压缩，避免超出模型窗口，让 Agent 能「记住」过往的交互。

### 2. 工具

**工具调用与环境交互**

这是让 Agent 能「动手」的关键。Harness 驱动 Agent 按需调用外部工具：执行代码、网络搜索、读写文件，完成实际任务。

### 3. 规划

**任务规划与分解**

面对「对比 Python 和 Go 的适用场景」这类任务，先制定分步计划再执行，避免一次处理全部信息导致混乱。不同 Harness 提供 Plan-Execute、Orchestrator 等模式。

### 4. 工程化

**工程化与可观测性**

审批策略（工具调用需人工确认）、OpenTelemetry 可观测性（监控 Agent 内部状态）。让 Agent 的行为更可控、更容易调试。

> 模型决定想做什么，Harness 决定能做什么、做过什么。后面几个部分，都围绕这四种能力展开。

## 第 5 页｜02 Context Engineering：Harness 的上下文是怎么组织的

每次调用模型，进入窗口的是四层拼装起来的 token，「一段对话」只是其中一层。

### L1 · 注意力最高：System Prompt

系统提示词。

包含：

- base instructions
- AGENTS.md
- memory
- 环境信息，例如 cwd、git、日期

最稳定，走 prompt cache。

### L2 · 稳定：Tool Definitions

工具描述层。

包含：

- name
- description
- JSON schema
- MCP tools
- Skills 只放索引，用到时再读全文

### L3 · 每轮增长：Conversation

对话层。

典型内容：

- user / assistant
- reasoning
- tool_use / tool_result
- 多轮 user / tool_result / assistant
- 可能出现 12k tokens 级别的工具结果

当窗口过长时，会出现 **compaction summary**，保留例如：

- 架构决策
- 未解决的 bug
- 改过的文件

用摘要替换掉更早的历史。

### L4 · 动态注入：Runtime State

Agent 状态栏。

通过 system-reminder 注入：

- todo 状态
- context 使用率
- hooks 输出
- 文件被外部修改的提醒

### Sub-agent

Sub-agent 会获得一套全新的 L1–L4：

- Tools
- 自己的对话
- State

最后只回传约 1–2k token 的结论。

### 这一页的关键逻辑

开始先看空白的窗口。Harness 每一轮都要决定：把什么放进去。

- **L1 · System Prompt**：你能控制的最高优先级。通过 AGENTS.md 定制。模型对开头的注意力最高，所以这一层要好好设计。
- **L2 · Tools**：工具描述是模型唯一能看到的说明书。它决定模型会不会选对工具、传对参数。Skills 只放索引，用时再读。
- **L3 · Conversation**：对话层占掉绝大多数 token。每一次 tool_use 都带回一份 tool_result，旧的结果很快就没人再看。
- **L4 · Runtime State**：状态栏是 Harness 替模型「记着」的东西。不靠模型回忆，而是每轮直接告诉它现在在哪。

再跑一轮：L1、L2 不变，L3 又长了一截。窗口就是这样一轮一轮被吃掉的。

### Compaction

窗口快满 → 压缩。

只压 L3：旧历史被一段摘要替换，L1、L2 原样保留，所以它们要写得稳定。

### Sub-agent

分治上下文。子 Agent 拿一份干净的 L1–L4 去深挖，主线只收到一两千 token 的结论。无关信息从头就进不来。

> L1 system · L2 tools · L3 conversation · L4 state，是一次典型长任务中的上下文组成。

## 第 6 页｜System Prompt：注意力最高的一层，用 AGENTS.md 定制

它每一轮都在，模型对它的注意力最高，也最容易被写坏。

### 高度：找对抽象高度

两个失败极端：

1. 写成一堆 if-else 式的硬规则，脆、难维护。
2. 写得太笼统，假设模型知道你没说的背景。

正确高度：具体到能指导行为，又给模型留判断空间。

### 原则：原则比禁令有效

禁令「不许用 X」可以被绕过；原则「为什么这样做」能泛化到你没枚举的场景。

先交代为什么，再给判断标准，最后才让它出方案。

### 迭代：最小 prompt 起步

用最强模型 + 最小 prompt 先跑，按暴露出来的失败模式逐条补指令和示例。

一条关键原则胜过十条无效规则，堆砌会稀释注意力。

> AGENTS.md 是活的。验证过的规则沉淀进去；被模型训练进去的东西，就从里面删掉。

## 第 7 页｜窗口大小 ≠ 真实有效的上下文

不同模型的窗口差好几倍。但上下文是稀疏的：token 越多，模型从中准确回忆信息的能力越差。

示例：

- Qwen 3.7 Plus：context window 256K
- Claude：context window 1M
- 有效上下文 effective：任何模型都会递减

### 为什么会衰减

- 注意力是 n² 的两两关系，越长越被摊薄。
- 训练数据里短序列占多数，超长依赖见得少。
- 所有模型都有，只是坡度不同。

真正要问的问题是：

> 在我的任务里，塞到多少 token 之后它开始漏东西？

「窗口多大」回答不了这个。

### 推论

上下文是有限的 attention budget，边际收益递减。

目标是：

> 能达成结果的最小高信号 token 集合。

## 第 8 页｜怎么避免上下文腐化：信息密集 + 分治

前提只有一条：

> 不要让无关的信息汇集到同一个 Agent / session 里。

### Compaction：压缩

窗口将满时，让模型把历史总结成摘要，带着摘要开新窗口。

保留：

- 架构决策
- 未解决的 bug
- 改过的文件

丢掉：

- 冗余的工具输出

最轻量的一招是直接清掉旧的 tool_result。

### Notes：窗口外的笔记

把进度、决定、待办写进窗口外的持久文件，例如：

- NOTES.md
- memory

上下文里只留一个「标识符」，需要时再用工具读全文。

### Sub-agent：分治上下文

Sub-agent 就是一种分治。

主 Agent 只做高层协调；子 Agent 用一份干净的小上下文深挖一个问题，只回传一两千 token 的结论。无关信息从一开始就进不了主线。

> 三招的共同点：都在缩小「每一轮真正进入模型」的 token 集合，而不是把窗口撑大。

## 第 9 页｜03 方法论：Skill 将死，方法论永生

### 为什么 Skill 会不断死亡

Skill 里的很多信息，会不断被最新的模型放进预训练。

之前很流行的头脑风暴 Skill Superpowers，已经被 Grill me 完全取代。Grill me 每个 skill 只有两三行，效果却非常强。

### 为什么方法论一句顶一万句

第一性原理、消融实验、奥卡姆剃刀……它们的整个流程和思维原理已经训练进模型里了。

我们只需要一个名词，就能激活模型内部与这套方法论相关的所有参数。

---

## 第 10 页｜一个名词，激活一整套原理

这些词一句顶一万句，因为它们的流程和思维方式已经训练进了模型。对 Agent 说出这个词，就够了。

### 第一性原理 · First principles

复现了吗？修复了吗？红绿了吗？修的是根因，还是在旧结构上打补丁？

### 对抗式审查 · Adversarial review

让没参与实现的 Agent 专挑毛病。

> Prove it, don't tell me.

### 消融实验 · Ablation

去掉一个组件再跑一遍。每条规则、每个工具都要证明自己在起作用。

### 奥卡姆剃刀 · Occam's razor

能用更少机制解决的方案优先。先做最简单能工作的版本。

### 列出所有不自信的点 · List every uncertainty

把「承认不确定」变成任务。全票通过不等于没有风险。

### 保持独立思考 · Independent thinking

采纳别人观点前先形成自己的判断。多 Agent 环境里尤其重要。

### 批判性思维 · Critical thinking

警惕讲得太顺的解释。不为对齐一张截图去编造不存在的 bug。

### 高内聚，低耦合 · High cohesion, low coupling

模块边界清晰，就是在做上下文分片。Agent 要理解的东西更少。

## 第 11 页｜04 长活 Agent：为什么要有长程 Agent

### 它会富集上下文

一次性的 session 每次从零开始。长程 Agent 持续累积一个项目的所有信息，慢慢长出自己的做事风格和流程。

### 它持续积累的内容

**项目信息**

- 代码结构
- 模块怎么协作
- 数据从哪来到哪去

**做事风格**

- 我们怎么拆任务
- 怎么提交
- 什么算完成

**设计准则与流程**

- 评审标准
- 不做的事
- 发布前要跑什么

像一个人一样积累起可复用的判断，而不只是记录。

> 关键区别：我们不断交给它项目信息、做事风格、设计准则，它把这些变成自己的上下文。它记住的是一套做法，聊天记录只是副产品。

## 第 12 页｜长活 Agent 示例：Apache Maka 的 Review Agent

每个维护者都有若干个 Review Agent。它不是一次性的 session：一直在运行，PR 来了就处理，方法论和记忆越积越多。

### Fix PR 流程

#### 第 1 步：复现

先在本地把问题真实跑出来，不是看描述。

#### 第 2 步：定位

找到根因，确认修的是根因而不是表象。

#### 第 3 步：评分

修复是否符合第一性原理，优雅不短视。

#### 第 4 步：改进

给出具体的修改建议，而不是「看起来没问题」。

### 门禁：Approve

完整跑过这套流程的 PR，我们才会 approve。

## 第 13 页｜04 多 Agent：Swarm、Graph、Agent Team

它们都是多 Agent，但解决的是三种不同的协调问题。

先看任务之间有没有依赖、要不要长活，再选形态。

### Swarm：独立并行

任务能拆成互不依赖的几份。

一个协调者 Agent 把任务拆成并行的若干份，分发给若干个 Agent 同时去做，最后汇总。

例：调研 10 个项目，显然可以拆给 10 个 Agent 并行做。

### Graph：有依赖，DAG

任务之间有前后依赖。

一个主 Agent 负责拆分任务、划出 DAG（有向无环图）、把节点分配给子 Agent，推进整张图的执行，并监督直到全部完成。

例：前端、后端的开发，和 review、测试是相互 block 的，有先后。

### Agent Team：长活，有角色

若干个彼此独立的长活 Agent。

每个 Agent 都有自己的 Memory、自己的工具链、自己的上下文，各有角色，相互交流、分配工作。

强依赖长活 Agent：产品经理、前端、后端一直在运行，在一个群聊里并行协作。

## 第 14 页｜多 Agent 示例：Maka Agent Graph

### 三权分立推进一张动态 DAG

Agent 的计划没法一次静态写死：探索会发现新分支，子任务失败会改路线。

所以 Maka 把 Graph 建成一张在会话里持续演进的 DAG，并把职责拆成三份。

1. **主 Agent 只写意图，不推图。** 只有 Root Session 的主 Agent 能改全局拓扑；子会话没有这个权限。
2. **Ready 可以反复算，执行只准入一次。** 就绪是无副作用的投影；真正拉起前先写 Claim，重试和抖动都不会重复跑。
3. **不造第二套 Runtime。** SQLite 只管调度事实，模型调用、工具、权限、事件全复用 Session Runtime。

参考：`github.com/apache/maka · docs/blogs/multi-agent-scheduling.zh-CN.md`

## 第 15 页｜Agent Team 最难：组织架构本身就难

有了长程 Agent，就会有多个长程 Agent，它们之间需要相互交流。

示意角色：

- 人：编排者
- Review：context A
- Triage：context B
- Fix：context C
- Release：context D

### 一个关键判断

> agent 数量 = 相互独立的 context 数量。

共享同一份上下文的 100 个 Agent，等于 100 个相同的人。

### Agent Team 的维护难点

- 需要分支上下文
- 需要人用心管理
- 需要人用心编排

因为组织架构学本身就是一件难事。谁负责什么、谁不负责什么、消息该给谁看，这些对人难，对 Agent 更难。

> 人是主线，Agent 是分支。方向、契约、最终判断留在人手里；Agent 之间多一轮讨论，常常不如多跑一次代码。

## 第 16 页｜05 人是编排者：人是 Agent 最好的编排者

现在有个很火的词叫蒸馏：一个强的 Agent 带几个弱的 Agent，给它一个标准范例让它学。人指导 Agent，做的其实是同一件事。

### 蒸馏

强 Agent 带弱 Agent，给标准范例让它学。

这条路线叫 **OPD · On-Policy Distillation**：给的是「标准动作」和「判断依据」，每一步操作让它自己走。

### 人指导 Agent，就是在蒸馏方法论

传递的是一套做事规则：

- 什么该做
- 什么情况下选 A 不选 B
- 什么算完成
- 什么错误必须拦

### 人本身就是高质量数据集的生产器

每一次纠正、确认、重写、否定，都带着意图、上下文和判断，比网上爬来的通用语料值钱得多。

### 长活 Agent 的价值

就是把这些人机之间的高质量互动积累下来。

> 壁垒在于它知道多少「只有你我知道」的东西，模型本身多强反而其次。

## 第 17 页｜放手执行，不放任方向

人不必逐行替 Agent 写代码，但必须保留四样东西。

让渡的是「执行路径的选择权」，保留的是「方向的判断权」和「结果的定义权」。

### 保留一：目标

要解决什么问题、为什么做。目标错了，执行再好也没用。

### 保留二：契约

输入输出、边界条件、不可违反的约束。契约是信任的基础，违约就是事故。

### 保留三：取舍

资源有限时优先保什么、牺牲什么。取舍体现价值观，Agent 无法替你排序。

### 保留四：验收

什么算「好」、什么算「完成」。验收标准就是人定义的「成功」本身。

### 流水线模型：上限低

人把任务拆成固定步骤，Agent 只执行其中一环。它永远学不到「为什么」，也不会进化。

### 师徒模型：上限高

人给目标、讲原则、看结果、给反馈；Agent 自己探索路径。

这才是「编排」，也是前面所有方法论起作用的前提。

## 第 18 页｜蒸馏是双向的，记忆分三层

人在蒸馏 Agent；跑得够久之后，Agent 也在蒸馏你。

长活 Agent 该记什么，决定了它能不能被通用模型替代。

### 反向蒸馏：Agent 也在学你

它在大量任务里发现你自己没意识到的规律。

例如：

- 发现你总是先看数据再看方案 → 它主动先把数据整理好。
- 发现你对某类错误零容忍 → 它主动加校验、加测试。
- 发现你这段时间偏好激进策略 → 它调整建议的风格。

所以这是一个双向蒸馏的过程：你教它方法论，它把你的偏好变成默认行为。

### 长活 Agent 的三层记忆

#### 1. 价值观记忆

冲突时的取舍倾向、你对「好」的定义。

**最难替代。**

#### 2. 方法论记忆

解决问题的固定套路、决策树、检查清单。

#### 3. 事实记忆

常用工具、路径、格式偏好、项目约定。

**最易替代。**

> 越往上，越难被通用模型替代，也越是你自己的护城河。

人是 Agent 的教练、质量官和价值观来源，写代码的活可以让出去。

蒸馏做的事，是把人身上难以言传的判断力，变成机器可以执行的方法论。

## 第 19 页｜多 Agent 示例：raft.build 与 Grok Bot

### 群聊里的长活同事

两个产品的形态几乎一样：每个 Agent 是一个持久进程，有自己的记忆和工具，人和 Agent 在同一个聊天空间里协作。

### raft.build

> “where humans and AI agents build together”

- Agent 是持久的团队成员，不是一次性工具。
- 每个 Agent 有自己的 memory，是一个 persistent process，能「从上次停下的地方接着做」。
- 协作发生在 channels、DM、threads 里，人和 Agent 共享同一份上下文。
- Agent 自己 claim 任务，并行跑，互相交接，在共享 thread 里互相 review 对方的产出。
- 跑在你自己的机器上：一个轻量 daemon（它叫 Computer）把 Agent 接到文件、工具和你的 AI 订阅上。

### Grok Bot

SpaceXAI，2026 年 8 月。

- 一个 Bot 是一个有名字的持久 Agent，跑在自己的云端电脑上。
- 你给它一个活和工具权限，合上笔记本它还在干。
- 只有需要人拍板时才回来找你。其余时间自己推进。
- Telegram / Slack 式界面：和每个 Agent 单独 DM，也有多个 Agent 一起的群频道。
- 典型玩法：一个「Chief of Staff」Bot 带队，把活分给调研、写码、运营等专职 Bot。
- 社区已有上千个团队配置。

> 对上前一页的定义：长活 + 各自独立的 Memory 和工具链 + 群聊里分工协作 + 人做最终决定。这就是 Agent Team，也是它为什么强依赖长活 Agent。

## 第 20 页｜多 Agent Team 实战：Apache Maka 的 Review Agent 团队

### 就跑在 raft 里

这是作者自己的工作区。

左边每个维护者一个 PR-Review 频道，右边这个只读群，是人写给 Agent 看的 Review 规则。

### 一人一个 Review 频道

例如：

- PR-Review-Qronos
- Kabi
- M4n5ter
- Leaders

每个维护者带自己的长活 Review Agent，以 owner 的身份对外发言。

### Review-Principle 只读群 = 方法论的沉淀处

人在这里写规则，Agent 在这里读规则。

这就是上一节说的「人蒸馏方法论给 Agent」。

### 规则长什么样

- 对外发布不提内部名词。
- 影响大的 PR 先 DM 人类。
- db schema 变更单独警惕、查 migration。
- 不是所有 PR 都要合并，质量低的标记延后。
- 检查冲突、该不该 rebase。

### 为什么是群聊而不是文档

规则在对话里长出来，带着上下文和讨论过程；长活 Agent 一直在群里，新规则立刻生效，不用重新部署。

## 第 21 页｜06 定义自己的 Harness：两件事

不需要从零写一个 Agent 框架。

在作者看来，定义自己的 Harness 主要就是两个方面。

### 1. 管理好上下文

做好上下文的分支：

- 不同任务
- 不同角色
- 各自独立的 context
- 不混在一起

做好上下文的压缩：

- 什么时候 compact
- 压缩时保留什么
- 丢掉什么

把自己的经验总结成 skill：

- 验证过的做法沉淀进 AGENTS.md
- skills
- memory
- 不只留在脑子里

### 2. 沉淀 Workflow 成工具

把自己的流程用代码具体沉淀下来，变成一个给 Agent 使用的工具。

可以是：

- 一个 CLI
- 一个 MCP
- 一段脚本

流程一旦是代码，Agent 每次都走同一条路，不用每次重新想。

> Agent 负责探索和决策，Workflow 承担固定步骤和门禁。

> 上下文决定它知道什么，工具决定它能做什么。两边都管住，Harness 就成型了。

## 第 22 页｜06 AX：Agent Experience

CLI、MCP、沉淀成脚本的 Workflow，它们的设计与描述，作者称之为 **AX**。

### 什么是 AX

AX 是给 Agent 做的体验设计，不是给人。

人靠视觉和直觉；Agent 只有上下文和文字。人觉得好用的工具，Agent 可能完全抓瞎。

AX 的设计会强影响 AI 的表现。

### Agent 能用的三种工具形态

- CLI
- MCP
- 程序 / 脚本化的 Workflow

它们的：

- name
- description
- 返回值

就是它们的全部界面。

### 原则一：Show the state

需要的事实直接返回到位，别指望 Agent 在压力下自己推导隐藏信息。

### 原则二：Recoverable failures

错误信息要说清原因、替代路径和重试条件，别把循环推进死角。

### 原则三：Measure the interface

很多「模型不行」其实是「接口没给好」。同一个模型，只改工具返回格式，结果就不一样。

### 检验：盲测 UAT

找一个没参与实现的 Agent，不给提示，能独立用成功才算工具可用。人觉得好用不算数。

> Agent is the developer.

工具的第一用户是 Agent。name 和 description 就是它唯一能看到的说明书。

## 第 23 页｜回顾：怎么 Harness 我的大模型

六个部分，其实是同一件事的六个切面：

> 让模型进入一个能记住、能动手、能被看见、能长期运行的系统。

### 01 Harness

模型决定想做什么，Harness 决定能做什么、做过什么。

### 02 Context

窗口大小不等于有效上下文。信息密集，分治，不让无关信息进同一个 session。

### 03 方法论

Skill 会被训练进模型；一个名词就能激活整套原理。

### 04 长活 & 多 Agent

长活 Agent 富集上下文；Swarm、Graph、Team 各解决一种协调问题。

### 05 人是编排者

人蒸馏方法论给 Agent，也是最贵的对齐数据；保留目标、契约、取舍、验收。

### 06 自己的 Harness

管住上下文，把 Workflow 沉淀成 CLI / MCP / 脚本，用 AX 的标准去设计。
