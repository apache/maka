# Design Generator

## Overview

Generate one reusable design-system package:

- `DESIGN.md` or `design.md`: the source of truth and AI page-generation constraint file, using one unified executable front matter schema plus ten human-readable chapters.
- `preview.html`: a visual validation panel for human review of design tokens, components, and page patterns.
- `preview-dark.html`: a real dark-mode or dark inspection validation panel.
- `example.html`: a source-matched prototype sample generated by the agent from `DESIGN.md` to prove the specification can guide downstream UI generation. Python scripts may scaffold a diagnostic placeholder, but must not invent the final page.
- `DESIGN_GAPS.md`: design gaps and conflict log — tracks uncertain, conflicting, missing, and low-confidence items found during analysis. Always generated by default.

The unified DESIGN.md format upgrades a design document into a **design system source file + AI page-generation constraint file**. It answers two questions simultaneously:

1. What is this design system?
2. How should AI generate pages according to this design system?

Do not produce a moodboard or a generic landing page. The output must be concrete enough for another agent or engineer to build new UI from the markdown file alone.

## Quick Start

1. Classify the input evidence mode: source + screenshot, source-only, screenshot-only, URL, or product brief.
2. Choose the output language from the user's request and product evidence. For Chinese projects, Chinese product names, Chinese screenshots, Chinese source comments/routes, or Chinese users, write human-facing markdown, preview copy, examples, checklists, and known gaps in Simplified Chinese unless the user asks otherwise. Keep code identifiers, token names, selectors, class names, file paths, library names, and API names unchanged.
3. Read [references/design-md-corpus.md](references/design-md-corpus.md) to choose the closest interface archetype and preview composition.
4. Read [references/input-analysis.md](references/input-analysis.md) for the matching evidence workflow.
5. Read [references/output-contract.md](references/output-contract.md) before writing the package.
6. Choose the output folder and markdown filename:
   - if the user specifies an output folder, use that exact folder
   - if a local project/source folder is being analyzed and no output folder is specified, write all generated files to `<project-root>/DESIGN`
   - if there is no local project root, such as URL-only or brief-only input, default to `./DESIGN` from the current working directory
   - follow an existing `DESIGN.md` or `design.md` convention if present
   - follow the user's explicit filename if provided
   - otherwise default to `DESIGN.md`
7. Scaffold the package:

```bash
python3 scripts/scaffold_design_folder.py --project-root /absolute/path/to/project --name "Product Name" --markdown-name DESIGN.md --format ai-design-system-v3
```

Use `--output /absolute/path/to/custom-folder` instead of `--project-root` when the user requests a specific destination.
Use `--language zh-CN` when the target product or user context is Chinese.

8. Replace the scaffolded markdown with a completed Design.md document following the unified executable front matter schema and 10-chapter structure.
9. Generate or refine previews. Derive `preview.html` and `preview-dark.html` from the markdown:

```bash
python3 scripts/render_preview_from_design_md.py /absolute/path/to/DESIGN --markdown-name DESIGN.md
```

10. Generate `example.html` as an agent-authored validation artifact from `DESIGN.md`. Choose the most representative `pageTemplates` entry, write a concrete sample request into `example-generation-input` metadata inside `example.html`, visibly render that request, and do not write the sample request back into `DESIGN.md`.
11. Generate DESIGN_GAPS.md to track uncertain items:

```bash
python3 scripts/generate_gaps_doc.py /absolute/path/to/DESIGN --markdown-name DESIGN.md --language zh
```

This extracts uncertain information from the front matter (`openQuestions`, `knownLimits`, `assumptions`, `legacyTokens`, and low-confidence `evidence.decisions`) and creates a DESIGN_GAPS.md file for tracking items that need confirmation. DESIGN_GAPS.md is the "to-be-confirmed ledger" — AI generates pages from DESIGN.md, not from DESIGN_GAPS.md.

12. Validate the result:

```bash
python3 scripts/validate_design_folder.py /absolute/path/to/DESIGN --markdown-name DESIGN.md --format ai-design-system-v3
```

## Output Rules

- Always create exactly one design-system package for the requested target.
- Save the package to the user's explicit output folder when provided; otherwise use `<project-root>/DESIGN` for local project analysis and `./DESIGN` for URL-only, screenshot-only without source, or brief-only work.
- Always include `DESIGN.md`, `preview.html`, `preview-dark.html`, `example.html`, and `DESIGN_GAPS.md`.
- Do not generate `EVIDENCE.json`, `VALIDATION_REPORT.md`, or other analysis artifacts by default. Only create optional debug artifacts under `<target-folder>/.design-generator/` when the user asks to retain evidence, output a quality report, run batch regression, or use debug/development mode.
- Make `DESIGN.md` the source of truth and AI generation constraint file; `preview.html` is a visual companion for human review.
- `DESIGN_GAPS.md` tracks uncertain items, conflicts, and missing coverage separately from the authoritative `DESIGN.md`. Always generated by default.
- Use `example.html` as an agent-authored source-matched prototype sample so users can judge downstream UI fidelity. `example.html` may contain sample-request metadata, but `DESIGN.md` must not contain one-off example requests.
- New scaffolds always use the unified executable schema with 10 chapters. Non-v3 validation modes are only for separately supplied `stitch-alpha` or old numbered legacy packages.
- Preserve real source systems. Do not inflate plain enterprise products into decorative marketing systems.
- Mark inferred or recommended values as such instead of presenting them as observed.
- Mark screenshot-only measurements as approximate unless source or computed styles confirm them.
- Do not start from a generic SaaS/admin design system and then revise it. First classify evidence, extract what is available, and only fill missing areas with labeled assumptions.
- Only **Brief mode** may synthesize a design system from scratch. Source, URL, screenshot, and mixed modes must stay extraction-first, but any field needed for downstream prototype generation must still receive a conservative executable recommendation with `evidence.decisions` rationale.
- Do not add component families, colors, motion, or layouts that contradict the source product. When evidence is missing but a prototype needs a decision, choose the least surprising product-appropriate default and document it as `recommended-default`.
- If the input brief, URL, screenshot notes, or source analysis contains required visual assets, preserve every required asset URL/path in `DESIGN.md` itself. Do not write "see original spec" or rely on chat history for images, videos, fonts, icons, project screenshots, or other assets needed to reproduce the UI.
- For source-backed prototype guidance, document app shell, page shell, page patterns, and component mappings; tokens alone are not enough.
- Keep `DESIGN.md` as an execution specification, not a long evidence report: compress source-scanning narratives and repeated evidence, but retain every rule that affects prototype generation.

## DESIGN.md Content Boundary

Keep these in `DESIGN.md` because downstream AI tools need them to generate consistent prototypes:

- real token values and semantic usage rules
- component recipes, states, combinations, and forbidden patterns
- app shell, page shell, content region, dimensions, and responsive behavior
- page templates and representative structure
- in-source and no-source generation rules
- default handling for unconfirmed capabilities
- self-check items for generated prototypes

Do not bloat `DESIGN.md` with:

- long source scanning narratives
- repeated file/path evidence
- low-priority inference details
- obsolete candidate values after a current default is chosen
- implementation history that does not change page generation
- one-off `example.html` sample requests that could bias future prototype generation

## DESIGN.md vs DESIGN_GAPS.md

```
DESIGN.md          = current executable rules / authoritative design system
DESIGN_GAPS.md     = pending confirmation ledger / conflict list / manual confirmation record
```

AI coding tools may later only receive `DESIGN.md`, so `DESIGN.md` must be self-consistent:

- `DESIGN.md` must state current default decisions.
- `DESIGN.md` must explain default handling rules for unconfirmed capabilities.
- `DESIGN.md` must NOT say "see DESIGN_GAPS.md for details" as its only content.
- `DESIGN_GAPS.md` records complete evidence, candidate values, pending items, and write-back records.
- After manually confirming items in `DESIGN_GAPS.md`, write back confirmed results to `DESIGN.md`, then regenerate `preview.html`.

## Workflow

### 1. Classify the evidence mode

Choose one primary evidence mode:

- **Source + screenshot mode**: local source plus screenshots or captured pages. Use source and computed styles for exact tokens; use screenshots to identify active runtime theme, layout state, visible page patterns, density, and conflicts.
- **Source-only mode**: local source or project folder without screenshots. Extract exact tokens and component mappings from code, then label runtime state as inferred where the app has multiple themes or layouts.
- **Screenshot-only mode**: screenshots without source. Extract page structure, component composition, density, and approximate visual tokens. Mark exact colors, spacing, and typography as approximate unless measured from a reliable design export.
- **URL mode**: live website or local rendered URL. Prefer DOM, CSS variables, and computed styles over visual sampling. Capture at least one content-heavy page and one narrow viewport when possible.
- **Brief mode**: product idea, feature concept, or workflow description only. Synthesize a coherent system and document assumptions clearly.

If a request combines an existing product with a new page or feature, stay in the strongest available extraction mode. The existing product remains the source of truth.

Mode boundary rules:

- In `source+screenshot`, `source-only`, `screenshot-only`, and `url` modes, do not seed the result with the scaffold template's generic tokens, generic Inter typography, generic 8px radius system, or generic admin/SaaS page examples. Use the scaffold only as a file and section skeleton.
- In `brief` mode, synthesized tokens and page patterns are allowed, but `evidence.mode` must be `brief`, `assumptions` must explain the synthesized choices, and `confidence.tokens` / `confidence.components` should not be `high` unless the user supplied explicit brand or implementation constraints.
- In `screenshot-only` mode, token confidence must stay below `high`; exact colors, spacing, radius, shadow, typography, and component states must be marked approximate or inferred.
- Do not write `unknown`, `unavailable`, empty placeholders, or leave key prototype-generation fields blank. If evidence is insufficient, write a safe current decision and record `source: recommended-default` plus rationale in `evidence.decisions`.

### 2. Choose the evidence hierarchy

Prefer evidence in this order:

1. User's explicit target constraints and corrections.
2. Runtime styles visible in URL/screenshots for the target state.
3. Source code tokens, theme files, CSS variables, component primitives, and layout wrappers that are active for the target state.
4. Historical source variables and alternate themes as candidates only.
5. Conservative product-appropriate recommendations for missing but necessary fields.

If source code or computed styles are available, do not use screenshots as the source of exact colors, font sizes, spacing, or radius values. Use screenshots to identify the active theme, current layout state, visible page pattern, component composition, density, and source conflicts. After interpreting a screenshot, trace each important visual decision back to source selectors, variables, components, DOM, or computed styles when possible.

Treat shell chrome as a distinct extraction layer:

- keep product primary color, top navigation background, tags/tab background, sidebar surface, and content canvas as separate semantic roles
- do not collapse shell colors into `primary` simply because they sit in the same visual family
- for source-backed projects, shell dimensions such as top-nav height, sidebar expanded width, sidebar collapsed width, and tags height should come from source/computed styles, not screenshot estimates
- screenshots may confirm the active shell state, but they must not override source-backed exact shell dimensions without an explicit runtime override or a documented conflict
- when the user explicitly corrects a target token or shell value, treat that correction as authoritative for the current deliverable, use it in `DESIGN.md` / previews / examples, and record any source mismatch in `DESIGN_GAPS.md`

If sources conflict, write the current decision into the authoritative field (`tokens`, `layout`, `components`, or `pageTemplates`) and document losing candidates in `legacyTokens` / `openQuestions`. Every open question must include `currentDecision` or `fallbackRule` so downstream prototype generation never stalls.

### 3. Select the interface archetype

Pick the dominant archetype before writing:

- enterprise-admin: 后台管理、CRUD、表格、权限、任务、审核、配置
- settings-admin: 设置中心、账号、组织、权限、计费
- marketing-site: 营销官网、落地页、功能介绍、CTA
- brand-portfolio: 作品集、个人品牌、创作者主页
- content-resource-portal: 资源门户、数字资源库、文化资源展示、媒体资料库、专题展
- media-content: 新闻、视频、播客、内容流
- ecommerce: 商品列表、商品详情、购物车、订单
- marketplace: 多方资源/服务/房源/课程/人才匹配
- analytics-dashboard: 分析仪表盘
- data-screen: 全屏可视化大屏
- mobile-app: 移动端应用
- aigc-workbench: AI 生成、Prompt、结果预览、任务历史
- chat-agent: 聊天式 AI、Copilot、客服、知识问答
- editor-workbench: 编辑器、画布、工具栏、属性面板
- docs-portal: 文档站、API 文档、开发者中心、知识库
- workflow-automation: 流程编排、节点画布、执行记录
- collaboration-workspace: 协作文档、项目空间、任务看板
- map-geospatial: 地图、点位、图层、空间分析
- file-asset-manager: 文件库、素材库、上传、预览、版本管理
- custom:<name>: 其他无法归类但结构明确的产品形态

Do not blend multiple archetypes unless the product actually spans them. For source-derived projects, fidelity is more important than novelty.
Do not label a public cultural archive / digital resource portal / media library / portfolio / docs site / landing page / mobile UI / data-screen / AIGC workbench / chat agent as an admin/dashboard archetype just because it includes filters, metadata, cards, or charts. Admin/dashboard archetypes are reserved for operator tools dominated by CRUD, tables, approval/task queues, management workflows, and privileged settings.

### 4. Build the token lockup first

Before drafting prose, build an internal evidence packet and token lockup.

Evidence packet:

- evidence mode and confidence
- source files, URLs, screenshots, or brief assumptions used
- runtime theme and layout state, if observable
- framework, component library, style system, and shell selectors
- representative page patterns and their source pages
- component mappings from product primitives to future prototype components
- conflicts, approximations, and recommended-default decisions for missing evidence

Token lockup:

- product posture and density
- semantic color roles (recommended vs legacy)
- typography roles
- spacing scale
- radius scale
- shadows and elevation
- motion rules
- component variants and states
- required asset inventory, including exact URLs/paths and where each asset is used
- app shell, page shell, and reusable page patterns
- responsive behavior
- known inferred or missing evidence

Use this evidence packet and lockup to write the YAML front matter first. The prose must explain and constrain the same tokens, page patterns, and component mappings; it must not introduce a second design language.

### 5. Write the DESIGN.md document (unified executable format)

Follow [references/output-contract.md](references/output-contract.md) for the complete output specification.

The markdown file must begin with one unified YAML front matter model. Do not create parallel compatibility layers or duplicate the same fact across multiple fields:

```yaml
---
version: 1
language: zh-CN # or en / auto
name: Product Name
summary: One dense paragraph describing the design system.
product:
technology:
runtime:
tokens:
layout:
components:
pageTemplates:
generationRules:
evidence:
legacyTokens:
openQuestions:
knownLimits:
assumptions:
---
```

Then write the ten human-readable chapters. Section titles follow the selected output language.

**Chinese canonical titles**:

1. 使用说明
2. 产品与界面画像
3. 设计原则
4. 设计令牌
5. 布局与应用壳
6. 组件系统
7. 页面模板
8. 交互状态与响应式规则
9. 原型生成规则与自检
10. 证据、限制与默认决策

**English canonical titles**:

1. Usage Guide
2. Product & Interface Profile
3. Design Principles
4. Design Tokens
5. Layout & App Shell
6. Component System
7. Page Templates
8. Interaction States & Responsive Rules
9. Prototype Generation Rules & Self-Check
10. Evidence, Limits & Default Decisions

Chapter purpose:

- **1-3**: Explain what this design system is.
- **4-8**: Explain what this design system consists of.
- **9**: Explain how AI should generate prototypes according to this design system.
- **10**: Explain evidence boundaries, default decisions, unconfirmed capabilities, and current fallback rules.

For source-derived systems:

- name real frameworks, component libraries, layout wrappers, utilities, and token carriers when they affect future UI generation
- preserve density, language, terminology, implementation grammar, and recurring page patterns
- preserve the product's working language; Chinese products should produce Chinese explanations, prompt guidance, checklists, gaps, preview text, and example UI labels
- map source components to the components future prototypes should use
- document whether screenshots were used for runtime/theme/layout calibration rather than exact token extraction
- label approximate values and missing states
- do not rebrand or beautify without evidence

For concept-derived systems:

- state the target users, operating context, and interface archetype
- choose one coherent visual direction
- document assumptions and benchmark influences
- make the system specific enough that future agents cannot fall back to generic defaults

### 5.0 Unified executable schema rules

Every `DESIGN.md` must expose flat semantic aliases under `tokens`. Nested source token groups may remain only as `legacyTokens` or evidence detail. Downstream AI tools and previews must be able to read these names directly:

```yaml
tokens:
  colors:
    primary: "#003EB3"
    primaryHover: "#0958d9"
    onPrimary: "#ffffff"
    text: "rgba(0,0,0,0.68)"
    textStrong: "rgba(0,0,0,0.83)"
    textMuted: "rgba(0,0,0,0.4)"
    canvas: "#ffffff"
    surface: "#fafafa"
    surfaceMuted: "#f5f5f5"
    border: "#d9d9d9"
    borderLight: "#f0f0f0"
```

If the source uses grouped tokens such as `primary-colors.primary.value`, keep them only as supplemental evidence or legacy detail. Recommended rules, previews, and examples must prefer `tokens.*`.

### 5.1 Chapter 4: Distinguish current tokens vs legacy tokens

Chapter 4 must separately list:

- **4.1-4.7**: current `tokens` the AI should use for new prototypes.
- **4.8**: `legacyTokens` / conflict tokens that exist in source but should NOT be used as defaults for new prototypes.

### 5.2 Chapter 6: Component recipes, not just style lists

Each `components.*` entry must include source primitive or prototype primitive, applicable scenarios, style rules, recommended combinations, forbidden patterns, and prototype generation advice.

### 5.3 Chapter 5: Distinguish in-source vs no-source development

Chapter 5 must distinguish two scenarios:

- **In-source development**: do not rebuild the app shell; generate pages inside the documented content region; use existing component libraries, classes, and selectors.
- **No-source prototype generation**: simulate the documented `layout.appShell`; use `tokens`, `components`, `pageTemplates`, and `generationRules`.

### 5.4 Chapter 7: Page templates

`pageTemplates` defines the page grammar future agents can use. It is not a code-side product preset and must not be treated as a hardcoded template catalog. Write page templates as **real product pages**, not generic admin/marketing full-page templates.

Each page template entry should include:

- `name`
- `archetype` (open values allowed, including `custom:<name>`)
- `purpose`
- `priority`: `primary` / `secondary` / `optional`
- `structure` or `sections`: ordered list of page blocks
- `components`: references to `components`
- `sampleContent` or `sampleData`: example labels, cards, rows, metadata, images/URLs used by `example.html`
- `evidence`: `observed` / `source-derived` / `screenshot-approximate` / `url-observed` / `brief-synthesized` / `inferred`
- `confidence`: `high` / `medium` / `low`

Write `structure` / `sections` so the renderer can turn it into a real page:

- Use stable section names such as `top-nav`, `sidebar`, `hero-search`, `search-toolbar`, `filter-panel`, `resource-card-grid`, `media-card-grid`, `data-table`, `pagination`, `prompt-input`, `generation-controls`, `result-preview`, `chat-thread`, `map-panel`, `canvas-workspace`, or `detail-panel`.
- Compact YAML such as `- dataTable: "资源表格"` is allowed, but the key must describe the actual section type.
- Nested layouts such as `left/right`, `content/aside`, or `main/side` must still contain named child sections; do not rely on prose-only layout descriptions.
- Put realistic labels, rows, card titles, images, metadata, and CTA text in `sampleContent` / `sampleData`; `example.html` must not invent a different product domain to fill empty samples.
- In source-backed modes, `evidence` for templates must be `observed`, `source-derived`, `screenshot-approximate`, or `url-observed` only when traceable. In brief mode, use `brief-synthesized` or `inferred`.

If multiple page templates exist, ensure one representative page can be selected:

- prefer `priority: primary`
- otherwise prefer the template with the most complete `structure/sections`
- otherwise prefer the template most aligned with the primary user task

### 5.4.1 Example generation boundary

Do not put one-off sample user requests in `DESIGN.md`. `example.html` is a validation artifact, not part of the reusable design specification.

When creating `example.html`, the agent should select a representative page from `pageTemplates`:

- prefer a template referenced by the user's current validation goal, if any
- otherwise prefer `priority: primary`
- otherwise prefer the template with the most complete `structure` / `sections`
- otherwise create a diagnostic `example.html` and record the missing page structure in `DESIGN_GAPS.md`

The selected sample request belongs only inside `example.html` metadata:

```html
<script type="application/json" id="example-generation-input">
  {
    "source": "generated-from-design-md",
    "userRequest": "根据 DESIGN.md 生成一个标准列表页原型。",
    "targetPage": "标准列表页",
    "selectedPageTemplate": "standard-list",
    "reason": "该模板是 pageTemplates 中的 primary 页面模式。"
  }
</script>
```

### 5.5 Chapter 9: prototype generation rules, forbidden patterns, self-check

Chapter 9 must contain three subsections:

- **9.1 Prototype Generation Rules**: mandatory rules for both no-source and in-source scenarios.
- **9.2 Forbidden Patterns**: what AI must NOT do when generating prototypes.
- **9.3 Post-Generation Self-Check**: checklist the AI should run after generating prototypes.

### 5.6 Chapter 10: Evidence, limits, and defaults — self-contained for AI

Chapter 10 must be self-contained so that an AI receiving only `DESIGN.md` can safely generate pages. It must include:

- **10.1 Evidence Summary**: what evidence was used to produce this DESIGN.md.
- **10.2 Current Default Decisions**: what defaults are in effect.
- **10.3 Unconfirmed Capabilities & Default Handling**: what is unconfirmed and how AI should handle it.
- **10.4 High-Impact Pending Items Summary**: only critical items that affect prototype fidelity.

Chapter 10 must NOT consist solely of "see DESIGN_GAPS.md". It may reference DESIGN_GAPS.md as a supplement, but only after providing its own executable default decisions and handling rules.

### 6. Build previews and agent-authored example page

Use `scripts/render_preview_from_design_md.py` after `DESIGN.md` is complete so `preview.html` and `preview-dark.html` are derived from the same front matter and prose. Do not hand-build a second design language in preview HTML.

Then generate `example.html` yourself as an agent-authored validation artifact from `DESIGN.md`. The Python renderer does not generate the final example by default because the example must demonstrate how an AI coding agent interprets the product specification.

Read [references/output-contract.md](references/output-contract.md) for the full preview contract before manual refinement. The short rules are:

- Previews are evidence-driven validation manuals, not token dumps, landing pages, or generic demo dashboards.
- `example.html` must simulate downstream use: a sample user feature request plus `DESIGN.md` should produce one representative prototype page. The sample request is written only inside `example.html`, not inside `DESIGN.md`.
- `example.html` must declare `data-example-source`, `data-example-archetype`, `data-example-pattern`, and `data-example-pattern-source` so validation can prove which DESIGN.md structure produced the page.
- `example.html` must embed and visibly render `example-generation-input.userRequest` so users can understand what input produced the page.
- `example.html` must not use product-level hardcoded presets from the renderer. If DESIGN.md lacks enough page structure, create a diagnostic example and record the gap instead of inventing a backoffice/content/marketing template.
- Source-derived outputs should prioritize source-matched specimens over product-type demos.
- Brand-site, portfolio, and strict landing-page outputs must omit admin/data-entry/table/pagination/dialog kit families unless explicitly documented.
- Theme handling must be evidence-driven. `preview.html` shows the primary runtime theme (`light-only`, `dark-only`, `supports-both`, or a documented current default), while `preview-dark.html` is a required compatibility file that must declare whether it is a real dark runtime, inspection view, or documented no-dark-mode strategy.
- Layout previews must be evidence-driven. Do not draw a sidebar, persistent top app bar, footer, or dashboard content area unless `layout`, source/URL/screenshot evidence, or page templates explicitly support that structure. For no-shell brand or portfolio pages, show a section-stack / page-template flow instead.
- High-detail briefs are not low-confidence filler tasks. Treat exact user-provided colors, title, typography, responsive classes, content, component recipes, dependencies, and asset URLs as confirmed brief evidence; only missing decisions belong in `DESIGN_GAPS.md`.
- Missing core tokens should remain visible as validation failures. When the source cannot prove a needed value, DESIGN.md must contain a documented `recommended-default` decision rather than letting the renderer invent generic blue, Inter, or generic admin UI.

### 7. Generate DESIGN_GAPS.md

Always generate `DESIGN_GAPS.md` by default. Use the script:

```bash
python3 scripts/generate_gaps_doc.py /absolute/path/to/DESIGN --markdown-name DESIGN.md --language zh
```

DESIGN_GAPS.md structure (7 numbered sections + header intro):

- Header: file description, evidence mode, confidence, generation time
- §1: Overall confidence summary
- §1b: Current default decisions (conditional — only when `evidence.decisions` or `knownLimits.defaultDecisions` are present)
- §2: High-priority pending items
- §3: Medium-priority pending items
- §4: Low-priority pending items
- §5: Design conflict list
- §6: Uncovered / unobserved content
- §7: Manual confirmation record
- Confirmation workflow (unnumbered)

Gap sources: `openQuestions`, `knownLimits`, `assumptions`, `legacyTokens`, and low-confidence or `recommended-default` entries in `evidence.decisions`.

Gap types: `unconfirmed`, `approximate`, `conflict`, `inferred`, `recommended-default`, `legacy`, `unsupported`.

Each gap must contain: ID, priority, type, question, current judgment, evidence source, confidence, impact scope, current handling strategy, question needing manual confirmation, and write-back location. Every gap must have a current decision or fallback rule.

### 8. Validate and refine

Run the validator and fix hard failures:

```bash
python3 scripts/validate_design_folder.py /absolute/path/to/DESIGN --format ai-design-system-v3 --markdown-name DESIGN.md
```

Then do a manual pass:

- exactly one markdown design file exists
- `DESIGN_GAPS.md` exists
- front matter and prose describe the same system
- `tokens.colors` exposes flat semantic aliases (`primary`, `text`, `canvas`, `surface`, `border`) and no second token system is introduced
- evidence mode, runtime state, source confidence, and known gaps are clear
- source-derived outputs cite real component primitives and page templates
- component token references such as `{tokens.colors.primary}` resolve
- previews expose the correct 4-section structure (design style overview, basic tokens, component specs, template pages) and use real token values, not generic defaults
- **component visual samples use inline styles from actual token values**: spot-check button and tag samples — the rendered inline styles must contain the same color, radius, and spacing values shown in the token documentation

## Iterative Refinement Workflow

After generating the initial design system package, users can iteratively refine it:

1. **Review DESIGN_GAPS.md** to see what needs confirmation.
2. **Provide feedback** (e.g., "Sidebar width confirmed as 240px").
3. **Update DESIGN.md** with confirmed values, especially in the relevant chapter and front matter.
4. **Regenerate previews** to reflect the updates.
5. **Update DESIGN_GAPS.md** to move confirmed items to the Manual Confirmation Record section.
