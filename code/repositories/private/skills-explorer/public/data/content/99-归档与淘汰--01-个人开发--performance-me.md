# performance-me — 月度绩效自评

把"这个月做了什么"写成能通过审核的绩效自评；月初反向支持绩效目标制定。

**核心原则：每个结论都要有数据或具体事件支撑。** 自评审核不通过的常见根因只有一种：只有态度描述（如"积极认真完成分配工作"），没有数据与事件。所有模板和规则都围绕这一点。

## 动笔前必读

- **必读** `references/template.md`：全部绩效维度的填空模板、数据来源和分档对齐规则，按表单维度名对号入座。
- 仅当需要完整真实案例对照时才读 `references/example-anonymized.md`；快速填表场景**不要加载**它。

## 身份与数据源（当次用户指令可覆盖）

- git 邮箱：优先用用户当次提供的；未提供时用 `git config user.email` 推断，并向用户确认一次。
- 缺陷/需求系统：以团队实际使用的为准（TAPD/Jira/禅道等）；量化指标的分子分母只认系统导出或截图。
- 考核月份：优先从绩效表标题解析（如"2026年8月员工绩效考核"）；解析不到时默认当前自然月，并向用户确认一次。注意表单维度名逐月会变，每次以当期表单为准，不沿用上月假设。

## 工作流 A：月末自评（主场景）

### 1. 收集输入

必须拿到两样东西，缺哪样向用户要哪样，其余全部自行收集：

1. **绩效表内容**：截图或粘贴文本。逐维度记下：维度名、权重、评价内容、**计算说明及评分标准**。评分档位（如"85-100：按时并高质量完成""80-100：按计划时间完成，设计输出超出预期"）直接决定每个维度该写几条、写到多具体——完成情况的措辞要复用目标档位的关键词，让审核人一眼能对上档。
2. **缺陷/需求数据**（仅当表里有缺陷需求比、bug率类量化指标）：让用户提供缺陷系统"当月创建 + 处理人=本人"的缺陷列表和需求分工表。git 的 fix 提交数不是缺陷数，永远不能拿来当分子。

### 2. Git 分析（前端/后端仓库通用）

在用户指定仓库（未指定则当前仓库）执行：

```bash
# 提交清单。--all 覆盖未合并分支；结果里排除 "On xxx:" / "index on xxx:" 开头的 stash 条目
git log --all --author="<邮箱>" --since="<月初>" --until="<次月1日>" --pretty=format:"%h|%ad|%s" --date=short

# 量级：变更文件数、增删行数
git log --all --author="<邮箱>" --since=... --until=... --pretty=format: --numstat \
  | awk 'NF==3 {add+=$1; del+=$2; files++} END {print "files:"files, "additions:"add, "deletions:"del}'

# 类型分布（仓库有 type(scope): 提交约定时）
git log --all --author="<邮箱>" --since=... --until=... --pretty=format:"%s" \
  | sed -E 's/^([a-z]+)\(.*/\1/; s/^([^(:]+).*/\1/' | sort | uniq -c | sort -rn
```

聚类规则：

- 有 scope：按 scope 聚成 3-6 条工作流，表述用中文业务名。
- 无提交约定（多数后端仓库）：按提交信息里的需求单号（JIRA/TAPD ID）聚类；没有单号则按变更文件的顶层目录聚类。
- feat 类提交数 ≈ 新功能需求量的参考值，可用于吞吐类维度；fix 类里大量是自测、联调修正、体验微调，对外表述用"问题在提测/当期收敛"，不能等同于缺陷数。

多项目覆盖：绩效表常有多个项目维度，用户往往说不清维度名对应哪个仓库。扫描同级/常用工作区目录：

```bash
for d in <工作区>/*/; do
  [ -d "$d/.git" ] && n=$(git -C "$d" log --all --author="<邮箱>" --since=... --until=... --oneline 2>/dev/null | wc -l) \
  && [ "$n" -gt 0 ] && echo "== $d : $n commits"
done
```

注意：**维度名 ≠ 仓库名**（案例：表单维度是一个产品名，本地仓库名是英文代号，README 首行才写明产品全称，且该月用户在该仓库可能 0 提交——此维度也可能是上月延续或由他人负责的关联端）。用 README 首行、最近提交、页面标题反查对应关系；查不到对应仓库或当月无提交的维度，写通用句并标注 `[需人工补充：xxx]`，不要猜着写。

### 3. 逐维度起草

按 `references/template.md` 对应题型起草。硬规则：

1. 先给结论（如"任务按时达成"），再补范围、数据、结果。
2. 每个维度至少一个数字（提交数/需求数/缺陷数/比例/吞吐量）或一件具体事（模块名 + 做了什么 + 结果）。
3. git 无证据的维度：写一句通用表述 + 显著标注 `[需人工补充：xxx]`，让用户补真实内容，不要替用户编。
4. 形容词（积极、主动、认真）只做连接词，不作为论据。

### 4. 总自评评语

固定三段结构：

- **主要任务**：3-5 条，每条对应一条工作流，动词开头，带模块名。
- **贡献**：量级（提交数、行数、需求数）+ 质量行为（接口契约驱动、口径统一、清理历史逻辑、公共能力沉淀、兼容性修复）。
- **问题与改进**：2 条真实、可改进的过程问题（如"契约确认可以更前置""设计标注对齐可以更细、一次做对"）。不写人格缺点，不写"沟通不足"式空话。

### 5. 核对后输出

- 数字与 git 命令输出、缺陷系统数据一致；每条事件性表述能对上至少一条提交记录（审核人追问时用户要答得上来）。
- 缺陷数、需求数未经系统数据核实前，不得写进最终文本。
- 按绩效表字段顺序输出纯文本块，可直接粘贴；`[需人工补充]` 标注保留给用户处理。

## 工作流 B：月初/季度初目标制定

- 从表单指标库选指标（表单通常约束：每模块目标个数 ≥1、模块内权重和 = 100%），优先延续上月指标保证可对比。
- 目标值写可验证的量化承诺（如"任务按时达成率≥95%""每月 bug<1""季度月均需求吞吐量≥N"），不写"继续保持""再接再厉"式无法验收的表述。

## 红线

1. 不编造缺陷数、需求数、比例、分数档。
2. git fix 数不等于缺陷数，不进表格。
3. 不替用户定自评分：把数据对照表单档位摆出来，分数由用户确认；档位临界（如比例贴近目标值）要显式提示。
4. 绩效维度与仓库对应不上时，摆出证据并建议用户与上级确认，不猜测着写。
