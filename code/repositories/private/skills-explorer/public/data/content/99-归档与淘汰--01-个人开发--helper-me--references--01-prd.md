# PRD To Module Blueprint

从 PRD、原型截图、接口资料、已有源码和历史 Bug 进入可执行开发蓝图：先定页面布局、组件边界、模块骨架、状态模型和接口契约，再进入编码。

## 输入优先级

当前源码 > 当前 README/dev/docs > PRD 与截图 > 历史 Bug 与测试 > 旧 PRD。当前事实优先，历史材料只作经验来源。

## 先判项目形态

| 项目形态         | 先读入口                                                           | 蓝图重点                                         |
| ---------------- | ------------------------------------------------------------------ | ------------------------------------------------ |
| Taro 小程序      | `package.json`、`src/app.config.ts`、`src/app.tsx`、request、store | 主包、分包、登录态、请求、业务主链路             |
| Taro H5 内嵌 App | `app.h5.tsx`、`authWrapper`、原生 SDK、页面入口                    | 原生 SDK、登录态缓存、H5 路由、原生注入数据      |
| Umi/Max 微前端   | `config/routes.ts`、`src/app.tsx`、`src/access.ts`、典型页面       | qiankun、权限、字典、通用列表组件、动态表单      |
| 独立 Node 服务   | `README.md`、`package.json`、routes、schemas、service、worker      | route、schema、任务状态、媒体处理、storage、测试 |
| 文档或学习库     | `dev/README.md`、`docs/README.md`                                  | 文档索引、阅读顺序、维护规则、验收入口           |

## 从组件反查页面入口

用户提供组件/页面文件，或问"这个组件从哪进""菜单路径是什么"时，先反查真实入口再做蓝图。

执行顺序：从组件路径搜 import/动态 import → 上追页面级文件（`src/pages/**`、`src/views/**`、懒加载组件或 `router-view` 父页面）→ 对齐 routes/菜单配置的 title、name、path → 搜 `router.push`/`router-link`/redirect 判断路由是否仍在用 → 输出真实点击路径，每一步对应界面可见的菜单、Tab、按钮或链接文案。

| 菜单可见 | 代码有跳转 | 结论                                 |
| -------- | ---------- | ------------------------------------ |
| 是       | 是         | 正常入口，输出菜单路径和其它跳转入口 |
| 是       | 否         | 主要从菜单进入，说明未发现其它跳转   |
| 否       | 是         | 输出触发跳转的页面、按钮或链接       |
| 否       | 否         | 标注可能废弃，暂停确认是否仍在使用   |

输出：进入路径 + 点击顺序 + 路由 path（或测试环境 hash）+ 组件职责 + 废弃路由风险。

## 截图到模块蓝图

截图/原型先按业务区域拆布局再决定组件（页面壳 / 筛选栏 / 标题操作区 / 主视图 / 分组页签 / 内容轴 / 表单详情弹窗，各归其位）。

拆分规则：

1. 按业务区块和交互职责拆，不按视觉元素机械拆；超过 500 行只是提醒，以职责、状态和复用边界裁决。
2. 能独立拥有状态、样式、接口动作或验收点的区块进 `components/`。
3. 页面入口只保留布局组合，业务编排进 `hooks/use<Module>.ts`（`index.hook.ts` 为历史命名，新模块不用）。
4. 弹窗、浮层、内容卡片先定义状态机，再写 UI。

## 模块骨架契约

新模块的默认目录、分层职责（`index.tsx`/`index.hook.ts`/`service`/`types`/`utils` 各层禁止事项）和轻量/重模块升级规则，以 [web-me 节](../03-dev/SKILL.md) 的"默认目录 / 目录索引规则 / 分层规则"为准，不在此复制。蓝图阶段只输出目录建议，并标注每个文件的新增与复用边界。

## 输出蓝图

| 部分     | 内容                                         |
| -------- | -------------------------------------------- |
| 项目定位 | 业务类型、目标端、技术栈、运行前置           |
| 页面范围 | 本模块解决什么，哪些能力本轮不做             |
| 区域拆分 | 页面区域、弹窗、浮层、列表、表单、媒体区     |
| 组件树   | 页面入口、容器组件、业务组件、共享组件       |
| 目录骨架 | 文件和目录职责，新增与复用边界               |
| 状态模型 | URL、页面 hook、Zustand、storage、服务端状态 |
| 数据流   | 初始化、查询、提交、刷新、失败路径           |
| 接口依赖 | 请求参数、响应字段、字典、权限、任务状态     |
| 测试入口 | 首批轻量测试、接口契约、人工验收             |
| 开发顺序 | 骨架、接口、状态、UI、兼容、总结             |

## dev/docs 知识库结构

模块级 `dev` 推荐 7 类目录（适用于体量大、资料多的重型模块；轻量资料直接进模块内 `docs/` 四册——prototype / interface / ui-design / test-case，口径见 [web-me 节](../03-dev/SKILL.md)「模块文档体系」，README 登记外部库路径即可，不在模块内重复建两套）：

| 目录          | 内容                                    |
| ------------- | --------------------------------------- |
| `01-技术方案` | 架构设计、处理链路、运行依赖、接口定义  |
| `02-产品原型` | PRD、原型截图、产品需求文档             |
| `03-UI设计`   | UI 还原说明、Figma 截图、样式清单       |
| `04-BUG报错`  | Bug 分类、踩坑记录、修复策略、历史问题  |
| `05-接口定义` | 接口字段、请求响应、Mock 数据、联调口径 |
| `06-测试用例` | 自动化测试、人工测试、截图验证          |
| `07-项目总结` | 模块说明、新手指南、阶段复盘、维护说明  |

## 反模式

- 不从 PRD 直接跳代码；不把截图中每个视觉元素拆成独立组件。
- 不让历史 README 覆盖当前源码事实；不用旧测试命令覆盖当前 `package.json`。
- 不把 `dev` 或 `docs` 当成资料垃圾桶。
- 不对大型项目全量扫源码，先从路由、入口、请求、状态、业务主链路切入。

## 输出格式

结论摘要 → 项目地图 → 模块蓝图 → 目录骨架 → 开发顺序 → 风险点 → 首批测试 → 待确认问题 → 交接或沉淀写入位置。
