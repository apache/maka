# 业务 UI 架构契约

本 skill 用来把旧 React、Vue 业务项目里反复验证过的经验沉淀为可执行契约。重点是页面布局、搜索表单、表格分页、加载更多、弹窗、无数据状态、中文注释、H5 业务适配和验收闭环。

核心判断：旧技术栈只提供案例证据，真正要复用的是业务 UI 的决策顺序、边界意识和失败模式。

## 契约速查表

| 场景 | 先看什么 | 本 skill 负责 | 需要组合的 skill |
| --- | --- | --- | --- |
| 页面布局 | `BaseLayout`、`MainLayout`、`Layout.vue`、路由壳 | 判断页面是否进入既有布局，明确导航、侧边栏、内容区和滚动归属 | 复杂视觉还原用 `css-me` |
| 搜索表单 | 附近完成页的 Form、请求参数、重置逻辑 | 统一查询、重置、页码回到第一页、参数清洗 | 表单校验复杂时结合测试 skill |
| 普通表格 | 表格封装、分页字段、total 来源、loading | 统一请求生命周期、分页状态、空状态、选择项 | 性能问题结合 `vercel-react-best-practices` |
| 加载更多 | API 分页字段、滚动容器、失败表现 | 判断 hasMore、追加数据、失败重试、隐藏无效 loading | H5 滚动细节结合 `taro-me` |
| 弹窗 | 同类新增、编辑、确认、导入弹窗 | 统一宽度、footer、遮罩关闭、重置、内部滚动 | 样式细节结合 `css-me` |
| 新增/编辑态 | 打开入口、record/id、详情接口、关闭回调 | 统一 open、echo、submit、success、close、reopen 状态机 | 复杂跨组件状态结合 `zustand-me` |
| 无数据和图片缺失 | Empty 组件、无数据图片、占位样式 | 统一居中、专用图、透明占位和错误保留 | 图片加载性能另用性能 skill |
| H5 适配 | 运行环境、键盘、横屏、安全区 | 定义业务可用性验收和触发边界 | 技术实现交给 `taro-me` |
| 中文注释 | 项目现有注释风格、复杂状态机 | 给业务意图、兜底原因、兼容原因写短注释 | 无 |

## 强度等级

用三个等级区分硬约束和建议。

- 硬约束：违反后容易造成业务错误、重复请求、数据丢失、布局不可用或用户误操作。
- 默认建议：优先采用，除非项目现有模式已经给出更强理由。
- 可选增强：有时间、有风险点或用户明确要求时补上。

在总结中说明被采用的硬约束，以及被放弃的默认建议。

## 基本姿态

开始实现前先读项目，因为业务系统最容易出错的地方通常是破坏本项目已经形成的页面契约。

硬约束：

- 先找同项目里最接近的已完成模块。
- 先找布局壳、路由结构、UI 组件库、请求封装、表格组件、弹窗样式、无数据规范和 CSS 约束。
- 优先复用本项目已有 helpers、组件和视觉语言。
- 保持最小改动，并说明为什么沿用或偏离现有模块。
- 需求、规则或信息不足时，暂停并向用户确认。

判断理由：

- 业务 UI 的一致性来自相邻模块，随意新建模式会让维护者在同一系统里记两套规则。
- 先读布局和共享组件，可以避免重复造 header、分页器、弹窗 footer、空状态。

## Skill 分工边界

本 skill 是业务 UI 主控 skill，负责判断页面应该长成什么样、状态应该怎么流动、验收应该看哪些业务态。

相邻 skill 职责：

- `css-me` 负责 CSS 还原、错位排查、overflow、`gap`、`inset`、响应式尺寸和视觉对齐细节。
- `taro-me` 负责 Taro、小程序、H5、多端、视口、安全区、移动端键盘和平台差异。
- `zustand-me` 负责 React Zustand 状态边界，尤其是搜索、表格、弹窗跨组件共享状态。
- `nextjs-react-typescript` 或 `next-best-practices` 负责 Next.js 路由、服务端与客户端边界。
- `vercel-react-best-practices` 负责 React 性能、组件组合和渲染开销。
- `test-driven-development`、`vitest`、`webapp-testing` 负责新行为、修复和回归验证。
- `design-taste-frontend` 只作为视觉质感辅助，用来判断间距、层级和观感，不主导后台表格和弹窗契约。
- `find-skills` 用于缺少领域 skill 或用户要求发现、安装 skill 的场景。

边界规则：

- 遇到 `100vh`、`safe-area`、`gap`、`inset` 时，本 skill 只判断是否影响业务可用性和验收范围，具体 CSS 改法交给 `css-me`。
- 遇到 H5 键盘、横屏、小程序、WebView 差异时，本 skill 只定义表单、弹窗、footer、滚动容器的业务目标，平台细节交给 `taro-me`。
- 如果任务同时涉及布局、表格、弹窗，本 skill 作为主 skill，其他 skill 作为专项补充。

## 页面布局契约

页面级需求先找基础布局，因为后台和业务系统的导航、权限、内容滚动通常由布局壳统一承载。

优先搜索：`BaseLayout`、`MainLayout`、`Layout.vue`、`BasicLayout`、`AppLayout`、`Outlet`、`router-view`、顶部导航组件、侧边栏或菜单容器。

硬约束：

- 顶部导航归布局组件管理。
- 侧边栏归布局或路由壳管理。
- 页面内容放进布局的 content 区域。
- 功能页不得重复实现 header、menu、breadcrumb、用户信息区。
- 明确滚动归属，常见做法是 body 固定，内容区或表格区滚动。

默认建议：

- 页面 padding、背景色、最小高度跟随现有 layout。
- 业务管理、工作流、运营页面优先对齐附近模块的导航高度、侧边栏宽度、内容区 padding、操作按钮位置、搜索区位置、表格高度和弹窗宽度。

判断理由：

- 布局壳承载系统身份，重复实现会造成权限入口、导航状态、滚动高度和响应式断点不一致。
- 滚动归属不清会引发布局抖动、表格高度失控和弹窗 footer 不可触达。

## 搜索表单契约

搜索表单要可理解、可重置、可复现，因为它决定用户能否回到同一个查询状态。

硬约束：

- 使用项目现有 Form 组件和校验方式。
- 搜索后从第一页重新加载。
- 重置按钮清空字段，并把页码重置到第一页。
- 文本提交前做 trim。
- 空查询字段在请求前清理。
- 日期范围拆成明确的开始和结束字段。

默认建议：

- 输入框支持清空时开启清空能力。
- 搜索按钮体现 loading。
- 密集业务页的主操作按钮优先放搜索栏右侧。
- 响应式表单保持列宽稳定，窄屏自然换行。

判断理由：

- 搜索不回第一页会导致用户在后几页看到空结果，以为数据不存在。
- 隐形默认值会让用户无法复现查询，也难以排查接口问题。
- 主操作放搜索栏右侧，可以让运营页保持“先筛选，再操作”的阅读路径。

```ts
// 搜索条件变化后回到第一页，避免旧页码导致空列表
setPage(1)
```

## 表格契约

表格应统一管理请求生命周期、分页、loading、选择项和空状态，因为表格是业务系统里最容易出现重复请求和状态漂移的组件。

编码前先确认：

- 页码字段叫 `page`、`pageNum`、`current` 还是其他名字。
- 每页数量字段叫 `pageSize`、`perPage` 还是其他名字。
- 总数字段来自 `total`、`count`、`meta.count` 还是其他结构。
- 本地表格使用 data function、ref method，还是外部受控。
- loading 和 emptyText 在哪里配置。
- 刷新后是否需要清空勾选行。

硬约束：

- loading 中阻止重复请求。
- 搜索从第一页开始。
- `page`、`pageSize`、`total`、列表数据放在清晰的状态组里。
- 普通分页替换列表数据。
- 无限列表追加列表数据。
- 刷新失败时尽量保留当前数据。

默认建议：

- 兄弟模块已有 `refresh` 或 `init` 暴露方式时继续沿用。
- 数据刷新后默认清空行选择，除非业务要求保留。
- 总数文案沿用项目 UI 文案。
- 项目支持切换 pageSize 时继续支持。
- pageSize 改变后重算或重置页码。

判断理由：

- page 字段命名是老项目最常见的返工点，先确认字段比后面补 bug 成本低。
- 保留失败前数据能避免用户在网络波动时丢失上下文。
- 普通分页和无限列表的数据合并策略相反，混用会造成重复数据或列表闪空。

## 加载更多契约

加载更多的核心是“接口状态驱动展示”，因为底部文案本身就是分页状态的用户承诺。

硬约束：

1. 接口返回存在下一页时，底部显示 `加载中...`。
2. 接口返回不存在下一页时，不显示 `加载中...`。
3. 滚动到底部时，请求下一页并追加数据。
4. 加载失败时保留当前数据，并允许用户重试。
5. 没有下一页时，不展示不可点击的无效按钮。

判断顺序：

1. 有 `hasNext` 或 `hasMore` 时直接使用。
2. 有 `nextPage` 时使用 nextPage 是否存在。
3. 有 `total` 时用 total、当前 page、pageSize 和已加载数量计算。
4. total 缺失时，只能根据本页返回数量推断，并用中文注释说明限制。

```ts
// 接口没有 hasMore 时，用 total 和已加载数量兜底判断是否还有下一页
const loadedCount = currentList.length
const pageLoadedCount = nextItems.length
const totalLoaded = loadedCount + pageLoadedCount
const hasMore = totalLoaded < total
```

滚动触发：

- 监听内容滚动容器，不默认监听 `window`。
- 请求中不重复触发下一页。
- 下一页成功后追加到当前列表。
- 下一页失败后保留旧列表，并提供重试。
- 没有下一页时隐藏 `加载中...`。

判断理由：

- 只要没有下一页仍显示 `加载中...`，用户就会误以为系统卡住。
- 失败后清空列表会放大网络错误的伤害，也会让用户丢失已浏览位置。

## 弹窗契约

新增、编辑、确认、导入、详情类弹窗要保持结构一致，因为弹窗承载的是高风险操作和短流程决策。

修改前先看附近弹窗：宽度、label 宽度、footer 对齐、按钮顺序、点击遮罩是否关闭、表单重置时机、滚动区域归属、标题样式、是否 destroy on close。

硬约束：

- 有状态表单弹窗不允许点击遮罩关闭。
- 关闭时重置表单和校验，除非明确需要保留草稿。
- 提交按钮展示 loading 并防止重复点击。
- 长内容弹窗使用内部滚动，footer 保持可触达。
- 弹窗 body 的最大高度跟随视口。

默认建议：

- 取消按钮保持次要视觉。
- 危险确认使用项目已有 warning 或 danger 风格。
- 添加记录或类似创建弹窗复用附近新增或编辑弹窗宽度。
- 字段按业务含义分组。
- 只有用户明确要求草稿能力时才保留未提交内容。

判断理由：

- 遮罩误关会造成表单输入丢失。
- footer 被滚走会让用户在短视口和移动端无法提交或取消。
- 同系统弹窗宽度不一致会降低用户对字段复杂度的预期。

## 新增/编辑态状态机契约

新增和编辑共用同一个弹窗或页面时，必须把它当成状态机处理。目标是避免编辑数据残留到新增态、保存后父列表不刷新、异步详情覆盖新打开弹窗、关闭后校验和临时选择项不清空。

状态机总览：

| 阶段 | 新增态 | 编辑态 | 必查项 |
| --- | --- | --- | --- |
| open | 清空 record/id，resetFields，设置默认值 | 设置 record/id，再请求详情或回填传入数据 | mode 是否唯一可信 |
| echo | 不允许残留旧值 | loading 中回填详情，必要时禁用关闭和提交 | 异步返回是否会覆盖新弹窗 |
| submit | 调 add API | 调 update API，并带上 id | loading 是否防重复提交 |
| success | 刷新父级，关闭 | 刷新父级，关闭 | 父级刷新方式是否明确 |
| close | 清表单、清校验、清临时态 | 清 record、清表单、清选择态 | afterClose/closed 是否执行 |
| reopen | 不显示旧编辑数据 | 显示当前 record 数据 | 新增态是否错回显 |

硬约束：

- `mode`、`record`、`id` 只能有一个主判定来源，标题、接口和提交参数都跟随它。
- 新增入口必须清空 `record/id`，重置表单字段和校验，再写入默认值。
- 编辑入口先设置 `record/id`，再执行详情请求或同步回显。
- 编辑详情请求要有 loading；请求中不要允许重复提交。
- 保存成功后先通知父级刷新，再关闭弹窗或返回上一页。
- 弹窗关闭完成后清理表单、校验、record、loading、临时列表、树选中、多选结果、上传状态和子弹层显隐。
- 异步详情返回前，如果用户已经关闭或切换到另一个 record，不得覆盖当前表单。

默认建议：

- React 弹窗优先用 `ref.open(record?)` 或受控 `open + mode + record`，不要把打开、回显和提交散在多个地方。
- Vue 弹窗可暴露 `init(id?)`、`add()`、`edit(record)`，并在 `closed` 或 `before-close` 里统一清理。
- Ant Design 类弹窗优先用 `afterClose` 清理，避免关闭动画期间清空导致闪烁。
- Element 类弹窗可在 `@closed` 清表单，在 `before-close` 处理拦截和确认。
- 父列表刷新统一封装为 `refresh/reload/callback`，子组件只通知成功，不直接理解父级表格内部状态。
- 页面型新增或编辑使用路由参数、返回刷新或 `eventChannel.emit('refresh')`，不要假装它是弹窗生命周期。

打开顺序：

```ts
// 新增入口先清旧态，再设置默认值，避免编辑残留进入新增态
setRecord(null)
form.resetFields()
form.setFieldsValue(defaultValues)
setOpen(true)
```

```ts
// 编辑入口先记录当前 id，再请求详情回显
setRecord(row)
setOpen(true)
await fetchDetail(row.id)
form.setFieldsValue(detail)
```

关闭清理清单：

- `form.resetFields()` 或等价表单重置。
- `form.clearValidate()` 或等价校验清理。
- `setRecord(null)`、`setMode('add')` 或清空 `id`。
- 清空树选中项、穿梭框、多选 select、上传列表、搜索缓存、临时表格数据。
- 关闭子弹层、picker、popover、图片预览和二级 modal。
- 重置 `loading`、`submitLoading`、`disabled`、`searching`、`lockRef` 等防重复状态。

事件监听契约：

- Vue 子弹窗保存成功后 `emit('refresh')`，父级负责 `getList`。
- React 子弹窗保存成功后调用父级 `callback/reload`，父级持有 `tableRef/actionRef`。
- Taro 或小程序跨页保存成功后，通过 `eventChannel.emit('refresh')` 通知 opener，再 `navigateBack`。
- 监听 visible/open 变化时，只在打开瞬间做回显，只在关闭完成后做清理，避免每次渲染都重置用户输入。

异步竞态防线：

```ts
// 只允许当前打开记录的详情回填，避免慢请求覆盖新弹窗
const currentId = row.id
latestOpenIdRef.current = currentId
const detail = await fetchDetail(currentId)
if (latestOpenIdRef.current !== currentId) return
form.setFieldsValue(detail)
```

判断理由：

- 新增和编辑共用 UI 可以省重复代码，但状态边界不清会制造最隐蔽的脏数据。
- 保存成功和关闭完成是两个时刻，前者负责业务结果，后者负责内部清场。
- 父级刷新权应该留在父级，子级只发出“保存成功”的事实。
- 异步回显必须防竞态，因为用户连续点击两条编辑记录时，慢请求最容易覆盖快请求。
## 无数据、加载和错误状态契约

组件级默认状态要统一，因为空白区域、破图和闪烁会让用户误判系统是否工作正常。

无数据硬约束：

- 在可用面板内居中。
- 项目已有 UI 库 Empty 组件时优先使用。
- 项目已有无数据专用图片时优先使用。
- 文案短，必要时带业务语义。

图片缺失硬约束：

- 不显示浏览器破图图标。
- 使用和真实图片相同宽高、比例的占位。
- 需要保持排版时使用透明占位。
- 需要提示用户时使用可见无数据图或文案。

加载和错误硬约束：

- loading 靠近被影响的组件。
- 后台刷新时尽量保留已有数据。
- 下一页加载失败时保留已加载数据。
- 可恢复失败提供重试入口。
- 错误提示沿用本项目 message、notification 或 modal。

判断理由：

- 无数据居中能让用户第一眼知道查询已完成。
- 图片占位稳定能避免报告、影像、卡片列表发生布局跳动。
- 局部 loading 比全屏 loading 更能保留用户上下文。

## 中文注释契约

需要写代码注释时，以中文短注释为主。注释要解释业务意图、兼容原因、状态机边界和不明显副作用。

硬约束：

- 复杂分页、键盘压缩、横屏适配、接口字段兜底逻辑要补中文说明。
- 公共组件的 props、事件、暴露方法优先用中文说明业务用途。
- 注释跟随代码一起维护，避免留下过期判断。

默认建议：

- 项目已有英文注释风格时，可保留局部英文专有名词，但新增解释仍以中文为主。
- 单行能说清的，不写长段落。

反例：

```ts
// 设置 loading 为 true
setLoading(true)
```

正例：

```ts
// 键盘弹起后重新计算可视高度，避免底部按钮遮挡输入框
const viewportHeight = window.visualViewport?.height ?? window.innerHeight
```

判断理由：

- 注释的价值在于补足代码无法表达的业务判断。
- 空注释会浪费阅读注意力，过期注释会误导维护者。

## H5 业务适配边界

本 skill 不主导 H5 底层兼容实现，只定义业务 UI 在移动端必须满足的可用性目标。

硬约束：

- 页面有明确的主要滚动容器。
- 键盘弹起后当前输入框仍可见。
- 固定底部按钮不被键盘遮挡。
- 横屏时 header、footer、表格、弹窗内容不重叠。
- 弹窗 footer 在短视口下仍可触达。

默认建议：

- 移动浏览器优先考虑 `100dvh` 或运行时视口变量。
- 有刘海屏风险时检查 `safe-area-inset-*`。
- 老 WebView 对 `gap` 和 `inset` 准备兜底写法。

需要专项 skill 时：

- 具体 CSS 兜底、样式改法、溢出修复交给 `css-me`。
- Taro、小程序、WebView 差异、键盘事件和安全区细节交给 `taro-me`。

```ts
// 键盘弹起后同步可视区域高度，避免表单 footer 被遮挡
const updateViewportHeight = () => {
  const height = window.visualViewport?.height ?? window.innerHeight
  document.documentElement.style.setProperty('--app-view-height', `${height}px`)
}
```

判断理由：

- 旧项目里的 `100vh` 和固定高度在移动浏览器上容易被地址栏、键盘和横屏压缩击穿。
- 本 skill 先定义“用户不能被遮挡、不能丢操作”，专项 skill 再决定具体 CSS 或平台写法。

## 资源型组件生命周期

播放器、图表、监听、定时器必须成对清理。页面卸载、弹窗关闭、路由切走后不应继续回调。图表实例要 `dispose`，resize 监听要移除。

## 常见反模式清单

遇到这些做法要优先拦截，并说明原因。

| 反模式 | 为什么危险 | 推荐修正 |
| --- | --- | --- |
| 功能页自己实现一套 header 或 sidebar | 导航状态、权限入口、滚动高度会分裂 | 回到 BaseLayout 或路由壳 |
| 搜索后沿用旧页码 | 后几页可能空白，用户误以为无数据 | 搜索和重置都回第一页 |
| 不确认接口分页字段就写分页 | `page/pageNum/current` 混用会导致请求错页 | 先读 API 调用和已有模块 |
| 没有下一页还显示 `加载中...` | 用户会认为系统卡住 | 用 hasMore 或 total 计算后隐藏 |
| 下一页失败后清空列表 | 网络错误会导致用户丢失已浏览数据 | 保留旧列表，提供重试 |
| 表单弹窗点击遮罩关闭 | 输入内容容易误丢 | 有状态弹窗禁用遮罩关闭 |
| 新增入口没有清 record/id | 上次编辑数据会错误回显到新增态 | open(add) 先清 record 和表单再写默认值 |
| 编辑详情慢请求覆盖新弹窗 | 连续点击编辑时表单显示错记录 | 用当前 id 或请求序号拦截过期回显 |
| 保存成功只关闭不刷新父列表 | 用户以为保存失败或数据没变化 | 子级通知成功，父级统一 reload |
| 关闭时只 resetFields | 树、多选、上传、搜索缓存仍残留 | afterClose/closed 统一清理态资产 |
| 长弹窗 footer 跟随正文滚走 | 短视口下无法提交或取消 | 内部滚动，footer 固定可触达 |
| 空状态只留白 | 用户无法判断是加载中、无权限还是无数据 | 使用 Empty、专用图或业务文案 |
| 图片缺失显示破图 | 报告和卡片布局跳动，视觉不可信 | 使用等比例占位 |
| 注释复述代码 | 增加噪音，没有知识增量 | 注释业务原因、兼容原因和边界 |
| 直接把 CSS/H5 细节塞进本 skill | 职责重叠，后续难维护 | 本 skill 定业务目标，专项 skill 定实现 |

## 复杂业务看板实战补充

本节沉淀复杂业务看板页面的实战决策，涵盖横屏 H5 适配、状态看板、强态依赖、多接口作用域、多端密度等场景。这些模式来自真实项目验证，代码是第一证据，开发文档作为决策动机补充。

### 三层分离实战

复杂业务看板把单页复杂度按"布局 → 编排 → 资源/变更 → 纯函数"四层切分，每层职责可单独验收。这套分层是看板类业务页面的强参考。

| 层级 | 角色 | 职责边界 | 不允许做的事 |
| --- | --- | --- | --- |
| 布局层 | 页面入口组件 | 组装布局壳、左侧栏、右侧主区、时间轴和操作层，只调一次编排层 hook 把聚合结果分发给子组件 | 不承载业务转换、不直接发请求、不维护表单状态 |
| 编排层 | 根 hook | 聚合多个子 hook、跨 hook 编排、详情竞态、操作互斥、变更后刷新调度 | 不写接口字段映射、不写时间轴几何计算 |
| 资源层 | 查询 hook | 树形数据、分类维度、列表、统计、标记五类查询接口 + 会话缓存读写 + 日期/组织/维度作用域串联 | 不发变更请求、不维护弹窗态 |
| 变更层 | 变更 hook | 新增、修改、详情、状态操作四类变更接口 + 请求前 ID 校验 + 失败兜底 | 不直接刷新列表（由编排层调度）、不写业务过渡逻辑 |
| 工具层 | 纯函数模块 | 时间戳转换、表单校验、时间轴几何、状态映射、查询参数构造 | 不持有 React state、不调用接口 |
| 缓存层 | 会话缓存 store | 树形数据、拍平结构、按维度分组、实体搜索、选项搜索等会话缓存 | 不做持久化、不发请求、不做派生计算 |

编排层根 hook 的核心动作清单：

| 动作 | 实现要点 |
| --- | --- |
| 详情竞态 | 用自增序号 ref，详情接口返回后比对序号，过期响应直接丢弃，避免连续点击两张卡片时慢请求覆盖快请求 |
| 操作互斥 | 用同步 ref 防重入，状态操作和二次确认进入 `try/finally` 复位，弥补 state 异步更新窗口期 |
| 提交防重 | 用"保存中"按钮态控制，提交函数入口 early return |
| 变更后刷新 | 用统一刷新调度函数统一调度列表、统计、标记三类刷新 |
| 弹窗关闭清理 | 用集中清理函数一次性清空可见态、编辑标识、编辑快照、错误态 |
| 关联实体实时查询 | 在保存前按业务键实时查关联实体 ID，避免关联记录未落地导致提交失败 |

判断理由：

- 编排层只暴露"页面要做的事"，纯转换沉到工具层，让根 hook 保持可读。
- 同步 ref 和 state 双保险防重入，因为 React state 在事件循环内不会立即更新，单靠 state 拦不住连点。
- 详情接口和状态操作都返回新实体，由编排层写回列表和选中项，避免组件层各自维护一份。

### 业务维度作用域

这是复杂业务看板最高频踩坑点。同一页面内"全局统计"和"局部列表"使用不同的业务维度，混用会造成列表、统计、标记口径不一致。

| 数据域 | 业务维度 | 是否随视图切换变化 | 典型实现 |
| --- | --- | --- | --- |
| 业务列表接口 | 随视图切换的维度标识字段 | 是，随右侧 tab 切换 | "我的"传当前登录用户，"待分配"传空字符串，分类 tab 传该分类 ID |
| 全局统计接口 | 固定当前登录用户维度 | 否 | 不随 tab 变，保证左侧全局口径稳定 |
| 日历标记接口 | 固定当前登录用户维度 | 否 | 不随 tab 变，不随左侧状态勾选变 |
| 左侧状态筛选栏 | 仅本地过滤"我的"页签数据 | 否 | 不进入列表接口请求参数 |

维度标识字段解析逻辑示例：

```ts
function resolveListDimensionId(activeTab, currentUserId) {
  if (activeTab === MY_TAB_ID) return currentUserId;
  if (activeTab === UNASSIGNED_TAB_ID) return '';
  return activeTab;
}
```

判断理由：

- 全局统计若跟随右侧 tab，用户切换分类时左侧数字会跳动，造成"我只是看一下某个分类，全局数据怎么变了"的困惑。
- 列表是局部视图，必须跟随 tab 才有意义；统计和标记是全局视图，必须固定用户口径。
- 左侧状态栏如果进入列表请求，会让"待分配"和"分类 tab"也带上状态过滤，破坏视图语义。

踩坑复盘：早期将左侧勾选状态、列表请求、日历标记和时间轴过滤共享同一状态，导致状态栏局部筛选污染了右侧分类 tab 数据加载。修正方式是把列表、统计、标记、左侧状态栏的作用域显式拆开，并用结构测试锁住。

### UTC 时间契约

后端存毫秒时间戳，前端统一走项目公共 UTC 工具转换，刻意不引入 dayjs 等额外时间库。

| 转换方向 | 工具 | 用途 |
| --- | --- | --- |
| 毫秒时间戳 → 页面日期 | 公共时间工具，格式 `YYYY-MM-DD`，按 UTC 口径 | 卡片日期、列表日期 |
| 毫秒时间戳 → 页面时间 | 公共时间工具，格式 `HH:mm`，按 UTC 口径 | 卡片开始时间 |
| 表单日期+时间 → 提交时间戳 | 公共本地转 UTC 工具 `localTimeToUtc('${date} ${time}:00')` | 新增/修改提交 |
| 选中日期 → 单日查询范围 | 公共本地转 UTC 工具，取 `00:00:00` 和 `23:59:59` | 列表接口请求 |
| 表单日期+时间 → 本地时间戳 | 直接用 `new Date().getTime()` | 仅用于本地限制判断（如"截止前 1 小时"），不提交后端 |

硬约束：

- 公共时间工具的 UTC 展示口径参数必须显式传入，保持全项目统一。
- 不在业务模块内自建固定时区偏移转换逻辑。曾有自建 `timestamp + 8小时` 算法与另一端看板产生 8 小时偏差，最终全部回退到公共工具。
- 后端时间戳不能直接和浏览器 `Date.now()` 比较，因为提交时间戳存在跨端时区口径差异。本地限制判断用独立的本地时间戳单独算。

日历标记字符串例外：

- 日历标记是后端返回的 `YYYY-MM` 本地字符串数组，不走毫秒时间戳转换。
- 月历和周视图的标记显示只由"该日期是否有记录"决定，选中态不参与显示判断，只负责样式。

判断理由：

- 同一项目常同时存在多端看板实现（如 Web 与 H5），必须共用同一套 UTC 口径才能避免字段偏差。
- 自建时区转换会绕开公共工具的兜底，调试时无法判断偏差来自业务还是时区口径。
- 额外时间库会引入体积成本，且公共时间工具已覆盖所有场景。

### 多端单套密度

复杂看板页面在多端运行时，"已验收端的样式稳定性"优先级高于"调试端的视觉精确度"。当前只保留单套密度常量，没有按设备类型或视口分支。这是经过多轮博弈后的回退结果。

| 常量示例 | 典型值 | 用途 |
| --- | --- | --- |
| 时间轴刻度高度 | `48px` | 半小时刻度高度 |
| 时间轴边缘留白 | `16px` | 时间轴上下边缘留白 |
| 时间列宽度 | `90px` | 左侧时间列宽度 |
| 卡片最小高度 | `48px` | 业务卡片最小高度 |

多端密度回退决策链：

| 阶段 | 决策 | 动机 |
| --- | --- | --- |
| 初始 | 按设备类型 + 视口尺寸区分多套密度 | 不同设备体验差异大 |
| 第一次回退 | 密度获取函数固定返回单套，删除设备判断 | 调试端和目标端共用紧凑刻度，避免维护两套分支 |
| 第二次试探 | 动态几何值改走框架提供的尺寸转换工具 | 让宽屏调试页和目标端共用设计稿比例 |
| 第二次回退 | 删除尺寸转换函数，恢复原始 `px` inline style | 尺寸转换影响目标端已验收的时间轴比例，超出"保留原样式"约束 |
| 最终态 | 单套密度常量，几何值用原始 `px` | 保护目标端既有样式优先级最高 |

判断理由：

- 看板类页面在多端运行时，"已验收端的样式稳定性"优先级高于"调试端的视觉精确度"。
- 引入多套密度分支会让结构测试、视觉走查、回归成本翻倍，且容易在端之间互相污染。
- 动态几何走框架尺寸转换听起来统一，但会破坏既有端的像素口径，属于"看似正确实则破坏性"的改动。

### 变更后统一刷新调度

复杂看板的变更操作影响多个数据域，需要用统一刷新调度函数作为刷新总入口，新增、修改、状态操作成功后统一调用。

| 刷新项 | 触发条件 | 数据源 |
| --- | --- | --- |
| 刷新业务列表 | 选中日期未变（`sameSelectedDate`）且调用方未禁用列表刷新 | 列表接口 |
| 刷新全局统计 | 始终刷新 | 统计接口 |
| 刷新日历标记 | 变更后的日期与当前面板同月（`shouldRefreshDateMarkers`） | 日历标记接口 |

刷新调度实现要点：

```ts
// 延迟一小段时间，让 toast 和弹窗关闭动画先完成，再触发接口刷新
setTimeout(() => {
  if (sameSelectedDate && options.refreshList !== false) {
    refreshListAfterMutation(nextSelectedDate);
  }
  refreshStatistics();
  if (shouldRefreshDateMarkers) {
    refreshDateMarkers();
  }
}, 80);
```

硬约束：

- 列表是业务卡片的权威来源，变更成功后必须重新拉列表，避免详情回查和本地替换导致卡片状态滞后。
- 同月判定用年月字符串比较，跨月变更不刷新标记（用户已切月，旧月标记无意义）。
- 切换 tab 时通过配置项抑制列表刷新，因为切 tab 本身会触发列表 effect，重复刷新浪费请求。
- 三类刷新各自 `catch` 错误并保留当前数据，避免一次刷新失败影响其他刷新和主流程。

判断理由：

- 变更操作影响多个数据域（列表、统计、标记），不集中调度就会出现"卡片变了但统计没变"的撕裂。
- 小延迟是业务经验值，用来错开 toast 和弹窗关闭动画，避免刷新请求和动画帧冲突。
- 同月判定避免无效请求，跨月时标记由用户切月后的 effect 重新拉取。

### 结构测试驱动

复杂业务看板大量使用结构测试锁定行为，因为问题多来自参数、路径、样式和状态边界。测试以静态扫源码为主，不触发多端构建。

| 测试域 | 锁定内容 | 典型测试场景 |
| --- | --- | --- |
| 刷新链路 | 变更后列表、统计、标记刷新调用 | mutation 后三类刷新函数被正确调用 |
| 状态作用域 | 列表用随视图切换的维度字段，统计和标记固定用户维度 | 不同接口的维度参数口径正确 |
| 时间轴布局 | 密度固定单套、卡片几何、当前时间线 | 密度常量、卡片样式计算、时间标记 |
| 表单交互 | 必填校验、编辑态锁定、时间选项 | 表单弹窗样式、时间下拉选项生成 |
| 时间口径 | UTC 转换走公共工具、本地限制判断 | 时间转换函数使用公共工具 |
| 业务边界 | 操作时间限制、特殊业务场景、单位转换 | 取消修改的时间限制、时长单位转换 |

适用场景判断：

- 接口参数、字段映射、状态作用域、关键 CSS 类名、组件结构这类"源码静态可读"的契约，优先用结构测试锁。
- 视觉还原、真机交互、动画体验这类"运行时才能验证"的，结构测试只能锁关键选择器和类名，真机验收不可省略。
- 结构测试不替代单元测试和 e2e，它的价值是低成本锁住"容易被无意破坏的口径"。

测试路径说明：结构测试通常放在模块开发目录下的测试子目录。运行命令示例：

```bash
node <module-path>/test/<test-name>.test.cjs
```

### 复杂看板反模式补充

在"常见反模式清单"基础上，复杂业务看板额外暴露以下反模式：

| 反模式 | 为什么危险 | 推荐修正 |
| --- | --- | --- |
| 全局统计和局部列表共用筛选状态 | 切换分类 tab 时左侧统计和标记跟着变，破坏全局口径 | 统计和标记固定当前登录用户，列表用随视图切换的维度字段 |
| 自建时区转换绕开公共工具 | 与另一端看板产生时区偏差，调试时无法定位 | 统一走公共时间工具的 UTC 口径转换 |
| 多端维护多套密度分支 | 结构测试和视觉走查成本翻倍，端之间互相污染 | 单套密度优先，多套必须有强业务理由 |
| 详情慢请求覆盖新弹窗 | 连续点击两张卡片时表单显示错记录 | 用自增序号 ref 拦截过期响应 |
| 只用 state 防重入 | React state 异步更新，连点会穿透 | 同步 ref + state 双保险，`try/finally` 复位 |
| 变更后只刷当前卡片 | 统计和标记不刷新，数据撕裂 | 统一走刷新调度函数调度三类刷新 |
| 标记显示条件混入选中态 | 没有记录的选中日期也显示标记 | 标记只由"是否有记录"决定，选中态只管样式 |
| 时间戳直接和 `Date.now()` 比较 | 跨端时区口径导致限制判断错乱 | 本地限制用独立的本地时间戳单独算 |

## 项目经验来源

这些模式来自当前项目经验库中的已解压项目：

- 电商后台表格组件集中处理 loading、分页、请求参数、行选择和 ref 刷新。
- 电商后台搜索页组合搜索区域、右侧操作、表格高度计算和确认弹窗。
- Vue Element 后台布局使用顶部或左侧导航的路由壳，并通过 `router-view` 承载页面。
- Element 表格封装使用 data function、内部 loading、total 统计和外部 refresh。
- React 后台项目使用 `MainLayout`、header、content 和 `Outlet` 组织页面。
- 中后台 dashboard 组合搜索表单、表格高度计算、分页、展开行和表单弹窗。
- 导入类弹窗使用固定筛选头、内部滚动区和固定底部操作。
- 报告图片组件通过稳定占位避免破图和布局跳动。
- 横屏 H5 业务看板的三层分离、业务维度作用域、UTC 时间契约、多端单套密度、变更后统一刷新调度，参见上文"复杂业务看板实战补充"章节。
