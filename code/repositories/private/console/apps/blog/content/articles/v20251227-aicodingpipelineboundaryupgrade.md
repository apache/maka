# AI Coding流水线真实边界升级：执行路线+验收条件

- **视频 ID**：`V20251227-AICodingPipelineBoundaryUpgrade`
- **日期**：2025-12-27

> **一句话**：AI Coding 的真实边界不是“验收”一个点，而是两道门槛：**验收条件 + 执行线路**。

## 精华总结
- 只给验收不给线路，AI 会走歪路、产出假成果、在错误路径上返工；你省掉的是过程盯梢，不是责任。
- Prompt 演化不是越长越好，而是把“导航 + 质量门”写死：先读什么、怎么验证、失败怎么返工。
- 通用 6 步路线：读设计 → 读环境 → 读现有测试 → 实现 → 编译 → E2E（不通过就返工）。
- 工程化的本质：把资深工程师的带教路径外化成机器可执行的 Route。

## 行动清单
1. 任何交给 AI 的交付任务，至少写两道 Gate：Build + E2E（或最小可验证测试）。
1. 把 Route 写成步骤，并拆分到可控的 subagent 单元（实现/测试分离）。
1. 主控不放水：没有证据的“PASS”一律视为失败，必须 resume 返工。

## Highlights（原文摘录）
- AI 编程流水线的边界不是一个点，而是两道门槛：**验收条件 + 执行线路**。
- 只给验收不给线路，AI 会：走歪路 / 做出“看似完成”的假成果 / 在错误路径上反复返工。
- 流水线替代的是“人盯过程的时间”，不是“人对结果负责的义务”。
- AI 很像新人：不知道业务时会按自己的习惯乱试，或提前宣布完成。
- Prompt 演化的关键不是“更长”，而是“更清晰的执行链路 + 更硬的闭环”。
- 1.0~1.2 的核心失败模式：**没跑编译、没跑验收、主控没逼闭环**。
- 1.3 的关键改法：任务拆细（功能 / E2E 分两个 subagent），主控负责 build + E2E + 返工收敛。
- 给需求的粗暴 6 步模板：读设计 → 读环境 → 读现有测试 → 实现 → 编译通过 → E2E 验收返工闭环。
- 给新手建议：别 overdesign，先做出来、先投放、有人付费再补工程化（测试/遥测/模块化）。

## Insights（原文摘录）
1) 认知升级：Boundary = Acceptance + Route
- 过去你把“边界”理解为验收（终点），现在补上了“线路”（导航）。
- 这实际上是在从“结果约束”升级为“过程约束”，才足以让长链路任务收敛。

2) Prompt 演化的真实因果
- 1.0/1.1/1.2 翻车，不是模型不行，而是主控缺少“执行线路”与“闭环强制”：
  - 没有规定先读什么、先验证什么、失败如何返工；
  - 主控没有被迫执行 build/E2E 作为硬门槛。
- 1.3 成功的关键：把“导航 + 质量门”写死，并将执行拆到可控的 subagent 单元。

3) 工程化本质：把“新人带教”写成机器可执行的流程
- 你本质上是在把“资深工程师脑子里的带教路径”外化为 prompt 的 route。
- 这就是为什么它能跨项目复用：route 不依赖具体业务细节，依赖“做事顺序 + 证据链”。

4) 面向观众的可复制交付点
- 这期最值钱的交付不是“我用 1.3 跑通了”，而是那套 6 步模板：
  读设计 / 读环境 / 读现有测试 / 实现 / 编译 / E2
