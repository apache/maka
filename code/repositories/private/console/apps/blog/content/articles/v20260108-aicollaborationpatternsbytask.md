# 别再找万能 prompt：不同任务必须配不同协作模式

- **视频 ID**：`V20260108-AICollaborationPatternsByTask`
- **日期**：2026-01-08

> **一句话**：不存在“万能 prompt”，只有“任务类型 → 协作结构”的匹配；选错档位，AI 会把混乱放大成失控。

## 精华总结
- 你以为 AI 不稳定，很多时候是你把 **不该自动化的任务** 交给了它（或用错协作档位）。
- 协作模式不是“自动化程度”，而是 **人站在链路里的责任位置**：你把哪些判断留给自己，把哪些执行交给 subagent。
- 模式选择的核心不在“角色数量”，而在 **执行路线（Route）+ 验收条件（DoD）** 是否被写死。
- overnight 不是 autopilot：你睡觉的前提，是第二天你能用证据链验收（.artifacts），并把经验沉淀成可复用的演化记录（docs/evolution）。

## 行动清单
1. 先给任务定性：是“方向确认/信息收集”（轻协作）、还是“可验证交付”（重协作）、还是“高风险长链路”（契约优先）。
1. 写 Route：先读什么 → 再改什么 → 最后跑什么；写 DoD：一句话 Done + 可执行验证。
1. 只相信证据：把 `.artifacts` 当作这次执行的事实；把 `docs/evolution` 当作下次复用的经验。

## Insights（原文摘录）
1. 本期视频的真实主题不是“Prompt / Agent 技巧”，而是「任务—协作结构匹配」：
   - 你不是在选模型，而是在选一种失败形态。
   - 不同任务，对“失控成本”的容忍度完全不同，这决定了协作模式的选择。

2. 你隐含提出了一个重要但没明说的判断标准：
   - 协作模式 ≠ 自动化程度
   - 协作模式 = 人在链路中的“责任位置”
   CLI、主控+Subagent、契约式主控，本质区别不是复杂度，而是**谁对失败负责**。

3. 三种模式的真实分界线不是“强不强”，而是“累不累”和“可不可控”：
   - CLI 模式：最灵活，但对人的注意力和判断力消耗最大
   - 主控+Subagent：效率与稳定性的甜区，但极度依赖前期结构设计
   - 契约式主控：试图系统化“执行路线”，但当前阶段极易产出“伪 E2E”

4. 你在这期里点破了一个行业集体幻觉：
   - 很多人以为自己在做“系统化 AI 协作”
   - 实际只是把「无法自动化的决策」包装成了脚本和流程
   那些“看起来像 E2E 测试但根本跑不通的脚本”，本质是**逃避真实验收成本**。

5. 这期内容在你体系里的位置很关键：
   - 它是从「工具崇拜」过渡到「系统判断」的一次转向
   - 你开始公开承认：第三种模式在当前很多任务上**达不到你的预期**
   这是一次主动“去神话化 Agent”的动作。

6. 更深一层的洞察是：协作模式本身也是一种“产品设计”：
   - CLI 面向的是“高认知密度的个人”
   - 主控+Subagent 是“个人工作室”的现实最优解
   - 契约式主控更像是未来形态，而不是现阶段可普及方案
   你实际上已经在用工程视角，给“个人 AI 使用方式”做分层设计。

7. 这期视频真正的长期价值不在结论，而在方法：
   - 遇到新任务时，不再问“该用什么 prompt”
   - 而是先问：
     * 这个任务失败的代价是什么？
     * 哪一层必须由人兜底？
     * 验收是否能被明确写出来？
   这是从“用 AI”升级到“调度 AI”的分水岭。
