# 04 · 性能点位、容错矩阵与学习路径

> 前置：01-03。本篇是收官：把散落的性能与容错决策收拢成两张全景表，最后给一张按你自己的阅读原则定制的地图。
> 本篇没有新的精读文件，是对前三篇的横向重组——检验你是否真的读懂了。

## 一句话定义

性能设计回答「怎么快、怎么省」，容错设计回答「哪里会死、死了怎么办」；这个项目规模小，但它把单机 Agent 系统该有的性能点位和容错分支几乎全占齐了，每一处都便宜且有效。

## 性能点位全景

新手听到「性能」第一反应是缓存和 Redis，但单机小系统的性能点位几乎全在**索引、窗口和止损**上。逐层盘点：

### 数据层

| 点位 | 位置 | 一句话原理 |
| --- | --- | --- |
| WAL 模式 | `database.ts` PRAGMA journal_mode | 写入先进 WAL 文件不阻塞读。类比边干活边在草稿纸上记，闲时再誊清到正式账本；读的人永远看得到一致快照又不互相卡 |
| 部分索引 | `migrations.ts` idx_todos_status | 只索引未删行，索引更小、维护更便宜（01 讲过） |
| 会话消息索引 | idx_messages_conversation | messages 唯一访问模式是按会话查，索引即为此而生 |
| 软删查询永带过滤 | 所有 repo 查询 | `deleted_at IS NULL` 走部分索引，不扫死数据 |

### 链路层（真正的性能大头在 LLM，不在代码）

| 点位 | 位置 | 效果 |
| --- | --- | --- |
| system prompt 限 50 条 | `prompt.ts` CONTEXT_LIMIT | todo 一万条也不会把 prompt 撑爆；超出时告知模型用 todo_list 工具按需查——**用工具查询替代无限注入**，这是 Agent 系统控制 token 成本的标准手法 |
| 历史窗口 40 条 | `chat.ts` recentMessages(40) | 对话 300 轮也不会线性变贵；配合「倒序取 40 再反转」只读需要的行 |
| 流式即时转发 | `chat.ts` delta 逐 chunk 发 | 用户首字节等待从「整轮生成完」降到「第一个 chunk 到」，体感快一个数量级 |
| usage 落库 | assistant rawJson | 每次 token 消耗可审计，成本可算——性能可观测是优化的前提 |
| 工具轮数封顶 5 | MAX_TOOL_ROUNDS | 硬止损：最坏情况有界 |
| 断线即中止上游 | AbortController + signal 透传 | 用户关页面，对 DeepSeek 的计费请求立刻取消，不多烧一分钱 |

### 前端层（略读即可）

TanStack Query 缓存 + invalidate 模式：智能体改完数据只失效 todos 这一个 key，不重拉会话；Zustand 存聊天流状态而非服务器状态，职责分离避免重复缓存。

**纠偏**：「性能 = 加缓存」。缓存只解决「重复计算」，而这里没有重复计算（每次对话都是新请求）。单机 Agent 的性能公式是：**token 花在刀刃上（窗口+注入上限）× 响应尽早露头（流式）× 失败成本有界（止损）**。

## 容错矩阵

一张表看全「什么坏了，系统什么反应」。行是故障，列是层次。

| 故障 | 立即反应 | 用户所见 | 数据后果 |
| --- | --- | --- | --- |
| 用户 body 非法 | Zod 抛 ApiError(400) | 红色错误信封 | 无 |
| LLM 上游抛错 | catch → send error 事件 | 气泡变红「生成失败」 | 已生成部分已在轮尾落库 |
| 模型给非法工具参数 | parse 失败 → 错误对象作为 tool 消息回注 | 模型自己道歉重试 | 无脏写入 |
| 用户拒绝确认 | resolve(rejected) → skipped 回注 | 模型说「好的已取消」 | 无 |
| 确认超时 120s | resolve(timeout) → timeout 回注 | 模型解释超时，对话继续 | 无 |
| 用户中途断线 | raw close → abort 上游 + cancelAll + flush | 页面没了 | **已生成文本以 finishReason=aborted 落库**，刷新可见 |
| confirm 打错目标 | approvals.resolve 返回 false → 404 CONFIRM_MISMATCH | 明确报错 | 无 |
| 迁移失败 | ROLLBACK + 启动退出 | 服务起不来（fail fast） | 库无半成品 |
| 缺 API key | EnvSchema 校验失败退出 | 启动期明确报错 | 无带病运行 |

两个值得咀嚼的设计立场：

1. **超时/拒绝是正常流不是异常流**。没有 try/catch 包超时——它走与正常确认相同的 `tool_result` 通道回给模型。设计原则「超时不猝死」：Agent 系统里任何等待外部世界的点都可能永远不回来，把它们统统建模为「一种正常结果」比抛异常稳健得多。
2. **断线 flush 放在 finally 而非 catch**（本项目真实返工的一处）：断线有两条退出路径——上游流被 signal 中止时抛错（进 catch），上游自然结束靠 aborted 标志 break（不进 catch）。初版把 flush 写在 catch 里，break 路径就漏了。教训：**清理逻辑放 finally，让它对所有退出路径成立**。

## 行业对比：这套自研 vs 框架

| | 本项目自研 | LangChain/LangGraph | Vercel AI SDK |
| --- | --- | --- | --- |
| 核心回路 | 300 行手写 | 框架抽象（Runnable/Graph） | SDK 流式工具 |
| 可控性/可读性 | 每一行都是你的 | 需读框架源码排障 | 中 |
| 学习价值 | 高（机制全暴露） | 低（先学框架再学原理） | 中 |
| 适合场景 | 单人/小团队、核心资产 | 快速拼装多组件 | Next.js 全栈 |

判断力结论：Agent 的核心回路（组装消息 → 调模型 → 解析工具 → 执行 → 回注）本质就几百行，**先手写一遍再谈框架**，否则出问题时你在黑箱外面。这与 deepseek-harness 的研究结论一致：成熟团队的工具层全是自研薄封装，框架用在真正的外围（评测、编排、观测）。

另一个行业事实：**OpenAI 兼容协议是事实标准**。本项目 `DEEPSEEK_BASE_URL` 改成任何兼容服务的地址（含本地 Ollama/vLLM）即可换模型后端——一行配置的供应商自由，就是当初选「OpenAI SDK 直连」而非某厂商专有 SDK 的回报。

## 你的定制阅读地图

按你定的原则（跳过测试/样式、略读 UI、精读设计）排的顺序，预计一个周末：

**第 1 小时 · 图纸**：`packages/contracts/src/` 全部 7 个小文件。先看 `sse.ts` 和 `todo.ts`，它们是 02/01 的骨架。**看懂图纸再看施工。**

**第 2-3 小时 · 数据与接口**：
- 精读 `db/migrations.ts` → `repo-todos.ts` → `repo-conversations.ts`（对照 01）
- 精读 `routes/todos.ts` → `lib/http.ts`（对照 02 前半）

**第 4-5 小时 · Agent 心脏**（对照 02 后半 + 03）：
- 精读 `agent/prompt.ts` → `agent/llm.ts` → `agent/tools.ts` → `agent/approvals.ts`
- 压轴精读 `routes/chat.ts`：带着四个问题读——hijack 前后世界怎么变？toolAcc 怎么拼出完整工具调用？wait() 挂起时谁在做什么？断线的两条退出路径分别怎么走？

**第 6 小时 · 略读与串联**：
- 略读 `app.ts` / `index.ts`（组装层，看依赖注入怎么把 db/llm/approvals 串起来——这也是测试不需要真实 API key 的原因）
- 略读 `web/src/chat/store.ts`（唯一值得看的 UI 文件：六类事件怎么驱动四种渲染态）
- 跳过：`tests/`、`index.css`、其余组件

## 掌握的检验标准与下一步路径

四篇读完，用三个问题自测（答不出就回到对应篇）：

1. messages.raw_json 为什么必须存在？删掉它会失去什么？（01 事件溯源 / 03 双重校验）
2. 前端点「批准」到模型收到结果，中间经过哪几步？（03 确认回路图）
3. 断线后刷新页面，为什么能看到没说完的半句话？（04 容错矩阵 + 02 链路）

下一步学习路径（按投入产出排序）：

1. **做完 01-03 三篇的动手练习**——读十遍不如改一遍，三个练习分别覆盖迁移、接口契约、工具全链
2. **给系统加多会话管理**（会话列表 UI + 切换）：数据库已支持，纯上层数小时搞定，顺便体会「数据底座设计得好，新需求只是薄薄一层」
3. **进阶阅读**：Anthropic 的 Building effective agents（对「回路 vs 编排」的流派划分）、OpenAI function calling 文档（工具协议细节）、SQLite WAL 官方文档（并发模型）
4. **观察真实系统**：把 Claude Code 的权限确认、流式输出、断线恢复和本项目的对应物对照着看——你会发现你已经在一个 300 行的尺度上复刻了工业级 Agent 的骨架

## 结语

这个项目没有用任何「Agent 框架」，但工业级 Agent 系统的骨架要件——契约先行、事件溯源、写前确认、超时回注、断线止损、token 窗口——一个不缺。把这四篇对应的千余行核心代码读透，你得到的不只是一个 todo 应用，而是一套可以按同样思路放大到任何业务领域的 Agent 工程心智模型。
