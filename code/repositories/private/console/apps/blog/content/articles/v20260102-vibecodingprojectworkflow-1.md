# Vibe Coding初学者忽视的项目管理与开发流程（一）

- **视频 ID**：`V20260102-VibeCodingProjectWorkflow-1`
- **日期**：2026-01-02

> **一句话**：Vibe Coding 新手翻车的根因不是 AI 幻觉，而是没有“收敛系统”：没有 Done、没有 WIP、没有决策追溯。

## 精华总结
- Issue 的价值不是“把需求写长”，而是把问题写成 **可复现、可验收** 的行为描述，并刻意避开实现细节。
- 看板的本质是风险雷达：In Progress 越多，越接近自我欺骗与集体烂尾；先用 WIP=1 把熵增压住。
- Issue 三分法：行为型（新手首选）/ 能力型（必须补 Done）/ 结构型（必须拆成 sub-issues）。
- Evo 的核心价值：记录“决策如何被现实推翻”，把 lessons 写出来，否则人和 AI 下次会踩同一个坑。

## 行动清单
1. 从一个“行为型 issue”开始：写清复现步骤 + 预期行为 + 一句话 Done。
1. 强制 WIP=1：当前 issue 未验收前，不开新 In Progress。
1. 每个 issue 结束补一行 lessons：这次为什么成功/失败？下次如何避免？

- Issue 三分法：行为型（最适合新手）/ 能力型（必须补 Done）/ 结构型（必须拆 sub-issues）。
- 做任何 issue 前问 3 个问题：类型？Done 能否一句话？不做会怎样？第三个答不上来别进 In Progress。
- Evo 的核心价值：记录“决策转化过程”，尤其是实测后推翻原设计的 lessons。
- 工作流价值：任务跑 30 分钟，人盯 1 分钟；人工 patch 是工程常态不是失败。
- L0 作业：可复现 issue + 单一 In Progress + 结束写决策一句话。

## Insights（原文摘录）
1) 你在打的不是“AI 使用技巧”，而是在打“项目熵增”
- 新手项目失控，不是因为 AI 会瞎编，而是因为没人定义：什么叫 Done、什么能同时做、失败怎么回滚。
- 你把“收敛系统”这个词提出来，其实是在把隐性工程纪律显性化：这是你这期的最大差异化卖点。

2) 你这套方法的核心不是工具链，而是三条铁律
- 行为可复现（issue）
- 并发受限（WIP limit）
- 决策可追溯（Evo/lessons）
这三条能把任何“vibe 项目”从玄学拉回工程。

3) 你在视频里无意暴露了一个更关键的真相：Spec 必然会变
- #15 的关键不是“弹窗提示”这个功能，而是你发现了多窗口共享状态导致的系统性副作用。
- 这类经验如果不写进 lessons，AI 下次还会踩同一个坑；人也会。

4) 你现在的瓶颈不在“让 AI 更会写”，而在“让反馈回灌可结构化”
- 你提到 artifacts 里删文件，却不知道怎么告诉系统“不合理在哪里”。
- 这其实是在提示你下一期的主题：如何把人工验收/删改动作转化成机器可读的反馈（比如 Reject Note / Audit Delta / Failure Taxonomy）。

5) 你要小心一个观众误区：大家会以为“你这套太复杂”
- 你已经给了 L0 作业，这是对的。
- 但你需要更狠一点：强调“先守住三条铁律”，否则一切自动化都是在加速爆炸。
