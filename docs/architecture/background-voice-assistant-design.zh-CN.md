# Maka 后台语音助手设计

## 1. 产品定位

Maka 的语音功能不只是“把语音转成文字”，也不只是给现有输入框增加一个麦克风。

最终产品应是一位可以在后台持续工作的语音助手：

- 用户不想使用键盘时，可以只通过说话完成整个工作过程；
- 用户可以随时发起任务、补充要求、询问状态、处理审批和听取结果；
- Maka 可以一边执行后台任务，一边继续和用户交流；
- 当任务出现重要进展、需要用户决定或已经完成时，Maka 会主动提醒；
- 即使应用窗口不在前台，用户仍然能通过语音继续当前工作；
- 语音会话结束后，已经开始的任务仍会继续执行。

语音因此是 Maka 的一种完整交互形态，与文字界面共享同一套会话、任务、权限和结果，
而不是一条独立、能力更弱的支线。

## 2. 核心产品承诺

用户打开语音助手后，应当获得四种明确感受。

### 2.1 一直能找到它

用户可以通过固定入口、快捷键或系统级控制快速开始语音交互。应用不必始终显示在
前台，但用户必须清楚当前是否正在监听、是否正在说话、是否有后台任务在运行。

### 2.2 不用碰键盘

一个完整任务应能只用语音完成：

```text
说出需求
  → Maka 复述关键目标
  → 必要时追问
  → 用户确认
  → Maka 开始执行
  → 用户随时补充或改变方向
  → Maka 主动报告阻塞、审批和结果
```

文字界面只作为可视化补充，不应成为完成流程的必需条件。

### 2.3 可以边做边聊

后台任务执行时，语音助手不能进入长时间沉默或完全不可用状态。用户仍然可以：

- 询问当前进展；
- 修改刚才的要求；
- 暂停或取消某个任务；
- 启动另一个任务；
- 询问与任务相关的问题；
- 让 Maka 稍后再播报结果。

### 2.4 重要事情会主动回来

用户不需要反复问“完成了吗”。以下事件应该由 Maka 主动通知：

- 任务已经开始；
- 任务进入新的重要阶段；
- 任务被阻塞，需要补充信息；
- 需要用户批准某个操作；
- 任务完成；
- 任务失败或需要重试。

普通过程日志不应打扰用户。主动通知必须经过筛选、合并和优先级管理。

## 3. 使用场景

### 3.1 离开键盘时继续工作

用户正在走动、开会、查看资料或操作其他窗口，可以直接说：

- “继续检查刚才那个问题。”
- “把修改范围限制在桌面端。”
- “跑完测试以后告诉我。”
- “先不要修改，只给我结论。”

Maka 应理解这些话与当前任务的关系，而不是要求用户重新描述完整上下文。

### 3.2 发起完整任务

用户可以从一个空闲状态开始：

```text
用户：帮我检查这个项目为什么启动失败。
Maka：我会先复现启动问题，再定位失败阶段。需要我直接修改吗？
用户：先分析，确认原因后再问我。
Maka：好，我先做只读分析，有结果会告诉你。
```

语音助手负责把模糊口语整理成可执行目标，并在执行前确认关键边界。

### 3.3 管理多个后台任务

用户可能同时运行多个任务。Maka 应能回答：

- “现在有几个任务在跑？”
- “测试那个做到哪了？”
- “停止刚才的文档任务。”
- “把第二个任务改成只分析。”

每个任务都需要稳定名称或简短编号，不能长期依赖含糊的“当前任务”。

### 3.4 处理审批

当后台工作需要用户决定时，Maka 应用自然语言说明：

1. 准备做什么；
2. 为什么需要这样做；
3. 可能影响什么；
4. 用户可以选择允许、拒绝或调整范围。

用户明确回答后，Maka 再继续执行。含糊回应不能被当成高风险操作的同意。

### 3.5 听取结果

任务完成后，语音助手先播报适合听取的短结论：

```text
问题已经定位：配置文件里使用了已经失效的服务地址。
我没有修改代码。详细证据已经放在任务结果里。
需要我继续修复吗？
```

长日志、代码差异和详细报告留在界面中，不逐字朗读。用户可以继续问：

- “具体是哪一行？”
- “为什么会失效？”
- “继续修吧。”
- “把完整结论整理成文档。”

## 4. 产品形态

### 4.1 语音助手入口

建议提供三种入口：

- **应用内按钮**：适合第一次使用和查看状态；
- **全局快捷键**：应用在后台时快速开始或结束；
- **浮动控制条**：显示监听、说话、执行和静音状态。

首个版本不默认常驻监听。开始监听必须由用户明确触发。

### 4.2 最小可视界面

即使目标是只用语音，仍需要一个轻量状态面板：

- 当前是否正在监听；
- 用户和 Maka 当前谁在说话；
- 当前焦点任务；
- 后台运行任务数量；
- 待处理审批；
- 最近一次转写；
- 静音、结束和切换到文字按钮。

这个面板用于建立信任和处理异常，不要求用户持续注视。

### 4.3 工作模式

| 模式 | 行为 |
| --- | --- |
| 正常模式 | 持续对话，允许主动播报重要事件 |
| 安静模式 | 继续监听和执行，但结果只显示，不主动发声 |
| 按住说话 | 用户按住快捷键时才收音，适合嘈杂环境 |
| 仅听写 | 只把语音放入输入框，不进入持续会话 |

模式之间应由用户明确切换，不能在后台静默变化。

## 5. 完整交互循环

### 5.1 开始

启动语音助手后，Maka 用很短的提示确认已经可用，例如：

```text
我在，直接说就可以。
```

如果存在未完成任务，可以补充：

```text
上次的两个任务还在运行，需要先听进度吗？
```

### 5.2 理解

每次用户表达后，系统先判断属于哪一类：

- 普通对话；
- 新任务；
- 对已有任务的补充；
- 状态查询；
- 取消或暂停；
- 审批回答；
- 要求播报结果；
- 切换语音模式。

对明确指令直接行动；对影响范围不清晰的任务先追问。

### 5.3 确认

确认不应机械重复用户原话，而应突出执行边界：

```text
我会检查问题并运行测试，但不会修改文件。
```

简单、低风险任务可以直接开始；复杂、高风险或歧义明显的任务需要先确认。

### 5.4 执行

任务被接受后，语音助手立即给出短回应，然后把工作交给后台执行。

```text
已经开始，我会在有关键进展时告诉你。
```

语音会话保持可用，不等待后台任务完成。

### 5.5 过程交流

用户可以随时改变任务：

```text
“暂停一下。”
“只看最近的改动。”
“不要运行网络请求。”
“把这个也加入刚才的任务。”
```

Maka 应先确认指令已经送达后台任务，再向用户声明改变成功。

### 5.6 结果

任务结束后，先给出口语化摘要，再询问下一步。结果应同步保存在文字会话中，方便用户
稍后查看、复制或继续处理。

## 6. 后台工作模型

### 6.1 语音会话与任务分离

语音会话代表“用户当前正在和 Maka 交流”；后台任务代表“正在执行的一件工作”。

两者生命周期不同：

- 结束语音会话，不代表取消任务；
- 一个语音会话可以创建多个任务；
- 一个任务完成后，可以在当前或下一次语音会话中播报；
- 重新打开语音助手时，应恢复未完成任务的简短状态；
- 用户可以选择不恢复旧话题，从新的空白会话开始。

### 6.2 任务身份

每个语音创建的任务都获得：

- 简短可读名称；
- 稳定任务编号；
- 当前状态；
- 最近进展；
- 是否等待用户；
- 最终结果。

当用户说“那个测试任务”时，系统根据名称、最近上下文和当前焦点解析。仍有多个候选时，
必须追问，不能猜测。

### 6.3 当前焦点

语音会话可以有一个“当前焦点任务”，用于理解“继续”“暂停”“怎么样了”等省略表达。

焦点会在以下情况变化：

- 用户新建任务；
- 用户明确提到另一个任务；
- 当前任务进入等待用户状态；
- 当前任务结束，用户转向其他任务。

焦点只是交互便利，不替代稳定任务身份。

## 7. 主动通知方案

### 7.1 事件等级

| 等级 | 示例 | 默认处理 |
| --- | --- | --- |
| 必须立即处理 | 审批、安全风险、任务即将进行不可逆操作 | 等用户停止说话后立即播报 |
| 重要结果 | 完成、失败、阻塞 | 主动播报 |
| 阶段进展 | 已复现、已定位、正在验证 | 合并后选择性播报 |
| 普通过程 | 打开文件、运行单个命令、读取日志 | 只记录，不播报 |

### 7.2 用户忙碌时

如果用户正在说话或刚刚要求安静：

- 不抢话；
- 将重要事件放入待播队列；
- 多条同类进展合并；
- 在合适的停顿处播报；
- 安静模式下只显示通知；
- 通话结束后，未播的重要事件保留在会话中。

### 7.3 播报长度

主动播报默认控制在一到三句话：

1. 发生了什么；
2. 是否需要用户；
3. 下一步是什么。

详细信息由用户追问后再展开。

## 8. 自然对话与打断

### 8.1 轮次判断

系统需要判断用户是否真的说完，而不是仅根据固定静音时间立刻回答。短暂停顿、思考、
改口和补充都应尽量保留在同一轮表达中。

### 8.2 用户打断

用户开口时：

- Maka 立即停止当前播音；
- 开始听取新内容；
- 被打断的一般回复可以丢弃；
- 被打断的审批、失败和完成通知仍需保留；
- 用户说完后，根据新意图决定继续原话题还是切换任务。

### 8.3 Maka 主动说话

主动播报前应检查：

- 用户是否正在说话；
- 当前是否为安静模式；
- 是否已有更高优先级消息；
- 同一结果是否已经播过；
- 内容是否适合语音表达。

## 9. 语音上下文

语音助手需要三类上下文。

### 9.1 当前对话

保留近期语音交流、代词指向、用户刚刚设置的限制和当前焦点任务。

### 9.2 后台任务

从任务系统读取权威状态，包括任务是否运行、等待、失败或完成。语音模型自己的记忆
不能替代任务事实。

### 9.3 用户偏好

可以保存用户主动设置的长期偏好，例如：

- 默认语言；
- 语速和音色；
- 是否允许主动播报；
- 默认是否先确认；
- 是否允许语音审批；
- 是否保存文字转写。

原始录音不作为默认长期记忆。

## 10. 实现方案

整体可分为五个协作部分。

### 10.1 实时语音服务

负责收音、播音、轮次判断、语音打断和双向实时交流。它提供自然通话能力，但不直接执行
复杂任务。

### 10.2 语音会话服务

负责维护当前是否在通话、当前焦点任务、近期对话摘要、用户模式和重连恢复。

### 10.3 任务服务

负责创建、查询、修改、暂停和取消后台任务。所有语音指令最终都通过同一任务系统执行，
因此文字和语音看到的状态一致。

### 10.4 事件与通知服务

负责接收后台任务事件，筛选重要内容，形成适合说出来的摘要，并按照优先级进入待播队列。

### 10.5 权限与审批服务

负责识别需要确认的操作、生成明确审批问题、校验用户回答，并保证语音模式不会绕过原有
权限边界。

五部分关系如下：

```text
用户语音
  ⇅
实时语音服务
  ⇅
语音会话服务
  ⇅
任务服务 ───── 后台执行
  ⇅              │
权限与审批服务    │
  ⇅              ▼
事件与通知服务 ← 任务事件
  ⇅
主动语音播报
```

## 11. 恢复与异常处理

### 11.1 网络中断

- 明确提示连接中断；
- 已经创建的后台任务继续运行；
- 自动重连成功后恢复任务摘要；
- 未确认送达的语音指令不能被当作已经执行；
- 多次重连不能重复创建同一个任务。

### 11.2 识别不确定

涉及任务范围、删除、发送、审批等重要动作时，如果识别置信度或语义不清，应复述并确认。

普通闲聊和可撤销查询可以更自然地继续，不必频繁打断用户确认。

### 11.3 无法播音

当扬声器、耳机或语音服务不可用时：

- 任务继续执行；
- 结果写入文字会话；
- 显示系统通知；
- 提供切换到听写或文字模式的入口。

### 11.4 应用重启

应用重新打开后：

- 恢复后台任务状态；
- 不自动恢复麦克风监听；
- 提示是否继续上次语音话题；
- 保留未处理审批和未读结果。

## 12. 隐私与信任

- 麦克风监听必须有持续可见状态；
- 开始和停止监听由用户明确控制；
- 原始音频默认不保存；
- 文字转写是否保存由用户设置；
- 语音模式不扩大任务权限；
- 高风险操作必须明确确认；
- 用户可以随时查看当前运行任务和待处理审批；
- 用户可以一键结束收音，但保留后台任务；
- 结束通话和取消所有任务必须是两个不同操作。

## 13. 分阶段落地

### 第一阶段：只用语音完成单任务

实现完整的开始、追问、确认、执行、查询、修改、取消和结果播报流程。

验收重点：

- 用户无需键盘完成一个任务；
- 后台执行时仍可继续对话；
- 用户打断后立即停播；
- 任务完成会主动通知；
- 结束通话不取消任务。

### 第二阶段：后台助手体验

增加全局快捷键、后台运行、安静模式、重要事件通知、重连恢复和应用重启恢复。

验收重点：

- 应用不在前台时仍可继续语音交互；
- 网络恢复后不重复任务；
- 未播重要消息不会丢失；
- 用户可以选择何时允许主动播报。

### 第三阶段：多任务与完整控制

支持多个并行任务、稳定任务名称、焦点切换、任务列表、语音审批和任务间上下文切换。

验收重点：

- “停止测试那个”不会影响错误任务；
- 多个完成结果可以合并播报；
- 审批准确绑定到对应任务；
- 含糊指代会追问。

### 第四阶段：更强的环境理解

在用户明确授权下，增加当前窗口、选中文本、图片和其他可见上下文，使用户可以说
“看一下这个”“继续处理当前页面”，进一步减少键盘和鼠标操作。

## 14. 产品验收标准

首个正式版本至少满足：

1. 用户能从空闲状态只用语音创建一个后台任务。
2. 用户能在任务执行中只用语音追加或修改要求。
3. 用户能查询、暂停、取消和继续任务。
4. 用户能通过语音处理必要审批。
5. 用户打断时，Maka 能快速停止播音并开始倾听。
6. 任务阻塞、失败和完成时，Maka 能主动通知。
7. 语音会话结束后，任务继续执行。
8. 再次打开语音助手时，可以恢复未完成任务的简短状态。
9. 网络或应用异常不会重复执行同一条重要指令。
10. 整个流程不要求用户打开输入框或使用键盘。

## 15. 非目标

首个版本不追求：

- 默认全天候监听；
- 用语音朗读所有后台日志；
- 让用户记住复杂命令；
- 用语音绕过审批和权限；
- 把所有视觉界面完全移除；
- 同时支持无限数量的语音任务；
- 保存完整通话录音；
- 在没有明确状态提示时后台收音。

## 16. 最终产品定义

Maka 后台语音助手不是输入法，也不是一个附加的语音聊天窗口。

它是 Maka 的免键盘工作模式：

```text
用户通过语音表达目标和决定
Maka 在后台持续执行工作
双方通过自然对话保持协作
重要进展主动回到用户
完整任务状态沉淀在同一个 Maka 中
```

当用户不方便或不愿意使用键盘时，仍然可以完整地使用 Maka，而不是只能完成一小部分
操作。这应当成为语音功能的最终判断标准。
