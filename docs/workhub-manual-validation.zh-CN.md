# WorkHub 中文手工验收指南

本文用于在真实 Maka 桌面应用中验证 WorkHub 的核心体验，重点覆盖：自动建 Work 与标题生成、最近焦点与指代消解、结构化 Work 记忆、混合语义召回、置信度分级、路由纠错、筛选状态下工作、Anchor Rail，以及跨 Work 协调。

这是一份可重复执行的手工验收脚本，不要求模型回答逐字一致。判断通过与否时，应优先检查消息是否进入正确的 Work、交互是否符合预期，以及用户能否理解和纠正系统行为。

## 1. 前置条件

- 使用包含 WorkHub 实验功能的 Maka 构建，并开启 WorkHub。
- 使用真实可用的模型连接，而不是 mock 或静态演示数据。
- 至少有一个可创建 Work 的 Project；如需验证跨 Workspace 行为，准备两个以上 Workspace。
- 建议使用临时测试 Project 或无破坏性的“只分析”指令，避免误改真实工作区。
- 开始前记下当前模型、Maka 版本或提交、操作系统和测试时间。

## 2. 建立三个测试 Work

在 WorkHub 中依次发送以下三条消息。每次等到系统完成路由或创建 Work 后，再发送下一条。

### Work A：登录问题

```text
排查登录刷新令牌过期导致重复登录的问题，先只分析并列出计划，不修改文件。
```

### Work B：支付幂等性

```text
检查支付回调重复投递时的幂等性，先只分析风险和测试点，不修改文件。
```

### Work C：移动端布局

```text
优化 WorkHub 在移动端窄屏下的消息布局，先给设计建议，不修改文件。
```

建立完成后，填写实际结果。后续步骤中的 `<Work A 标题>` 等占位符均替换成这里记录的真实标题。

| 测试 Work | 实际 Project / Work 标题 | 标识色 | 是否独立创建 | 标题质量 |
| --- | --- | --- | --- | --- |
| Work A |  |  | 是 / 否 | 通过 / 失败 |
| Work B |  |  | 是 / 否 | 通过 / 失败 |
| Work C |  |  | 是 / 否 | 通过 / 失败 |

标题质量通过标准：

- 能概括工作的对象和目标，例如“修复登录重复登录”或“支付回调幂等性”。
- 中文通常为 6–16 个字；因语义需要略有浮动可以接受，但不应复制整句输入。
- 不包含“请帮我”“先分析”“不修改文件”等过程性或礼貌性措辞。
- 不以句号、问号等无意义标点结尾。
- 三条消息形成三个独立 Work，而不是混入同一个 Work 或停留为普通讨论。

## 3. 核心验收场景

每个场景执行后记录：目标 Work、实际 Work、显示的路由置信度、是否出现澄清，以及最终结果。若同一场景依赖上一场景，请按编号顺序执行。

### WH-01：明确名称路由

发送：

```text
<Work A 标题>：补充一下最容易复现问题的三个入口，仍然只分析。
```

预期：

- 消息直接进入 Work A，不新建 Work，也不要求澄清。
- Work 元信息显示 Work A 的 `Project / Work`，颜色与 Work A 保持一致。
- 问与答使用同一 Work 标识色。
- 路由应表现为高置信度；来源的内部实现可以变化，但用户不应感到系统在猜测。

### WH-02：当前焦点与“它”指代

在 WH-01 完成后立即发送：

```text
继续它，按影响程度给这些入口排个序。
```

预期：

- “它”解析为刚刚聚焦的 Work A。
- 消息直接进入 Work A，不新建 Work，不出现目标选择卡片。
- Work A 成为最近焦点；Anchor Rail 中新增对应锚点。

### WH-03：“上一个工作”指代

先用明确名称向 Work B 发送一句：

```text
<Work B 标题>：把风险按高、中、低分组。
```

确认消息进入 Work B 后，再发送：

```text
回到上一个工作，把刚才的复现入口整理成检查清单。
```

预期：

- “上一个工作”解析为切换到 Work B 之前的 Work A，而不是当前 Work B。
- 消息进入 Work A；不新建 Work，不要求澄清。
- 若产品展示置信度，应为足以直接路由的等级。

### WH-04：结构化记忆召回

先明确进入 Work C：

```text
<Work C 标题>：补充横屏模式下的注意点。
```

随后不要说 Work A 的标题，只发送：

```text
刷新令牌过期时，重复登录的观测日志应该记录哪些字段？
```

预期：

- 系统根据此前记住的实体“刷新令牌过期”“重复登录”召回 Work A。
- 消息进入 Work A，不创建标题相近的新 Work。
- 如果候选仍有竞争，允许展示中置信度并提供“更正目标”；不应无依据地路由到 Work C。

### WH-05：模糊目标与澄清

发送：

```text
继续处理稳定性问题，但我不确定具体是哪一个。
```

预期：

- 系统不武断地修改某个 Work，也不自动创建一个叫“稳定性问题”的 Work。
- 当至少两个已有 Work 都可能相关时，显示“选择目标 Work”的卡片，候选来自真实已有 Work。
- 选择某个候选后，消息仅在所选 Work 中执行。
- 已选择的卡片显示最终目标，候选按钮不可再次点击；反复返回该历史位置也不会重复执行请求。
- 低置信度不能静默直达；用户始终有明确的选择或纠正路径。

> 如果当前三个 Work 的语义差异过大，模型可能合理地把这句话保留为讨论。此时可把输入改为“继续处理重复问题”，使 Work A 的“重复登录”和 Work B 的“重复投递”同时成为候选，再验证澄清卡片。

### WH-06：路由纠错与学习

本场景使用一个临时、语义刻意模糊的代号。先在 Work A 中发送：

```text
<Work A 标题>：把“青鸟检查点”记作登录链路的最终验收步骤。
```

再明确进入 Work B，然后发送：

```text
继续青鸟检查点，列出验收项。
```

如果消息没有进入 Work A：

1. 点击该消息附近的“更正目标”。
2. 在卡片中选择 Work A。
3. 等待错误目标的执行停止，并确认请求在 Work A 重新开始。
4. 再次发送一条相近输入：

```text
继续青鸟检查点，补充失败时的回滚条件。
```

预期：

- 更正操作不会删除原消息；原路由保留可追溯状态，并标记为已停止或已更正。
- 同一请求不会同时在错误 Work 和正确 Work 中继续运行。
- 更正后的请求进入 Work A。
- 再次使用相同或高度相似的表达时，系统优先进入 Work A，体现已学习的纠错记忆。
- 如果同一类表达后来又被纠正到另一个 Work，下一条相似表达必须服从最新一次纠正，而不是较早记录。

如果第一次就正确进入 Work A，可以改用另一个新代号重复该步骤，直到实际覆盖一次纠错交互。

### WH-07：按 Work 筛选后直接工作

1. 点击 Work B 的标识色图例，或点击任意 Work B 消息侧边的主题色标记。
2. 确认时间线只保留 Work B 的内容。
3. 在不退出筛选的情况下发送：

```text
补充一组最小的幂等性回归测试用例，仍然不修改文件。
```

预期：

- 顶部清楚显示当前选择的 `Project / Work`。
- Composer 在筛选状态下默认绑定 Work B，体验与进入普通 Session 后工作一致。
- Composer 与每条 Work 元信息使用同一套权限名称和状态；例如底层为 `ask` 时，两处都显示“自动”，不能一处显示“每次询问”、另一处显示“自动”。
- 新消息和回答进入 Work B，不经过模糊路由，也不新建 Work。
- 新内容立即保留在当前筛选结果中。
- 点击“全部”后，三个 Work 的内容恢复，历史没有丢失。

### WH-08：Anchor Rail 对话导航

确保全部筛选状态下已经产生至少三个可导航锚点，然后检查屏幕最右侧的 Anchor Rail。

预期：

- Anchor Rail 的位置、尺寸和滚动行为与普通 Session 一致。
- 未悬停时保持普通 Session 的中性视觉，不形成一条过强的彩色装饰带。
- 悬停某个 Work 的刻度时，该刻度显示对应 Work 的标识色。
- 悬停摘要包含 Work 名称、用户输入摘要和回答摘要；Work 名称使用对应标识色。
- 点击刻度能跳转到正确消息，滚动页面时当前刻度同步变化。
- 普通讨论、澄清或跨 Work 协调等非单一 Work 项保持中性。
- 筛选到 Work B 后，Anchor Rail 只保留 Work B 的对话历史；取消筛选后恢复全部锚点。

### WH-09：跳转进入 Work 与返回 WorkHub

1. 点击某条 Work A 消息上方的 `Project / Work` 信息。
2. 确认进入对应的普通 Session。
3. 使用返回控件回到 WorkHub。

预期：

- 点击目标明确，进入的 Session 与消息所属 Work 完全一致。
- 普通 Session 中存在可发现的返回按钮或返回路径。
- 返回后恢复 WorkHub 的上下文；筛选状态和滚动位置应尽可能保留。
- WorkHub 与普通 Session 的消息宽度、Composer 宽度、气泡间距和基础组件视觉一致，差异仅来自 Work 标识及其元信息。

### WH-10：跨 Work 有序协调

先确保 Work A 与 Work B 都处于可继续工作的状态，然后发送：

```text
先让 <Work A 标题> 汇总登录问题的验收结论；完成后，让 <Work B 标题> 根据这份结论补充支付回调的统一监控建议。
```

预期：

- 系统创建一个“跨 Work 协调”消息块，而不是把两个工作的回答混进同一个气泡。
- 协调图包含两个节点，Work B 显示依赖 Work A。
- Work A 未完成时，Work B 为“等待前置工作”；Work A 完成后，Work B 才开始。
- 每个节点继续使用自身的 Work 身份、权限模式和状态。
- 完成、失败、等待用户或停止均有低噪音状态提示。

### WH-11：Waiting for you 时继续发送

1. 让 Work A 触发一张权限或问题交互卡片，并保持“等待你的决定”状态。
2. 筛选到 Work A，在未处理卡片前输入一条新请求并尝试发送。

预期：

- 不出现 `Session already has an active or pending root Turn` 等内部错误。
- WorkHub 明确提示这项 Work 仍有待处理决定，并引导用户先完成交互卡片。
- 新请求没有被送入第二个 root Turn，Composer 草稿仍保留，用户处理决定后可以再次发送。
- 如果该状态出现在澄清选择之后，澄清卡片保持可操作，不被误标成已经执行。

## 4. 跨 Workspace 补充验证

如果有两个以上 Workspace，再执行以下场景：

1. 在 Workspace X 创建一个关于“搜索索引”的 Work。
2. 在 Workspace Y 创建一个关于“登录索引”的 Work。
3. 回到 WorkHub，通过完整 `Project / Work` 名称明确进入二者各一次。
4. 再用“搜索索引”“登录索引”等实体分别继续工作。

预期：

- WorkHub 能召回不同 Workspace 中的 Work。
- 消息元信息以简洁的 `Project / Work` 告知当前工作归属，不因完整 Workspace 或 gittree 名称过长而破坏布局。
- 需要更完整 Workspace 信息时，可在其他位置查看，但气泡上方不应被长路径挤占。
- 当用户描述的目标不属于现有 Workspace 时，系统先询问是否开启新 Workspace，而不是擅自创建。

## 5. 全局视觉与交互检查

在以上场景中一并检查：

- WorkHub 对话正文和底部 Composer 使用与普通 Session 相同的阅读宽度。
- 工作元信息按“工作（Project / Work）→ 权限 → 状态”的顺序平行排列。
- 元信息紧贴气泡上方，字号较小但可读，不抢正文层级。
- 同一 Work 的用户消息和助手消息使用同一种标识色。
- 颜色主要用于侧边标识、文字或交互反馈，不用大面积填充气泡。
- 侧栏中对应 Session 使用相同标识色，帮助建立 WorkHub 与 Session 的统一认知。
- 用户消息刚发出、尚未完成路由判断时保持普通颜色；识别目标后再切换为 Work 色。
- 处理中显示轻量状态；完成后有可感知但不过度打扰的提示。
- 权限选择沿用普通 Session 的权限机制，并允许在 WorkHub 内改变目标 Work 的权限模式。
- 所有澄清、权限和纠错交互均可只用键盘完成，并具有清楚的焦点状态和可访问名称。

## 7. 最低通过门槛

本轮 WorkHub 手工验收通过需同时满足：

- WH-01、WH-02、WH-03、WH-07、WH-09 必须全部通过。
- WH-04 至少能正确召回或给出合理澄清，不能静默进入明显错误的 Work。
- WH-05 的低置信度路径必须可控，不能擅自执行有副作用的操作。
- WH-06 必须完成一次真实纠错，并验证相似表达的后续路由得到改善。
- WH-08 的跳转目标和筛选后锚点集合必须正确。
- WH-10 必须遵守依赖顺序，后置 Work 不能抢跑。
- WH-11 必须以用户可理解的提示阻止第二个 root Turn，且不得丢失待发送草稿。
- 不得出现消息丢失、错误 Work 持续执行、权限模式绕过或不可逆历史破坏。
