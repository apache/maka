# Windows Direct2D / GPUI comparison — 2026-11-02

These measurements describe the pre-review revisions below, not the later
review fixes. Windows now uses only Direct2D; GPUI is the historical baseline,
not a selectable Windows backend. No new performance run is claimed here.

## Setup

- Windows 11 Pro, build 26200; Intel Core i5-12450HX, 12 logical processors, 32 GiB RAM, Intel UHD Graphics.
- Both shells use Cargo's release profile, from merge commit `cca8264fd` (upstream `22e92bb2a`). Follow-up changes add a focus regression test, lint cleanup and documentation, without changing rendering behavior.
- Same debug Host/CLI executable for both backends; SHA-256 `d1c03348649fb54931d87b569794857d1d673c0aae8efac5b7dbdba65520d9ee`.
- Both request a 1280 × 820 window; platform decorations differ. Empty independent Roots, the normal fully loaded workbench, no model connections or inference.
- Five trials per backend, alternating order between rounds. After the window becomes visible, wait eight seconds and sample the shell every 200 ms for twenty seconds. Report the median across each trial's averages. The machine was an interactive desktop, not an isolated lab runner.
- Visibility is a Win32 window observation, not a measured first-contentful-frame timestamp. Shell startup begins at the shell process's creation, excluding Host admission.

## Five-trial results

| Metric | Direct2D median (range) | GPUI median (range) |
| --- | --- | --- |
| Shell process to visible window | 1.270 s (1.186–1.820) | 1.724 s (1.617–1.891) |
| Working set | 140.16 MiB (137.51–141.10) | 173.05 MiB (170.64–180.39) |
| Private bytes | 118.22 MiB (115.51–118.45) | 146.71 MiB (144.52–149.12) |
| Idle CPU, one logical core = 100% | 3.17% (2.24–10.38) | 8.20% (6.73–18.10) |
| Process exits within 10 s of WM_CLOSE | 5 / 5 | 1 / 5 |

The four GPUI close timeouts required terminating the test-owned process before continuing; this reference-build shutdown observation remains unresolved. It is not a Direct2D rendering failure.

Host residency differed after closing each backend, so the launcher-to-window numbers from these trials are **not** a fair end-to-end startup comparison.

## Controlled cold startup

Three additional trials per backend each use a brand-new Root, the same Host executable, no warmup delay and no idle-resource sampling. Order alternates as above.

| Metric | Direct2D median (range) | GPUI median (range) |
| --- | --- | --- |
| Launcher start to visible window, including new Host/Root admission | 15.707 s (15.697–17.041) | 15.598 s (14.935–15.606) |
| Shell process to visible window | 1.352 s (1.260–1.374) | 1.426 s (1.351–1.477) |

The measurements support a smaller steady-state memory footprint in this workload, not a claim of significantly faster end-to-end startup. CPU varies substantially. No FPS, GPU utilization, frame-time percentiles, long-history scrolling, streamed replies, or model inference was measured.

## Functional verification

- Normal workbench loads in both release shells.
- Direct2D: settings modal opens; Unicode text entry and filtering work; workspace picker opens the native folder dialog, and cancellation restores interaction.
- Windows backend: 151 unit tests pass, including the non-input Tab-focus regression test. Removing non-input focus stops makes that test fail.
- At the measured revision, six desktop-shell tests pass with the then opt-in Direct2D backend; Windows backend strict Clippy passes; four Mermaid/Pele tests pass after `npm ci`.
- Initial builds made without the newly added npm dependency `pele` displayed the same runtime import error in **both** backends. Installing locked dependencies and rebuilding the CLI's embedded plugin bundles resolved it; those error screens were excluded from the measurements.

After synchronizing the Rust dependency inventory, `cargo-deny` 0.20.2 and `node scripts/rust/dependencies.mjs check` passed. The full repository check was not completed: the local notice check reports a license-data digest mismatch for the unchanged pinned Git dependency `clipboard-rs@0.3.5`.

Raw per-process samples and the local PowerShell measurement harness are retained in the testing worktree under `.nsh/backend-comparison/`, separate from product source.
